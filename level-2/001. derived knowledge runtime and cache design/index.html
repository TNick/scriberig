    Derived Knowledge Runtime and Cache Design¶

    1. Purpose¶

    This document translates design/level-1/008. derived knowledge caching and incrementality.md into a reusable Rust subsystem.

    The subsystem owns the domain-independent mechanics required to:

    • describe derivations from exact immutable inputs;
    • build stable derivation keys;
    • record exact object and scope dependencies;
    • store and retrieve immutable derived results;
    • choose among multiple compatible results;
    • model freshness for external observations;
    • model retention without accidentally pinning canonical history;
    • find derived results affected by semantic changes;
    • explain reuse and recomputation decisions;
    • expose derived-state events separately from canonical snapshot events;
    • let domain adapters register meaningful derivations without implementing private cache systems.

    This design does not make derived state canonical. Cache population, eviction, index rebuilds, and preferred-result changes must not advance canonical snapshots.

    Concrete SQL schemas, distributed cache protocols, model-provider integrations, compiler integrations, HTTP payloads, UI components, and domain-specific derivation algorithms are outside this design.

    2. Architectural Position¶

    The universal graph design already defines a generic derived artifact and explicitly does not implement a cache. This design continues from that boundary.

    The dependency direction is conceptually:

    shared core identities/provenance
          |
          v
universal graph derived-artifact model
          |
          v
scriberig-derive
          |
          +----> domain adapters register derivations
          +----> app/runtime consume derivation services
          +----> protocol adapters translate derivation events

    The repository-wide workspace design currently uses the scriberig-* crate naming convention. Some earlier persistence designs use the provisional sr-* prefix.

    Implementation must inspect the actual workspace and use its canonical naming convention. There must be exactly one derivation/cache crate. If the workspace has standardized on sr-*, create or extend sr-derive rather than creating a competing scriberig-derive crate.

    For the remainder of this design, scriberig-derive means that one canonical derivation crate.

    The derivation crate may depend on:

    • the shared core identity/provenance crate;
    • the universal graph crate;
    • narrowly required storage abstractions if they already exist as backend-independent traits.

    It must not depend on:

    • an agent runtime;
    • a model provider;
    • a concrete SQLite driver;
    • HTTP or WebSocket frameworks;
    • CLI, TUI, or web UI crates;
    • Markdown-, Rust-, PDF-, or session-specific code.

    3. Files Prescribed by This Design¶

    Create one reusable derivation crate if it does not already exist.

    Target layout:

    crates/scriberig-derive/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── profile.rs
│   ├── key.rs
│   ├── dependency.rs
│   ├── result.rs
│   ├── repository.rs
│   ├── selection.rs
│   ├── freshness.rs
│   ├── retention.rs
│   ├── invalidation.rs
│   ├── explain.rs
│   ├── event.rs
│   └── registry.rs
└── tests/
    └── derived_knowledge.rs

    If equivalent modules already exist in the canonical workspace, extend them rather than creating parallel implementations.

    Update the root workspace manifest only as required to register the one derivation crate.

    Do not create domain adapter files, server endpoints, agent tools, or UI files as part of this design.

    4. Reuse Existing Universal Types¶

    Do not redefine concepts already owned by lower layers.

    Reuse existing equivalents of:

    EntityId
RevisionId
SnapshotId
StyleId or exact style revision reference when present
EntityRevisionRef
Provenance
DerivedArtifact

    If DerivedArtifact has not yet been implemented in the universal graph crate, that is a prerequisite. The derivation crate must not create a second incompatible graph artifact model merely to proceed.

    The derivation layer adds cache/derivation semantics around those universal objects.

    5. Derivation Profiles¶

    profile.rs defines exact derivation semantics.

    A derivation profile identifies what computation is being requested, independently of one invocation.

    Examples include:

    function-summary/v1
markdown-section-description/v2
rust-pretty-print-ir/v3
symbol-reference-index/v1
semantic-diff/v2
agent-context-fragment/v4

    A profile must be versionable. Changing behavior that can change the meaning or output compatibility of a derivation must produce a distinct profile/version identity.

    A profile may carry:

    • stable kind/name;
    • exact version or revision identity;
    • optional producer/implementation identity;
    • configuration identity when that configuration affects semantics;
    • scheduling hints such as eager or lazy preference.

    Do not use a mutable string such as "current" as the exact cache identity.

    Human-facing aliases may resolve to an exact profile, but exact reuse uses the resolved profile identity.

    6. Derivation Keys¶

    key.rs defines the lookup identity for a derivation request.

    A DerivationKey must encode every input whose change can alter result meaning.

    Conceptually:

    DerivationKey {
    profile,
    direct_dependencies,
    scope_dependencies,
    configuration_dependencies,
    freshness_input_if_required,
}

    The representation must be deterministic.

    Two keys compare equal only when they describe the same compatible derivation request.

    Do not key exact reuse only by EntityId.

    Do not automatically include the global snapshot in every key. Include it only when the derivation genuinely depends on whole-scope state.

    7. Dependency Model¶

    dependency.rs defines domain-independent dependencies.

    The dependency model must distinguish at least:

    7.1 Exact revision dependencies¶

    The result depends on one exact immutable entity revision.

    Entity F @ Revision R7

    7.2 Snapshot dependencies¶

    The result depends on the complete canonical state represented by a snapshot or explicitly scoped snapshot.

    Use this for genuinely global derivations or conservative early implementations.

    7.3 Collection or scope dependencies¶

    The result asserts completeness or absence over a collection/scope.

    Examples:

    all callers of F
all implementations of trait T
all paragraphs containing X
no diagnostics in module M

    The dependency must change when membership relevant to the assertion can change, even if the positive result members do not.

    7.4 Configuration dependencies¶

    Examples include:

    • style revision;
    • compiler/toolchain configuration;
    • feature configuration;
    • schema version;
    • adapter version;
    • model/prompt policy identity.

    Use exact identifiers or deterministic value identities. Do not hide semantically relevant configuration in process globals.

    7.5 Derived-result dependencies¶

    A derived result may depend on other immutable derived results.

    This enables hierarchical reuse such as function summaries feeding module summaries.

    Dependency types must remain extensible without hard-coding every domain.

    8. Derived Result Record¶

    result.rs defines runtime/cache metadata around the universal graph's derived artifact model.

    A stored result must identify conceptually:

    derivation key
immutable artifact/result reference
status
provenance
creation/observation metadata when relevant
freshness metadata when relevant
validation metadata when relevant

    The result record does not make the artifact canonical.

    A failure may also be represented as a result when caching the failure is useful and policy permits it.

    Failure records must distinguish retryable/transient failures from failures that are deterministic for immutable inputs.

    The result representation must permit multiple results for compatible subjects/profiles rather than one mutable cache row that is overwritten forever.

    9. Repository Abstraction¶

    repository.rs defines a backend-independent persistence/query contract for derived knowledge.

    The contract must support at least:

    put immutable derived result
lookup results by exact derivation key
lookup derived results related to an entity/revision
record dependency metadata
lookup reverse dependencies
remove disposable result metadata/artifacts
inspect result provenance

    The repository abstraction must not expose SQL.

    A backend may store canonical and derived data in the same physical database, but the API must preserve lifecycle separation.

    This design does not require a durable backend implementation yet. The conformance tests may use a small in-memory implementation local to tests or an existing backend-neutral memory facility if one already exists.

    A later persistence integration may map this contract onto the canonical database without changing derivation semantics.

    10. Result Selection¶

    selection.rs separates exact identity from convenience selection.

    Exact lookup asks:

    Do we have a result for this exact DerivationKey?

    Selection may ask:

    What is the preferred current summary for F@R7?
What is the newest fresh external observation for source X?
What is the cheapest compatible summary?
What is the latest successful validation for snapshot S?

    Selection policy must not mutate historical results.

    Preferred-result pointers or indexes are derived selection metadata. Changing them does not advance canonical snapshots.

    Selection results should explain which candidate was chosen and why when requested by diagnostics/debugging tools.

    11. Freshness¶

    freshness.rs models derivations whose validity includes time-varying external state.

    Local immutable revision derivations normally do not expire merely because time passed.

    External observations may require:

    • source identity;
    • observation time;
    • optional source revision/validator;
    • freshness deadline or policy;
    • revalidation metadata;
    • retry-after or failure freshness rules.

    Freshness is separate from immutable historical truth.

    An observation can remain historically exact after it becomes too old to satisfy a request for current information.

    The freshness model must permit source-specific policy without embedding web-specific concepts into the universal crate.

    12. Retention¶

    retention.rs defines the lifecycle strength of derived artifacts.

    At minimum distinguish concepts equivalent to:

    disposable cache
expensive reusable artifact
historical evidence
pinned derived artifact

    Dependency references from disposable cache entries must not automatically act as strong roots that keep all historical canonical revisions alive forever.

    Retention policy must be separate from validity.

    A result can still be valid but eligible for eviction because it is cheap to recompute.

    A result can be retained for audit/history even if it is no longer the preferred current result.

    13. Reverse Dependencies and Invalidation¶

    invalidation.rs defines how semantic changes identify affected derivations.

    Given a set of changed exact revisions, structures, scopes, configuration revisions, or snapshots, the system must be able to find derivation records whose declared dependencies may no longer match.

    Invalidation means:

    this result must not satisfy a request whose required dependency state differs.

    It does not necessarily mean immediate deletion or recomputation.

    The result may remain stored as a correct historical artifact for its original inputs.

    The API should support a conceptual outcome such as:

    Unaffected -> reuse
Affected   -> miss for new state; recompute if/when policy requests

    Do not invalidate semantic results because a file timestamp changed when reconciliation preserved the same semantic revisions.

    14. Explainability¶

    explain.rs defines structured diagnostic reasons for cache decisions.

    The system should be able to represent explanations such as:

    ReuseReason:
  exact derivation key matched

MissReason:
  no compatible result exists

RecomputeReason:
  dependency Type T changed R5 -> R6

FreshnessReason:
  external observation expired

SelectionReason:
  preferred profile resolved to profile P7

    Use machine-readable reason codes plus human-readable context.

    Do not reduce explanations to log strings only.

    The same explanation objects may later be rendered by CLI, server, web, TUI, and agent surfaces.

    15. Derived Events¶

    event.rs defines domain-level events that higher runtime/protocol layers can translate.

    At minimum support equivalents of:

    DerivationStarted
DerivedResultAvailable
DerivationFailed
DerivedResultSelected
DerivedResultEvicted
DerivedResultInvalidatedForState
IndexUpdated

    These events must be distinct from canonical events such as:

    CanonicalSnapshotChanged

    The derivation crate owns event semantics, not transport encoding.

    Do not add HTTP/WebSocket types here.

    16. Derivation Registry¶

    registry.rs lets domain adapters declare derivations without each adapter inventing its own cache mechanics.

    A registration should conceptually describe:

    • derivation profile/kind;
    • accepted input/scope kinds;
    • dependency discovery strategy;
    • eager versus lazy policy hint;
    • freshness behavior if any;
    • retention default;
    • producer/implementation version identity;
    • optional cost information.

    The registry must not require an agent runtime.

    A Markdown, Rust, PDF, session, or future domain adapter should be able to use the same contracts.

    Execution of domain-specific derivation code may be synchronous or asynchronous in later designs. This Level 2 design defines registration and identity, not a mandatory task scheduler or async runtime.

    17. Eager Versus Lazy Policy¶

    Eager and lazy are scheduling policy, not validity semantics.

    The same exact derivation key and result type must remain valid regardless of whether the result was precomputed or requested on demand.

    The first implementation should support policy metadata sufficient to distinguish:

    Lazy
Eager

    without introducing a background scheduler unless another design already provides one.

    The cache model must be useful in embedded/library-only applications that have no server and no agent runtime.

    18. Concurrency¶

    Concurrent requests for the same exact derivation key should not corrupt state or produce ambiguous identity.

    The architecture permits more than one immutable result for nondeterministic derivations, but duplicate deterministic work should be avoidable by higher execution layers when practical.

    The repository contract must remain correct if two workers finish compatible derivations concurrently.

    Selection policy, not mutation of old results, decides which artifact is preferred.

    Do not make process-local locks part of persistent semantic identity.

    19. Domain Boundaries¶

    The universal derivation crate must not hard-code derivation types such as:

    RustTypeCheck
MarkdownSummary
PdfExtraction
SessionBranchSummary

    Profiles and adapter registration carry domain meaning.

    Domain adapters may use the universal engine for:

    • compiler/static analysis;
    • render intermediates;
    • descriptions/summaries;
    • extracted document structure;
    • semantic diffs;
    • agent context fragments;
    • validation results;
    • search/index materialization.

    The universal crate provides mechanics, identity, dependency, lifecycle, and observability.

    20. Canonical Promotion Is Outside Cache Mutation¶

    The derivation subsystem may expose enough provenance to support promotion, but it must not silently promote derived results.

    Promotion is a canonical migration handled by the normal change system.

    Conceptually:

    DerivedResult D
    |
    | explicit acceptance
    v
canonical entity/revision
    |
    v
new canonical snapshot

    The derivation repository remains unchanged in authority even if the promoted canonical object points back to D for provenance.

    21. Persistence Shape¶

    A durable backend should be able to represent the derivation layer conceptually as four independent concerns:

    immutable derived results
exact derivation-key -> result lookup
result -> dependency metadata
reverse dependency -> affected result lookup

    Additional mutable derived metadata may include:

    preferred-result selection
retention/pinning state
freshness/revalidation state

    These structures are outside canonical snapshot identity.

    The physical backend may use tables, key/value namespaces, indexes, or another representation. It must preserve the same logical contracts.

    Do not require one database transaction to advance a canonical snapshot merely because a derived result was inserted.

    22. Public API Shape¶

    Exact names may evolve, but the crate should expose concepts equivalent to:

    DerivationProfile
DerivationKey
Dependency
DependencySet
DerivedResultRecord
DerivedRepository
SelectionPolicy
FreshnessPolicy
RetentionPolicy
InvalidationSet
ReuseExplanation
DerivationEvent
DerivationRegistry

    Prefer small explicit types over large maps of untyped strings.

    Public APIs should make exact identity and lifecycle distinctions obvious.

    23. Conformance Tests¶

    tests/derived_knowledge.rs must cover at least these scenarios:

    1. identical exact inputs and profile produce equal derivation keys;
    2. changing one exact revision changes the derivation key;
    3. changing unrelated global state does not change a local derivation key;
    4. a global/snapshot derivation changes key when its snapshot changes;
    5. a completeness query can depend on scope independently of positive result members;
    6. multiple immutable results can coexist for nondeterministic derivations;
    7. preferred-result selection can change without a canonical snapshot operation;
    8. an external observation can be historically retained but no longer satisfy freshness policy;
    9. reverse dependency lookup identifies an affected result;
    10. an unaffected result remains reusable after an unrelated semantic change;
    11. formatting/style dependency invalidates rendering without invalidating semantic summary dependency;
    12. disposable cache dependencies do not imply strong canonical retention;
    13. derived failure policy distinguishes deterministic failure from retryable transient failure;
    14. derived events are distinct from canonical snapshot events;
    15. a domain-like test registration can declare a custom derivation without adding a production enum variant.

    Tests should use test schemas/profile names only. Do not introduce production domain vocabulary.

    24. Documentation Requirements¶

    Public module documentation must explain:

    • canonical versus derived lifecycle;
    • exact revision-based reuse;
    • why global snapshots are not the default local cache key;
    • scope/absence dependencies;
    • freshness versus historical immutability;
    • retention versus validity;
    • selection versus identity;
    • why cache operations do not advance canonical snapshots.

    The crate-level documentation should state clearly that the derivation subsystem is useful without agents, servers, or a UI.

    25. Completion Criteria¶

    Implementation status: complete. The canonical implementation is scriberig-derive; its repository, selection, freshness, retention, invalidation, explanation, event, and registration modules are covered by unit and conformance tests. Application-level authorization wraps this backend-neutral contract without adding product dependencies to the crate.

    This Level 2 design is implemented when:

    • [x] one canonical derivation/cache crate exists and is registered in the workspace;
    • [x] derivation profiles and deterministic keys are represented explicitly;
    • [x] exact, scope, snapshot, configuration, and derived-result dependencies are supported;
    • [x] derived result records retain provenance and immutable identity;
    • [x] a backend-independent derived repository contract exists;
    • [x] multiple compatible results can coexist;
    • [x] selection policy is separate from exact identity;
    • [x] freshness is explicit for external observations;
    • [x] retention is independent of validity;
    • [x] reverse-dependency invalidation works without deleting historical artifacts;
    • [x] reuse/miss/recompute decisions can be explained structurally;
    • [x] derived events are separate from canonical snapshot events;
    • [x] domain derivations can be registered without hard-coded domain variants;
    • [x] conformance tests demonstrate local reuse plus global certainty;
    • [x] no agent runtime, concrete database driver, HTTP server, CLI, TUI, or UI dependency was introduced.

    26. Level 3 Work Decomposition¶

    Create focused implementation instructions in this order:

    1. scaffold the canonical derivation crate and implement profiles, dependency types, and deterministic derivation keys;
    2. implement immutable result records and the backend-independent derived repository contract;
    3. implement result selection, freshness, failure, and retention policy types;
    4. implement reverse-dependency invalidation and structured reuse/recompute explanations;
    5. implement derivation events and the domain registration contract;
    6. add the conformance test suite, crate documentation, and workspace validation.

    Each implementation task must inspect the actual workspace first and extend canonical crates rather than duplicating a provisional sr-* versus scriberig-* naming variant.
