    Universal Knowledge Model Rust Libraries¶

    1. Purpose¶

    This document translates design/level-1/002. universal knowledge model.md into reusable Rust model libraries.

    It is intentionally limited to the domain-independent semantic vocabulary required for entities, properties, typed relations, collections, schemas, provenance, descriptions, derived knowledge, and snapshot-bound graph inspection.

    This design does not own repository bootstrapping, identity generation, content addressing, snapshot-map persistence, database backends, migrations, domain parsers, projections, agents, transports, or UI.

    Those concerns are defined by other design lineages and must be treated as prerequisites or later layers rather than reimplemented here.

    2. Prerequisites and Ownership Boundaries¶

    Before implementing this design, the repository-wide Rust workspace and the shared identity types must already exist.

    In particular, this work consumes existing equivalents of:

    EntityId
RevisionId
SnapshotId
TypeId or EntityTypeId

    It must not redefine how those IDs are generated, hashed, serialized canonically, or persisted.

    The repository-wide workspace design currently names the relevant crates:

    scriberig-core
scriberig-schema
scriberig-graph

    If prerequisite implementation work has already instantiated the same architectural crates under an equivalent established name, implementation agents must extend the existing canonical crate rather than create a duplicate crate with another prefix.

    The rule is:

    There is one shared core identity crate, one universal schema crate, and one universal graph crate in the workspace. This design adds model functionality to those layers; it does not fork them.

    3. Files Prescribed by This Design¶

    Within the already-established shared core crate, add the universal value/provenance modules if they do not already exist:

    src/value.rs
src/provenance.rs

    Within the universal schema crate, create:

    src/lib.rs
src/entity.rs
src/property.rs
src/relation.rs
src/collection.rs
src/validation.rs

    Within the universal graph crate, create:

    src/lib.rs
src/revision.rs
src/relation.rs
src/collection.rs
src/description.rs
src/derived.rs
src/view.rs

tests/universal_model.rs

    If a prescribed file already exists because another prerequisite design created the crate skeleton, modify that file instead of creating a competing module.

    Do not create a new root Cargo.toml or a second core/store crate as part of this design.

    4. Dependency Direction¶

    The model-layer dependency direction remains:

    shared core
   ↑
   ├──────── universal schema
   │
   └──────── universal graph
                 ↑
                 └── schema definitions

    The universal schema layer depends on the shared core types.

    The universal graph layer depends on shared core types and schema contracts. It may also consume storage-facing traits from the established store layer where snapshot resolution requires them, but graph semantics must not become tied to one database backend.

    None of these model modules may depend on:

    • an agent runtime;
    • an HTTP framework;
    • a CLI or TUI crate;
    • a UI toolkit;
    • a Markdown/Rust/PDF/session parser;
    • a concrete database driver merely to represent semantic values.

    5. Shared Core Additions¶

    5.1 Universal property values¶

    Add a domain-neutral property value representation capable of representing at least:

    null
boolean
signed integer
unsigned integer
floating-point number
string
bytes
list of values
string-keyed record/map

    This value type is for local property payloads.

    Do not use it to hide semantic entity relationships that should be represented as typed relations or collections.

    Do not add domain-specific variants such as RustExpression, MarkdownParagraph, PdfPage, or SessionBranch.

    5.2 Canonical versus derived classification¶

    Provide one shared classification vocabulary for distinguishing canonical semantic state from derived knowledge.

    The concrete type may be named KnowledgeClass, DataClass, or another clear equivalent, but it must at least express:

    Canonical
Derived

    5.3 Provenance¶

    Add reusable provenance data capable of recording:

    • origin/source kind;
    • optional producer identity;
    • exact entity/revision dependencies when known;
    • optional profile/configuration identity;
    • optional human-readable note.

    Source kinds must support known categories such as user, authoritative import, parser, compiler, static analysis, agent, model-generated output, system, external tool, and migration, while remaining extensible.

    Provenance records origin, not trust policy.

    Do not add authorization or trust scoring to this layer.

    6. Universal Schema Library¶

    The schema library defines how domains add strong meaning to the universal graph without changing storage architecture.

    It must not contain concrete production schemas for Markdown, Rust, PDF, sessions, or any other domain.

    6.1 Entity type schemas¶

    An entity type schema must support:

    • entity type identifier;
    • human-readable name;
    • optional description;
    • schema version association;
    • declared properties;
    • declared relation types;
    • declared collection types.

    6.2 Property schemas¶

    A property schema must represent:

    • property key;
    • expected value shape;
    • required versus optional;
    • canonical versus derived classification where applicable;
    • small schema-level constraints;
    • optional description.

    The value-shape system should cover the universal value variants without becoming a general-purpose type language.

    6.3 Relation schemas¶

    A relation schema must represent:

    • relation type identifier;
    • semantic name;
    • permitted source entity types;
    • permitted target entity types;
    • canonical versus derived classification;
    • cardinality;
    • optional description;
    • whether reverse navigation is expected to be derived/index-backed.

    Reverse edges must not be required as duplicated canonical state.

    6.4 Collection schemas¶

    Collections are modeled separately from generic relations because sequence semantics matter.

    A collection schema must represent:

    • collection type identifier;
    • owner entity type;
    • permitted member entity types;
    • ordered versus unordered semantics;
    • cardinality constraints;
    • canonical versus derived classification;
    • optional description.

    6.5 Validation contracts¶

    Schema validation must return structured issues rather than plain strings.

    A validation issue must contain at least:

    • severity;
    • stable machine-readable code;
    • human-readable message;
    • optional semantic location such as entity/property/relation/collection.

    The schema crate must not depend on the graph crate merely to validate graph-shaped data. Define a small validation-subject/context trait using shared core types; graph revision records can implement that trait from the graph side.

    Schema validation covers schema-level structure only. Parser validity, compiler validity, tests, and product policy belong elsewhere.

    7. Universal Graph Library¶

    The graph library provides immutable semantic revision records and snapshot-bound read contracts.

    It must not become a persistence backend.

    7.1 Revision record¶

    A universal semantic revision record represents one exact entity state and includes, conceptually:

    entity type
property values
owned canonical relation values
owned canonical collection values

    It must not require:

    • mutable parent pointers;
    • database row IDs;
    • a database connection;
    • reverse-edge caches;
    • current-snapshot mutable state;
    • file paths as semantic identity.

    Exact RevisionId generation remains owned by the identity/storage design.

    7.2 Relation values¶

    A relation value identifies a typed semantic relation and target entity handles.

    Targets are semantic entities, not filenames or line numbers.

    Derived relations such as compiler-computed call edges may be stored as derived knowledge rather than silently inserted into canonical revision payloads.

    7.3 Collection values¶

    Ordered and unordered collections must be semantically distinct.

    Requirements:

    • ordered collections preserve order exactly;
    • unordered collections do not expose incidental insertion/storage order as meaning;
    • members use semantic entity handles;
    • moving a member changes collection state but does not require changing the member entity identity;
    • child entities do not require parent pointers for containment.

    7.4 Descriptions¶

    Descriptions are navigation objects that bind to an exact entity revision and contain:

    • description profile;
    • provenance;
    • textual content;
    • optional information-cost metadata.

    Generated descriptions are derived knowledge by default and must not silently become canonical entity content.

    7.5 Derived artifacts¶

    A generic derived artifact must identify:

    • artifact/profile kind;
    • exact immutable input dependencies;
    • producer/configuration identity;
    • provenance;
    • result payload or result reference;
    • status/validation metadata where useful.

    The exact dependency list is essential for later incremental reuse.

    This design does not implement a cache.

    7.6 Snapshot-bound graph view¶

    Define a storage-independent read interface that can, conceptually:

    resolve an entity to its revision in a snapshot
read a revision
inspect properties
follow owned relations
read collections
obtain reverse relations through an index/view abstraction
obtain schema information

    Operations that depend on entity state must be explicitly snapshot-bound. Do not introduce ambiguous implicit-current-state APIs as the universal contract.

    Universal search, history, diff, migrations, and writes are outside this design.

    8. Canonical Versus Derived Data¶

    The implementation must keep canonical and derived knowledge visibly distinct.

    Canonical data participates in semantic snapshots and history.

    Derived data is computed from canonical data or external evidence and records exact dependencies and provenance.

    Do not simplify the model by inserting these directly into canonical revision payloads by default:

    • model-generated descriptions;
    • summaries;
    • compiler call graphs;
    • reverse indexes;
    • cached render output;
    • validation runs;
    • embeddings.

    9. No Hard-Coded Domain Vocabulary¶

    Production universal libraries must not define enums or structs whose variants hard-code domain types such as:

    MarkdownSection
RustFunction
PdfPage
SessionBranch

    Domain crates will provide schemas and adapters later.

    Examples with Document, Section, and Paragraph are allowed inside tests and documentation only.

    10. Conformance Tests¶

    The graph library integration test tests/universal_model.rs must demonstrate the Level 1 invariants without requiring SQLite, networking, parsers, or an agent runtime.

    Required scenarios:

    1. one conceptual entity can be represented at two exact revisions without changing its entity identity;
    2. one entity resolves to different revisions in two snapshots through a test/mocked view;
    3. ordered collection order is preserved and reordering changes only collection state;
    4. unordered collection semantics do not depend on insertion order;
    5. a child revision does not need a canonical parent pointer;
    6. a typed relation is validated against a test schema;
    7. invalid property/relation structure yields machine-readable validation issues;
    8. a description binds to an exact entity revision with provenance;
    9. a derived artifact exposes exact dependency revisions;
    10. domain names used by the test come from the test schema, not hard-coded production variants.

    11. Documentation Requirements¶

    Public modules and types must document semantic purpose and important exclusions.

    In particular, generated API documentation should make clear:

    EntityId   = conceptual continuity
RevisionId = exact immutable state
SnapshotId = exact consistent graph view

    The universal-model modules consume these identities but do not redefine their generation semantics.

    Documentation must also make clear that:

    • relation direction is canonical ownership/meaning, while reverse navigation may be derived;
    • ordering is a collection semantic;
    • descriptions and derived artifacts carry provenance;
    • these libraries remain useful without an agent runtime.

    12. Completion Criteria¶

    Implementation status: complete. The shared scriberig-core, scriberig-schema, and scriberig-graph crates provide the universal model; their cross-layer conformance tests verify identity, provenance, ordering, relations, derived dependencies, and snapshot-bound view contracts.

    This design is implemented when:

    • [x] the existing shared core library exposes a domain-neutral property value type;
    • [x] the existing shared core library exposes provenance and canonical/derived classification;
    • [x] the universal schema crate defines entity/property/relation/collection schemas;
    • [x] schema-level validation returns structured issues;
    • [x] the universal graph crate defines storage-independent revision/relation/collection records;
    • [x] child records do not require parent pointers;
    • [x] ordered and unordered collections are distinct;
    • [x] descriptions are separate derived navigation objects;
    • [x] derived artifacts declare exact immutable dependencies;
    • [x] a snapshot-bound storage-independent graph view exists;
    • [x] conformance tests demonstrate the Level 1 semantics;
    • [x] no duplicate core/workspace layer was introduced;
    • [x] no database, parser, projection, migration, agent, transport, or UI subsystem was implemented by this work.

    13. Work Decomposition¶

    Create focused Level 3 implementation tasks in this order:

    1. extend the established shared core crate with universal values and provenance;
    2. implement the universal schema contracts;
    3. implement universal graph semantic records and snapshot-bound views;
    4. add universal-model conformance tests and public documentation.

    Every implementation task must first inspect the existing workspace and reuse the canonical shared crates already established by prerequisite designs. A task must never create a second competing core/schema/graph crate merely because another design used a different provisional prefix.
