    Agent Operations, Protocol, and Cross-Surface Product Contract¶

    1. Purpose¶

    This document defines the public application/protocol contract through which one-shot CLI, TUI, web, remote clients, and other product surfaces start and observe model-driven agent work.

    It refines:

    1. design/level-1/016. model driven agent execution and branch isolation.md;
    2. design/level-2/011. application operations protocol and runtime boundaries.md;
    3. design/level-2/017. web workspace packages and integrated editor.md;
    4. design/level-2/021. terminal ui runtime and state architecture.md;
    5. design/level-2/022. terminal ui views interaction and conformance.md;
    6. design/level-2/023. agent runtime model provider and branch orchestration.md.

    The controlling rule is:

    Product surfaces differ only in presentation and waiting behavior. They start and observe the same agent operation, session tree, branch results, and canonical mutation flow.

    2. Semantic Owner¶

    The semantic owner of agent execution requests is the application/session boundary, not CLI, TUI, web, server transport, or model provider code.

    The public operation family should be represented in scriberig-app and serialized by scriberig-protocol.

    The agent runtime is injected/composed as the executor behind those application operations.

    A product surface must never call OpenAiCompatibleProvider or equivalent directly.

    3. Public Operation Family¶

    The first complete public agent/session operation family should contain concepts equivalent to:

    agent_start
agent_continue
agent_cancel
agent_operation_status
session_inspect
session_list_branches
branch_inspect
branch_list_children
branch_list_activity
branch_result_inspect

    Where an existing universal operation already covers inspection/listing/following, prefer reusing it over duplicating session-specific request types. Specialized agent operations are justified for starting/continuing execution and observing runtime-specific lifecycle.

    4. Start Request¶

    Define a transport-safe request conceptually equivalent to:

    AgentStartRequest {
    prompt
    session: CreateNew | Existing(SessionRef)
    parent_branch: None | BranchRef
    selection: optional SemanticSelection
    base_snapshot: optional SnapshotRef
    agent_profile: optional AgentProfileRef
    context_policy: optional ContextPolicyRef
    retention: RetentionPolicy
    limits: optional AgentLimits
}

    The caller does not supply provider credentials or raw provider request JSON.

    New session¶

    If session requests creation, the application creates a session and a root branch before model execution begins.

    Existing session¶

    If an existing session is supplied, the application verifies visibility/capabilities and either creates a child/root continuation branch according to request semantics.

    Existing parent branch¶

    Continuing from an existing branch creates new durable activity in that branch only when the branch lifecycle permits it. When completed branches are immutable by policy, continuation creates a child/sibling continuation branch instead of silently reopening history.

    5. Start Response¶

    Starting agent work returns stable handles immediately:

    AgentStartResponse {
    operation: OperationRef
    session: SessionRef
    root_branch: BranchRef
    accepted_snapshot: optional SnapshotRef
}

    The response does not wait for the model to finish.

    A presentation surface that wants synchronous behavior waits by observing the returned operation.

    6. Continue Request¶

    A continue operation supports follow-up user input without requiring clients to understand provider message formats.

    Conceptually:

    AgentContinueRequest {
    session
    branch
    prompt
    selection: optional SemanticSelection
    limits: optional AgentLimits
}

    Continuation records a new human input/turn and starts a new operation tied to the selected branch or a new continuation child according to branch lifecycle policy.

    The application returns the same handle shape as agent_start.

    7. Cancellation¶

    Agent cancellation uses the shared operation cancellation model.

    A specialized agent_cancel request may exist as a convenience wrapper, but it must resolve to the same OperationId cancellation semantics used by other long-running application work.

    Cancellation request fields:

    operation
optional reason

    Cancellation response reports acceptance/rejection, not a false immediate terminal state.

    The operation becomes terminal only when the runtime reports a stable cancelled/completed/failed state.

    8. Operation Status¶

    Agent work uses the shared operation lifecycle:

    queued
running
completed
failed
cancelled

    Status metadata may additionally expose:

    session ref
root branch ref
current active branch refs
model/tool/validation phase summary
bounded progress counters
final result ref
structured failure

    Do not expose raw provider prompts or secrets in ordinary operation status.

    9. Agent Event Model¶

    Extend the shared event system with stable, transport-safe agent/session event kinds.

    At minimum support concepts equivalent to:

    AgentOperationStarted
BranchCreated
BranchStateChanged
ModelInvocationStarted
ModelTextDelta
ToolInvocationStarted
ToolInvocationCompleted
ChildBranchStarted
ChildBranchCompleted
BranchResultProduced
AgentOutputCommitted
AgentOperationCompleted
AgentOperationFailed
AgentOperationCancelled

    Not every event must be durable session state.

    Durable event references¶

    Events that correspond to durable knowledge carry stable references to the committed session object.

    Transient stream events¶

    Text deltas and low-level progress may be transient. They carry operation/branch correlation and sequence information but do not pretend to be canonical session objects.

    10. Event Ordering and Reconnection¶

    Within one agent operation, emitted events need a monotonically increasing sequence number or equivalent cursor.

    Conceptually:

    operation_id
sequence
kind
branch_ref
payload

    This allows clients to:

    • order concurrently delivered events;
    • detect gaps;
    • resume when the transport supports replay;
    • fall back to authoritative operation/session refresh when replay is unavailable.

    Correctness must never depend on receiving every transient event.

    After reconnect, a client can always recover by querying:

    operation status
session/branch tree
branch activity/result

    11. Protocol Types¶

    Add transport-neutral types under scriberig-protocol for:

    SessionReference
BranchReference
BranchResultReference
AgentStartRequest/Response
AgentContinueRequest/Response
AgentLimits
RetentionPolicy
AgentEvent
AgentEventKind
AgentFailure

    Reuse existing OperationReference, snapshot selectors, structured errors, and capability models where possible.

    Do not serialize internal runtime scheduler structures or provider wire DTOs.

    12. Application Service Boundary¶

    scriberig-app exposes an injected agent execution service conceptually equivalent to:

    AgentService
  start(context, request)
  continue(context, request)
  cancel(context, operation)

    The default product composition wires this service to scriberig-agent-runtime.

    Tests may wire it to a deterministic fake service.

    This prevents the application/protocol crates from depending on concrete HTTP provider implementations while keeping product semantics stable.

    13. Server Boundary¶

    scriberig-server maps public agent requests onto scriberig-app.

    The server owns:

    authentication/authorization at transport entry
decoding/encoding
request correlation
event delivery/stream transport
operation lookup

    It does not own:

    prompt construction
provider credentials exposed to clients
branch orchestration
tool semantics
canonical mutations

    For remote mode, the provider is configured on the server host, not in the browser or remote TUI.

    14. Client Boundary¶

    scriberig-client exposes semantic methods conceptually equivalent to:

    start_agent(...)
continue_agent(...)
operation_status(...)
cancel_operation(...)
subscribe_agent_events(...)
inspect_session(...)
inspect_branch(...)

    The Rust client hides envelope/correlation details.

    The TypeScript client exposes equivalent concepts through @scriberig/client.

    Neither client knows how to contact the model provider.

    15. Capability Discovery¶

    Add capability entries for at least:

    agent_start
agent_continue
agent_events
agent_streaming_text
branch_tree
branch_activity
operation_cancel
model_cache_reuse   # informational/runtime feature, not caller privilege

    Capability discovery should distinguish:

    • runtime feature availability;
    • caller authorization;
    • provider-dependent optional features such as streaming.

    A UI must not show an enabled cancellation action when the operation/runtime says cancellation is unsupported or the caller lacks permission.

    16. One-Shot CLI Contract¶

    The canonical one-shot user flow is built on AgentStartResponse and operation observation.

    Target behavior for srig run <PROMPT>:

    parse command
-> compose local app/session/agent runtime/provider
-> AgentStartRequest(CreateNew session/root branch)
-> receive OperationId + SessionRef + BranchRef
-> observe until terminal
-> print final agent output/result
-> select exit status from structured terminal state

    One-shot mode may choose a concise progress policy:

    • when stdout is a terminal, optionally show bounded progress on stderr;
    • when machine-readable output is requested, emit stable structured output without decorative progress;
    • final answer goes to stdout;
    • diagnostics/progress go to stderr.

    The command does not implement its own model loop.

    srig agent¶

    The existing srig agent <PROMPT> spelling may remain as a compatibility/advanced alias or later accept explicit agent-profile controls. It must call the same shared start operation. The design does not permit run and agent to drift into separate orchestration engines.

    17. One-Shot Exit Semantics¶

    Define stable categories for process exit behavior.

    Conceptually:

    0   completed successfully
nonzero provider/runtime/application failure
130 user interrupt/cancellation where platform conventions permit
77  permission denied where existing CLI convention applies

    The exact exit-code table should be finalized in the Level 3 CLI task and documented in CLI_REFERENCE.md.

    A successful model answer with a failed candidate mutation is not automatically process success; the operation's semantic terminal result decides.

    18. TUI Contract¶

    The TUI uses its existing service/effect architecture.

    Required service/effect concepts:

    StartAgent(request)
ContinueAgent(request)
LoadSession(session)
LoadBranch(branch)
LoadBranchActivity(branch, page)
ObserveOperation(operation)
CancelOperation(operation)

    The TUI reducer owns only presentation state.

    Session tree¶

    Rows are loaded from authoritative session/branch queries and show:

    branch title/purpose
status
compact outcome
child count
activity counts
result handles
active/running marker

    Opening a child branch loads its activity on demand.

    Streaming¶

    ModelTextDelta may update an in-progress presentation buffer keyed by operation/branch. Once AgentOutputCommitted arrives, the durable object replaces the transient buffer as the authoritative view.

    Concurrent navigation¶

    The user can navigate away while an agent operation runs. Returning to the session view refreshes from durable state and operation status.

    19. Web Client/Model Contract¶

    Add the agent/session protocol to the generated/authoritative web protocol boundary.

    @scriberig/client adds semantic methods for start/continue/status/cancel/events/session queries.

    @scriberig/model adds reusable state for:

    loaded session trees
loaded branch descriptors
branch activity pages
active agent operations
transient stream buffers
operation event cursors
reconnect/stale state

    Canonical session objects and transient stream buffers must remain distinct.

    20. @scriberig/agent-ui Responsibility¶

    The existing @scriberig/agent-ui package becomes the reusable branch-aware interaction layer.

    It should expose headless/view-model or React components/hooks for concepts equivalent to:

    AgentComposer
SessionBranchTree
BranchSummaryCard
BranchActivity
ToolInvocationView
OperationProgress
AgentOutputView

    It may depend on public protocol/client/model/react/editor-core packages as allowed by web workspace guidance.

    It must not import server code or provider SDKs.

    The reference web app composes these reusable pieces into SessionAgentView.

    21. Web Interaction Contract¶

    The web agent surface must support:

    start work from current universal selection
continue selected branch
observe active operation
collapse/expand branch tree
open child branch history
open result semantic handles in other editor views
cancel when permitted
review/promote candidate changes through normal migration UI

    The browser does not assume the live stream is the session transcript. Durable branch data comes from session queries.

    On reload/reconnect, the app can reconstruct the session tree and operation terminal state without replaying the original stream.

    22. Semantic Selection Binding¶

    Starting agent work from TUI or web may include the current universal selection.

    The runtime receives stable semantic references such as:

    entity
optional exact revision
snapshot/branch context
projection location when meaningful

    Do not convert the selection into only a filename/line-range string before passing it into the agent request.

    Context compilation may later render projection text for the model while retaining the semantic handle/dependency identity.

    23. Retention Policy¶

    The public request may select among a small set of safe retention policies, for example:

    ProjectDefault
RetainSession
EphemeralAfterResult

    EphemeralAfterResult still uses real session/branch objects during execution; it only changes post-completion reachability/retention policy.

    A product surface must not invent a separate non-session execution path merely to avoid long-term storage.

    Audit/security policy may override a caller's request to discard records.

    24. Structured Final Result¶

    The terminal operation result should reference a structured agent result conceptually equivalent to:

    AgentResult {
    session
    root_branch
    final_output: optional AgentOutputRef
    branch_result: BranchResultRef
    produced_changes: [SemanticRef]
    validation_results: [SemanticRef]
    unresolved_questions: [SemanticRef]
}

    Product surfaces may render only final text by default, but machine-readable callers can inspect all result handles.

    25. Security and Secrets¶

    Provider secrets never cross the public Scriberig protocol.

    The protocol may expose a safe provider/model display descriptor where authorized, such as:

    profile name
model id
feature flags

    It must not expose:

    API keys
Authorization headers
secret environment variable values
provider private headers

    Agent events and errors must sanitize provider diagnostics before transport.

    26. Cross-Surface Conformance¶

    Add conformance scenarios that invoke the same fake-backed agent operation through:

    embedded application
Rust client/server dispatch
one-shot CLI adapter
TUI service adapter
web client/model adapter

    Assertions compare semantic results, not presentation strings.

    At minimum prove:

    • the same prompt/scope creates the same session/branch topology under a deterministic fake provider;
    • child branch results are visible on all surfaces;
    • cancellation resolves to the same terminal operation category;
    • provider secrets are absent from public DTOs/events;
    • stream loss does not prevent recovery from durable state;
    • result semantic handles navigate through existing query operations.

    27. Capability Matrix¶

    Extend capabilities.toml with agent/session coverage.

    A capability must not become verified for a surface until an implementation and conformance test exist.

    Suggested rows:

    agent_start
agent_continue
session_branch_tree
session_branch_activity
agent_event_subscription
agent_streaming_output
agent_operation_cancel
agent_final_result

    The semantic owner should normally be scriberig-app or scriberig-session, not the UI surface.

    28. Implementation Order¶

    Implement vertically:

    1. provider-neutral session execution records;
    2. agent runtime and fake provider;
    3. app-level agent_start with operation/session/branch handles;
    4. protocol/server/client mapping;
    5. event/status/cancellation path;
    6. one-shot CLI;
    7. TUI branch-aware session flow;
    8. web client/model/agent-ui flow;
    9. cross-surface conformance.

    Do not complete the full web UI before the same operation can run through the application boundary.

    29. Completion Criteria¶

    This Level 2 design is satisfied when:

    • one public request starts model-driven branch execution;
    • start returns stable operation/session/root-branch handles before completion;
    • continue/cancel/status/event semantics are shared across surfaces;
    • the public protocol contains no provider credentials or provider-specific session schema;
    • one-shot CLI waits on the same operation instead of implementing a private model loop;
    • TUI renders authoritative branch/session state and treats streams as transient;
    • web uses public client/model/agent-ui packages and never contacts the model endpoint directly;
    • universal semantic selection can scope agent work;
    • reconnect can recover from durable operation/session state;
    • final results expose semantic handles beyond plain text;
    • deterministic conformance tests can compare all product adapters.
