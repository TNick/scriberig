    Application Operations, Protocol, and Runtime Boundaries¶

    1. Purpose¶

    This document turns design/level-1/011. runtime libraries protocol and product surfaces.md into concrete Rust package boundaries and source-file responsibilities.

    It complements design/level-2/001. workspace and package layout.md. That document establishes the overall monorepo shape; this document defines the runtime/application side that Level 1 intentionally left for Level 2.

    The main implementation rule is:

    Product surfaces are adapters over shared application operations. No product surface owns semantic business logic or bypasses the migration, validation, snapshot, and session models.

    This document prescribes crate and source-file structure, but it does not define domain-specific behavior, database tables, web UI components, or a concrete HTTP framework.

    2. Crates Added Above the Foundation¶

    The Rust workspace must contain these runtime-facing packages in addition to the foundational crates already defined elsewhere:

    crates/
├── scriberig-app/
├── scriberig-protocol/
├── scriberig-client/
├── scriberig-agent-core/
├── scriberig-agent-runtime/
├── scriberig-server/
├── scriberig-tui/
└── scriberig-cli/

apps/
└── scriberig/

    These packages have distinct independent-use boundaries.

    scriberig-app¶

    Owns user-visible application operations and orchestration over the knowledge platform.

    It may depend on reusable semantic libraries and domain adapters, but not on server, CLI, TUI, remote client, or agent-runtime packages.

    scriberig-protocol¶

    Owns the stable transport-facing contract.

    It contains serializable references, requests, results, errors, operations, events, capability discovery, and protocol compatibility metadata.

    It must not depend on server implementation details or expose persistence-backend structures.

    scriberig-client¶

    Owns the reusable Rust remote client.

    It depends on scriberig-protocol and transport support only. It must not depend on scriberig-server internals.

    scriberig-server¶

    Adapts remote requests onto scriberig-app operations and converts results/events into scriberig-protocol forms.

    The server is a transport host, not a semantic implementation.

    scriberig-agent-core¶

    Owns reusable agent-facing adapters such as tool contracts, progressive-disclosure views, capability exposure, and context-input interfaces.

    It composes application/session operations and must not access storage internals directly.

    scriberig-agent-runtime¶

    Owns integrated model execution and orchestration.

    It depends on scriberig-agent-core and the shared application/session layers. Lower layers must never depend on it.

    scriberig-tui¶

    Owns terminal interaction and presentation over application operations or a public client boundary.

    It must not own semantic mutations.

    scriberig-cli¶

    Owns command parsing, command dispatch, human-readable terminal output, and selection of executable modes.

    It must remain thin.

    apps/scriberig¶

    Owns the final executable entry point and composition root.

    It wires concrete implementations together but should contain almost no business logic.

    3. Required Dependency Direction¶

    The runtime crates must preserve this dependency direction:

    foundation/domain crates
        |
        v
  scriberig-app
     /      \
    v        v
protocol   agent-core
   |          |
   v          v
client   agent-runtime
   |
   +------------------+
                      |
app + protocol ------> server
app/client ----------> tui
app/server/tui/
agent-runtime -------> cli
cli -----------------> apps/scriberig

    More precisely:

    • scriberig-app may depend on scriberig-core, graph/query/migration/projection/session crates, and selected domain adapters.
    • scriberig-protocol may depend on scriberig-core for stable identifier/value types, but not on scriberig-app internals.
    • scriberig-client depends on scriberig-protocol.
    • scriberig-server depends on scriberig-app and scriberig-protocol.
    • scriberig-agent-core depends on scriberig-app, scriberig-session, and small shared types as required.
    • scriberig-agent-runtime depends on scriberig-agent-core and the application/session layers.
    • scriberig-tui may use either direct scriberig-app access for local mode or scriberig-client for remote mode; its presentation code must not be imported by lower layers.
    • scriberig-cli may compose app, server, TUI, client, and agent-runtime crates.
    • apps/scriberig depends on scriberig-cli and composition-only dependencies.

    Cycles are forbidden.

    4. scriberig-app Source Layout¶

    Create the application crate with a small stable public surface and internal operation modules.

    Target structure:

    crates/scriberig-app/
├── Cargo.toml
└── src/
    ├── lib.rs
    ├── error.rs
    ├── context.rs
    ├── query.rs
    ├── command.rs
    ├── operation.rs
    ├── event.rs
    └── capability.rs

    Responsibilities:

    • context.rs: explicit snapshot, actor, capability, and request context passed to operations.
    • query.rs: application-level read operations such as inspect, list, follow, find, diff, and history.
    • command.rs: application-level state-changing operations such as branch, apply, reconcile, validate, merge, and commit.
    • operation.rs: stable identity and lifecycle for long-running work.
    • event.rs: application events that notify consumers without becoming authoritative state.
    • capability.rs: capability discovery and operation availability.
    • error.rs: semantic error categories shared by embedded callers and adapters.

    The exact function names may evolve, but the query/command distinction and snapshot-aware context are required.

    5. Queries and Commands¶

    Application operations must distinguish reads from canonical-state-changing commands.

    Queries include concepts equivalent to:

    inspect
list
follow
find
query
diff
history

    Commands include concepts equivalent to:

    create branch
apply migration
reconcile projection
validate candidate
commit branch
merge branches
update projection configuration
start agent command

    Expensive queries may populate derived caches but must not advance canonical snapshots merely because they ran.

    Commands that can conflict must carry an explicit base snapshot or branch context.

    6. Application Errors¶

    Application errors must be machine-readable enums or equivalent structured values, not free-form text categories.

    The application layer must be able to represent at least these semantic classes:

    not found
schema violation
stale base snapshot
semantic conflict
validation failure
permission denied
unsupported operation
projection out of sync
operation cancelled
internal failure

    Adapters may attach human-readable messages and transport metadata, but they must preserve the semantic category.

    7. Operation Lifecycle¶

    Long-running work is represented through stable OperationId values.

    The application layer must provide a common lifecycle equivalent to:

    queued
running
completed
failed
cancelled

    An operation record/result must carry enough information to associate it with:

    • operation kind;
    • requester/provenance;
    • input snapshot or branch;
    • status;
    • progress where meaningful;
    • final result reference;
    • diagnostics or structured failure.

    Streaming is an observation mechanism over this lifecycle, not a separate result model.

    8. Events¶

    The application event model should include semantic notification categories equivalent to:

    snapshot changed
entity changed
projection changed
branch changed
migration created
operation started
operation progressed
operation completed
validation completed
agent output produced

    Events should normally contain stable handles and concise metadata.

    Consumers that need full state resolve it through normal query operations.

    Event payloads must not become a second canonical representation of entities or snapshots.

    9. scriberig-protocol Source Layout¶

    Target structure:

    crates/scriberig-protocol/
├── Cargo.toml
└── src/
    ├── lib.rs
    ├── version.rs
    ├── refs.rs
    ├── request.rs
    ├── response.rs
    ├── error.rs
    ├── operation.rs
    ├── event.rs
    └── capability.rs

    The protocol crate owns the public wire contract, not server routing.

    The protocol should contain transport-neutral serializable values for:

    • entity/revision/snapshot references;
    • request and correlation IDs;
    • query and command requests;
    • typed summaries and results;
    • structured errors;
    • operation states and results;
    • runtime events;
    • capability discovery;
    • protocol version/compatibility metadata.

    It must not expose SQLite row IDs, database page numbers, table names, or private application structs.

    10. One Authoritative Wire Contract¶

    The Rust protocol crate is the authoritative contract for the first implementation.

    It must be possible to derive a machine-readable schema from the public protocol types and use that schema to generate or validate non-Rust client types.

    Do not manually maintain an independently invented TypeScript wire model.

    The exact generator/tool is an implementation decision, but these outputs must be reproducible from the authoritative contract.

    Generated artifacts should be treated as build outputs, while hand-written TypeScript convenience clients belong in the web/client design.

    11. Protocol Versioning¶

    scriberig-protocol must define a protocol version independent of the crate/package version.

    The first protocol version may be 1.

    The contract must support:

    • client/server protocol-version exchange;
    • explicit rejection of unsupported major versions;
    • additive capability discovery;
    • unknown capability tolerance where safe;
    • structured unsupported-operation errors.

    Do not use application package version strings as the sole compatibility mechanism.

    12. scriberig-client¶

    Target structure:

    crates/scriberig-client/
├── Cargo.toml
└── src/
    ├── lib.rs
    ├── client.rs
    ├── transport.rs
    ├── operation.rs
    └── subscription.rs

    The public client API should expose semantic methods rather than raw endpoint assembly.

    Examples include concepts equivalent to:

    inspect
query
diff
apply
operation status
cancel operation
subscribe
capabilities

    Transport-specific implementation belongs behind an internal/public transport abstraction so tests can use an in-memory fake transport.

    13. scriberig-server¶

    Target structure:

    crates/scriberig-server/
├── Cargo.toml
└── src/
    ├── lib.rs
    ├── server.rs
    ├── transport.rs
    ├── dispatch.rs
    ├── operation.rs
    └── subscription.rs

    The server has four responsibilities:

    1. authenticate/authorize when configured;
    2. decode protocol requests;
    3. invoke scriberig-app operations;
    4. encode results and deliver events/operation progress.

    dispatch.rs must not contain semantic implementations that cannot be called without the server.

    The concrete HTTP/streaming framework is intentionally deferred to a focused implementation task.

    14. Agent Runtime Boundary¶

    The agent layer uses the same application semantics.

    Target package responsibilities:

    scriberig-agent-core
  tool definitions
  progressive-disclosure adapters
  capability filtering
  structured context inputs

scriberig-agent-runtime
  model-provider execution
  tool loop
  session branch orchestration
  operation tracking
  cancellation

    Agent tools may combine several application operations into one simpler tool, but all canonical mutations must still pass through application migrations/validation.

    15. CLI, TUI, and Executable Boundary¶

    scriberig-cli parses commands and selects modes.

    scriberig-tui renders interactive terminal state and invokes public operations.

    apps/scriberig is a composition root.

    The executable should eventually be able to host concepts equivalent to:

    serve
tui
run one-shot command
run agent command
maintenance command

    The exact command spelling belongs in the implementation-level task.

    No command handler may directly manipulate database tables.

    16. Snapshot Awareness Across Boundaries¶

    Important query results must identify the snapshot/revision under which they were resolved.

    Commands must identify the base state when conflict detection matters.

    Client caches must key semantic data by immutable revision/snapshot identity rather than only by EntityId.

    The protocol must preserve enough context to distinguish:

    resolve this entity as of snapshot S

    from:

    resolve the current revision of this entity

    17. Capability Discovery¶

    Both embedded and remote consumers need a way to discover available operations.

    Capability discovery should be able to report:

    • runtime-supported operation families;
    • protocol capabilities;
    • domain-contributed operations;
    • renderer/validator availability;
    • permission-filtered actions for a request context.

    A generic consumer must be able to inspect an unknown domain using universal operations even when specialized commands are absent.

    18. Testing Boundary¶

    Each layer needs its own tests, but user-visible capabilities also require cross-surface conformance tests.

    At minimum:

    • scriberig-app tests operation semantics without a network;
    • scriberig-protocol tests round-trip serialization and version compatibility;
    • scriberig-client tests against a fake transport;
    • scriberig-server tests dispatch without duplicating semantic assertions;
    • vertical tests compare embedded and remote results for semantic equivalence.

    A separate Level 2 design defines the capability matrix and conformance harness.

    19. Implementation Order¶

    Implement in this order:

    1. scaffold runtime-facing crates and dependency edges;
    2. implement protocol references, errors, operation lifecycle, events, and version metadata;
    3. implement the application operation context and one read-only capability (inspect) end to end;
    4. add server/client transport around that capability;
    5. expose the same capability through CLI and agent adapters;
    6. add operation/event streaming and cancellation;
    7. add further capabilities vertically rather than building one surface far ahead of the others.

    Do not implement broad domain behavior in this sequence merely to populate APIs.

    20. Completion Criteria¶

    This Level 2 design is satisfied when:

    • the prescribed runtime crates exist;
    • dependency direction is acyclic and enforced by manifests;
    • application operations are distinct from transport and presentation;
    • the protocol has one authoritative Rust contract and machine-readable generation path;
    • errors, operations, events, capabilities, and protocol versioning are structured;
    • server and client are adapters over the same semantics;
    • the agent runtime cannot bypass application operations for canonical mutations;
    • CLI/TUI/executable packages remain thin product hosts;
    • at least one capability can be exercised equivalently in embedded and remote form;
    • conformance work can test semantic equivalence without depending on presentation text.
