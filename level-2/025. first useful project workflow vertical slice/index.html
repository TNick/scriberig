    First Useful Project Workflow Vertical Slice¶

    1. Purpose¶

    This document implements the product-completion rule from design/level-1/013. vertical product completion and end to end usability.md for the first software-project workflow.

    It is the concrete design for turning the existing onboarding, semantic store, code adapters, projection/change infrastructure, web editor, TUI, and agent runtime into one continuous useful workflow.

    The target is deliberately narrow:

    • local Git-backed project;
    • Rust as the required editable language for the first slice;
    • browser editor and native TUI as required interactive surfaces;
    • CLI/application/protocol remain shared diagnostic and automation peers;
    • deterministic local test fixtures and deterministic agent provider;
    • no external network or model service is required for acceptance.

    The goal is not to redesign the platform. The goal is to connect existing public layers so a user can inspect and safely change a real source project.

    2. Existing Pieces and the Integration Gap¶

    The repository already contains substantial pieces of the workflow:

    • project catalog, scan, import, ownership, and project-specific snapshots;
    • Rust syntax/domain import;
    • immutable snapshots and history;
    • application operations and protocol/client/server layers;
    • projection and reconciliation infrastructure;
    • migration/change/validation machinery;
    • filesystem projection ownership and atomic I/O support;
    • native TUI views;
    • reusable web packages and the reference web app;
    • session/agent operations and branch-aware product views;
    • browser and native terminal E2E harnesses.

    The missing contract is composition.

    An import response that says imported is not enough. The product must know which project/snapshot/root is active, navigate meaningful symbols, render the source representation, route edits through migrations, materialize accepted output, refresh to the successor snapshot, and preserve semantic scope for agents.

    This document specifies those connections.

    3. Non-Goals¶

    Do not expand this slice into unrelated platform work.

    Not required for first acceptance:

    • full IDE language-server functionality;
    • arbitrary multi-file refactoring UI;
    • every imported programming language becoming editable;
    • syntax highlighting parity with a dedicated code editor;
    • remote cloud project upload;
    • collaborative multi-user editing;
    • desktop shell integration;
    • persistent docking/layout systems;
    • external model-provider access in CI;
    • generalized build-system execution beyond the deterministic fixture requirement;
    • replacing the universal graph with a code-specific store.

    If a missing foundational capability blocks the golden path, implement the smallest reusable public capability needed and keep it domain/surface boundaries-correct.

    4. Golden Fixture¶

    Create one repository-controlled fixture specifically for product E2E tests.

    Recommended location:

    tests/fixtures/golden-rust-project/
  Cargo.toml
  src/
    lib.rs

    The fixture must have no external Cargo dependencies.

    Its source must contain stable names and a stable editable expression. Use the following semantic content unless an equivalent existing fixture is already shared by both web and TUI tests:

    pub mod math {
    pub struct Calculator;

    impl Calculator {
        pub fn add(&self, left: i32, right: i32) -> i32 {
            left + right
        }
    }
}

    The exact formatting may follow repository Rust formatting rules, but these strings are acceptance anchors:

    math
Calculator
add
left + right

    The accepted edited form for the primary scenario is:

    left.saturating_add(right)

    The fixture must compile with a local cargo check without downloading dependencies.

    Every E2E run copies the fixture to a fresh temporary directory and initializes Git there if the checked-in fixture itself is not a nested Git repository. Tests must never mutate the checked-in fixture or Scriberig's own working tree.

    5. Project Workspace Contract¶

    5.1 Server/application project record remains canonical catalog data¶

    The existing project service remains the owner of:

    • ProjectId;
    • canonical project path;
    • display name;
    • import status;
    • current project snapshot;
    • project semantic root/ownership data.

    Do not add a separate web-only or TUI-only project database.

    5.2 Active project is client/product state¶

    The active project is not one global mutable server setting.

    Each interactive client maintains an ActiveProjectWorkspace equivalent containing at least:

    project_id
project_name
canonical_path or path metadata appropriate to the client
snapshot_id
root_entity_id

    The public server/client contract must provide enough information to construct this value from ProjectId.

    If the existing project status/import response does not expose the exact project root reference required for semantic browsing, extend the shared application operation and public protocol response. Do not infer the root by scanning database tables or by assuming the server's global capability root belongs to the project.

    5.3 Required activation operations¶

    The product runtime must support these conceptual actions:

    list projects
resolve/open workspace for project_id
activate resolved workspace locally
refresh active workspace after project snapshot changes

    The exact method names may fit existing project-operation conventions.

    Do not create a server-side set_current_project_for_everyone mutation.

    5.4 Import-to-activation behavior¶

    After successful import in web or TUI:

    1. resolve the imported project's current workspace/root;
    2. make it the active workspace in that client;
    3. reset/rebase navigation tree to that project root;
    4. clear a selection that points to a different project's snapshot;
    5. navigate to the semantic/raw project browser or otherwise provide an explicit Open project action that the E2E test exercises;
    6. show project identity and current snapshot visibly.

    The user must never have to restart the server or manually copy an entity ID after import.

    6. Workspace Events and Refresh¶

    The client runtime must be able to refresh active workspace state after:

    • import creates a new project snapshot;
    • a migration is applied;
    • external reconciliation creates a successor snapshot;
    • an event reports that the active project's current snapshot changed.

    Refresh means resolving the authoritative project status/root again, not modifying local snapshot IDs optimistically without server confirmation.

    When semantic identity survives the change, preserve selection by entity identity and resolve it against the new snapshot.

    When it does not survive, clear the invalid selection and show a meaningful state rather than silently selecting an unrelated object.

    7. Human-Readable Code Navigation Contract¶

    7.1 Public semantic data owns display names¶

    The Rust/code adapter must expose display metadata through the shared semantic object model.

    For named source concepts, at least the following must be represented when applicable:

    display label / symbol name
semantic kind
source-relative path
source range or projection mapping
parent/containment relation

    Frontends may decorate these fields but must not parse serialized syntax trees privately to recover names.

    7.2 Required fixture navigation¶

    From the active golden fixture workspace, the public semantic/navigation API must let a client reach the fixture method add through recognizable labels.

    The exact intermediate hierarchy may depend on current code-domain modeling, but product output must expose enough context that a human can identify:

    src/lib.rs
math
Calculator
add

    If the universal tree contains low-level syntax nodes as well, products may hide/collapse them by default in a semantic mode. Raw knowledge mode may still expose them.

    7.3 Raw and semantic modes¶

    The integrated products may retain both:

    • raw graph/knowledge navigation for debugging;
    • semantic/domain navigation for ordinary work.

    The golden-path test uses semantic/domain navigation, not opaque raw node indices.

    7.4 Stable labels¶

    Labels must not depend on enumeration order such as #17 when a symbol name exists.

    A label may include disambiguating context, e.g. add · method · src/lib.rs, but add must be available as semantic data.

    8. Source Projection Contract¶

    8.1 What projection must return¶

    For the selected add method, source projection must expose at least:

    projection identifier
project identifier
snapshot/base identifier
source-relative path
rendered source text
semantic-to-source mapping covering the selected entity
editable/read-only capability
stale/conflict state

    For the fixture selection, the rendered text must include left + right before the edit.

    8.2 Projection granularity¶

    The implementation may render:

    • the entire source file with selection range; or
    • a bounded semantic source region with enough context.

    The web E2E test must be able to edit the selected source deterministically.

    The TUI must be able to inspect the same source and create the same candidate through a terminal-appropriate interaction.

    8.3 No inspector fallback for required source capability¶

    If a Rust source projection is supported, showing only object metadata/description does not satisfy this contract.

    Generic inspector fallback remains valid for unsupported domains.

    9. Candidate Edit Contract¶

    9.1 Web edit¶

    The web editor must allow the E2E test to replace:

    left + right

    with:

    left.saturating_add(right)

    through a public projection/change API.

    The edit must not immediately write the filesystem or advance current canonical state.

    It produces a candidate/migration based on the exact active snapshot.

    9.2 TUI edit¶

    The TUI does not need a full-screen IDE editor for this milestone.

    It must nevertheless expose a deterministic terminal interaction that creates the same kind of candidate through the public change path. Acceptable first forms include:

    • an edit command that opens/edits a projection buffer within the TUI;
    • a command palette action that supplies replacement text for the selected mapped range;
    • an external $EDITOR handoff only if the test harness can deterministically drive it and the edited result returns through reconciliation rather than direct canonical mutation.

    Do not implement a TUI-only direct filesystem patch command.

    9.3 Candidate invariants¶

    A candidate must include or resolve:

    migration/proposal identity
exact base snapshot
candidate/result snapshot when materialized
changed semantic entities
changed source projection(s)
validation state
stale/conflict state
provenance identifying human/agent source

    10. Diff and Review Contract¶

    Before application, both web and TUI must let the user review the candidate.

    For the fixture, review must show enough information to establish that:

    old: left + right
new: left.saturating_add(right)

    Review should prefer semantic diff plus a source/text diff when source is editable.

    At minimum the candidate review must expose:

    • base snapshot ID;
    • changed file src/lib.rs;
    • affected semantic object add or its stable entity identity plus human label;
    • old/new source content or a unified equivalent;
    • validation status;
    • stale/conflict status;
    • explicit apply/accept action;
    • reject/close action that does not mutate current state.

    11. Validation Contract¶

    The first Rust golden-path candidate must pass two levels of deterministic validation before acceptance is enabled:

    1. Scriberig semantic/projection validation: reconciliation parses successfully, semantic mappings remain valid enough to produce a candidate, and migration base is current;
    2. fixture project validation: execute cargo check against the candidate materialization or an isolated candidate workspace without network dependencies.

    If the existing validation architecture already supports validator registration, add the fixture/project Rust validator there rather than special-casing the web UI.

    Validation output must be represented as operation/result data consumable by web and TUI.

    A failed validation prevents normal acceptance in the golden path and shows diagnostics.

    Tests must also include one intentionally invalid candidate, such as malformed Rust, and assert that current snapshot and working tree remain unchanged.

    12. Apply and Canonical Snapshot Contract¶

    Applying a valid candidate must use shared compare-and-swap migration semantics.

    The application operation must reject a stale base if current project state no longer matches the candidate base.

    On successful application:

    • a successor immutable snapshot exists;
    • the project current root advances to that snapshot;
    • migration provenance/history links base and successor;
    • the selected semantic object is resolved against the successor when identity survives;
    • clients learn the authoritative new snapshot through operation result/event/refresh.

    No product UI directly edits project snapshot tables.

    13. Filesystem Materialization Contract¶

    13.1 Required successful behavior¶

    After a candidate is accepted, the resulting Rust projection must be materialized to the fixture working tree using shared filesystem projection infrastructure.

    The E2E test must observe:

    src/lib.rs contains left.saturating_add(right)

    and must confirm the file did not contain that text before acceptance.

    13.2 Safety¶

    Materialization must enforce:

    • target path belongs to active project;
    • target is the registered source projection/path;
    • stale source digest/external changes are detected;
    • atomic replacement semantics are used where supported;
    • symlink/path escape is rejected;
    • unrelated files are untouched.

    13.3 External effect failure¶

    Canonical database promotion and filesystem I/O cannot be assumed to be one transaction.

    Use the repository's external-effect receipt/reconciliation design to represent success/failure.

    If filesystem materialization fails after semantic promotion, expose a repairable out-of-sync/effect-failed state and retain the accepted canonical snapshot. Do not lie that write-back succeeded.

    If the existing architecture stages materialization before final promotion, preserve its documented correctness rules. The key requirement is explicit recoverable state, not a particular impossible cross-resource transaction.

    13.4 Conflict scenario¶

    A required E2E/conformance scenario modifies src/lib.rs externally after the candidate is created but before write-back.

    Acceptance/write-back must not silently overwrite the external content.

    The operation must produce a stale/conflict result that is visible through the product surface, and the externally modified file must remain intact.

    14. History and Post-Apply Refresh¶

    After successful application and materialization:

    • active workspace snapshot changes from base to successor;
    • source projection reload shows left.saturating_add(right) from authoritative state;
    • history includes the change/migration/snapshot transition;
    • reloading the web page and reopening the project still shows successor state;
    • restarting the TUI against the same database/project still shows successor state;
    • project status reports the successor snapshot.

    The E2E test records the base snapshot ID and asserts it differs from the successor snapshot ID.

    15. Agent Golden Path¶

    15.1 Deterministic provider¶

    Add/reuse a deterministic model provider for E2E tests.

    It must not make network requests.

    For a known prompt such as:

    Change add so overflow saturates instead of wrapping.

    it must exercise the real agent runtime/tool boundary sufficiently to produce a candidate equivalent to replacing left + right with left.saturating_add(right).

    The provider may use scripted responses/tool calls; it must not bypass the agent application operation by inserting a migration directly from the test.

    15.2 Scope assertion¶

    The test must prove the agent operation received semantic scope containing the selected add entity and the active snapshot.

    This may be asserted through captured deterministic-provider request metadata, operation/session records, or a test-visible agent-tool invocation record.

    Do not reduce this to an assertion that the prompt string happened to contain add.

    15.3 Same review path¶

    The agent-generated candidate enters the same migration review/validation/apply surface as a human edit.

    The agent must not auto-write the working tree in the golden scenario.

    Before user acceptance, filesystem source remains unchanged.

    16. Web Runtime Changes¶

    The reference web application runtime must gain explicit active-project/workspace coordination.

    Conceptually it owns:

    connection
capabilities
project catalog access
active workspace
knowledge/semantic tree rooted at active workspace
shared semantic selection
operations/session state
workspace refresh

    ProjectManager must not be an isolated island with only local projects state after import.

    It must call a public runtime/controller action such as activateProject(projectId) or invoke an injected callback that does so.

    Do not rebuild a second ScriberigClient or WorkspaceModel inside the project view.

    On activation the raw/semantic navigation root is replaced by the active project's root rather than the server's unrelated generic bootstrap root.

    17. TUI Runtime Changes¶

    The native TUI must represent active project workspace explicitly in application state.

    Starting with srig tui --project PATH --import must land in the imported project's browsable semantic workspace.

    When multiple projects share a database, the TUI must use the selected ProjectId/workspace root and never infer the active project from whichever root was most recently imported globally.

    Required user-visible context includes project name/path and current snapshot (full or shortened display is acceptable).

    TUI explorer rows for supported named code entities use semantic labels, not opaque ordinal labels.

    18. Public Protocol and Client Rules¶

    If new data is required remotely, extend the canonical protocol/client/server path once.

    Likely required data includes:

    • project workspace/root reference;
    • project snapshot refresh information;
    • source projection including mapping/editability/staleness;
    • create/reconcile candidate request/result;
    • validation operation/result;
    • materialization/effect status if not already public.

    Before adding a new operation, inspect current public operations and reuse existing migration/render/reconcile/apply/operation mechanisms when their semantics already match.

    Do not add one-off /web/... endpoints.

    Do not serialize SQLite row IDs.

    20. Required Browser E2E Scenarios¶

    Extend the existing Playwright harness under web/e2e.

    Tests launch the real server and real built/dev browser app as the harness already does.

    Required scenarios:

    WEB-GOLDEN-01: onboard and open active project¶

    1. copy golden fixture to temp workspace;
    2. initialize Git and add fixture files when needed;
    3. open Projects;
    4. scan temp path with Git-tracked mode;
    5. import reviewed scan;
    6. activate/open imported project;
    7. navigate to semantic project browser;
    8. assert active project name/path context;
    9. assert explorer visibly contains Calculator and add;
    10. assert browser health diagnostics are clean.

    The test fails if it only sees status=imported.

    WEB-GOLDEN-02: selection opens exact source¶

    1. continue from/import fixture;
    2. select add;
    3. navigate/open source projection;
    4. assert projection path contains src/lib.rs;
    5. assert source contains left + right;
    6. assert selection summary identifies add and current snapshot;
    7. assert projection is editable and not stale.

    WEB-GOLDEN-03: human edit creates reviewable candidate without write-through¶

    1. edit the mapped source expression to left.saturating_add(right);
    2. submit/propose change;
    3. assert migration review opens;
    4. assert base snapshot equals recorded pre-edit snapshot;
    5. assert diff contains old and new expressions;
    6. assert changed path is src/lib.rs;
    7. assert validation becomes successful;
    8. read temp src/lib.rs from the test harness and assert it still contains left + right before acceptance.

    WEB-GOLDEN-04: accept writes file and refreshes snapshot/history¶

    1. accept validated candidate;
    2. wait for operation completion and authoritative workspace refresh;
    3. assert successor snapshot differs from base;
    4. read temp file and assert left.saturating_add(right);
    5. reopen projection and assert accepted text;
    6. open history and assert the change/migration is present;
    7. reload browser;
    8. reopen active project if activation is intentionally session-local;
    9. assert accepted source and successor snapshot remain observable.

    WEB-GOLDEN-05: invalid edit cannot apply¶

    1. start from fresh fixture;
    2. edit source to invalid Rust;
    3. propose candidate;
    4. assert validation failure/diagnostic is visible;
    5. assert normal apply action is disabled or application operation rejects it;
    6. assert project current snapshot remains base;
    7. assert filesystem source remains original.

    WEB-GOLDEN-06: stale external edit is not overwritten¶

    1. create valid candidate from base;
    2. modify temp src/lib.rs externally through test harness before acceptance/write-back;
    3. attempt apply/materialize;
    4. assert conflict/stale/effect failure is visible;
    5. assert external content remains on disk;
    6. assert no silent overwrite occurs;
    7. assert product offers/reports a recoverable state.

    WEB-GOLDEN-07: agent uses selection and enters same review path¶

    1. start fresh fixture and select add;
    2. switch to Session/Agent;
    3. submit the deterministic golden prompt;
    4. assert agent operation completes using fake provider;
    5. assert recorded semantic scope is the selected add entity at active snapshot;
    6. assert resulting candidate/migration can be opened in the normal migration review;
    7. assert diff contains the saturating-add change;
    8. assert filesystem is unchanged before user acceptance.

    21. Required Native TUI E2E Scenarios¶

    Extend the existing native PTY TUI suite rather than replacing it with reducer-only tests.

    Tests run a real srig tui binary in a pseudo-terminal against a temporary database and golden fixture.

    Required scenarios:

    TUI-GOLDEN-01: onboarded project is active and named symbols are navigable¶

    Run the equivalent of:

    srig tui --db <temp-db> --project <temp-project> --git-tracked --import

    Then drive keys/actions to verify:

    • project context shows golden fixture;
    • current snapshot is visible;
    • explorer contains Calculator and add;
    • selection can reach add without typing an entity ID.

    TUI-GOLDEN-02: selected method opens source projection¶

    Select add, open projection/source action, and assert terminal output contains:

    src/lib.rs
left + right

    TUI-GOLDEN-03: create/review/apply candidate¶

    Using the defined deterministic TUI edit interaction:

    • create the saturating-add candidate;
    • open review;
    • assert old/new expressions and validation success;
    • assert disk is unchanged before apply;
    • apply;
    • assert successor snapshot/current state is visible;
    • assert disk contains accepted expression;
    • assert history/projection reflects successor state.

    TUI-GOLDEN-04: stale external edit is protected¶

    Create candidate, mutate source externally, attempt apply/materialize, and assert terminal reports conflict/stale state while external file survives unchanged.

    TUI-GOLDEN-05: agent candidate uses selected semantic scope¶

    With deterministic provider enabled, select add, issue the golden agent prompt, and assert the resulting migration is reviewable through the same TUI change-review path.

    The PTY test may inspect deterministic provider/session records after the terminal run to prove exact semantic scope, but it must drive the user operation through the real TUI.

    22. Cross-Surface Conformance Scenarios¶

    In addition to UI E2E, add programmatic conformance tests over public interfaces:

    1. resolving the same ProjectId through embedded application and HTTP client returns equivalent workspace root/snapshot;
    2. semantic navigation to add yields the same entity identity through embedded, client, web-model, and TUI application adapter paths;
    3. rendering source for that entity at the same snapshot yields equivalent path/text/mapping;
    4. the same source edit produces equivalent migration semantics independent of initiating surface;
    5. stale-base application is rejected consistently;
    6. successful apply advances exactly one project root and does not affect another project in the same database;
    7. write-back modifies only the intended fixture source;
    8. agent candidate uses the same migration/change types and does not bypass application operations.

    23. Test Harness Requirements¶

    Product tests must be deterministic and diagnosable.

    The harness must record or preserve on failure:

    • server stderr/stdout log;
    • web console/page errors;
    • operation failure diagnostics;
    • temporary database path or a copied artifact when practical;
    • fixture working-tree diff;
    • PTY screen/output transcript for failed TUI scenarios.

    Tests must use bounded waits with explicit operation/state conditions. Avoid arbitrary multi-second sleeps when polling an operation/event/DOM condition is available.

    Do not weaken assertions to make timing flakes disappear.

    25. Implementation Order¶

    Implement in this order and do not skip ahead by adding placeholders:

    1. active project workspace resolution/activation;
    2. semantic names and navigable Rust hierarchy;
    3. real source projection for selected Rust semantic objects;
    4. candidate creation from projection edit;
    5. review and deterministic validation;
    6. apply + controlled filesystem write-back + workspace refresh;
    7. web golden path;
    8. TUI golden path;
    9. deterministic agent-scoped candidate path;
    10. stale/conflict scenarios;
    11. cross-surface conformance and normal quality-gate integration.

    Each step has a Level-3 task with a detailed checklist. Later tasks must not mark themselves complete while a prerequisite task has unchecked acceptance items.

    26. Completion Criteria¶

    This Level-2 design is satisfied only when:

    • every required Level-3 task created for this vertical slice is checked and verified;
    • all WEB-GOLDEN scenarios pass against real processes and temp fixture;
    • all TUI-GOLDEN scenarios pass against the real native binary;
    • cross-surface public-interface conformance passes;
    • the fixture working tree changes only after accepted change;
    • stale/conflicting source is never silently overwritten;
    • current snapshot/history refresh is observable after apply;
    • deterministic agent scope/candidate behavior is proven without external network;
    • capabilities.toml statuses are truthful;
    • full repository quality checks pass.

    Subsystem tests from earlier design tasks are necessary regression coverage but cannot substitute for these criteria.
