    Upstream-First Agent Runtime and Terminal Product Ownership Correction¶

    1. Purpose¶

    This document corrects the ownership boundary established by 031. rpi tui adoption and shared presentation migration plan.md.

    The first migration successfully proved that Scriberig can consume rpi code without importing foreign session semantics, but it stopped at an adapter layer. It left Scriberig owning most of the visible TUI shell, terminal lifecycle, model catalog abstraction, thinking-level abstraction, model controls, and a substantial amount of commodity agent/runtime plumbing.

    That is not the desired final architecture.

    The new controlling rule is:

    Scriberig owns the semantics that make Scriberig unique. Commodity provider, model, agent-loop, plugin, package, and terminal-product machinery should be owned by upstream rpi whenever upstream provides it or can reasonably be extended to provide it.

    A second controlling rule is:

    When a generally useful capability is missing upstream, prefer contributing or extracting that capability upstream and then consuming it from Scriberig. Do not create a Scriberig-only substitute merely because it is faster locally.

    This plan supersedes the final ownership and completion criteria in Level-2 plan 031. Work from tasks 138 through 143 remains useful migration evidence and may be reused, but it is not the final target.

    2. Why the Previous Migration Is Not the End State¶

    The current branch demonstrates the problem clearly:

    • rpi-tui is vendored, but Scriberig still owns the Ratatui application shell;
    • upstream editor and Markdown output are adapted back into Scriberig-owned rendering instead of letting upstream own the terminal presentation stack;
    • Scriberig still defines its own model descriptors, thinking-level descriptors, model profiles, and model library;
    • Scriberig still owns provider/model selection presentation;
    • the active terminal lifecycle remains Scriberig Crossterm code;
    • the upstream plugin/extension/package ecosystem is not the integrated product extension mechanism;
    • the local agent runtime still owns provider and tool-loop machinery that upstream already exposes as reusable libraries.

    The implementation can therefore change many files and pass many tests while the product still looks and feels like the same locally maintained TUI.

    The corrective migration must optimize for delegation and deletion, not merely for wrapping upstream primitives.

    3. Upstream Baseline¶

    At the reviewed upstream revision aab74de0737f4b7c454cd8c8c16ca66e4dfbf898 (rpi 0.6.2), upstream already provides or documents reusable machinery for:

    rpi-ai
  provider-neutral model descriptors
  provider protocol implementations
  model compatibility metadata
  model costs/context/max-output metadata
  model-specific sampling parameters
  model-specific compatibility/custom properties
  thinking-level maps and supported-level clamping

rpi-agent
  provider-neutral agent loop
  tool schemas and validation
  tool execution sequencing
  streaming events
  cancellation
  hooks/queues

rpi-tui
  terminal runtime
  regular/fullscreen modes
  component abstraction
  focus
  overlays
  editor/composer
  text and Markdown rendering
  fuzzy/select UI
  themes/styles
  transcript/message components
  scroll/resize/input behavior

rpi-plugin-sdk + rpi-extensions
  stable plugin ABI
  tool registration
  provider registration
  slash commands
  event handlers
  Markdown renderers
  discovered resources

rpi-cli / provider-package infrastructure
  dynamic model registry/catalog
  provider authentication status
  provider/model selection

  provider packages
  package install/update/link/reload
  model catalog refresh

    Some of these capabilities currently live in rpi-cli rather than a narrow reusable crate. That is an upstream API-boundary problem, not permission to copy the implementation into Scriberig.

    When Scriberig needs one of those capabilities as a library and upstream has it only inside the CLI, the implementation sequence is:

    identify reusable upstream capability
  -> contribute/extract reusable upstream library API
  -> pin/release upstream revision
  -> consume that API from Scriberig
  -> delete local duplicate

    A temporary pinned Git dependency is acceptable while an upstream release is pending. A hand-maintained copied implementation is not the preferred final state.

    4. Final Ownership Boundary¶

    4.1 Scriberig owns distinctive semantic architecture¶

    Scriberig remains authoritative for:

    universal semantic knowledge
stable semantic identity
immutable revisions
exact snapshots
schemas and domain adapters
semantic query/follow/inspect operations
projections and bidirectional semantic editing
candidate -> migration -> validation -> conflict -> promotion
session and branch semantic topology
ContinuationAnchor semantics
BranchResult semantics
context-isolation policy
agent profiles as semantic/context configuration
context-component activation
canonical effective model request construction
plan nodes
plan dependency DAG
one auto-advancing plan coordinator
branch/plan execution assignment
provider-continuation validity relative to Scriberig context fingerprints
semantic capability/trust policy
application operations
public Scriberig protocol/server/client/web semantics
execution provenance bound to semantic/session identities

    These concepts must not be replaced by upstream transcript, filesystem, task-list, or session semantics.

    4.2 Upstream owns commodity model/provider machinery¶

    Scriberig must not maintain a parallel model catalog implementation.

    Upstream owns:

    provider implementations
provider packages
provider discovery
provider authentication and credential resolution
model catalog loading/refresh
model metadata schema
provider/model compatibility metadata
model cost/context/output metadata
model-specific custom properties
sampling parameters
model-specific request-shaping properties
thinking-level names/order/support
thinking-level mapping to provider effort
thinking-level clamping
provider/model selector behavior
provider reload/package lifecycle

    Scriberig may store a reference or safe historical snapshot of the resolved upstream execution selection for provenance. It must not become the authority that decides which thinking levels or custom properties a model supports.

    The existing Scriberig-owned ModelDescriptor, ThinkingLevelDescriptor, ModelCapabilities, and model-library catalog are migration targets for removal or reduction to compatibility/protocol projections.

    4.3 Upstream owns the ordinary in-branch agent loop¶

    Use rpi-agent for commodity loop behavior such as:

    model invocation loop
tool-call schema handling
tool argument validation
streaming event normalization
tool result sequencing
cancellation
ordinary retry/settlement mechanics exposed by upstream

    Scriberig still decides:

    which branch is executing
what context that branch receives
which semantic capabilities become tools
whether a tool is atomic or branch-producing
when a child branch is created
what BranchResult returns to the parent
what durable session objects are recorded
what semantic mutations are allowed

    Do not adopt rpi-harness as canonical Scriberig session storage or branch identity. It solves a different session problem.

    4.4 Upstream owns the plugin/package host¶

    The integrated Scriberig agent product should use the upstream plugin ABI, extension loader, and package lifecycle rather than creating another model/tool/slash-command plugin system.

    Scriberig-specific integration supplies adapters and capability policy.

    For example:

    upstream plugin registers AgentTool
  -> Scriberig host checks configured trust/capability policy
  -> tool executes through allowed Scriberig/application capability or approved fallback environment
  -> any canonical semantic mutation still converges on Scriberig candidate/change semantics

    Scriberig domain adapters remain Scriberig semantic extensions because they define semantic meaning, parsing, reconciliation, validation, and projections. They are not replaced by the upstream agent plugin ABI.

    Where one extension needs both roles, keep the roles explicit:

    Scriberig domain extension
  -> semantic/domain capability

upstream rpi plugin/package
  -> agent/provider/UI/runtime extension

    Do not invent a second agent plugin loader to bridge them.

    4.5 Upstream owns the terminal product framework¶

    The active Scriberig TUI must run on upstream rpi-tui as the terminal runtime and component system.

    Upstream should own:

    terminal lifecycle
terminal input normalization
render scheduling/differential rendering
regular/fullscreen mode
scrolling
resize handling
focus
hardware cursor
editor/composer
selection/fuzzy lists
overlays
status/footer mechanics
Markdown rendering
theme/style system
copy/paste integration
model/provider/thinking selectors where upstream exposes them

    Scriberig must not retain a parallel Ratatui application shell as the normal product path.

    4.6 Scriberig custom terminal panels are upstream components¶

    Scriberig will still need custom semantic views because upstream cannot know Scriberig concepts.

    Those views are implemented on top of upstream UI contracts, not beside them.

    Examples:

    RecursiveConversationComponent
SessionTreeComponent
PlanComponent
SemanticExplorerComponent
SemanticInspectorComponent
ProjectionComponent
CandidateReviewComponent
OperationComponent
EffectivePromptComponent
ReasoningActivityComponent

    They should implement/use rpi-tui Component, TUI child composition, overlays, upstream text/layout/theme/scroll primitives, and upstream focus/input conventions.

    They may adapt Scriberig semantic state to UI rows. They may not recreate terminal lifecycle, a second widget framework, a second theme system, or a second event/render runtime.

    If a generally useful panel/layout/tree/table primitive is missing from upstream, contribute it upstream first and use it from there.

    5. The Upstream-First Rule¶

    For every implementation decision in the agent/TUI product layer, classify the desired behavior before coding.

    Class U — upstream commodity¶

    A feature belongs upstream when it is useful independent of Scriberig semantic knowledge.

    Examples:

    model catalog
provider packages
provider auth
thinking levels
model custom properties
model selector
provider selector
package manager
plugin ABI
agent loop
editor
Markdown
scrolling
terminal lifecycle
overlay placement
tree/list/table widget primitives
status/footer widget
copy/paste
terminal images, if later enabled

    Action:

    use upstream; if the API is not reusable enough, contribute/refactor upstream before adding a Scriberig implementation.

    Class S — Scriberig semantic¶

    A feature belongs in Scriberig when its meaning depends on Scriberig architecture.

    Examples:

    BranchResult
ContinuationAnchor
semantic entity/revision/snapshot navigation
candidate review
semantic diff
plan dependency semantics
context-component activation
semantic tool applicability
projection reconciliation
provider-continuation staleness after Scriberig context divergence

    Action:

    implement in Scriberig, but expose/present it through upstream runtime/UI extension seams.

    Class A — adapter¶

    An adapter translates between Class S semantics and Class U infrastructure.

    Examples:

    Scriberig semantic operation -> rpi AgentTool
Scriberig branch execution selection -> upstream resolved model selection
rpi AgentEvent -> Scriberig ModelInvocation/Activity
Scriberig ConversationModel -> rpi-tui Component rows
Scriberig capability denial -> upstream tool disabled/error result
upstream safe model snapshot -> Scriberig invocation provenance

    Adapters should be narrow and contain no duplicated catalog/UI/runtime policy.

    6. Model Catalog, Thinking, and Custom Model Properties¶

    This boundary is explicit because Scriberig currently duplicates it.

    6.1 Remove Scriberig as catalog authority¶

    Do not maintain Scriberig-owned truth equivalent to:

    ModelDescriptor
ModelCapabilities
ThinkingLevelDescriptor
supported thinking list
default thinking map
provider-specific model property schema
custom provider catalog parser
provider auth state

    The upstream catalog is authoritative for these values.

    6.2 Preserve Scriberig assignment semantics¶

    Scriberig still needs to say:

    this branch uses execution selection E
this plan node is assigned execution selection E
this invocation actually resolved to model M with thinking T

    That does not require a Scriberig model catalog.

    Use an upstream-owned execution-selection/configuration type where available. If upstream lacks a reusable safe selection/snapshot type, contribute one upstream.

    Scriberig durable records should contain only what Scriberig needs for reproducibility/provenance, conceptually:

    provider/model stable public identifiers
upstream catalog/version or selection fingerprint
selected thinking level as resolved by upstream
safe output-affecting model configuration snapshot/hash
safe provider/model metadata needed for historical explanation

    Do not persist resolved credentials or secret headers.

    6.3 Thinking levels are upstream semantics¶

    The TUI and runtime must ask upstream which levels a selected model supports.

    Do not hard-code or independently validate lists such as:

    off
minimal
low
medium
high
xhigh
max

    Scriberig may record the selected resolved value. Upstream decides support, mapping, fallback/clamping, and provider serialization.

    6.4 Custom model properties are upstream semantics¶

    Model-specific properties such as:

    sampling parameters
reasoning effort maps
compatibility flags
strict-tool support
custom headers/endpoint metadata
provider-specific request-shaping fields
input modality
context/output limits
cost metadata

    must come from upstream model/provider machinery.

    If the product needs a UI for editing arbitrary/custom model properties, that editor should be implemented as or extracted into upstream UI/config machinery. Scriberig should consume it rather than build a Scriberig-specific property editor.

    Scriberig may apply policy to whether a property/override is allowed in one project/session, but it must not redefine the property schema.

    7. Agent Profiles Remain Scriberig-Owned but Stop Owning Models¶

    AgentProfile remains a Scriberig semantic configuration because it controls Scriberig context composition, branching policy, semantic tool disclosure, and execution behavior.

    Refine its execution portion from a local model profile/catalog to an upstream execution reference.

    Conceptually:

    AgentProfile
  Scriberig profile identity/revision
  context components
  context policy
  branch policy
  semantic capability policy
  runtime budget policy
  preferred upstream execution selector/reference

    The upstream reference may express preferred provider/model/thinking/custom configuration through an upstream-owned type or stable serialized reference.

    Scriberig does not duplicate model metadata merely because an AgentProfile references a model.

    8. Per-Branch and Per-Plan-Node Model Assignment¶

    Scriberig's multi-model semantics remain unchanged:

    branch B -> execution assignment X
branch C -> execution assignment Y
plan node P -> execution assignment Z

    The ownership split is:

    Scriberig owns:
  which branch/node has an assignment
  inheritance/override rules
  assignment provenance
  when assignments change

upstream owns:
  what provider/model selections exist
  how a selection resolves
  thinking support
  custom model properties
  provider auth/readiness
  provider request serialization

    A plan/session branch may keep an assignment that later becomes unavailable in the live upstream catalog. Historical identity remains inspectable; new execution must resolve/fail through upstream with a structured availability error.

    9. Provider Continuation¶

    Scriberig continues to own the semantic validity decision for provider continuation because only Scriberig knows whether canonical branch context diverged.

    Upstream should own provider-wire continuation support whenever possible.

    Therefore:

    Scriberig:
  branch-local continuation association
  context fingerprint
  stale/reseed decision
  provider-neutral provenance

upstream:
  provider-specific conversation/response handles
  request serialization
  continuation request mechanics
  provider error interpretation

    If an upstream provider lacks continuation support required by Scriberig, contribute it upstream rather than extending a separate Scriberig HTTP provider implementation.

    10. Semantic Tools on Top of rpi-agent¶

    Scriberig semantic operations become rpi-agent tools through a thin adapter.

    The adapter owns:

    stable exposed tool name
JSON schema generated from Scriberig operation input
capability check hook
conversion to shared application operation
bounded semantic result projection
correlation back to Scriberig activity identity

    It does not own:

    provider tool-call parsing
ordinary tool-call ordering
stream settlement
agent loop cancellation
model transcript mechanics

    Those remain upstream.

    Branch-producing work¶

    When a tool request requires focused recursive work, the Scriberig adapter may suspend/complete the current upstream tool call by creating a Scriberig child branch, executing that branch through another upstream agent-loop instance, then returning the child's compact BranchResult projection as the tool result.

    The session tree is still Scriberig's.

    11. Upstream Plugins and Scriberig Trust¶

    Use the upstream plugin loader and package system for integrated agent-product extensions.

    Do not automatically grant all loaded upstream plugins every Scriberig capability.

    Scriberig contributes a host policy adapter that decides which registered tools/resources/commands are enabled in the current product/project/branch.

    A plugin tool that wants to alter understood semantic content must call public Scriberig semantic operations or operate through a Scriberig-provided tool adapter. Direct filesystem writes remain fallback/interoperability behavior, not the canonical semantic editing path.

    Where upstream plugin registration exposes a generic capability that Scriberig does not want for a given branch, Scriberig filters it from the model/tool surface rather than forking the plugin loader.

    12. TUI Target Architecture¶

    The terminal product should converge on:

    Scriberig application/session semantic models
        |
        v
thin Scriberig TUI adapters/components
        |
        v
rpi-tui Component / TUI APIs
        |
        v
upstream terminal runtime/render/input/theme/editor

    Not:

    rpi-tui primitive
        |
        v
scriberig-tui-kit converts to plain text
        |
        v
Ratatui widgets
        |
        v
Scriberig terminal runtime

    12.1 Remove the double-rendering bridge¶

    The final path must not render upstream widgets to ANSI/plain lines merely to reconstruct them as Ratatui Paragraphs.

    Use upstream components directly.

    12.2 Use upstream model controls¶

    Provider/model/thinking selectors and status presentation should come from upstream product/UI machinery.

    If those components are currently private to rpi-cli, extract or expose them upstream before Scriberig implements an alternative.

    12.3 Custom Scriberig panels use upstream composition¶

    The recursive session tree, plan status, semantic browser, projection/review, and model-observability surfaces are custom because their data is Scriberig-specific.

    They must nevertheless use upstream:

    component contract
layout primitives
overlays
focus
scrolling
text/style/theme
input handling
status/footer conventions

    A custom panel is not permission to retain the current Scriberig shell.

    13. Upstream UI Gaps Must Be Fixed Upstream¶

    If implementation discovers that rpi-tui lacks a reusable generic primitive required by Scriberig, classify it.

    Examples likely useful upstream:

    TreeView / hierarchical list
split/panel composition
virtualized large list/tree
structured status/footer slot
model custom-property editor
reusable provider/model/thinking selector
component registry/panel extension point
safe structured table

    If the primitive is generally useful, implement it upstream and consume it after pinning a compatible revision.

    A Scriberig-local implementation is acceptable only when the behavior is inherently Scriberig-semantic, such as how BranchResult rows relate to a ContinuationAnchor.

    14. Plugin-Supplied UI¶

    The reviewed upstream plugin ABI registers tools, providers, slash commands, event handlers, Markdown renderers, and resources. It does not currently establish that arbitrary native TUI panels are a stable plugin ABI.

    Therefore:

    1. built-in Scriberig semantic panels may directly implement upstream rpi-tui components;
    2. do not create a separate Scriberig plugin ABI just for terminal panels;
    3. if third-party agent plugins need custom panels, design/contribute a generic upstream panel/component extension point;
    4. keep Scriberig semantic-domain UI extension needs separate from the agent runtime plugin ABI where their lifecycle/security requirements differ.

    The important invariant is that all terminal panels render through the same upstream TUI framework.

    15. Dependency and Source Policy¶

    Prefer this dependency order:

    released upstream crate
  > pinned upstream git revision
  > temporary local patch with explicit upstream PR/issue
  > copied/vendor fork only as a last resort

    The current hand-copied third_party/rpi-tui tree is not the preferred final arrangement.

    Once required upstream APIs are available through a release or pinned Git revision:

    • remove the hand-maintained vendor fork;
    • remove scriberig-tui-kit if it only wraps upstream commodity behavior;
    • keep a small integration/adaptation crate only for Scriberig-semantic adapters;
    • preserve licensing notices through normal dependency/license reporting.

    Offline/reproducible builds may use generated Cargo vendoring in release tooling without making the vendored copy the architectural source of truth.

    16. Server, Protocol, and Web Remain Scriberig Surfaces¶

    Do not replace the Scriberig public server or web semantic API with upstream remote-agent session semantics.

    Scriberig's server must expose Scriberig concepts such as entities, snapshots, migrations, branches, plans, candidates, and operations.

    However, server-side model/provider information should be projected from upstream runtime state rather than reconstructed by Scriberig.

    For example:

    upstream model catalog
  -> safe protocol projection
  -> web model selector

    The web client may have its own React rendering, but it consumes the same upstream-resolved model/provider/thinking/custom-property semantics through Scriberig's server projection.

    Scriberig protocol types should avoid inventing a second model schema. Prefer safe passthrough/projection types generated from or versioned against upstream public model descriptors.

    17. Migration Strategy¶

    The correction is executed in ordered slices. Do not perform another giant compatibility refactor that leaves all old owners in place.

    Phase 1 — freeze and classify¶

    Inventory every local commodity owner and map it to an upstream owner or an explicit upstream-gap issue.

    No new local catalog/TUI/plugin/runtime abstractions may be added during this phase.

    Phase 2 — model/provider ownership¶

    Move catalog, provider, auth, thinking, custom properties, selection, and model readiness to upstream APIs.

    Delete local model-catalog authority as soon as consumers migrate.

    Phase 3 — agent loop and extension host¶

    Adopt rpi-agent and the upstream plugin/extension/package host for integrated agent execution.

    Keep Scriberig branch/context/tool semantics as adapters around that loop.

    Phase 4 — upstream terminal runtime¶

    Make rpi-tui the actual terminal lifecycle/render/input owner.

    Move model/provider/thinking UI to upstream components.

    Phase 5 — Scriberig semantic components¶

    Port recursive session, plan, semantic explorer, projection/change review, prompt/reasoning, and operation views into upstream components.

    Phase 6 — delete duplicate infrastructure¶

    Remove Ratatui shell ownership, local terminal lifecycle, local generic TUI kit, local catalog/thinking machinery, local plugin duplication, and superseded provider/tool-loop code.

    18. Acceptance Criteria That Prevent a Repeat of the Previous Outcome¶

    The correction is not complete until all of these are true.

    18.1 Model/provider delegation¶

    • No Scriberig-owned model catalog determines available providers/models.
    • No Scriberig-owned thinking-level catalog determines supported thinking values.
    • Model custom properties are defined/interpreted by upstream.
    • Provider authentication/readiness comes from upstream.
    • TUI model/provider/thinking controls consume upstream data/components.
    • Branch/plan assignment stores references/provenance without becoming a catalog.

    18.2 Agent/runtime delegation¶

    • Ordinary in-branch model/tool loop runs through rpi-agent or its current upstream replacement.
    • Provider wire implementations come from upstream.
    • Upstream plugin/extension/package machinery is used for integrated agent extensions.
    • Scriberig does not adopt upstream session/harness identity as canonical state.

    18.3 TUI delegation¶

    • The active TUI terminal lifecycle is upstream-owned.
    • scriberig-tui has no direct Ratatui dependency in the final path.
    • The active shell is composed from upstream TUI/Component APIs.
    • The composer is an upstream component, not rendered through a Scriberig text bridge.
    • Markdown is rendered by upstream directly, not rendered then stripped and reconstructed.
    • Focus, overlays, scrolling, resize, theme and status mechanics are upstream-owned.
    • Provider/model/thinking selection is upstream UI.
    • Scriberig custom panels are upstream components.

    18.4 Deletion evidence¶

    The final implementation report must include a deletion ledger showing the local owners removed.

    At minimum review/remove current equivalents of:

    third_party/rpi-tui hand-maintained fork
scriberig-tui-kit generic wrappers
Ratatui application shell
direct Scriberig Crossterm lifecycle
local generic composer/editor
local Markdown/fuzzy/theme wrappers
local model descriptor/library/catalog authority
local thinking-level support/mapping authority
local provider/model selector logic
local plugin/extension host if any
local provider wire code superseded by upstream
local ordinary tool-loop code superseded by rpi-agent

    Keeping one of these requires an explicit architectural exception in this Level-2 document, not merely a code comment.

    18.5 Visible product acceptance¶

    The migration must include a before/after deterministic terminal scenario proving that the normal TUI is actually running on the upstream interaction model.

    A successful migration cannot be accepted solely because internal unit tests prove an upstream editor was called.

    The golden/snapshot acceptance should exercise:

    startup composer
streaming answer
Markdown/code rendering
model/provider selector
thinking selector
one custom model property flow when supported
slash command/palette
recursive child branch
historical reply anchor
plan state
semantic explorer
candidate review
resize/scroll
terminal exit

    The output need not clone upstream's CLI product exactly, but the upstream component/runtime behavior must be the actual active implementation.

    Implement this correction in order:

    144  Stop local commodity ownership and establish upstream contribution gates
  |

  |

    Each task must keep its checklist current and must not begin the next task until its completion gate is satisfied.

    1. the upstream capability exists in a released version;
    2. the upstream capability exists at a pinned reviewed commit that Scriberig can consume;
    3. the user explicitly authorizes a temporary local exception with an upstream issue/PR and a removal condition.

    20. Relationship to Existing Tasks 138–143¶

    Tasks 138–142 are historical foundation work. Their focused tests and useful safety/conformance improvements should be retained where compatible.

    Task 143 must not be completed as the final adoption gate under the old ownership model.

    Its remaining repository test gate can still be useful, but final architectural acceptance moves to task 149 and this Level-2 plan.

    Do not interpret checked boxes in 138–142 as permission to preserve duplicated commodity ownership that this plan explicitly removes.

    21. Final Principle¶

    The simplest test for every contested owner is:

    If this code would be useful in a generic terminal coding-agent runtime that knew nothing about Scriberig's semantic graph, revisions, branches, plans, migrations, or validation, why is Scriberig maintaining it?

    If the answer is only convenience or historical accident, move it upstream.

    Scriberig should spend its engineering budget on the semantic knowledge system, recursive context architecture, durable plans, semantic operations, validation/promotion, and cross-surface product semantics that upstream does not provide.
