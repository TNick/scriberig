    Workspace and Package Layout¶

    1. Purpose¶

    This document turns the architectural constraints in design/level-1/001. vision and principles.md into a concrete repository and package layout.

    It defines boundaries and dependency direction. It does not define the internal data model, persistence schema, migration algorithms, protocol payloads, or domain-specific semantics. Those require later Level 1 and Level 2 decisions.

    The layout must preserve these Level 1 requirements:

    • storage and domain libraries are useful without an agent runtime;
    • CLI, API, TUI, web, and agents are peer consumers of shared application capabilities;
    • the official web editor uses the same public libraries available to third parties;
    • domain adapters plug into shared storage, query, migration, and projection systems;
    • all write surfaces converge on one change model;
    • product capabilities can be developed vertically across interfaces;
    • lower layers never depend on higher product layers.

    2. Repository Shape¶

    Scriberig is a monorepo containing a Rust workspace and a TypeScript/web workspace.

    The target top-level layout is:

    3. Rust Workspace Layers¶

    3.1 Foundation¶

    These crates define the reusable knowledge platform.

    scriberig-core¶

    Owns universal identifiers and small cross-cutting types that must not depend on storage, agents, transport, UI, or domain adapters.

    It is the bottom of the dependency graph.

    scriberig-store¶

    Defines persistence-facing abstractions for revisions, snapshots, and stored objects.

    It depends on scriberig-core only at this stage.

    A concrete storage backend must remain replaceable. Backend-specific persistence should not leak into higher layers.

    scriberig-schema¶

    Defines the reusable schema/type vocabulary used by domains to describe structured knowledge.

    It depends on scriberig-core.

    scriberig-graph¶

    Defines the universal entity/relation graph view over stored knowledge.

    It may depend on:

    • scriberig-core;
    • scriberig-store;
    • scriberig-schema.

    It must not depend on agents, server code, CLI code, TUI code, or web-specific concepts.

    scriberig-query¶

    Defines domain-independent query and traversal concepts over the graph.

    It may depend on scriberig-core and scriberig-graph.

    scriberig-migration¶

    Defines the common change boundary used by all mutation surfaces.

    It may depend on the core graph/storage abstractions but not on product interfaces.

    scriberig-projection¶

    Defines common projection concepts: render/import/reconcile boundaries and projection state abstractions.

    It may depend on the graph and migration layers.

    It must not contain Markdown-, Rust-, PDF-, or UI-specific implementations.

    scriberig-session¶

    Defines sessions, branches, goals, tool interactions, and related structured session concepts as another domain over the universal system.

    It must remain usable without an agent runtime.

    4. Application Layer¶

    scriberig-app¶

    This crate is the shared application-operation boundary.

    The CLI, server, TUI, web server integration, and agent runtime must call application capabilities through this layer rather than reproduce business logic in their own surfaces.

    Examples of future operations include inspecting semantic objects, querying, rendering, proposing changes, validating changes, branching, and committing. Their exact APIs are deferred.

    scriberig-app may depend on the foundation crates and selected domain adapters. Foundation crates must never depend on it.

    5. Transport and External Client Layer¶

    scriberig-protocol¶

    Owns stable serializable transport-facing data types used between remote clients and the server.

    It must not contain server business logic.

    It should depend on small stable identifier/value types, not on backend implementation details.

    The exact schema-generation mechanism for TypeScript is deferred, but the Rust and TypeScript protocol packages must represent one wire contract rather than diverging manually.

    scriberig-client¶

    Provides a reusable Rust client for a running Scriberig server.

    It depends on scriberig-protocol, not on server internals.

    scriberig-server¶

    Adapts remote requests onto scriberig-app operations and emits protocol responses/events.

    The server is an adapter. It is not the owner of application semantics.

    6. Agent Layer¶

    scriberig-agent-core¶

    Contains reusable agent-facing concepts such as tool descriptions, capability exposure, semantic navigation adapters, and context construction interfaces.

    It consumes application/session capabilities. Nothing in the foundation may depend on it.

    scriberig-agent-runtime¶

    Contains integrated agent execution/orchestration behavior and model-provider integration.

    It depends on scriberig-agent-core and higher product-level capabilities.

    Splitting agent concepts from runtime orchestration keeps the reusable knowledge platform independent from agent execution.

    7. Native Product Surfaces¶

    scriberig-tui¶

    Implements the terminal UI over shared application capabilities.

    It must not own storage or mutation semantics.

    scriberig-cli¶

    Defines command parsing and command dispatch for the Scriberig executable.

    Commands may invoke local application operations, TUI mode, server mode, or agent runtime behavior. Core business logic belongs below this crate.

    apps/scriberig¶

    Contains the final Rust executable named scriberig.

    The executable is composition only. It wires together the CLI, application layer, server, TUI, and agent runtime. It should contain minimal logic of its own.

    The same executable is expected to support the product modes selected by later designs, including command-style operation, server mode, TUI mode, and agent operation.

    8. Domain Adapter Location¶

    Domain-specific Rust crates belong under:

    crates/domains/

    A domain adapter may provide:

    • schemas;
    • parsers;
    • renderers;
    • reconcilers;
    • validators;
    • derived indexes;
    • specialized queries;
    • semantic operations.

    A domain crate may depend on the shared foundation appropriate to its function. It may not introduce an alternative persistence, snapshot, migration, or agent-access architecture.

    The first concrete domain directories must be introduced only by a design document that defines that domain sufficiently to implement it.

    9. TypeScript and Web Workspace¶

    The web workspace uses pnpm and lives entirely under web/.

    Public packages use the @scriberig/ namespace.

    @scriberig/protocol¶

    TypeScript representation of the wire contract exposed by scriberig-protocol.

    It has no React or MUI dependency.

    @scriberig/client¶

    Browser/Node client for the Scriberig server.

    It depends on @scriberig/protocol.

    @scriberig/model¶

    Client-side domain/application state: object caches, snapshot awareness, selections, navigation state, operation state, and other UI-independent client behavior.

    It depends on the client/protocol layer and has no MUI dependency.

    @scriberig/editor-core¶

    Headless reusable editor and browser controllers for semantic trees, selection, commands, diffs, history, and structured editing behavior.

    It must not impose product styling.

    @scriberig/react¶

    React bindings/hooks over the public model and client capabilities.

    It must not require MUI.

    @scriberig/components¶

    Reusable non-MUI Scriberig UI components or component primitives built on the public React/editor layers.

    It must remain styleable by consumers.

    @scriberig/components-mui¶

    Opinionated MUI implementation built on the reusable web layers.

    MUI-specific dependencies must stop here or in the integrated editor application.

    @scriberig/agent-ui¶

    Reusable agent/session UI primitives built on the same model, selection, protocol, and operation concepts used by other web surfaces.

    web/apps/editor¶

    The complete Scriberig browser editor.

    It is a consumer of the public packages above. It must not import private server implementation code or bypass the public client/model abstractions.

    The editor must eventually combine low-level and high-level views, including raw knowledge/revision browsing, semantic views, projection views, history/diffs, session branches, and agent commands scoped to semantic selections.

    10. Required Dependency Direction¶

    The conceptual Rust dependency direction is:

    scriberig-core
    |
    +--> scriberig-store
    +--> scriberig-schema
              |
              v
         scriberig-graph
          /      |      \
         v       v       v
      query   migration  projection
         \       |       /
          \      |      /
           +-- session --+
                 |
                 v
            scriberig-app
              /      \
             v        v
        protocol     agent-core
           |             |
           v             v
        client       agent-runtime
           |
           +----> server

scriberig-app ---> tui
scriberig-app ---> cli/product composition

    This diagram is directional, not exhaustive. The invariant is more important than exact edges:

    reusable foundation -> application operations -> adapters/product surfaces

    Never the reverse.

    The web dependency direction is:

    @scriberig/protocol
        |
        v

     v       v

        +--> agent-ui
                 |

          integrated editor

    No public package may depend on web/apps/editor.

    12. Scaffold Rules¶

    The initial scaffold must obey all of the following:

    • use Rust edition 2024;
    • keep package versions at 0.1.0 until release/versioning design exists;
    • use workspace dependency declarations where practical;
    • keep all newly created Rust crates compileable with cargo check --workspace;
    • keep source files minimal and documentation-oriented;
    • do not implement placeholder fake domain behavior;
    • do not add concrete database schemas;
    • do not define wire payloads beyond what is required for an empty package to compile;
    • do not create domain adapter crates yet;
    • do not create private APIs solely for the official editor;
    • do not add MUI dependencies outside components-mui or the integrated editor;
    • do not add agent dependencies to foundation crates.

    13. Acceptance Criteria¶

    The scaffold is complete when:

    • the Rust workspace recognizes all prescribed Rust members;
    • cargo check --workspace succeeds;
    • every Rust package has a clear crate-level statement of its architectural role;
    • the Scriberig executable builds without containing substantive application behavior;
    • pnpm recognizes all prescribed web packages and the editor app;
    • TypeScript package boundaries match this document;
    • the public web packages do not import from the integrated editor app;
    • MUI is isolated to the MUI-specific package/editor boundary;
    • .gitignore covers generated artifacts for both workspaces;
    • no semantic implementation has been invented ahead of its design.

    14. Level 3 Decomposition¶

    The scaffold should be implemented by focused Level 3 tasks rather than one agent changing the whole repository at once:

    1. initialize the Rust workspace and foundation crates;
    2. scaffold Rust application, protocol, agent, and native surface crates;
    3. initialize the TypeScript/web workspace and headless/public packages;
    4. scaffold UI packages and the integrated editor shell.

    Each Level 3 document must repeat the dependency constraints relevant to its task and include explicit acceptance checks.
