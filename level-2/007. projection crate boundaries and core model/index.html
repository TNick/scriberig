    Projection Crate Boundaries and Core Model¶

    Purpose¶

    This document turns the file-facing requirements of design/level-1/006. projections and bidirectional editing.md into concrete Rust library boundaries.

    It covers only projection capabilities that are required to create, track, render, and reconcile external files. Other projection kinds such as browser views and agent context remain governed by Level 1 and should get their own lower-level designs later.

    This design depends on the identity, persistence, and migration layers defined by Levels 1–5. It does not change those models.

    Required crates¶

    Create three backend-independent/domain-oriented crates:

    crates/
├── sr-projection/
├── sr-projection-fs/
└── sr-markdown/

    Dependency direction:

    sr-core
   ↑
sr-store
   ↑
sr-change
   ↑
sr-projection
   ↑          ↑
sr-projection-fs   sr-markdown

    sr-markdown may also depend on the universal graph/schema crates once those exist.

    No crate in this slice may depend on agents, sessions, CLI, HTTP, TUI, React, or a concrete storage backend.

    sr-projection¶

    sr-projection owns domain-independent projection concepts.

    It must define public types or traits for:

    • projection identity/reference;
    • projection class;
    • projection capabilities;
    • projection kind;
    • style reference;
    • renderer version;
    • rendering context;
    • rendered output metadata;
    • persistent projection specification;
    • runtime synchronization state boundary;
    • adapter capabilities;
    • rendering;
    • parsing of editable representations;
    • reconciliation of parsed candidates;
    • projection validation hooks;
    • structured projection/import errors.

    The crate must not know about filesystem watcher APIs, Markdown syntax, Rust ASTs, or agents.

    Projection classes¶

    The core model must represent at least:

    ReadOnly
Editable
Ephemeral
Interactive

    For the file-focused implementation slice, ReadOnly and Editable must be fully usable. The other variants may initially be model-only.

    Projection capabilities¶

    Adapters must declare capabilities instead of callers inferring them.

    At minimum:

    renderable
parseable
editable
round_trip_capable
structure_preserving
style_preserving

    Capabilities must be explicit and deterministic for a given adapter/version.

    Projection specification¶

    A persistent projection specification represents user-meaningful configuration. It should be able to identify:

    • semantic scope;
    • projection kind;
    • projection class;
    • style entity/revision or style selector;
    • adapter identity/version;
    • external location when applicable;
    • ownership policy;
    • domain configuration needed for deterministic rendering.

    The specification is distinct from runtime synchronization state.

    User-meaningful projection configuration may live as normal knowledge entities. Operational sync metadata may live in derived/runtime storage.

    Render contract¶

    The rendering contract must make all output-affecting inputs explicit enough for reproducibility and cache keys.

    Conceptually:

    render(
    semantic scope,
    exact snapshot/revisions,
    projection kind,
    style revision,
    renderer version,
    rendering context
) -> RenderedProjection

    A renderer must not read undeclared mutable global settings that affect output.

    RenderedProjection must expose enough metadata to identify the exact bytes/text produced and the exact semantic/style inputs used.

    Editable adapter contract¶

    An editable adapter must separate parsing from reconciliation.

    Conceptually:

    external representation
    -> parse
    -> candidate semantic representation
    -> reconcile(existing canonical state)
    -> semantic operations/migration proposal

    Parsing must not assign stable canonical entity identity merely because candidate nodes happen to occupy similar positions.

    Reconciliation is responsible for justified continuity.

    Reconciliation result¶

    The generic projection layer must support results equivalent to:

    NoSemanticChange
MigrationProposal
Ambiguous
Conflict
InvalidExternalState

    The exact Rust enum names may differ, but the states must remain distinguishable.

    A formatting-only external edit must be representable as NoSemanticChange rather than a fake migration.

    Structured diagnostics¶

    Projection errors and conflicts must preserve structured information suitable for CLI, API, UI, and agent rendering.

    Do not reduce all failures to strings.

    At minimum, diagnostics must be able to identify:

    • projection/specification;
    • semantic scope;
    • synchronization base;
    • affected entity when known;
    • stage: render, observe, parse, reconcile, validate, commit, or rerender;
    • domain-specific details;
    • retryability where meaningful.

    Style model¶

    sr-projection owns only the universal reference to style configuration and generic cache identity requirements.

    Domain crates own actual style properties.

    A style affecting output must resolve to an immutable revision or an equivalent exact immutable value before rendering.

    Changing style must not create semantic content revisions merely because rendered bytes change.

    Incremental rendering boundary¶

    The core renderer API must permit adapters to return or use reusable intermediate fragments keyed by exact local immutable inputs.

    Do not require all adapters to implement incremental rendering immediately.

    Do not key all rendering caches only by global SnapshotId.

    Prescribed files¶

    Implementation of this design must create at least:

    crates/sr-projection/Cargo.toml
crates/sr-projection/src/lib.rs
crates/sr-projection/src/model.rs
crates/sr-projection/src/capabilities.rs
crates/sr-projection/src/style.rs
crates/sr-projection/src/render.rs
crates/sr-projection/src/adapter.rs
crates/sr-projection/src/reconcile.rs
crates/sr-projection/src/diagnostic.rs
crates/sr-projection/src/state.rs
crates/sr-projection/tests/projection_conformance.rs

crates/sr-projection-fs/Cargo.toml
crates/sr-projection-fs/src/lib.rs

crates/sr-markdown/Cargo.toml
crates/sr-markdown/src/lib.rs

    The workspace Cargo.toml must include the three crates once implemented.

    Architectural rules¶

    • Canonical state is never replaced directly from parsed projection bytes.
    • Projection code consumes public storage/change interfaces; it must not issue SQL directly.
    • sr-projection is domain-independent.
    • sr-projection-fs owns filesystem-specific behavior and depends on sr-projection, not the reverse.
    • sr-markdown implements projection contracts; sr-projection never depends on Markdown.
    • Agent functionality must remain optional and above these crates.
    • UI code must not gain a separate privileged mutation path.

    Completion criteria¶

    This design is satisfied when all three crates can exist in the workspace with the dependency direction above, sr-projection expresses the complete domain-independent render/parse/reconcile lifecycle, and no file/domain/agent-specific assumption leaks into its public core model.
