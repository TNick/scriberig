    Rich Project Artifacts: Office, CAD, and Geospatial Implementation Plan¶

    1. Purpose¶

    This document turns level-1/025. compound artifacts scalable collections and rich domain editing.md into an implementation plan for the current Scriberig repository.

    It also refines and depends on:

    • level-2/007. projection crate boundaries and core model.md;
    • level-2/008. filesystem projection synchronization.md;
    • level-2/010. universal query and operation implementation.md;
    • level-2/011. application operations protocol and runtime boundaries.md;
    • level-2/012. capability matrix and cross surface conformance.md;
    • level-2/016. universal knowledge model rust libraries.md;
    • level-2/017. web workspace packages and integrated editor.md;
    • level-2/019. change history and merge crate design.md;
    • level-2/024. agent operations protocol and cross surface product contract.md;
    • level-2/025. first useful project workflow vertical slice.md;
    • level-2/027. project wide candidate workspaces validation and materialization.md;
    • level-2/032. upstream first agent runtime and terminal product ownership correction.md;
    • level-2/034. projection style resolution loss-aware reconciliation and cross-surface contracts.md.

    The goal is to make a mixed project containing XLSX, DOCX, CAD, QGIS projects, and GIS layers behave like one Scriberig project: semantically navigable, editable through domain operations, candidate-based, reviewable, validated, and materialized through shared infrastructure.

    2. Current Repository Baseline¶

    The branch already contains these relevant owners:

    crates/scriberig-project

    The implementation must extend these boundaries first. Do not create a second project catalog, a second change engine, a second projection engine, a second protocol stack, or product-local domain stores.

    The current binary domain only describes opaque binary files. It remains a fallback for unsupported artifacts; it must not become the implementation for supported XLSX/DOCX/CAD/GIS semantics.

    The current PDF domain is the closest precedent for preserving exact source evidence while deriving richer semantic structure.

    3. Implementation Strategy¶

    Implement in this order:

    Phase A  shared artifact + scalable collection infrastructure
Phase B  XLSX spreadsheet vertical slice
Phase C  DOCX rich-document vertical slice
Phase D  CAD schema + DXF vertical slice
Phase E  optional DWG provider boundary
Phase F  geospatial datasets + QGIS project vertical slice
Phase G  shared rich projections and cross-surface UI
Phase H  mixed-project conformance and product gates

    Do not begin with four unrelated parser integrations. Shared correctness infrastructure must exist before format-specific write support.

    4. Shared Logical Artifact Model¶

    4.1 Ownership¶

    Use the existing project/domain/projection boundaries.

    Recommended ownership:

    scriberig-project
  scan classification
  grouping physical paths into logical imported artifacts
  project-relative source membership

universal graph/schema/domain crates
  artifact entities/revisions/relations as semantic knowledge

sr-projection
  artifact projection identity
  fidelity/editability descriptors
  exact baseline association
  logical output member descriptions

sr-projection-fs
  staged filesystem members
  multi-member write/recovery receipts
  external baseline verification

domain crates
  package/container parsing
  artifact grouping rules specific to the format
  semantic mapping
  rendering/reconciliation

    Do not add a new generic scriberig-artifact-store unless implementation audit proves the existing immutable store/blob/projection infrastructure cannot represent exact artifact evidence without architectural distortion. If a new crate is truly required, document the gap in the implementing Level-3 task before adding it.

    4.2 Shared types¶

    Introduce or reuse contracts equivalent to:

    ArtifactKind
ArtifactMemberId / logical member key
ArtifactMember
ArtifactSourceEvidence
ArtifactExternalReference
ArtifactPreservationMode
ArtifactFidelity
ArtifactMaterializationSet
ArtifactMaterializationReceipt

    These names are illustrative. Reuse current repository naming conventions where equivalent types already exist.

    4.3 Physical member identity¶

    A member needs:

    logical member key
physical target kind
project-relative path or container part name when applicable
exact source/output digest
media/format metadata
required/optional role

    Do not use absolute local path as stable semantic identity.

    5. Scan and Import Changes¶

    Extend project classification/import so one scan manifest can describe both raw files and logical grouping candidates.

    Required behavior:

    1. scanning still records every selected regular file as exact evidence;
    2. classification may nominate a grouping rule;
    3. import groups related files only through deterministic domain rules;
    4. one file may be imported as a compound container without extracting members as project files;
    5. grouped members retain their project-relative paths and digests;
    6. grouping ambiguity becomes a diagnostic instead of silently selecting a dataset;
    7. unsupported artifacts continue through the binary fallback.

    Examples:

    roads.shp + roads.dbf + roads.shx + roads.prj
  -> one Shapefile artifact

book.xlsx
  -> one OpenXML spreadsheet artifact with logical package parts

project.qgz
  -> one QGIS project artifact with logical package parts

    No implicit filesystem rescan is allowed during semantic import; use the persisted scan manifest as already required by project onboarding design.

    6. Exact Evidence and Opaque Preservation¶

    6.1 Exact source evidence¶

    Every supported rich artifact must retain an exact source digest and retrievable evidence according to existing retention/storage policy.

    For packages/multi-file sets, evidence is per member plus an exact artifact manifest identity.

    6.2 Opaque preservation record¶

    Domain adapters need an adapter-owned representation for unsupported-but-preserved content.

    Do not force unknown bytes into generic semantic property maps.

    The preserved content must be bound to:

    artifact/member
base source identity
adapter version
location/ownership context
preservation behavior

    6.3 Edit safety¶

    Before advertising write support, an adapter must prove one of:

    all source-significant content is modeled
or
unmodeled source-significant content is preserved through round trip
or
write support is restricted/read-only

    This decision participates in capability discovery.

    7. Scalable Collection Implementation¶

    7.1 Do not change the universal model contract¶

    A worksheet cell or GIS feature remains a semantic object from the consumer perspective.

    7.2 Add paged/ranged collection access¶

    Extend the current query/list abstractions only where needed to support domain-specific selectors such as:

    SpreadsheetRangeSelector
FeatureQuerySelector
SpatialWindow

    Prefer domain query AST extensions over adding one universal Any blob selector.

    7.3 Stable member handles¶

    Stable semantic handles must be reconstructible/resolvable without enumerating the full collection.

    For example, a cell handle may derive from workbook/worksheet identity plus semantic address and reconciliation state, but must still obey the Entity/Revision/Snapshot separation.

    A GIS feature may use a stable native feature ID as reconciliation evidence, but Scriberig identity remains separate.

    7.4 Indexes¶

    Indexes are derived/rebuildable unless a domain explicitly makes some external index part of canonical source semantics.

    Use existing derivation/provenance infrastructure for:

    • used-range indexes;
    • formula dependency indexes;
    • attribute indexes;
    • spatial R-tree-like indexes;
    • CAD layer/block/entity lookup indexes.

    8. Projection and Fidelity Extensions¶

    Build on Level-1 024 and Level-2 034.

    Projection capabilities must expose at least:

    projection kind
resolved style/policy when applicable
fidelity/editability
opaque-preservation status
baseline requirements
supported semantic operations
supported anchors/selections

    Add typed non-text anchors in domain crates or shared projection contracts where they are genuinely generic enough.

    Avoid one giant universal anchor enum if domain-owned opaque anchor payloads with schema identity fit the existing design better.

    Required cross-surface semantics:

    selection in UI projection
  -> semantic handle + exact snapshot/revision
  -> application semantic operation
  -> candidate

    Never make grid row number, canvas pixel coordinate, map screen coordinate, or terminal row a canonical semantic identity.

    9. Compound Materialization¶

    Extend sr-projection-fs or the existing materialization owner with staged multi-member output.

    Required state machine:

    render complete artifact member set
validate staged set
verify expected external baseline(s)
stage every output
commit/replace members
record per-member + artifact receipt
establish new synchronization baseline

    If a platform cannot atomically replace all members, implement explicit recovery journal/receipt semantics. Never report success after updating only some mandatory members.

    Container formats such as XLSX/DOCX/QGZ may materialize to one outer file but should still produce logical member diagnostics internally when useful.

    10. Spreadsheet Domain and XLSX Adapter¶

    10.1 New crate¶

    Add:

    crates/domains/scriberig-domain-spreadsheet

    This crate owns the format-independent spreadsheet schema/operations.

    Add a separate XLSX adapter either as focused modules in that crate initially or as:

    crates/domains/scriberig-domain-xlsx

    Prefer a separate crate once external OpenXML dependencies or package-specific logic are nontrivial. Do not make generic spreadsheet semantics depend on XLSX implementation types.

    10.2 Minimum schema¶

    Implement at least:

    Workbook
Worksheet
Cell
Range
Formula
DefinedName
Table
CellStyleRef

    Rows/columns may be structural/index concepts rather than one entity per empty row/column. Avoid eager empty-grid expansion.

    10.3 Minimum XLSX fidelity¶

    The first vertical slice must support:

    • workbook and sheet names;
    • scalar cell values;
    • formulas as authored expressions;
    • shared strings as an adapter representation detail;
    • basic number/text/date distinction where safely available;
    • used-range discovery;
    • preserving package parts not modified by the operation when possible;
    • deterministic materialization;
    • reopen validation.

    Charts, macros, pivot tables, external connections, signatures, and advanced formatting may remain preserved opaque/read-only initially, but their presence must influence fidelity/write capability if the chosen library cannot preserve them.

    10.4 Semantic operations¶

    First operations:

    spreadsheet.set_cell_value
spreadsheet.set_formula
spreadsheet.rename_sheet
spreadsheet.insert_rows

    If insert-row formula rewriting cannot be made correct in the first implementation, do not expose that operation until it is correct. Start with set-cell/set-formula vertical slice.

    10.5 Library policy¶

    Evaluate current Rust XLSX libraries during implementation. External library choice is adapter implementation detail and must be documented in THIRD_PARTY_NOTICES.md when required.

    Do not let an external library's in-memory object graph become the Scriberig canonical schema.

    11. Rich Document Domain and DOCX Adapter¶

    11.1 Shared document concepts¶

    Prefer reuse/alignment with existing Markdown document semantic concepts instead of duplicating Paragraph, TableRow, and TableCell semantics without reason.

    Where current Markdown types are format-specific, introduce a small shared rich-document schema crate only if reuse cannot be achieved cleanly through schema specialization.

    Recommended new domain crate:

    crates/domains/scriberig-domain-document

    with DOCX-specific adapter crate/modules:

    crates/domains/scriberig-domain-docx

    11.2 Minimum schema¶

    Support:

    Document
Section
Paragraph
Inline/Run
Table
TableRow
TableCell
ImageReference
Hyperlink

    DOCX-specific extension types include:

    DocumentStyle
HeaderFooter
Footnote
Endnote
Bookmark
Field
Comment
TrackedChange
ContentControl

    Not every extension must be editable in the first slice, but unsupported source-significant structures must be preserved or cause capability degradation.

    11.3 First semantic operations¶

    document.replace_paragraph
document.insert_paragraph
document.update_table_cell

    11.4 Layout¶

    Do not model Word pagination as canonical paragraph identity. Page layout/rendering is derived unless a future adapter/provider proves an exact layout contract.

    12.1 New CAD domain crate¶

    Add:

    crates/domains/scriberig-domain-cad

    Minimum schema:

    Drawing
DrawingSpace
Layout
Layer
BlockDefinition
BlockReference
Line
Polyline
Arc
Circle

    12.2 DXF adapter¶

    Implement DXF first because it provides a practical editable interchange target.

    The adapter must:

    • parse supported entity types;
    • preserve native handles as external identifiers/provenance;
    • preserve unsupported sections/entities where safe;
    • render deterministic supported DXF;
    • reconcile by native handle plus semantic/structural evidence;
    • validate by reopening output.

    First operations:

    cad.move_entity
cad.change_layer
cad.update_text
cad.insert_polyline

    Start with one or two operations if needed for vertical completion.

    12.3 DWG¶

    Do not make a native DWG library a mandatory dependency of the reusable CAD schema.

    Implement an adapter-provider interface able to describe:

    provider identity/version
read capability
write capability
supported object classes
fidelity/preservation guarantees
validation capability
license/deployment requirements

    An optional native/out-of-process provider may implement DWG later or in the same task when a suitable dependency is available.

    The initial product may legitimately expose DWG as inspect-only or provider-required while DXF is editable.

    13. Geospatial Dataset Domain¶

    13.1 New crate¶

    Add:

    crates/domains/scriberig-domain-geo

    Minimum schema:

    GeoDataset
GeoLayer
Feature
Geometry
Field
CoordinateReferenceSystem

    Raster support may be represented as a separate type family and remain inspect-only initially.

    13.2 Provider/adapters¶

    Use GDAL-compatible capability where practical, but keep GDAL bindings behind the geospatial adapter boundary. Do not add GDAL types to universal graph/protocol contracts.

    Initial editable formats:

    1. GeoPackage preferred;
    2. Shapefile for compound multi-file materialization coverage;
    3. GeoJSON optional if already easy to support.

    13.3 Spatial query operations¶

    Add domain query forms for:

    attribute predicate
bbox intersection
geometry intersection/within
nearest with bounded result count
layer extent

    All responses are paged and snapshot-bound.

    13.4 Semantic edit operations¶

    geo.set_attribute
geo.replace_geometry
geo.insert_feature
geo.delete_feature

    First vertical slice may require only set_attribute and one geometry edit.

    13.5 Geometry validity¶

    Geometry edits must run domain validation before promotion/materialization when the backend exposes validity checks.

    14. QGIS Project Domain¶

    Add:

    crates/domains/scriberig-domain-qgis

    This crate owns QGIS project semantics, not generic GIS data.

    Minimum semantic structure:

    QgisProject
LayerGroup
LayerReference
ProjectCrs
RendererConfiguration
LabelingConfiguration
Join
Relation
Layout
MapItem

    The adapter must support .qgs and .qgz project sources at least for inspection and reference resolution.

    Layer references resolve through explicit external/project artifact references to GeoLayer entities when an adapter can open them.

    Do not copy all referenced layer features into the QGIS project entity.

    First editable QGIS operations may be limited to:

    qgis.reorder_layer
qgis.rename_layer_reference
qgis.update_project_setting

    The golden GIS edit may edit the referenced GeoLayer while using QGIS only as composition/navigation context.

    15. Shared Application Operations¶

    Extend scriberig-app with domain-neutral orchestration and domain-specific registered operations rather than hard-coding format logic in transport/UI code.

    Required conceptual operations include:

    artifact.inspect_source
artifact.list_members
artifact.fidelity
artifact.render

spreadsheet.*
document.*
cad.*
geo.*
qgis.*

    Operations must be discoverable through existing capability mechanisms and capability-scoped for agents.

    Every write operation must create a candidate/change using the existing shared change model.

    16. Protocol and Client¶

    Transport only stable semantic DTOs.

    Do not serialize parser/library native objects.

    Add shared protocol/client DTOs for:

    • artifact member summaries;
    • fidelity/editability;
    • paged spreadsheet ranges;
    • bounded feature query results;
    • geometry summaries/transport representation;
    • drawing entity summaries;
    • typed projection anchors where needed;
    • domain operation arguments/results;
    • materialization/recovery diagnostics.

    Large binary package members or geometries must not be embedded blindly into ordinary list responses. Use bounded references/streaming/download mechanisms already available or add explicit artifact-content operations if needed.

    17. Agent Tool Exposure¶

    The agent should receive domain operations progressively based on selection/capability.

    Examples:

    selected Worksheet
  inspect
  list used ranges
  spreadsheet.set_cell_value
  spreadsheet.set_formula

selected GeoLayer
  inspect
  query features
  geo.set_attribute
  geo.replace_geometry

selected CAD entity
  inspect
  render drawing preview
  cad.move_entity

    Do not expose direct ZIP/XML/SQLite/DWG byte mutation as the normal tool path.

    Opaque/raw inspection may remain available as fallback evidence.

    18. Web Editor Integration¶

    Implement reusable web components before app-specific pages where practical.

    Recommended package ownership follows the existing dependency direction:

    protocol -> client -> model -> editor/react -> reusable components -> web app

    Minimum rich editors/views:

    • spreadsheet grid with bounded range loading and semantic cell selection;
    • document outline/paragraph/table editor;
    • CAD layer/entity explorer plus canvas or simplified vector preview;
    • map/layer/feature viewer with semantic selection;
    • shared artifact fidelity/source/member inspector;
    • candidate diff/review using existing shared change review contracts.

    Do not implement persistence/change logic in React components.

    19. TUI Integration¶

    Follow Level-2 032.

    The TUI must support:

    • semantic tree/list navigation of workbook/document/drawing/project/layer structures;
    • paged table-like inspection for cells/features;
    • compact geometry/entity/property inspection;
    • invocation of shared semantic operations;
    • candidate/change review;
    • projection/fidelity diagnostics;
    • artifact source/member inspection.

    It does not need a full terminal spreadsheet, word processor, CAD editor, or GIS map editor before the semantic workflow is considered complete.

    Use upstream RPI/RPI-TUI primitives for commodity terminal interaction and rendering.

    21. Validation Matrix¶

    Each domain needs focused validation.

    Shared¶

    • exact evidence digest preserved;
    • candidate does not mutate live materialization;
    • apply uses expected base snapshot;
    • failed validation leaves canonical state unchanged;
    • materialization receipt matches produced artifact set.

    XLSX¶

    • reopen produced package;
    • edited cell/formula matches semantic state;
    • unrelated cells/sheets preserved;
    • opaque-preservation/fidelity status respected.

    DOCX¶

    • reopen produced package;
    • edited paragraph/table cell matches;
    • unrelated paragraphs and preserved parts survive.

    DXF¶

    • reopen produced drawing;
    • edited entity remains addressable;
    • native handle behavior documented/tested;
    • unsupported content preservation behavior tested.

    Geo/QGIS¶

    • reopen dataset/project;
    • feature attribute/geometry matches;
    • CRS/schema preserved;
    • unrelated features preserved;
    • QGIS layer reference still resolves.

    22. Performance Requirements¶

    Add tests/benchmarks sufficient to prevent accidental eager loading.

    At minimum prove:

    • listing workbook sheets does not decode every cell into response DTOs;
    • reading a small spreadsheet range is bounded by the range plus required indexes;
    • querying a bounded GIS area does not serialize the entire layer;
    • TUI/web list models page results;
    • agent context receives summaries/selected results, not complete large artifacts.

    Do not require a production-scale benchmark corpus in the first implementation, but structure APIs so scaling does not require a breaking redesign.

    23. Dependency and Licensing Review¶

    Before adding each third-party parser/native library:

    1. inspect license;
    2. verify compatibility with the crate/product licensing boundary;
    3. record required notices;
    4. avoid leaking native/library types into public semantic APIs;
    5. make system/native dependencies optional when they are not universally available;
    6. provide deterministic test behavior when the optional provider is absent.

    DWG/native CAD and GDAL/system-library integration deserve explicit review.

    24. Level-3 Task Breakdown¶

    Implement through these ordered tasks:

    154  shared compound artifact, scalable collection, fidelity, and materialization infrastructure
155  spreadsheet domain and editable XLSX vertical slice
156  rich document domain and editable DOCX vertical slice
157  CAD domain and editable DXF vertical slice
158  optional DWG provider boundary and licensing-safe capability integration
159  geospatial datasets, spatial query, GeoPackage/Shapefile, and QGIS project integration
160  reusable web and RPI-TUI rich artifact projections and semantic editing surfaces
161  mixed rich-project conformance, performance, recovery, and real-process product gates

    Tasks are intentionally sequential at the infrastructure boundary. Format tasks may be parallelized only after task 154's shared contracts are stable and only when they do not introduce competing versions of those contracts.

    25. Definition of Completion¶

    This design is implemented when a user or agent can onboard a mixed project and perform the following without format-private mutation shortcuts:

    inspect workbook -> edit cell -> validate -> apply -> reopen XLSX
inspect DOCX -> edit paragraph/table cell -> validate -> apply -> reopen DOCX
inspect drawing -> edit supported DXF entity -> validate -> apply -> reopen DXF
inspect QGIS project -> resolve GeoLayer -> edit feature -> validate -> apply -> reopen dataset

    and when:

    • exact source evidence remains inspectable;
    • unsupported/opaque content is preserved or write support is explicitly restricted;
    • large collections remain bounded/paged;
    • all writes use shared candidate/change semantics;
    • local/remote/web/TUI/agent paths agree on domain capability and results;
    • no optional proprietary/native integration is required for unrelated domains.
