    Agent Runtime, Model Provider, and Branch Orchestration¶

    1. Purpose¶

    This document turns design/level-1/016. model driven agent execution and branch isolation.md into concrete Rust subsystem boundaries.

    It also depends on:

    1. design/level-1/009. agent interaction and sessions.md;
    2. design/level-2/011. application operations protocol and runtime boundaries.md;
    3. design/level-3/082. implement session domain structure and views.md.

    The controlling rule is:

    scriberig-agent-runtime owns provider communication and agent execution, but all semantic reads and mutations still flow through public application/session capabilities.

    The implementation must support nested session branches, OpenAI-compatible model endpoints, progressive tool disclosure, model-request fingerprinting, cancellation, and deterministic testing without a real model service.

    2. Package Ownership¶

    Keep the existing package split:

    crates/scriberig-agent-core/
crates/scriberig-agent-runtime/
crates/scriberig-session/
crates/scriberig-app/

    Do not introduce provider dependencies into foundation/domain crates.

    scriberig-agent-core¶

    Owns provider-neutral contracts that are useful independently of one concrete model transport:

    agent profile descriptors
tool descriptors and JSON-schema-like argument contracts
tool result projections
context input blocks
branch execution policy descriptors
provider-neutral model input/output forms where reuse is useful

    It must not perform HTTP.

    scriberig-agent-runtime¶

    Owns:

    OpenAI-compatible provider adapter
provider configuration and capability negotiation
model request execution and streaming
context compilation orchestration
request fingerprinting and cache lookup/write
model/tool loop
nested child-branch execution
operation cancellation
runtime events
execution budgets

    scriberig-session¶

    Owns durable provider-neutral session entities and views:

    Branch
Turn
ModelInvocation
ModelOutput
ToolInvocation
ToolResult
BranchResult
Summary

    Raw provider request/response JSON, if retained, is optional external/audit artifact data and is not the canonical session shape.

    scriberig-app¶

    Owns public start/continue/cancel/query operations and capability enforcement. The runtime is invoked through an application-facing service boundary rather than directly from product UIs.

    3. Target scriberig-agent-runtime Layout¶

    Converge on a structure equivalent to:

    crates/scriberig-agent-runtime/
├── Cargo.toml
└── src/
    ├── lib.rs
    ├── config.rs
    ├── error.rs
    ├── runtime.rs
    ├── budget.rs
    ├── cancel.rs
    ├── event.rs
    ├── provider/
    │   ├── mod.rs
    │   ├── types.rs
    │   ├── openai_compatible.rs
    │   ├── stream.rs
    │   └── error.rs
    ├── context/
    │   ├── mod.rs
    │   ├── compiler.rs
    │   ├── policy.rs
    │   ├── dependencies.rs
    │   └── fingerprint.rs
    ├── tools/
    │   ├── mod.rs
    │   ├── catalog.rs
    │   ├── dispatch.rs
    │   └── projection.rs
    ├── branch/
    │   ├── mod.rs
    │   ├── orchestrator.rs
    │   ├── state.rs
    │   ├── result.rs
    │   └── policy.rs
    └── cache/
        ├── mod.rs
        ├── key.rs
        ├── record.rs
        └── repository.rs

    Files may be split differently to remain below repository source-size limits, but the responsibilities must stay distinct.

    4. Provider-Neutral Model Contract¶

    Define an internal/public-as-needed provider trait conceptually equivalent to:

    ModelProvider
  capabilities() -> ProviderCapabilities
  invoke(ModelRequest, Cancellation) -> ModelResponse/stream

    The provider-neutral request must be able to represent:

    model identifier
ordered context/messages/blocks
tool definitions
tool choice policy
structured-output schema when requested
output-affecting generation parameters
request metadata safe for logging

    The provider-neutral response must be able to represent:

    assistant text blocks
structured output
tool calls
finish/termination reason
usage metadata
provider request identifier
provider model/fingerprint metadata when available

    Do not expose authorization headers or raw secret configuration through these structures.

    5. OpenAI-Compatible Adapter¶

    Implement the first provider adapter as an OpenAI-compatible HTTP client.

    Compatibility is capability-based rather than assuming every endpoint implements every feature identically.

    The adapter configuration includes at least:

    base_url
model
credential source
request timeout
connect timeout
stream enabled/disabled
compatibility mode/profile
optional default generation parameters

    Credentials are supplied through a secret source/environment/config mechanism owned by product composition. Never persist them in session records or cache keys.

    The adapter must support a compatibility subset sufficient for:

    • text assistant output;
    • tool/function definitions;
    • tool calls with structured arguments;
    • streaming when enabled;
    • usage metadata when returned;
    • structured provider errors.

    The exact HTTP path and wire envelope are adapter details. Support for multiple OpenAI-family endpoint styles may be added behind the same provider-neutral contract.

    Do not make upstream session code depend on OpenAI wire type names.

    6. HTTP and Async Boundary¶

    Provider network I/O is asynchronous work owned by the agent runtime.

    The first implementation should use a production HTTP client with:

    TLS support
request timeout
stream/body limits
cancellation support
proxy behavior inherited/configured explicitly
structured status/body errors

    reqwest is the preferred first implementation unless repository constraints established by the implementation task justify another client.

    The async runtime must remain above foundation/application semantics. Product composition may host the runtime on Tokio; lower semantic crates must not gain a Tokio dependency merely because model transport is asynchronous.

    Tests must be able to replace the HTTP provider with an in-memory fake provider.

    7. Provider Capability Model¶

    Represent provider support explicitly instead of scattering compatibility checks.

    At minimum track concepts equivalent to:

    streaming
function/tool calls
parallel tool calls
structured output
usage reporting
provider request IDs
reasoning controls, if exposed
maximum request context, when known

    The context compiler/orchestrator asks the provider capability model before using optional features.

    A provider lacking parallel tool-call support may serialize calls. A provider lacking structured-output support may use ordinary text/tool contracts where safe.

    Unsupported required capability produces a structured runtime failure before sending a malformed request.

    8. Agent Profile¶

    An agent profile identifies reusable execution policy independent of one session.

    Conceptually it includes:

    profile id/revision
system instructions
preferred provider profile
preferred model
context policy id/revision
initial tool exposure policy
branching policy
runtime budgets
default model parameters
cache policy

    Profiles must be versioned or otherwise fingerprintable so model request identity changes when behaviorally relevant profile content changes.

    A profile is configuration, not session identity. A session branch records which profile revision executed it.

    9. Context Compiler¶

    The context compiler receives a BranchExecutionContext and returns a provider-neutral CompiledContext plus an exact dependency manifest.

    Inputs may include:

    branch identity and purpose
current user instruction
parent branch descriptor/result chain
recent current-branch turns
accepted decisions/open tasks
semantic selection
explicitly pinned knowledge handles
relevant derived summaries/descriptions
available tools after capability filtering
context/token budget
provider capabilities

    The compiler must not simply concatenate the complete session transcript.

    It applies a context policy in a deterministic order so tests can prove the same input state produces the same compiled context before provider-specific serialization.

    10. Parent-to-Child Context Inheritance¶

    Creating a child branch requires an explicit inheritance plan.

    The plan may include:

    parent branch descriptor
selected parent result handles
selected accepted decisions
selected semantic scope
explicit user/delegation instruction
capability subset
base snapshot/workspace

    The child does not receive all parent turns by default.

    A branch policy may allow a bounded recent parent excerpt, but that choice is explicit and participates in context identity.

    When the child completes, the parent receives the child's BranchResult, not implicit access to the child transcript.

    11. Tool Catalog¶

    scriberig-agent-core exposes tool descriptors. scriberig-agent-runtime builds the tool catalog for each model step.

    A descriptor includes at least:

    stable tool id
human/model description
argument schema
result-shape description
read-only vs state-changing classification
atomic vs child-branch execution mode
capability requirement
optional semantic/domain applicability

    The runtime must never execute an arbitrary provider-returned name without resolving it against the trusted catalog.

    Tool schemas must be canonical/fingerprintable because they participate in model request identity.

    12. Progressive Tool Disclosure¶

    The initial catalog should be intentionally small.

    A practical bootstrap set may expose concepts equivalent to:

    inspect
list/follow
find/query
open referenced result
start focused branch

    Domain-specific operations become available when:

    • the current selection/domain advertises them;
    • an inspected result advertises a next operation;
    • the current agent profile explicitly enables them;
    • the branch capability scope permits them.

    The runtime recompiles tool definitions before the next model step when capability context changes.

    13. Tool Dispatch¶

    For every tool call:

    1. resolve tool id from the trusted catalog;
    2. parse and validate arguments;
    3. verify branch/application capability scope;
    4. determine execution mode;
    5. execute an atomic application operation or create a child branch;
    6. persist ToolInvocation and ToolResult session objects;
    7. construct a bounded tool-result projection for the next model step.

    A state-changing atomic operation still uses the shared application mutation/validation path.

    Provider tool-call identifiers may be recorded for correlation but are not semantic identity.

    14. Child-Branch Tool Mode¶

    A child-branch tool descriptor contains or resolves an execution specification equivalent to:

    purpose template
expected result kind
context inheritance policy
capability subset
base selection/snapshot/workspace
budget override or inherited limits

    The orchestrator creates the child branch before any child model request is made.

    The child branch runs the same model/tool loop recursively.

    When terminal, its compact result is returned to the parent as the tool result projection and durable BranchResult handle.

    Recursion depth and total branch counts are budgeted to prevent unbounded delegation.

    15. Branch Orchestrator State Machine¶

    Use an explicit state machine conceptually equivalent to:

    Created
-> CompilingContext
-> AwaitingModel
-> InterpretingModel
-> ExecutingTools / AwaitingChildren
-> CompilingContext ...
-> Completing
-> Completed

terminal alternatives:
Failed
Cancelled
BudgetExceeded

    State transitions produce runtime/application events.

    Durable session branch lifecycle may remain simpler (active/completed/abandoned) while runtime execution state is more granular. Do not overload canonical branch status with every transient scheduler state.

    16. Model Loop¶

    The core loop is:

    compile context
-> fingerprint request
-> optionally reuse cache
-> invoke provider
-> persist complete model output metadata
-> if final answer: complete branch
-> if tool calls: dispatch calls
-> append structured results
-> repeat

    The loop must enforce budgets before each expensive step.

    The runtime must reject malformed tool-call arguments with a structured tool error. Whether that error is returned to the model for self-correction or terminates execution is controlled by policy and error class.

    17. Parallel Tool Calls¶

    Parallel provider tool calls are permitted only when runtime semantics allow them.

    Safe parallel candidates are normally independent read-only atomic operations.

    State-changing operations, branch-producing operations sharing a mutable workspace, or calls with ordering dependencies must be serialized or explicitly isolated into independent child workspaces/branches.

    Provider support for parallel tool calls does not override Scriberig consistency rules.

    18. Context Dependency Manifest¶

    Every compiled context carries a manifest of exact dependencies used to construct it.

    Dependency records include concepts such as:

    session object + exact revision
project entity + exact revision
branch result + exact revision
agent profile revision
context policy revision
tool definition schema hash
derived summary record/revision

    This manifest serves three purposes:

    1. provenance/explanation;
    2. model request fingerprinting;
    3. precise invalidation/recomputation.

    The manifest must not include unrelated global snapshot state merely because a global snapshot exists.

    19. Model Request Fingerprint¶

    Construct a canonical hash over all output-relevant non-secret inputs.

    Conceptual fields:

    fingerprint format/version
provider compatibility profile
provider/model identifier
provider capability subset affecting serialization
agent profile revision
context policy revision
compiled provider-neutral context
exact dependency manifest
tool schemas and ordering
structured-output schema
model parameters

    Do not include:

    API keys
Authorization headers
random local request IDs
timestamps that do not affect model input
UI state
unrelated global snapshot changes

    Canonical encoding must be deterministic.

    20. Cache Repository¶

    The runtime needs a cache repository independent of one storage backend.

    A cache record includes:

    request fingerprint
provider profile/model identity
provider fingerprint/version metadata when returned
successful complete response
usage metadata
original invocation provenance
creation time/retention metadata

    Initial cache policies:

    Disabled
RecordOnly
ReuseExact

    ReuseExact returns the previous complete response without calling the provider and records a reuse relationship for the new model invocation.

    Do not cache incomplete/cancelled streams as successful model responses.

    Provider errors may have a separate short-lived retry cache only if a later design explicitly requires it.

    21. Provider Payload Retention¶

    Provider-neutral model inputs/outputs needed for execution provenance are stored through session/runtime records.

    Raw HTTP request/response payload retention is optional.

    If enabled:

    • redact credentials and sensitive headers;
    • do not persist transport TLS/proxy secrets;
    • mark raw payloads as external/audit artifacts;
    • keep them out of the canonical branch context unless deliberately inspected;
    • apply retention limits independently from durable branch results.

    Correct replay/navigation must not require raw provider JSON.

    22. Streaming¶

    The provider adapter may emit a normalized stream:

    ResponseStarted
TextDelta
ToolCallDelta
UsageUpdate
ResponseCompleted
ResponseFailed

    The adapter assembles fragments into one complete provider-neutral response before durable model-output commit.

    Runtime events may forward safe text/progress deltas to product surfaces.

    Disconnecting a product client must not cancel the provider call unless the shared operation itself is cancelled.

    23. Cancellation¶

    Use one cancellation tree rooted in the shared agent operation.

    Cancellation propagates to:

    current provider request
pending atomic tools when cancellable
active child branches
runtime waits

    A child may also fail/cancel independently without automatically cancelling its parent when branch policy permits the parent to recover.

    The root operation reaches cancelled only after runtime cancellation handling reaches a stable terminal state.

    24. Budgets and Limits¶

    Execution budgets protect against runaway loops.

    Support policy fields conceptually equivalent to:

    maximum model steps per branch
maximum branch depth
maximum child branches
maximum tool calls
maximum context size/token estimate
maximum output size
maximum provider request duration
maximum total operation duration/cost when measurable

    Limit exhaustion becomes a structured runtime failure/branch result rather than a panic.

    Budgets participate in execution policy but do not need to be part of the model request fingerprint unless they change the serialized request itself.

    25. Errors¶

    Define structured runtime categories at least for:

    provider configuration
provider authentication
provider transport
provider rate limit
provider unsupported capability
provider malformed response
context compilation
tool not found
tool argument validation
capability denied
application operation failure
child branch failure
budget exceeded
cancelled
cache corruption
internal runtime failure

    Preserve safe provider diagnostics without leaking credentials or full sensitive prompts into ordinary error messages.

    26. Testing Strategy¶

    All orchestration tests use a deterministic fake provider and fake/embedded application tools.

    The fake provider must be scriptable with a sequence such as:

    return tool call inspect(X)
return tool call start_child(Y)
return final text

    Tests must prove:

    • context compilation is deterministic;
    • provider serialization can be tested independently;
    • tool calls cannot escape the trusted catalog;
    • capability denial occurs before semantic execution;
    • child branches receive only selected inherited context;
    • child completion returns a compact result to the parent;
    • parent context does not automatically include child history;
    • nested recursion obeys budgets;
    • cache reuse avoids provider invocation and preserves provenance;
    • cancellation stops the execution tree;
    • no external network is required for runtime conformance tests.

    Provider-adapter integration tests may use a local mock HTTP server.

    27. Dependency Direction¶

    The intended direction remains:

    foundation/session/app
        |
        v
scriberig-agent-core
        |
        v
scriberig-agent-runtime
        |
        v
product composition

    scriberig-agent-runtime may depend on scriberig-session, scriberig-app, scriberig-agent-core, HTTP/async libraries, and cache support.

    No foundation/domain crate may depend on it.

    scriberig-tui, web packages, and CLI must interact through shared app/protocol operation boundaries rather than importing provider internals.

    28. Implementation Order¶

    Implement in this order:

    1. extend provider-neutral session execution records;
    2. define provider-neutral model contract and fake provider;
    3. implement OpenAI-compatible adapter;
    4. implement deterministic context compiler and dependency manifest;
    5. implement request fingerprint and cache repository;
    6. implement trusted tool catalog/dispatch;
    7. implement branch orchestrator and nested child execution;
    8. expose execution through shared application operations;
    9. add product surfaces and cross-surface conformance.

    29. Completion Criteria¶

    This Level 2 design is satisfied when:

    • provider communication exists only in the agent runtime/product composition layers;
    • a fake provider can drive the complete agent loop without network access;
    • OpenAI-compatible text/tool calling is supported behind the provider-neutral boundary;
    • context compilation records exact dependencies and does not flatten the complete session by default;
    • tool exposure is capability filtered and progressive;
    • nested child branches execute recursively and return compact BranchResult values;
    • model requests have deterministic non-secret fingerprints;
    • cache policy can record and exactly reuse completed responses;
    • streaming is observable without making fragments canonical project state;
    • cancellation propagates through provider/tool/branch work;
    • runtime budgets prevent unbounded loops;
    • tests prove branch isolation and trusted tool dispatch.
