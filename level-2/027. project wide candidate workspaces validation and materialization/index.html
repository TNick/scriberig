    Project-Wide Candidate Workspaces, Validation, and Materialization¶

    1. Purpose¶

    The first useful project workflow proves a safe candidate change to an existing Rust projection. Self-hosting requires a broader but compatible unit of change: one candidate may create, update, and delete several project files that together implement one capability.

    This document extends the existing migration/projection/apply model without introducing a parallel repository patch system.

    The target case is an agent-produced candidate that adds a new source-domain crate, updates workspace metadata and project import dispatch, adds tests/fixtures, and may change a lockfile, while leaving the live project and working tree unchanged until explicit acceptance.

    2. Core Invariant¶

    A project-wide source change is still one normal candidate/migration based on one exact project snapshot.

    Conceptually:

    Project P @ S0
    + ordered source effects
    + semantic/reconciliation result
    + provenance
    = Candidate C

    Creating C must not:

    • advance P.current;
    • write new files into the live checkout;
    • modify existing live files;
    • delete live files;
    • invent a second canonical patch/history type.

    Human and agent callers consume the same candidate APIs.

    3. Project Source Effect Model¶

    A candidate must be able to express at least three source effect kinds.

    3.1 Create¶

    Create {
    relative_path
    new_content or projection content reference
    expected_absence policy
    ownership/projection metadata
}

    Create fails normal application if a conflicting external target exists and is not explicitly accounted for by reviewed reconciliation policy.

    3.2 Update¶

    Update {
    relative_path
    expected_base_source identity/digest
    new_content or projection result
    ownership/projection metadata
}

    The expected base is exact. Apply must not silently update whatever content happens to be on disk later.

    3.3 Delete¶

    Delete {
    relative_path
    expected_base_source identity/digest
    ownership/projection metadata
}

    Delete must not remove an externally modified or unrelated file merely because its path matches a stale candidate.

    The implementation may use existing migration operation types internally. These conceptual effect kinds do not require a second storage model if equivalent semantics already exist.

    4. Path and Ownership Rules¶

    Every file effect is project-relative.

    Clients and agents do not supply authoritative absolute target paths.

    Before candidate creation/application as appropriate, shared projection/filesystem infrastructure enforces:

    • target resolves under the canonical project root;
    • path traversal is rejected;
    • symlink escape is rejected according to existing policy;
    • the effect is associated with the intended project;
    • update/delete targets correspond to expected source/projection ownership where ownership exists;
    • create targets cannot silently replace unrelated pre-existing data.

    A candidate that contains one invalid escaping path is rejected rather than partially accepted.

    5. Exact Base Binding¶

    The aggregate candidate has one exact project base snapshot.

    Each update/delete effect additionally retains enough exact source evidence to detect external divergence at materialization time.

    At minimum this is equivalent to:

    project_id
base_snapshot_id
relative_path
base source artifact/revision or digest

    Create effects retain an expected-absence/precondition state.

    Do not use "latest" or "whatever is current" as the base for an already-created candidate.

    6. Candidate Semantic State¶

    Where Scriberig can reconcile candidate source into semantic state before acceptance, the candidate/result snapshot contains the semantic result of all effects together.

    This is important for changes where one file depends on another, for example:

    new domain crate source
+ Cargo.toml workspace/dependency registration
+ project importer reference to the new crate

    The candidate must be inspectable as a coherent whole, not as independent file patches whose combined meaning is unknown until after live write-back.

    If some source format has only text-level candidate semantics, the candidate may retain source effects without pretending unsupported semantic reconciliation exists. Capability metadata must remain truthful.

    7. New File Projection Semantics¶

    A source projection may have no base live file.

    Candidate infrastructure therefore needs a representation for proposed new owned output without first creating it in the project checkout.

    The projection/render API should be able to answer conceptually:

    render candidate C / path crates/.../lib.rs

    and return candidate content and provenance even though the path does not yet exist in the live tree.

    This proposed projection participates in diff, validation, review, and eventual materialization.

    8. Aggregate Diff and Review¶

    The candidate review model exposes both aggregate and per-path information.

    Required aggregate data includes:

    candidate id
project id
base snapshot
candidate/result snapshot when available
provenance
validation state
stale/conflict state
counts of create/update/delete effects

    Per-path review includes:

    relative path
effect kind
old content identity/content when applicable
new content identity/content when applicable
semantic context when known
source diff

    The TUI/web/client layers may paginate or lazily render large diffs, but the canonical review model is shared.

    9. Candidate Workspace¶

    Validation requiring a filesystem view uses an isolated candidate workspace.

    Conceptually it is derived from:

    base project source state
+ all candidate source effects

    Requirements:

    • exact candidate content is what validators see;
    • live project files are not modified;
    • created files appear in the candidate workspace;
    • deleted files are absent there;
    • unaffected project files match the intended base/current validation policy;
    • temporary build outputs stay outside canonical project state;
    • cancellation/failure does not leak a half-materialized live change.

    Reuse existing candidate/projection staging infrastructure where possible rather than introducing an unrelated checkout manager.

    10. Validation Profiles¶

    Validation remains an application operation associated with an exact candidate.

    A profile may compose deterministic checks such as:

    semantic reconciliation/invariants
focused unit/integration tests
cargo fmt --check
cargo check --workspace --all-targets
cargo clippy ...
selected cargo test targets
fresh-database project ingestion E2E

    The profile name is policy/configuration. Product UI does not hard-code shell execution.

    Results are structured and durable, including bounded diagnostics and exact candidate reference.

    11. External Process and Dependency Capabilities¶

    Validation may need to execute repository tools.

    Process execution must remain bounded by the existing operation/capability model. React/TUI/model-provider code must not directly spawn arbitrary commands merely because the candidate spans multiple files.

    A new declared dependency may also require acquisition.

    Dependency resolution, when not already satisfied by the build environment, is an explicit capability with bounded intent. It should record sufficient evidence to reproduce what entered the candidate, including exact lockfile/version changes.

    This is distinct from granting the model arbitrary network access.

    12. Validation Gating¶

    Normal Apply is enabled only when required validation policy is satisfied and the candidate is not stale/conflicted.

    For a project-wide candidate, validation success applies to the exact aggregate source state.

    Any edit that changes candidate content after validation invalidates or supersedes the prior evidence according to existing exact-input binding rules.

    Do not reuse a validation result from a previous set of source effects.

    13. Preflight Before Multi-File Materialization¶

    Application must not begin unsafe write-back before evaluating all required preconditions it can check in advance.

    For each effect, preflight includes conceptually:

    • project/root containment;
    • path/symlink safety;
    • expected base digest for update/delete;
    • expected absence/conflict state for create;
    • projection ownership expectations;
    • candidate applicability/validation state.

    If one effect is already known to conflict, do not apply the other source effects and report overall success.

    The chosen external-effect protocol may still have unavoidable failure after canonical promotion or during I/O. Such cases must be represented honestly through receipts/recovery state.

    14. Canonical Apply¶

    Candidate acceptance uses the same exact-base compare-and-swap project semantics as existing single-projection changes.

    Required aggregate semantics:

    candidate.base_snapshot == project.current_snapshot

    unless an explicit reviewed rebase/merge created a new candidate.

    Application must not silently retarget all file effects to a newer snapshot.

    On canonical success, the resulting successor snapshot/history records the one coherent change.

    15. Filesystem Materialization¶

    Accepted project-wide source effects are materialized through shared filesystem projection infrastructure.

    For updates/creates, use the existing safe atomic-replacement strategy where applicable.

    For deletes, preserve the repository's effect/recovery semantics and never remove an externally changed target under stale assumptions.

    The operation result exposes aggregate and per-effect state sufficient to distinguish:

    not attempted due to precondition conflict
materialized successfully
failed and recoverable/retryable
canonical state advanced but external effect incomplete

    Do not reduce a multi-file result to one generic completed boolean that can hide a missing file.

    16. Failure Ordering and Recovery¶

    Database canonical promotion and multiple filesystem effects cannot be made literally atomic as one transaction.

    Continue using the repository's external-effect receipt/reconciliation architecture.

    The multi-file extension must make the chosen ordering and partial-effect recovery explicit.

    Recovery must be able to identify exactly which intended paths/effects have been satisfied and which remain divergent.

    Retry must remain idempotent/safe with respect to already completed effects.

    17. External Conflict Example¶

    Given candidate effects:

    Create crates/domains/scriberig-domain-php/src/lib.rs
Update Cargo.toml from digest A
Update crates/scriberig-project/src/adapters.rs from digest B

    if an external process edits Cargo.toml after candidate creation, Apply must not silently overwrite that edit and then report the whole project-wide candidate as successfully materialized.

    The user must see a stale/conflict/reconciliation-required state and retain the external content.

    18. Provenance¶

    The aggregate candidate records normal provenance such as:

    initiating principal
surface
session/branch/operation for agent changes
base project/snapshot

    Per-path effects need not each create an independent history lineage unless the existing model requires it, but review/history must make their membership in the accepted migration clear.

    Agent-generated and human-generated project-wide candidates remain structurally equivalent after initiation.

    19. Protocol and Client Contract¶

    Public application/protocol/client APIs must be able to:

    create/propose a project-wide candidate
inspect its aggregate metadata
page/list changed paths
render per-path candidate source/diff
start/observe validation
apply through shared operation
inspect per-path external-effect result

    Do not require clients to upload an opaque git patch as the canonical API if the server cannot validate project/path/source preconditions from it.

    A textual patch may be a transient representation converted into shared candidate effects.

    20. TUI Contract¶

    The native TUI review view must scale from one file to a project-wide candidate.

    It should let the user:

    • see candidate/base/validation state;
    • browse changed paths and effect kinds;
    • open old/new or unified diffs;
    • see important semantic labels where available;
    • invoke normal Apply only when allowed;
    • inspect conflict/effect-recovery state after Apply.

    No full IDE multi-file editor is required for this milestone; the agent may be the producer of the candidate.

    21. Cross-Surface Equivalence¶

    Embedded application, remote protocol/client, TUI, web, and agent adapters must identify the same candidate and effects.

    Do not create a TUI-only repository patch structure for the self-hosting test.

    The reference web application may gain project-wide review affordances later or concurrently, but the canonical model/API must already be reusable by it.

    22. Required Conformance Cases¶

    The implementation should provide reusable tests equivalent to:

    PROJECT-CANDIDATE-01 — create + update¶

    Create a candidate that adds a new source file and updates an existing manifest/config file. Assert current snapshot/tree unchanged and candidate render contains both changes.

    PROJECT-CANDIDATE-02 — delete¶

    Create a candidate deleting an owned source file. Assert live file remains until Apply.

    PROJECT-CANDIDATE-03 — aggregate diff¶

    Inspect candidate through public API and verify effect kinds/paths/source diffs.

    PROJECT-VALIDATE-01 — exact candidate workspace¶

    Run a validator that requires the newly created file and updated metadata together. It must succeed only if the isolated workspace contains the aggregate candidate.

    PROJECT-VALIDATE-02 — validation does not touch live tree¶

    Compare live bytes before/after validation.

    PROJECT-APPLY-01 — all effects materialize after acceptance¶

    Apply a valid candidate and verify successor snapshot plus intended create/update/delete results.

    PROJECT-CONFLICT-01 — external update conflict¶

    Externally modify one update target after candidate creation. Assert no silent overwrite/full-success claim.

    PROJECT-CONFLICT-02 — create target unexpectedly exists¶

    Create the proposed new path externally before Apply. Assert explicit conflict.

    PROJECT-STALE-01 — project snapshot advances¶

    Advance canonical project state after candidate creation and assert exact-base rejection.

    PROJECT-EFFECT-FAIL-01 — deterministic mid-effect failure¶

    Use shared fault injection to prove effect receipts/recovery identify incomplete paths without hiding canonical/external divergence.

    23. Non-Goals¶

    This design does not require:

    • replacing Git;
    • generic arbitrary binary patching;
    • transactions that falsely claim SQLite + filesystem atomicity;
    • automatically merging arbitrary external edits;
    • giving agents unrestricted filesystem access;
    • making every source adapter editable;
    • executing user-supplied project commands without validation policy/capability checks.

    24. Completion Criteria¶

    This subsystem is complete for the self-hosting milestone when one exact-base candidate can safely create a new Rust domain crate, update workspace and importer source, add tests/fixtures, validate the complete candidate in isolation, remain non-current/non-materialized before acceptance, and after explicit acceptance produce one authoritative successor plus truthful safe multi-file materialization/effect state through the existing shared change architecture.
