    Web Workspace, Packages, and Integrated Editor¶

    1. Purpose¶

    This document refines design/level-1/012. web platform and integrated editor.md into a concrete TypeScript/React workspace and file plan.

    It is intentionally implementation-oriented but still architectural. It defines package boundaries, dependency directions, required public surfaces, and the initial reference-editor composition. Exact function bodies and component implementations belong in Level 3 tasks.

    Read before implementing:

    1. design/level-1/010. universal query and operation model.md
    2. design/level-1/011. runtime libraries protocol and product surfaces.md
    3. design/level-1/012. web platform and integrated editor.md

    The controlling invariant is:

    The complete Scriberig editor must be buildable entirely from public protocol, client, model, interaction, and component packages.

    2. Web Workspace Location¶

    Create a dedicated web workspace under:

    web/

    The web workspace is separate from the Rust Cargo workspace but lives in the same repository.

    Use pnpm workspaces for JavaScript/TypeScript package management.

    Initial top-level files:

    web/package.json
web/pnpm-workspace.yaml
web/tsconfig.base.json

    The workspace contains reusable packages and applications:

    web/
├── package.json
├── pnpm-workspace.yaml
├── tsconfig.base.json
├── packages/
│   ├── protocol/
│   ├── client/
│   ├── model/
│   ├── react/
│   ├── editor-core/
│   ├── components/
│   └── components-mui/
└── apps/
    └── scriberig/

    Do not place reusable logic directly in apps/scriberig if it can live in one of the public packages.

    3. Package Names¶

    Use these package names:

    @scriberig/protocol
@scriberig/client
@scriberig/model
@scriberig/react
@scriberig/editor-core
@scriberig/components
@scriberig/components-mui

    The reference application package is private and uses:

    @scriberig/app

    All reusable packages must be publishable independently even if publication is not enabled initially.

    4. Common Package Shape¶

    Every reusable package starts with this minimum shape:

    package-name/
├── package.json
├── tsconfig.json
├── src/
│   └── index.ts
└── test/

    Additional source files should be introduced only when they correspond to a defined responsibility.

    Each package must:

    • use TypeScript;
    • emit declarations when built as a library;
    • avoid importing from another package's private source paths;
    • export supported APIs through src/index.ts;
    • expose package boundaries through package exports rather than repository-relative imports.

    The Level 3 tasks may add focused files below src/ as required.

    5. Dependency Direction¶

    The package dependency graph is:

    @scriberig/protocol
        |
        v
@scriberig/client
        |
        v
 @scriberig/model
      /      \
     v        v
@scriberig/react   @scriberig/editor-core
      \            /
       \          /
        v        v
      reusable React UI
       /             \
      v               v
@scriberig/components   @scriberig/components-mui
             \          /
              \        /
               v      v
              @scriberig/app

    The graph is conceptual; a package should depend only on what it actually imports.

    Hard rules:

    • @scriberig/protocol depends on no other Scriberig web package.
    • @scriberig/client may depend on @scriberig/protocol, but not React or MUI.
    • @scriberig/model may depend on protocol and client, but not React or MUI.
    • @scriberig/editor-core may depend on protocol and model, but not React or MUI.
    • @scriberig/react may depend on protocol, client, model, and editor-core, but not MUI.
    • @scriberig/components may depend on React bindings and headless interaction packages, but not MUI.
    • @scriberig/components-mui may depend on MUI and the public reusable packages.
    • @scriberig/app may depend on all public web packages but must not import server internals or database code.

    6. @scriberig/protocol¶

    Responsibility¶

    Represent the public wire contract used by browser and Node clients.

    It owns TypeScript representations for public concepts such as:

    • entity, revision, and snapshot references;
    • descriptions and typed summaries;
    • relations and collections;
    • query expressions;
    • semantic diffs;
    • migrations;
    • validation results;
    • operations and operation events;
    • sessions and branches;
    • projections;
    • capability information;
    • structured errors and stale-state conditions.

    Required boundary¶

    This package must not independently redesign server semantics.

    The authoritative protocol definition comes from the shared runtime/protocol design. When protocol generation becomes available, generated definitions should land behind this package's public exports.

    Initial source organization¶

    web/packages/protocol/src/
├── index.ts
├── ids.ts
├── objects.ts
├── query.ts
├── changes.ts
├── operations.ts
├── sessions.ts
├── projections.ts
├── capabilities.ts
└── errors.ts

    If generation produces different internal files, index.ts remains the stable import boundary.

    7. @scriberig/client¶

    Responsibility¶

    Provide a framework-independent transport client over the public protocol.

    The package exposes operations equivalent to:

    inspect
list
follow
query
diff
history
branch
migrate
validate
render
session operations
agent operations
operation inspection
event subscriptions

    Initial source organization¶

    web/packages/client/src/
├── index.ts
├── client.ts
├── transport.ts
├── http-transport.ts
├── event-stream.ts
└── errors.ts

    transport.ts defines a transport abstraction so tests and alternate deployments can provide non-HTTP implementations.

    The client must not contain React hooks, view state, MUI types, or reference-editor concerns.

    8. @scriberig/model¶

    Responsibility¶

    Coordinate client-side semantic state without becoming a second canonical database.

    It owns:

    • immutable revision cache entries;
    • current snapshot awareness;
    • entity-to-current-revision resolution for loaded data;
    • relation-page caches;
    • operation records;
    • event application;
    • stale-view detection;
    • local navigation state where reusable;
    • migration preview state;
    • opened session/branch state.

    Initial source organization¶

    web/packages/model/src/
├── index.ts
├── workspace-model.ts
├── revision-cache.ts
├── snapshot-state.ts
├── relation-cache.ts
├── operation-store.ts
├── event-reducer.ts
└── stale-state.ts

    Canonical server state and browser-local state must be represented separately.

    The model must preserve unchanged immutable revisions when a new snapshot arrives.

    9. @scriberig/editor-core¶

    Responsibility¶

    Provide framework-independent interaction models for semantic browsing and editing.

    Initial primitives:

    • universal semantic selection;
    • relation/tree expansion;
    • semantic navigation;
    • command discovery and execution descriptors;
    • history navigation;
    • diff navigation;
    • branch navigation;
    • migration review state;
    • operation-progress coordination;
    • projection/editor coordination.

    Initial source organization¶

    web/packages/editor-core/src/
├── index.ts
├── selection.ts
├── commands.ts
├── knowledge-tree.ts
├── navigation.ts
├── history.ts
├── diff.ts
├── branches.ts
├── migration-review.ts
└── projection-session.ts

    This package must contain behavior and state transitions, not JSX.

    10. @scriberig/react¶

    Responsibility¶

    Expose React bindings for client, model, and editor-core without imposing a visual design system.

    Initial source organization:

    web/packages/react/src/

├── provider.tsx
├── use-object.ts
├── use-children.ts

    Bindings should subscribe to reusable model/controller state rather than reproduce state logic inside each hook.

    No MUI dependency is allowed.

    14. Required Reference Editor Views¶

    Create view modules corresponding to the Level 1 conceptual surfaces:

    web/apps/scriberig/src/views/RawKnowledgeView.tsx

    These are application composition views. Reusable widgets must remain in reusable packages.

    The initial application shell may use a simple layout. Panel docking, persistence of layout, and sophisticated workspace UX are deferred.

    15. Universal Selection¶

    Define one reusable selection model in @scriberig/editor-core.

    It must be able to represent:

    entity
optional exact revision
snapshot
optional relation/path context
optional projection location

    It should support both current-resolution selection and exact historical selection.

    Views use this model to coordinate:

    • graph reveal;
    • semantic inspection;
    • projection highlighting;
    • history loading;
    • relation browsing;
    • agent scope;
    • migration highlighting.

    The reference application owns which selection is active; packages own how that selection is interpreted.

    16. Universal Commands¶

    Define a command descriptor model in @scriberig/editor-core.

    A command descriptor must be able to express at least:

    • stable command identifier;
    • human title;
    • applicability to a selection/capability context;
    • whether it is read-only or mutating;
    • invocation through a shared application operation;
    • optional keyboard/menu metadata;
    • optional domain extension metadata.

    The UI may expose the same command through:

    • a palette;
    • a context menu;
    • a toolbar;
    • a button;
    • an agent-oriented action.

    The command descriptor must not embed MUI components.

    17. Events and Snapshot Synchronization¶

    The transport client exposes the shared event stream.

    The model consumes events and updates loaded state incrementally.

    Minimum event handling behavior:

    • a snapshot-advanced event updates current snapshot identity;
    • unchanged cached revisions remain available;
    • changed loaded entities may be marked for resolution/refetch;
    • operation progress updates operation records;
    • branch/session events update relevant loaded models;
    • disconnect state is explicit;
    • reconnect may resume or re-establish subscriptions according to server capability.

    The browser must never pretend that a historical snapshot has silently become current.

    18. Drafts and Mutations¶

    Browser-local drafts are not canonical knowledge.

    Mutation flow:

    UI intent
  -> public command/application operation
  -> migration proposal or domain operation
  -> validation
  -> resulting snapshot
  -> protocol event
  -> client model update

    The reference application may show optimistic local state, but must keep candidate state distinguishable from accepted canonical state.

    No package may implement direct database writes.

    19. Projection Integration¶

    Projection components receive semantic selection and snapshot context.

    Where an adapter provides location mappings, projection views should support:

    semantic selection -> projection location
projection location -> semantic selection

    The initial package architecture must not hard-code source-code-only assumptions because Markdown, PDFs, sessions, and future domains use the same projection concept.

    Domain-specific editors can be plugged into ProjectionHost through extension registration defined in a later design.

    20. Domain UI Extensions¶

    The initial extension contract should allow domains to contribute descriptors for:

    • semantic inspectors;
    • projection renderers/editors;
    • diff renderers;
    • relation views;
    • commands;
    • icons/labels;
    • validation presentation.

    The concrete registry API may be finalized during Level 3 implementation of editor-core, but registration must happen through public web packages rather than direct imports into the app shell.

    21. Testing Layers¶

    Each package has tests at its own boundary.

    Required categories:

    protocol: serialization/type contract fixtures where applicable
client: transport and event-stream behavior with fake transport
model: snapshot/event/cache transitions
editor-core: pure interaction/controller behavior
react: provider and hook subscription behavior
components: accessible rendering and interaction contracts
components-mui: integration/smoke tests
app: end-to-end composition and public-boundary conformance

    The reference application must include a conformance test that fails if application source imports private paths from reusable packages or server/database code.

    22. Initial Tooling¶

    Use:

    • pnpm workspaces;
    • TypeScript;
    • React for framework bindings and the reference app;
    • Vite for the reference browser application;
    • Material UI for the opinionated component package and reference app;
    • Vitest for package-level unit tests;
    • React Testing Library for React component/hook tests where appropriate.

    Do not introduce a global client-state framework until @scriberig/model requirements demonstrate that one is necessary. The model should initially be implemented with explicit TypeScript state and subscription primitives.

    Do not introduce Storybook, Electron/Tauri, code generation frameworks, or a browser E2E runner in the first web bootstrap unless a later design requires them.

    23. Implementation Order¶

    Implement in this order:

    1. web workspace bootstrap
2. @scriberig/protocol
3. @scriberig/client
4. @scriberig/model
5. @scriberig/editor-core
6. @scriberig/react
7. @scriberig/components
8. @scriberig/components-mui
9. reference editor application
10. cross-package and conformance tests

    Packages may initially be small, but each step must preserve the dependency direction.

    Do not build the reference editor first and extract libraries afterward.

    24. Completion Criteria¶

    This Level 2 design is satisfied when:

    • the web/ workspace exists;
    • all seven public packages exist with the prescribed dependency direction;
    • the reference editor exists as a separate app;
    • no lower package depends on React unless it is a React/UI package;
    • no lower package depends on MUI;
    • protocol semantics are not independently reinvented in the browser;
    • one semantic selection can coordinate multiple application views;
    • commands are represented independently of visual controls;
    • snapshot and stale-state information are explicit;
    • web edits flow through public migrations/operations rather than database writes;
    • the editor exposes at least skeletal raw, semantic, projection, history, session/agent, and operation views;
    • the reference app communicates only through public web packages;
    • package tests and conformance checks enforce these boundaries.

    25. Level 3 Work Items¶

    Level 3 should split implementation into focused tasks:

    1. bootstrap the web workspace and reusable package scaffolds;
    2. implement the protocol package boundary;
    3. implement the framework-independent transport client;
    4. implement the client semantic model and incremental event handling;
    5. implement headless editor-core selection, tree, command, and navigation primitives;
    6. implement React providers and hooks;
    7. implement neutral reusable components;
    8. implement Material UI components;
