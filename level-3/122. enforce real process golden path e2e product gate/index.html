    Enforce Real-Process Golden Path E2E Product Gate¶

    Objective¶

    Create the final executable product-verification gate for the first useful Scriberig workflow.

    This task is intentionally test-heavy. Its job is to prove that tasks 117 through 121 compose through the actual user products, not merely that their individual unit/integration tests pass.

    Do not implement missing product behavior by weakening this test task. If a golden scenario fails because product behavior is missing, go back to the owning implementation task and fix the product.

    The first useful project workflow is not product-verified until every required scenario in this file passes from a clean checkout.

    Prerequisites¶

    Every checklist item in these tasks must already be complete:

    117. implement active project workspace across application web and tui.md
118. implement named semantic code navigation and rust source projection.md
119. implement projection edit candidate review and validation.md
120. implement migration apply filesystem materialization refresh and conflict recovery.md
121. implement semantically scoped agent candidate through shared change path.md

    If any prerequisite is incomplete, stop and finish it before closing this task.

    Non-Negotiable Test Boundary¶

    Browser scenarios¶

    Browser golden tests must use:

    • a real Scriberig server process or the repository's normal E2E server composition;
    • the real reference web application served through its normal E2E/Vite/build path;
    • Playwright/browser interaction through accessible selectors;
    • a real temporary SQLite/database/runtime as normally configured;
    • a copied temporary golden project on disk;
    • public HTTP/protocol paths used by the real app.

    Do not replace the server with request mocks for golden scenarios.

    Do not call React component methods directly.

    Do not mark a scenario passed because an API request succeeded if the required UI/file outcome was not observed.

    TUI scenarios¶

    TUI golden tests must use:

    • the real built srig executable;
    • an actual pseudo-terminal harness;
    • normal CLI arguments;
    • actual terminal key/input sequences;
    • a copied temporary golden project and temp database;
    • screen/output assertions through the terminal harness.

    Do not replace these with reducer snapshots or direct state mutation.

    Shared backend/conformance scenarios¶

    Programmatic conformance tests use public application/protocol/client interfaces. They may create in-process servers/transports when that is the repository's established conformance pattern, but must not access private database tables to fake semantic results.

    Test Fixture Lifecycle¶

    Provide one reusable fixture factory for golden product tests.

    For every scenario unless intentionally testing persistence across restarts:

    1. create fresh temporary directory;
    2. copy tests/fixtures/golden-rust-project into it;
    3. initialize Git repository if needed;
    4. git add the fixture files so --git-tracked includes them;
    5. create fresh SQLite/database path;
    6. start required Scriberig process(es) with project-root authorization containing only the temporary workspace where relevant;
    7. run scenario;
    8. on failure preserve/log useful diagnostics;
    9. terminate child processes cleanly;
    10. clean temporary data after success according to test-harness conventions.

    Never point write-back tests at the Scriberig repository root.

    Stable Acceptance Anchors¶

    The golden fixture/tests rely on these semantic/source anchors:

    project source path: src/lib.rs
module: math
type: Calculator
method/function: add
base expression: left + right
accepted expression: left.saturating_add(right)
agent prompt: Change add so overflow saturates instead of wrapping.
external-conflict marker: // external edit

    Tests may use accessible labels that include additional kind/context text, but they must verify these anchors remain user-visible/semantically discoverable.

    Browser Golden Suite¶

    Create/organize specs so every scenario below has one obvious test mapping. You may use one file such as web/e2e/specs/golden-project-workflow.spec.ts or several focused files.

    Do not delete existing bootstrap/offline/onboarding tests; keep them as regression tests.

    WEB-GOLDEN-01 — onboard and open active project¶

    Required steps:

    1. launch clean server/app against fresh temp db and allowed project root;
    2. navigate to Projects;
    3. enter copied fixture path;
    4. enable Git-tracked-only scan;
    5. scan;
    6. assert scan review lists src/lib.rs;
    7. import reviewed scan;
    8. activate/open imported project through user-visible action/automatic documented flow;
    9. navigate to semantic browser;
    10. assert active project name/context visible;
    11. capture visible/non-empty base snapshot ID or stable shortened representation plus test-accessible full value if UI shortens it;
    12. expand/navigate semantic structure;
    13. assert Calculator visible;
    14. assert add visible;
    15. assert browser has no uncaught page/console errors.

    Failure conditions:

    • test stops at status=imported;
    • explorer still uses generic pre-import root;
    • only opaque #N labels exist for named symbols;
    • test reaches add by hard-coded entity ID.

    WEB-GOLDEN-02 — selection opens exact source projection¶

    Required steps:

    1. begin with active imported fixture;
    2. select visible add entry through UI;
    3. assert selection/semantic context identifies add;
    4. open Projection/Source route/action;
    5. assert src/lib.rs visible;
    6. assert source text contains left + right;
    7. assert projection is current at recorded base snapshot;
    8. assert editability is advertised for this supported Rust projection;
    9. assert selected semantic mapping/context is present enough that returning to Semantic still identifies same add.

    WEB-GOLDEN-03 — human edit creates reviewed validated candidate without write-through¶

    Required steps:

    1. open editable source for add;
    2. replace only left + right with left.saturating_add(right) using real UI control;
    3. assert dirty/local-edit state if product exposes one;
    4. click Review/Propose change;
    5. wait for candidate/migration review;
    6. assert review base snapshot is the recorded base;
    7. assert changed path src/lib.rs;
    8. assert old expression visible;
    9. assert new expression visible;
    10. wait for semantic/project validation completion;
    11. assert validation successful and Apply enabled;
    12. from test harness read live temp src/lib.rs;
    13. assert disk STILL contains left + right and does NOT contain accepted expression;
    14. resolve project status through public API if needed and assert current snapshot is still base.

    This test is specifically designed to fail a direct-write implementation.

    WEB-GOLDEN-04 — accept writes file and refreshes snapshot/history¶

    Required steps:

    1. continue from or recreate valid reviewed candidate;
    2. record base snapshot;
    3. click Apply;
    4. wait for terminal operation state that explicitly includes successful required materialization/effect;
    5. assert active current snapshot changes to successor;
    6. assert successor != base;
    7. read live temp src/lib.rs and assert accepted expression present;
    8. assert base expression is no longer the active expression at target location;
    9. reopen Projection and assert accepted source;
    10. open History/Diff and assert transition/change is visible;
    11. if UI exposes migration ID, assert it remains inspectable;
    12. reload browser application;
    13. reopen/select existing imported project if active workspace is session-local;
    14. navigate back to add projection;
    15. assert accepted expression and successor current snapshot remain observable;
    16. assert browser diagnostics clean.

    WEB-GOLDEN-05 — invalid edit cannot apply¶

    Fresh fixture.

    Required steps:

    1. record base snapshot and base file bytes;
    2. select add and edit to deterministic invalid Rust;
    3. propose/review;
    4. assert structured parse/validation diagnostic visible;
    5. assert Apply disabled/unavailable or application rejects through normal UI with clear validation failure;
    6. assert current project snapshot still base;
    7. assert live file bytes equal original;
    8. assert no successor/materialization success is shown.

    WEB-GOLDEN-06 — stale external edit is not overwritten¶

    Fresh fixture.

    Required steps:

    1. create valid reviewed candidate and wait for validation;
    2. before Apply, modify live temp src/lib.rs from test harness to include // external edit;
    3. click Apply;
    4. wait for conflict/stale/effect outcome;
    5. assert UI explicitly shows conflict/stale/reconciliation-required or equivalent non-success state;
    6. read disk and assert // external edit still exists;
    7. assert stale candidate did not silently replace file with its old-base output;
    8. assert UI does not show full write-back success;
    9. if canonical apply already occurred per architecture, assert UI exposes out-of-sync/effect-recovery state rather than hiding it;
    10. if canonical apply was prevented, assert project remains at appropriate pre-apply snapshot.

    WEB-GOLDEN-07 — agent uses semantic selection and enters same review path¶

    Fresh fixture with deterministic provider configured.

    Required steps:

    1. import/activate fixture;
    2. navigate/select add semantically;
    3. record selected entity ID through public/test-observable semantic state and base snapshot;
    4. open Session/Agent;
    5. submit exact golden prompt through UI;
    6. wait for real agent operation completion/events;
    7. open candidate result through product Review candidate/equivalent action;
    8. assert normal Migration Review is used;
    9. assert src/lib.rs, old expression, new expression, and validation success;
    10. assert deterministic trace/session/tool evidence contains same selected EntityId and base SnapshotId;
    11. assert live source still base before Apply;
    12. assert no external provider/network access occurred;
    13. assert browser diagnostics clean.

    GOLDEN-CONFORMANCE-01 — workspace equivalence¶

    Embedded application and server/client resolution for same ProjectId return equivalent project snapshot/root.

    GOLDEN-CONFORMANCE-02 — semantic selection equivalence¶

    Public navigation reaches the same add EntityId/SnapshotId across embedded application and remote client. Web/TUI adapters/models must preserve that identity rather than translate it into private IDs.

    GOLDEN-CONFORMANCE-03 — source projection equivalence¶

    Rendering add at the same exact snapshot yields equivalent source-relative path/text/mapping through embedded and remote public paths.

    GOLDEN-CONFORMANCE-04 — human initiation does not change migration meaning¶

    Equivalent human edit initiated through available surface adapters produces the same semantic/source change meaning. Random migration IDs/timestamps may differ.

    GOLDEN-CONFORMANCE-05 — stale apply semantics¶

    Stale base is rejected consistently through embedded and server/client application operation.

    GOLDEN-CONFORMANCE-06 — multi-project isolation¶

    Applying project A candidate advances/materializes only A; B root/files unchanged.

    GOLDEN-CONFORMANCE-07 — agent uses shared change type¶

    Agent result candidate can be consumed by the same migration detail/validation/apply public APIs as a human candidate. No agent-specific canonical patch type bypasses them.

    Failure Artifact Requirements¶

    When browser golden tests fail, preserve/report enough evidence to debug without rerunning blindly:

    Playwright trace/screenshot when configured
browser console/page errors
server stdout/stderr log
operation error/result diagnostics
temp fixture path or captured git diff when safe
current project/snapshot identifiers

    When TUI golden tests fail, preserve/report:

    PTY transcript/final screen
process exit status
stderr/logs
fixture git diff/current file content
project/snapshot identifiers

    Do not dump secrets. Deterministic provider uses no secrets.

    Timing and Flake Rules¶

    Do not use long arbitrary sleeps as synchronization.

    Browser tests wait for:

    • accessible UI state;
    • operation terminal state;
    • network response only when paired with user outcome;
    • authoritative refreshed snapshot text/state.

    TUI tests wait for expected screen token/state with bounded timeout through existing harness helpers.

    Agent tests wait for operation lifecycle/event result.

    Filesystem assertions should retry only when architecture is explicitly asynchronous and there is a durable operation/effect state indicating completion is pending.

    Do not weaken content assertions to substring-free generic states such as Ready merely to reduce flakes.

    Test Independence¶

    Except where a scenario explicitly tests reload/restart persistence, each golden test gets fresh fixture/db state.

    Do not make WEB-GOLDEN-04 depend on WEB-GOLDEN-03 having run earlier in the test process unless the framework fixture deliberately scopes them as one serial scenario with clear setup. Prefer independent tests/helpers for parallel reliability.

    Do not depend on test execution order across files.

    Normal Quality Gate Integration¶

    Inspect tools/check.sh, CI workflows, Makefile, and package scripts.

    Ensure the product golden gate runs in CI in addition to existing unit/integration/static checks.

    If product E2E is too environment-specific for every local tools/check.sh invocation, use an explicit separate mandatory CI job/target and document that distinction. The full release/merge quality policy must not omit it.

    Do not remove existing checks to make room for E2E.
