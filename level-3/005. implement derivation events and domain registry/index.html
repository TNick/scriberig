    Implement Derivation Events and Domain Registry¶

    Objective¶

    Implement the domain-independent event vocabulary and derivation registration mechanism required by the reusable derived-knowledge subsystem.

    This task allows domain adapters to declare derivations without implementing their own private cache semantics, and allows higher product layers to observe derived-state activity without confusing it with canonical snapshot changes.

    Do not implement HTTP/WebSocket transport, an async task scheduler, model execution, compiler execution, or any specific domain derivation in this task.

    Read First¶

    Read:

    1. design/level-1/008. derived knowledge caching and incrementality.md
    2. design/level-2/001. derived knowledge runtime and cache design.md
    3. derived Level 3 tasks 001 through 004.

    Inspect existing application/protocol/event conventions before naming event types.

    If a generic event envelope already exists in a lower reusable layer, integrate cleanly rather than creating an unrelated event framework.

    Do not make the derivation crate depend on transport or application crates merely to reuse an event envelope from a higher layer.

    Files to Create or Modify¶

    Inside the canonical derivation crate:

    src/event.rs
src/registry.rs
src/lib.rs

    If the profile module needs a very small extension to carry producer/version metadata or eager/lazy hints, modify it narrowly.

    Do not edit server or protocol crates in this task.

    1. Derived Event Semantics¶

    In event.rs, define a reusable event enum or tagged structure for derived-state lifecycle events.

    Support at least conceptual equivalents of:

    DerivationStarted
DerivedResultAvailable
DerivationFailed
DerivedResultSelected
DerivedResultEvicted
DerivedResultInvalidatedForState
IndexUpdated

    Each event should include the smallest useful exact references needed to correlate it with:

    • derivation profile/key;
    • result handle where one exists;
    • relevant subject/scope where available;
    • structured failure/explanation reason where relevant.

    Do not require every event to carry full payload contents.

    2. Canonical Events Are Not Derived Events¶

    Do not define CanonicalSnapshotChanged as a derivation event.

    Documentation must make the distinction explicit:

    canonical event -> authoritative semantic state changed

derived event -> analysis/cache/index/selection availability changed

    A derived event must never imply a canonical snapshot transition by itself.

    The higher application/protocol layer may later combine both event streams.

    3. Event Payload Stability¶

    Events should use exact identifiers and structured reason/status types already defined by earlier tasks.

    Do not embed arbitrary formatted prose where a machine-readable enum/type already exists.

    Human-readable optional detail is acceptable in addition to structured fields.

    Avoid transport-specific concepts such as:

    websocket connection id
HTTP status
JSON field names
SSE event names

    Those belong to protocol adapters.

    4. Derivation Registry¶

    In registry.rs, define a domain-independent registry of available derivation definitions.

    A registration must describe at least:

    exact derivation profile
input/subject compatibility descriptor
dependency discovery strategy descriptor
eager or lazy policy hint
freshness behavior descriptor/default
retention default
producer/implementation identity
optional cost hint

    The registry defines what can be derived and how it should be treated by generic infrastructure.

    It does not execute domain code in this task.

    5. Extensible Input Compatibility¶

    Do not hard-code domain types into a production enum.

    A registration should be able to say conceptually:

    profile X applies to entity type Y
profile Z applies to snapshot/scope kind Q

    using existing universal type identifiers or opaque schema/type IDs.

    Test-only fake domains are allowed.

    Do not add variants such as:

    RustFunction
MarkdownSection
PdfPage
SessionBranch

    inside the universal registry.

    6. Dependency Discovery Contract¶

    The registry must describe how a derivation obtains its dependency set.

    The first implementation may support strategies equivalent to:

    DeclaredExactInputs
WholeSnapshot
ProducerSupplied

    or another small extensible representation.

    The goal is not to implement dependency analysis here.

    The goal is to make the derivation contract explicit so later execution layers can construct a correct DerivationKey.

    Do not hide dependencies behind an untyped closure if doing so makes them impossible to inspect or serialize conceptually.

    If execution callbacks are added later, keep metadata separately inspectable.

    7. Scheduling Hint¶

    Reuse the existing eager/lazy profile scheduling hint.

    The registry may override/default this per registration if needed.

    Do not start background tasks.

    The only requirement is that higher layers can discover whether a derivation is intended to be:

    Lazy
Eager

    without changing validity semantics.

    8. Freshness and Retention Defaults¶

    A registration may provide default freshness/retention behavior.

    Examples:

    local deterministic summary -> immutable freshness, reusable-expensive retention
external observation -> source freshness policy, historical/disposable retention depending on adapter
navigation index -> local freshness, disposable/eager retention

    Do not encode those examples as production domain rules.

    Reuse the generic policy types from task 003.

    9. Registry Operations¶

    Provide a small API conceptually supporting:

    register definition
lookup exact profile
list profiles applicable to subject/type/scope
reject conflicting duplicate registration
inspect registration metadata

    Registration order must not affect semantic identity.

    If duplicate exact profiles are registered with conflicting metadata, return a structured error rather than silently selecting the last registration.

    10. Event Emission Boundary¶

    Do not bake a global event bus into the derivation crate.

    Prefer event values that can be returned/emitted by higher execution services.

    If an event-sink trait is necessary for existing project style, keep it tiny and optional.

    The derivation crate must remain usable in an embedded application that simply calls functions synchronously and ignores events.

    11. Public API¶

    Expose equivalents of:

    DerivationEvent
DerivationRegistration
DerivationRegistry
DependencyDiscovery
RegistrationError

    Reuse existing profile, freshness, retention, status, and explanation types.

    Do not duplicate them inside event/registry modules.

    Required Tests¶

    Add tests for:

    1. every required derived-event kind can be constructed;
    2. derived events contain exact key/result handles where appropriate;
    3. no event type implies canonical snapshot advancement;
    4. registry accepts a custom test-domain profile;
    5. registry exact-profile lookup works;
    6. applicable-profile listing works using universal type IDs;
    7. conflicting duplicate exact profile registration fails structurally;
    8. identical duplicate registration behavior is deterministic;
    9. eager/lazy hint is inspectable;
    10. freshness and retention defaults are inspectable;
    11. dependency-discovery strategy is inspectable;
    12. registry contains no hard-coded production domain variants.

    Validation¶

    Run:

    cargo fmt
cargo check --workspace
cargo test --workspace

    Run clippy if already part of repository practice.

    Do Not¶

    Do not:

    • add HTTP/WebSocket/SSE code;
    • add an async runtime merely for event dispatch;
    • execute domain derivations;
    • add a worker queue or task scheduler;
    • add model or compiler dependencies;
    • add agent tools;
    • add hard-coded domain variants;
    • treat derived events as canonical snapshot events.

    Completion Checklist¶

    • [x] required derived event kinds exist;
    • [x] canonical and derived event semantics are documented separately;
    • [x] event payloads use structured exact identifiers;
    • [x] derivation registry exists;
    • [x] registrations are version/profile specific;
    • [x] input compatibility is domain-neutral;
    • [x] dependency-discovery metadata is explicit;
    • [x] eager/lazy hint is exposed without scheduler implementation;
    • [x] freshness and retention defaults reuse generic policies;
    • [x] duplicate registration conflicts are structured;
    • [x] no transport, agent, or domain-specific dependency was added.
