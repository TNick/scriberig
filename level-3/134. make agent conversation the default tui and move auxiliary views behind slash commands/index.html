    Make Agent Conversation the Default TUI and Move Auxiliary Views Behind Slash Commands¶

    Status: [ ] In Progress

    Objective¶

    Restructure the native Scriberig TUI so that its ordinary, default experience is an agent conversation similar in interaction shape to Pi, PiG, Codex, or Claude Code:

    • Scriberig starts in an agent conversation surface;
    • the user can type immediately without first opening a composer or pressing i;
    • normal text is submitted as an agent message;
    • the main viewport shows the current session/current branch conversation history plus configured agent activity;
    • the composer remains visible at the bottom of the conversation;
    • model, thinking, trace, session-tree, explorer, inspector, history, changes, operations, and other secondary surfaces are opened explicitly through /commands;
    • closing a secondary surface returns to the conversation;
    • the existing semantic browser and session-tree implementations are preserved and reused, but are no longer the default shell layout.

    The key product rule is:

    Conversation is home. Everything else is an explicit tool/view opened from the conversation.

    This task builds on task 133. Do not create a second agent runtime, second session model, second model selector, or second tool/activity system.

    Instructions for the Implementation Agent¶

    This document is intentionally detailed for a smaller implementation agent. Follow it in order. Do not skip ahead because a later step looks easier.

    Before modifying code:

    1. read the repository root AGENTS.md;
    2. read crates/scriberig-tui/AGENTS.md;
    3. read every additional nearest AGENTS.md for directories you modify;
    4. read this document fully before coding;
    5. read task 133 and the Level 1/2 TUI/session documents listed below;
    6. inspect the current implementation before choosing new file/type names;
    7. prefer extending existing reducers, effects, view models, and application boundaries over adding parallel abstractions.

    Checklist discipline¶

    • [ ] Keep this file open while implementing.
    • [ ] Tick each checkbox from [ ] to [x] immediately after that exact item is implemented and its targeted verification passes.
    • [ ] Never bulk-tick checkboxes at the end.
    • [ ] If a checked item later becomes false because of another change, immediately change it back to [ ].
    • [ ] If the repository has moved since this document was written, update the relevant “Current implementation facts” entry before implementing the changed step.
    • [ ] Before setting this task to Complete, re-read every checked item against the final code and test evidence.

    Mandatory test discipline¶

    While implementation checkboxes remain incomplete, run only targeted tests/checks for the crate/module/behavior just changed.

    Do not run workspace-wide/full-suite commands during implementation, including:

    cargo test --workspace
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
pnpm --dir web test

    If the shared application/protocol contract must change to support creation of a new session from the first message, use focused tests for those exact crates while implementing that path.

    Only after every implementation checkbox and targeted-verification checkbox is complete may the final full-suite gate at the end of this document be run.

    Current Implementation Facts¶

    Verify these facts against main before changing them. Update this section if they are no longer true.

    • crates/scriberig-tui/src/state.rs currently defaults primary_view to PrimaryView::Overview.
    • crates/scriberig-tui/src/runtime.rs starts interactive state from TuiState::default() plus optional project configuration, so the shell does not currently start in the agent conversation.
    • crates/scriberig-tui/src/layout.rs currently chooses panels from terminal width:
    • wide: Explorer + Primary + Inspector;
    • medium: Explorer + Primary;
    • narrow: Primary only.
    • crates/scriberig-tui/src/render.rs renders those responsive panes automatically.
    • the persistent session composer introduced by task 133 is rendered only while PrimaryView::Session is selected and a session_composer exists.
    • the persistent composer currently requires pressing i to focus it after browsing.
    • / in browse context currently opens semantic Find.
    • : currently opens the command palette.
    • PrimaryView::Session currently renders the structural session projection (SessionModel) rather than a normal conversational projection.
    • crates/scriberig-tui/src/view/session.rs is useful and must be preserved as the structural session-tree view.
    • crates/scriberig-tui/src/render_session.rs already knows how to render depth rails and trace activity.
    • model selection, thinking-level selection, reasoning visibility, tool invocation detail, tool output verbosity, and prompt visibility were implemented by task 133 and must be reused.
    • Effect::SubmitAgent currently requires an existing session: EntityId.
    • scriberig_app::AgentCommandRequest currently requires an existing session identity.
    • scriberig_protocol::AgentStartRequest currently also requires a session identity.
    • therefore the ordinary product flow “launch with no session, type a first message, and let the shared application create the session” is not yet fully represented by the current public contract.

    Do not work around the last point by inventing a session identifier inside the TUI. If no existing shared session-creation/start operation exists when implementation begins, add the smallest shared application/protocol operation necessary to create the session through the owning session subsystem.

    Product Contract¶

    The implementation is successful only if the following behavior is true from the user’s point of view.

    Normal launch¶

    Running the native interactive TUI should ordinarily produce a screen conceptually equivalent to:

     scriberig · no active project                         model-name · thinking high


 No conversation yet.

 Type a message to start a session.


──────────────────────────────────────────────────────────────────────────────
> _

    The cursor is in the composer immediately.

    The user does not need to:

    press i
open a modal
select Session from a palette
select a semantic object
select a project

    before typing the first agent message.

    Normal conversation¶

    After messages exist, the normal screen should look conceptually like:

     scriberig · project-name                              sonnet · thinking high

 You
 Onboard the current project.

 ▏ Thinking…
 ▏ project.scan .
 ▏ ✓ 317 files
 ▏ project.import manifest:...
 ▏ ✓ snapshot a1b2...

 Onboarded Scriberig.

 Project: scriberig
 Snapshot: a1b2...

──────────────────────────────────────────────────────────────────────────────
> Add support for PHP ingestion. _

    The exact typography is implementation-dependent. The semantic requirements are not.

    Special views¶

    Auxiliary functionality should be entered explicitly from the conversation with commands such as:

    /model
/thinking
/view
/session
/explorer
/inspect
/find
/history
/diff
/projection
/changes
/operations
/project
/status
/help

    A special view replaces or overlays the conversation body deliberately. It must not appear automatically because the terminal became wider.

    Esc from a special view returns to the conversation unless an inner modal first needs to close.

    Architectural Invariants¶

    1. Conversation is a projection, not new canonical state¶

    Do not create a second transcript store.

    The conversation screen is a projection over the same durable session/branch/model/tool records already owned by Scriberig.

    The structural session tree remains available as another projection through /session.

    Conceptually:

                        durable Session graph
                           │
                 ┌─────────┴─────────┐
                 │                   │
        conversation projection   structural projection
             DEFAULT                  /session

    2. TUI must not own session or agent semantics¶

    scriberig-tui remains a presentation/controller layer over shared application operations.

    Do not:

    • allocate canonical session IDs in the TUI;
    • mutate session persistence directly;
    • invoke provider APIs directly;
    • create TUI-only model/thinking state that changes execution;
    • duplicate model/runtime behavior from task 133.

    If the first-message/new-session flow requires a shared application change, implement it below the TUI and expose the same semantics to protocol/server/client layers as required by repository dependency rules.

    3. Structural session tree remains intact¶

    Do not delete SessionModel, structural branch rows, candidate links, or branch/result inspection.

    They move behind /session.

    4. Explorer/Inspector/etc. remain useful¶

    Do not delete the existing semantic Explorer, Inspector, History, Find, Diff, Projection, Changes, or Operations view models merely because they are no longer always visible.

    The task changes navigation and prominence, not the ownership of those capabilities.

    5. Width controls wrapping, not product mode¶

    Terminal width may change:

    • text wrapping;
    • bounded rail count;
    • compact labels;
    • truncation;
    • optional minor chrome.

    Terminal width must not automatically change the product from conversation mode into Explorer/Inspector mode.

    6. Slash commands are local UI commands¶

    A recognized /command is handled locally and must not be sent to the model.

    A normal user message is sent to the agent.

    Unknown slash commands must not accidentally become model prompts.

    Provide an explicit escape for a user who really wants a prompt beginning with /.

    Recommended rule:

    /model          -> local command
/unknown        -> local error + suggestions; do not send to model
//literal       -> send the prompt "/literal" to the agent

    7. The composer remains independent from active agent execution¶

    While an agent invocation is running:

    • the composer remains editable;
    • submitting another normal message follows the already-defined queue/continuation policy;
    • cancellation remains explicit and separate;
    • typing must not implicitly cancel the running invocation.

    8. Child branches do not flood the default conversation¶

    The normal conversation follows the current conversational branch.

    Nested child branches should appear as compact branch activity/result summaries unless the user explicitly opens /session or navigates into that branch.

    This preserves the branch-isolation/context-management model.

    Required TUI State Model¶

    Exact names may differ, but keep these concepts distinct.

    Home mode versus auxiliary mode¶

    Introduce an explicit top-level presentation concept equivalent to:

    enum TuiSurface {
    Conversation,
    Auxiliary(AuxiliaryView),
}

enum AuxiliaryView {
    SessionTree,
    Explorer,
    Inspector,
    Find,
    History,
    Diff,
    Projection,
    Changes,
    Operations,
    Project,
    Status,
    Help,
}

    Do not blindly add this exact enum if PrimaryView can be cleanly adapted. The semantic requirement is:

    • one clearly identifiable conversation home;
    • explicit temporary auxiliary views;
    • deterministic return-to-conversation behavior.

    If keeping PrimaryView, prefer adding a Conversation variant and treating the existing variants as auxiliary destinations.

    Do not rename structural Session to Conversation; they are different views.

    Conversation target¶

    The default composer must work both before and after a session exists.

    Use a concept equivalent to:

    enum ConversationTarget {
    NewSession,
    Existing {
        session: EntityId,
        branch: Option<EntityId>,
    },
}

    The existing SessionComposerState currently always contains session: EntityId; that shape cannot accurately represent the initial no-session composer.

    Refactor it so the TUI can hold an ordinary draft before a session exists.

    Do not create a fake/dummy EntityId for NewSession.

    Current session/current branch¶

    Keep explicit state for the active conversation identity after the first submission is accepted:

    current session
current conversational branch
current operation, if any

    When the first shared start operation returns stable handles, update the conversation target to the returned session/branch.

    When continuing an existing conversation, use the returned/durable branch according to shared session policy.

    Conversation Projection¶

    Add a dedicated TUI conversation projection instead of using the raw structural session rows as the default transcript.

    A likely owner is a new focused module such as:

    crates/scriberig-tui/src/view/conversation.rs

    but inspect existing file-size/module organization before choosing the final path.

    The conversation projection should derive from provider-neutral session/activity state and produce UI-neutral rows such as conceptual equivalents of:

    enum ConversationRowKind {
    HumanMessage,
    AssistantMessage,
    ReasoningSummary,
    RuntimeStatus,
    ModelInvocation,
    ToolInvocation,
    ToolResult,
    ChildBranchSummary,
    SelectionChange,
    Error,
}

    Do not persist these row types as canonical session state merely for the TUI.

    Conversation ordering¶

    Preserve causal/recorded order from the session/activity data.

    Do not sort by formatted labels or rely on wall-clock timestamps when a stable sequence/ordinal already exists.

    A typical turn should project approximately as:

    HumanInput
  safe/runtime activity when enabled
  model invocation when useful
    optional prompt detail when enabled
    tool invocation(s)
      tool result(s)
  AssistantOutput

    Human messages¶

    Render human input as ordinary conversation content, for example:

    You
Add support for PHP ingestion.

    Do not show the entity ID by default.

    IDs belong in /session, /inspect, or debug/status views unless necessary for an error.

    Assistant messages¶

    Render provider-neutral final/assistant output as ordinary conversation content.

    Do not prefix ordinary final output with implementation labels such as:

    ModelOutput 1234...

    unless the user has deliberately opened a structural/debug view.

    Tool activity¶

    Reuse task-133 presentation preferences:

    tool invocation: simple | detailed
tool output: hidden | summary | full

    Simple example:

    ▏ project.scan .
▏ ✓ 317 files

    Detailed example:

    ▏ project.scan
▏   path: .
▏   selection_policy: git_tracked
▏ ✓
▏   317 files
▏   0 blocking diagnostics

    Do not duplicate redaction/detail-fetch logic that task 133 already implemented.

    Reasoning/status¶

    Reuse task-133 reasoning visibility.

    When hidden, omit safe reasoning/runtime-status rows from the conversation projection.

    When shown, display only safe user-facing reasoning summaries/status already allowed by task 133.

    Never expose private chain-of-thought.

    Prompt display¶

    Prompt/model-request visibility remains an opt-in trace/detail feature.

    It may expand beneath a model invocation in the conversation when enabled.

    Do not display it by default.

    Child branches¶

    In the normal parent conversation, render a child branch compactly, for example:

    ▏ Architecture investigation
▏ ✓ completed — 6 relevant extension points

    Do not flatten the child branch’s complete conversation into its parent.

    The user can inspect the detailed structure through /session.

    Slash Command System¶

    Implement slash commands as a first-class TUI presentation feature.

    Do not send recognized slash commands to the model.

    Parsing rules¶

    Use deterministic rules equivalent to:

    1. inspect the submitted composer text;
    2. if it begins with //, remove one leading slash and submit the remainder to the agent;
    3. otherwise, if the first non-whitespace character is /, parse a local slash command;
    4. otherwise submit the text as a normal agent message.

    Prefer requiring slash commands to start at the beginning of the composer after optional leading whitespace.

    Do not scan arbitrary message paragraphs for /commands.

    Unknown commands¶

    For:

    /does-not-exist

    show a local error such as:

    Unknown command: /does-not-exist
Type /help to list commands.

    Do not send it to the model.

    Optionally show nearest command matches when deterministic and easy.

    Command registry¶

    Do not implement slash dispatch as a growing chain of unrelated string comparisons spread across reducers.

    Create one registry/descriptor owner equivalent to:

    struct SlashCommandDescriptor {
    name: &'static str,
    aliases: &'static [&'static str],
    summary: &'static str,
    argument_hint: Option<&'static str>,
    availability: CommandAvailability,
}

    The registry should drive:

    • parsing/lookup;
    • /help listing;
    • autocomplete suggestions;
    • labels/hints where practical.

    Keep actual command effects/reducer actions typed.

    Minimum command set¶

    Implement at least these commands, adapting to actual existing capabilities:

    /help¶

    Show the slash-command list and brief descriptions.

    /model¶

    Open/reuse the existing model picker from task 133.

    If an argument form is practical, support:

    /model <profile-id-or-unambiguous-name>

    but the picker is sufficient for the first implementation.

    /thinking¶

    Open/reuse the existing thinking-level picker for the current model.

    /view¶

    Open/reuse presentation controls for:

    reasoning       hidden | shown
tool calls      simple | detailed
tool output     hidden | summary | full
prompt          hidden | shown

    /session¶

    Open the existing structural session tree view.

    This is where branch IDs, nested branches, durable result rows, candidate references, and exact structure can be inspected.

    /explorer¶

    Open the semantic Explorer as an explicit auxiliary surface.

    If there is no semantic selection/project context, show a clear local empty-state message rather than failing silently.

    /inspect [reference]¶

    Open the existing inspector.

    If an argument is supplied, resolve/use it through the existing inspection path.

    If no argument is supplied, inspect the current semantic selection when available or use the existing input flow.

    /find [query]¶

    Replace the current global / shortcut with a named slash command.

    If query is supplied, execute the existing Find flow directly.

    If no query is supplied, open the existing find input UI.

    /history¶

    Open the existing history surface for the current applicable selection/snapshot.

    /diff¶

    Open the existing diff flow. Reuse existing target-selection/input behavior.

    /projection¶

    Open the existing projection surface for the applicable selection.

    /changes¶

    Open the existing change/candidate review surface.

    Do not bypass existing explicit confirmation/promotion behavior.

    /operations¶

    Open the existing operations surface.

    /project¶

    Show current project/workspace context or the nearest existing project selection surface. Do not invent project semantics inside the TUI.

    /status¶

    Show debugging/status information that is useful but too noisy for normal conversation chrome, including connection state and other safe runtime status already available locally.

    /new¶

    Start a fresh conversation target.

    This command must not fabricate persistent session state in the TUI. It resets the local conversation target to NewSession; the next normal message invokes the shared new-session start path.

    If product semantics support immediate empty-session creation and that is preferred by the shared application owner, use that shared operation instead. Do not invent local persistence.

    Slash Autocomplete¶

    When the composer begins with /, show bounded command suggestions near the composer.

    Example:

    > /th
  /thinking    Change the thinking level for future invocations

    Requirements:

    • suggestions are local and deterministic;
    • suggestions are derived from the command registry;
    • they do not require a model call;
    • Up/Down selects suggestions while the suggestion list is active;
    • Enter accepts/executes the selected command according to ordinary input rules;
    • Esc dismisses suggestions without leaving conversation mode;
    • autocomplete must not destroy the draft;
    • no autocomplete panel should permanently occupy screen space when the user is not typing a slash command.

    Keep this simple. A bounded list of command-name prefix matches is enough.

    Input and Key Behavior¶

    Normal conversation mode¶

    The composer should own ordinary text input immediately.

    Recommended behavior:

    printable characters -> insert in composer
Enter                -> submit message or execute slash command
Ctrl+J               -> newline
paste                -> insert paste text
Esc                   -> dismiss autocomplete/inner overlay first; otherwise no destructive action
Ctrl+C                -> preserve repository/global quit/cancel policy

    Do not require i to enter edit mode in the default conversation.

    The old i binding may be removed from the ordinary flow once no longer needed.

    Browse/navigation keys¶

    Up/Down currently drive row selection in browse mode. After this task:

    • if slash autocomplete is active, Up/Down navigate suggestions;
    • if composer has text and the product does not yet support message-history recall, do not unexpectedly move the transcript cursor;
    • transcript scrolling should use explicit keys or only use Up/Down when the composer is not in active text editing according to a clearly tested rule;
    • special views may retain their existing browse key behavior.

    Prefer simple predictable behavior over clever mode switching.

    Special view behavior¶

    When an auxiliary view is open:

    • the auxiliary surface owns its existing navigation keys;
    • Esc returns to conversation when no inner overlay/modal is active;
    • the current conversation draft must be preserved;
    • returning to conversation restores composer focus;
    • opening a special view must not submit or clear the draft.

    New Session Bootstrap¶

    This is a required part of the task.

    The user must be able to launch Scriberig with no current session and type a message immediately.

    The current public TUI/application path requires an existing session identity, so first inspect whether another shared operation already creates a session.

    If a shared operation already exists¶

    Reuse it.

    Wire the TUI’s ConversationTarget::NewSession submission through that operation and consume the returned:

    OperationRef
SessionRef
BranchRef

    Then update TUI state to the returned existing-session target and begin observing/loading the session.

    If no shared operation exists¶

    Add the smallest shared application operation with semantics equivalent to:

    agent_start {
    prompt
    session: CreateNew
    selection?
    agent_profile/default execution selection as appropriate
}

    The owning application/session subsystem must create stable durable identities for the session/root branch/human input/operation.

    The TUI receives the handles; it does not create them.

    Keep existing continuation semantics for messages sent after the session exists.

    If adding this operation requires protocol/server/Rust-client/TypeScript-client updates to preserve cross-surface equivalence, implement those narrow adaptations too. Do not make “start a new session” a TUI-only semantic capability.

    Add focused tests proving:

    • first message from no-session state creates/returns a durable session;
    • the exact user text becomes the first human input;
    • the returned session can be read through the normal session API;
    • a second message uses continuation semantics rather than creating another session;
    • no fake session ID exists in TUI state before acceptance of the first start operation.

    Navigation Model¶

    The conversation is the stable home route.

    Auxiliary views are temporary.

    A simple model is preferred:

    Conversation
    |
    +-- /session ---- Esc --> Conversation
    +-- /explorer --- Esc --> Conversation
    +-- /changes ---- Esc --> Conversation
    +-- /operations - Esc --> Conversation
    +-- /model ------ close -> Conversation
    +-- /thinking --- close -> Conversation

    Do not create a complicated browser-like navigation stack merely to satisfy this task.

    Existing Back/Forward semantics for semantic navigation can remain inside applicable auxiliary views.

    The important invariant is that closing a top-level auxiliary command returns to conversation.

    Layout Changes¶

    The current width-driven multi-pane shell must stop being the ordinary layout.

    Conversation layout¶

    For all usable terminal widths, reserve:

    optional compact header
conversation viewport
composer
optional compact status/footer

    A conceptual layout helper could return:

    struct ConversationLayout {
    header: Rect,
    transcript: Rect,
    composer: Rect,
    status: Rect,
}

    Do not force this exact type if existing layout types can be adapted cleanly.

    Composer height¶

    Use a bounded dynamic or fixed composer height that supports multiline text without consuming most of the screen.

    A reasonable initial implementation is:

    minimum 3 lines
maximum approximately 6-8 lines or a bounded fraction of terminal height

    The exact numbers may follow existing tests/layout conventions.

    Auxiliary layout¶

    Existing panels may reuse nearly all available body space when opened explicitly.

    Do not automatically add Explorer or Inspector columns based on width.

    If a special view later wants a deliberate split layout, that is allowed, but it must be a property of that view, not a global width side effect.

    Too-small terminal¶

    Retain the existing safe “terminal too small” behavior.

    Do not regress terminal restoration/error handling.

    Header and Status Chrome¶

    The ordinary conversation should be quiet.

    Do not show debug-oriented information such as focus: Primary in normal chrome.

    Prefer a compact header conceptually like:

    scriberig · project-name                         sonnet · high

    Possible safe fields:

    • product name;
    • active project display name or “no active project”;
    • active model display name;
    • thinking level;
    • a minimal running-operation marker when useful.

    Connection internals, focus enum values, request IDs, and other implementation detail belong in /status or debug output unless the connection is degraded and needs a visible warning.

    Structural /session View¶

    Reuse the existing structural session implementation.

    /session should show the richer tree representation currently supplied by SessionModel, including:

    • session root;
    • branches;
    • nested branches;
    • turns/activity;
    • model invocation rows;
    • tool invocation/result rows;
    • branch results;
    • candidate review links;
    • execution selection where useful.

    Do not attempt to make the structural view look like ordinary conversation.

    Its purpose is inspection/debugging/navigation.

    Esc returns to the conversation and restores the draft.

    Explorer and Inspector¶

    /explorer¶

    The existing Explorer becomes an explicit full-body/auxiliary surface.

    It may still use semantic row selection and the existing list operations.

    It should not appear automatically on wide terminals.

    /inspect¶

    The current Inspector should become an explicit auxiliary view/overlay reached via slash command or activation from another semantic view.

    It should not occupy a permanent right-hand column in the normal conversation.

    When a user activates an entity from /explorer, it is acceptable to transition into /inspect or show a deliberate explorer+inspect special layout. The important point is that this occurs because the user explicitly entered semantic browsing, not because the terminal is wide.

    Model, Thinking, and Presentation Controls¶

    Reuse task 133.

    Do not recreate selectors.

    Slash commands are only new entry points:

    /model    -> existing model-library picker
/thinking -> existing model-specific thinking picker
/view     -> existing presentation preferences

    The normal header should reflect the authoritative current model/thinking selection after successful mutation.

    A mutation conflict/error remains an application error and must not be hidden by the slash-command layer.

    Cancellation¶

    Retain explicit cancellation semantics.

    Do not make Esc from conversation implicitly cancel the active agent operation.

    Do not make typing a new message cancel it.

    If there is an existing cancel key/action, preserve it and expose it in /help.

    If a /cancel alias is cheap to add over the existing application cancellation action, it may be added, but do not build new cancellation semantics in this task.
