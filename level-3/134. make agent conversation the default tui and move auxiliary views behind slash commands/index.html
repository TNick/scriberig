    Make the Recursive Agent Tree the Default TUI and Move Auxiliary Views Behind Slash Commands¶

    Status: [x] Complete

    Objective¶

    Restructure the native Scriberig TUI so that its ordinary experience is a conversation-like projection of the real recursive session tree rather than a linear transcript or multi-pane semantic browser.

    The user should still experience the simplicity of Pi/Codex/Claude-style terminal interaction:

    • launch directly into the agent surface;
    • type immediately;
    • see human messages, assistant results, semantic operations, branches, plans, and progress in one main viewport;
    • keep a persistent composer at the bottom;
    • use slash commands to open secondary controls/views.

    But the underlying and visible interaction is explicitly tree-aware:

    • agents recursively create child branches;
    • /plan creates durable planned nodes in the same tree;
    • plan dependencies can block/enable sibling work;
    • different branches may be assigned to different model/provider profiles;
    • one auto-advancing plan coordinator exists at a time;
    • the user can navigate to a stable historical replyable node and continue from it;
    • new activity appears at its structural location rather than always at the bottom;
    • completed children collapse to compact BranchResult-style summaries but remain expandable;
    • nesting is shown by colored vertical depth rails;
    • the current reply anchor has a distinct background highlight;
    • per-activity detail settings control rendering without affecting context;
    • source/document edits are normally semantic/domain operations, not generic file writes.

    The controlling product rule is:

    Conversation is home, but the conversation is a projection of the recursive session/plan tree. Auxiliary inspection/control surfaces are explicit slash-command destinations.

    This task depends on and must preserve the invariants in:

    • design/level-1/017. recursive agent decomposition and context isolation.md;
    • design/level-1/018. durable plans dependency scheduling and multi-model execution.md;
    • design/level-1/019. semantic agent operations and projection-first editing.md;
    • task 133 shared model/thinking/trace controls.

    The cross-layer implementation sequence is defined in task 135. Do not implement TUI-owned substitutes for missing shared semantics.

    Current Implementation Facts to Verify First¶

    Before coding, verify these against current main and update this section if repository structure has changed.

    • TuiState currently starts in PrimaryView::Overview rather than a conversation home.
    • interactive startup derives from TuiState::default() and does not automatically create a session.
    • layout currently auto-adds Explorer/Inspector panes based on terminal width.
    • persistent session composer exists but is tied to the structural Session surface.
    • pressing i is currently required to focus the persistent composer after browsing.
    • / currently maps to Find in browse context rather than slash-command composition.
    • : opens an existing command palette.
    • PrimaryView::Session is currently a structural session-tree projection and must be preserved as /session.
    • task-133 model/thinking/reasoning/tool/prompt controls exist and must be reused.
    • current submission contracts may require an existing session identity.
    • current branch continuation APIs may identify only session + branch rather than an exact historical reply anchor.
    • current durable activity/session types may not yet represent planned nodes, dependency edges, coordinator state, per-node assignments, or execution leases.

    Do not work around any missing shared contract by inventing local fake IDs, local plan state, or TUI-only continuation semantics.

    Required Home Surface¶

    Normal launch¶

    The native interactive TUI must open directly into the recursive agent conversation surface.

    Conceptual first frame:

    scriberig · no active project                         default-model · medium

No conversation yet.
Type a message to start a session.

──────────────────────────────────────────────────────────────────────────────
> _

    The composer owns ordinary typing immediately.

    The user must not have to:

    press i
open a composer modal
select Session
open a palette
select a project

    before typing the first agent message.

    Ordinary unbranched interaction¶

    When no visible branch divergence exists, the surface may feel almost linear:

    You
Inspect the parser architecture.

▏ inspect Function parse_type
▏ ✓ 4 code groups

Assistant
The parser is split into prefix, named-type, nullable-suffix, and result groups.

──────────────────────────────────────────────────────────────────────────────
> _

    The canonical model is still tree-shaped.

    Tree-Aware Conversation Projection¶

    The normal conversation must be a dedicated projection over durable session/plan/activity state.

    Do not reuse the structural /session tree rows directly as the default transcript.

    Conceptually, build UI-neutral rows equivalent to:

    HumanMessage
AssistantMessage
BranchHeader
BranchResult
PlanNode
DependencySummary
ModelInvocation
ReasoningSummary
RuntimeStatus
SemanticOperationInvocation
ToolInvocation
OperationResult
ToolResult
Validation
Selection/AssignmentChange

    Exact enum names may differ.

    Each rendered row must retain stable references to its semantic/session/plan/activity source.

    Never use visual row index as semantic identity.

    Structural Placement, Not Append-Only Placement¶

    The conversation is not a vector whose only update operation is push.

    When new activity arrives:

    1. update durable/shared state or local observation cache;
    2. rebuild/incrementally update the tree projection;
    3. locate the activity's structural parent/branch/plan node;
    4. place it beneath that location;
    5. preserve deterministic sibling/activity ordering using shared sequence/ordinal data;
    6. adjust scroll/follow state without changing semantic selection.

    If the user replies to an earlier node, the new continuation appears there.

    If an agent creates a child branch halfway through a root turn, that child appears there.

    If a planned node starts later, execution fills that planned location rather than appearing only at the bottom because wall-clock time advanced.

    Vertical Depth Rails¶

    Render one visible rail per ancestor depth.

    Conceptually:

    ▏ depth 1
▏ ▏ depth 2
▏ ▏ ▏ depth 3

    Requirements:

    • each depth receives a stable color from a theme palette;
    • the palette may cycle;
    • all ancestor rails should be shown when width permits;
    • color is supplemental; rail count/position must preserve nesting without color;
    • narrow terminals may compact older ancestors with an explicit marker such as … ▏ ▏;
    • rail color/depth is derived, never persisted as canonical state;

    • activity-local depth and branch depth may combine visually but remain distinguishable in source data.

    • [x] Branch ancestry produces deterministic rail depth.

    • [x] Rail colors are stable for a given depth during a session.
    • [x] No semantic behavior depends on terminal color support.
    • [x] Narrow layout preserves understandable ancestry.

    Navigation Cursor, Reply Anchor, and Coordinator Cursor¶

    The TUI must keep these separate:

    navigation cursor
reply anchor
coordinator cursor

    Navigation cursor¶

    Indicates the node currently being browsed.

    It may move without changing where the next message will attach.

    Reply anchor¶

    Identifies the stable replyable session location that receives the next human message.

    It must survive:

    • rerendering;
    • width changes;
    • activity verbosity changes;
    • collapse/expand changes;
    • live insertion of unrelated sibling activity.

    Coordinator cursor¶

    Represents the current location of the single auto-advancing /plan coordinator.

    While the user is idle/following, reply anchor may auto-follow coordinator cursor.

    Once the user deliberately pins another node or begins composing against it, coordinator movement must not steal the reply target.

    • [x] No cursor/anchor is represented only by row number.
    • [x] Selecting a historical replyable node can set reply anchor.
    • [x] Reply anchor remains stable while unrelated rows appear/disappear.
    • [x] Coordinator auto-follow pauses when the user browses/pins another node.
    • [x] Explicit action returns the UI to coordinator-follow mode.

    Reply-Anchor Visual Treatment¶

    The current reply anchor must have a strong background highlight or equivalent non-rail treatment.

    Do not use the rail color to communicate reply targeting.

    The two cues mean different things:

    background highlight -> next human message attaches here
rail(s)              -> structural ancestry/depth

    When replying to the normal current/coordinator head, the composer may remain visually quiet.

    When pinned to a historical/sibling node, show a compact context hint such as:

    Replying to: “The parser has four code groups…”
> _

    Important state must remain understandable without color alone.

    Replyable Nodes¶

    For the first implementation, prefer a conservative set of replyable semantic nodes, such as:

    HumanInput
AssistantOutput
completed Turn
BranchResult
PlanNode/branch head when shared continuation semantics allow it

    Do not allow arbitrary tool-result/activity rows to become continuation anchors unless the shared context compiler defines exact semantics for them.

    Non-replyable rows remain navigable/inspectable.

    First Message and New Session¶

    The initial composer must represent a true NewSession target rather than a fake session ID.

    Conceptually:

    ConversationTarget::NewSession
ConversationTarget::Existing { session, reply_anchor }

    Submission from NewSession must call a shared application start/create operation.

    When accepted:

    1. receive authoritative session/root-branch/operation handles;
    2. replace local target with those handles;
    3. render the user input from durable/shared state;
    4. observe execution through normal activity/operation semantics.

    Do not allocate canonical session identities inside scriberig-tui.

    Historical Continuation¶

    Submitting against a historical reply anchor must call a shared continuation operation that identifies the exact semantic continuation location.

    The TUI must not construct provider context itself.

    The application/runtime context compiler decides which ancestor turns, branch descriptors/results, dependency results, decisions, semantic handles, and recent local activity belong in the new branch context.

    Later siblings must not enter the continuation merely because they were created later in wall-clock time.

    /plan Presentation¶

    The plan is rendered in the same home tree.

    Example:

    / Plan: PHP ingestion
▏ ✓ Discover architecture                     local-fast
▏ ◉ Implement parser                          openai-codex
▏ ○ Implement importer                        openrouter-claude
▏   waits: parser
▏ ◉ Research PHP edge cases                   local-research
▏ ○ Integration                               openai-codex
    waits: parser, importer, research

    Requirements:

    • planned/blocked/ready/running/completed/failed state has textual/symbolic cues;
    • assignment is compactly visible when useful;
    • dependencies are compact by default and inspectable in detail;
    • starting a planned node fills that structural location;
    • plan revision/replanning does not erase historical durable nodes;
    • coordinator position can be indicated without confusing it with user reply anchor;
    • many worker branches may show running concurrently.

    /plan Command Family¶

    Recognized commands should map to shared plan operations, conceptually:

    /plan <goal>
/plan start
/plan pause
/plan resume
/plan replan
/plan stop
/plan show

    The first implementation should prefer plan creation/review before autonomous start.

    Do not keep plan structure only in TUI state.

    Per-Branch Assignment¶

    The user must be able to assign a model/profile to a selected planned/ready branch without changing every other branch.

    Use a local command such as:

    /assign

    or another unambiguous command chosen by the shared command registry.

    Do not overload /model ambiguously.

    Recommended meaning:

    /model   -> session/default future model selection
/assign  -> selected plan node/branch execution assignment

    Assignment UI consumes the shared model library/profile capabilities from task 133.

    It never stores credentials.

    Semantic Operations in the Conversation¶

    Tool/activity rendering must reflect that most known source/document work is semantic.

    Compact semantic operation:

    ▏ add function parse_union_type to php::parser
▏ ✓ Function F194 created

    Full one-line/wrapped form:

    ▏ code.add_function module=php::parser after=parse_named_type name=parse_union_type return_type=TypeResult

    Structured parameter form:

    ▏ code.add_function
▏   module: php::parser
▏   after: parse_named_type
▏   name: parse_union_type
▏   return_type: TypeResult

    Actual external process:

    ▏ cargo test -p scriberig-domain-php ...
▏ ✓ 12 tests passed

    Do not render every operation as though it were shell syntax.

    Auxiliary controls/views are explicit local commands, for example:

    A recognized command must never be sent to the model.

    Unknown slash commands must not silently become model input.

    Use an explicit literal escape, recommended:

    //literal -> send "/literal" as ordinary agent input

    Slash completion must operate while typing:

    > /mo
  /model

    and:

    > /pl
  /plan

    Auxiliary View Behavior¶

    Explorer, Inspector, History, Find, Diff, Projection, Changes, Operations, structural Session tree, model/thinking/view controls, plan detail, and status/debug remain available.

    They do not auto-appear based on terminal width.

    Opening one deliberately replaces/overlays the body.

    Esc returns toward Conversation after closing any inner modal.

    Do not delete existing view models merely because they are no longer always visible.

    /session specifically preserves the low-level structural session view with IDs/status/provenance useful for deep inspection.

    Layout¶

    All normal terminal widths should share the same product mode:

    quiet header
conversation/tree viewport
persistent composer
optional compact status

    Width may change:

    • wrapping;
    • truncation;
    • number of visible ancestor rails;
    • minor chrome;
    • compact metadata.

    Width must not automatically open Explorer or Inspector.

    Quiet Chrome¶

    Prefer a header similar to:

    scriberig · project-name                         codex · high

    Optional status line may contain concise information such as:

    main · context 34% · plan running · 3 workers

    Do not continuously show internal focus enum, verbose service status, or UUID noise in ordinary mode.

    Detailed connection/runtime/debug information belongs behind /status or debug/structural views.

    Composer Behavior¶

    Normal mode:

    ordinary key -> edit draft
Enter        -> submit
Ctrl+J       -> newline

    No i is required.

    Esc may enter tree-navigation/browse mode or close the current special view according to final keymap design, but returning to ordinary conversation typing must be direct and obvious.

    While agent work runs:

    • composer remains usable;
    • submission follows shared queue/continuation policy;
    • typing does not implicitly cancel;
    • cancellation is explicit.

    Do not let coordinator auto-advance steal a pinned reply anchor or draft.

    Do Not Do¶

    Do not:

    • create a second session/transcript store;
    • create TUI-only plan/dependency state;
    • create fake session/branch/plan IDs;
    • let row indices become continuation identity;
    • append every event at the bottom regardless of structure;
    • treat human branching as the only source of branches;
    • flatten autonomous child transcripts into parent context;
    • use terminal width to switch product modes;
    • require i for ordinary typing;
    • send recognized slash commands to the model;
    • implement provider/model selection locally in the TUI;
    • display secrets;
    • expose hidden chain-of-thought;
    • present every semantic operation as a shell command;
    • implement source editing through raw file writes when shared semantic capabilities exist;
    • silently merge concurrent worker candidates because dependencies completed;
    • allow more than one auto-advancing coordinator for one plan.

    Final Acceptance Criterion¶

    The task is complete when all of the following are true:

    Launching the native TUI opens a persistent agent composer and a tree-aware conversation projection. The user can type immediately, navigate stable replyable nodes, pin an earlier reply anchor, and submit a continuation whose new activity appears at that exact structural location. Autonomous recursive agent branches and /plan nodes appear in the same tree, completed branches collapse to compact results, dependency/assignment state is visible, multiple worker models can be observed concurrently, one coordinator can auto-advance while the user independently navigates, and nesting is rendered with colored vertical rails plus a distinct reply-anchor highlight. Known project edits are presented as semantic operations, with raw shell/file activity reserved for actual fallback/runtime use. Auxiliary views and controls are entered explicitly through slash commands and return to the conversation when closed.
