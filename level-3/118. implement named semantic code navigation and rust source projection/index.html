    Implement Named Semantic Code Navigation and Rust Source Projection¶

    Objective¶

    Make an active imported Rust project understandable and inspectable through real semantic names and real source projection.

    After task 117, products know which project root/snapshot is active. This task makes that workspace useful enough that a person can navigate to Calculator::add without entity IDs and view the exact source containing left + right.

    This is prerequisite 118. Do not begin candidate-edit work in task 119 until every required test here passes.

    Read First¶

    Read:

    design/level-1/007. domain modeling and adapters.md
design/level-1/012. web platform and integrated editor.md
design/level-1/013. vertical product completion and end to end usability.md
design/level-2/025. first useful project workflow vertical slice.md
design/level-3/059. implement language independent code domain.md
design/level-3/067. implement rust syntax domain adapter.md
design/level-3/078. implement projection specifications rendering and adapter api.md
design/level-3/091. implement rust semantic reconciliation.md
design/level-3/117. implement active project workspace across application web and tui.md

    Inspect current code-domain schemas, Rust adapter extraction, generic object summaries, list/inspect application operations, projection rendering operations, web tree components, and TUI explorer row generation before adding fields.

    Required User Outcome¶

    With the golden fixture active, both web and TUI must let a user reach the method add by reading normal labels.

    The user must be able to identify this semantic context:

    src/lib.rs
math
Calculator
add

    Selecting add and opening Projection/Source must show source that includes:

    left + right

    The user must not need to copy/paste an entity ID or understand ordinal syntax-node labels.

    Shared Semantic Naming Contract¶

    1. Named code entities¶

    For Rust entities that represent named concepts, shared semantic data must expose at least:

    name/display_label
semantic kind
source-relative path
source range or projection mapping
containment parent or a navigable semantic relation

    Required named kinds for the fixture:

    module: math
type/struct: Calculator
method/function: add

    If existing code-domain schema uses different canonical kind names, keep those canonical names and map presentation consistently. Do not create duplicate kinds solely to match this wording.

    2. Object summaries¶

    Ensure public ObjectSummary/equivalent responses can carry a meaningful label without clients inspecting raw adapter payloads.

    Prefer a generic semantic summary field or description mechanism already intended for this purpose.

    The web and TUI must consume the same summary/name semantics.

    3. Deterministic extraction¶

    Rust import must extract these names deterministically from syntax/semantic data.

    Reimporting unchanged source must preserve stable entity identity and labels according to existing adapter identity rules.

    4. Raw syntax remains available¶

    Do not delete complete syntax-tree entities or raw graph access merely to simplify the product tree.

    Instead provide a semantic/domain navigation relation/view that can skip or collapse low-level syntax nodes for ordinary navigation.

    Semantic Navigation Contract¶

    1. Public operation¶

    Use or extend the public list, relation traversal, query, or domain-navigation operation so clients can request meaningful semantic children from the active project/root.

    Do not make React recursively fetch the entire graph and guess which nodes are important.

    Do not make the TUI parse source files directly.

    2. Required reachability¶

    Starting from the golden project root, there must be a deterministic public navigation path to add.

    The exact relation chain can follow existing schemas, but an integration test must traverse only public application operations and discover labels:

    src/lib.rs
math
Calculator
add

    If directories such as src are not semantic entities in the current model, the product may display source-relative file path context rather than invent a fake canonical directory entity. The required outcome is recognizable navigation, not a specific database hierarchy.

    3. Pagination¶

    If semantic children are paginated, the fixture path must remain discoverable through normal pagination and products must request additional pages correctly.

    Do not assume required symbols are always in the first arbitrary page.

    4. Duplicate names¶

    Display disambiguating path/kind context when two entities share a name. Stable entity identity remains the selection key.

    Source Projection Contract¶

    1. Render from semantic selection¶

    Use shared projection/application operations to render source for a selected semantic entity at an exact snapshot.

    For add, response must contain or allow derivation of:

    projection_id
entity reference
snapshot/base reference
source path: src/lib.rs
source text containing the selected method or file
selection/source mapping
editability capability
stale/current state

    2. Mapping¶

    The mapping must identify where selected add appears inside returned source text.

    At minimum include a byte/character range using the repository's canonical range semantics.

    Products may highlight the range, scroll to it, or show the selected region. Mapping must remain protocol/public-model data where remote clients need it.

    3. Text source of truth¶

    Projection text must be rendered/resolved from canonical semantic/source-artifact state for the requested snapshot.

    Do not read the live filesystem directly in the web server merely to make the Projection panel look correct, because historical/candidate snapshots must remain renderable independently of current disk contents.

    4. Read-only vs editable¶

    For the golden Rust source projection, mark it editable only when the reconciliation/change path required by task 119 is actually available.

    During implementation of this task it is acceptable for focused tests to observe source as read-only until task 119 lands, but do not falsely advertise editable capability.

    5. Historical behavior¶

    Rendering an exact historical snapshot must show the source belonging to that snapshot, even after current project state later changes.

    Add a lower-level regression test for this behavior if projection infrastructure did not already prove it.

    Web Requirements¶

    Semantic view/tree¶

    The web application must expose a semantic/domain navigation view distinct from opaque raw knowledge where practical.

    Required browser behavior for fixture:

    • visible Calculator text;
    • visible add text after expanding/navigating appropriate ancestors;
    • clicking/selecting add updates shared SelectionController with its entity and exact active snapshot;
    • selection summary shows a human label/kind where supported, not only the ID.

    You may reuse MuiObjectTree if it can consume semantic summaries, or extend reusable components/headless tree primitives. Do not hard-code golden fixture names into the app.

    Projection view¶

    Replace the generic inspector fallback for supported Rust source selection with the real projection handler.

    Required visible fields/state:

    src/lib.rs
source text containing left + right
current snapshot/base context
current/read-only or editable status

    The generic object inspector remains a fallback for selections with no registered projection.

    Shared selection¶

    Navigating between Semantic and Projection routes must preserve the same entity selection.

    Do not create a separate source-view selection object keyed only by path.

    TUI Requirements¶

    Explorer labels¶

    For named Rust entities, TUI rows display semantic names and kinds.

    Examples acceptable:

    Calculator  struct
add         method

    or compact equivalents.

    Do not display src/lib.rs :: function #42 when add is known.

    Raw/debug mode may still expose IDs/ordinals.

    Navigation¶

    The PTY test must reach add through normal explorer expansion/selection keys or command palette navigation.

    Do not add a test-only key that selects a hard-coded entity.

    Source projection¶

    Provide a TUI action/view that renders the selected source projection and visibly contains:

    src/lib.rs
left + right

    It must use the same application projection operation as other clients.

    Protocol/TypeScript Contract¶

    If existing inspect/list/render protocol results lack fields needed for name/path/mapping, extend canonical protocol types and regenerate/update checked language representations according to project rules.

    Do not add browser-only JSON shapes.

    Any new fields should be additive where protocol compatibility permits.

    Add round-trip/schema/conformance tests for new public fields.

    Required Focused Tests¶

    CODE-NAME-01: Rust adapter extracts stable names¶

    Import golden fixture and assert shared semantic data contains named entities for:

    math
Calculator
add

    Assert semantic kinds are correct according to code-domain schema.

    Reimport unchanged fixture and assert identities/labels remain stable according to existing identity rules.

    CODE-NAV-01: public navigation reaches fixture method¶

    Using embedded application public operations only:

    1. resolve golden project workspace;
    2. navigate/list semantic children/relations;
    3. find Calculator then add;
    4. assert selected entity belongs to src/lib.rs;
    5. assert no test reaches into adapter-private tables/payloads.

    CODE-NAV-02: client/server navigation equivalence¶

    Perform equivalent navigation through Rust/TS public client path and assert same add entity identity and snapshot.

    SOURCE-PROJ-01: exact source projection¶

    Render source for add at imported base snapshot.

    Assert:

    path == src/lib.rs
text contains left + right
mapping contains selected add entity/range
base snapshot == active workspace snapshot

    SOURCE-PROJ-02: historical exactness¶

    After creating a successor snapshot in a focused fixture test, render base snapshot again and assert original text remains available.

    WEB-NAV-01¶

    Real Playwright:

    1. activate golden project using task 117 flow;
    2. open semantic browser;
    3. expand/navigate until Calculator and add are visible;
    4. select add;
    5. assert selection summary/semantic view identifies add;
    6. open Projection;
    7. assert src/lib.rs and left + right visible;
    8. assert no browser console/page errors.

    TUI-NAV-01¶

    Real PTY:

    1. launch golden project as active workspace;
    2. navigate explorer to visible Calculator/add;
    3. select add;
    4. open source projection action;
    5. assert terminal includes src/lib.rs and left + right.

    Negative Tests¶

    • anonymous/unnamed syntax node: falls back to kind/compact diagnostic label without fabricated symbol name;
    • duplicate symbol names in different scopes: UI can distinguish through context while identity stays correct;
    • selection with no source projection: explicit unsupported/no-projection state, not crash;
    • stale/historical selection: projection shows exact historical state and visible historical status;
    • binary/non-source entity: no attempt to decode as Rust source.

    Performance Constraint¶

    Do not make product startup load every syntax node/source file in the project.

    Navigation must remain progressive/lazy using existing list/query pagination.

    Golden fixture tests are small, but implementation must not bake in eager full-project traversal.

    Add a focused test or instrumentation assertion if a proposed implementation accidentally fetches the whole graph to show the first tree level.
