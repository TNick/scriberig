    Replace Local Provider/Tool Loop and Extension Host with Upstream Agent and Plugin Runtime¶

    Status: [ ] In Progress

    Current dependency note (2026-10-21, late revalidation): all ScribeRig rpi-* dependencies now pin controlled fork commit ebcf8d5e75d20fa3a6cc7cc76cbcdcec4cc36eb8, based on official upstream 0.7.1 main 281dfddfa39ac063d86de57b75370974c4d75e6c. The fork now includes the isolated plugin worker protocol, host-call allowlist, and injected sandbox launcher contract, so the worker/IPC gate is no longer blocked on an uncommitted API. ScribeRig still does not activate workers in production and does not merge worker tools into branch catalogs. Older revision references below are historical implementation checkpoints.

    The integration brings in canonical upstream 0.7.0 (bigfish1913/pi-rust commit 7a272ec). Its reusable provider ABI is in rpi-plugin-sdk; generic package lifecycle helpers are in rpi-extensions. The earlier fork-only rpi-provider-runtime wrapper was removed. Historical sections below that name earlier revisions or owners should be read as checkpoints.

    Invocation adapter update (2026-10-21): ToolCatalog no longer performs generic argument-shape or required-field validation. Its authorize methods only resolve registered ScribeRig tool names and enforce branch capabilities; rpi-agent validates arguments against the supplied JSON Schema before calling SemanticAgentTool::execute, and owns call lookup, settlement, and late-update handling. The adapter still rechecks the trusted descriptor and branch capability before executing the semantic callback. It bounds provider-visible results by dropping images, structured details, and dynamic tool additions, and caps text at 16 KiB; those are ScribeRig result-projection safeguards, not generic call settlement. ScribeRig's semantic descriptors and scenario responses use upstream rpi_ai::types::Tool and ToolCall directly; the local field-for-field schema and call types and conversion code were deleted. The cargo check -p scriberig --bin srig passes at the active pin. Focused behavior verification is deferred, so the matching acceptance item remains unchecked.

    1. Objective¶

    After Task 145's §16 preflight gate authorizes prerequisite implementation, move commodity in-branch agent execution and integrated agent extensibility onto upstream rpi-agent, rpi-ai, rpi-plugin-sdk, and rpi-extensions while preserving ScribeRig's branch/context/semantic-operation architecture. Task 145 remains In Progress until it returns after Tasks 137, 146, 136, and 147 to reverify its dependent criteria.

    The goal is not to make Scriberig use upstream session semantics. The goal is to stop maintaining a separate provider/tool-loop and agent plugin runtime when upstream already provides those capabilities.

    Do not begin task 147 until this sheet is complete.

    4. Define the Branch Execution Adapter¶

    One active Scriberig branch/executor context should drive one upstream agent-loop instance or equivalent upstream execution context.

    Scriberig supplies:

    compiled effective context
resolved upstream model execution selection
allowed tool set
branch-local cancellation
runtime budget decisions that remain Scriberig-specific
semantic activity correlation

    Upstream supplies:

    provider invocation mechanics
assistant streaming
provider tool-call parsing
tool schema validation
ordinary tool-call settlement/order
loop continuation
cancellation mechanics
agent events

    Acceptance:

    • [ ] Branch identity remains Scriberig identity.
    • [ ] Upstream agent instance/session identifiers are not used as Scriberig SessionId/BranchId.
    • [ ] One branch can select a different upstream provider/model than a sibling.
    • [ ] Parent/child context isolation is determined before upstream execution begins.

    5. Preserve Scriberig Context Compilation¶

    Do not let upstream transcript/session history become the source of Scriberig context.

    The execution flow remains:

    Scriberig branch state
  -> Scriberig context compiler
  -> canonical safe effective request/context
  -> upstream agent/provider execution

    If upstream agent state internally retains current-branch messages for loop mechanics, treat that state as disposable branch-local execution state.

    Acceptance:

    • [ ] Scriberig context compiler remains authoritative.
    • [ ] Child context is selected from Scriberig state, not copied from upstream parent transcript.
    • [ ] Parent resumes from selected BranchResults, not child upstream transcript.
    • [ ] Full prompt/effective request inspection remains provider-neutral Scriberig state.

    6. Adapt Scriberig Semantic Operations to AgentTool¶

    Create a narrow tool adapter around public Scriberig semantic/application operations.

    Each adapter maps:

    Scriberig operation/capability descriptor
  -> upstream AgentTool schema/label
  -> validated upstream tool call
  -> Scriberig capability check
  -> shared Scriberig application operation
  -> bounded semantic result projection
  -> upstream AgentToolResult

    Do not duplicate upstream generic tool-call validation or settlement.

    Acceptance:

    • [ ] Tool JSON-schema validation is upstream-owned where upstream provides it.
    • [ ] Unknown provider-returned tool names cannot bypass the advertised tool set.
    • [ ] Scriberig capability checks run before semantic execution.
    • [ ] Canonical mutations still use candidate/migration/validation/promotion.
    • [ ] Tool result projections retain stable Scriberig result handles where exact state matters.

    7. Branch-Producing Tool Calls¶

    Retain Scriberig's atomic-vs-child-branch distinction.

    For branch-producing work:

    upstream tool call
  -> Scriberig creates child branch
  -> compile selected child context
  -> run child through upstream agent loop
  -> finalize durable BranchResult
  -> return compact BranchResult projection as upstream tool result

    Acceptance:

    • [ ] Child branch is durable before its first model invocation.
    • [ ] Child may use a different upstream execution selection.
    • [ ] Parent receives compact result rather than child transcript.
    • [ ] Nested recursion obeys Scriberig budgets/policy.
    • [ ] A failed/cancelled child returns structured Scriberig branch outcome.

    8. Delegate Provider Wire Implementations¶

    Remove or retire Scriberig-owned generic provider HTTP implementations when upstream covers the required protocols.

    Scriberig should not maintain its own OpenAI-compatible/Anthropic request serialization in parallel with upstream.

    If Scriberig needs a missing provider feature, implement it in the controlled TNick/pi-rust fork's rpi-ai provider API and consume it only after pinning the reviewed fork commit. Upstream-main merge status and GitHub issue filing are not prerequisites for this dependency direction.

    Provider composition and protected-auth gate¶

    At the current fork pin 15a68ef2d69a312122c09c1eccfa0fbd454c48b5, rpi-ai exposes reusable concrete provider implementations under rpi_ai::providers; this pin includes the earlier extraction commit 3ae8416ceaf2dcdbf853b03c7b4662ad832497cf. The current pin also exposes rpi-model-runtime/src/provider_factory.rs with create_builtin_provider/create_builtin_provider_for_api for resolved built-in provider/model sets. This removes the upstream factory extraction blocker for built-in APIs. It does not discover providers, resolve extension providers, or compose CLI configuration, auth-store policy, package manifests, and model rows; those remain in rpi-cli/src/provider/factories.rs and rpi-cli::provider::resolve_with_extensions. ScribeRig must not call that CLI resolver or recreate its auth/package policy in native_tui_agent/provider_config.rs. ScribeRig's native root and plan worker now use the upstream built-in factory after exact model resolution, while retaining host-owned authorization and provider-independent configuration policy. Keep package installation and CLI configuration policy in their existing owners.

    At the pinned revision, built-in OpenAI Completions, OpenAI Responses, and Anthropic implementations expose combined protected-request-secret and applied-settings forwarding. rpi-extensions::PluggableProvider also forwards protected credentials to extensions that opt into the versioned protected ABI; legacy providers fail closed. Its versioned applied-settings callback accepts safe provider attestation, while providers without attestation produce an explicitly incomplete report after the extension attempt settles. Built-in reports project allowlisted values from the post-transformation request body and remain incomplete because they omit request-affecting categories. These upstream APIs are available but ScribeRig has not yet routed its active provider calls through them or persisted the reports. Do not infer application from catalog metadata or providerOptions transport alone.

    The ScribeRig host bridge must be created per invocation and bind the exact resolved provider/model, immutable catalog/config snapshot, effective endpoint, selected scriberig_secrets::SecretRef, and SecretUseContext. It must call AuthorizedCredential::credential only after binding that destination, wrap the resulting SecretValue as rpi_ai::SecretMaterial, and pass it only via RequestSecret. Override upstream ProtectedCredentialResolver::resolve_with_policy so authorization or resolution errors become CredentialResolutionError and stop precedence; never translate them to a source miss or route through ordinary-string AuthStore, SimpleStreamOptions.api_key, model headers, or plugin JSON.

    The native TUI root, one-shot, and plan-worker paths create an upstream provider for the exact selected catalog model and run it through run_upstream_branch_invocation with the scoped ScribeRig semantic broker. The broker retains branch identity, compiled context, semantic authorization, recursive child creation, request projections, and tool evidence. Deterministic scenarios are being adapted as upstream FauxProvider scripts that produce upstream AssistantMessage values. Configured built-in providers use their upstream implementations and protected credentials. Native provider extensions are rejected at startup until upstream supplies an isolated worker/IPC boundary. The ScribeRig-local generic agent loop, provider decision bridge, response cache, and generic provider connection-check path have been removed. Every branch runs through the shared upstream loop and semantic broker. The previous runtime test files were broadly deleted during this migration, including nested_branches.rs, provider_profile_provenance.rs, and runtime_request_history.rs. App-level native_tui_agent_tests/decomposition.rs now exercises recursive durable branches, compact results, child context isolation, and request ordering through the upstream runner. Existing agent_context_tests.rs, native_tui_agent_tests_part1.rs, coordinator, and plan tests retain root/non-root context activation, exact continuation anchors, durable dependency scheduling, and result semantics. A focused upstream request-projection test now checks that a ScribeRig provider profile remains provenance and affects ScribeRig request identity without entering provider-visible content. The upstream-backed failure scenario now asserts that its prepared request is retained on the durable failed invocation. The provider fixtures now use upstream faux scripts, and request assertions read the durable ScribeRig model-invocation projections. Compilation is pending the shared model-catalog API integration; runtime verification remains deferred. Do not restore tests of the removed generic local loop.

    The generic request/response DTOs, provider trait, fake provider, and local upstream translation bridge have been removed from production. ScribeRig's compiled context message representation now lives under context, and provider::HostConfigurationError is limited to host configuration and ScribeRig scenario diagnostics. The NativeScenario wrapper and bootstrap, arithmetic, PHP self-hosting, and app test scenarios consume upstream Context/Model and FauxProvider/AssistantMessage. Doctor diagnostics map stream failures to the upstream failure boundary without recreating provider transport/authentication classifications. Compilation of the integrated catalog path remains pending. Do not restore the deleted generic provider loop or DTOs to make these paths compile.

    The CredentialSource::Authorized created by the shared provider configuration is now offered to each selected built-in model, including non-local catalog rows. The protected bridge resolves it only after the exact selected model endpoint is known and wraps it as RequestSecret; the live AuthorizedCredential policy rechecks its SecretRef, endpoint, project root, purpose, and execution mode before reading. A denied or failed resolution stops the upstream invocation and is not converted to an unauthenticated request. Catalog-supplied credentials and headers remain rejected. A catalog row that needs a distinct credential reference cannot yet supply one through the native model-selection path; that remains a TEMPORARY configuration gate. Remove it only after host-owned per-connection configuration binds a specific SecretRef and SecretUseContext to that selected model endpoint. Applied-settings callbacks are captured on the current request projection, but the report persistence/API boundary still needs focused verification. Upstream stream failures now remain at the upstream invocation boundary; doctor reports only distinguish host configuration from an upstream check failure rather than recreating provider transport/authentication classes. Focused behavior verification and distinct per-model credential-reference configuration remain open.

    The inspect semantic operation still uses the non-cancellable Tool::invoke path. It addresses one entity at an exact or current snapshot and returns bounded compact/detailed output, but the synchronous application query boundary does not accept a cancellation token. Cancellation therefore stops the broker and provider loop but cannot interrupt an inspect query after that query has started. Add a cancellable query operation before claiming per-tool cancellation for inspect.

    Acceptance:

    • [x] Active provider requests use upstream provider implementations.
    • [x] Scriberig runtime no longer owns generic provider HTTP request shaping for supported providers.
    • [ ] Provider errors are mapped into Scriberig public runtime error categories through a thin adapter.
    • [x] Credential handling stays upstream/runtime-secret and is never persisted in session state.

    Isolated worker cancellation and shutdown update (2026-10-21)¶

    The current fork working tree now passes a CancellationToken into each PluginToolAdapter::execute call. A host Cancel frame cancels the matching token, and worker shutdown or input closure cancels all active tokens. The worker joins calls that finish during a two-second settlement window and joins its input-reader thread after the loop. This provides a cooperative cancellation signal; it cannot safely preempt native plugin FFI that ignores the signal. Such work may remain detached after the grace window, and the worker process must exit to terminate it. Embedding serve_worker in a long-lived host process would therefore risk retaining unfinished plugin threads.

    The host request deadline is a hard fallback: it kills the supervised process tree, marks the connection closed, and fails pending requests. Graceful host shutdown waits about 500 ms before killing the tree, shorter than the worker's two-second cooperative settlement window; in that path the process kill can preempt the worker's own grace period. Cancellation has no worker acknowledgement that a plugin call has stopped. Host capability RPC can block a plugin action for up to its 60-second reply timeout, and shutdown frames cannot be handled while synchronous plugin registration is still running. These are source-level claims only: no build, tests, or runtime lifecycle verification has been run. The fork changes are uncommitted and not in ScribeRig's pinned revision. Keep plugin activation disabled until the fork API is reviewed, pinned, and verified under runtime cancellation, timeout, and shutdown scenarios.

    Branch-scoped continuation follow-up (2026-10-21)¶

    The current transient continuation implementation is intentionally root-only. NativeTuiAgentRunner::execute_accepted removes and validates a cache entry keyed by the accepted root branch, and reinserts the opaque upstream handle only after successful completion. execute_root_branch_with_continuation recompiles the root context and independently validates its ScribeRig fingerprint before handing the handle to rpi-agent. The runner cache is the only lifecycle owner for these handles.

    Child executions are dispatched recursively by upstream_execution/delegation.rs through the active branch broker and inherit the current upstream invocation. They do not enter the root runner, and their context is a context-isolation frame rather than a distinct executor identity per Level-1 021. Reusing or capturing a handle there would require defining which exact child context/provider selection it is bound to and how a later turn re-enters that child identity. The current branch/tool execution request does not expose a corresponding child-turn lifecycle.

    Plan workers have a separate invocation lifecycle. plan_worker/execution.rs builds a precompiled UpstreamBranchInvocation from PlanWorkerContext and calls execute_precompiled_branch; that path neither accepts nor returns a continuation. Plan context includes exact ContinuationAnchor, ancestor and dependency results, local branch history, and resolved assignment. Those inputs differ from the root runner's completed-root fingerprint. Applying a root handle to that invocation would cross branch/context boundaries, while blindly associating handles with durable worker branches would be unsafe for retries, changed claims, plan edits, or changed dependencies.

    No code change is made in this slice: the allowed runtime paths lack a shared transient cache lifecycle and exact reusable lineage key for child/worker executions. Adding a map keyed only by branch would not prove equivalence of anchor, plan claim, provider/model/profile/thinking assignment, and compiled context; adding persistence would violate the opaque-handle non-persistence invariant. A safe continuation extension needs an explicit in-memory owner scoped to the execution tree plus context fingerprints derived from each exact child/worker context, and lifecycle rules for child re-entry and plan retries. The focused lifecycle coverage requested by the preceding audit (same-scope reuse, divergence reseed, failure/cancellation non-reinsertion, branch isolation, and restart reseed) remains unrun. No acceptance criteria are checked by this follow-up.

    Child and durable plan continuation implementation gate (2026-10-21)¶

    Do not add child-branch or plan-worker continuation reuse until the execution owner can prove exact semantic validity for every handle. The current root cache is not that owner: it is keyed only by root branch and its root lineage fingerprint cannot identify a nested child invocation or durable plan claim. Do not treat a branch-only map, provider/model match, or a smaller context cache key as sufficient.

    The present lifecycle lacks a single ScribeRig-owned continuation identity and handoff spanning child execution and plan-worker execution. The child delegation request does not expose a re-entry identity/lifecycle for a later turn. PlanWorkerContext provides compiled inputs but does not itself bind a continuation record to the full durable execution tuple. In particular, PlanWorkerExecutor::execute_bound_upstream_worker has the exact PlanNode, WorkerClaim, ResolvedPlanExecution, and compiled context at dispatch, but the upstream precompiled execution API accepts no continuation and returns no extracted continuation. Any later reuse also needs the authoritative current plan revision and anchor resolution; a retry must distinguish claim identity and generation, and dependencies must bind their exact fulfilled result IDs.

    The next implementation must first introduce an explicit ephemeral ScribeRig-owned continuation owner for the execution tree and establish a canonical validity value before passing a handle upstream. For child work, that requires a stable child execution identity and a defined re-entry point. For a plan worker, the validity value must include session and plan identity plus plan revision, node identity, ContinuationAnchor and its resolved location/result, worker branch, WorkerClaim ID and generation, claim assignment, resolved provider/model/profile/thinking identity, the complete canonical compiled-context fingerprint, and ordered ancestor/dependency result identities (including each dependency's fulfilled result ID). Resolve and compile from the authoritative snapshot for use, then recompute/compare that same ScribeRig value immediately before upstream handle application.

    Preserve ScribeRig BranchResult, ContinuationAnchor, profile/context fingerprint, plan assignment, and branch identity as the source of validity and durable semantics. Keep upstream ProviderContinuation completely opaque provider-owned process state: never serialize it, include it in BranchResult/session identity, or let its provider response ID stand in for the ScribeRig key. Consume a candidate handle before an attempted execution; reinsert only after successful, non-cancelled completion whose returned ScribeRig lineage still matches. Any missing/stale plan, changed anchor or dependency, assignment/profile/context divergence, failed attempt, or cancellation must discard the handle and seed from canonical ScribeRig context. Process restart always reseeds.

    Only after the child re-entry API and plan snapshot/claim inputs above are available, and focused lifecycle evidence covers same-key reuse, every-key component divergence, sibling/branch isolation, failed/cancelled non-reinsertion, and restart reseed, may child/plan continuation acceptance be marked complete.     Plan worker execution boundary and claim preflight (2026-10-21)¶

    The scheduler is the ScribeRig coordinator for durable plan-node claims, assignment resolution, exact PlanWorkerContext compilation, concurrent node dispatch, and BranchResult settlement. Its scoped worker threads call PlanWorkerExecutor; the production NativePlanWorkerExecutor resolves the provider/model and invokes execute_precompiled_branch, which enters run_branch_with_semantic_broker and delegates the ordinary provider/tool loop to rpi-agent through run_upstream_branch_invocation_with_continuation. The thread scope in scheduler_execution_helpers.rs is plan-DAG dispatch concurrency, not a second model/tool loop. Keep it with the ScribeRig plan coordinator.

    Claim setup previously mutated the caller's Plan before compiling all worker contexts and before durable claim persistence. A context compilation or persistence error could therefore return without execution while leaving the caller's in-memory plan in Running state. claim_workers now stages claims on a cloned plan, compiles every exact context against that staged plan, persists the staged claims, and only then replaces the caller's plan. Thus preflight or persistence failure leaves the caller's plan unchanged, while successful persistence and returned worker snapshots share the same claims. This preserves ScribeRig ownership of plan claims and assignment while keeping provider streaming, tool-call validation/settlement, and loop cancellation in upstream rpi-agent. No checklist item is checked by this source change; focused failure-path verification remains required. No tests or long checks were run.
