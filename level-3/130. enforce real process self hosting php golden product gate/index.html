    Enforce Real-Process Self-Hosting PHP Golden Product Gate¶

    Objective¶

    Create the final executable product gate proving the complete Scriberig self-hosting scenario from a clean baseline:

    fresh copied Scriberig checkout that does not have first-class PHP ingestion
+ fresh SQLite database
+ real built native TUI
+ deterministic provider

USER: Onboard the current project.
-> project becomes active semantic P@S0

USER: Add support for ingesting PHP source files.
-> semantic architecture discovery
-> nested implementation branch
-> normal validated project-wide Candidate C1
-> live checkout still base

USER: Review candidate / Apply
-> exact-base safe apply/materialization
-> P@S1
-> PHP support present in checkout
-> durable history/session/provenance
-> restart recovers state

    This is a product-verification task. Do not weaken its assertions to accommodate missing implementation. Fix the owning task instead.

    Prerequisites¶

    All relevant existing first-use product-gate work through task 122 must remain passing.

    Every checklist item in these new tasks must be complete:

    123. enable agent bootstrap and project onboarding from empty database.md
124. make onboarded project semantic context primary for agent discovery.md
125. implement project wide source change candidates.md
126. validate and apply project wide candidates safely.md
127. define php self extension contract and golden candidate fixture.md
128. implement deterministic self hosting provider scenario for php ingestion.md
129. deliver native tui agent self extension workflow for php ingestion.md

    If a prerequisite is incomplete, stop and finish the owning implementation task rather than adding test-only shortcuts here.

    Read First¶

    Read:

    AGENTS.md
design/AGENTS.md

design/level-2/026. agent native self hosting golden workflow.md
design/level-2/027. project wide candidate workspaces validation and materialization.md

design/level-3/123 through 129
existing product-golden/PTY harness documentation

    Reuse the existing real-process golden harness from task 122. Extend it; do not create another unrelated E2E framework.

    Non-Negotiable Test Boundary¶

    The main self-hosting scenario must use:

    • the real built srig executable;
    • an actual pseudo-terminal;
    • normal CLI/TUI startup arguments;
    • a fresh temporary SQLite/database path;
    • a copied temporary Scriberig checkout;
    • an actual Git repository/index when git_tracked scan is expected;
    • normal deterministic provider configuration through agent runtime;
    • public/shared application/project/query/change/validation operations;
    • real filesystem assertions performed by the harness;
    • restart of the real process.

    Do not satisfy the gate with:

    • reducer/state-machine unit tests only;
    • mocked TUI widgets;
    • direct private database inserts;
    • direct migration repository inserts from the scripted provider;
    • pre-created active project IDs injected into the TUI;
    • pre-applying the expected PHP patch to the fixture;
    • HTTP/request mocks standing in for the native composition;
    • a source-text assertion that never compiles/runs the candidate PHP adapter.

    Baseline Checkout Rule¶

    The temporary Scriberig checkout copied for the test must begin without first-class PHP ingestion.

    Before launching the TUI, assert the baseline using task 127 guard logic:

    normal project scan/import policy does not select registered PHP adapter
production PHP domain crate/registration from the golden candidate is absent

    If production Scriberig later gains PHP support independently, this exact gate can no longer prove the requested self-extension. Update the absent-format scenario deliberately rather than deleting the guard and pretending the same prompt remains meaningful.

    For this milestone, PHP remains the required target.

    Fixture Lifecycle¶

    For every independent scenario unless persistence/restart is intentionally under test:

    1. create a fresh temp directory;
    2. copy the Scriberig repository fixture/checkout into it;
    3. ensure required Git metadata/index state exists for git_tracked scan;
    4. record baseline hashes/bytes for paths expected to change;
    5. create a fresh database path;
    6. configure deterministic self-hosting provider and required validation/dependency policy;
    7. launch real srig tui --db <fresh-db> from the temp checkout root;
    8. drive PTY interaction;
    9. on failure preserve bounded diagnostics/artifacts;
    10. terminate child processes cleanly;
    11. clean temporary data after success according to existing harness policy.

    Never run write-back self-hosting tests against the developer's real Scriberig checkout.

    Stable Golden Inputs¶

    The main scenario uses these exact user prompts:

    Onboard the current project.

    and:

    Add support for ingesting PHP source files.

    The PHP candidate behavior is defined by Level 2 document 028 and task 127 fixtures.

    Representative semantic anchors include:

    PHP fixture class: Greeter
PHP fixture method: greet
candidate PHP domain crate path from current fixture manifest
project Scriberig
base snapshot S0
candidate C1
successor snapshot S1

    Do not hard-code random entity/snapshot/candidate IDs; capture them from public product/test-observable results.

    GOLDEN-SELFHOST-01 — Empty-Database Agent Onboarding¶

    Required steps:

    1. launch real TUI from temp Scriberig checkout with fresh DB and no --project/--import;
    2. assert no active project is visible;
    3. assert agent input is usable;
    4. type exact onboarding command;
    5. wait on operation lifecycle, not arbitrary sleeps;
    6. inspect deterministic trace/session evidence and assert capability discovery occurred;
    7. assert scan tool used trusted current checkout context and Git-tracked policy as designed;
    8. assert persisted manifest was inspected/reviewed before import;
    9. assert import consumed the exact manifest reference;
    10. assert project workspace resolves to non-empty ProjectId P, SnapshotId S0, root;
    11. assert TUI visibly activates project without restart;
    12. assert agent performed semantic smoke check before terminal success;
    13. assert no direct SQLite/project-root mutation tool was used;
    14. assert process/browser-independent terminal diagnostics are clean.

    Failure conditions include:

    • agent cannot start without a project;
    • test pre-injects a project ID;
    • scan is replaced by one model-visible file read per repository file;
    • import silently rescans different filesystem state;
    • TUI stops at status=imported without active semantic workspace;
    • agent claims success without semantic workspace resolution.

    GOLDEN-SELFHOST-02 — Semantic Architecture Discovery and Branch Isolation¶

    Continue from exact P@S0.

    1. type exact PHP command;
    2. capture normalized root provider request and assert exact P/S0;
    3. assert provider uses semantic find/inspect/render to read project guidance/source precedent;
    4. assert architecture discovery child B1 is created with exact base and read-only catalog;
    5. assert B1 discovers actual current language adapter, scanner, importer, workspace/test owners without hard-coded EntityIds;
    6. let B1 complete;
    7. assert parent receives compact architecture BranchResult with stable refs;
    8. assert captured parent request does not include entire B1 transcript;
    9. assert full B1 detail remains durably inspectable separately;
    10. assert project remains P@S0 and checkout unchanged.

    Failure conditions include using unrestricted filesystem grep/read as the sole architecture model while semantic project state is ignored.

    GOLDEN-SELFHOST-03 — Agent Creates Normal Project-Wide PHP Candidate¶

    Continue from B1 result.

    1. implementation child B2 starts with exact P@S0 and architecture refs;
    2. assert B2 has read/propose/inspect/validate capabilities and no normal Apply capability;
    3. assert exact target source projections are re-inspected/rendered at S0;
    4. provider submits the task-127 PHP candidate edits through normal project-wide change tool;
    5. capture returned CandidateId C1;
    6. inspect C1 through public shared review API;
    7. assert expected create/update path classes are present;
    8. assert one coherent candidate/base S0, not independent applied file edits;
    9. externally read live temp checkout and assert candidate-created production PHP paths are still absent;
    10. assert expected updated files are byte-identical to baseline;
    11. assert public project workspace still reports current S0.

    This scenario fails any direct agent write-through implementation.

    GOLDEN-SELFHOST-04 — Candidate Validation Proves Real PHP Ingestion¶

    Run/observe required shared validation profiles for C1.

    Required assertions:

    php-domain-focused = success
project-import-focused = success
rust-workspace = success
project-ingestion-e2e = success

    The gate must inspect evidence establishing that candidate code was actually compiled/executed.

    The PHP ingestion E2E must use a fresh database and PHP fixture project against candidate code/build, and must prove through public semantic/project operations:

    • .php manifest classification selects PHP;
    • exact source bytes/digest are retained;
    • PHP document/syntax/code entities are imported;
    • Greeter is semantically discoverable;
    • greet is semantically discoverable;
    • source projection renders correctly;
    • malformed PHP negative test preserves prior valid snapshot;
    • unrelated adapter classification regression remains correct.

    The gate fails if validation only checks that candidate source contains expected strings.

    After validation, live Scriberig checkout and P.current must still be base S0.

    GOLDEN-SELFHOST-05 — Durable Agent Result Opens Normal Review¶

    1. let B2 complete and return compact validated-candidate result;
    2. assert root parent receives compact result, not complete B2 transcript;
    3. root agent operation finishes with durable C1 link and validation refs;
    4. through TUI, activate Review candidate;
    5. assert normal shared project-wide migration review opens;
    6. assert candidate/base/validation/stale state visible;
    7. browse representative created PHP crate path and updated project/workspace path;
    8. assert real old/new/create diffs are visible;
    9. reconnect/recreate session/client view if harness supports it and recover C1 from durable result;
    10. reassert live checkout/current remain base before Apply.

    Do not parse assistant prose to discover a hidden patch.

    GOLDEN-SELFHOST-06 — User Apply Produces S1 and Safe Multi-File Materialization¶

    1. record displayed/public S0 and baseline relevant file bytes;
    2. invoke normal TUI Apply action;
    3. wait for terminal shared apply operation state;
    4. assert exact-base acceptance succeeded;
    5. assert result explicitly reports required external materialization/effect success;
    6. resolve authoritative project workspace and capture S1;
    7. assert S1 != S0 and P.current == S1;
    8. externally inspect checkout and assert candidate-created PHP domain files now exist with expected source;
    9. assert intended updated workspace/project files reflect accepted candidate;
    10. assert unrelated files are unchanged according to fixture expectations;
    11. open History/Diff and assert one transition/migration contains the project-wide PHP change;
    12. render/inspect historical S0 where appropriate and prove it remains addressable;
    13. assert operation/session/candidate/provenance links remain inspectable.

    The TUI itself must not have written these files directly.

    GOLDEN-SELFHOST-07 — Restart Durability¶

    After successful Apply:

    1. exit TUI cleanly;
    2. launch real srig tui --db <same-db> from same temp checkout;
    3. reopen existing project through normal product behavior if not automatically active;
    4. assert current authoritative snapshot remains S1;
    5. assert materialized PHP-support source remains on disk;
    6. assert history still exposes base/candidate/successor;
    7. reopen session/branch activity and recover onboarding result, B1 result, B2 validated candidate result, validation refs;
    8. no original provider token stream replay is needed to reconstruct these references.

    GOLDEN-SELFHOST-08 — Accepted Checkout Can Build and Ingest PHP¶

    After Apply, build/test the now-modified temporary Scriberig checkout according to repository policy.

    Then run a post-acceptance PHP ingestion proof using code from the accepted checkout, not the isolated pre-acceptance candidate workspace.

    This may be a focused integration test or candidate/accepted srig invocation appropriate to current architecture.

    Required result:

    fresh PHP fixture DB
scan -> PHP adapter
import -> PHP semantic entities
find Greeter/greet
render source

    This closes the loop: the accepted source on disk is capable of the feature the agent was asked to add.

    GOLDEN-SELFHOST-FAIL-01 — Validation Failure Does Not Mutate Current State¶

    Use controlled bad candidate/provider variation.

    Assert:

    • structured validation diagnostic visible/inspectable;
    • no validated-success result unless repair succeeds;
    • Apply disabled/unavailable or shared operation rejects;
    • P.current == S0;
    • live checkout remains baseline;
    • no candidate-created PHP production file leaked live.

    GOLDEN-SELFHOST-CONFLICT-01 — External Update Is Protected¶

    Fresh scenario or recreate validated C1.

    1. externally modify one update target after validation and before Apply with known marker;
    2. invoke TUI Apply;
    3. assert explicit conflict/stale/effect state;
    4. read disk and assert external marker remains;
    5. assert stale candidate did not silently overwrite it;
    6. assert UI does not report full materialization success;
    7. assert canonical/effect state is truthful according to chosen ordering.

    GOLDEN-SELFHOST-CONFLICT-02 — External Create Target Is Protected¶

    1. before Apply, externally create a file/path that candidate expects absent/create;
    2. invoke Apply;
    3. assert explicit create-target conflict;
    4. external content remains;
    5. no silent replacement/full success.

    GOLDEN-SELFHOST-STALE-01 — Canonical Base Advance Is Protected¶

    1. create validated C1 from S0;
    2. advance project current state through another legitimate operation to Sx;
    3. attempt Apply C1;
    4. assert exact-base stale rejection;
    5. assert project remains Sx;
    6. assert no silent rebase and no stale PHP source effects materialized.

    GOLDEN-SELFHOST-CANCEL-01 — Cancellation Is Safe¶

    Cover cancellation at representative phases:

    onboarding before import completion
B1 discovery
B2 before candidate completion
validation

    Assert durable cancelled state and no hidden live source/current-root mutation beyond any explicitly completed onboarding state appropriate to the phase.

    Cross-Surface Conformance¶

    Although the main gate is TUI-native, add/extend shared conformance so the resulting stable identities remain usable outside TUI.

    Required programmatic checks equivalent to:

    SELFHOST-CONFORMANCE-01 — project workspace¶

    Embedded application and public server/client (where normal test harness supports it) resolve same P@S0/P@S1 semantics.

    SELFHOST-CONFORMANCE-02 — branch result durability¶

    Architecture/implementation BranchResult references resolve equivalently through public session/application APIs.

    SELFHOST-CONFORMANCE-03 — project-wide candidate¶

    C1 changed paths/diffs/validation/apply detail are consumable through canonical client APIs, not TUI-private state.

    SELFHOST-CONFORMANCE-04 — provenance/history¶

    Accepted change links user/session/branch/candidate/validation/successor through public history/result models.

    Do not require the web product to reproduce the entire self-hosting UX in this milestone if canonical APIs/models remain reusable by it.

    Do not make assertions depend on a fragile exact count of benign semantic reads.

    No-Shortcut Assertions¶

    Add explicit tests/guards proving the scenario did not use:

    direct SQLite mutation by provider/TUI
direct live filesystem writes by provider before Apply
preinstalled production PHP adapter in baseline
agent-only canonical patch type
hard-coded EntityId for architecture targets
hidden auto-Apply
full child transcript injection as the only branch communication
test-only source mutation to fake post-Apply result
external model provider

    Where practical, assert catalogs/traces lack these forbidden paths rather than relying only on code review.

    Timing and Synchronization¶

    Do not use arbitrary long sleeps.

    PTY tests wait on stable observable tokens/states and operation lifecycle with bounded timeout.

    Candidate validation waits on operation terminal result.

    Filesystem assertions occur only after authoritative state says the relevant phase completed, except deliberate pre-Apply/conflict checks.

    Keep failure messages specific to the phase/expected token to reduce debugging cost.

    Failure Artifacts¶

    On failure preserve/report safe bounded evidence equivalent to:

    PTY transcript/final screen
process exit code
server/application stderr logs
normalized deterministic provider/tool trace
session/branch/operation ids
project/current snapshot ids
candidate id + changed path summary
validation profile results/diagnostics
filesystem git diff or relevant file hashes/content markers
external-effect receipts/conflicts
candidate validation workspace path/artifacts when repository test policy permits

    Never dump secrets. The deterministic provider requires none.

    Stable Product Gate Command¶

    Add one repository-idiomatic command that runs the complete self-hosting gate, for example:

    make test-self-hosting-golden

    or the current build system's equivalent.

    It must compose at least:

    real PTY self-hosting golden scenarios
PHP candidate domain/import/E2E validation
shared self-hosting conformance
baseline no-PHP guard
no-external-model-provider guard

    Do not silently skip an unavailable component and exit success.

    Document exact invocation in the existing product-golden testing documentation or a focused self-hosting README referenced by it.

    CI Integration¶

    Integrate the self-hosting golden gate into mandatory CI/release verification according to repository policy.

    If the gate is too expensive/environment-specific for every local tools/check.sh, give it a distinct mandatory CI job/target rather than omitting it.

    Do not remove existing task-122 product golden checks.

    Pin/cache ordinary Rust dependencies as appropriate for CI stability while preserving explicit dependency-resolution semantics.

    External model-provider credentials must not be required.

    Capability Matrix¶

    Only after this gate passes, update truthful capability metadata for concepts equivalent to:

    agent_empty_db_project_onboarding
agent_semantic_project_discovery
nested_branch_compact_results
project_wide_candidate
project_wide_candidate_validation
project_wide_materialization
self_hosting_agent_change

    Do not mark PHP as a permanently baseline-supported capability merely because a temporary golden checkout's accepted candidate adds it, unless production main subsequently intentionally accepts that PHP implementation through normal development policy.

    Distinguish product ability to self-extend from the set of adapters shipped in the baseline release.

    Run the stable self-hosting gate command from a clean checkout/environment matching CI.

    Then run repository quality gates including at least:

    cargo check --workspace --all-targets

    and any existing task-122 product-golden command.

    Review failure artifacts for accidental hidden network/model dependence and ensure all checked checklist items are backed by executable evidence.
