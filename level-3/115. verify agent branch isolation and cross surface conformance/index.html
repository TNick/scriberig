    Verify Agent Branch Isolation and Cross-Surface Conformance¶

    Status: [x] Complete

    Objective¶

    Build deterministic conformance fixtures proving that one-shot CLI, embedded application, server/client, TUI adapters, and web client/model consume the same branch-aware agent semantics and preserve branch isolation.

    Read first:

    1. design/level-1/016. model driven agent execution and branch isolation.md;
    2. design/level-2/012. capability matrix and cross surface conformance.md;
    3. design/level-2/023. agent runtime model provider and branch orchestration.md;
    4. design/level-2/024. agent operations protocol and cross surface product contract.md;
    5. tasks 107 through 114;
    6. the updated TUI task 103.

    The controlling rule is:

    Conformance compares semantic operation/session results, not screenshots, terminal strings, React markup, or provider wire payloads.

    Test Locations¶

    Use existing cross-package test infrastructure, adding focused fixtures/tests equivalent to:

    tests/fixtures/agent/
tests/conformance/agent_runtime.rs
tests/conformance/agent_surfaces.rs
tests/end-to-end/agent_http.rs

    Add web tests in the owning packages for browser-specific adapters/models, and expose fixture JSON/generated protocol data from a shared test artifact when useful.

    Do not duplicate large fake scenarios separately in every crate/package.

    Deterministic Provider Fixture¶

    Create a deterministic fake-provider script format capable of expressing steps equivalent to:

    expect model request matching semantic assertions
return assistant text
return tool call(tool_id, args)
return multiple tool calls
return stream fragments
return provider error
wait until cancellation

    The fixture should support referencing symbolic semantic handles created by the test setup rather than hard-coding unstable database ids.

    The fake provider records received provider-neutral model requests for branch/context assertions.

    No public model endpoint is used.

    Canonical Scenario A: Simple Root Answer¶

    Set up:

    user prompt: "Summarize X"
provider: final answer without tools

    Assert across embedded app and product adapters:

    one session created
one root branch created
one ModelInvocation/AgentOutput path
terminal OperationStatus = completed
AgentResult references session/root branch/BranchResult
same final output text

    Presentation formatting may differ.

    Canonical Scenario B: Atomic Semantic Tool¶

    Script:

    root model requests inspect(entity X)
atomic tool returns exact X @ revision R
root model returns final answer

    Assert:

    • tool id resolves through trusted catalog;
    • invocation/result are stored in the root branch;
    • exact entity/revision handle is preserved;
    • no unnecessary child branch is created;
    • final result is visible through all relevant surfaces;
    • provider request after the tool contains the bounded tool-result projection/handle rather than hidden database structures.

    Canonical Scenario C: Nested Child Branch¶

    Script:

    root model requests focused complex/delegated tool
-> child branch B1 created
B1 model requests atomic inspect
B1 model receives result
B1 model returns child outcome
-> BranchResult BR1
root model receives compact BR1 projection
root model returns final answer

    Assert:

    session
└── root branch
    └── child B1

    and:

    • B1 has explicit parent root;
    • B1 has its own model/tool history;
    • BR1 is durable and referenced by parent activity;
    • root's next compiled context contains the compact child result;
    • root's next compiled context does not contain B1's full activity by default;
    • TUI/web branch tree can open B1 later through the stable reference;
    • one-shot final result succeeds without needing to print B1 history.

    Canonical Scenario D: Nested Branch Isolation Marker¶

    This is a required architectural regression test.

    Inside child B1 create a unique marker only in an internal child tool/model result, for example:

    CHILD_PRIVATE_CONTEXT_MARKER_7F3A

    Do not include it in BranchResult.

    After B1 completes, capture the next root provider-neutral model request.

    Assert the marker is absent.

    Then explicitly use the supported semantic operation/tool to open deeper child history and assert the marker can become visible only after deliberate retrieval.

    This proves:

    retained history remains reachable, but completed branch internals are not automatically permanent parent context.

    The test must operate on the provider-neutral compiled context, not vendor-specific serialized JSON.

    Canonical Scenario E: Nested Depth and Budget¶

    Script recursive delegation until one configured limit is reached.

    Assert:

    • branch hierarchy is preserved up to the limit;
    • no extra branch/model request occurs after limit exhaustion;
    • terminal failure category is budget exceeded or equivalent;
    • already-created branches/history remain inspectable;
    • no stack overflow/panic;
    • all product surfaces observe the same semantic failure category.

    Canonical Scenario F: Cache Reuse¶

    Run an execution path with ReuseExact using exact unchanged inputs.

    Assert:

    • first matching model invocation calls fake provider and records cache entry;
    • second exact matching invocation does not increment provider call count;
    • second session/branch still records its own ModelInvocation/reuse provenance;
    • original invocation/cache source is referenced;
    • final semantic result is equivalent;
    • unrelated global snapshot/session change outside request dependencies does not invalidate the hit.

    Then mutate one referenced semantic revision and assert cache miss/fingerprint change.

    Canonical Scenario G: Capability Denial¶

    Advertise or request a tool that the current branch/caller lacks capability to execute.

    Assert:

    • runtime denies at trusted dispatch boundary;
    • application mutation/read operation is not executed;
    • structured denial is stored/returned safely;
    • model may receive bounded tool error only according to configured recovery policy;
    • no product surface can bypass the denial;
    • TUI/web action availability reflects capability state where applicable.

    Canonical Scenario H: Candidate Change and Validation¶

    Use a child branch that produces a semantic migration/candidate and validation result.

    Assert:

    • branch completion references candidate/validation handles;
    • model completion alone does not advance canonical main state;
    • one-shot result reports produced candidate handles;
    • TUI/web navigate those handles into shared review surfaces;
    • promotion/application through the normal change path advances state only after required validation/confirmation/capability conditions;
    • stale/conflict result remains shared across surfaces.

    Canonical Scenario I: Cancellation¶

    Configure fake provider or child branch to wait.

    Start operation, then request cancellation from each supported control path.

    Assert:

    • same shared OperationId cancellation semantics;
    • provider wait is cancelled where supported;
    • active child branches stop starting new work;
    • terminal operation category is cancelled;
    • already durable history remains inspectable;
    • no surface reports cancellation merely because its view/subscription closed.

    For one-shot, assert Ctrl-C adapter maps to shared cancellation and selected exit status.

    Canonical Scenario J: Event Disconnect and Recovery¶

    Run through concrete HTTP/event transport with deterministic fake runtime.

    Flow:

    start agent
subscribe events
observe root/child progress
intentionally disconnect stream
allow operation to complete
reconnect with cursor or force cursor-too-old path
refresh operation/session

    Assert:

    • final AgentResult is correct regardless of missing stream deltas;
    • branch tree/result can be reconstructed from durable queries;
    • replay works inside retention window;
    • too-old cursor triggers explicit resync rather than silent omission;
    • web/TUI transient stream buffers do not become fake durable history.

    Surface Adapters to Exercise¶

    Where implementation exists, exercise these boundaries against the same deterministic scenario data:

    1. scriberig-app embedded AgentService
2. scriberig-server dispatcher/in-process transport + Rust client
3. concrete HTTP protocol + event transport
4. one-shot command adapter/composition helper
5. TUI service adapter/reducer model
6. TypeScript @scriberig/client + @scriberig/model
7. integrated web agent controller/component smoke path

    Do not require terminal screen scraping or browser screenshots for semantic equivalence.

    TUI/web rendering tests remain in their own packages; conformance operates below presentation.

    Semantic Equivalence Assertions¶

    Create reusable comparison helpers for normalized results.

    Compare concepts such as:

    operation terminal category
session/root branch topology
branch parent/child relations
BranchResult status/kind/result handles
AgentResult semantic handles
structured error category
exact referenced entity/revision/snapshot identities
candidate/validation references

    Exclude from equality when nondeterministic/non-semantic:

    local request correlation ids
wall-clock timestamps
transport connection ids
provider request id unless scenario asserts preservation
presentation labels/formatting
stream chunk boundaries

    One-Shot Assertions¶

    In addition to semantic adapter testing, verify command presentation contract:

    human final output on stdout
progress/diagnostics on stderr
JSON mode structured terminal result
nested branches do not dump full histories by default
cancellation exit code
permission/error exit mapping

    The CLI is conformant only if it uses the shared semantic result used by embedded/server paths.

    TUI Assertions¶

    Use TUI service/reducer tests to assert:

    root/child branch refs map to branch-tree state
completed child defaults to compact result state
expand requests activity deliberately
stream delta stays transient
committed output replaces transient buffer
navigation away does not cancel operation
cancel action invokes shared cancellation
result handle becomes normal semantic navigation intent

    Do not compare cell styling for cross-surface semantic conformance.

    Web Assertions¶

    Use TypeScript client/model/controller fixtures to assert:

    same AgentStartResponse handles
same nested branch topology
same BranchResult handles
same duplicate/out-of-order event behavior
same disconnect -> authoritative refresh recovery
same final AgentResult
no provider credential fields in public request/state

    A minimal integrated React test may prove the public packages compose, but semantic equality belongs in model/client tests.

    Secret Leakage Tests¶

    Use unmistakable fake secret values such as:

    TEST_PROVIDER_SECRET_DO_NOT_LEAK_9A2D

    Inject through the provider secret source.

    Search/assert it is absent from:

    session records
BranchResult / AgentResult
protocol request/response DTO snapshots
ProtocolEvent payloads
cache fingerprints/material
TUI formatted errors/state
web model state/serialized fixtures
CLI stdout/stderr on normal structured failures
server safe logs captured by tests where feasible

    The provider HTTP mock may assert that the secret is correctly used only in the outbound authorization header.

    Capability Matrix Advancement¶

    After all relevant implementation paths are real, update capabilities.toml.

    Rows may advance toward verified for:

    agent_start
agent_continue
agent_final_result
session_branch_tree
session_branch_activity
agent_event_subscription
agent_streaming_output
operation_cancel

    Each surface column advances independently.

    Do not mark web/TUI verified based only on runtime tests.

    Regression Fixture Stability¶

    Keep deterministic fixture scripts small and semantic.

    Prefer symbolic fixture helpers over copying provider JSON blobs.

    When protocol schemas evolve add explicit compatibility fixtures rather than silently updating expected objects so older-version behavior disappears from tests.

    Validation¶

    Final verification should include the repository-wide relevant checks, at least:

    cargo fmt --all -- --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
pnpm --dir web format
pnpm --dir web typecheck
pnpm --dir web test
pnpm --dir web build
python3 tools/lint_repo.py

    Use narrower commands during development, but the task is not complete until the cross-surface suite and changed product packages pass together.

    Do Not Do¶

    • Do not call a public model endpoint in conformance tests.
    • Do not use hidden chain-of-thought as fixture data or assertion input.
    • Do not compare provider wire JSON as the definition of Scriberig semantics.
    • Do not compare screenshots/terminal cells for semantic conformance.
    • Do not make branch isolation tests depend only on UI collapse state; assert compiled parent context directly.
    • Do not mark capability rows verified without a real corresponding surface path.
    • Do not ignore secret leakage merely because tests use fake credentials.
