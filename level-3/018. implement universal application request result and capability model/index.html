    Implement Universal Application Request, Result, and Capability Model¶

    Objective¶

    Implement the transport-independent universal application vocabulary in scriberig-app.

    This task creates the request/result enums or equivalent typed command model for all eleven universal operations and the capability descriptors needed for discoverable clients.

    It does not implement transport endpoints, CLI commands, React hooks, agent tools, or the actual diff/history/render/change engines. Later tasks wire those engines into the application service.

    Read First¶

    Read before editing:

    1. design/level-1/010. universal query and operation model.md
    2. design/level-2/010. universal query and operation implementation.md
    3. design/level-3/015. implement universal query handles scope and pagination.md
    4. design/level-3/016. implement inspect list and follow read operations.md
    5. design/level-3/017. implement find and structured query ast.md
    6. design/level-2/001. workspace and package layout.md
    7. existing change/history and projection Level 2 designs

    Inspect the workspace and use the canonical scriberig-app crate. If it has not been scaffolded by prerequisite workspace work, create it only at the path prescribed by the workspace design and register it there. Do not create a second application crate.

    Files to Create or Modify¶

    Within crates/scriberig-app/:

    Cargo.toml
src/lib.rs
src/request.rs
src/result.rs
src/capability.rs

    You may add narrowly scoped private helper modules only if necessary.

    Do not edit protocol, server, client, CLI, TUI, agent-runtime, or web packages.

    1. Dependencies¶

    Add dependencies only on established reusable crates required by the public application vocabulary, primarily:

    scriberig-core
scriberig-query
scriberig-migration / change subsystem public types
scriberig-projection public types

    If history/diff types live in a distinct canonical crate, depend on that crate rather than duplicating them.

    The app crate must not depend on HTTP, terminal UI, model providers, or browser packages.

    2. Universal Operation Kind¶

    Define a stable domain-independent OperationKind or equivalent covering exactly the Level 1 universal grammar:

    Inspect
List
Follow
Find
Query
Diff
History
Render
Branch
Apply
Commit

    This type identifies semantic operation kind only.

    Do not add surface-specific variants such as HttpInspect, CliQuery, or AgentRender.

    Domain-specific high-level operations should use a separate extensible capability identifier rather than endlessly expanding this universal enum.

    3. Application Request¶

    In src/request.rs, define an AppRequest/ApplicationRequest enum or an equivalent typed command family with one variant for each universal operation.

    Reuse request types already owned by scriberig-query for:

    Inspect
List
Follow
Find
Query

    For the remaining operations, carry canonical subsystem request/spec types where they already exist rather than cloning their entire model into the app crate.

    The application request must be transport-neutral.

    Do not include:

    • URL paths;
    • HTTP methods/headers;
    • CLI flags;
    • terminal rendering preferences;
    • React state;
    • model-provider settings.

    4. Snapshot Resolution Input¶

    Allow convenience requests to indicate that the application layer should resolve a named/current root only through an explicit application-level selector.

    A useful abstraction is conceptually:

    SnapshotSelector {
    Exact(SnapshotId),
    NamedRoot(RootName),
}

    If another canonical type already represents named roots, reuse it.

    Do not put Current into scriberig-query scopes.

    Before dispatching any canonical read, the application service must later resolve this selector to one exact SnapshotId and return that exact ID in the result.

    This task only defines the request vocabulary; service resolution is implemented later.

    5. Universal Application Result¶

    In src/result.rs, define an AppResult/ApplicationResult enum or equivalent typed result family.

    Provide variants for:

    Inspect
List
Follow
Find
Query
Diff
History
Render
Branch
Apply
Commit
OperationStarted

    Reuse canonical result types from owning crates.

    Do not flatten structured results into String.

    Every result that describes canonical state must expose the exact snapshot/revision/branch context used or contain an underlying result type that does so.

    6. Capability Identifiers¶

    In src/capability.rs, define stable extensible identifiers for capabilities that go beyond the universal eleven operations.

    Distinguish categories equivalent to:

    RelationCapability
CollectionCapability
ViewCapability
DomainOperationCapability
FindStrategyCapability

    A capability identifier should be serializable later without using Rust type names as its public identity.

    Use a stable string/newtype or established typed identifier convention.

    7. Capability Descriptor¶

    Implement a common descriptor structure with fields equivalent to:

    id
kind
short label
short description
applicable entity types (optional)
availability
canonical/derived classification where relevant
estimated information cost (optional)

    Specialized descriptors may include:

    • relation target/cardinality/direction;
    • collection ordering;
    • view style/projection requirements;
    • domain-operation input hints.

    Keep these hints declarative and transport-neutral.

    Do not encode executable closures/function pointers in descriptors.

    8. Domain Operation Request Envelope¶

    Provide an extensible application-level envelope for a high-level domain operation without adding every future operation to OperationKind.

    Conceptually:

    DomainOperationRequest {
    capability: CapabilityId,
    subject: semantic handle/selection,
    branch/workspace: change context,
    arguments: typed or schema-described values,
}

    Prefer existing universal KnowledgeValue or schema/value types for arguments if they are sufficient.

    Do not use arbitrary JSON as the only in-process representation.

    Document that domain operations must eventually produce ordinary semantic changes through the canonical branch/migration system.

    9. Referential Results¶

    Ensure application results expose semantic handles directly.

    A caller must never need to parse a rendered message such as:

    "Function process_payment"

    to recover the target for a follow-up request.

    Where a canonical subsystem result lacks a reusable handle, add an application wrapper field rather than relying on display text.

    10. Public Exports¶

    Update src/lib.rs so later surfaces can import:

    OperationKind
ApplicationRequest
ApplicationResult
SnapshotSelector
CapabilityId
CapabilityDescriptor
DomainOperationRequest

    or the established equivalent names.

    Avoid exposing private service implementation details here.

    11. Tests¶

    Add focused unit tests verifying:

    1. every universal operation has a request representation;
    2. every universal operation has a structured result representation;
    3. query request/result types are reused rather than copied into new incompatible structs;
    4. application requests contain no transport/UI-specific fields;
    5. exact and named-root snapshot selectors are distinguishable;
    6. capability IDs survive clone/equality/hash use as appropriate;
    7. a capability descriptor can describe a relation, view, and domain operation;
    8. a domain operation request identifies its branch/change context;
    9. results retain semantic handles;
    10. no test needs an HTTP server or database backend.

    Run:

    cargo test -p scriberig-app
cargo check --workspace

    12. Non-Goals¶

    Do not implement:

    • dispatch/service execution;
    • named-root lookup itself;
    • diff/history/render algorithms;
    • branch/apply/commit algorithms;
    • validation policy;
    • operation scheduling;
    • HTTP/CLI/TUI/web/agent adapters.

    Completion Criteria¶

    This task is complete when:

    • scriberig-app contains one transport-independent vocabulary for all eleven universal operations;
    • later surfaces can depend on one request/result model instead of inventing their own semantics;
    • exact-vs-named snapshot selection is explicit at the application boundary;
    • capability discovery has stable extensible descriptors;
    • high-level domain operations have an extensible envelope tied to branch/change context;
    • all public results remain structured and referential.
