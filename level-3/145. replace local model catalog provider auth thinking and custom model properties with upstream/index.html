    Replace Local Model Catalog, Provider Auth, Thinking, and Custom Model Properties with Upstream¶

    Status: [ ] In Progress

    1. Objective¶

    Implement the model/provider ownership correction from Level-2 plan 032 after task 144 is complete.

    The goal is to remove Scriberig as an authority for provider/model catalogs, thinking-level capability, provider authentication/readiness, and model-specific/custom execution properties.

    The resulting system must treat upstream rpi model/provider machinery as the source of truth while preserving Scriberig's own branch/plan assignment semantics and historical execution provenance.

    Do not begin task 146 until this sheet is complete.

    4. Preserve Scriberig Assignment, Remove Scriberig Catalog Authority¶

    Scriberig still owns the fact that one semantic execution location has one configured execution selection.

    Examples:

    branch -> execution selection
plan node -> execution selection
session default -> execution selection
agent profile preference -> execution selection
historical invocation -> resolved execution provenance

    But Scriberig must no longer decide what models exist or what capabilities/properties they expose.

    Acceptance:

    • [x] Branch/plan assignment identity remains stable and Scriberig-owned.
    • [x] Assignment resolution reads upstream catalog/runtime state.
    • [x] No branch/plan/session code depends on a Scriberig-owned list of model capabilities.
    • [x] Historical assignment remains inspectable if the live upstream catalog later changes.

    5. Replace ModelDescriptor and Local Model Library Authority¶

    Current equivalents of these concepts are migration targets:

    ModelDescriptor
ModelCapabilities
ThinkingLevelDescriptor
ModelLibrary as model/provider truth
local provider-profile metadata used as catalog truth

    Use upstream model descriptors directly at the product/runtime integration boundary or a safe upstream-provided public snapshot/projection.

    If upstream lacks a stable safe snapshot type suitable for protocol/history, contribute one upstream rather than defining a second capability schema in Scriberig.

    Scriberig may define a narrow historical record containing:

    provider public ID
model public ID
upstream catalog/version/fingerprint reference
safe resolved output-affecting selection fingerprint
safe display metadata needed for historical UI

    That record is provenance, not a live catalog.

    Acceptance:

    • [x] Native selection resolves cached compatibility-projection rows against upstream at runtime; projection generation uses upstream at composition time, while catalog additions/removals still require rebuilding the service.
    • [x] Live model metadata is queried from upstream.
    • [ ] Local ModelDescriptor/capability definitions are compatibility projections in native composition, but the public JSON loader and with_model_library still allow caller-supplied catalog authority.
    • [x] Local model-library validation no longer interprets model capabilities or thinking support; profile identity checks remain compatibility validation.
    • [ ] Tests prove an upstream catalog change is reflected without editing Scriberig catalog code.

    6. Delegate Thinking-Level Semantics Completely¶

    Upstream owns thinking-level support, ordering, mapping, clamping, and provider serialization.

    Scriberig must not maintain a separate support table or validation list.

    Required behavior:

    selected model changes
  -> supported levels come from upstream model
  -> currently requested level is accepted/clamped/rejected according to upstream
  -> provider request receives upstream-mapped value

    Scriberig may persist the user-selected or resolved public level as execution configuration/provenance, but does not interpret its provider meaning.

    Acceptance:

    • [x] Supported thinking values come from upstream API.
    • [ ] Thinking-level mapping to provider effort comes from upstream.
    • [x] Unsupported-level fallback/clamping comes from upstream.
    • [x] TUI/web protocol projection does not invent an independent thinking enum/catalog.
    • [x] Existing Scriberig ThinkingLevelDescriptor is a derived compatibility projection with no independent support authority.
    • [ ] A model switch test proves levels update from the new model's upstream metadata.

    7. Delegate Custom Model Properties¶

    Use upstream model/provider metadata for custom and model-specific properties.

    This includes current/future upstream equivalents of:

    sampling parameters
reasoning maps
compatibility flags
strict-tool support
model input modalities
context window
max output
cost metadata
provider endpoint/public metadata
provider-specific request-shaping values
custom property maps

    Do not introduce a Scriberig enum/schema for these fields.

    When Scriberig needs to retain user overrides, store/forward them through an upstream-owned configuration type or an opaque serialized upstream value that upstream validates and resolves.

    Acceptance:

    • [ ] Scriberig does not define custom model property semantics.
    • [ ] Runtime validation of model properties is upstream-owned.
    • [ ] Output-affecting properties participate in Scriberig effective-request provenance/fingerprinting through a canonical safe upstream snapshot/hash.
    • [ ] Secret headers/credential material are excluded from Scriberig durable records.
    • [ ] Unknown future upstream properties can flow through without a Scriberig code change where the upstream public type supports that.

    8. Delegate Provider Authentication and Readiness¶

    Provider authentication, credential resolution, and readiness belong upstream.

    Scriberig may apply product trust/policy around whether a provider can be used, but it must not duplicate credential-source precedence or authentication status resolution.

    Required behavior:

    upstream provider package/catalog
  -> upstream auth/readiness
  -> safe status projection
  -> Scriberig TUI/web/server display

    Acceptance:

    • [ ] Provider auth status comes from upstream.
    • [ ] Credential-source precedence comes from upstream.
    • [ ] Resolved credentials never enter Scriberig session/protocol state.
    • [ ] Scriberig product policy may deny use without changing upstream auth semantics.
    • [ ] Provider reload/auth changes refresh Scriberig-visible safe status from upstream.

    9. Delegate Provider Packages and Catalog Refresh¶

    Use upstream provider-package and catalog-refresh infrastructure.

    If install/update/link/reload APIs are currently CLI-only, complete the upstream contribution gate from task 144 before implementing a local package manager.

    Acceptance:

    • [ ] Provider package discovery/loading is upstream-owned.
    • [ ] Catalog refresh is upstream-owned.
    • [ ] Provider package reload updates available models without a Scriberig restart where upstream supports it.
    • [ ] Scriberig does not scan package/plugin directories independently for model providers.
    • [ ] Scriberig does not maintain a second package manifest format for agent providers.

    10. Refine AgentProfile Execution References¶

    Keep Scriberig AgentProfile semantics for context composition and branch behavior.

    Replace local model-profile ownership with an upstream execution reference.

    The final profile should conceptually contain:

    Scriberig profile id/revision
Scriberig context-component policy
Scriberig branch/tool policy
Scriberig runtime budgets
preferred upstream execution selection/reference

    It should not duplicate:

    model capability table
thinking-level capability table
provider auth information
provider custom property schema

    Acceptance:

    • [ ] AgentProfile remains revisioned Scriberig semantic configuration.
    • [ ] Preferred execution selection resolves through upstream.
    • [ ] Profile fingerprinting changes when its upstream selection reference/override changes.
    • [ ] Profile editing does not create a local shadow model catalog.

    11. Preserve Historical Model Invocation Provenance¶

    Historical Scriberig model invocations still need safe explanation after upstream catalog updates.

    Record exact safe execution facts used for each invocation without owning the live catalog.

    At minimum preserve:

    provider/model public ids
resolved thinking selection
safe output-affecting configuration fingerprint/snapshot
upstream runtime/catalog version reference when available
provider request/response public ids when safe
Scriberig effective request id

    Acceptance:

    • [ ] Historical invocation detail remains inspectable after live catalog mutation.
    • [ ] Historical provenance cannot expose credentials.
    • [ ] Historical safe snapshots are not re-used as a live catalog unless explicitly imported back through upstream resolution.

    12. Protocol and Web Projection¶

    The Scriberig server/web client may need safe model information, but must not define another independent model schema.

    Prefer one of:

    1. upstream public model snapshot serialized through a thin Scriberig protocol wrapper;
    2. generated/versioned safe projection whose fields map directly to upstream public fields and preserve unknown extensible properties;
    3. stable upstream DTO contributed for remote presentation.

    Acceptance:

    • [ ] Web model/provider selectors consume server data derived from upstream state.
    • [ ] Web thinking options come from upstream-derived state.
    • [ ] Web custom-property UI, where exposed, follows upstream schemas/metadata.
    • [ ] Rust and TypeScript fixtures prove no Scriberig-only capability inference is required.

    17. Implementation Notes¶

    17.1 Upstream evidence and current gate¶

    The prior audit inspected upstream commit aab74de0737f4b7c454cd8c8c16ca66e4dfbf898 (rpi 0.6.2). The user has selected the TNick/pi-rust fork as the intended source; missing APIs at upstream main are not a blocker. ScribeRig must consume a reviewed, committed fork revision and must never depend on fork working-tree changes.

    • rpi-ai/src/model.rs exposes upstream Model metadata and typed model properties, sampling/configuration fields, cost/context/output metadata, compatibility, and thinking maps. rpi-ai/src/types.rs defines ThinkingLevel and ThinkingLevelMap; model support and clamping are upstream-owned. Provider- effort mapping is adapter-specific and is not yet delegated by ScribeRig's current native execution path.
    • rpi-ai/src/provider.rs and rpi-ai/src/providers/ expose provider traits, stream options, and provider implementations. Those APIs are the target for execution, but do not supply a product model registry/auth configuration service.
    • rpi-cli/src/model_registry.rs is public but is not a reusable catalog boundary: refresh_catalog reads CLI config directly, and no call site outside that module was found in the inspected rpi-cli tree.
    • The active product resolution path is rpi-cli/src/provider.rs: resolve_with_extensions, authenticated_catalog, catalog_with_manifests, and execution_catalog_with_manifests. It depends on CLI args/settings/config and rpi_extensions::ExtensionSession.
    • In the previously audited upstream-main revision, rpi-cli/src/credentials.rs was private and rpi-cli/src/auth.rs plus config.rs owned credential resolution and precedence. The selected fork extracts ordinary-string resolution/readiness APIs to rpi-model-runtime; ScribeRig consumes those APIs only after the protected-material request path is wired.
    • rpi-cli/src/interactive_tui/selectors.rs and settings.rs keep reusable selector functions private to the CLI UI.

    The selected fork is TNick/pi-rust, branch codex/model-runtime-extraction, at reviewed commit 4a52baf41a19a889ca96c0f38369f7482f26973e. This pinned revision includes the rpi-model-runtime catalog/config/auth APIs, canonical thinking-name parsing, model support/clamping, and parsing of unknown model-definition properties into the runtime-only provider_options map. This preserves values along the catalog-to-Model path, but does not provide end-to-end request execution: Model.provider_options is skipped during serialization, built-in adapters ignore it, and the current ScribeRig native provider path does not forward it. ScribeRig must pin this exact committed revision; the earlier audit pins 24f79c15eafd25ca1fa29cea75ceae9436d1f94f and a15e8616e6d595b2d56d2199fbfd8386327d236d are historical only. Package installation/update/reload, package discovery composition, and reusable selectors remain in rpi-cli at this revision.

    The native catalog composition has moved to upstream ModelsConfig and build_catalog. The app retains upstream Vec<rpi_ai::Model> values and uses resolve_selection, model-supported thinking levels, and upstream clamping for provider/model validation and plan assignment resolution. This covers selection support and clamping only; provider-effort mapping and serialization remain outside the current ScribeRig execution path. Session and plan selection mutations now store and transmit explicit upstream provider_id + model_id; TUI and web pickers enumerate model descriptors and use local row IDs only as transient display handles. The ModelLibrary profile array remains in compatibility responses but does not resolve live assignments. Protocol DTOs and legacy presentation types also remain as compatibility projection/deletion targets. The scriberig-app/src/agent_console/configuration.rs JSON loader is only referenced by its own tests; resolution.rs resolves from upstream models without a library parameter. Old persisted model_profile/model session selections lose their model on deserialization, and old plan assignments using profile/model cannot deserialize into the new required provider/model pair. A safe persisted-data migration is still required; the IDs cannot be inferred without their old catalog. Provider package refresh/reload and reusable upstream selector consumption remain later gates. Section 4 and selected criteria in sections 5–6 are checked; unchecked criteria remain in sections 5–12 and 15–16. Section 13's no-local-selector rule is met, with reusable upstream selector consumption remaining a task-147 gate.     17.2 Native upstream catalog composition¶

    apps/scriberig pins rpi-ai and rpi-model-runtime to fork revision 4a52baf41a19a889ca96c0f38369f7482f26973e. The native catalog loader now parses SCRIBE_AGENT_MODEL_CATALOG as upstream ModelsConfig JSON and calls build_catalog with an empty provider manifest list. The former ScribeRig models/connections/thinking_levels schema is no longer consumed. When no provider config is supplied, the host creates a minimal OpenAI Completions provider config from SCRIBE_AGENT_MODEL.

    The native runner retains the returned Vec<rpi_ai::Model> and passes it to the TUI and HTTP application services through with_upstream_models. A credential-free ModelLibrary remains as a compatibility protocol/UI projection. Live session and plan assignments carry upstream provider/model IDs and resolve directly through rpi_model_runtime; local profile rows do not participate in that path. Its thinking list is derived from upstream model support. The native provider adapter currently accepts OpenAI Completions models only. The current protocol has required boolean capability fields, and upstream Model lacks flags for each of those fields; the projected capability booleans are compatibility-only and non-authoritative.

    Session selection mutations and history, plan assignments, and Rust and TypeScript request/response mappings now carry provider/model pairs. The server's model-selection history projection returns that pair. Legacy single-model history cannot be mapped safely without the retired catalog and remains a migration concern.

    Display model IDs and the temporary native adapter lookup key use a versioned provider/model composite with UTF-8 byte-length-prefixed components in the form rpi1:<provider-byte-length>:<provider><model-byte-length>:<model> for every catalog entry, even when the model ID is currently unique. This remains injective when either ID contains separators or Unicode text. Live assignment identity is the pair itself, not this composite. The adapter lookup key is a temporary native bridge until provider execution is fully delegated upstream.

    The host resolver supports literal values and simple $NAME/${NAME} references; it does not execute upstream command expressions. Before calling build_catalog, the loader strips provider/model typed api_key, auth_header, and header maps. It rejects catalog configuration that contains those typed fields with a generic error, so those values are neither resolved nor retained in rpi_ai::Model. Unknown model fields are retained in the upstream provider_options map and are not inspected for credential-like names; this map is currently neither persisted nor passed to requests, but must not be treated as safe for durable provenance. Catalog-specific auth cannot yet be passed through ScribeRig's authorized host credential path. The upstream resolve_credential API and auth store are not wired, so provider credential precedence/readiness remains unavailable through the catalog. The legacy ConfigValueResolver and resolve_credential APIs resolve values as ordinary Strings, which cannot satisfy ScribeRig's destination-authorized SecretValue boundary. Fork commit 4a52baf41a19a889ca96c0f38369f7482f26973e adds a separate protected-material source resolver in rpi-model-runtime and request-only secret handle in rpi-ai; the ordinary CLI string APIs remain available. ScribeRig does not consume the new seam yet. Built-in provider request implementations still need to override the protected request method, and the extension-provider ABI needs a request path that does not serialize credentials through generic options. The default protected method fails closed, so callers must not fall back to legacy stream_simple for protected credentials. Until ScribeRig integrates the seam end to end, it rejects catalog credentials and headers before catalog construction. The current OpenAI adapter does not consume all upstream sampling, compatibility, or arbitrary provider-option fields. Package manifest loading, provider auth-store/readiness, package refresh/reload, and request-adapter mapping remain follow-up seams. The pinned ModelDefinition preserves opaque values in its upstream provider_options bag, and catalog construction carries those values into rpi_ai::Model; the current native provider adapter does not yet interpret or route that bag. Unknown properties outside the upstream schema and provider_options are not preserved. Scriberig's separately configured default endpoint and credential continue through its existing host path. The older generic server entry point no longer loads the ScribeRig catalog JSON; product composition must pass its host-loaded projection and upstream models explicitly.

    The pinned fork's rpi_model_runtime::ModelDefinition parses typed sampling, compatibility, reasoning, modality, limit, cost, and header fields, and carries unknown values in provider_options. provider_to_models copies these values to rpi_ai::Model; built-in OpenAI adapters apply known sampling settings, but opaque provider_options are not applied generically and extension provider serialization omits them. ScribeRig currently drops these properties before request construction: provider_config.rs::from_connection reduces the model to a local connection, and plan_worker.rs/scriberig-agent-runtime build ModelRequest without upstream sampling or compatibility values. Scriberig does not persist this fingerprint; it is not a canonical effective-request fingerprint or a safe durable provenance value.     17.3 Implemented consumer slice¶

    scriberig-app consumes rpi-ai and rpi-model-runtime from fork commit 4a52baf41a19a889ca96c0f38369f7482f26973e. Its ThinkingLevelId is a transparent wrapper around upstream rpi_ai::ThinkingLevel; construction delegates exact-name parsing to ThinkingLevel::parse_name, and display uses upstream as_str. Scriberig session and plan assignments now retain provider/model pairs rather than local model-profile IDs. Application validation no longer accepts arbitrary thinking names or rejects a canonical upstream level because it is absent from the local presentation list. Model switching preserves a valid current thinking choice and lets upstream clamp it for the newly selected model; it does not choose the first entry in the display projection. The service keeps upstream models private and exposes a borrowed accessor only for trusted runtime composition.

    Safe model-library presentation levels are rebuilt from each upstream model's supported_thinking_levels. App selection and plan assignment resolution use rpi_model_runtime::resolve_selection for provider/model matching and effective thinking-level clamping. The scheduler carries the host catalog to the assignment resolver. Unassigned runtime fallback models are matched in the upstream catalog and then passed through resolve_selection; missing or provider-ambiguous fallback IDs fail selection. Existing fixtures now inject explicit upstream models and use canonical thinking IDs.

    ResolvedPlanExecution marks when resolution used the host runtime fallback. The native plan worker selects the same configured local adapter used by ordinary unselected turns, while retaining the upstream provider/model pair for selection and provenance. Explicit provider/model selections continue to use their pair-keyed adapter.

    Generated display model IDs and temporary native adapter lookup IDs are versioned, length-prefixed provider/model composites, so embedded separators cannot alias a different pair. Live assignments store the pair directly. Existing persisted local profile/model references cannot be mapped safely without their original catalog: legacy session choices deserialize as empty, and legacy plan assignments fail decoding. The SQLite store persists unversioned JSON in session_records and decodes it directly in list/load and both CAS paths. Close this blocker only with a versioned importer that accepts the archived exact legacy catalog and maps uniquely resolved old assignments to current upstream provider/model IDs. If that catalog is unavailable or a match is ambiguous, preserve the raw payload until an operator chooses reset or plan recreation; do not infer from past ModelInvocation records.

    The catalog loader strips provider/model typed API keys, auth headers, and request header maps before build_catalog, and rejects catalog configs containing those typed values. Opaque model provider_options are not inspected for credential-like names and must not be treated as safe for durable records. The loader does not resolve credential references or copy API-key references into local adapters. The catalog adapter has no authorized per-provider credential injection seam yet; catalog-specific auth remains unsupported. The Scriberig-configured default provider endpoint and credential continue through its existing host configuration path.
