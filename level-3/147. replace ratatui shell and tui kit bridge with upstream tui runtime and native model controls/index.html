    Replace the Ratatui Shell and TUI-Kit Bridge with the Upstream TUI Runtime and Native Model Controls¶

    Status: [ ] In Progress

    Current dependency note (2026-10-21, late revalidation): all ScribeRig rpi-* dependencies now pin controlled fork commit ebcf8d5e75d20fa3a6cc7cc76cbcdcec4cc36eb8, based on official upstream 0.7.1 main 281dfddfa39ac063d86de57b75370974c4d75e6c. The fork additionally exports upstream key types, caches visible rows, adds validated TreeList item replacement, exposes a host tick callback on the TUI lifecycle, publishes theme preset metadata, and adds typed AssistantMessageEvent::ReasoningSummaryDelta plus the isolated worker boundary. Earlier focused checks passed at a previous pin; checks have not been rerun after this pin change. Older revision references below are historical implementation checkpoints.

    1. Objective¶

    After task 146 completes, make upstream rpi-tui the actual terminal product framework rather than a hidden primitive source underneath the existing ScribeRig Ratatui shell.

    This task replaces the normal terminal lifecycle/render/input/focus/overlay/composer/model-control path with upstream TUI/component machinery.

    It intentionally creates a visibly different implementation boundary. Passing tests while retaining the old Ratatui shell is not completion.

    Do not begin task 148 until this sheet is complete.

    2. Read Before Editing¶

    • [ ] Read root and design/AGENTS.md.
    • [ ] Read crates/scriberig-tui/AGENTS.md and nearest instructions for all terminal/product code changed.
    • [ ] Read Level-1 documents 015, 020, 022.
    • [ ] Read Level-2 documents 021, 022, 032.
    • [ ] Read completed tasks 144–146.
    • [ ] Inspect upstream rpi-tui Component, TUI, terminal, editor, layout, overlay, selection, theme, status/footer, transcript/message, and main/fullscreen implementations.
    • [ ] Inspect upstream model/provider/thinking selector code and task 145's upstream extraction gates.

    3. Checklist Discipline¶

    • [ ] Keep this file open during implementation.
    • [ ] Tick exact criteria after focused verification.
    • [ ] Never bulk-tick.
    • [ ] Revert invalidated criteria.
    • [ ] Do not preserve the current Ratatui shell as the default compatibility path.
    • [ ] Do not convert upstream ANSI/component output back into Ratatui widgets.
    • [ ] Missing generic upstream UI primitives must be contributed upstream rather than recreated as a new ScribeRig widget framework.

    4. Select Upstream Terminal Mode and Lifecycle¶

    Use upstream terminal/runtime ownership for the active srig tui process.

    Select the appropriate upstream regular/fullscreen mode according to the desired product behavior, but let upstream own:

    terminal setup/restore
raw mode
alternate/main screen behavior
cursor
input loop
render scheduling
resize
focus routing
overlay routing

    Acceptance:

    • [x] Active srig tui starts through upstream TUI runtime.
    • [x] ScribeRig's direct terminal guard is no longer the active lifecycle owner.
    • [x] Exactly one terminal lifecycle owner exists.
    • [ ] Normal exit, Ctrl-C, panic/error restoration remain covered.

    5. Remove the Double-Rendering Bridge¶

    The current path that uses upstream components internally and then strips/reconstructs their output through Ratatui must be removed from the normal product path.

    Forbidden final pattern:

    rpi-tui component.render()
  -> strip ANSI / flatten lines
  -> Ratatui Text/Paragraph/Block

    Required final pattern:

    ScribeRig semantic component
  + upstream components
  -> upstream TUI child/overlay composition
  -> upstream render/runtime

    Static baseline audit (2026-10-20): crates/scriberig-tui/src/render_conversation.rs::conversation_text calls scriberig_tui_kit::render_markdown; that wrapper sanitizes the row text, renders it with upstream rpi_tui::Markdown, strips ANSI styling, and returns plain lines that conversation_text converts into Ratatui spans. The Markdown parser is already upstream-owned. The remaining duplicate is the flattening bridge into the active Ratatui shell. Do not remove the wrapper in isolation: it is currently the sanitization boundary, and its consumer still requires Ratatui text. Replace this entire path when the semantic conversation component is composed directly into the upstream TUI runtime. No acceptance item below is satisfied by this inventory alone.

    Acceptance:

    • [x] Composer renders directly as an upstream component.
    • [x] Markdown/message rendering remains upstream-rendered through the final terminal path.
    • [x] Selection/list components render directly through upstream.
    • [x] Upstream theme/style output is not flattened and recreated in Ratatui.
    • [x] No normal render frame is built with Ratatui widgets.

    6. Move the Composer to the Upstream Product Path¶

    Use the upstream editor/composer directly as the active input component.

    Preserve ScribeRig submission semantics:

    ordinary prompt -> shared ScribeRig branch operation
recognized slash command -> local/upstream command dispatch
historical reply target -> stable ScribeRig ContinuationAnchor
multiline draft -> local UI state until submit

    Acceptance:

    • [x] Startup composer is an upstream component.
    • [ ] Cursor/IME/Unicode behavior comes from upstream.
    • [ ] Paste goes through upstream terminal/editor behavior and ScribeRig safety policy.
    • [ ] ScribeRig stable reply anchor remains independent of editor cursor/focus.
    • [x] Submission does not bypass shared ScribeRig application operations.

    7. Use Upstream Provider/Model/Thinking Controls¶

    Provider/model/thinking selection must use upstream product/UI machinery rather than ScribeRig selectors built from upstream data.

    rpi-tui already exposes reusable generic SelectItem, SelectList, and SearchableSelectList components. Adapt the ScribeRig credential-safe model library rows to those generic selector APIs; keep selection effects and ScribeRig assignment semantics in ScribeRig.

    Do not extract the rpi-cli model/provider/thinking selector orchestration into rpi-tui. That code includes CLI catalog matching and ambiguity rules, provider authentication/default persistence, and AgentLane updates. Those behaviors are not generic UI responsibilities. A task-144/145 upstream contribution is warranted only if migration demonstrates a missing reusable UI primitive beyond the existing generic selector components.

    Earlier pinned API integration checkpoint (superseded by the current pin): ScribeRig pinned the controlled pi-rust fork at 15a68ef2d69a312122c09c1eccfa0fbd454c48b5, which includes the current bigfish1913/pi-rust upstream commit 7d019f85cde614a6aa267a7d2e816e04a7e6abbe and exposes typed rpi_tui::InputEvent, Component::handle_event(&InputEvent), native SelectList/SearchableSelectList components, and TuiAltScreen::{run_until, dispatch_input, note_resize}. The active conversation and selector paths use upstream Markdown, Editor, list, and fullscreen lifecycle APIs. At that checkpoint, run_until owned startup, input reading, and restoration; ScribeRig's synchronous application loop ran inside its stop predicate. The then-pinned Editor and selector lists did not implement typed event handling, so thin adapters forward normalized events to their upstream key and paste handlers. TuiAltScreen::set_focus owns the active component for composer, help, and selector paths. Because the pinned TuiAltScreen dispatches only to the focused component and has no global key hook, every ScribeRig focused adapter recognizes normalized Ctrl-C before forwarding input to upstream selectors, editors, and overlays. This keeps quit global while terminal input, focus, and lifecycle remain upstream-owned. Model-library selections still pass through the existing revision-checked ScribeRig reducers/effects. The scriberig-tui target has no Ratatui or scriberig-tui-kit dependency. The legacy renderer's semantic assertions were moved to model/projection tests; renderer-specific layout and style assertions were retired with that renderer. These test targets have compile-checked, but the tests have not been run.

    The active command palette opens upstream SearchableSelectList on Ctrl+P. Its selected stable action ID returns to ScribeRig's existing reducer/effect path. Palette state no longer stores an upstream-backed stable selector.

    Model and plan-node assignment selection now share the upstream selector path. The old ScribeRig palette-backed model/thinking picker implementation and its model-library-loaded overlay side effect were removed. /model, /thinking, the provider/model/thinking controls, command-palette actions, and /assign open upstream selector components; chosen IDs continue through the existing revision-checked ScribeRig session or plan operations. cargo fmt --all, the repository convention linter, and cargo check -p scriberig-tui --all-targets --locked pass after this change. Runtime interaction was not run; the user can verify the TUI behavior directly.

    At the current fork pin, SelectList and SearchableSelectList both implement Component::handle_event, while SearchableSelectList also implements Focusable. Upstream selectors own filtering and row navigation; their callbacks return stable IDs to ScribeRig, whose reducers retain assignment and command semantics. Plain SelectList lacks a hardware-cursor focus contract, but this does not require a ScribeRig selector adapter. Use the upstream TuiAltScreen dispatch and resize APIs rather than adding a second generic dispatch framework.

    Acceptance:

    • [x] Model selector is upstream UI.
    • [x] Provider selector is upstream UI where product-exposed.
    • [x] Thinking selector is upstream UI and shows levels from upstream selected-model metadata.
    • [x] Model switch updates thinking options using upstream behavior.
    • [x] Provider authentication/readiness is rendered from upstream state.
    • [x] No ScribeRig-local model selector/picker remains on the normal terminal path.

    The source audit and package all-target compile verified this criterion. /model, /thinking, provider/model/thinking controls, command-palette actions, and /assign all open upstream selector components. The removed ScribeRig palette-backed model/thinking picker code has no production module or runtime call site. Interactive behavior remains for user verification.

    The active root invocation resolves its selected upstream model and thinking assignment from one catalog snapshot. Provider construction receives that exact model value, avoiding a second catalog lookup between selection and binding. Plan workers now retain the exact upstream Model in the ephemeral ResolvedPlanExecution produced from the catalog snapshot used for selection; provider construction receives that model without a second catalog lookup. The resolved value is not serialized or debug-formatted. Custom model-property settings use upstream PropertyEditor and schema descriptors through the ScribeRig host adapter; Task 145 retains the remaining provenance and request-shaping verification gates.

    Provider controls now display per-model credential readiness derived with upstream readiness_from_catalog and ScribeRig's destination-authorized secret provider. The projection is limited to available, missing, denied, unsupported, or catalog-header states. It never includes source names, endpoint URLs, or credential values. The local TUI obtains the projection from its configured agent runner; remote model-library responses may omit it when their host does not supply an authorized readiness resolver. This status describes credential availability only and does not claim that the provider endpoint has passed a live request health check.

    The assignment and readiness strip adapts the current ScribeRig session selection, provider credential status, and shell message into upstream FooterComponent status/model/thinking fields. ScribeRig supplies semantic content and key hints; the upstream component owns footer layout and rendering.

    8. Use Upstream Custom Model Property UI¶

    When upstream supports editable model/provider custom properties, use upstream UI/config components.

    Do not implement a ScribeRig-specific editor for:

    sampling parameters
reasoning effort maps
compatibility flags
provider-specific model properties
custom model fields

    If upstream lacks a generic custom-property editor needed by ScribeRig, complete the upstream contribution before checking this section.

    Acceptance:

    • [x] Custom-property editing uses the upstream PropertyEditor component.
    • [x] Upstream model-runtime APIs validate property values before updating config and runtime models.
    • [x] ScribeRig applies local authorization policy and live-catalog refresh around upstream configuration.
    • [ ] A deterministic test exercises a property through upstream UI/config and into a resolved provider request.

    Fork commit 46ea1250bd695540b7f0b395afd6e10518fc05ff adds rpi-tui::PropertyEditor and the schema-validated ModelsConfig update API. ScribeRig has a local TUI/service adapter that passes submitted values to upstream validation, checks the local agent_model_config_edit capability, and refreshes the live ModelCatalog. Secret-like, write-only, read-only, password-format, nested sensitive, and opaque compound properties are omitted before display. This does not create a ScribeRig property schema or expose schemas through protocol.

    The upstream PropertyEditor supports distinct choice labels and opaque values. The cited b4b8739a5c0b6dab42293f70006222327be01845 revision was an earlier integration checkpoint, not the active pin. The current controlled fork pin at that checkpoint was bad1c5b4aa6f26cc231168d75a09165e990de39a; its model-runtime source includes ModelsConfigFile. When SCRIBE_AGENT_MODEL_CONFIG_PATH selects a file, edits are validated by upstream and atomically persisted through that API before the live catalog is refreshed. SCRIBE_AGENT_MODEL_CATALOG environment JSON remains read-only. Extension manifest-only models without a corresponding ModelsConfig row remain read-only. Source inspection of runtime/upstream/property_editor.rs, runtime/upstream/event_loop/input/model_properties.rs, service_operation_adapter.rs, and apps/scriberig/src/native_tui_agent/model_properties.rs confirms that the UI uses upstream PropertyEditor, edits pass through upstream schema validation, and the embedded host requires agent_model_config_edit before publishing a transactionally persisted catalog refresh. These source-level criteria are checked; the end-to-end request-shaping criterion remains unchecked.

    The active scriberig-tui shell depends on rpi-tui for keybinding key types. The controlled fork's rpi-tui root did not re-export the KeyCode and KeyModifiers types used by its public KeyCombo API, so ScribeRig had a redundant direct production dependency on Crossterm. A focused fork API contribution now re-exports those key types; ScribeRig imports them from rpi_tui and keeps Crossterm only as a test dependency for the test-only input translator. This does not move terminal input ownership back into ScribeRig; TuiAltScreen::run_until continues to own the live input reader and lifecycle.

    9. Move Palette, Help, Status, Focus, and Overlays Upstream¶

    Adopt upstream mechanics for:

    command palette/search
help overlay
modal focus
confirmation/input overlays
status/footer
scroll/navigation primitives

    ScribeRig may supply command/action rows and semantic content, but not another generic overlay framework.

    Acceptance:

    • [x] Palette is an upstream component.
    • [x] Help is composed through upstream overlay/component APIs.
    • [x] Focus is managed by upstream TUI focus APIs.
    • [x] Confirmation and input dialogs are upstream overlays/components.
    • [x] Status/footer structure is upstream-owned.
    • [x] Important ScribeRig status remains visible through content supplied to upstream components.

    The reachable /edit input flow now mounts an upstream Editor inside an upstream overlay and forwards changed, submitted, and cancelled values into the existing ScribeRig reducers. Confirmation state also has an upstream Dialog adapter: it renders the stored action, target, base, and summary, then emits only accept/cancel intents carrying the exact ConfirmedCommit shown. The existing CommitConfirmed reducer revalidates the review against that payload before issuing the shared commit operation; stale acceptance or cancellation events cannot act on a newer confirmation. Task 148 still needs to expose the review route through its semantic review surface.

    10. Theme and Styling¶

    Use upstream theme/style ownership.

    ScribeRig may define semantic roles or map branch depth/status into upstream style tokens, but it must not maintain a second concrete color/theme framework.

    Acceptance:

    • [x] Theme selection/application is upstream-owned.
    • [x] ScribeRig semantic roles map into upstream styles.
    • [x] Branch depth/status styling still has non-color structural/text cues.
    • [x] Theme changes do not alter semantic/execution state.

    The ScribeRig-owned Tone/PaletteColor/StyleToken mapping and the scriberig-tui-kit crate have been removed.
