    Scaffold Derivation Crate, Profiles, Dependencies, and Keys¶

    Objective¶

    Create the canonical reusable derivation/cache crate and implement the minimum public model needed to describe exact derivation requests.

    This task must produce:

    • the crate scaffold;
    • derivation profile identity;
    • dependency types;
    • deterministic dependency sets;
    • deterministic derivation keys;
    • focused unit tests for those types.

    Do not implement result persistence, invalidation, selection, freshness, retention, events, domain execution, agents, or server integration in this task.

    Read First¶

    Read these documents before editing:

    1. design/level-1/008. derived knowledge caching and incrementality.md
    2. design/level-2/001. derived knowledge runtime and cache design.md
    3. design/level-2/001. universal knowledge model rust libraries.md
    4. the repository-wide workspace/package-layout Level 2 design;
    5. the identity/revision/snapshot implementation design.

    Inspect the actual root Cargo.toml and existing crate directories.

    The design uses the name scriberig-derive, but earlier designs may have standardized the workspace on sr-* crate names. Use the naming convention already established in the real workspace.

    Do not create both scriberig-derive and sr-derive.

    If a derivation crate already exists, extend it.

    If the shared core identity crate or universal graph crate does not exist yet, this task has unmet prerequisites. Do not reimplement those prerequisites inside the derivation crate.

    Files to Create or Modify¶

    Inside the one canonical derivation crate:

    Cargo.toml
src/lib.rs
src/profile.rs
src/dependency.rs
src/key.rs

    Modify the root workspace manifest only if the derivation crate must be registered.

    Add module-local unit tests in these files or a focused test file if that matches repository convention.

    Do not create any additional domain-specific crate.

    1. Crate Dependencies¶

    Depend only on the lowest layers needed for exact identities and universal graph references.

    Expected dependencies are conceptually:

    shared core
universal graph

    Do not add:

    • SQLite;
    • Tokio merely for future async work;
    • HTTP libraries;
    • model-provider SDKs;
    • CLI libraries;
    • UI libraries;
    • Markdown/Rust/PDF/session crates.

    Keep dependencies minimal.

    2. Derivation Profile¶

    In profile.rs, define public types representing an exact derivation definition.

    The model must distinguish:

    human/domain kind
exact version/revision
optional producer/implementation identity
optional configuration identity
scheduling hint

    Use existing strongly typed identifier/value conventions where available.

    A simple initial representation is acceptable if it remains explicit and deterministic.

    For example, an exact profile may conceptually contain:

    kind: "function-summary"
version: "v1"
producer: optional exact producer identity
configuration: optional exact configuration identity
schedule: Lazy | Eager

    Do not create a mutable global current profile.

    If aliases are needed later, they belong outside exact profile identity.

    Required properties¶

    • profiles are cloneable and debuggable;
    • equality means compatible derivation semantics;
    • fields participating in equality are deterministic;
    • domain names are represented by extensible identifiers/strings, not hard-coded production enums.

    3. Dependency Types¶

    In dependency.rs, define a domain-independent dependency enum or equivalent tagged representation.

    It must support at least:

    ExactRevision
Snapshot
ScopeOrCollection
Configuration
DerivedResult

    Exact revision dependency¶

    Must reference an exact entity/revision pair using the existing shared type when available.

    Do not represent an exact dependency as EntityId alone.

    Snapshot dependency¶

    References an exact SnapshotId when a derivation genuinely depends on a whole scope.

    Scope or collection dependency¶

    Represents completeness/absence dependencies independently from positive result members.

    The first implementation may use an opaque deterministic scope identity rather than designing every possible domain scope.

    The important requirement is that scope dependency is a first-class variant.

    Configuration dependency¶

    Represents exact semantic configuration such as style/toolchain/schema/adapter configuration.

    Use an opaque exact identity/value rather than process-global mutable state.

    Derived-result dependency¶

    References another immutable derived result identity or exact artifact handle using an existing appropriate type if one exists.

    Do not invent domain-specific variants.

    4. Dependency Set¶

    Define DependencySet or an equivalent type.

    It must:

    • contain zero or more dependencies;
    • produce deterministic equality/order/encoding behavior;
    • avoid treating incidental insertion order as semantic when dependencies are logically a set;
    • make duplicate dependencies harmless or reject them deterministically;
    • be easy to inspect for debugging.

    Prefer a deterministic ordered set representation or explicit normalization.

    Do not rely on nondeterministic hash-map iteration for cache-key identity.

    5. Derivation Key¶

    In key.rs, define DerivationKey.

    It must include:

    exact derivation profile
normalized dependency set

    If the project already has a canonical encoding/hash abstraction appropriate for deterministic values, integrate with it.

    If not, implement deterministic structural equality first and leave cryptographic/content hashing to the existing identity layer or later work. Do not invent a second hashing system.

    The key must satisfy these invariants:

    1. same profile + same normalized dependencies => same key/equality;
    2. changing one RevisionId => different key;
    3. changing one scope/snapshot/config dependency => different key;
    4. changing dependency insertion order alone => same key;
    5. unrelated project changes are absent from a local key unless explicitly declared as dependencies.

    Do not automatically insert the current SnapshotId into every key.

    6. Public API¶

    Update lib.rs to expose stable public equivalents of:

    DerivationProfile
DerivationSchedule
Dependency
DependencySet
DerivationKey

    Avoid broad glob re-exports if the repository style prefers explicit module paths.

    Add crate-level documentation stating:

    • the crate models derived/cache semantics;
    • cache population does not alter canonical snapshots;
    • exact reuse is revision/dependency based;
    • the crate is usable without agents or a server.

    7. Required Tests¶

    Add tests for:

    • two equal profiles;
    • profile version change changes equality;
    • exact revision dependency uses both entity and revision;
    • dependency-set normalization ignores insertion order;
    • duplicate dependency normalization;
    • same profile/dependencies produce equal derivation keys;
    • one revision change changes key;
    • one configuration dependency change changes key;
    • one snapshot dependency change changes key;
    • a local key remains unchanged when an unrelated snapshot exists but is not a declared dependency;
    • scope dependency is representable without positive result members;
    • custom domain/profile names work without changing production enums.

    Use fake/test IDs according to the existing core test helpers.

    Validation¶

    Run at minimum:

    cargo fmt
cargo check --workspace
cargo test --workspace

    If available and already used by the project:

    cargo clippy --workspace --all-targets

    Do Not¶

    Do not:

    • create a second core or graph crate;
    • redefine EntityId, RevisionId, or SnapshotId;
    • implement DerivedArtifact again if the graph crate already owns it;
    • add a database schema;
    • add background scheduling;
    • add async runtime dependencies without necessity;
    • add agent/model code;
    • add protocol/server/web code;
    • hard-code Rust, Markdown, PDF, or session derivation kinds.

    Completion Checklist¶

    • [x] exactly one derivation crate exists;
    • [x] workspace registration is correct;
    • [x] profile identity is explicit and versioned;
    • [x] eager/lazy hint exists without a scheduler;
    • [x] exact revision dependency exists;
    • [x] snapshot dependency exists;
    • [x] scope/collection dependency exists;
    • [x] configuration dependency exists;
    • [x] derived-result dependency exists;
    • [x] dependency sets normalize deterministically;
    • [x] derivation keys are deterministic;
    • [x] no implicit global snapshot is added to local keys;
    • [x] required tests pass;
    • [x] no higher-level subsystem dependency was introduced.
