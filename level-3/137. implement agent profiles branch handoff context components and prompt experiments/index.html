    Implement Agent Profiles, Branch Handoff Context Components, and Evidence-Driven Prompt Experiments¶

    Status: [ ] Not Started

    1. Objective¶

    Implement the architecture defined by:

    • design/level-1/021. agent profiles context composition and evidence driven optimization.md;
    • design/level-2/030. agent profile context component and prompt experiment runtime.md.

    Also preserve the controlling contracts from:

    • design/level-1/016. model driven agent execution and branch isolation.md;
    • design/level-1/017. recursive agent decomposition and context isolation.md;
    • design/level-1/018. durable plans dependency scheduling and multi-model execution.md;
    • design/level-1/019. semantic agent operations and projection-first editing.md;
    • design/level-1/020. provider continuation state and observable model execution.md;
    • design/level-2/023. agent runtime model provider and branch orchestration.md;
    • design/level-2/025. provider continuation and observable model execution.md;
    • design/level-3/135. implement recursive semantic agent plans dependencies and tree tui.md;
    • design/level-3/136. implement provider continuation full prompt and observable reasoning.md.

    The first visible behavior change is intentionally small:

    Every model invocation receives the Scriberig core behavioral invariants, and every non-root branch receives an additional instruction to make its final response a compact one-paragraph parent handoff. Root branches do not receive that handoff instruction. Existing child completion continues to persist the final child output as BranchResult.summary; do not add another summarizer model call.

    The complete task then makes those instructions versioned context components, records their exact provenance in effective requests, and establishes evidence-backed prompt experiments without making prompt files canonical state.

    Follow phases in order. A simpler implementation agent should not jump directly to an autonomous optimizer.

    2. Non-Negotiable Working Rules¶

    2.1 Read before editing¶

    Before changing code:

    • [ ] Read root AGENTS.md completely.
    • [ ] Read design/AGENTS.md completely.
    • [ ] Read the nearest AGENTS.md for every crate/directory modified.
    • [ ] Read Level-1 documents 009, 016, 017, 018, 019, 020, and 021.
    • [ ] Read Level-2 documents 023, 025, and 030.
    • [ ] Read Level-3 tasks 135 and 136, especially incomplete task-136 work that may own complete-request provenance.
    • [ ] Inspect current scriberig-agent-core, scriberig-agent-runtime, scriberig-session, scriberig-app, and apps/scriberig implementations before creating names.
    • [ ] Search for existing profile/context/branch-role/effective-request types before adding any new type.
    • [ ] Record any material difference from the baseline in this document before adapting the prescribed steps.

    2.2 Checklist discipline¶

    • [ ] Keep this file open while implementing.
    • [ ] Tick a checkbox only after the exact criterion is implemented and focused verification passes.
    • [ ] Tick items immediately; do not bulk-check at the end.
    • [ ] If later work invalidates a checked item, return it to [ ] immediately.
    • [ ] Keep unfinished later phases unchecked even if scaffolding exists.
    • [ ] Before changing this status to Complete, review every checked item against code and test evidence.

    2.3 Architectural prohibitions¶

    Do not:

    • create a second session/branch store;
    • create a second model/tool execution loop;
    • equate child branch identity with a new agent identity;
    • add an AgentId that merely aliases branch identity;
    • copy the full parent transcript into a child by default;
    • copy the child transcript into its parent at completion;
    • add a second provider call solely to summarize every child branch;
    • force root user-facing output into a one-paragraph summary;
    • compile prompts independently in TUI/web/server code;
    • make Markdown/TOML/source prompt files canonical profile state;
    • automatically append every observed failure to always-on prose;
    • let prompt experiments overwrite the active base profile before validation/promotion;
    • use provider continuation IDs as Scriberig session/branch/profile identity;
    • expose hidden chain-of-thought as experiment evidence;
    • bypass ordinary semantic candidate/revision/validation/promotion because the edited knowledge happens to control prompts.

    2.4 Test discipline¶

    Until all implementation phases are complete, prefer focused tests such as:

    cargo test -p scriberig-agent-core profile
cargo test -p scriberig-agent-runtime context
cargo test -p scriberig-agent-runtime fingerprint
cargo test -p scriberig-session model_invocation
cargo test -p scriberig-app child
cargo test -p scriberig-app prompt_experiment
cargo test -p scriberig -- child_runtime

    Do not run the repository-wide final gate after every phase.

    4. Phase A — Make Branch Role Explicit¶

    Do this before changing prompt text.

    Task A1 — Add a provider-neutral branch role¶

    Add an explicit type in the lowest appropriate reusable owner. Prefer scriberig-agent-runtime::context if the role is currently only context-compilation input; move to scriberig-agent-core only if it is already useful across reusable agent APIs.

    Use a shape equivalent to:

    pub enum BranchRole {
    Root,
    NonRoot { parent: String },
}

    Exact field types may follow existing stable branch-reference conventions.

    Requirements:

    • [ ] Root/non-root is explicit and not inferred from titles.
    • [ ] Non-root can retain the parent branch reference when useful.
    • [ ] The type is documented according to repository rules.
    • [ ] Serialization is added only if the type crosses a durability/protocol boundary.
    • [ ] No new canonical branch identity system is created.

    Task A2 — Extend BranchExecutionContext¶

    Add branch role to BranchExecutionContext or the current replacement type.

    Prefer constructors/builders that make ordinary root behavior backward-safe, for example:

    BranchExecutionContext::new(...) -> Root by default
.with_branch_role(...)

    or distinct root/child constructors if current APIs make that clearer.

    Requirements:

    • [ ] Existing root callers remain explicit or safely default to Root.
    • [ ] Child/delegation callers explicitly mark NonRoot.
    • [ ] Historical continuation that creates a new child uses the correct role from actual branch topology.
    • [ ] Plan workers use actual branch parentage rather than plan nesting heuristics.

    Focused tests¶

    • [ ] default/root constructor yields Root;
    • [ ] child constructor/builder retains parent branch identity;
    • [ ] role equality/debug behavior is deterministic.

    Task B2 — Define the bootstrap default profile¶

    Add one deterministic bootstrap profile construction function in the shared agent/runtime layer.

    It must contain separate components for:

    1. core Scriberig invariants — activation Always;
    2. non-root branch handoff — activation NonRootOnly.

    Core component meaning must include:

    operate inside the current Scriberig branch/context frame
semantic/domain operations first for understood domains
files are projections where understood
canonical changes use candidate/migration/validation/promotion
stable semantic handles and exact snapshots/revisions when exact state matters
child branches are focused context isolation and do not alone imply another agent
parents/dependencies consume compact durable results, not child transcripts
capabilities are used progressively

    Non-root handoff meaning must include:

    When about to finish this non-root branch, make the final response a compact
one-paragraph summary for the parent. Include important outcome,
decisions/discoveries, remaining issues, and durable semantic/result handles.
Do not reproduce the branch transcript or hidden reasoning.

    The exact prose may be polished, but preserve the semantic requirements.

    • [ ] Core and handoff are separate components.
    • [ ] Profile identity/revision is stable for identical definitions.
    • [ ] Component identities/revisions are stable for identical definitions.
    • [ ] Changing a component's behaviorally relevant content changes its revision/fingerprint.
    • [ ] The bootstrap definition is short; no unrelated domain guidance is added.
