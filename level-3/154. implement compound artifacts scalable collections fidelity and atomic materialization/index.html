    Implement Compound Artifacts, Scalable Collections, Fidelity, and Atomic Materialization¶

    Status¶

    Planned.

    All completion items remain unchecked until implemented and verified.

    1. Goal¶

    Implement the shared infrastructure required before XLSX, DOCX, CAD, or geospatial write support is added.

    This task must deliver:

    1. logical artifacts that may have one, many, or container-internal physical members;
    2. exact source evidence and artifact/member manifests;
    3. explicit fidelity/editability and opaque-preservation capability;
    4. bounded scalable semantic collection access;
    5. typed support for non-text projection anchors where needed;
    6. staged multi-member materialization with failure/recovery evidence;
    7. shared application/protocol/client exposure sufficient for later domain tasks.

    This task is constrained by:

    • level-1/002. universal knowledge model.md;
    • level-1/003. identity revisions and snapshots.md;
    • level-1/005. changes migrations branches and merge.md;
    • level-1/006. projections and bidirectional editing.md;
    • level-1/007. domain modeling and adapters.md;
    • level-1/010. universal query and operation model.md;
    • level-1/013. trust validation capabilities and provenance.md;
    • level-1/019. semantic agent operations and projection-first editing.md;
    • level-1/024. projection styles personalized representations and materialization policy.md;
    • level-1/025. compound artifacts scalable collections and rich domain editing.md;
    • level-2/008. filesystem projection synchronization.md;
    • level-2/010. universal query and operation implementation.md;
    • level-2/011. application operations protocol and runtime boundaries.md;
    • level-2/027. project wide candidate workspaces validation and materialization.md;
    • level-2/034. projection style resolution loss-aware reconciliation and cross-surface contracts.md;
    • level-2/035. rich project artifacts office cad and geospatial implementation plan.md.

    4. Architectural Prohibitions¶

    Do not:

    • create a second project catalog;
    • create a second canonical blob/file database disconnected from the universal store/projection evidence model;
    • equate an artifact with exactly one filesystem path;
    • use absolute machine paths as semantic identity;
    • make parser-library object IDs canonical Scriberig identities;
    • make fidelity a UI-only flag;
    • silently drop unknown source-significant package members;
    • report successful multi-member materialization after only some required members were written;
    • bypass candidate/migration/validation/promotion for artifact edits;
    • add unrestricted ZIP/XML/SQLite mutation as the model-facing normal editing API;
    • eagerly serialize huge spreadsheet/GIS collections merely to satisfy inspect or list.

    5. Phase A — Define Artifact and Member Contracts¶

    Implement or reuse shared contracts equivalent in responsibility to:

    ArtifactKind
ArtifactMemberKey
ArtifactMemberDescriptor
ArtifactSourceEvidence
ArtifactExternalReference
ArtifactManifest
ArtifactFidelity
ArtifactPreservationStatus

    The owning crate must follow current dependency direction. Prefer existing project/core/projection owners over a new crate.

    Requirements:

    • [ ] One artifact has stable semantic identity separate from paths/member names.
    • [ ] One artifact revision can reference one or more exact physical source members.
    • [ ] A member carries a logical key and exact digest.
    • [ ] Filesystem members carry project-relative paths, never absolute paths as canonical identity.
    • [ ] Container-internal members can use adapter-defined logical part names without pretending they are project files.
    • [ ] Artifact manifests serialize deterministically.
    • [ ] Exact evidence provenance identifies scan/import source and adapter/version where applicable.
    • [ ] External references are represented explicitly rather than hidden in arbitrary strings.
    • [ ] Public types contain no parser-native handles/pointers.

    Focused tests:

    • [ ] one-file artifact manifest round trip;
    • [ ] four-member Shapefile-like manifest round trip;
    • [ ] container-member manifest with no extracted filesystem path;
    • [ ] deterministic equality/encoding for equivalent manifests;
    • [ ] absolute path changes do not redefine semantic artifact identity.

    6. Phase B — Extend Project Scan Classification and Grouping¶

    Extend persisted scan/import classification so adapters may group related paths deterministically.

    Requirements:

    • [ ] Every selected regular file still has its own exact scan evidence and digest.
    • [ ] Classification may nominate a logical artifact/grouping key.
    • [ ] Grouping happens from the persisted scan manifest, not by a hidden fresh rescan.
    • [ ] Grouping rules are domain/adapter owned.
    • [ ] Ambiguous grouping returns structured diagnostics.
    • [ ] Unsupported files still use the existing binary fallback.
    • [ ] A grouped artifact retains each member's project-relative path and digest.
    • [ ] A single container file can classify as one compound artifact without exposing internal package parts as scanned project files.
    • [ ] Import produces stable artifact semantic handles usable by later operations.

    Add a synthetic test adapter if necessary; do not wait for XLSX/Shapefile tasks to test the generic mechanism.

    Focused tests:

    • [ ] group roads.shp, roads.dbf, roads.shx, roads.prj into one synthetic artifact;
    • [ ] leave unrelated roads.txt outside that group;
    • [ ] prove import uses the recorded manifest after the physical directory changes;
    • [ ] prove grouping ambiguity is diagnostic and not silently resolved.

    7. Phase C — Add Fidelity and Preservation Capability¶

    Build on current projection capabilities and Level-2 034.

    Introduce an exact capability model able to represent at least the responsibilities of:

    InspectOnly
ReadOnlyDerived
LosslessEditable
LossAwareEditable
EditableWithOpaquePreservation
RestrictedExternalProviderEdit
Unsupported

    Exact enum names may differ if repository naming already exists.

    Requirements:

    • [ ] Fidelity is available through shared domain/projection capability discovery.
    • [ ] Fidelity can depend on adapter/version and artifact-specific conditions.
    • [ ] Opaque-preservation guarantee/status is explicit.
    • [ ] A parser being available does not automatically imply write support.
    • [ ] Unsupported unknown content can downgrade editability deterministically.
    • [ ] Capability diagnostics explain why an artifact is read-only/restricted.
    • [ ] Fidelity participates in editable projection/reconciliation safety checks.
    • [ ] UI/agent code consumes capability rather than guessing from file extension.

    Focused tests:

    • [ ] artifact without writer reports read-only;
    • [ ] artifact with unknown unpreservable extension reports restricted/read-only;
    • [ ] artifact with proven opaque preservation reports editable-preserving;
    • [ ] serialized protocol/client view preserves the same fidelity result.

    8. Phase D — Add Opaque Preserved Content Boundary¶

    Implement an adapter-owned preserved-content mechanism.

    Requirements:

    • [ ] Opaque preserved content is bound to exact base artifact/member evidence.
    • [ ] Opaque content is not flattened into arbitrary universal property bags when it has no semantic interpretation.
    • [ ] Adapters can carry opaque preserved records through render/materialization.
    • [ ] Unrelated semantic edits can prove preserved records survived.
    • [ ] A requested operation that invalidates/removes the owner may explicitly discard affected opaque records with provenance.
    • [ ] Failure to preserve required opaque content blocks promotion/materialization or downgrades capability.
    • [ ] Opaque source evidence remains distinct from derived extraction.

    Create a synthetic compound fixture containing one understood record and one opaque record and prove the understood record can change without losing the opaque record.

    9. Phase E — Add Scalable Collection Access¶

    Do not redesign the universal graph. Add the minimum contracts necessary for bounded semantic collections.

    Requirements:

    • [ ] Collection reads support deterministic pagination/range selection.
    • [ ] Domain-specific selector/query extensions can be registered without a universal untyped Any payload.
    • [ ] Results retain exact snapshot/revision context.
    • [ ] Member results contain stable semantic handles.
    • [ ] A collection may report count/extent/summary without enumerating all members.
    • [ ] Large collection implementations may use indexes/backing blocks internally.
    • [ ] Derived indexes record provenance/dependencies through existing derivation infrastructure.
    • [ ] Semantic mutations identify the smallest changed member/range/collection structure rather than replacing an entire huge collection by default.

    Add test-only scalable collection data with at least tens of thousands of logical members without building an enormous protocol response.

    Focused tests:

    • [ ] request page 2 returns only bounded members;
    • [ ] range query touches only requested logical range plus required index data;
    • [ ] member handle resolves in the same snapshot without enumerating all siblings;
    • [ ] changing one member produces a local changed set;
    • [ ] stale snapshot member reads remain exact.

    10. Phase F — Add Non-Text Projection Anchor Boundary¶

    Use existing selection/projection architecture.

    Requirements:

    • [ ] A projection may expose adapter/domain-owned typed anchor data.
    • [ ] Anchor schema/kind is discoverable.
    • [ ] Anchor resolves to semantic handle(s) plus exact snapshot/revision context.
    • [ ] Anchor itself is not canonical entity identity.
    • [ ] Existing textual source anchors continue to work unchanged.
    • [ ] Protocol/client transport can carry bounded anchor descriptors needed by remote/web clients.
    • [ ] UI-specific pixel/screen positions are not persisted as semantic identity.

    Add generic test anchors equivalent to a cell/range and geometry/bounds without adding actual XLSX/GIS code in this task.

    11. Phase G — Implement Artifact-Level Staged Materialization¶

    Extend the current filesystem projection materialization owner rather than introducing a domain-private writer transaction.

    Implement state equivalent to:

    ArtifactMaterializationPlan
  artifact
  expected external baseline
  required output members
  optional output members
  staged bytes/digests

ArtifactMaterializationReceipt
  artifact
  per-member result/digest
  completion/recovery state
  new baseline identity

    Requirements:

    • [ ] All required output members are rendered before final replacement starts.
    • [ ] Candidate validators can inspect the complete staged set.
    • [ ] Expected external baseline/digest is checked before destructive replacement.
    • [ ] Single-file artifacts continue to use existing safe atomic path.
    • [ ] Multi-file artifacts stage all required members.
    • [ ] If platform-level all-member atomic replacement is unavailable, a recovery journal/receipt records exactly what happened.
    • [ ] Partial failure is never reported as success.
    • [ ] Self-write observation suppression/hash tracking is updated only for members actually committed.
    • [ ] Successful completion establishes one new exact artifact synchronization baseline.
    • [ ] Failed completion does not advance canonical project snapshot a second time or invent success state.
    • [ ] Recovery path is idempotent or detects already-completed members safely.

    Focused tests must inject failure after at least one staged/committed member.

    • [ ] failure leaves explicit recoverable/failed receipt;
    • [ ] success receipt contains every mandatory member;
    • [ ] external concurrent modification blocks replacement;
    • [ ] retry/recovery produces deterministic final state.

    Focused tests:
