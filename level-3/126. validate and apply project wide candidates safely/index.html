    Validate and Apply Project-Wide Candidates Safely¶

    Objective¶

    Complete the project-wide candidate path from task 125: materialize the exact aggregate candidate in isolation for validation, then apply an accepted candidate through exact-base canonical promotion and safe multi-file filesystem effects with truthful conflict/recovery state.

    Required successful path:

    P@S0
+ project-wide Candidate C1
-> isolated candidate workspace
-> focused/workspace/E2E validation bound to C1
-> normal review enables Apply
-> exact-base/preflight checks
-> canonical successor S1
-> safe create/update/delete effects
-> effect receipts/status
-> active workspace refreshes to P@S1

    Required invariant before user Apply:

    P.current == S0
live checkout == base checkout
candidate workspace may differ

    Read First¶

    Read:

    design/level-1/014. agent native semantic self hosting.md
design/level-2/027. project wide candidate workspaces validation and materialization.md
design/level-3/047. implement validation evidence and exact input binding.md
design/level-3/064. implement external effect receipts and reconciliation.md
design/level-3/080. implement filesystem projection ownership hashing and atomic io.md
design/level-3/083. implement filesystem observation synchronization and recovery.md
design/level-3/119. implement projection edit candidate review and validation.md
design/level-3/120. implement migration apply filesystem materialization refresh and conflict recovery.md
design/level-3/125. implement project wide source change candidates.md

    Reuse the exact-base/candidate validation/apply/effect semantics already proven for focused Rust edits. Do not invent a second repository checkout or transaction model unless the existing abstractions cannot be extended.

    Candidate Workspace Contract¶

    Provide a reusable way to materialize the exact source state represented by a project-wide candidate without changing the user's live checkout.

    Conceptually:

    CandidateWorkspace(C) = BaseProjectSource(C.base) + C.source_effects

    It must correctly implement:

    • create: candidate path exists with new bytes;
    • update: candidate path contains proposed bytes;
    • delete: candidate path is absent;
    • unaffected tracked/required files reflect the chosen exact base/source policy;
    • workspace root is isolated from the live project root;
    • build outputs/temp state remain outside canonical project knowledge.

    Prefer existing candidate materialization/staging helpers from task 119 and projection infrastructure.

    Exact Candidate Validation¶

    Every validator result must bind to stable candidate identity/content and exact base according to existing validation evidence rules.

    If candidate effects change, previous validation is stale and must not keep Apply enabled.

    Structured result includes at least:

    validation id
candidate id
base/candidate state identity
profile
status
bounded diagnostics
operation/process result category

    Do not decide success by UI strings or shell-output substring matching.

    Validation Profile Registry¶

    Add/reuse application-level validation profile registration/composition suitable for repository self-hosting.

    Profiles are policy identifiers such as:

    focused domain tests
project import tests
rust workspace quality checks
fresh-database ingestion E2E

    The TUI/provider requests a profile; application/validation infrastructure owns which commands/checks it entails.

    Do not encode raw shell pipelines in provider prompts or React/TUI widgets as canonical policy.

    Process Execution Boundary¶

    Repository validation commands execute through the existing bounded operation/process capability owner.

    Requirements:

    • cancellable/bounded according to current operation conventions;
    • working directory is the isolated candidate workspace;
    • environment is controlled/filtered according to validation policy;
    • stdout/stderr retained in bounded structured form/artifact references;
    • timeout/start failure are structured validation failures;
    • child processes are cleaned on cancellation;
    • no command runs in the live project root if it could rewrite source/lock/config as part of validation.

    If existing validation invokes cargo check directly in a safe abstraction, extend that abstraction rather than spawning Cargo from agent/TUI code.

    Dependency Acquisition Capability¶

    A project-wide candidate may add a new declared dependency.

    If validation cannot proceed from already available Cargo cache/vendor state, dependency acquisition must be explicit and bounded.

    Model it as validation/dependency-resolution capability, not generic agent internet access.

    Required evidence includes the resulting locked dependency state that becomes candidate source (Cargo.lock where applicable).

    Tests may prewarm/cache dependencies for deterministic CI, but must not fake parser functionality merely to avoid dependency resolution.

    No external model-provider network access is required for the deterministic golden suite.

    PHP Self-Hosting Validation Profiles¶

    The final golden scenario will request profiles equivalent to:

    php-domain-focused¶

    Run candidate's PHP adapter tests covering declarations, comments, nested syntax, inline HTML, malformed PHP, and deterministic parse structure.

    project-import-focused¶

    Run candidate's scanner/import/ownership/navigation/projection/regression tests for PHP.

    rust-workspace¶

    Run repository-standard compile/format/lint/test policy appropriate to affected Rust workspace.

    project-ingestion-e2e¶

    Against the candidate build/workspace, create a fresh Scriberig database and small PHP fixture project; use public scan/import/workspace/semantic operations and prove the new adapter composes.

    These are target profiles for the later test fixture. Keep the validation machinery generic.

    Fresh-Database E2E From Candidate Code¶

    The project-ingestion-e2e profile must test the candidate implementation, not the baseline executable that lacks PHP.

    Choose an architecture-consistent approach, for example:

    • build/run a candidate-workspace test/binary through Cargo;
    • run an integration test compiled from candidate source;
    • invoke a candidate-built srig/test harness when appropriate.

    The proof must establish:

    candidate PHP adapter is actually compiled
.php scan selects PHP
project import creates expected semantic PHP data
public find/inspect/render succeed

    A test that only reads the candidate source files and searches for the word php is insufficient.

    Validation Must Preserve Live Checkout¶

    Add an explicit test that snapshots live relevant files/directories before validation and verifies byte/existence equality afterward.

    For the self-hosting shape this includes proving candidate-only created crate files are still absent live before Apply.

    Build tooling that writes target/ or caches should be directed to candidate/temp locations so it does not pollute assertions or user checkout unnecessarily.

    Apply Preconditions¶

    Before accepted project-wide materialization, perform all feasible aggregate preflight checks.

    At minimum:

    candidate is validated/applicable
project current snapshot == candidate exact base
all relative paths are project-contained and authorized
update/delete expected source digests match live observed base state
create targets satisfy expected absence/conflict policy
ownership/projection identity matches where applicable
symlink escape rules pass

    Evaluate the full effect set before performing avoidable writes.

    If one path already conflicts, do not knowingly materialize unrelated paths and then report candidate success.

    Exact-Base Canonical Promotion¶

    Reuse existing migration/project compare-and-swap semantics.

    Do not silently rebase a project-wide candidate to a new current snapshot.

    A stale candidate may remain inspectable, but normal Apply rejects it until an explicit merge/rebase/reconciliation produces a newly reviewed candidate.

    The canonical transition records one migration/change linking base and successor.

    Multi-File Filesystem Effects¶

    Extend shared filesystem materialization to execute the accepted set of create/update/delete effects safely.

    For create/update, use existing atomic sibling/staging write + replace semantics where applicable.

    For delete, verify expected source state immediately before destructive effect according to existing ownership/digest policy.

    Do not let the agent/TUI execute std::fs::write, rm, or equivalent as the product Apply implementation.

    Aggregate and Per-Effect Receipts¶

    Application result must make external effect state inspectable.

    At aggregate level expose at least:

    candidate/migration id
base snapshot
successor snapshot if canonical promotion occurred
project id
overall materialization/effect state

    Per path/effect expose enough to distinguish:

    created/updated/deleted successfully
not attempted due to preflight conflict
failed during I/O
already satisfied/idempotent recovery
requires reconciliation

    Reuse/extend existing external effect receipt types.

    Do not collapse partial failure into a misleading single success boolean.

    Ordering and Partial Failure¶

    SQLite canonical state and multiple filesystem writes cannot be one physical transaction.

    Inspect and preserve the ordering architecture established by task 120/external-effect receipts.

    Extend it so recovery knows every intended source effect and its state.

    If canonical promotion succeeds and effect N fails after some effects succeeded, persist durable recovery evidence sufficient to:

    • tell the product canonical and filesystem states differ;
    • identify completed/incomplete paths;
    • retry safely/idempotently where allowed;
    • avoid rewriting externally changed paths during recovery;
    • avoid claiming full materialization success.

    Create Conflict Rule¶

    If a candidate proposes creating a path that was absent at base, but an external actor creates that live path before Apply, default behavior is conflict.

    Do not silently overwrite the externally created file with candidate content.

    A future explicit reconcile/merge can decide how to combine it.

    Update/Delete Conflict Rule¶

    If live digest/content for an update/delete target no longer matches the candidate's expected base, reject unsafe materialization for that candidate.

    Preserve the external bytes.

    The UI/result should identify the specific path and expected/observed state in bounded form.

    TUI Validation and Apply¶

    Extend/reuse normal change review from task 125.

    Required behavior:

    1. candidate review shows required validation profiles/progress;
    2. Apply disabled until required policy succeeds;
    3. validation can be started/observed through public application operation;
    4. user can inspect bounded diagnostics;
    5. before Apply, live tree remains base;
    6. Apply invokes shared application operation;
    7. terminal state distinguishes canonical/materialization outcome;
    8. on full success, TUI refreshes authoritative project workspace;
    9. on conflict/effect failure, persistent inspectable state remains available.

    No optimistic local snapshot switching before authoritative result.

    Post-Apply Refresh and History¶

    On successful full path:

    P.current = S1
S1 != S0

    The TUI/client refreshes project workspace from the application.

    History/diff remains able to render base and successor source states and list the complete accepted project-wide change.

    Candidate/session provenance remains linked.

    Multi-Project Isolation¶

    With projects A and B in one database, a project-wide candidate for A:

    • validates/materializes A workspace/path only;
    • advances only A current root;
    • writes only A owned/authorized checkout;
    • cannot use relative-path collisions to modify B;
    • emits project-scoped events so B clients do not adopt A state.

    Add conformance coverage.

    Required Focused Tests¶

    PROJECT-WORKSPACE-VALIDATE-01¶

    Candidate creates a small crate and updates workspace metadata. Validator compiles/checks the aggregate candidate successfully only because created files and manifest update coexist in isolated workspace.

    PROJECT-WORKSPACE-VALIDATE-02¶

    Snapshot live tree before/after validation. Assert exact equality for intended source paths and absence of candidate-created paths.

    PROJECT-WORKSPACE-VALIDATE-03¶

    Modify candidate after validation or create superseding candidate. Assert old validation cannot enable Apply for changed candidate.

    PROJECT-APPLY-01¶

    Apply validated create+update candidate. Assert canonical successor and intended live files only after acceptance.

    PROJECT-APPLY-DELETE-01¶

    Apply validated delete effect and verify historical/base source remains renderable while live target is removed only after acceptance.

    PROJECT-APPLY-STALE-01¶

    Advance project snapshot after candidate creation. Assert exact-base rejection and no candidate source effects.

    PROJECT-CONFLICT-UPDATE-01¶

    Externally modify one update target before Apply. Assert external content survives and full-success is not reported.

    PROJECT-CONFLICT-CREATE-01¶

    Externally create candidate's proposed new path. Assert no overwrite and explicit conflict.

    PROJECT-EFFECT-FAIL-01¶

    Inject deterministic I/O failure in middle of multiple effects. Assert durable per-path receipt/recovery status and truthful aggregate result.

    PROJECT-RECOVERY-01¶

    Retry/reconcile deterministic incomplete effect according to existing recovery architecture; assert already-completed effects are handled idempotently and unrelated files untouched.

    MULTIPROJECT-PROJECT-APPLY-01¶

    Apply candidate to A; assert B semantic root/files unchanged.

    TUI-PROJECT-APPLY-01¶

    Real PTY: open multi-file candidate, run/observe validation, assert live base, invoke Apply, verify explicit success, refreshed snapshot, and resulting files.

    TUI-PROJECT-CONFLICT-01¶

    Real PTY: external edit/create conflict before Apply, assert visible conflict and external bytes survive.

    Required Verification¶

    Run focused project-wide validation/apply/effect tests, existing single-file candidate/apply regression suites, protocol/client conformance, native PTY Apply/conflict tests, and multi-project isolation.

    Then repository-standard quality gates including at least:

    cargo check --workspace --all-targets

    Completion Checklist¶

    • [x] Create/update/delete effects are reflected correctly in candidate workspace.
    • [x] Validators execute against candidate workspace, never live source checkout.
    • [x] Validation evidence binds to exact aggregate candidate content.
    • [x] Changed candidate cannot reuse stale validation evidence.
    • [x] Validation profiles are application policy, not UI/provider shell strings.
    • [x] Process execution is bounded/cancellable and diagnostics structured.
    • [x] Dependency acquisition, when needed, is explicit and bounded.
    • [x] PHP-target validation profiles can be expressed without PHP being preinstalled in baseline.
    • [x] Fresh-database ingestion E2E can execute candidate code/build.
    • [x] Apply performs full feasible preflight before unsafe multi-file writes.
    • [x] Apply uses exact project base compare-and-swap.
    • [x] Create conflicts never silently overwrite external files.
    • [x] Update/delete digest conflicts preserve external content.
    • [x] Shared filesystem infrastructure owns all live source effects.
    • [x] Aggregate and per-path effect receipts are durable/inspectable.
    • [x] Partial I/O failure is never presented as full materialization success.
    • [x] Recovery is bounded/idempotent according to existing effect architecture.
    • [x] TUI validation/review/apply uses public shared operations.
    • [x] Successful Apply refreshes authoritative P@S1 and history.
    • [x] Multi-project isolation is proven.
    • [x] PROJECT-WORKSPACE-VALIDATE-01 through -03 pass.
