    Implement Provider Continuation, Full Effective Prompt, and Observable Reasoning¶

    Status: [ ] In Progress

    1. Objective¶

    Implement the provider-continuation and model-observability contract defined by:

    • design/level-1/020. provider continuation state and observable model execution.md;
    • design/level-2/025. provider continuation and observable model execution.md.

    This task is a mandatory refinement of tasks 133, 134, and 135 where those tasks discuss prompt visibility, reasoning visibility, provider execution, model activity, or branch execution.

    The final implementation must prove all of these properties together:

    1. Scriberig session/branch identities remain canonical and provider-neutral;
    2. provider-native conversation/session/response handles are opaque branch-local runtime state;
    3. sibling/child branches never share provider continuation accidentally;
    4. compatible same-branch invocations may reuse provider continuation;
    5. provider/profile/context divergence causes deterministic reseed/fork rather than blind continuation;
    6. provider continuation loss never makes the Scriberig session unrecoverable;
    7. every inspectable model invocation retains or references the complete safe effective Scriberig request used for that invocation;
    8. Full prompt display shows that effective request even when the provider wire request only sent a continuation ID plus new input;
    9. provider-visible reasoning may be represented before, between, and after semantic/tool operations in deterministic order;
    10. prompt visibility and reasoning visibility are independently selectable;
    11. changing either presentation setting performs no model/tool execution;
    12. hidden/private chain-of-thought is never requested, persisted as visible trace, or exposed;
    13. embedded, remote, TUI, and web surfaces consume the same application/protocol semantics.

    Follow this task in order. Do not begin by adding TUI toggles. Runtime/session/application contracts come first.

    4. Phase A — Define Provider-Neutral Continuation Types¶

    Owner: scriberig-agent-runtime unless the repository already has an equivalent provider-neutral runtime crate/type.

    Implement the minimum provider-neutral types needed to express:

    provider/profile identity
branch identity
continuation strategy
opaque provider handle
context/lineage fingerprint
status
created/last-used invocation references
safe non-secret provider metadata

    Requirements:

    • [ ] Provider continuation type does not reuse SessionId, BranchId, or any semantic entity ID as the provider handle.
    • [ ] Provider handle is opaque outside provider/runtime implementation.
    • [ ] Strategy can distinguish OpenAI Conversation-style state from previous-response-style chaining and future provider-specific/local sessions.
    • [ ] Status can distinguish reusable/stale/unavailable/expired-or-equivalent states.
    • [ ] No credentials are fields in continuation records.
    • [ ] No hidden/private reasoning is stored in continuation records.
    • [ ] Type documentation follows repository declaration-documentation rules.

    Focused tests:

    • [ ] serialize/deserialize safe continuation metadata if durability requires serialization;
    • [ ] prove secret sentinel values are absent from debug/public projection;
    • [ ] prove two branches can carry distinct opaque handles for the same provider profile.

    Do not implement OpenAI HTTP behavior yet.

    5. Phase B — Add Continuation Storage/Lookup Boundary¶

    Implement an explicit runtime/session persistence boundary rather than passing continuation handles ad hoc through provider call sites.

    Required operations are conceptually:

    load(branch, provider/profile)
store/update(successor state)
mark_stale
mark_unavailable
list safe provenance when needed

    Requirements:

    • [ ] Storage lookup is keyed by canonical Scriberig branch plus resolved provider/profile identity.
    • [ ] Old provider state can remain historical after provider switch without becoming current automatically.
    • [ ] TUI/web cannot directly mutate opaque provider continuation handles.
    • [ ] Restart can recover whatever continuation metadata is intentionally durable.
    • [ ] Absence/unavailability is a normal state, not corruption.

    Focused tests:

    • [ ] continuation survives configured durable round trip if persistence is intended;
    • [ ] missing continuation produces normal None/unavailable semantics;
    • [ ] provider A state is not returned for provider B;
    • [ ] branch A state is not returned for branch B.

    6. Phase C — Formalize Context Lineage Compatibility¶

    Extend current context fingerprinting rather than adding a second unrelated hash system.

    Implement a deterministic decision that can answer:

    Can provider continuation P represent the exact expected provider-visible predecessor context for invocation I?

    Inputs should include as needed:

    compiled context fingerprint
prior invocation/request fingerprint
resolved provider/profile/model
continuation strategy
branch identity

    Requirements:

    • [ ] Fingerprint inputs contain no credentials.
    • [ ] Fingerprint is deterministic across equivalent reconstruction.
    • [ ] Same branch + unchanged compatible lineage is reusable.
    • [ ] Sibling branch is never reusable merely because text happens to match.
    • [ ] Provider/profile switch is not reusable by default.
    • [ ] An intervening canonical branch turn not represented by old provider state makes old state stale unless context compiler explicitly excludes it and fingerprint equivalence proves compatibility.
    • [ ] Historical continuation/fork semantics use exact anchors/lineage rather than current-head assumptions.

    Focused tests:

    • [ ] same lineage -> reusable;
    • [ ] changed dependency result -> stale;
    • [ ] changed selected ancestor result -> stale;
    • [ ] sibling branch -> not reusable;
    • [ ] provider switch -> not reusable;
    • [ ] reconstructing identical canonical context after restart yields same fingerprint/compatibility decision.

    7. Phase D — Introduce Complete Safe Canonical Model Request¶

    Do not remove the existing bounded request projection if it serves ordinary activity rendering.

    Add or extend a complete safe provider-neutral request record used for durable/on-demand inspection.

    It must be able to represent:

    invocation identity
session/branch/continuation anchor
context fingerprint
instruction sections
ordered messages/context sections
selected ancestor results
fulfilled dependency results
semantic context/projections
tool/semantic capability definitions
structured-output request when present
resolved model/provider/profile/thinking configuration
provider continuation strategy/reference
safe generation configuration
optional token estimate
explicit redaction records

    Requirements:

    • [ ] The record is created after context compilation and before provider serialization.
    • [ ] It represents effective Scriberig context, not raw provider HTTP JSON.
    • [ ] It contains no API key/header/secret values.
    • [ ] Sensitive capability parameters are redacted according to existing security policy.
    • [ ] Redactions remain structurally visible rather than silently deleting context.
    • [ ] The complete record can be retrieved later without model re-execution.
    • [ ] Bounded activity projection references the complete record or invocation identity.

    Focused tests:

    • [ ] all compiled safe context sections appear in complete request;
    • [ ] long request remains complete in full-detail storage while bounded projection reports truncation;
    • [ ] secret sentinel values absent;
    • [ ] dependency/ancestor result references are included when context compiler selected them;
    • [ ] excluded sibling transcript does not appear.

    8. Phase E — Make Provider Serialization Consume Canonical Request¶

    Refactor request construction so provider adapters serialize from the canonical provider-neutral request or an exact derived runtime structure rather than independently rebuilding context.

    Requirements:

    • [ ] There is one authoritative compiled request before provider-specific mapping.
    • [ ] OpenAI adapter does not have a hidden second context compiler.
    • [ ] Provider-specific omissions caused by continuation optimization happen after canonical request capture.
    • [ ] Request fingerprint/provenance refers to canonical effective request.

    Focused tests:

    • [ ] stateless fake provider sees exact canonical request mapping;
    • [ ] provider serializer can omit repeated wire context without altering stored effective request;
    • [ ] equivalent canonical requests produce expected fingerprint behavior.

    9. Phase F — Implement Continuation Reuse/Reseed Decision¶

    Before invoking a provider:

    1. resolve branch model/provider/profile assignment;
    2. compile canonical effective request;
    3. compute context lineage identity;
    4. load candidate provider continuation;
    5. ask provider capability/strategy whether state can be reused/forked;
    6. reuse only when lineage compatibility passes;
    7. otherwise mark stale/reseed or run stateless;
    8. after successful provider execution, persist successor provider state bound to the completed invocation.

    Requirements:

    • [ ] Decision is explicit/testable and not scattered through request fields.
    • [ ] Provider continuation failure can fall back to canonical context when policy permits.
    • [ ] Failed provider continuation does not mutate canonical Scriberig session identity.
    • [ ] Cancellation does not incorrectly promote a half-established successor state.

    Focused fake-provider tests:

    • [ ] first invocation initializes state;
    • [ ] second compatible same-branch invocation reuses it;
    • [ ] incompatible branch context reseeds;
    • [ ] provider-state error falls back or fails structurally according to policy;
    • [ ] cancelled invocation does not become reusable successor.

    10. Phase G — Implement OpenAI Conversation Strategy¶

    Use the OpenAI Responses/Conversations capability only behind the provider adapter.

    Requirements:

    • [ ] Provider capability declares Conversation support separately from generic OpenAI compatibility.
    • [ ] A new isolated Scriberig branch receives a new OpenAI Conversation when this strategy is selected.
    • [ ] Conversation initialization reflects the branch's compiled selected context.
    • [ ] Same-branch compatible continuation reuses the branch Conversation.
    • [ ] Child/sibling branch never reuses the parent/sibling Conversation implicitly.
    • [ ] Conversation ID is retained only as opaque provider runtime/provenance state.
    • [ ] OpenAI Conversation ID is never exposed as canonical Scriberig session identity.

    Tests must use an HTTP fake/mock adapter boundary; do not require live OpenAI credentials.

    • [ ] assert create-conversation request for first branch invocation;
    • [ ] assert reuse on compatible continuation;
    • [ ] assert separate conversations for siblings;
    • [ ] assert reseed/new conversation after incompatible provider switch/context divergence.

    11. Phase H — Implement OpenAI previous_response_id Strategy¶

    Support previous-response chaining/forking only as a separate explicit strategy.

    Requirements:

    • [ ] Strategy is mutually exclusive with Conversation strategy on one request.
    • [ ] Stable/top-level Scriberig instructions required for the new invocation are resent rather than assumed inherited.
    • [ ] Previous response is reused only when exact lineage compatibility passes.
    • [ ] Historical fork uses the response corresponding to the exact anchor when retained and valid; otherwise recompile/reseed from canonical Scriberig state.
    • [ ] Provider response IDs are opaque safe provenance, not branch IDs.

    Focused tests:

    • [ ] request with previous response contains required instructions;
    • [ ] request never contains both provider continuation mechanisms;
    • [ ] exact fork chooses correct predecessor;
    • [ ] unavailable predecessor falls back to canonical context.
