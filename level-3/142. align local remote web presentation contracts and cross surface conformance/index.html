    Align Local/Remote/Web Presentation Contracts and Cross-Surface Conformance¶

    Status: [x] Complete

    1. Objective¶

    After the TUI presentation migration is functionally complete, verify and close any shared-contract gaps exposed by the migration so embedded TUI, remote TUI, API clients, and the integrated web application continue to consume the same Scriberig semantics.

    This task is the implementation refinement of the multi-surface part of design/level-1/022. Adopt TUI.md.

    It must not create a second UI backend merely to match the research report's illustrative ScriberigUiPort, UiSnapshot, HTTP/SSE, or React examples.

    The controlling rule is:

    Extend current shared application/protocol/client/presentation owners only where conformance evidence proves a missing contract.

    Do not begin task 143 until this sheet is complete.

    2.3 Architectural prohibitions¶

    Do not:

    • create scriberig-ui merely because the Level-1 report sketched it;
    • add a new UI-only session store;
    • add a new UI-only plan store;
    • compile model context in protocol/TUI/web layers;
    • let the web app reconstruct semantic truth from display strings;
    • let the TUI reconstruct semantic truth from protocol row order;
    • create a second command/event protocol if current scriberig-protocol can be extended;
    • replay state-changing commands on reconnect without application-level idempotency guarantees;
    • make event cursor/sequence numbers semantic entity identity;
    • expose provider credentials or hidden reasoning through presentation APIs.

    Current implementation note¶

    The audited owners in this checkout are:

    Concern Current owner
    Recursive durable session, branch, activity, plan and dependency state scriberig-session (Session, branch/activity, plan types)
    Safe model library and shared presentation preferences scriberig-app::agent_console; wire values in scriberig-protocol
    Local application operations and operation lifecycle scriberig-app::ApplicationService and OperationRegistry
    Session/plan wire serialization scriberig-protocol::session
    Remote calls, event cursor and cursor-expiry refresh scriberig-client and scriberig-tui::RemoteAdapter
    Local TUI session projection scriberig-tui service adapter and session/conversation models
    Browser wire normalization web/packages/client/src/session-views.ts
    Browser durable/transient state and event reduction web/packages/model/src/agent-workspace.ts and agent-workspace/events.ts
    Reusable agent rendering web/packages/agent-ui; integrated composition

    The protocol already carried plan revision, goal, status, anchor, coordinator claim, plan history, node expected result/scope/claim/supersession and branch result handles. The TypeScript contract/normalizer dropped those fields, and the browser workspace did not retain plans. This task extends those existing owners. A single JSON fixture under tests/fixtures/ is now consumed by Rust protocol and TypeScript client tests. Event sequences are transport cursors; Rust remote recovery already refreshes known sessions after CursorTooOld, and the browser reducer now marks its state stale when an established cursor skips a sequence. Rust and TypeScript clients do not automatically retry state-changing requests. Remote TUI reconnect only issues event subscriptions and authoritative session reads; a continuation is submitted only by an explicit user/application command. The protocol has no durable key for a caller that manually retries after an ambiguous command timeout, so this guarantee covers reconnect and automatic retry behavior only.

    State-changing requests are not automatically retried by the Rust/TypeScript clients. Plan lifecycle/assignment/replan operations use the plan revision compare-and-swap contract; candidate promotion uses the expected base snapshot. The reconnect regression test records every remote request and asserts that recovery performs only Subscribe requests. A caller manually resubmitting after an ambiguous timeout remains a separate invocation and is not deduplicated by a durable command key.

    The local/remote operation conformance test now compares completed operation records containing candidate and validation evidence through both TUI service adapters. It exposed that terminal transitions synthesized an empty local progress record, which the remote mapping did not report. The shared app lifecycle now preserves absent progress; its regression test verifies that a terminal status does not fabricate progress data.

    6. Task C — Audit Event Ordering, Replay, and Reconnect¶

    Determine the current protocol guarantees for ordered activity/event delivery and reconnect.

    If the existing system already exposes exact durable session/activity sequence data sufficient for deterministic reconstruction, reuse it.

    If a transport cursor is missing and reconnect currently risks gaps/duplicates, add the smallest shared protocol/application capability needed.

    A transport cursor/sequence:

    • is not a session/branch/activity semantic identity;
    • may be retained by clients for replay position;
    • must detect gaps/too-old replay conditions;
    • may require authoritative state refresh when replay cannot continue.

    Acceptance:

    • [x] Remote reconnect can reconstruct/refresh current presentation state without provider stream replay.
    • [x] Duplicate delivered observations do not duplicate durable semantic activity.
    • [x] Missing replay range triggers explicit refresh/resync behavior.
    • [x] Transport cursor is not used as reply anchor or plan-node identity.
    • [x] Reconnect does not silently execute a model/tool/application command.
