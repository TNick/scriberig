# Implement: Markdown Node Matching and Semantic Reconciliation

## Objective

Implement deterministic Markdown node matching and reconciliation in `sr-markdown` so an edited Markdown candidate can be mapped back onto existing canonical entities without hidden IDs and converted into a semantic migration proposal.

This task handles the common single-base case where the current canonical state still equals the synchronization base. Three-way concurrent reconciliation is the next task.

## Preconditions

The reconciler receives:

- exact synchronization-base snapshot/semantic scope;
- current canonical state, which for this task must equal the base for the target scope;
- parsed `CandidateDocument`;
- projection specification and Markdown adapter configuration.

If current canonical state differs from base, return/route to an explicit three-way-required result rather than pretending this task resolved concurrency.

## Matching phases

Implement deterministic matching in passes. Keep evidence/results inspectable for diagnostics.

Recommended order:

1. exact subtree/content equality within corresponding structural context;
2. exact same-kind content match;
3. heading/section name plus parent-context match;
4. ordered sibling sequence alignment using already matched anchors;
5. neighboring unchanged anchors;
6. conservative same-kind text similarity only where one best candidate is clearly distinguishable.

Do not use one global fuzzy match across the whole document.

Prefer local structural context.

## Match result model

For each candidate semantic node, represent at least:

```text
Matched(existing EntityId, evidence)
New
Ambiguous(possible matches, evidence)
```

Also track canonical entities in the projected semantic surface that were not matched, so removals/structural changes can be proposed deliberately.

Do not mark a canonical entity deleted merely because the Markdown projection does not represent unrelated relations/metadata.

## Duplicate-content safety

Explicitly test duplicate paragraphs/list items.

If two canonical candidates remain equally plausible after structural context and anchors, produce `Ambiguous`.

Do not choose the first by hash-map iteration or source position alone.

Stable identity correctness is more important than reducing the number of new entities.

## Content update semantics

When a candidate matches an existing entity but projected canonical properties changed:

- keep the same `EntityId`;
- create/propose a new immutable revision containing only the semantic dimensions owned by Markdown;
- preserve canonical fields/relations outside the projection surface;
- record an entity delta/operation through `sr-change`.

A line/column change alone must never create a new revision.

## Insert semantics

For an unmatched candidate that clearly belongs in a projected collection:

- create a new semantic entity through the normal graph/change construction APIs;
- create its initial revision;
- update the parent collection structure;
- do not recreate unchanged siblings.

## Remove semantics

If an existing projected child is absent from the candidate and the Markdown projection owns that child collection, propose removal from that collection.

Do not automatically delete the entity globally if it may still be referenced elsewhere; follow the universal graph/change semantics for entity removal versus relation/collection removal.

## Reorder/move semantics

If the same child entities are present but order changes, propose a collection-order/structure change rather than delete-and-recreate.

If a block moves between sections and identity continuity is justified, preserve the block entity and update collection membership/structure.

Do not let projected line numbers define a move.

## Formatting-only no-op

Call semantic equivalence before producing revisions/migrations where possible.

If candidate semantics equal canonical projected semantics:

```text
ReconciliationOutcome::NoSemanticChange
```

No migration/entity revision should be created.

## Migration proposal

Use `sr-change` rather than implementing a separate migration type.

The proposal should identify:

- base snapshot;
- affected entity deltas;
- generic collection/relation operations where available;
- provenance source as external projection;
- projection reference/path as structured provenance metadata;
- domain-specific Markdown operation details only through supported extension mechanisms.

Do not promote/commit the migration inside the pure reconciler.

## Preserving unrepresented knowledge

When replacing a paragraph revision due to changed text, retain all canonical fields/relations that Markdown does not own.

Add a test where a paragraph has an extra provenance/citation/custom relation not represented in Markdown; editing text must not remove that relation.

## Ambiguity diagnostics

Return structured Markdown reconciliation diagnostics containing:

- candidate local node/path;
- node kind;
- possible existing `EntityId` matches;
- evidence/scores/categories used;
- containing section/collection;
- suggested safe action if known.

Do not expose only a string.

## Tests

Cover at least:

- edit one paragraph: same entity, new revision;
- insert paragraph between two unchanged paragraphs: neighbors reused, one new entity, parent structure changes;
- remove paragraph from projected section without deleting unrelated knowledge;
- reorder paragraphs: identities retained, collection order changes;
- move a paragraph between sections when anchors make identity clear;
- formatting-only input returns no semantic migration;
- exact duplicate paragraphs with insufficient context return ambiguity;
- changed heading keeps section identity when evidence is sufficient;
- inserting a heading creates new section entity;
- unrelated canonical relations survive projected text edit;
- parser source spans never enter migration identity.

## Do not do

- Do not perform three-way merge when current differs from base.
- Do not commit/promote migrations.
- Do not resolve ambiguity with an LLM.
- Do not use hidden IDs inserted into Markdown.
- Do not rebuild the whole canonical document from the candidate.
- Do not discard relations not represented in Markdown.
