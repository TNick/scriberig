# Expose Trust State Through Protocol and Events

## Objective

Expose trust-relevant application results through the shared Rust/wire protocol so server, remote clients, web libraries, TUI, CLI adapters, and agent tooling can observe the same semantics.

This task is transport representation only. It must not reimplement authorization, validation, promotion, or external-effect logic inside the protocol/server.

## Expected Area

Typical files/modules:

```text
crates/scriberig-protocol/src/trust.rs
crates/scriberig-protocol/src/event.rs
crates/scriberig-protocol/src/lib.rs
crates/scriberig-server/... application-to-protocol adapters
web/packages/protocol/... generated/shared representations if that path already exists
```

Follow the repository's established schema generation approach. Do not maintain unrelated Rust and TypeScript wire models manually if generation already exists.

## Protocol Types

Expose serializable representations for at least:

```text
CapabilityDenied
TrustSummary / provenance summary
ValidationSummary
ValidationDiagnostic
PolicyEvaluationSummary
ApprovalSummary
PromotionResult
ConflictSummary
ExternalEffectSummary / ReceiptSummary
```

Use stable IDs/references to inspect full underlying knowledge objects rather than embedding entire graphs into every response.

A compact trust summary should be able to say things equivalent to:

```text
source kind
current validation state
last accepted migration/promotion
whether generated vs authored/observed
links/handles for deeper provenance
```

Do not invent one global trust score.

## Events

Add event variants for at least:

```text
CandidateCreated
ValidationStarted
ValidationCompleted
ApprovalRecorded
ConflictDetected
CapabilityDenied
ExternalEffectUpdated
SnapshotPromoted
```

Events must carry operation/candidate/snapshot handles sufficient for a client to fetch current details.

Do not duplicate full validation output into every event when a result object can be referenced.

## Server Adapter

Map application results/errors to protocol types. The server must not reinterpret policy or retry denied operations with broader authority.

A capability denial must remain a denial, not become a generic 500/error string.

A stale/conflict promotion result must remain distinguishable from validation failure.

## TypeScript Parity

If the TypeScript protocol package exists, update the generated/shared type surface and add compile-time tests/examples proving the trust/event variants are available to web clients.

## Tests

Test:

1. structured capability denial round-trip;
2. validation result with diagnostics round-trip;
3. promotion allowed/rejected/stale states remain distinct;
4. conflict summary contains resolvable handles;
5. external-effect unknown state survives serialization;
6. events reference exact candidate/snapshot/operation IDs;
7. no secret/credential field exists in trust protocol objects;
8. Rust and TypeScript protocol representations stay in sync using the repository's normal conformance test.

## Validation

Run Rust workspace checks and web/type generation checks already defined by the repository.

## Do Not

Do not add server-only business rules. Do not flatten all trust state into strings. Do not leak restricted payloads inside denials/events. Do not expose reusable credentials.

## Completion Checklist

- [ ] trust outcomes have stable protocol representations;
- [ ] denial/validation/conflict/promotion states remain distinct;
- [ ] trust events use the common event model;
- [ ] server is an adapter, not policy owner;
- [ ] TypeScript consumers receive the same contract;
- [ ] no sensitive material is serialized.
