# Implement Reverse Dependency Invalidation and Explanations

## Objective

Implement the reusable mechanics that determine which derived results are affected by semantic change and explain why a cached result can or cannot be reused.

This task must use declared dependencies. It must not invalidate everything merely because the global snapshot changed.

It also must not eagerly delete historical artifacts simply because they are not valid for a newer state.

Do not implement domain-specific analyzers, background scheduling, protocol transport, agents, or a durable backend in this task.

## 1. Change Input Model

Define `InvalidationSet`, `ChangeSet`, or an equivalent domain-neutral input type describing semantic changes relevant to derived dependencies.

It must support at least conceptual changes for:

```text
entity revision changed
snapshot changed
scope/collection revision changed
configuration identity changed
derived-result dependency changed
```

Do not encode file timestamps or line ranges as universal invalidation inputs.

Domain adapters may later translate a semantic migration into this universal change set.

The input model should make old and new exact identities available where useful for explanation.

Example:

```text
ExactRevisionChanged {
    entity: Type T,
    from: R5,
    to: R6,
}
```

---

## 2. Affected Result Lookup

Implement a service/function that uses reverse dependency lookup to find derived result records potentially affected by the change set.

The outcome should separate:

```text
Affected
Unaffected / not returned
```

A result is affected when one of its declared dependencies no longer matches the requested semantic state.

Do not automatically classify all results created under an older global snapshot as affected.

Snapshot-dependent results are affected only when they explicitly declared the relevant snapshot dependency.

---

## 3. Scope and Absence Dependencies

Add tests proving that scope dependencies work even when positive result members are unchanged.

Example:

```text
query: all callers of F
old result: [G, H]
```

A new function `J` is added and now calls `F`.

Neither `G` nor `H` changed.

The cached result must still be considered affected because its completeness dependency on caller scope changed.

Do not implement source-code caller analysis in this task. Model the scenario with generic test dependency identities.

---

## 4. Historical Artifacts Remain Valid for Old Inputs

Invalidation for new state must not mutate the old result record into an invalid object.

The historical statement remains:

```text
result D was produced for DerivationKey K
```

The new request simply has a different key/dependency state.

Therefore invalidation should conceptually produce:

```text
result D does not satisfy new state
```

not:

```text
rewrite D as invalid
```

A backend may maintain disposable invalidation/index metadata, but immutable result content must remain unchanged.

---

## 5. Reuse Explanation Model

In `explain.rs`, define structured explanation types with stable machine-readable reason codes.

Support at least equivalents of:

```text
ExactKeyMatch
NoStoredResult
ProfileMismatch
RevisionChanged
SnapshotChanged
ScopeChanged
ConfigurationChanged
DerivedDependencyChanged
FreshnessExpired
StatusNotReusable
SelectionRejected
```

Reuse freshness/selection outcomes from task `003` rather than redefining them.

Every explanation should be capable of carrying relevant exact IDs in structured fields when available.

Do not make callers parse prose to discover which dependency changed.

---

## 6. Reuse Decision

Implement a pure or mostly pure evaluation path that can answer conceptually:

```text
Can this stored result satisfy this requested DerivationKey/policy?
```

Possible outcomes should include:

```text
Reuse(result, explanation)
Miss(explanation)
Recompute(explanation)
```

If `Miss` and `Recompute` are semantically the same at this layer, use one type plus a reason that higher scheduling layers can interpret. Do not invent fake distinctions just to match names in the design.

The important behavior is structured explainability.

---

## 7. Invalidation Propagation Through Derived Dependencies

Support derived-result dependencies transitively.

Example:

```text
Function F@R1 -> Summary SF
Summary SF + Summary SG -> ModuleSummary M1
```

If `F@R1` changes to `F@R2`:

1. `SF` is affected for the new function state;
2. results depending on `SF`, such as `M1`, are also affected for any derivation request expecting a summary built from the changed function state.

Implement cycle protection even if derivation graphs are expected to be acyclic in normal operation.

Use visited-result tracking during traversal.

Do not crash or loop forever if malformed metadata contains a dependency cycle.

---

## 8. Conservative Dependencies Are Correct

Add tests demonstrating that a derivation may depend on an entire snapshot.

When that snapshot changes, the result is affected even if the particular leaf objects it inspected did not.

This is conservative invalidation and is valid.

The invalidation engine must not attempt to second-guess declared dependencies by inspecting result payloads.

Dependency precision belongs to the producer/adapter.

---

## 9. Formatting vs Semantic Change

Add a generic test proving this intended pattern:

```text
semantic summary depends on FunctionRevision F@R7
rendering depends on F@R7 + Style ST1
```

When only style changes:

```text
ST1 -> ST2
```

then:

- rendering for the old style does not satisfy the new render request;
- semantic summary remains reusable.

Do not require a Rust renderer for this test.

Use generic dependency identities.

---

## 10. Public API

Expose equivalents of:

```text
InvalidationSet
SemanticChange
AffectedResult
ReuseDecision
ReuseExplanation
ReuseReasonCode
```

Keep APIs small and domain-neutral.

Documentation must state that invalidation is based on declared semantic dependencies rather than file timestamps.

---

## Required Tests

Add tests for:

1. exact revision change affects a dependent result;
2. unrelated revision change does not affect a local result;
3. explicit snapshot dependency is affected by snapshot change;
4. local result without snapshot dependency survives unrelated snapshot change;
5. scope dependency invalidates a completeness result when membership changes;
6. configuration/style change affects only results that declared it;
7. derived-result dependency propagates invalidation transitively;
8. cycle protection terminates safely;
9. old result record remains immutable after invalidation analysis;
10. explanation includes exact changed dependency IDs;
11. no stored result returns a structured miss reason;
12. stale freshness result integrates with explanation without duplicating freshness logic;
13. failed status integrates with explanation without parsing error strings.

## Do Not

Do not:

- invalidate all results on every snapshot change;
- inspect source files to infer dependencies;
- mutate old result records;
- delete results automatically during invalidation;
- recompute derivations;
- add a task scheduler;
- add domain-specific dependency variants;
- add agent/server/UI code.
