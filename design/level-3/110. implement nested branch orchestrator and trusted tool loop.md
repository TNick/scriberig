## Runtime Entry Point

Expose a runtime service conceptually equivalent to:

```text
start_branch_execution(request, execution_context) -> operation/handle
```

The exact application-facing wrapper is added in the next protocol task, but the runtime API must already accept:

```text
session
branch
prompt/current user input
agent profile
semantic selection/base snapshot
capability scope
retention policy
limits/cancellation
```

The runtime assumes the branch exists before the first provider request.

## Core Loop

Implement the loop:

```text
compile context
-> compute request fingerprint
-> apply cache policy
-> invoke provider or reuse cache
-> persist complete ModelInvocation/ModelOutput semantics
-> interpret normalized model result
-> if final output: complete branch
-> if tool calls: validate/dispatch tools
-> append tool/child results
-> repeat
```

No provider-specific DTO should appear in branch orchestration code.

---

## Trusted Tool Catalog

Build the model-visible catalog only from registered trusted Scriberig tool descriptors.

Each descriptor must expose:

```text
stable id
description
argument schema
result shape summary
read-only/state-changing classification
execution mode: atomic or child branch
required capability/domain applicability
```

The runtime validates returned tool names and arguments against this catalog.

Unknown tool ids never become arbitrary function dispatch.

---

## Atomic Tool Execution

Atomic tools execute within the current branch when they do not require an independent reasoning loop.

Required behavior:

1. create/record `ToolInvocation`;
2. validate capability and arguments;
3. invoke the public application/session operation;
4. create/record `ToolResult`;
5. project a bounded result back into the next model context;
6. preserve semantic result handles.

Use public app APIs rather than storage internals.

For state-changing operations, the returned result must still follow shared migration/validation semantics.

---

## Child-Branch Tool Execution

For tools classified as child-branch operations:

1. derive child purpose from trusted descriptor plus validated arguments;
2. resolve explicit parent-to-child context inheritance;
3. derive capability subset;
4. resolve base snapshot/workspace/selection;
5. create the child branch in `scriberig-session` before provider execution;
6. recursively invoke the same branch orchestrator;
7. wait/observe according to tool semantics;
8. obtain durable `BranchResult`;
9. return only a compact child-result projection to the parent loop by default.

The parent model context must not automatically absorb child model/tool history.

---

## Recursive Limits

Enforce at least:

```text
max model steps per branch
max branch depth
max child branch count
max tool calls
max total active branches
max provider request duration
optional total operation duration
```

Budget exhaustion becomes a structured terminal result and session provenance.

No recursion path may panic or overflow the process stack because the model repeatedly delegates.

An iterative scheduler is acceptable/preferred when useful, but semantic nesting must remain explicit.

---

## Parallelism

Initial correctness is more important than broad parallelism.

The runtime may execute independent read-only atomic tools concurrently when:

- provider requested them together;
- their tool descriptors allow it;
- application semantics say they are independent;
- result ordering is reconstructed deterministically.

Serialize by default:

```text
state-changing tools
child branches sharing mutable workspace state
tools with declared ordering dependencies
```

Parallel child branches are allowed only when their base/workspace isolation is explicit.

---

## Tool Result Projection

Do not return unbounded raw tool payloads to the model.

Every tool result projection should prefer:

```text
short result summary
exact semantic result handles
resolved revision/snapshot identity when important
structured status/error category
advertised next operations when available
```

Large content remains queryable through semantic handles.

The durable `ToolResult` may reference larger stored artifacts without injecting them into context.

---

## Model Final Output

A model result counts as branch-final only when normalized response semantics indicate no required tool calls and runtime policy accepts the output as terminal.

On completion:

- record the final externally meaningful `AgentOutput`;
- construct a durable `BranchResult`;
- include produced semantic change/validation handles;
- transition durable branch state to completed;
- emit terminal runtime event.

A branch may complete with a structured result and no user-facing text when a delegated task is purely semantic.

---

## Failure Behavior

Map failures into stable runtime categories.

For recoverable tool errors, policy may return a structured tool error to the model for correction.

For non-recoverable errors, finish the branch as failed/abandoned with a compact failure result.

Child failure must be representable as a tool result to the parent when parent policy allows recovery.

Never silently discard failed child branch history.

---

## Cancellation Tree

Implement a cancellation token/tree rooted at the agent operation.

Root cancellation propagates to:

```text
in-flight provider request
active atomic tool where cancellable
active child branches
scheduler waits
```

Child cancellation/failure does not necessarily cancel the parent unless branch policy declares it fatal.

Persist already completed durable records; do not roll back history merely because execution was cancelled.

---

Emit normalized events equivalent to:

```text
BranchExecutionStarted
```

Do not emit secret configuration or entire context blobs by default.

## Tests

Use scripted fake-provider sequences to prove at least:

### Simple final answer

```text
user prompt -> model final text -> completed root branch
```

### Atomic tool loop

```text
model requests inspect -> tool result -> model final text
```

### Nested branch

```text
model requests edit/delegated tool
-> child branch created
-> child executes two model/tool steps
-> child BranchResult produced
-> parent receives compact result only
-> parent final answer
```

### Nested branch isolation

Put a unique marker in child internal history and verify it is absent from the next parent context unless parent explicitly opens/references the child history.

### Cache

Run the same fingerprint with `ReuseExact` and prove the provider invocation count does not increase.

### Capability denial

Provider requests a registered tool outside branch capability scope; verify application operation is never executed.

### Unknown tool

Provider invents a tool id; verify structured failure rather than dynamic dispatch.

### Cancellation

Cancel while a child/provider request is active and verify the execution tree reaches stable cancellation state.

### Budget exhaustion

Script repeated tool calls and verify deterministic budget failure.

```text
cargo fmt --all -- --check
```

## Do Not Do

- Do not implement CLI/TUI/web presentation.
- Do not dispatch arbitrary provider-returned function names.
- Do not let model output write canonical state directly.
- Do not copy complete child histories into parent context by default.
- Do not make provider/network access mandatory for tests.
- Do not bypass application capability checks because a tool was advertised earlier.
