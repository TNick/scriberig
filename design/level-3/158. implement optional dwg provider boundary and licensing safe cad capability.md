# Implement Optional DWG Provider Boundary and Licensing-Safe CAD Capability

## Status

Planned.

All completion items remain unchecked until implemented and verified.

## 1. Goal

Add native DWG capability without coupling the reusable CAD semantic domain to one mandatory proprietary, copyleft-incompatible, native, or platform-specific implementation.

This task must establish a provider boundary that can support:

```text
DWG inspect/read
optional DWG semantic import
optional DWG write/materialization
provider-specific validation
explicit fidelity/capability diagnostics
```

The CAD schema from task 157 remains canonical. A DWG provider maps to that schema; it does not create a second CAD model.

This task depends on tasks 154 and 157.

## 4. Architectural Prohibitions

Do not:

- change `scriberig-domain-cad` semantic identity/types to match a provider's native object model;
- make DWG support mandatory for using CAD/DXF support;
- add a provider dependency with incompatible licensing to the reusable platform without explicit licensing approval reflected in repository metadata/design;
- expose native provider pointers/handles through protocol or persistent semantic records;
- store provider credentials/license keys as semantic project/session content;
- silently downgrade a DWG write to DXF conversion unless the user explicitly requests/export policy permits it;
- report write capability when provider only supports reading;
- bypass Scriberig candidate/change/materialization semantics because a vendor SDK has its own save API.

## 5. Phase A — Define Provider-Neutral CAD Format Adapter Capability

Reuse existing domain adapter architecture where possible. Add only the minimum CAD-specific provider contract needed for native formats.

Conceptual contract:

```text
CadExternalProvider
  provider_id/version
  supported_formats
  open/import capabilities
  render/export capabilities
  validation capabilities
  preservation/fidelity descriptors
  deployment requirements
```

Requirements:

- [ ] Provider identity/version is explicit and safe for provenance.
- [ ] Provider capability distinguishes read/write/validation separately.
- [ ] Provider reports supported native object classes/features when relevant.
- [ ] Provider fidelity maps to shared artifact fidelity from task 154.
- [ ] Provider-native objects are converted to/from CAD semantic types at adapter boundary.
- [ ] Absence of provider is a normal discoverable state.
- [ ] Provider errors are structured and do not expose secret license material.
- [ ] DXF adapter from task 157 remains usable with no DWG provider installed.

Focused tests:

- [ ] fake read-only provider reports inspect capability but no write;
- [ ] fake read/write provider advertises write only for supported feature set;
- [ ] absent provider returns explicit unavailable capability;
- [ ] provider A/B cannot leak native handles into semantic public model.

## 6. Phase B — Choose Integration Strategy

Pick one of these implementation forms based on licensing/deployment evidence:

```text
optional in-process library
optional dynamically loaded/native bridge
out-of-process adapter service/tool
user-supplied provider plugin
```

Requirements:

- [ ] Document why chosen strategy preserves the repository's platform/product licensing boundary.
- [ ] Make native/system dependency optional at build/runtime when it cannot be assumed on all systems.
- [ ] Provide a deterministic fake provider for CI.
- [ ] Do not require proprietary SDK/license in ordinary workspace tests.
- [ ] Update license/notice/package docs for any shipped dependency/bridge code.

If no acceptable real DWG provider can be shipped under current project constraints:

- [ ] Implement the provider boundary and fake/conformance provider only.
- [ ] Expose real DWG as `provider required/unavailable` rather than weakening licensing rules.
- [ ] Leave real-provider-specific checkboxes unchecked and document the blocker.

## 7. Phase C — DWG Import/Inspect Mapping

When a real provider is available, implement import for the subset that maps safely to task-157 CAD semantics.

Requirements:

- [ ] Exact DWG source evidence/digest is retained.
- [ ] Drawing/layers/blocks/supported entities map to existing CAD schema.
- [ ] Native object handles/IDs remain external identifiers/provenance.
- [ ] Unsupported native object classes are represented as preserved opaque/provider-owned evidence or cause read/write fidelity downgrade.
- [ ] Provider version is recorded in import provenance.
- [ ] Re-import through a different provider does not silently redefine semantic entity identity without reconciliation.
- [ ] Inspect/list/find use shared CAD application operations.

Focused tests may use fake provider records if redistribution of native DWG fixtures is problematic; if a legal deterministic DWG fixture is included, document its provenance.

---

## 8. Phase D — Optional DWG Write/Materialization

Only implement if chosen provider supplies safe write capability.

Requirements:

- [ ] DWG output is generated from exact candidate CAD semantic state plus required preserved provider evidence.
- [ ] Provider save/export occurs in candidate staging, not directly against live project file.
- [ ] Shared expected-baseline verification runs before replacement.
- [ ] Provider-reported unsupported semantic operation blocks output rather than dropping data.
- [ ] Resulting DWG is reopened/validated through provider before live replacement.
- [ ] Materialization records provider/version and exact new digest.
- [ ] Failure leaves canonical/project external state recoverable under task-154 materialization rules.

If write is unavailable:

- [ ] Capability is read-only/provider-inspect.
- [ ] Explicit DXF export may be offered as a separate operation, never as hidden DWG overwrite.

---

## 9. Phase E — Application/Protocol/Configuration

Requirements:

- [ ] Shared capability view identifies DWG provider availability/version/fidelity.
- [ ] Product configuration selects/enables provider through existing configuration/plugin boundaries.
- [ ] Protocol contains provider-neutral capability/result DTOs only.
- [ ] Remote server may have DWG provider even when client machine does not.
- [ ] Client/TUI/web do not need native provider libraries to inspect remote semantic CAD state.
- [ ] Agent tools receive CAD semantic operations, not vendor SDK calls.
- [ ] Provider credentials/license paths/keys are not serialized into session/project semantic state.

## 10. Phase F — Validation and Failure Modes

Add tests for:

- [ ] provider unavailable;
- [ ] provider load/init failure;
- [ ] read-only provider;
