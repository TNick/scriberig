# Agent Task: Implement Migration, Operations, and Provenance

## Goal

Implement the universal migration data model in `sr-change`.

This task covers exact snapshot transitions, entity deltas, generic semantic operations, domain-extensible operations, and change provenance. It does not implement history traversal, branch logic, merge, rebase, or persistence backends.

2. `design/level-2/002. change history and merge crate design.md`.

Add unit tests beside the implementation or in a focused test module following repository convention.

## Implement `EntityDelta`

Add a public universal entity transition type equivalent in meaning to:

```text
EntityDelta {
    entity: EntityId,
    before: Option<RevisionId>,
    after: Option<RevisionId>,
}
```

Enforce the invariant that `before == after` is not a valid delta.

Provide clear helpers or predicates for:

```text
is_created
is_removed
is_modified
```

Do not infer physical deletion from `is_removed`; it only means absence from the resulting canonical state.

## Implement `Migration`

A migration must contain at least:

```text
base SnapshotId
result SnapshotId
entity deltas
source/provenance
semantic operations
```

Add parent/change references only if the current identifier model supports them cleanly. Do not invent storage-specific row IDs.

Construction must reject:

- identical base/result snapshots when the migration claims canonical changes;
- duplicate deltas for the same entity;
- no-op entity deltas.

A representation-only operation is not a semantic migration and should not be modeled by manufacturing an empty canonical migration.

## Generic operations

Implement a universal enum or equivalent tagged model containing the Level 2 operations:

```text
CreateEntity
ReplaceRevision
RemoveEntity
AddRelation
RemoveRelation
InsertCollectionMember
RemoveCollectionMember
MoveCollectionMember
ReplaceCollectionStructure
```

Use existing universal relation/collection identifiers from `sr-core` or adjacent generic crates if available.

If those identifiers do not exist yet, do not define domain-specific substitutes. Introduce only the smallest generic value type required and document why it belongs in `sr-change` versus `sr-core`.

Each operation must reference semantic entities and semantic positions/relations, never file offsets or line numbers.

## Domain-specific operation support

Add a representation that lets domain crates attach richer semantic intent without adding domain variants to the generic enum.

Requirements:

- explicit domain/type identity;
- opaque payload or typed reference whose encoding does not require `sr-change` to understand the domain;
- safe round-trip through the generic model;
- no dependency from `sr-change` to a domain crate.

Prefer the repository's canonical encoding/value conventions. Do not introduce JSON merely for convenience if the repository uses another generic value representation.

## Provenance

Implement a source category model covering at least:

```text
User
ExternalProjection
Agent
Cli
Api
WebEditor
Tui
Importer
Refactoring
Merge
Synchronization
System
Other
```

Add a provenance structure that can carry optional structured references such as:

- actor/tool identifier;
- branch/workspace entity;
- projection entity;
- validation result references;
- parent migration/change references;
- extension metadata.

Keep optional metadata generic. Do not make agent-specific fields mandatory.

## Ordering and determinism

Where migration identity or canonical encoding depends on ordering, normalize the representation deterministically.

Entity deltas should have a deterministic order independent of insertion order.

Do not silently reorder operations whose sequence is semantically meaningful.

## Error handling

Use typed errors for invalid migration construction.

At minimum distinguish:

```text
NoOpDelta
DuplicateEntityDelta
InvalidSnapshotTransition
InvalidOperation
```

Fit these into existing repository error conventions rather than creating a parallel error framework.

## Tests

Add tests proving:

- create delta is classified correctly;
- remove delta is classified correctly;
- modified delta is classified correctly;
- no-op delta is rejected;
- duplicate entity deltas are rejected;
- migration preserves exact base/result snapshots;
- generic operations round-trip through the chosen canonical representation if serialization exists;
- domain-specific opaque operation does not require a domain dependency;
- provenance supports each universal source category;
- ordering is deterministic where required.

## Constraints

- Never mutate a snapshot or revision.
- Do not infer history from timestamps.
- Do not add concrete backend code.
- Do not add domain-specific operation variants.
- Do not conflate diff with migration.
- Do not treat formatting-only changes as semantic migrations.
