# Verify TUI Conformance, Accessibility, and Terminal Recovery

**Status: [ ] In Progress**

## Objective

Complete the first TUI design suite by proving that terminal behavior is robust, semantic behavior conforms to shared operations, responsive layouts remain usable, and failure paths restore the user's terminal.

This is a verification/hardening task, not an excuse to introduce new semantic behavior.

Read first:

1. `design/level-1/015. terminal user interface principles.md`;
2. `design/level-2/012. capability matrix and cross surface conformance.md`;
3. `design/level-2/021. terminal ui runtime and state architecture.md`;
4. `design/level-2/022. terminal ui views interaction and conformance.md`;
5. tasks 099 through 105 that are applicable/complete when this task runs.

## Test Layers

Ensure the repository has coverage at four distinct layers:

```text
pure reducer/keymap tests
Ratatui TestBackend rendering tests
TUI service-adapter semantic tests
cross-surface conformance tests
```

Do not replace semantic tests with screenshots, and do not replace rendering tests with semantic adapter assertions. Each layer catches a different class of defect.

## Cross-Surface Conformance

Extend `scriberig-conformance` or its current equivalent so TUI-invoked operations can be compared without launching an interactive terminal and without scraping ANSI/cell output.

For every TUI capability marked `verified`, compare the TUI adapter/result model against the authoritative application semantics using the same deterministic fixture.

At minimum verify currently implemented equivalents of:

```text
inspect_entity
runtime_capabilities
operation_status         when implemented
operation_cancel         when implemented
event_subscription       when implemented
```

For history/diff/mutation/session capabilities, add conformance cases only when their shared operation contracts and TUI adapters exist.

Update `capabilities.toml` so `verified` means a real test proves the path.

## Rendering Matrix

Use deterministic rendering tests for at least:

```text
140x40 wide
100x30 medium
72x24 narrow
minimum-size guard case
```

Cover representative states:

```text
empty/loading
successful inspect
structured error
permission denied
stale data
history/diff or another secondary view when implemented
modal command palette
confirmation/review
running operation when implemented
```

Assert important labels/regions and focus state rather than relying only on brittle full-frame snapshots.

A small number of full-frame golden assertions are acceptable for shell regressions.

## Accessibility Checks

Tests/review must verify:

- every core workflow is keyboard reachable;
- focus is represented by text/symbol/border semantics, not color alone;
- validation/conflict/error/permission states have textual or symbolic meaning;
- no-color or limited-color rendering remains understandable;
- help can be opened from normal interactive states;
- command palette exposes contextual actions discoverably;
- mouse support, if present, is optional;
- Unicode decoration is not necessary to understand semantic status.

If the theme implementation supports a no-color mode, include it in rendering tests. Otherwise make style-free semantic markers directly testable.

## Terminal Recovery Tests

Abstract terminal command execution enough to test the lifecycle state machine without taking over the CI terminal.

Verify attempted restoration after:

```text
normal user quit
runtime loop error
render error
input/event error
panic restoration hook path where safely testable
partial startup failure after raw mode but before full initialization
```

Restoration expectations include the supported equivalents of:

```text
leave alternate screen
disable bracketed paste
disable mouse capture if enabled
show cursor
disable raw mode
```

Test idempotent/drop behavior so an explicit exit followed by `Drop` does not produce an invalid state transition.

Do not write a test that can leave the developer shell in raw mode when it fails.

---

## Input Safety Tests

Add cases for untrusted/pasted strings containing:

```text
ESC
CSI/control sequences
newlines/tabs
very long lines
invalid/edge Unicode sequences representable in Rust strings
```

Verify that application/projection/session text cannot inject terminal control behavior through ordinary rendering.

Paste must remain input data and must not execute palette/global key commands.

Where the terminal backend provides bracketed-paste events, test the TUI translation rather than manually splitting the text into key events.

---

## Resize and State Preservation

Exercise transitions among width classes while state is populated:

```text
wide -> medium -> narrow -> wide
```

Verify preservation of:

```text
semantic selection
navigation back/forward stack
active primary view
open data/view models
operation observation state
```

Presentation-only cursor/scroll state may be adjusted when a pane disappears, but it must remain safe and deterministic.

No resize path may panic on zero-sized intermediate rectangles.

---

## Responsiveness and Bounded Work

Add deterministic tests or instrumentation proving that:

- drawing does not call the semantic service;
- a static UI does not busy-spin continuously;
- large list rendering processes only the bounded/visible model supplied to it;
- stale service responses do not overwrite newer requests;
- event bursts do not create unbounded duplicate refresh work for the same visible target where coalescing is implemented.

Do not use fragile wall-clock microbenchmarks as the only evidence. Prefer counters/fakes that make forbidden work observable.

---

## Error Hygiene

Review and test that user-visible/internal error formatting does not expose:

```text
raw SQL
private backend row identifiers
secrets/authentication values
Rust debug dumps as product output
untrusted ANSI/control sequences
```

Semantic error categories and safe diagnostics should remain visible.
