# Implement Universal Graph Semantic Records

## Objective

Implement the storage-independent universal graph records and snapshot-bound read contracts required by the universal knowledge model.

This task owns runtime semantic revision payloads, typed relations, ordered/unordered collections, descriptions, derived artifacts, and a read-only graph view contract.

It must reuse the existing shared core, schema, and identity/storage abstractions. It must not create a second persistence system.

## 1. Runtime Relation Values

In `relation.rs`, implement the runtime representation for an owned semantic relation.

The representation must keep separate:

```text
relation type identity
target semantic entity identity/identities
```

Targets must use the established `EntityId` or equivalent semantic entity handle.

Do not use:

- filenames;
- line numbers;
- database row IDs;
- display names;

as relation identity.

### Semantics

- Ordinary canonical relations point to conceptual entities.
- The exact target revision is resolved in a snapshot when needed.
- Derived relations may be represented as derived artifacts rather than silently inserted into canonical revision data.
- Reverse relation copies are not required inside target revisions.

Use the schema relation cardinality to validate how many targets are legal; do not bake every cardinality rule into the raw relation-value type itself unless the existing schema API makes that natural.

---

## 2. Ordered and Unordered Collection Values

In `collection.rs`, implement a public collection-value model with semantically distinct ordered and unordered cases.

Conceptually:

```text
Ordered(Vec<EntityId>)
Unordered(Set<EntityId>)
```

The concrete containers may differ, but required behavior is:

- ordered collections preserve member sequence exactly;
- reordering produces a different ordered collection value;
- unordered collections compare/behave by membership rather than insertion order;
- collection members are semantic entity handles;
- parent position is not stored in the child entity;
- moving a member changes the owning collection state, not the member entity identity.

Document duplicate-member policy explicitly.

If duplicates are prohibited, enforce that deterministically. If ordered duplicate membership is allowed for a specific future domain, the universal representation must not accidentally prohibit it without schema support. Prefer the least surprising generic representation and let schemas constrain it.

---

## 3. Universal Semantic Revision Record

In `revision.rs`, implement a storage-independent `RevisionRecord` or equivalent representing one exact semantic entity state.

It must include conceptually:

```text
entity type
properties
owned relation values
owned collection values
```

Use deterministic maps where practical.

### Interaction with existing revision storage

The identity/storage layer may already define a lower-level canonical revision blob/value used to compute `RevisionId`.

Do not replace it.

Instead, this semantic revision record should be encodable/serializable through the existing canonical revision mechanism or otherwise be a higher-level model that the store can persist without redefining revision identity rules.

If a canonical-encoding trait already exists, implement it here as appropriate.

Do not invent a second `RevisionId` algorithm.

### Prohibited state

A semantic revision record must not require:

- mutable parent pointer;
- database connection;
- database row ID;
- mutable current snapshot;
- reverse-index cache;
- file path as semantic identity;
- agent runtime state.

---

## 4. Schema Validation Integration

Implement the universal schema crate's `ValidationSubject` or equivalent trait for `RevisionRecord`.

Expose:

```text
entity type
property keys/values
relation types/targets
collection types/members
```

When target/member entity type validation requires a context, adapt the graph/read-view layer to provide the schema validator with the required type resolution.

Do not add a graph dependency to the schema crate.

---

## 5. Description Object

In `description.rs`, implement a derived description record.

Required semantic content:

```text
exact source entity + revision
description profile
text
provenance
optional information-cost metadata
```

Information-cost metadata may include optional estimates such as:

```text
bytes
characters
estimated tokens
```

Do not require a tokenizer dependency.

Generated descriptions are **derived knowledge by default** and must not be inserted into the canonical semantic revision record merely because they describe it.

---

## 6. Derived Artifact

In `derived.rs`, implement a generic derived-artifact representation.

It must expose at least:

```text
artifact/profile kind
exact immutable dependencies
producer/configuration identity
provenance
result payload or result reference
status if useful
```

Use the shared `KnowledgeValue` for generic small payloads where appropriate, or an explicit typed result reference if the existing architecture provides one.

The important invariant is that exact dependency revisions remain inspectable.

Do not implement caching or invalidation here. Later caching logic will decide reuse by comparing declared dependencies.

---

## 7. Snapshot-Bound Read View

In `view.rs`, define or extend a storage-independent trait such as `KnowledgeView`.

Required conceptual operations:

```text
resolve(snapshot, entity) -> exact revision
read semantic revision
obtain schema/entity-type information
obtain reverse relations through a view/index abstraction
```

Owned forward properties, relations, and collections may be read directly from the semantic revision record.

### Explicit snapshot requirement

Any operation whose result depends on which revision of an entity is active must accept an explicit `SnapshotId` or operate on an already snapshot-bound view object.

Do not make an unqualified `get_current(entity)` the universal semantic API.

### Backend neutrality

Use an associated error type or equivalent abstraction so the trait can be implemented by:

- in-memory test stores;
- SQLite-backed stores;
- future remote stores;
- test doubles.

The graph crate must not expose SQLite error types in its universal API.

---

## 8. Reverse Navigation

Define a small result type for reverse navigation, conceptually:

```text
source entity
relation type
optional resolved source revision
```

Reverse navigation is provided by an index/view implementation.

It must not require adding canonical `parent` or reverse-edge fields to every target revision.

---

## 9. Public API

`lib.rs` should expose the main universal graph concepts through stable imports:

```text
RevisionRecord
RelationValue
CollectionValue
Description
DerivedArtifact
KnowledgeView
ReverseRelation
```

Use existing project names if equivalent types already exist.

Avoid two public types that represent the same semantic concept just because separate design tasks created provisional names.

---

## 10. Focused Unit Tests

Add module-level tests for:

1. ordered collection order preservation;
2. reordered ordered collection is different;
3. unordered collection membership is independent of insertion order;
4. relation targets are semantic entity IDs;
5. revision record requires no parent pointer;
6. revision record implements schema validation subject;
7. description binds to exact entity/revision and provenance;
8. derived artifact retains exact dependencies;
9. a mock/read view resolves one entity to different revisions in different snapshots;
10. reverse lookup can be represented without canonical reverse-edge duplication.

Do not add database integration tests in this task unless the existing graph crate already has a backend-neutral test harness that makes this free.

---

## Documentation

Public docs must explain:

- revision records are exact semantic state, but revision-ID generation belongs to identity/storage code;
- relations target semantic identities;
- collections own order/membership semantics;
- child entities do not carry parent position;
- descriptions and derived artifacts are separate derived knowledge;
- graph interpretation is snapshot-bound;
- reverse navigation is an index/view capability.
