# Implement: Filesystem Observation, Synchronization, and Recovery

## Objective

Complete the filesystem synchronization engine in `sr-projection-fs` so managed projections can detect external changes, suppress feedback from Scriberig's own writes, retain failed imports, and hand exact three-way inputs to a domain adapter.

This task does not implement Markdown semantics. Use a fake editable adapter in tests.

## Observation model

Define an internal/public-neutral event model supporting at least:

```text
Created(path)
Modified(path)
Removed(path)
Renamed { from, to }
RescanRequired(scope)
```

Treat events as hints. Every event handler must inspect current file/synchronization state before deciding what changed.

Duplicate or coalesced events must be safe.

## Observation source abstraction

Provide a trait or stream boundary so tests can inject deterministic events.

If a concrete watcher crate is selected:

- keep it behind one adapter module;
- convert its events immediately into Scriberig observation events;
- do not leak its debounce/coalescing semantics into projection correctness;
- document platform limitations in code.

## Synchronization store boundary

Define a small interface used by the synchronization engine to load/update runtime projection sync state.

The first implementation may include an in-memory implementation for tests.

Do not add SQLite tables in this task unless another existing design has already defined where runtime projection state belongs. Keep the interface backend-independent.

Updates to synchronization state around writes/imports must be coherent and ordered so a failed operation cannot falsely mark a projection synchronized.

## Render-to-file path

Implement a service operation equivalent to:

```text
render_managed_projection(spec, exact semantic input)
    -> adapter render
    -> atomic filesystem write
    -> record exact output digest and base
    -> state = Synchronized
```

Rules:

- reject `Unmanaged`;
- respect read-only/editable ownership;
- store the actual renderer/style/base used;
- update the synchronized digest only after successful write;
- expose structured diagnostics on failure.

## External modification detection

On a relevant observation:

1. load projection sync state;
2. inspect current path;
3. if missing, transition according to missing/deletion policy without inventing semantics;
4. read exact bytes if present;
5. compute digest;
6. if digest equals last synchronized rendered digest, ensure state is synchronized and stop;
7. if different, mark `ExternallyModified` and begin editable-import flow if ownership permits.

For `ManagedReadOnly`, do not call parse/reconcile. Surface drift state or configured regeneration behavior.

For `Unmanaged`, do nothing beyond optional observation metadata.

## Feedback-loop suppression

Correctness must rely on exact state/hash checks rather than only timestamps/debounce.

After Scriberig writes bytes H and watcher emits `Modified(path)`, reading the file and seeing H must result in no import.

If the file changed again before processing and now hashes to H2, the external edit must still be noticed even if an old self-write token exists.

Optional operation tokens may reduce IO but cannot override contradictory content.

## Editable import orchestration

For an externally modified managed-editable file:

```text
read F
load synchronization base B
load current canonical D
adapter.parse(F)
adapter.reconcile(B, D, candidate)
adapter.validate(result)
```

The synchronization engine must react to generic outcomes:

- `NoSemanticChange`: optionally rerender configured canonical style, then establish new base;
- `MigrationProposal`: pass to change/promotion service boundary, then rerender successful canonical result;
- `Ambiguous`: state becomes conflict/attention-required; preserve external bytes/base;
- `Conflict`: same as above with structured conflict;
- `InvalidExternalState`: state becomes `ImportFailed`; preserve base and diagnostics.

Do not apply migrations directly by modifying store records. Use public `sr-change`/application-level promotion boundaries available in the repository.

## Failed import recovery

`recovery.rs` must represent enough information to retry:

- projection reference;
- base snapshot;
- current canonical snapshot observed for the attempt;
- external digest;
- path;
- stage of failure;
- structured diagnostics;
- optional captured external bytes if policy chooses to retain them.

A later event for unchanged invalid bytes should be idempotent. A later event with different bytes should create a new attempt while keeping historical diagnostics only if the runtime store policy supports it.

Never advance the last synchronization base on failure.

## Rename/move handling

A rename event should update external-location mapping/state only through a projection ownership/configuration service boundary.

Do not change semantic entity identity.

If the destination is not owned by the same projection, surface an unresolved ownership/mapping event rather than silently taking control.

## Removal handling

File removal is not semantic deletion by default.

Represent `Missing` and expose enough context for higher/domain policy to choose regeneration, projection unmapping, or candidate semantic deletion.

## Tests

Using fake observation source, in-memory sync state, temporary filesystem, and fake domain adapter, cover:

- self-write watcher event does not call parse;
- external content change calls parse exactly as needed;
- duplicate modified events are idempotent;
- changed-again file is not hidden by stale self-write suppression;
- read-only projection does not import;
- unmanaged file is ignored;
- parse failure retains old base and enters `ImportFailed`;
- later valid content retries and can become synchronized;
- ambiguity/conflict retains external state and base;
- missing file enters `Missing` without deleting semantic state;
- rename preserves projection identity and does not alter semantic entity IDs;
- current canonical snapshot can differ from synchronization base and both are passed to reconciliation.

## Do not do

- Do not implement Markdown matching here.
- Do not resolve semantic conflicts in the filesystem layer.
- Do not use watcher timing as the authority for self-write detection.
- Do not advance sync base after failed parse/reconcile/validation.
- Do not treat deletion as semantic deletion automatically.
- Do not add agent/server/UI dependencies.
