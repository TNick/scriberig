# Implement Candidate Promotion and Approval Pipeline

## Objective

Implement the application-level path that turns an isolated candidate snapshot into canonical state only after capability checks, required validation evidence, policy evaluation, and any required approval.

This task must make promotion an explicit state transition rather than a storage write shortcut.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 14–19, 34–36 and 61.
2. `design/level-1/005. changes migrations branches and merge.md`.
3. `design/level-3/001. implement principal and capability model.md`.
4. `design/level-3/003. implement validation evidence and exact input binding.md`.
5. Existing migration/snapshot/application designs.

If branches/candidate snapshots or atomic canonical-root update are not implemented, stop and report the prerequisite.

## Expected Area

Work in the application layer and reuse migration/store primitives. Typical modules:

```text
crates/scriberig-app/src/promotion.rs
crates/scriberig-app/src/policy.rs
crates/scriberig-app/src/approval.rs
crates/scriberig-app/src/lib.rs
```

Do not put project promotion policy in the generic store.

## Promotion Request

Define a promotion request that includes at least:

```text
principal
base canonical snapshot
candidate snapshot
migration/change reference
available validation evidence references
requested policy/profile
optional approvals
```

The request must be explicit about the expected current canonical snapshot.

## Promotion Evaluation

Implement the pipeline in this order:

```text
verify Promote capability
verify expected base/current canonical state
collect required evidence
verify evidence applies to exact candidate/dependencies
evaluate promotion policy
verify required approval evidence
atomically advance canonical root
record promotion provenance/result
```

If the canonical root changed after proposal creation, do not apply approximately. Return a structured result such as rebase/merge/conflict required.

## Policy Interface

Define a project/domain-extensible policy interface that consumes candidate metadata plus validation/approval evidence and returns a structured decision:

```text
Allow
Reject
RequireApproval
RequireAdditionalValidation
ConflictOrStale
```

Record which exact policy revision/profile produced the decision.

Do not hard-code `tests passed => allow` as the universal policy.

## Approval

Represent approval as an attributable operation/evidence object, not a mutable boolean. It must record principal, candidate, policy context, and time/operation metadata according to existing history conventions.

Approval for candidate A must not silently apply to candidate B.

## Promotion Result

Return and persist enough information to reconstruct:

```text
old canonical snapshot
candidate/new canonical snapshot
migration/change
principal/proposer if known
validation evidence used
policy evaluation
approval evidence used
promotion operation
```

Rejected candidates remain non-canonical and inspectable if retained by normal branch/history policy.

## Tests

Test at least:

1. promotion without Promote capability is denied;
2. validation capability alone cannot promote;
3. stale base snapshot prevents direct promotion;
4. evidence for another candidate is rejected;
5. policy can require additional validation;
6. policy can require approval;
7. approval for the wrong candidate is rejected;
8. successful promotion atomically advances the canonical root;
9. failed policy evaluation leaves canonical state unchanged;
10. promotion provenance can explain why the candidate was accepted.

## Validation

Run workspace formatting, check, tests, and lint. Include a concurrency/stale-root test if the store supports compare-and-swap or equivalent root guards.

## Do Not

Do not let validators call root-update APIs directly. Do not bypass migration/history recording. Do not rewrite candidate snapshots in place. Do not grant approval based solely on actor identity or model quality.

## Completion Checklist

- [x] promotion is one application operation;
- [x] exact base/current state is checked;
- [x] exact validation evidence is checked;
- [x] policy decision is structured and attributable;
- [x] approval is attributable evidence;
- [x] canonical root update is atomic;
- [x] rejected/stale candidates cannot silently become canonical.
