# Implement External Effect Receipts and Reconciliation

## Objective

Create the application-level record and state machine for side-effecting external operations so retries, failures, and local/external disagreement remain explicit.

This task provides reusable external-effect semantics. It does not implement any specific GitHub, email, cloud, or messaging connector.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 27–30 and 61.
2. `design/level-3/001. implement principal and capability model.md`.
3. Existing application operation/event designs.
4. Existing session/tool invocation designs if they are already implemented.

If application operations and capability checks are not implemented, stop and report the prerequisite.

## Expected Area

Typical modules:

```text
crates/scriberig-app/src/external_effect.rs
crates/scriberig-app/src/lib.rs
```

Protocol exposure is handled by a later task. Connector-specific code must remain outside this module.

## External Effect Intent

Represent an immutable intent containing at least:

```text
principal
operation kind
external destination identifier
request fingerprint or idempotency key when available
input semantic snapshot/revisions
capability reference/context
created operation id
```

Do not store reusable credentials in the semantic object.

## State Model

Represent explicit states equivalent to:

```text
Requested
Attempted
ConfirmedExternally
ReflectedLocally
Failed
Unknown
```

A local exception after sending a remote request must not be reported as definitely failed when the external outcome is unknown.

State transitions must preserve history/provenance. Do not overwrite a single mutable status without retaining the operation chain.

## Receipt

Provide a durable receipt/result representation capable of storing non-secret evidence such as:

```text
external operation id
remote resource reference
response/status metadata
confirmation observation
time if supported by existing history model
request fingerprint/idempotency key
```

Keep raw secrets and credential material out of receipts.

## Execution Boundary

The application operation must verify `InvokeExternal` authority for the exact destination before calling connector code.

A local `ModifyBranch` or `Promote` capability must not imply external invocation authority.

Run all applicable local validation and approval checks before irreversible invocation where the operation permits it.

## Retry Semantics

Expose enough state for connector adapters to make safe retry decisions:

- confirmed success: do not resend blindly;
- definite failure before remote acceptance: retry may be safe according to connector policy;
- unknown outcome: require reconciliation/lookup when supported;
- idempotency key available: reuse it for the same semantic intent.

Do not pretend all external systems are transactional or idempotent.

## Reconciliation

Provide an operation to record a later external observation and reconcile it with the pending intent. The result must state whether the effect is confirmed externally and whether local semantic state reflects that confirmation.

## Tests

Use a fake connector and test:

1. external invocation without destination capability is denied;
2. local write capability alone cannot invoke remote effect;
3. confirmed success records a receipt;
4. timeout after send becomes `Unknown`, not definite failure;
5. unknown outcome can be reconciled by later observation;
6. repeated confirmed operation is not blindly resent;
7. idempotency key is stable for retry of the same intent where configured;
8. credentials are absent from persisted intent/receipt fixtures;
9. external success plus local persistence failure remains recoverable/inspectable;
10. all transitions retain operation provenance.

## Validation

Run workspace formatting, check, tests, and lint. No live external service is required.

## Do Not

Do not implement a generic secret vault. Do not add a universal network client. Do not claim local database transactions make remote services atomic. Do not log credential values for debugging.

## Completion Checklist

- [ ] external authority is destination-specific;
- [ ] intent and receipt are durable structured objects;
- [ ] unknown outcome is representable;
- [ ] retry behavior can use idempotency/reconciliation;
- [ ] local and external state remain distinguishable;
- [ ] no connector-specific policy leaks into the universal model.
