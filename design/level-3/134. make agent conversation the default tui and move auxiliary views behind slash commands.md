# Make the Recursive Agent Tree the Default TUI and Move Auxiliary Views Behind Slash Commands

**Status: [x] Complete**

## Objective

Restructure the native Scriberig TUI so that its ordinary experience is a conversation-like projection of the real recursive session tree rather than a linear transcript or multi-pane semantic browser.

The user should still experience the simplicity of Pi/Codex/Claude-style terminal interaction:

- launch directly into the agent surface;
- type immediately;
- see human messages, assistant results, semantic operations, branches, plans, and progress in one main viewport;
- keep a persistent composer at the bottom;
- use slash commands to open secondary controls/views.

But the underlying and visible interaction is explicitly tree-aware:

- agents recursively create child branches;
- `/plan` creates durable planned nodes in the same tree;
- plan dependencies can block/enable sibling work;
- different branches may be assigned to different model/provider profiles;
- one auto-advancing plan coordinator exists at a time;
- the user can navigate to a stable historical replyable node and continue from it;
- new activity appears at its structural location rather than always at the bottom;
- completed children collapse to compact `BranchResult`-style summaries but remain expandable;
- nesting is shown by colored vertical depth rails;
- the current reply anchor has a distinct background highlight;
- per-activity detail settings control rendering without affecting context;
- source/document edits are normally semantic/domain operations, not generic file writes.

The controlling product rule is:

> **Conversation is home, but the conversation is a projection of the recursive session/plan tree. Auxiliary inspection/control surfaces are explicit slash-command destinations.**

This task depends on and must preserve the invariants in:

- `design/level-1/017. recursive agent decomposition and context isolation.md`;
- `design/level-1/018. durable plans dependency scheduling and multi-model execution.md`;
- `design/level-1/019. semantic agent operations and projection-first editing.md`;
- task 133 shared model/thinking/trace controls.

The cross-layer implementation sequence is defined in task 135. Do not implement TUI-owned substitutes for missing shared semantics.

# Structural Placement, Not Append-Only Placement

The conversation is not a vector whose only update operation is `push`.

When new activity arrives:

1. update durable/shared state or local observation cache;
2. rebuild/incrementally update the tree projection;
3. locate the activity's structural parent/branch/plan node;
4. place it beneath that location;
5. preserve deterministic sibling/activity ordering using shared sequence/ordinal data;
6. adjust scroll/follow state without changing semantic selection.

If the user replies to an earlier node, the new continuation appears there.

If an agent creates a child branch halfway through a root turn, that child appears there.

If a planned node starts later, execution fills that planned location rather than appearing only at the bottom because wall-clock time advanced.

# Navigation Cursor, Reply Anchor, and Coordinator Cursor

The TUI must keep these separate:

```text
navigation cursor
reply anchor
coordinator cursor
```

## Navigation cursor

Indicates the node currently being browsed.

It may move without changing where the next message will attach.

## Reply anchor

Identifies the stable replyable session location that receives the next human message.

It must survive:

- rerendering;
- width changes;
- activity verbosity changes;
- collapse/expand changes;
- live insertion of unrelated sibling activity.

## Coordinator cursor

Represents the current location of the single auto-advancing `/plan` coordinator.

While the user is idle/following, reply anchor may auto-follow coordinator cursor.

Once the user deliberately pins another node or begins composing against it, coordinator movement must not steal the reply target.

- [x] No cursor/anchor is represented only by row number.
- [x] Selecting a historical replyable node can set reply anchor.
- [x] Reply anchor remains stable while unrelated rows appear/disappear.
- [x] Coordinator auto-follow pauses when the user browses/pins another node.
- [x] Explicit action returns the UI to coordinator-follow mode.

---

# Reply-Anchor Visual Treatment

The current reply anchor must have a strong background highlight or equivalent non-rail treatment.

Do not use the rail color to communicate reply targeting.

The two cues mean different things:

```text
background highlight -> next human message attaches here
rail(s)              -> structural ancestry/depth
```

When replying to the normal current/coordinator head, the composer may remain visually quiet.

When pinned to a historical/sibling node, show a compact context hint such as:

```text
Replying to: “The parser has four code groups…”
> _
```

Important state must remain understandable without color alone.

# First Message and New Session

The initial composer must represent a true `NewSession` target rather than a fake session ID.

Conceptually:

```text
ConversationTarget::NewSession
ConversationTarget::Existing { session, reply_anchor }
```

Submission from `NewSession` must call a shared application start/create operation.

When accepted:

1. receive authoritative session/root-branch/operation handles;
2. replace local target with those handles;
3. render the user input from durable/shared state;
4. observe execution through normal activity/operation semantics.

Do not allocate canonical session identities inside `scriberig-tui`.

---

# Historical Continuation

Submitting against a historical reply anchor must call a shared continuation operation that identifies the exact semantic continuation location.

The TUI must not construct provider context itself.

The application/runtime context compiler decides which ancestor turns, branch descriptors/results, dependency results, decisions, semantic handles, and recent local activity belong in the new branch context.

Later siblings must not enter the continuation merely because they were created later in wall-clock time.

# Semantic Operations in the Conversation

Tool/activity rendering must reflect that most known source/document work is semantic.

Compact semantic operation:

```text
▏ add function parse_union_type to php::parser
▏ ✓ Function F194 created
```

Full one-line/wrapped form:

```text
▏ code.add_function module=php::parser after=parse_named_type name=parse_union_type return_type=TypeResult
```

Structured parameter form:

```text
▏ code.add_function
▏   module: php::parser
▏   after: parse_named_type
▏   name: parse_union_type
▏   return_type: TypeResult
```

Actual external process:

```text
▏ cargo test -p scriberig-domain-php ...
▏ ✓ 12 tests passed
```

Do not render every operation as though it were shell syntax.

# Slash Commands Are the UI Escape Hatch

The default home remains the conversation/tree.

Auxiliary controls/views are explicit local commands, for example:

```text
/model
/assign
/thinking
/view
/plan
/session
/explorer
/inspect
/find
/history
/diff
/projection
/changes
/operations
/project
/status
/help
/new
```

A recognized command must never be sent to the model.

Unknown slash commands must not silently become model input.

Use an explicit literal escape, recommended:

```text
//literal -> send "/literal" as ordinary agent input
```

Slash completion must operate while typing:

```text
> /mo
  /model
```

and:

```text
> /pl
  /plan
```

# Composer Behavior

Normal mode:

```text
ordinary key -> edit draft
Enter        -> submit
Ctrl+J       -> newline
```

No `i` is required.

`Esc` may enter tree-navigation/browse mode or close the current special view according to final keymap design, but returning to ordinary conversation typing must be direct and obvious.

While agent work runs:

- composer remains usable;
- submission follows shared queue/continuation policy;
- typing does not implicitly cancel;
- cancellation is explicit.

Do not let coordinator auto-advance steal a pinned reply anchor or draft.
