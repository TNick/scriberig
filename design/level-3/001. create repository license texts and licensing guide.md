# Create Repository License Texts and Licensing Guide

## Objective

Create the repository-level licensing artifacts required by:

1. `design/level-1/014. extensibility ecosystem and licensing.md`
2. `design/level-2/001. licensing artifacts package metadata and notices.md`

This task is limited to the two complete license texts and the human-readable repository licensing guide.

Do not edit package manifests, contributor policy, source headers, or dependency notices in this task.

The controlling rule is:

> Reusable infrastructure is Apache-2.0. The integrated Scriberig product and runtime are AGPL-3.0. The repository must make the boundary understandable without weakening either side.

---

## Files to Create

Create exactly these repository-level files if they do not already exist:

```text
LICENSES/Apache-2.0.txt
LICENSES/AGPL-3.0.txt
LICENSING.md
```

If one already exists, inspect it before changing it. Do not overwrite user-authored legal material blindly.

---

## Step 1 — Read the Controlling Designs

Before editing, read the full contents of:

```text
design/level-1/014. extensibility ecosystem and licensing.md
design/level-2/001. licensing artifacts package metadata and notices.md
```

Do not infer a different licensing model from package names, README text, or personal preference.

The Level 1 document is authoritative for the architectural split. The Level 2 document is authoritative for the concrete repository artifacts created by this task.

---

## Step 2 — Obtain the Complete Apache-2.0 Text

Populate:

```text
LICENSES/Apache-2.0.txt
```

with the complete, unmodified Apache License 2.0 text from an authoritative source.

Requirements:

- copy the legal text verbatim;
- do not summarize it;
- do not insert Scriberig-specific commentary into the license text;
- do not remove the appendix;
- preserve the license title and version;
- do not add a copyright holder unless the official text itself contains placeholder/example text;
- do not convert the text into a different license template.

If the agent cannot obtain or verify the authoritative full text, stop this task and report the missing prerequisite rather than generating legal text from memory.

---

## Step 3 — Obtain the Complete GNU AGPL Version 3 Text

Populate:

```text
LICENSES/AGPL-3.0.txt
```

with the complete, unmodified GNU Affero General Public License version 3 text selected by the Level 1 design.

Requirements:

- copy the legal text verbatim from an authoritative source;
- do not summarize or rewrite clauses;
- include all sections of the license;
- do not insert project commentary into the license body;
- do not silently switch to ordinary GPL;
- do not silently choose a later-version clause or a different license variant on behalf of the project.

If the exact intended legal text cannot be verified, stop and report the ambiguity instead of inventing wording.

## Step 4 — Create `LICENSING.md`

`LICENSING.md` is explanatory documentation, not a replacement for the complete license texts.

Use a clear structure similar to:

```text
# Licensing Scriberig

## Overview
## Apache-2.0 reusable platform
## AGPL-3.0 integrated product
## How to determine a package's license
## Agent and CLI boundary
## Third-party applications and extensions
## Third-party dependencies
## Source headers and SPDX metadata
## Contributions and future dual licensing
## License texts
```

The headings may vary slightly, but all required information below must be present.

---

## Required `LICENSING.md` Content

### Overview

Explain that the repository intentionally uses two licenses following the architectural platform/product boundary.

State the rule directly:

```text
Reusable platform and building blocks: Apache-2.0
Integrated Scriberig product and runtime: AGPL-3.0
```

Do not describe the repository as wholly Apache or wholly AGPL.

### Apache reusable platform

Explain that reusable infrastructure is Apache-2.0 by default and give representative categories from the design:

- identity/core types;
- storage;
- graph and schemas;
- queries and migrations;
- projections;
- domain adapters;
- protocol definitions;
- Rust and TypeScript clients;
- client-side models and framework bindings;
- headless editor behavior;
- neutral components;
- reusable MUI components;
- reusable agent interfaces that do not implement the integrated runtime.

Make clear that organizations may build proprietary applications using these Apache-licensed components subject to their applicable license terms.

### AGPL integrated product

Explain that the integrated product is AGPL-3.0 by default and give the representative categories from the design:

- reference Scriberig server application;
- integrated agent execution/orchestration runtime;
- complete Scriberig editor application;
- product-specific integrated workflows.

Do not claim that every server library, every binary, or every agent-related abstraction is automatically AGPL.

### Package-level decision

State that each distributable crate/package declares its own license in its package metadata and that this package declaration is the immediate indicator for that component.

Explain that architectural responsibility determines the classification.

A reusable CLI client may be Apache. A binary embedding the integrated AGPL runtime may be AGPL.

### Third-party applications

State that merely using Apache-licensed Scriberig platform libraries or interoperating with the public protocol does not turn an independent third-party application into the integrated Scriberig AGPL product.

Do not attempt to give legal advice about every possible combined work. Keep this section tied to the architectural intent expressed by the design.

### Third-party dependencies

State that third-party dependencies and assets retain their own licenses and that required attribution/notices must be preserved.

Do not list dependencies that are not actually present.

### SPDX/source headers

Explain that package metadata is required while repository-wide SPDX source headers are not currently mandated by this design.

Do not add a policy that every source file must contain a header.

### Contributions and future dual licensing

State that contributions follow the license of the component they modify.

State that commercial dual licensing of AGPL-covered components is only a possible future decision and is not promised or implicitly authorized by the current contribution terms.

Do not invent a CLA, DCO, assignment, or relicensing grant.

### License links

Link to:

```text
LICENSES/Apache-2.0.txt
LICENSES/AGPL-3.0.txt
```

using relative repository links.

## Content Quality Requirements

`LICENSING.md` must be understandable to a developer deciding whether to depend on a Scriberig package.

Prefer direct language over legal speculation.

Do not duplicate the full license texts inside `LICENSING.md`.

Do not claim that this guide overrides the actual licenses.

Do not add a copyright owner because the controlling designs do not specify one.

Do not add commercial contact information because the designs do not specify a commercial licensing program.

---

## Verification

Before completing the task:

- verify both files under `LICENSES/` contain complete authoritative texts;
- verify `LICENSING.md` names both licenses;
- verify it distinguishes reusable platform from integrated product;
- verify it says package metadata identifies each distributable component's license;
- verify it does not imply reusable MUI libraries are AGPL merely because the reference app uses them;
- verify it does not make all agent abstractions AGPL;
- verify it does not promise commercial dual licensing;
- verify all relative links resolve inside the repository.

## Do Not Do

Do not:

- edit `Cargo.toml` files;
- edit `package.json` files;
- create placeholder crates or web packages;
- add source SPDX headers;
- create a CLA or DCO;
- add a copyright assignment;
- create a plugin registry;
- add a commercial license;
- create protocol specifications;
- paraphrase legal license text;
- substitute GPL for AGPL;
- label the entire monorepo with one license.
