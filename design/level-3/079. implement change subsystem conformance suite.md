# Agent Task: Implement the Change Subsystem Conformance Suite

## Goal

Complete `crates/sr-change/tests/change_conformance.rs` as an end-to-end executable specification of the architectural invariants from `design/level-1/005. changes migrations branches and merge.md`.

This task should add tests and only the minimal production fixes required to make already-designed behavior conform. Do not redesign public APIs opportunistically from the test task.

```text
crates/sr-change/tests/change_conformance.rs
```

Production files may be modified only when a test reveals a real mismatch with the approved designs.

## Test environment

Use `sr-store-memory` as the default backend for this suite.

Build small fixtures through public APIs only. Do not reach into internal hash maps or private store fields to construct states.

Create helper functions for:

```text
empty/base snapshot creation
entity/revision creation
snapshot descendant creation
migration creation
branch/workspace setup
named-root setup
```

Keep helpers deterministic and small.

## Required scenario 1: exact direct migration

Create `S1` containing entity `E -> R1`.

Create `S2` containing `E -> R2`.

Record migration `M1` from `S1` to `S2`.

Verify:

- `S1` still resolves `E -> R1`;
- `S2` resolves `E -> R2`;
- migration base/result are exact;
- delta is exactly `R1 -> R2`;
- history query finds `M1` as touching `E`.

## Required scenario 2: creation and semantic removal

From one base:

- introduce entity `A`;
- remove entity `B` from the next canonical state.

Verify creation/removal delta classification and that historical snapshots still resolve retained old state.

Do not assert physical garbage collection.

## Required scenario 3: branches are cheap lines of work

Create two branches/workspaces from the same base snapshot.

Advance each independently.

Verify:

- shared base remains unchanged;
- each branch points to its own descendant;
- branch creation did not duplicate semantic entities/revisions;
- both results remain queryable.

Use public store metrics only if such metrics exist. Otherwise prove sharing through identical snapshot/revision identities rather than backend internals.

## Required scenario 4: optimistic promotion

Set:

```text
main -> S1
```

Create workspaces producing `S2` and `S3` from `S1`.

Promote `S2` with expected `S1`; it must succeed.

Attempt to promote `S3` with expected `S1`; it must fail as stale and report actual `S2`.

Verify `S3` remains available and no work was overwritten.

## Required scenario 5: arbitrary semantic diff

Build:

```text
S1 -> S2 -> S4
 \
  -> S3
```

Compare:

- `S1` with `S4`;
- `S2` with `S3`;
- a snapshot with itself.

Verify diff correctness without requiring direct ancestry.

## Required scenario 6: disjoint merge

Base contains entities `A@A1` and `B@B1`.

Left changes only `A`.

Right changes only `B`.

Three-way merge must resolve both automatically with zero conflicts.

Verify base, left, and right remain unchanged.

## Required scenario 7: convergent merge

Both descendants independently produce the same exact revision for one entity.

Merge must converge to that revision without conflict.

History may remain distinct even though resulting state is equal.

## Required scenario 8: competing edit conflict

Both sides modify the same entity to different revisions.

Verify:

- conflict kind is `BothModified` or the approved equivalent;
- base/left/right revision handles are present;
- no side is silently selected;
- unrelated disjoint changes remain in resolved output.

## Required scenario 9: delete/modify conflict

One side removes an entity while the other modifies it.

Verify a structured `DeleteModify` conflict and no textual conflict-marker dependency.

## Required scenario 10: rebase preserves original history

Create original work `S1 -> S2`.

Create newer base `S1 -> S3` affecting unrelated state.

Rebase original work onto `S3` to produce `S4`.

Verify:

- `S2` and its migration still exist unchanged;
- `S4` descends from `S3`;
- semantic intent was replayed;
- history query can distinguish original and rebased paths.

## Required scenario 11: rebase conflict

Create original work modifying `E`.

Create new base modifying the same `E` differently.

Rebase must return a structured conflict rather than overwrite the new base.

## Required scenario 12: history topology ignores insertion order

Persist migration/history records in an order different from logical ancestry where the test infrastructure permits it.

Verify ancestry/common-ancestor/entity-history queries use explicit references and still return correct topology.

## Required scenario 13: move preserves entity continuity

Represent a structural move of one existing entity between generic collections/owners.

Verify:

- the moved entity retains its `EntityId`;
- structural owners change as required;
- history describes a move/structural change rather than unrelated delete/create when continuity is known.

## Required scenario 14: cross-domain universal migration

Create entities with at least two different generic type/domain identities.

Change them atomically in one migration/snapshot transition.

Without loading any domain adapter, verify:

- all entity deltas are visible;
- summary counts are correct;
- query APIs do not assume one file or language;
- provenance is preserved.

## Required scenario 15: representation-only change creates no migration

Simulate or construct the highest-level available representation/style change that leaves canonical entity revisions identical.

Verify:

- canonical snapshot identity remains equal where the underlying snapshot model says state is identical;
- no semantic migration is manufactured;
- derived/render artifacts may change independently if those APIs are available.

Do not create a fake empty migration to satisfy this test.

## Required scenario 16: compact navigation summaries

Create a migration with several changes and a branch/workspace with description metadata.

Verify summary APIs return:

- exact handles;
- counts;
- branch status/base/current snapshots;
- short metadata where present;

without requiring domain adapters.

## Determinism checks

Repeat relevant diff/query construction with different insertion order.

Verify public result ordering remains deterministic.

Do not snapshot-test unstable debug formatting unless repository convention explicitly uses it.

## Backend independence check

Inspect `sr-change` dependencies as part of review.

The library must not depend on:

```text
sr-store-memory
sr-store-sqlite
```

except that `sr-store-memory` may appear under dev-dependencies for tests.

No production source file may import concrete backend implementation types.

## No domain leakage check

Search `sr-change` production code for domain-specific types.

```text
Markdown
PDF
session agent behavior
filesystem line offsets
```

Generic extension traits are allowed.
