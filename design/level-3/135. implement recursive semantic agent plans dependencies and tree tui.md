# Implement Recursive Semantic Agent Plans, Dependencies, Multi-Model Execution, and the Tree TUI

**Status: [ ] In Progress**

## 1. Objective

Implement the synchronized agent architecture defined by:

- `design/level-1/017. recursive agent decomposition and context isolation.md`;
- `design/level-1/018. durable plans dependency scheduling and multi-model execution.md`;
- `design/level-1/019. semantic agent operations and projection-first editing.md`;
- `design/level-3/134. make agent conversation the default tui and move auxiliary views behind slash commands.md`.

The final product must support all of these properties together:

1. sessions are recursive branch trees, not linear transcripts;
2. branches are context-isolation boundaries created by users, agents, plans, or runtime policy;
3. the user can reply from an exact historical replyable node;
4. `/plan` creates durable planned work visible in the same tree;
5. plan dependencies form an explicit DAG over plan nodes and are satisfied by durable results;
6. one auto-advancing coordinator advances a plan while many worker models may execute different branches concurrently;
7. each branch/plan node may have its own model/provider/profile/thinking/configuration;
8. one branch has at most one active executing owner; parallel attempts use sibling branches;
9. worker contexts receive selected ancestor/dependency results, not sibling/child transcripts;
10. understood source/document work is performed through semantic/domain operations rather than generic raw file writes;
11. shell/process execution is a bounded runtime/validation capability rather than the ordinary mutation interface;
12. the default TUI is a tree-aware conversation projection with structural insertion, colored depth rails, a highlighted reply anchor, plan/dependency/assignment state, per-activity detail modes, and slash-command auxiliary views;
13. reconnect/restart reconstructs durable state without provider-stream replay;
14. all product surfaces consume the same shared application/protocol semantics.

This task is deliberately written for a simple implementation agent. Follow it in order. Do not skip a phase because a later phase looks easier.

# 5. Phase 1 — Extend the Session Domain for Exact Continuations

## Task 1.1 — Define `ContinuationAnchor`

Add a provider-neutral session-domain representation that can identify a valid reply/continuation location.

Initial supported anchors should be conservative and explicit. Prefer variants equivalent to:

```text
BranchHead { branch }
Turn { branch, turn }
HumanInput { branch, turn/message }
AssistantOutput { branch, output }
BranchResult { branch, result }
```

Do not support arbitrary tool-result anchors unless the context compiler can define exact semantics for them.

Requirements:

- anchor points to stable durable identity;
- anchor can be validated against a session snapshot;
- anchor resolution can identify the branch/path and the cut-off position inside that branch;
- invalid/missing/non-replyable targets fail structurally.

Likely files:

```text
crates/scriberig-session/src/types.rs
crates/scriberig-session/src/turn.rs
crates/scriberig-session/src/views.rs
crates/scriberig-session/src/error.rs
```

Split modules if file-size rules require it.

- [ ] Anchor type added.
- [ ] Validation rejects missing session objects.
- [ ] Validation rejects non-replyable activity kinds.
- [ ] Anchor resolution is deterministic.

### Targeted tests

Prove:

- branch head resolves;
- earlier assistant output resolves;
- later sibling activity is not part of an earlier anchor path;
- invalid entity fails without fallback to current head.

## Task 1.2 — Add continuation branch creation from an anchor

The session layer must support creating a child/continuation branch whose origin references the exact anchor.

Do not overwrite the original branch history.

Store origin/provenance equivalent to:

```text
created_from_anchor
origin = HumanContinuation | AgentDelegation | PlanExecution | Retry | Validation | Alternative | RuntimePolicy
```

Origin may be an enum or structured provenance field; reuse existing provenance infrastructure where possible.

- [ ] Continuation creates a new branch or valid continuation according to shared policy.
- [ ] Original later sibling/turn history remains intact.
- [ ] Origin is inspectable but does not create separate branch semantics.

### Targeted tests


Only start this phase after plan/readiness/context/claim tests pass.


- [ ] Pure readiness/scheduler tests use no provider.

## Task 10.2 — Dispatch unassigned ready work

Coordinator selects ready nodes according to deterministic policy.

Initial policy may be simple:

```text

```

Do not invent sophisticated optimization before correctness.

- [ ] Scheduler respects concurrency budget.
- [ ] Scheduler does not dispatch blocked node.
- [ ] Scheduler does not double-dispatch claimed node.

## Task 10.3 — Run many workers concurrently

Use runtime concurrency primitives consistent with existing async architecture.

Do not share mutable provider request state between workers.

- [ ] Two independent sibling nodes can run with two fake provider profiles concurrently.
- [ ] Their model/profile provenance remains distinct.

## Task 10.4 — Consume worker result

On worker completion:

1. persist branch result;
2. mark plan node terminal/result-linked;
3. release worker claim;
4. derive newly ready nodes;
5. notify coordinator/activity stream;
6. continue scheduling if plan is running.

- [ ] Dependent starts only after durable result linkage.

## Task 10.5 — Failure handling

Initial policy must support at least:

```text

surface failure to coordinator
allow coordinator/user replan or explicit retry
```

Do not silently treat failed dependency as complete.

- [ ] Failure test proves blocked dependent remains blocked.

## Task 10.6 — Plan completion

Plan is complete only when completion policy is satisfied and no required unresolved node remains.

- [ ] Completed plan persists final state and releases coordinator claim.
