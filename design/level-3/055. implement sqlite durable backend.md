# Implement: SQLite Durable Backend

## Objective

Implement `sr-store-sqlite` as the first durable backend for the storage interfaces already implemented by `sr-store` and exercised by `sr-store-memory`.

The SQLite backend must preserve exactly the same logical behavior as the memory backend while adding durable transactions and recovery.

## Read first

Read:

1. `design/level-1/004. persistence and storage model.md`
2. `design/level-2/001. persistence crate boundaries.md`
3. `design/level-2/004. sqlite backend transactions and recovery.md`
4. Level 3 tasks 001 through 003.

Do not redesign the public storage traits unless a concrete incompatibility is found. If a trait must change, update the memory backend and tests in the same change.

## Database initialization

Implement opening a database by path and an in-memory SQLite database for tests.

On first open:

- create the backend schema;
- record a backend schema version;
- initialize any required metadata.

On later opens:

- detect the schema version;
- reject unsupported newer versions explicitly;
- run supported storage-schema upgrades if any exist.

Do not treat storage-schema upgrades as semantic migrations.

## Revision persistence

Persist immutable revision records keyed by `RevisionId`.

Requirements:

- exact duplicate insertion is idempotent;
- retrieval reconstructs the same logical revision record;
- stored bytes are sufficient to recompute and verify revision identity;
- backend row IDs are never exposed as semantic IDs.

## Snapshot persistence

Persist the internal structurally shared snapshot-map representation selected by the existing storage API.

A snapshot record must identify its persistent map root and deterministic `SnapshotId`.

Do not serialize a complete entity-to-revision map into a new monolithic blob for every snapshot if that defeats the Level 1 structural-sharing requirement.

## Named roots and transactions

Implement root promotion with compare-and-set semantics inside a SQLite transaction.

Conceptual sequence:

```text
BEGIN
insert missing immutable revisions/map nodes/snapshot
read root current value
compare with expected
if mismatch: ROLLBACK and return stale-root conflict
update root
COMMIT
```

The exact SQL may differ, but externally visible behavior must match this model.

## Recovery behavior

A reopened database must expose only committed named-root state.

Prepared immutable objects that were inserted but never made reachable by a promoted root are allowed.

No recovery path may mutate an old revision or snapshot to repair an incomplete write.

## Tests

Add durable backend tests for:

- initialize fresh database;
- close and reopen database;
- revision survives reopen;
- snapshot survives reopen;
- named root survives reopen;
- duplicate revision insert is idempotent;
- stale root CAS fails and root remains unchanged;
- explicit transaction rollback leaves old root visible;
- unsupported newer backend schema version fails with a typed error;
- failure before root promotion does not expose attempted new root.

Where possible, run tests against temporary database files rather than only SQLite `:memory:`.

## Commands to run

```text
cargo fmt --check
cargo test --workspace
```

## Do not do

- Do not expose a raw SQLite connection through the public `sr-store` interface.
- Do not add agent/session/domain tables.
- Do not rely on SQLite row order for canonical identity.
- Do not mutate existing canonical revision rows.
- Do not implement semantic merges.

## Completion checklist

- [x] SQLite backend implements the existing revision/snapshot/root interfaces.
- [x] Fresh initialization and reopen work.
- [x] Named-root promotion is transactional and compare-and-set based.
- [x] Previous snapshots remain readable.
- [x] Backend schema versioning is explicit.
- [x] Crash/reopen semantics expose only committed roots.
- [x] Workspace tests pass.

Stop after these conditions are met.
