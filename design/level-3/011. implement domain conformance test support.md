# Implement Domain Conformance Test Support

## Objective

Create reusable test support that lets every domain adapter prove it respects the architectural invariants in `design/level-1/007. domain modeling and adapters.md`.

The goal is not to test domain-specific semantics in one generic suite. The goal is to make common invariants easy to verify consistently across Markdown, Rust/code, PDF, sessions, and future domains.

Read before editing:

1. `design/level-1/007. domain modeling and adapters.md`
2. `design/level-1/006. projections and bidirectional editing.md`
3. the existing domain crates and shared schema/graph/migration/projection test APIs

---

## Files to Create or Update

Create a reusable test-support crate if no equivalent already exists:

```text
crates/domains/test-support/Cargo.toml
crates/domains/test-support/src/lib.rs
crates/domains/test-support/src/conformance.rs
crates/domains/test-support/src/fixture.rs
```

Use package name:

```text
scriberig-domain-test-support
```

Update the root workspace membership.

Domain crates may add this crate as a `dev-dependency` only.

If an existing generic test-support crate already serves this role, extend it instead of creating another one.

---

## Common Conformance Model

Define a small fixture/test contract that domain test suites can implement to provide:

```text
a representative canonical entity graph
a semantically equivalent projection round trip when the domain supports editable projections
a changed semantic example
a formatting/projection-only change example when applicable
a derived-data example when the domain supports derived analysis
a generic inspection target
```

Do not force unsupported concepts on a domain. Capabilities must be optional and tests should run only when the fixture declares them.

---

## Required Common Invariants

Provide reusable assertions/helpers for these invariants where applicable:

1. canonical state can be inspected through universal graph APIs;
2. domain-specific inspection adds meaning without bypassing universal identity;
3. unchanged semantic entities/revisions are reusable;
4. projection-only formatting changes do not create semantic changes;
5. editable projection reconciliation produces shared migration/change objects rather than direct mutation;
6. derived knowledge records provenance and can be rebuilt/discarded without losing canonical state;
7. descriptions/summaries marked generated remain derived;
8. source coordinates are metadata and not semantic identity;
9. generic handles survive irrelevant projection changes;
10. no agent runtime is needed to instantiate or use the domain fixture.

Not every domain must support editable projections or derived analysis. The harness must distinguish unsupported capability from failed conformance.

---

## Domain-Specific Adoption

Add conformance tests to the domain crates implemented by the other Level 3 tasks when those crates exist:

```text
scriberig-domain-markdown
scriberig-domain-code
scriberig-domain-rust
scriberig-domain-pdf
scriberig-session
```

Use `dev-dependencies` only. Do not make production domain code depend on the conformance crate.

For `scriberig-domain-code`, run only schema/identity/derived-boundary tests if no projection parser exists.

For PDF, treat exact source bytes versus derived extraction as the important authority/provenance boundary.

For sessions, verify provider-independent use and cross-domain references.

---

## Test Reporting

Failures should clearly identify:

```text
domain
capability/invariant
fixture case
expected invariant
observed behavior
```

Avoid opaque macro failures.

Prefer normal Rust test functions/helpers over a complex custom test runner unless the repository already has one.

---

## Workspace Checks

Run:

```text
cargo fmt --all -- --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

Also verify from manifests that `scriberig-domain-test-support` appears only as a development/test dependency for domain crates.

---

## Do Not Do

- Do not encode Markdown-specific rules into the generic harness.
- Do not require every domain to support rendering/reconciliation.
- Do not depend on agent crates.
- Do not create runtime production dependencies from domain crates to test-support.
- Do not use snapshots of huge serialized output as the only assertion mechanism.
- Do not treat unsupported optional capabilities as conformance failures.
- Do not replace domain-specific tests with this suite.
