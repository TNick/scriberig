# Implement Derived Selection, Freshness, Failure, and Retention Policies

## Objective

Implement policy types for choosing among immutable derived results and deciding whether a result is fresh enough or retained long enough to satisfy a request.

This task must keep four concerns separate:

```text
identity
selection
freshness
retention
```

A result's immutable identity must never change because it becomes preferred, stale for a current-information request, or eligible for eviction.

Do not implement reverse-dependency invalidation, protocol events, domain registration, background scheduling, agents, or a durable backend in this task.

## 1. Selection Is Not Identity

In `selection.rs`, define policy/request types for choosing among already stored immutable result records.

Exact lookup by `DerivationKey` remains the strongest path and is not replaced by selection.

Selection should support policy dimensions conceptually equivalent to:

```text
exact profile required
preferred profile
successful results only
fresh results only
newest compatible result
cheapest compatible result when cost metadata exists
trusted/allowed producer filter when caller supplies one
```

Do not hard-code one global selection policy.

A caller should be able to request a specific policy.

Selection must return the chosen exact result handle/record plus enough structured reason metadata to explain the choice later.

Do not mutate old results to mark one as current.

---

## 2. Preferred Result Metadata

The architecture allows convenience pointers such as:

```text
preferred_summary(F@R7) -> Summary S3
```

If this task introduces preferred-result metadata, represent it as derived selection state outside canonical snapshots.

Changing a preferred pointer must not:

- change a canonical `SnapshotId`;
- rewrite the immutable result record;
- delete older results;
- change the `DerivationKey`.

If the existing repository contract does not yet have a place to persist preferred metadata, define the policy/value type now and leave persistence to a later backend integration.

Do not distort the repository trait simply to force persistence into this task.

---

## 3. Freshness Model

In `freshness.rs`, define a domain-neutral freshness model.

The model must distinguish local immutable derivations from external/time-varying observations.

Local exact-state results should normally support:

```text
Freshness::Immutable
```

or an equivalent concept meaning that passage of time alone does not make them invalid.

External observations should be able to record conceptually:

```text
source identity
observed_at
optional valid_until / max_age policy
optional source revision / validator token
optional revalidation metadata
```

Use the repository's established time type if one exists. Do not introduce a second timestamp library without need.

The API must be able to answer:

```text
Fresh
Stale
RequiresRevalidation
NotApplicable
```

or equivalent structured outcomes.

Do not encode freshness only as a boolean if the policy needs to explain why revalidation is required.

---

## 4. Historical Truth vs Current Suitability

A stale external observation is still an exact historical artifact.

Tests and API docs must preserve this distinction:

```text
observed at T1: value X
```

can remain permanently true as an observation even when:

```text
X is the current value
```

can no longer be asserted.

Therefore freshness evaluation must not delete or mutate the historical record.

It only decides whether that record satisfies a request with a freshness requirement.

---

## 5. Failure Policy

Extend result/failure policy only as needed to classify reuse/retry behavior.

At minimum support clear policy for:

```text
deterministic failure for immutable inputs
transient/retryable failure
cancelled/incomplete work
```

Examples:

- parser rejects immutable invalid syntax -> deterministic and cacheable;
- network timeout -> transient and normally retryable;
- model request cancelled -> incomplete, not a successful reusable result.

Do not infer these categories from error-message text.

Selection policy must be able to exclude failures unless a caller explicitly asks to inspect them.

---

## 6. Retention Policy

In `retention.rs`, define retention categories equivalent to:

```text
Disposable
ReusableExpensive
HistoricalEvidence
Pinned
```

Names may differ if repository conventions suggest better terminology.

Retention answers:

> Should this artifact be kept when storage pressure or garbage collection policy runs?

It does **not** answer:

> Is this result still valid for a derivation request?

Keep these concepts separate in types and documentation.

### Reference strength

Represent whether a retained derived artifact should preserve its canonical inputs strongly enough for historical interpretation.

At minimum distinguish:

```text
WeakDependency
StrongPinnedDependency
```

or an equivalent mechanism.

Disposable cache dependencies must not automatically pin canonical history forever.

Pinned historical evidence may intentionally preserve required inputs.

Do not implement canonical garbage collection in this task.

---

## 7. Selection Evaluation

Implement a pure selection function or service that can evaluate a collection of immutable candidate records against a `SelectionPolicy`.

The function should:

1. filter incompatible profiles;
2. filter unusable status categories;
3. evaluate freshness when requested;
4. apply explicit producer/trust filter supplied by caller, if present;
5. rank remaining candidates according to requested preference;
6. return the exact selected result plus a structured reason;
7. return a structured no-match reason when nothing qualifies.

Do not query network sources or run derivations here.

Selection evaluates existing candidates only.

---

## 8. Public API

Expose equivalents of:

```text
SelectionPolicy
SelectionOutcome
SelectionReason
FreshnessPolicy
FreshnessState
RetentionPolicy
RetentionStrength
```

Reuse the existing result status/failure types rather than duplicating them.

Public docs must state that none of these operations modify canonical snapshots.

## Required Tests

Add tests for at least:

1. exact-profile selection;
2. preferred-profile selection among two immutable results;
3. newest-result selection without mutating older results;
4. failed result excluded from normal success selection;
5. deterministic failure remains inspectable;
6. transient failure remains retryable by policy;
7. immutable local result never expires only because time passes;
8. external observation is fresh before its policy deadline;
9. same observation is stale after the deadline but remains historically retrievable;
10. revalidation-required outcome is representable;
11. disposable retention is distinct from validity;
12. pinned retention is representable;
13. weak cache dependency does not imply canonical-history retention;
14. changing preferred selection does not call or modify canonical snapshot APIs.

Tests must use test-domain profile names only.
