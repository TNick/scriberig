## 2. Conformance Scenario: Local Reuse

Create a local derived result:

```text
Entity F @ Revision R1
+ summary profile P1
-> Result S1
```

Then simulate an unrelated entity changing:

```text
Entity G @ Revision G1 -> G2
```

Assert:

- the global test snapshot may differ;
- the local derivation key for `F@R1` does not change;
- `S1` remains reusable;
- reuse explanation states that exact dependencies still match.

This is the primary proof of local reuse despite global change.

---

## 3. Conformance Scenario: Global Dependency

Create a derivation explicitly depending on `Snapshot S1`.

Change canonical state so the scope is represented by `Snapshot S2`.

Assert:

- the derivation key changes;
- the old result remains historically retrievable;
- it does not satisfy the new snapshot-bound request;
- explanation identifies the snapshot dependency change.

This proves that conservative whole-scope dependencies remain valid when deliberately chosen.

---

## 4. Conformance Scenario: Scope/Absence Dependency

Model:

```text
query: all members matching condition Q
old positive members: A, B
```

Add a new matching member `C` without changing `A` or `B`.

Assert that the cached complete-result derivation is affected because the declared scope dependency changed.

This test must not rely on positive dependencies alone.

## 5. Conformance Scenario: Style-Only Change

Create:

```text
semantic summary depends on Entity F@R1
render result depends on F@R1 + Style ST1
```

Change only style/configuration to `ST2`.

Assert:

- semantic summary remains reusable;
- old render result does not satisfy the `ST2` request;
- no semantic revision change is needed for this test;
- explanation names the configuration/style dependency.

---

## 6. Conformance Scenario: Hierarchical Derived Reuse

Create:

```text
F1@A -> Summary SF1
F2@B -> Summary SF2
SF1 + SF2 -> ModuleSummary M1
```

Change only `F2@B` to `F2@C` and create `SF2C`.

Assert:

- `SF1` is reused;
- old `SF2` remains historical;
- the new module summary depends on `SF1 + SF2C`;
- the old module summary remains historical and is not mutated;
- reverse dependency traversal can identify the old module summary as affected for a new-state request.

## 7. Conformance Scenario: Fresh External Observation

Create an external-observation-like derived record with:

```text
source X
observed at T1
fresh until T2
```

Assert:

- before `T2`, freshness policy accepts it;
- after `T2`, it no longer satisfies a current/fresh request;
- the exact historical observation remains retrievable;
- no canonical snapshot operation is performed by freshness evaluation.

Use a deterministic test clock or explicit timestamps passed into evaluation. Do not sleep in tests.

---

## 8. Conformance Scenario: Multiple Model-Like Results

Using a fake nondeterministic summary profile, store two different result artifacts for one exact derivation key.

Assert:

- both immutable results remain present;
- exact key lookup returns both;
- selection policy can choose one according to a stated rule;
- changing the preferred selection does not rewrite either artifact;
- no canonical snapshot changes.

Do not invoke a real model.

## 9. Conformance Scenario: Failure Reuse Policy

Create:

- one deterministic failure for immutable input;
- one transient failure for the same or another request.

Assert:

- deterministic failure may be recognized as reusable/inspectable according to explicit policy;
- transient failure does not incorrectly block retry forever;
- failure behavior is based on structured status, not error-message parsing.

## 10. Conformance Scenario: Retention Strength

Create one disposable result with weak dependencies and one pinned historical result with strong retention semantics.

Assert at the policy/model level:

- disposable validity does not imply strong canonical retention;
- pinned historical evidence can request strong retention;
- validity and retention categories are independently inspectable.

Do not run canonical GC.

## 13. Public Documentation

Update crate-level and module-level docs so a library user can understand the following without reading implementation source:

### Canonical vs derived

State clearly:

> Derived results may share storage with canonical knowledge but do not participate in canonical snapshot identity unless explicitly promoted through the normal canonical change model.

### Exact reuse

State clearly:

> Reuse is based on exact declared dependencies and derivation semantics, not `EntityId` alone and not filename timestamps.

### Global vs local

Document:

```text
SnapshotId -> did anything canonical change in the scope?
DerivationKey/dependencies -> does this specific result still apply?
```

### Scope completeness

Explain why queries claiming `all`, `none`, or completeness need scope dependencies.

### Freshness

Explain that external observations may become stale for current-information requests while remaining exact historical observations.

### Retention

Explain that retention and validity are independent.

### Agents

State that the crate has no agent dependency and is useful to ordinary library consumers.
