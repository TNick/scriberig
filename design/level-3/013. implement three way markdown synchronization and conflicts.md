# Implement: Three-Way Markdown Synchronization and Conflicts

## Objective

Extend Markdown/file synchronization to the normal concurrent case where canonical state changed after the last synchronized file was rendered.

Implement semantic three-way reconciliation using:

```text
B = synchronization base
D = current canonical state
F = externally edited Markdown
```

The result must merge disjoint semantic changes automatically and return structured conflicts for incompatible overlapping changes.

## Three-way preparation

For an externally changed file:

1. parse `F` into a candidate;
2. reconstruct/read the exact semantic scope from synchronization base `B`;
3. reconcile candidate against `B` to derive the external semantic intent `B -> F_semantic`;
4. obtain canonical change `B -> D` using `sr-change`/snapshot diff;
5. combine both changes through generic merge first;
6. invoke Markdown-specific resolution only for conflicts that require document semantics.

Do not match `F` directly against only `D` because that loses the edit base and can misinterpret concurrent movement/changes.

## Automatic merge rules

At minimum automatically merge:

- canonical change to entity A plus external change to unrelated entity B;
- canonical text change to paragraph P1 plus external insertion P3 in a different collection/location when structurally independent;
- both sides producing the same resulting revision;
- independent insertions at non-competing collection positions;
- style/formatting-only external change plus semantic canonical change;
- path/projection-location-only change when domain semantics say location is non-semantic.

## Conflict cases

Return structured conflicts for at least:

- both sides changing the same paragraph text differently;
- one side removing a projected entity while the other modifies it;
- competing incompatible reorder/collection edits;
- ambiguous identity matching that prevents safe external intent construction;
- incompatible heading/section restructuring;
- external edit based on a synchronization base that is no longer retrievable.

Use the universal `sr-change` conflict object as the authoritative base/result conflict model. Add Markdown domain detail through its extension/domain-detail mechanism.

## Conflict detail

Markdown conflict detail should be able to expose:

- affected semantic entity/collection;
- base revision;
- canonical/current revision;
- external candidate/proposed revision;
- candidate source span for presentation only;
- operation kind: text update, insertion, removal, move, restructure, ambiguity;
- possible resolutions when deterministic alternatives are known.

Do not write conflict marker text into the canonical Markdown document as the conflict representation.

## Formatting-only external edit during canonical change

If the external file differs from B only by presentation but D contains semantic changes:

- do not generate an external semantic migration;
- render D using configured style;
- write result;
- advance synchronization base to D after successful write.

Add an explicit test for this path.

## Successful merge path

If merge succeeds:

```text
B + D + F
    -> merged migration/result snapshot M
    -> validate Markdown result
    -> promote through normal change/root rules
    -> deterministic Markdown render
    -> atomic file write
    -> synchronization base = promoted snapshot
```

Do not advance synchronization base until promotion and rerender/write succeed.

If promotion fails because the target root changed again, restart reconciliation from the preserved external input/new current state rather than silently overwriting.

## Failed/conflicted path

On conflict:

- preserve last valid canonical root;
- preserve original synchronization base;
- preserve external digest/content access;
- set projection state to conflict/attention-required;
- store structured conflict diagnostics;
- do not normalize/rewrite the external file unless policy explicitly requests a preview/alternate output;
- allow retry after canonical or external state changes.

## Stale base handling

If B was garbage-collected or cannot be resolved, do not guess a two-way merge.

Return a structured `MissingSynchronizationBase`/equivalent error requiring user/system policy to re-establish a baseline or perform a consciously lossy import.

## Validation

Before promotion of merged state:

- validate universal schema invariants;
- validate Markdown domain structure;
- render resulting Markdown;
- parse rendered Markdown;
- verify semantic equivalence for the supported projection surface.

Validation failure leaves current canonical state unchanged.

## Tests

Cover at least:

- canonical modifies P1, external inserts P3 elsewhere -> merge succeeds;
- canonical inserts one paragraph, external inserts another at independent location -> merge succeeds;
- both change P1 to same semantic text -> converges;
- both change P1 differently -> structured conflict;
- canonical removes P1, external modifies P1 -> delete/modify conflict;
- canonical semantic change plus external formatting-only change -> no external semantic delta and canonical change renders successfully;
- competing section reorder -> structured collection conflict;
- ambiguous external duplicate matching -> conflict/ambiguity preserved;
- promotion race after reconciliation -> no overwrite; retry required;
- missing synchronization base -> explicit error;
- successful merge rerenders and establishes new base.

## Do not do

- Do not replace current canonical state with parsed file content.
- Do not use textual Git-style conflict markers as canonical conflict state.
- Do not advance the base before successful promotion/rerender.
- Do not silently two-way merge when B is missing.
- Do not let filesystem layer invent Markdown conflict semantics.
- Do not add agent-assisted conflict resolution in this task.
