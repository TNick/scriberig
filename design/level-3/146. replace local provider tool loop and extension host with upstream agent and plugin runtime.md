**Status: [ ] In Progress**

pin the controlled `TNick/pi-rust` fork at
`15a68ef2d69a312122c09c1eccfa0fbd454c48b5`. It includes official upstream
`bigfish1913/pi-rust` main commit `7d019f85cde614a6aa267a7d2e816e04a7e6abbe`.
Older revision references below are historical implementation checkpoints.

commit `7a272ec`). Its reusable provider ABI is in `rpi-plugin-sdk`; generic
package lifecycle helpers are in `rpi-extensions`. The earlier fork-only
`rpi-provider-runtime` wrapper was removed. Historical sections below that
name earlier revisions or owners should be read as checkpoints.

Invocation adapter update (2026-10-21): `ToolCatalog` no longer performs
generic argument-shape or required-field validation. Its `authorize` methods
only resolve registered ScribeRig tool names and enforce branch capabilities;
`rpi-agent` validates arguments against the supplied JSON Schema before calling
`SemanticAgentTool::execute`, and owns call lookup, settlement, and late-update
handling. The adapter still rechecks the trusted descriptor and branch
capability before executing the semantic callback. It bounds provider-visible
results by dropping images, structured details, and dynamic tool additions,
and caps text at 16 KiB; those are ScribeRig result-projection safeguards, not
generic call settlement. ScribeRig's semantic descriptors and scenario
responses use upstream `rpi_ai::types::Tool` and `ToolCall` directly; the local
field-for-field schema and call types and conversion code were deleted. The
`cargo check -p scriberig --bin srig` passes at the active pin. Focused
behavior verification is deferred, so the matching acceptance item remains
unchecked.

## 4. Define the Branch Execution Adapter

One active Scriberig branch/executor context should drive one upstream agent-loop instance or equivalent upstream execution context.

Scriberig supplies:

```text
compiled effective context
resolved upstream model execution selection
allowed tool set
branch-local cancellation
runtime budget decisions that remain Scriberig-specific
semantic activity correlation
```

Upstream supplies:

```text
provider invocation mechanics
assistant streaming
provider tool-call parsing
tool schema validation
ordinary tool-call settlement/order
loop continuation
cancellation mechanics
agent events
```

Acceptance:

- [ ] Branch identity remains Scriberig identity.
- [ ] Upstream agent instance/session identifiers are not used as Scriberig `SessionId`/`BranchId`.
- [ ] One branch can select a different upstream provider/model than a sibling.
- [ ] Parent/child context isolation is determined before upstream execution begins.

## 5. Preserve Scriberig Context Compilation

Do not let upstream transcript/session history become the source of Scriberig context.

The execution flow remains:

```text
Scriberig branch state
  -> Scriberig context compiler
  -> canonical safe effective request/context
  -> upstream agent/provider execution
```

If upstream agent state internally retains current-branch messages for loop mechanics, treat that state as disposable branch-local execution state.

Acceptance:

- [ ] Scriberig context compiler remains authoritative.
- [ ] Child context is selected from Scriberig state, not copied from upstream parent transcript.
- [ ] Parent resumes from selected `BranchResult`s, not child upstream transcript.
- [ ] Full prompt/effective request inspection remains provider-neutral Scriberig state.

## 6. Adapt Scriberig Semantic Operations to `AgentTool`

Create a narrow tool adapter around public Scriberig semantic/application operations.

Each adapter maps:

```text
Scriberig operation/capability descriptor
  -> upstream AgentTool schema/label
  -> validated upstream tool call
  -> Scriberig capability check
  -> shared Scriberig application operation
  -> bounded semantic result projection
  -> upstream AgentToolResult
```

Do not duplicate upstream generic tool-call validation or settlement.

Acceptance:

- [ ] Tool JSON-schema validation is upstream-owned where upstream provides it.
- [ ] Unknown provider-returned tool names cannot bypass the advertised tool set.
- [ ] Scriberig capability checks run before semantic execution.
- [ ] Canonical mutations still use candidate/migration/validation/promotion.
- [ ] Tool result projections retain stable Scriberig result handles where exact state matters.

## 7. Branch-Producing Tool Calls

Retain Scriberig's atomic-vs-child-branch distinction.

For branch-producing work:

```text
upstream tool call
  -> Scriberig creates child branch
  -> compile selected child context
  -> run child through upstream agent loop
  -> finalize durable BranchResult
  -> return compact BranchResult projection as upstream tool result
```

Acceptance:

- [ ] Child branch is durable before its first model invocation.
- [ ] Child may use a different upstream execution selection.
- [ ] Parent receives compact result rather than child transcript.
- [ ] Nested recursion obeys Scriberig budgets/policy.
- [ ] A failed/cancelled child returns structured Scriberig branch outcome.

## 8. Delegate Provider Wire Implementations

Remove or retire Scriberig-owned generic provider HTTP implementations when upstream covers the required protocols.

Scriberig should not maintain its own OpenAI-compatible/Anthropic request serialization in parallel with upstream.

If Scriberig needs a missing provider feature, implement it in the controlled
`TNick/pi-rust` fork's `rpi-ai` provider API and consume it only after pinning
the reviewed fork commit. Upstream-main merge status and GitHub issue filing
are not prerequisites for this dependency direction.

### Provider composition and protected-auth gate

At the current fork pin `15a68ef2d69a312122c09c1eccfa0fbd454c48b5`, `rpi-ai`
exposes reusable concrete provider implementations under
`rpi_ai::providers`; this pin includes the earlier extraction commit
`3ae8416ceaf2dcdbf853b03c7b4662ad832497cf`. The current pin also exposes
`rpi-model-runtime/src/provider_factory.rs` with
`create_builtin_provider`/`create_builtin_provider_for_api` for resolved
built-in provider/model sets. This removes the upstream factory extraction
blocker for built-in APIs. It does not discover providers, resolve extension
providers, or compose CLI configuration, auth-store policy, package manifests,
and model rows; those remain in `rpi-cli/src/provider/factories.rs` and
`rpi-cli::provider::resolve_with_extensions`. ScribeRig must not call that CLI
resolver or recreate its auth/package policy in
`native_tui_agent/provider_config.rs`. ScribeRig's native root and plan worker
now use the upstream built-in factory after exact model resolution, while
retaining host-owned authorization and provider-independent configuration
policy. Keep package installation and CLI configuration policy in their
existing owners.

At the pinned revision, built-in OpenAI Completions, OpenAI Responses, and
Anthropic implementations expose combined protected-request-secret and
applied-settings forwarding. `rpi-extensions::PluggableProvider` also forwards
protected credentials to extensions that opt into the versioned protected ABI;
legacy providers fail closed. Its versioned applied-settings callback accepts
safe provider attestation, while providers without attestation produce an
explicitly incomplete report after the extension attempt settles. Built-in
reports project allowlisted values from the post-transformation request body
and remain incomplete because they omit request-affecting categories. These
upstream APIs are available but ScribeRig has not yet routed its active
provider calls through them or persisted the reports. Do not infer application
from catalog metadata or `providerOptions` transport alone.

The ScribeRig host bridge must be created per invocation and bind the exact
resolved provider/model, immutable catalog/config snapshot, effective endpoint,
selected `scriberig_secrets::SecretRef`, and `SecretUseContext`. It must call
`AuthorizedCredential::credential` only after binding that destination, wrap
the resulting `SecretValue` as `rpi_ai::SecretMaterial`, and pass it only via
`RequestSecret`. Override upstream
`ProtectedCredentialResolver::resolve_with_policy` so authorization or
resolution errors become `CredentialResolutionError` and stop precedence;
never translate them to a source miss or route through ordinary-string
`AuthStore`, `SimpleStreamOptions.api_key`, model headers, or plugin JSON.

The native TUI root, one-shot, and plan-worker paths create an upstream
provider for the exact selected catalog model and run it through
`run_upstream_branch_invocation` with the scoped ScribeRig semantic broker.
The broker retains branch identity, compiled context, semantic authorization,
recursive child creation, request projections, and tool evidence. Deterministic
scenarios are being adapted as upstream `FauxProvider` scripts that produce
upstream `AssistantMessage` values. Configured built-in providers use their
upstream implementations and protected credentials. Native provider
extensions are rejected at startup until upstream supplies an isolated
worker/IPC boundary.
The ScribeRig-local generic agent loop, provider decision bridge, response
cache, and generic provider connection-check path have been removed. Every
branch runs through the shared upstream loop and semantic broker. The previous
runtime test files were broadly deleted during this migration, including
`nested_branches.rs`, `provider_profile_provenance.rs`, and
`runtime_request_history.rs`. App-level `native_tui_agent_tests/decomposition.rs`
now exercises recursive durable branches, compact results, child context
isolation, and request ordering through the upstream runner. Existing
`agent_context_tests.rs`, `native_tui_agent_tests_part1.rs`, coordinator, and
plan tests retain root/non-root context activation, exact continuation anchors,
durable dependency scheduling, and result semantics. A focused upstream
request-projection test now checks that a ScribeRig provider profile remains
provenance and affects ScribeRig request identity without entering
provider-visible content. The upstream-backed failure scenario now asserts
that its prepared request is retained on the durable failed invocation.
The provider fixtures now use upstream faux scripts, and request assertions read
the durable ScribeRig model-invocation projections. Compilation is pending the
shared model-catalog API integration; runtime verification remains deferred. Do
not restore tests of the removed generic local loop.

The generic request/response DTOs, provider trait, fake provider, and local
upstream translation bridge have been removed from production. ScribeRig's
compiled context message representation now lives under `context`, and
`provider::HostConfigurationError` is limited to host configuration and
ScribeRig scenario diagnostics. The `NativeScenario` wrapper and bootstrap,
arithmetic, PHP self-hosting, and app test scenarios consume upstream
`Context`/`Model` and `FauxProvider`/`AssistantMessage`. Doctor diagnostics map
stream failures to the upstream failure boundary without recreating provider
transport/authentication classifications. Compilation of the integrated
catalog path remains pending. Do not restore the deleted generic provider loop
or DTOs to make these paths compile.

The `CredentialSource::Authorized` created by the shared provider
configuration is now offered to each selected built-in model, including
non-local catalog rows. The protected bridge resolves it only after the exact
selected model endpoint is known and wraps it as `RequestSecret`; the live
`AuthorizedCredential` policy rechecks its `SecretRef`, endpoint, project root,
purpose, and execution mode before reading. A denied or failed resolution
stops the upstream invocation and is not converted to an unauthenticated
request. Catalog-supplied credentials and headers remain rejected. A catalog
row that needs a distinct credential reference cannot yet supply one through
the native model-selection path; that remains a `TEMPORARY` configuration
gate. Remove it only after host-owned per-connection configuration binds a
specific `SecretRef` and `SecretUseContext` to that selected model endpoint.
Applied-settings callbacks are captured on the current request projection, but
the report persistence/API boundary still needs focused verification. Upstream
stream failures now remain at the upstream invocation boundary; doctor reports
only distinguish host configuration from an upstream check failure rather
than recreating provider transport/authentication classes. Focused behavior
verification and distinct per-model credential-reference configuration remain
open.

The `inspect` semantic operation still uses the non-cancellable
`Tool::invoke` path. It addresses one entity at an exact or current snapshot
and returns bounded compact/detailed output, but the synchronous application
query boundary does not accept a cancellation token. Cancellation therefore
stops the broker and provider loop but cannot interrupt an inspect query after
that query has started. Add a cancellable query operation before claiming
per-tool cancellation for inspect.

Acceptance:

- [x] Active provider requests use upstream provider implementations.
- [x] Scriberig runtime no longer owns generic provider HTTP request shaping for supported providers.
- [ ] Provider errors are mapped into Scriberig public runtime error categories through a thin adapter.
- [x] Credential handling stays upstream/runtime-secret and is never persisted in session state.

## 9. Provider Continuation Split

Preserve Level-1 document 020.

Scriberig owns:

```text
branch-to-continuation association
context fingerprint
stale/reseed decision
provider-neutral provenance
```

Upstream owns:

```text
provider-specific continuation handles
wire request fields
provider continuation API mechanics
provider protocol errors
```

The pinned `TNick/pi-rust` revision `46ea1250bd695540b7f0b395afd6e10518fc05ff`
provides an opaque, non-serializable, debug-redacted `rpi_ai::ProviderContinuation`
scoped to provider/model, plus `Provider::continuation_from_response` and
`stream_simple_with_continuation`. `rpi-agent` exposes a continuation-aware
stream callback, extraction callback, and `Agent::set_provider_continuation`.
These APIs do not own ScribeRig branch identity or context validity. No concrete
`rpi-ai` provider currently implements continuation extraction or consumption.
The provider method also accepts no `Context`, protected `RequestSecret`, or
applied-settings callback; it therefore cannot carry the next user message or
preserve the current ScribeRig credential/report path. Deferred response
polling IDs do not satisfy provider continuation.

Acceptance:

- [x] Pin the fork commit containing the continuation API and `rpi-agent`
  `AgentBuilder`/`Agent` seam before ScribeRig consumes it.
- [ ] At least one required provider implements extraction and continuation;
  unsupported providers fail closed and use ScribeRig replay/reseed behavior.
- [ ] ScribeRig associates handles with canonical branch and context
  fingerprints, clears them on divergence, and never uses them as session
  identity.
- [ ] Provider-specific continuation support is not reimplemented as ScribeRig
  HTTP code.
- [ ] Losing upstream continuation does not make a ScribeRig branch unrecoverable.

The API pin criterion is satisfied. The preceding limitations describe the
earlier `46ea125` snapshot. At ScribeRig's current `0f50101` pin, the audited
continuation API accepts the current `Context`, optional protected
`RequestSecret`, and required applied-settings callback. OpenAI Responses
implements extraction and audited continuation, and advertises this support
through `Provider::supports_response_continuation()`; the trait default is
false. Its opaque provider/model-scoped handle is validated against the
provider's private state type. The request builder supports a fresh context
without the previous assistant response object and retains legacy anchor
behavior when that object is present. The host must validate context/branch
lineage because provider/model scope cannot prove it. ScribeRig has not yet
implemented its in-memory branch/context handle store or verified stale,
failure, and reseed behavior, so those continuation criteria remain unchecked.
No upstream GitHub issue filing or upstream-main merge is a gate.

The long-lived native TUI root runner now keeps the opaque continuation in
process memory under canonical root-branch identity. It checks provider,
resolved model, connection profile, thinking level, provider/model scope, and a
versioned fingerprint covering the compiled provider context, exact profile
and active component revisions, dependency/omission identities, and effective
semantic grants. Divergence removes the cached handle and replays from
canonical ScribeRig branch state. The handle is not persisted or projected.
Child branches, plan workers, one-shot CLI runs, and server-scoped invocations
remain stateless. The continuation result is compiled, but no tests have been
run; behavioral acceptance, including failure/reseed behavior, remains
unchecked until the requested final validation phase.

## 10. Adopt Upstream Plugin ABI and Extension Host

Use `rpi-plugin-sdk` and `rpi-extensions` for integrated agent-product plugins.

Do not create or preserve a parallel Scriberig ABI for:

```text
agent tools
providers
slash commands
agent event handlers
Markdown renderers
agent resources
```

Acceptance:

- [ ] Upstream extension loader owns discovery/loading of configured provider extensions.
- [ ] Upstream plugin version negotiation/ABI is used.
- [ ] Registered provider plugins become selectable through the same extension session.
- [ ] Scriberig does not re-load the same extension through another registry.

At the current ScribeRig fork pin
`15a68ef2d69a312122c09c1eccfa0fbd454c48b5`, extension tool loading and
invocation are reusable from `rpi-extensions`, not trapped in the CLI:
`RegistrySnapshot::tools()` exposes `ExtensionTool { tool, handle, origin }`,
`ExtensionSession::keepalive()` retains loaded libraries, and
`PluginToolAdapter` implements upstream `rpi_agent::AgentTool`. The adapter
offers a host-stamped origin and a pre-execution authorization callback.
`PluginToolAdapter::from_registered` fails closed until a host policy is
installed; `from_registered_authorized` preserves origin and policy together.
These support host-mediated authorization, but do not provide process
isolation or prevent native code from accessing ambient host resources.

ScribeRig currently fails closed before loading a configured native provider
extension. `apps/scriberig/src/native_tui_agent/provider_config/extensions.rs`
checks `SCRIBE_AGENT_EXTENSION_DIRS` and `SCRIBE_AGENT_PACKAGE_ROOTS` and
returns a configuration error when either selects native code. The pinned
loader uses in-process `libloading`, so the former trusted-code opt-in could
not enforce the canonical-knowledge invariant. The extension-consumption
criteria above remain unchecked until an upstream isolated worker/IPC API is
pinned and consumed; the no-duplicate-load criterion is also unchecked while
ScribeRig has no active extension loader.

The same pin exposes reusable project-package operations from
`rpi-extensions`: `read_project_registry`, `write_project_registry`,
`project_package_resource_dirs`, `install_project_artifact`, and
`uninstall_project_package`. The install API activates an already-built
artifact under a host-selected project root; it does not build, download, or
authorize the project root. Resource paths are lexically composed after
registry/name validation, so the host still owns root authorization and any
canonical-path or symlink policy. The library also exposes provider-reload
predicates and provider-set composition, but not a complete extension-session
swap with catalog reconciliation and active-provider handling. Build/link,
update acquisition, and live extension reload/session swap remain in
`rpi-cli`. ScribeRig should delegate registry and artifact operations to the
library if it adds package controls; it must retain host root authorization
and should not duplicate CLI build/update or session-swap orchestration.

### Package lifecycle boundary

The ScribeRig provider adapter at
`apps/scriberig/src/native_tui_agent/provider_config/extensions.rs` now rejects
process-selected extension directories/package roots before loading any
native code. It does not call `package_resource_dirs` or `load_session`, and it
does not read or write a project registry, install/uninstall artifacts,
build/update packages, or reload a live extension session. The one-shot path
uses the same fail-closed gate. ScribeRig has no local package manager or
duplicate registry/artifact lifecycle implementation to remove.

Do not add package controls as part of provider-extension discovery. If a
product requirement later calls for project package management, ScribeRig must
authorize the selected project root first and call the upstream registry,
resource, install, and uninstall APIs. Upstream must expose reusable build and
update acquisition plus an atomic extension-session/catalog replacement seam
before ScribeRig offers build/update/reload controls. Until then, retain the
current startup adapter and leave package controls absent; do not use
`rpi-cli` command handlers as a library boundary or recreate them in ScribeRig.

## 11. Apply Scriberig Trust and Capability Policy to Plugins

Using the upstream plugin host does not mean granting unrestricted semantic authority.

Add a Scriberig host-policy adapter that can:

```text
allow/deny a registered tool for the current branch
limit semantic scopes
require explicit approval for fallback filesystem/shell authority
prevent direct canonical semantic mutation outside public operations
hide unavailable capabilities from model context
```

Do not fork the loader to implement policy if upstream exposes hooks/filtering. If necessary, contribute generic host-policy hooks upstream.

At the current pin, `ExtensionToolOrigin` supplies host-stamped registration
identity and `PluginToolAdapter::with_pre_execute_authorizer` can deny a
host-mediated call before native execution. ScribeRig still does not pass
registered extension tools to `rpi-agent`. This is an explicit deny-by-default
boundary in product code: `UpstreamBranchInvocation.tools` accepts only
`SemanticAgentTool`, and `upstream_execution::build_tools` constructs that
vector only from capability-filtered `ToolCatalog` descriptors. An
`ExtensionTool` or `PluginToolAdapter` cannot enter the branch tool list. Do
not widen this type or merge extension schemas into the broker while plugins
execute in process.

After upstream isolation exists, a bridge must bind the worker's host-stamped
extension/tool identity to a ScribeRig capability, authorize against the
immutable branch capability snapshot before dispatch, and route approved
operations through the ScribeRig broker for activity/evidence. The worker must
not receive database paths, canonical-store handles, or unrestricted runtime
actions. The current authorization callback is only a host-mediated call gate;
it cannot stop native code from opening canonical files or using other process
APIs directly.

The pinned `rpi-extensions/src/loader.rs` still uses `libloading` to map
cdylibs into the host process. Withholding ScribeRig store handles and omitting
`ToolCallContext` or runtime-action bridges reduces host-mediated authority,
but does not prevent trusted native code from opening canonical store files or
calling other process APIs directly. The direct-mutation acceptance item
requires an upstream isolated worker/IPC host with a capability-scoped host
API. Until that API is implemented, pinned, and consumed, keep native
extension loading disabled, keep plugin tools absent from ScribeRig agent tool
sets, make no containment claim, and leave the direct-mutation item unchecked.
This is a fork contribution gate, not a reason to create a second ScribeRig
plugin ABI or loader.

Acceptance:

- [ ] Loaded does not imply authorized.
- [ ] Plugin tools visible to the model match branch capability policy.
- [ ] Plugin tools cannot directly mutate Scriberig database state through the integration API.
- [ ] Raw file/shell tools remain fallback capabilities and are not automatically preferred for understood domains.

## 14. Preserve Model Observability

The upstream loop may serialize requests differently, but Scriberig must still retain the canonical safe effective request before provider serialization.

Provider-applied settings are a separate observation from the canonical
ScribeRig request projection. Consume upstream `AppliedRequestSettings` only
from the final provider preparation callback; do not infer application from
catalog/execution-configuration metadata or the `providerOptions` envelope.
Persist the schema version, allowlisted values, omitted categories, and
`complete` status with the canonical invocation. Built-in reports and
extension fallbacks are intentionally incomplete; they do not replace the
full safe ScribeRig prompt/context projection.

Acceptance:

- [ ] Full prompt means complete safe Scriberig effective context, not upstream HTTP body.
- [ ] Any provider applied-settings report is captured from the final provider boundary and persisted with its explicit omissions and completeness; catalog metadata alone is never reported as applied.
- [ ] Provider-visible reasoning is captured only when upstream/provider exposes it for user/application consumption.
- [ ] Hidden chain-of-thought remains unavailable.
- [ ] Prompt/reasoning presentation settings do not alter upstream execution.

Implementation in progress: `UpstreamBranchInvocation` now always installs the
upstream `AppliedRequestSettingsCallback` on the provider stream. It stores the
upstream report as opaque JSON on that request's durable
`ModelRequestProjection`, while forwarding to any caller callback. The report
is returned only through the existing authorized model-request detail
operation and rendered as an upstream-owned report in the web activity view.
Catalog values are not used to fabricate this report. The acceptance item
remains unchecked until focused persistence/API verification is complete.

## 19. Implementation Notes

Record upstream versions/commits, upstream contribution references, and any deliberately retained adapter responsibilities.

The configured one-shot OpenAI-compatible CLI path now creates an upstream
`rpi-model-runtime` provider and delegates the turn through the shared
`native_tui_agent::upstream_execution` semantic broker. The CLI still owns
credential-source resolution and endpoint authorization; the broker preserves
the canonical session/branch, compiled ScribeRig context, semantic tool
authorization, child results, bounded request projections, and streamed text
callback. Deterministic local provider scenarios used by native root execution
adapt to `rpi_ai::Provider` and run through the same upstream semantic broker.
Plan-worker execution now uses `execute_precompiled_branch`, which invokes the
same upstream semantic broker as root execution. Recursive delegate calls use
that broker to create, execute, and finalize child branches with bounded
request projections and tool evidence. The old `LocalChildExecutor` and local

#### Plugin/package ownership audit (2026-10-21)

The current pinned `rpi-extensions` API in fork commit
`15a68ef2d69a312122c09c1eccfa0fbd454c48b5` supplies the `rpi-plugin-sdk` ABI,
`load_session`/`ExtensionSession`, `RegistrySnapshot`/`ExtensionTool`, and
`PluginToolAdapter`. The loader uses `libloading::Library` in the ScribeRig
process. `PluginToolAdapter::from_registered_authorized` and
`with_pre_execute_authorizer` can gate host-mediated calls, but cannot prevent
plugin code from opening ScribeRig's database or using ambient process APIs.
An ordinary child process is not enough: it needs OS-enforced access limits
that keep canonical storage and secrets unavailable except through explicit
host-mediated capabilities.

The same upstream crate exposes project-registry read/write, resource-root
discovery, activation of a prebuilt artifact, and uninstall APIs. These are
metadata/artifact operations, not a package build/download service or an atomic
extension-session plus model-catalog generation swap. Root authorization,
symlink/canonical-path policy, acquisition, and in-flight generation lifetime
remain host/lifecycle concerns. ScribeRig has no local plugin ABI, loader,
package registry, installer, or updater. `apps/scriberig/Cargo.toml` therefore
no longer declares a direct `rpi-extensions` dependency while the production
host deliberately does not load extensions. Cargo.lock retains the crate as
an upstream transitive dependency of `rpi-agent` at the same fork revision.

The exact upstream contribution gate is a reusable isolated plugin worker
contract in `rpi-extensions`/`rpi-plugin-sdk`: a versioned serialized tool
protocol, cancellation and worker-lifetime handling, a host capability RPC
surface, and a host-injected OS sandbox launcher whose contract denies direct
canonical-store and secret access. The `rpi-agent` adapter must expose only
registered tools whose host-stamped identities can be authorized against the
immutable ScribeRig branch capability snapshot and dispatched through the
semantic broker. A later lifecycle contribution must atomically replace the
extension session and catalog while active invocations retain the old
generation. The current in-process ABI cannot safely meet these conditions;
keep `reject_in_process_extensions` and do not create a ScribeRig loader or
package manager as a substitute.

#### Tool ownership and capability audit (2026-10-21)

The production semantic tool path in `upstream_tool.rs` delegates schema
