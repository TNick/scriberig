## 4. Define the Branch Execution Adapter

One active Scriberig branch/executor context should drive one upstream agent-loop instance or equivalent upstream execution context.

Scriberig supplies:

```text
compiled effective context
resolved upstream model execution selection
allowed tool set
branch-local cancellation
runtime budget decisions that remain Scriberig-specific
semantic activity correlation
```

Upstream supplies:

```text
provider invocation mechanics
assistant streaming
provider tool-call parsing
tool schema validation
ordinary tool-call settlement/order
loop continuation
cancellation mechanics
agent events
```

Acceptance:

- [ ] Branch identity remains Scriberig identity.
- [ ] Upstream agent instance/session identifiers are not used as Scriberig `SessionId`/`BranchId`.
- [ ] One branch can select a different upstream provider/model than a sibling.
- [ ] Parent/child context isolation is determined before upstream execution begins.

---

## 5. Preserve Scriberig Context Compilation

Do not let upstream transcript/session history become the source of Scriberig context.

The execution flow remains:

```text
Scriberig branch state
  -> Scriberig context compiler
  -> canonical safe effective request/context
  -> upstream agent/provider execution
```

If upstream agent state internally retains current-branch messages for loop mechanics, treat that state as disposable branch-local execution state.

Acceptance:

- [ ] Scriberig context compiler remains authoritative.
- [ ] Child context is selected from Scriberig state, not copied from upstream parent transcript.
- [ ] Parent resumes from selected `BranchResult`s, not child upstream transcript.
- [ ] Full prompt/effective request inspection remains provider-neutral Scriberig state.

---

## 6. Adapt Scriberig Semantic Operations to `AgentTool`

Create a narrow tool adapter around public Scriberig semantic/application operations.

Each adapter maps:

```text
Scriberig operation/capability descriptor
  -> upstream AgentTool schema/label
  -> validated upstream tool call
  -> Scriberig capability check
  -> shared Scriberig application operation
  -> bounded semantic result projection
  -> upstream AgentToolResult
```

Do not duplicate upstream generic tool-call validation or settlement.

Acceptance:

- [ ] Tool JSON-schema validation is upstream-owned where upstream provides it.
- [ ] Unknown provider-returned tool names cannot bypass the advertised tool set.
- [ ] Scriberig capability checks run before semantic execution.
- [ ] Canonical mutations still use candidate/migration/validation/promotion.
- [ ] Tool result projections retain stable Scriberig result handles where exact state matters.

---

## 7. Branch-Producing Tool Calls

Retain Scriberig's atomic-vs-child-branch distinction.

For branch-producing work:

```text
upstream tool call
  -> Scriberig creates child branch
  -> compile selected child context
  -> run child through upstream agent loop
  -> finalize durable BranchResult
  -> return compact BranchResult projection as upstream tool result
```

Acceptance:

- [ ] Child branch is durable before its first model invocation.
- [ ] Child may use a different upstream execution selection.
- [ ] Parent receives compact result rather than child transcript.
- [ ] Nested recursion obeys Scriberig budgets/policy.
- [ ] A failed/cancelled child returns structured Scriberig branch outcome.

Remove or retire Scriberig-owned generic provider HTTP implementations when upstream covers the required protocols.

Scriberig should not maintain its own OpenAI-compatible/Anthropic request serialization in parallel with upstream.

`TNick/pi-rust` fork's `rpi-ai` provider API and consume it only after pinning

## 9. Provider Continuation Split

Preserve Level-1 document 020.

Scriberig owns:

```text
branch-to-continuation association
context fingerprint
stale/reseed decision
provider-neutral provenance
```

Upstream owns:

```text
provider-specific continuation handles
wire request fields
provider continuation API mechanics
provider protocol errors
```

Recorded at the historical `TNick/pi-rust` checkpoint
`46ea1250bd695540b7f0b395afd6e10518fc05ff` (an ancestor of the authoritative
current pin `587c63f3a521567b2ef8fe9ce038fd35e3896f15`, which still carries the
`rpi_ai::ProviderContinuation`, `Provider::continuation_from_response`, and
`stream_simple_with_continuation` surface), the fork provided an opaque,
non-serializable, debug-redacted `rpi_ai::ProviderContinuation` scoped to
provider/model. `rpi-agent` exposes a continuation-aware stream callback,
extraction callback, and `Agent::set_provider_continuation`. These APIs do not
own ScribeRig branch identity or context validity. At that checkpoint no
concrete `rpi-ai` provider implemented continuation extraction or consumption,
and the provider method accepted no `Context`, protected `RequestSecret`, or
applied-settings callback; it therefore could not carry the next user message
or preserve the ScribeRig credential/report path. Deferred response polling IDs
do not satisfy provider continuation.

Acceptance:

- [x] Pin the fork commit containing the continuation API and `rpi-agent`
  `AgentBuilder`/`Agent` seam before ScribeRig consumes it.
- [ ] At least one required provider implements extraction and continuation;
  unsupported providers fail closed and use ScribeRig replay/reseed behavior.
- [ ] ScribeRig associates handles with canonical branch and context
  fingerprints, clears them on divergence, and never uses them as session
  identity.
- [ ] Provider-specific continuation support is not reimplemented as ScribeRig
  HTTP code.
- [ ] Losing upstream continuation does not make a ScribeRig branch unrecoverable.

The API pin criterion is satisfied. The preceding limitations describe the
historical `46ea125` checkpoint. The audited continuation API was recorded at
the historical `0f501019a7be28a575fc5d8ed27f1f1ef47b2e6a` checkpoint, an
ancestor of the authoritative current pin
`587c63f3a521567b2ef8fe9ce038fd35e3896f15`. At that checkpoint the audited

## 10. Adopt Upstream Plugin ABI and Extension Host

Use `rpi-plugin-sdk` and `rpi-extensions` for integrated agent-product plugins.

Do not create or preserve a parallel Scriberig ABI for:

```text
agent tools
providers
slash commands
agent event handlers
Markdown renderers
agent resources
```

Acceptance:

- [ ] Upstream extension loader owns discovery/loading of configured provider extensions.
- [ ] Upstream plugin version negotiation/ABI is used.
- [ ] Registered provider plugins become selectable through the same extension session.
- [ ] Scriberig does not re-load the same extension through another registry.

Recorded at the historical ScribeRig fork checkpoint
`15a68ef2d69a312122c09c1eccfa0fbd454c48b5` (an ancestor of the authoritative
current pin `587c63f3a521567b2ef8fe9ce038fd35e3896f15`), extension tool loading
and invocation are reusable from `rpi-extensions`, not trapped in the CLI:
`RegistrySnapshot::tools()` exposes `ExtensionTool { tool, handle, origin }`,
`ExtensionSession::keepalive()` retains loaded libraries, and
`PluginToolAdapter` implements upstream `rpi_agent::AgentTool`. The adapter
offers a host-stamped origin and a pre-execution authorization callback.
`PluginToolAdapter::from_registered` fails closed until a host policy is
installed; `from_registered_authorized` preserves origin and policy together.
These support host-mediated authorization, but do not provide process
isolation or prevent native code from accessing ambient host resources.

ScribeRig currently fails closed before loading a configured native provider
extension. `apps/scriberig/src/native_tui_agent/provider_config/extensions.rs`
checks `SCRIBE_AGENT_EXTENSION_DIRS` and `SCRIBE_AGENT_PACKAGE_ROOTS` and
returns a configuration error when either selects native code. The pinned
loader uses in-process `libloading`, so the former trusted-code opt-in could
not enforce the canonical-knowledge invariant. The extension-consumption
criteria above remain unchecked until an upstream isolated worker/IPC API is
pinned and consumed; the no-duplicate-load criterion is also unchecked while
ScribeRig has no active extension loader.

The same pin exposes reusable project-package operations from
`rpi-extensions`: `read_project_registry`, `write_project_registry`,
`project_package_resource_dirs`, `install_project_artifact`, and
`uninstall_project_package`. The install API activates an already-built
artifact under a host-selected project root; it does not build, download, or
authorize the project root. Resource paths are lexically composed after
registry/name validation, so the host still owns root authorization and any
canonical-path or symlink policy. The library also exposes provider-reload
predicates and provider-set composition, but not a complete extension-session
swap with catalog reconciliation and active-provider handling. Build/link,
update acquisition, and live extension reload/session swap remain in
`rpi-cli`. ScribeRig should delegate registry and artifact operations to the
library if it adds package controls; it must retain host root authorization
and should not duplicate CLI build/update or session-swap orchestration.

### Package lifecycle boundary

The ScribeRig provider adapter at
`apps/scriberig/src/native_tui_agent/provider_config/extensions.rs` now rejects
process-selected extension directories/package roots before loading any
native code. It does not call `package_resource_dirs` or `load_session`, and it
does not read or write a project registry, install/uninstall artifacts,
build/update packages, or reload a live extension session. The one-shot path
uses the same fail-closed gate. ScribeRig has no local package manager or
duplicate registry/artifact lifecycle implementation to remove.

Do not add package controls as part of provider-extension discovery. If a
product requirement later calls for project package management, ScribeRig must
authorize the selected project root first and call the upstream registry,
resource, install, and uninstall APIs. Upstream must expose reusable build and
update acquisition plus an atomic extension-session/catalog replacement seam
before ScribeRig offers build/update/reload controls. Until then, retain the
current startup adapter and leave package controls absent; do not use
`rpi-cli` command handlers as a library boundary or recreate them in ScribeRig.

## 11. Apply Scriberig Trust and Capability Policy to Plugins

Using the upstream plugin host does not mean granting unrestricted semantic authority.

Add a Scriberig host-policy adapter that can:

```text
allow/deny a registered tool for the current branch
limit semantic scopes
require explicit approval for fallback filesystem/shell authority
prevent direct canonical semantic mutation outside public operations
hide unavailable capabilities from model context
```

Do not fork the loader to implement policy if upstream exposes hooks/filtering. If necessary, contribute generic host-policy hooks upstream.

At the current pin, `ExtensionToolOrigin` supplies host-stamped registration
identity and `PluginToolAdapter::with_pre_execute_authorizer` can deny a
host-mediated call before native execution. ScribeRig still does not pass
registered extension tools to `rpi-agent`. This is an explicit deny-by-default
boundary in product code: `UpstreamBranchInvocation.tools` accepts only
`SemanticAgentTool`, and `upstream_execution::build_tools` constructs that
vector only from capability-filtered `ToolCatalog` descriptors. An
`ExtensionTool` or `PluginToolAdapter` cannot enter the branch tool list. Do
not widen this type or merge extension schemas into the broker while plugins
execute in process.

After upstream isolation exists, a bridge must bind the worker's host-stamped
extension/tool identity to a ScribeRig capability, authorize against the
immutable branch capability snapshot before dispatch, and route approved
operations through the ScribeRig broker for activity/evidence. The worker must
not receive database paths, canonical-store handles, or unrestricted runtime
actions. The current authorization callback is only a host-mediated call gate;
it cannot stop native code from opening canonical files or using other process
APIs directly.

The pinned `rpi-extensions/src/loader.rs` still uses `libloading` to map
cdylibs into the host process. Withholding ScribeRig store handles and omitting
`ToolCallContext` or runtime-action bridges reduces host-mediated authority,
but does not prevent trusted native code from opening canonical store files or
calling other process APIs directly. The direct-mutation acceptance item
requires an upstream isolated worker/IPC host with a capability-scoped host
API. Until that API is implemented, pinned, and consumed, keep native
extension loading disabled, keep plugin tools absent from ScribeRig agent tool
sets, make no containment claim, and leave the direct-mutation item unchecked.
This is a fork contribution gate, not a reason to create a second ScribeRig
plugin ABI or loader.

Acceptance:

- [ ] Loaded does not imply authorized.
- [ ] Plugin tools visible to the model match branch capability policy.
- [ ] Plugin tools cannot directly mutate Scriberig database state through the integration API.
- [ ] Raw file/shell tools remain fallback capabilities and are not automatically preferred for understood domains.

#### Isolated worker cancellation and shutdown update (2026-10-21)

The current fork working tree now passes a `CancellationToken` into each
`PluginToolAdapter::execute` call. A host `Cancel` frame cancels the matching
token, and worker shutdown or input closure cancels all active tokens. The
worker joins calls that finish during a two-second settlement window and joins
its input-reader thread after the loop. This provides a cooperative cancellation
signal; it cannot safely preempt native plugin FFI that ignores the signal. Such
work may remain detached after the grace window, and the worker process must
exit to terminate it. Embedding `serve_worker` in a long-lived host process
would therefore risk retaining unfinished plugin threads.

The host request deadline is a hard fallback: it kills the supervised process
tree, marks the connection closed, and fails pending requests. Graceful host
shutdown waits about 500 ms before killing the tree, shorter than the worker's
two-second cooperative settlement window; in that path the process kill can
preempt the worker's own grace period. Cancellation has no worker acknowledgement
that a plugin call has stopped. Host capability RPC can block a plugin action
for up to its 60-second reply timeout, and shutdown frames cannot be handled
while synchronous plugin registration is still running. These are source-level
claims only: no build, tests, or runtime lifecycle verification has been run.
The fork changes are uncommitted and not in ScribeRig's pinned revision. Keep
plugin activation disabled until the fork API is reviewed, pinned, and verified
under runtime cancellation, timeout, and shutdown scenarios.

#### Provider continuation and context binding audit (2026-10-21)

Compared ScribeRig's root continuation cache and fingerprint checks with the
active upstream `ProviderContinuation` contract. Upstream handles are opaque,
non-serialized, and scoped to provider/model; `rpi-agent` exposes them through
its continuation extractor/callback and `Agent::set_provider_continuation`.
ScribeRig adds the separate branch and context validity binding in
`apps/scriberig/src/native_tui_agent/runner.rs` and
`upstream_execution/lineage.rs`. Cache entries are held only in the runner's
process-local map, keyed by root branch, and contain provider/model/profile,
thinking identity, a ScribeRig context fingerprint, and the opaque handle.
They are removed before each attempted turn, rejected on identity/fingerprint/
upstream-scope mismatch, and only reinserted after successful completion when
not cancelled. No provider handle is written into session, request projection,
or durable execution state; restart therefore reseeds from canonical ScribeRig
context.

The fingerprint is ScribeRig-owned rather than an upstream duplicate: it binds
compiled profile and active component revisions, dependencies, omitted handles,
provider context, and sorted capability/grant identity under the
`provider-continuation-v1` domain. The request projection separately fingerprints
the canonical compiled context for request identity. The root runner computes
its pre-use candidate fingerprint from the completed branch with the submitted
human turn omitted, while `execute_root_branch_with_continuation` recompiles
with the actual prompt and independently rechecks the supplied fingerprint
before passing the upstream handle. That is consistent with the prompt being
sent as the next upstream user message rather than baked into the prior
continuation context; provider/model scope itself remains guarded by upstream
and rechecked locally.

No concrete persistence or validation defect was established, so this audit
changes no runtime code and checks no acceptance items. The next executable
gate is focused lifecycle coverage at the owning runtime/app boundary: verify
same-root reuse, provider/model/profile/thinking and context divergence reseed,
cancelled or failed-turn non-reinsertion, branch isolation for child/plan
workers, and restart reseed. Then verify each advertised provider route either
extracts and consumes the opaque handle or cleanly remains stateless. Keep the
continuation acceptance criteria and Task 144 G7 unchecked until that evidence
exists; no tests or long checks were run for this audit.

#### Branch-scoped continuation follow-up (2026-10-21)

The current transient continuation implementation is intentionally root-only.
`NativeTuiAgentRunner::execute_accepted` removes and validates a cache entry
keyed by the accepted root branch, and reinserts the opaque upstream handle
only after successful completion. `execute_root_branch_with_continuation`
recompiles the root context and independently validates its ScribeRig
fingerprint before handing the handle to `rpi-agent`. The runner cache is the
only lifecycle owner for these handles.

Child executions are dispatched recursively by
`upstream_execution/delegation.rs` through the active branch broker and inherit
the current upstream invocation. They do not enter the root runner, and their
context is a context-isolation frame rather than a distinct executor identity
per Level-1 021. Reusing or capturing a handle there would require defining
which exact child context/provider selection it is bound to and how a later
turn re-enters that child identity. The current branch/tool execution request
does not expose a corresponding child-turn lifecycle.

Plan workers have a separate invocation lifecycle. `plan_worker/execution.rs`
builds a precompiled `UpstreamBranchInvocation` from `PlanWorkerContext` and
calls `execute_precompiled_branch`; that path neither accepts nor returns a
continuation. Plan context includes exact `ContinuationAnchor`, ancestor and
dependency results, local branch history, and resolved assignment. Those
inputs differ from the root runner's completed-root fingerprint. Applying a
root handle to that invocation would cross branch/context boundaries, while
blindly associating handles with durable worker branches would be unsafe for
retries, changed claims, plan edits, or changed dependencies.

No code change is made in this slice: the allowed runtime paths lack a shared
transient cache lifecycle and exact reusable lineage key for child/worker
executions. Adding a map keyed only by branch would not prove equivalence of
anchor, plan claim, provider/model/profile/thinking assignment, and compiled
context; adding persistence would violate the opaque-handle non-persistence
invariant. A safe continuation extension needs an explicit in-memory owner
scoped to the execution tree plus context fingerprints derived from each exact
child/worker context, and lifecycle rules for child re-entry and plan retries.
The focused lifecycle coverage requested by the preceding audit (same-scope
reuse, divergence reseed, failure/cancellation non-reinsertion, branch
isolation, and restart reseed) remains unrun. No acceptance criteria are
checked by this follow-up.

#### Child and durable plan continuation implementation gate (2026-10-21)

Do not add child-branch or plan-worker continuation reuse until the execution
owner can prove exact semantic validity for every handle. The current root
cache is not that owner: it is keyed only by root branch and its root lineage
fingerprint cannot identify a nested child invocation or durable plan claim.
Do not treat a branch-only map, provider/model match, or a smaller context
cache key as sufficient.

The present lifecycle lacks a single ScribeRig-owned continuation identity
and handoff spanning child execution and plan-worker execution. The child
delegation request does not expose a re-entry identity/lifecycle for a later
turn. `PlanWorkerContext` provides compiled inputs but does not itself bind a
continuation record to the full durable execution tuple. In particular,
`PlanWorkerExecutor::execute_bound_upstream_worker` has the exact `PlanNode`,
`WorkerClaim`, `ResolvedPlanExecution`, and compiled context at dispatch, but
the upstream precompiled execution API accepts no continuation and returns no
extracted continuation. Any later reuse also needs the authoritative current
plan revision and anchor resolution; a retry must distinguish claim identity
and generation, and dependencies must bind their exact fulfilled result IDs.

The next implementation must first introduce an explicit ephemeral
ScribeRig-owned continuation owner for the execution tree and establish a
canonical validity value before passing a handle upstream. For child work,
that requires a stable child execution identity and a defined re-entry point.
For a plan worker, the validity value must include session and plan identity
plus plan revision, node identity, `ContinuationAnchor` and its resolved
location/result, worker branch, `WorkerClaim` ID and generation, claim
assignment, resolved provider/model/profile/thinking identity, the complete
canonical compiled-context fingerprint, and ordered ancestor/dependency
result identities (including each dependency's fulfilled result ID). Resolve
and compile from the authoritative snapshot for use, then recompute/compare
that same ScribeRig value immediately before upstream handle application.

Preserve ScribeRig `BranchResult`, `ContinuationAnchor`, profile/context
fingerprint, plan assignment, and branch identity as the source of validity
and durable semantics. Keep upstream `ProviderContinuation` completely opaque
provider-owned process state: never serialize it, include it in
`BranchResult`/session identity, or let its provider response ID stand in for
the ScribeRig key. Consume a candidate handle before an attempted execution;
reinsert only after successful, non-cancelled completion whose returned
ScribeRig lineage still matches. Any missing/stale plan, changed anchor or
dependency, assignment/profile/context divergence, failed attempt, or
cancellation must discard the handle and seed from canonical ScribeRig
context. Process restart always reseeds.

Only after the child re-entry API and plan snapshot/claim inputs above are
available, and focused lifecycle evidence covers same-key reuse, every-key
component divergence, sibling/branch isolation, failed/cancelled
non-reinsertion, and restart reseed, may child/plan continuation acceptance
be marked complete. Until then retain stateless child and plan execution;
this gate does not authorize a smaller cache or persistence of provider
handles. No runtime code changed and no tests or long checks were run.

#### Plan worker execution boundary and claim preflight (2026-10-21)

The scheduler is the ScribeRig coordinator for durable plan-node claims,
assignment resolution, exact `PlanWorkerContext` compilation, concurrent node
dispatch, and `BranchResult` settlement. Its scoped worker threads call
`PlanWorkerExecutor`; the production `NativePlanWorkerExecutor` resolves the
provider/model and invokes `execute_precompiled_branch`, which enters
`run_branch_with_semantic_broker` and delegates the ordinary provider/tool
loop to `rpi-agent` through
`run_upstream_branch_invocation_with_continuation`. The thread scope in
`scheduler_execution_helpers.rs` is plan-DAG dispatch concurrency, not a
second model/tool loop. Keep it with the ScribeRig plan coordinator.

Claim setup previously mutated the caller's `Plan` before compiling all worker
contexts and before durable claim persistence. A context compilation or
persistence error could therefore return without execution while leaving the
caller's in-memory plan in `Running` state. `claim_workers` now stages claims
on a cloned plan, compiles every exact context against that staged plan,
persists the staged claims, and only then replaces the caller's plan. Thus
preflight or persistence failure leaves the caller's plan unchanged, while
successful persistence and returned worker snapshots share the same claims.
This preserves ScribeRig ownership of plan claims and assignment while keeping
provider streaming, tool-call validation/settlement, and loop cancellation in
upstream `rpi-agent`. No checklist item is checked by this source change;
focused failure-path verification remains required. No tests or long checks
were run.

#### Provider-error category adapter (2026-10-24)

`crates/scriberig-agent-runtime/src/upstream_invocation/failure.rs` now owns the
whole terminal-failure classification for one branch invocation.
`classify_agent_state` projects the final upstream `AgentState` (loop
`error_message`, final assistant `error_message`, terminal `StopReason`) together
with the upstream-typed `provider_error_reason`, and `classify_loop_failure`
projects the failure returned by the upstream loop entry point through upstream's
own `is_abort()` category. Upstream's distinction is preserved instead of being
flattened into one agent text: authentication/authorization becomes
`UpstreamBranchError::Authentication`, an abort becomes `Cancelled`, and a
transport fault remains `Agent`. `upstream_invocation/types.rs` adds the single
`From<UpstreamBranchError> for AgentError` projection consumed by
`apps/scriberig/src/main_agent_execution/upstream.rs` and
`apps/scriberig/src/native_tui_agent/test_execution.rs`; the duplicated inline
matches there were deleted. `run_upstream_branch_invocation_with_continuation`
keeps only the missing-final-assistant rule and the captured request projections,
so no existing invocation contract changed and no ScribeRig code parses provider
transport text to choose a category.
