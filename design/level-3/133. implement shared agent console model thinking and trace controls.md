# Implement Shared Agent Console, Model/Thinking Controls, and Trace Presentation

**Status: [ ] Planned**

## Objective

Implement one shared Agent Console capability across Scriberig's application, protocol, TUI, reusable web packages, and integrated web application.

The completed feature must provide:

- a persistent free-text agent composer in the normal TUI/session surface, not only a modal overlay;
- the equivalent persistent composer in the reusable web agent UI;
- a user-visible model library and session-scoped active model selection;
- model-declared available thinking levels and a user-selectable current thinking level;
- a structured, causal activity view for model execution, reasoning summaries/status, tool calls, tool results, nested branches, validation, and final output;
- colored nesting rails: a narrow terminal rail in TUI and a literal `2px` rail in web;
- independent presentation controls for reasoning visibility, tool invocation detail, tool output verbosity, and prompt/model-request visibility;
- synchronized execution semantics between TUI, web, server/client, and other future clients;
- durable provenance for execution-affecting configuration without polluting session semantics with presentation-only preferences;
- deterministic cross-surface tests proving that the same underlying activity/model state is rendered with different verbosity without re-executing work.

This task integrates and extends the completed work in tasks 103, 107, 111, 113, 114, and 115. Do not create a parallel agent/session implementation.

## Architectural Invariants

These rules are not optional.

### 1. Execution configuration and presentation preferences are different

Execution configuration changes what the model does:

```text
model
thinking level
generation parameters when exposed later
branch/invocation overrides
```

Presentation preferences change only what a client renders:

```text
reasoning visibility
tool invocation simple/detailed
tool output hidden/summary/full
prompt/model-request hidden/shown
```

Do not store presentation-only changes as semantic session turns or model invocations.

### 2. Capture once, render many ways

The runtime/session/application layers must capture enough safe structured activity that the user can change presentation mode without rerunning the model or tool.

Changing:

```text
tool output: hidden -> full
reasoning: hidden -> shown
prompt: hidden -> shown
tool invocation: simple -> detailed
```

must not execute anything again.

### 3. Never expose private chain-of-thought

"Show thinking" means:

- Scriberig-generated runtime status such as `Thinking`, `Planning`, `Waiting for tool`, or equivalent safe phase information;
- provider/model content explicitly intended to be shown to the user, represented as a reasoning summary when available.

It does **not** mean capturing, persisting, requesting, or displaying hidden/private chain-of-thought.

### 4. Persist causality, not UI indentation

The canonical/shared activity representation stores parent/correlation relationships. TUI/web derive visual depth.

Do not persist fields such as `indent_pixels`, `terminal_depth`, or a color index as semantic state.

### 5. Branch tree and activity tree remain distinct

The session graph owns branch ancestry.

The activity projection owns immediate execution causality such as:

```text
model invocation
  reasoning summary
  tool invocation
    tool result
  child branch start
    child activity
```

Do not replace the existing session branch graph with an arbitrary UI activity tree.

### 6. Credentials never enter public/session activity

Credentials remain references resolved at the runtime/provider boundary.

Never place these into session records, protocol DTOs, prompt-display payloads, TUI state, web state, logs, test snapshots, or model profiles:

```text
API key value
Authorization header value
secret environment value
resolved credential value
```

### 7. Running invocations are immutable with respect to later selection changes

Changing model or thinking level while an invocation is running affects the **next** invocation only.

The running invocation keeps the resolved model/thinking configuration it started with.

### 8. Observation ordering and mutation concurrency are separate

Reuse monotonic event/activity cursor semantics for observation/replay.

Use session/config revision or equivalent optimistic-concurrency data for mutations where simultaneous TUI/web changes can conflict.

Do not use an event cursor as a mutation revision.

## Required Conceptual Data Model

Use existing repository naming/owners when equivalents already exist. The following shapes define semantics, not mandatory exact Rust names.

### Model descriptor

A model known to the system must expose safe capabilities:

```rust
struct ModelDescriptor {
    id: ModelId,
    display_name: String,
    provider_profile: ProviderProfileId,
    provider_model_id: String,
    capabilities: ModelCapabilities,
    thinking_levels: Vec<ThinkingLevelDescriptor>,
    default_thinking_level: Option<ThinkingLevelId>,
}

struct ThinkingLevelDescriptor {
    id: ThinkingLevelId,
    label: String,
    description: Option<String>,
    order: u32,
}
```

Do not define one global `Low/Medium/High` enum. The available levels belong to the model/provider capability declaration.

### Model profile/library entry

User/project configuration should be able to describe a curated model entry without containing a resolved secret:

```rust
struct ModelProfile {
    id: ModelProfileId,
    display_name: String,
    model: ModelId,
    connection: ConnectionRef,
    credential: Option<CredentialRef>,
    default_thinking_level: Option<ThinkingLevelId>,
    enabled: bool,
}
```

Adapt this to existing provider/profile configuration rather than duplicating it.

### Execution selection

Interactive resolution order must be explicit and tested:

```text
invocation override
  -> branch override
  -> session active selection
  -> project default
  -> user/model-profile default
  -> runtime/provider fallback
```

The session-level selection is the ordinary interactive default.

### Resolved invocation provenance

Every actual invocation records safe resolved provenance sufficient to explain history later:

```text
provider profile/display id
provider model id/model descriptor id
model profile id when used
thinking level actually used
safe generation parameters when applicable
context/request fingerprint already supported by session/runtime design
```

Editing/deleting a model profile later must not make old invocation provenance ambiguous.

### Presentation preferences

Use independent fields equivalent to:

```rust
enum ReasoningVisibility { Hidden, Shown }
enum ToolInvocationPresentation { Simple, Detailed }
enum ToolOutputVisibility { Hidden, Summary, Full }
enum PromptVisibility { Hidden, Shown }

struct AgentPresentationPreferences {
    reasoning: ReasoningVisibility,
    tool_invocation: ToolInvocationPresentation,
    tool_output: ToolOutputVisibility,
    prompt: PromptVisibility,
}
```

Optional presets may map to those fields:

```text
Minimal -> hidden / simple / hidden / hidden
Normal  -> shown  / simple / summary / hidden
Verbose -> shown  / detailed / full / hidden
Debug   -> shown  / detailed / full / shown
```

Presets are shortcuts only. Do not replace the independent fields with one `trace_level` enum.

### Structured model request for prompt display

Do not model "prompt" as one flat string if the runtime already compiles multiple sections/messages/tools.

Expose a safe structured representation equivalent to:

```text
ModelRequestRecord
  invocation
  instruction sections
  conversation/messages
  semantic/context references or safe rendered context
  tool definitions/references
  resolved model configuration
  optional token estimate
```

The visible representation is the canonical Scriberig request immediately before provider-specific serialization, not raw outbound HTTP JSON.

Secret values, authorization information, and sensitive tool parameters must be redacted/omitted before this structure reaches a public/application activity stream.

### Shared session activity item

Create or extend a UI-neutral projection equivalent to:

```rust
struct SessionActivityItem {
    id: ActivityId,
    sequence: ActivitySequence,
    session: SessionRef,
    branch: BranchRef,
    parent: Option<ActivityId>,
    kind: ActivityKind,
    state: ActivityState,
    content: ActivityContent,
    durable_ref: Option<SemanticRef>,
}
```

Required kinds include semantic equivalents of:

```text
HumanInput
AssistantOutput
ReasoningSummary
RuntimeStatus
ModelInvocation
ModelRequest
ToolInvocation
ToolResult
BranchStarted
BranchCompleted
OperationProgress
Validation
ModelSelectionChanged
ThinkingLevelChanged
Error
```

Do not add an activity kind for raw hidden chain-of-thought.
