# Implement Operation Handles, Structured Errors, and the Extension Registry

## Objective

Complete the cross-cutting parts of the universal application model that make it usable by future CLI, server, web, TUI, and agent surfaces.

This task implements:

- application-level long-running operation handles and lifecycle records;
- structured application failures with semantic context;
- the extensible registry/provider mechanism through which domains advertise relations, collections, views, find strategies, and high-level operations.

It must not implement a background worker runtime, transport event stream, authorization policy, or any domain operation algorithm.

## 1. Operation Reference

Use the universal `OperationRef` type established in the query/application vocabulary.

If it is only a placeholder newtype, define the canonical application-layer ownership now without changing its public semantic meaning.

An operation reference identifies one tracked execution attempt, not the semantic entity being operated on.

Do not derive operation identity from display text.

---

## 2. Operation Lifecycle

In `src/operation.rs`, implement a lifecycle enum equivalent to:

```text
Queued
Running
Completed
Failed
Cancelled
```

Keep terminal states unambiguous.

Do not add retry/scheduler policy into the lifecycle enum.

Implement an `OperationRecord`/`OperationStatus` capable of carrying:

```text
operation ref
operation kind or capability id
base snapshot/branch context
state
optional progress
optional produced result handles
optional diagnostics/error reference
```

Progress should be coarse and optional. A simple structure containing completed/total/message is sufficient if used.

Do not require every operation to report progress.

---

## 3. Immediate Versus Tracked Results

The application model must support both:

```text
immediate typed result
```

and:

```text
OperationStarted(OperationRef)
```

without changing the semantic meaning of the requested operation.

Do not make all operations artificially asynchronous.

The choice to execute inline or delegate to a runtime is an execution/runtime concern.

This task defines only the representation used when tracking is needed.

---

## 4. Structured Application Error

In `src/error.rs`, implement or complete the application error enum/record.

Required categories:

```text
NotFound
InvalidRequest
UnsupportedCapability
Conflict
ValidationFailed
Ambiguous
PermissionDenied
SnapshotUnavailable
OperationFailed
Internal
```

Each error should include:

```text
operation kind/capability when known
snapshot or branch context when known
subject handles when known
structured diagnostics/details
```

Use nested typed detail enums/records for important cases instead of a single free-form message.

A human-readable message is allowed as supplemental information.

---

## 5. Structured Conflict Details

Add conflict detail structures capable of preserving cases such as:

```text
subject entity
base revision
expected revision
current revision
left/right revisions or migrations
conflicting collection/relation operation
```

Do not require every conflict to use every field.

If the canonical change subsystem already defines conflict types, wrap or reuse them. Do not create a second semantic conflict model merely for the app crate.

The key requirement is that downstream surfaces can inspect and resolve conflicts without parsing an error string.

---

## 6. Ambiguity Details

Add an ambiguity representation capable of returning candidate semantic handles.

Example conceptual result:

```text
Ambiguous {
    scope,
    candidates: [EntityRef...],
    reason,
}
```

This is needed for reconciliation, selection, and query-like operations where multiple semantic targets are plausible.

Do not choose a candidate silently at the application boundary.

---

## 7. Capability Provider Trait

In `src/capability.rs`, define a provider/registry abstraction through which domains can advertise capabilities for a semantic subject.

It should support discovery of at least:

```text
relations
collections
views
find strategies
high-level domain operations
```

The registry should operate on stable capability descriptors from the previous task.

Avoid a global mutable singleton when a normal injected registry/service can work.

The application service must be testable with a small in-memory registry.

---

## 8. Registration and Composition

Provide a mechanism to combine multiple domain capability providers.

Requirements:

- adding a new domain should not require editing a central match statement over every domain type;
- duplicate capability IDs for the same applicability scope must be rejected or resolved by an explicit deterministic rule;
- providers may declare that a capability is unavailable because required derived data is missing;
- generic capabilities and domain capabilities can coexist;
- capability ordering shown to clients is not canonical semantic state.

Do not make registry population advance the project snapshot.

---

## 9. Capability Execution Boundary

High-level domain operation capabilities should expose an execution adapter that ultimately receives:

```text
semantic subject/selection
exact snapshot or branch/workspace context
arguments
```

and produces a canonical change request/result through the existing migration/change subsystem.

Do not let a capability provider update storage rows directly.

For this task, it is sufficient to define the trait boundary and test it with a dummy operation. Do not implement real domain algorithms such as rename-symbol or split-paragraph.

---

## 10. Capability Discovery Integration

Update the application service so `inspect` can merge:

- relation/collection capabilities from schema/graph inspection;
- registered views;
- registered find strategies;
- registered high-level operations.

Inspection must remain useful when no domain provider is registered.

Unknown/unsupported entities should still expose generic operations that actually apply.

Do not advertise capabilities whose provider reports unavailable.

---

## 11. Tests

Extend `tests/universal_operation_model.rs` to cover at least:

1. operation lifecycle moves through valid states;
2. completed/failed/cancelled are distinguishable terminal states;
3. immediate results do not require an operation record;
4. tracked work returns an `OperationRef` that can retrieve status through the application abstraction or test registry;
5. conflict errors preserve exact semantic handles/revisions;
6. ambiguity errors preserve candidate handles;
7. validation failure is distinct from conflict;
8. two independent capability providers can be composed;
9. duplicate capability IDs are handled deterministically;
10. a new dummy domain capability can be registered without editing core dispatch code;
11. inspect advertises registered capabilities;
12. unavailable derived capability is not falsely advertised as ready;
13. dummy high-level operation routes through the change-service test double rather than direct storage mutation;
14. registry/cache population does not advance the canonical snapshot.

Run:

```text
cargo test -p scriberig-app
cargo check --workspace
```

---

## 12. Non-Goals

Do not implement:

- a thread pool or job scheduler;
- process supervision;
- WebSocket/SSE events;
- HTTP status-code mapping;
- CLI progress bars;
- authorization decisions;
- model-provider execution;
- real Rust/Markdown/PDF high-level operations;
- persistent operation-history storage unless another design already owns it.

---

## Completion Criteria

This task is complete when:

- long-running work has a reusable application-level `OperationRef` and lifecycle model;
- important failures are structured and preserve semantic context;
- conflicts and ambiguity are machine-inspectable;
- domains can register discoverable capabilities without central core branching;
- capability execution cannot bypass the canonical change boundary;
- inspect can advertise generic and domain-provided capabilities coherently;
- no transport/runtime dependency is required.
