# Implement Rust Derived Compiler Analysis

## Objective

Add Rust compiler/static-analysis integration as derived knowledge over canonical Rust syntax.

This task must keep compiler facts separate from canonical source syntax. The same canonical Rust entities remain authoritative even when compiler/toolchain-derived analysis is absent, stale, or rebuilt.

Read before editing:

1. `design/level-1/007. domain modeling and adapters.md`
2. `design/level-3/005. implement language independent code domain.md`
3. `design/level-3/006. implement rust syntax domain adapter.md`
4. the current derived-knowledge/provenance APIs in shared crates

---

## Files to Create or Update

Inside `crates/domains/rust/`, create or update:

```text
src/lib.rs
src/analysis.rs
src/analysis_profile.rs
src/analysis_mapping.rs
src/diagnostics.rs
src/error.rs
```

Add tests under:

```text
tests/derived_analysis.rs
```

If the project has already standardized on a separate crate for compiler integration, place the files there instead and preserve the boundaries in this task.

---

## Analysis Boundary

Implement analysis as a producer of derived knowledge.

The derived output must identify enough provenance to answer:

```text
which canonical entities/revisions were inputs?
which analyzer/tool produced the result?
which tool version/profile/configuration was used?
which project/build settings affected the result?
```

Do not write compiler facts into canonical Rust syntax revisions.

---

## Initial Derived Facts

Support an initial useful subset such as:

```text
resolved symbol references
function callers/callees where available
resolved/inferred type information where available
compiler diagnostics
lint diagnostics
```

If the chosen analysis integration naturally provides additional facts, keep them behind explicit derived-analysis types rather than promoting them into canonical state.

Control-flow and data-flow graphs may be deferred unless already straightforward with the chosen integration.

---

## Tool/Library Choice

Prefer an analysis API already selected elsewhere in the repository.

If none exists, choose one Rust analysis integration suitable for library use and document why it is used. Do not integrate multiple competing analyzer stacks in this task.

The external analyzer's transient IDs must not become Scriberig semantic identity.

Map analyzer references back to canonical Scriberig entities using source/syntax correspondence and store the result as derived relations with provenance.

---

## Dependency Tracking

Derived results may depend on more than one source entity.

Track exact or sufficiently precise dependencies for each analysis result so unchanged inputs can reuse cached analysis and changed dependencies can invalidate it.

Include relevant environment/profile inputs when they change semantics, including as applicable:

```text
toolchain/compiler version
target
features
workspace/dependency state
configuration
```

Do not key validity only by the global current snapshot if a narrower dependency set is available.

---

## Queryability

Make the resulting facts available through shared graph/query abstractions where those APIs exist.

A future caller should be able to support operations equivalent to:

```text
find references to symbol/function
find callers
inspect resolved type
list diagnostics affecting an entity
```

Do not create an agent-specific query API.

---

## Failure Behavior

Compiler analysis may fail because source is incomplete, dependencies are unavailable, or the environment is invalid.

Represent failures explicitly as derived analysis/diagnostic results when useful.

A failed analysis must not corrupt or invalidate canonical source knowledge.

---

## Tests

Use a small Rust fixture workspace and test at least:

- a function reference resolves to the intended canonical function entity;
- caller/callee relation can be queried;
- one type fact is mapped to the correct source entity;
- diagnostics are derived objects with provenance;
- changing a relevant source revision invalidates/recomputes dependent analysis;
- changing an unrelated entity does not force unrelated analysis to become semantically different when dependencies are unchanged;
- compiler/analyzer transient IDs are not exposed as Scriberig identities.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-rust
cargo clippy -p scriberig-domain-rust --all-targets -- -D warnings
```

---

## Do Not Do

- Do not store compiler IR as the canonical program.
- Do not overwrite canonical syntax with inferred types or resolved symbols.
- Do not use analyzer IDs as semantic IDs.
- Do not require an agent runtime.
- Do not make failed analysis delete source entities.
- Do not create a separate analysis persistence database.
- Do not implement model-generated code descriptions in this task.

---
