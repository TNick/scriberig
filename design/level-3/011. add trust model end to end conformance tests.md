# Add Trust Model End-to-End Conformance Tests

## Objective

Create cross-surface integration tests that prove Scriberig's trust model is enforced consistently from semantic input through application operations, protocol/server, CLI/web-facing clients, validation, promotion, conflicts, and external-effect state.

This task should be implemented after the preceding trust tasks. It is a conformance suite, not another business-logic layer.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 30, 41, 54, 65 and 66.
2. `design/level-1/011. runtime libraries protocol and product surfaces.md`.
3. `design/level-1/012. web platform and integrated editor.md`.
4. Level 3 trust tasks `001` through `010` in this series.
5. Existing repository-wide protocol/conformance/end-to-end test conventions.

If the application layer, protocol/server, or trust primitives are incomplete, implement only tests for completed prerequisites and clearly mark remaining scenarios as blocked; do not fake passing behavior.

## Location

Use the repository's established integration/conformance test locations. The workspace design anticipates repository-level test areas; reuse those rather than burying all scenarios in one crate.

Possible locations, only if they exist in the implemented workspace:

```text
tests/conformance/
tests/protocol/

```

Do not create a second test harness if one already exists.

## Canonical Scenario Fixture

Build one small semantic project fixture containing:

```text
one public entity
one restricted entity
one generated summary derived from restricted content
one editable projection
one candidate branch
one validation policy
one fake external connector
```

Use deterministic IDs/test data where the implementation allows it.

The fixture must not contain real credentials or live external services.

## Required Scenarios

### 1. Untrusted content cannot grant authority

Store/import text containing an instruction equivalent to requesting broader authority. Run the normal application/agent-facing read path and prove the effective capability set is unchanged.

### 2. Restricted traversal does not leak

Allow read access to a public entity linked to a restricted entity. Verify inspect, relation traversal, reverse lookup, search, summary access, and protocol responses do not expose restricted content.

### 3. Generated knowledge retains provenance

Create or load a generated summary and prove a consumer can distinguish it from authored/observed evidence and follow provenance back to exact immutable inputs.

### 4. Validation is exact

Validate candidate `S2`, change a relevant dependency to produce `S3`, and prove the `S2` validation is not accepted for `S3`.

Also change an unrelated entity while keeping declared dependencies identical and prove reusable evidence remains applicable where the dependency model permits it.

### 5. Promotion cannot be bypassed

Attempt canonical advancement through:

```text
application operation
server/protocol path
CLI-facing path if testable in-process
web/client path if available
```

Prove each path requires the same promotion policy and exact evidence. There must be no product-surface storage bypass.

### 6. Stale proposal is explicit

Create a proposal from base `S1`, advance canonical state independently, then attempt promotion. Verify stale/rebase/merge-needed result rather than silent overwrite.

### 7. Ambiguous projection edit becomes conflict

Feed an intentionally ambiguous external edit. Prove the original observation is retained, conflict is first-class, canonical state is unchanged, and later resolution produces a normal migration.

### 8. Failed validation remains evidence

Run a validator that fails. Prove the failure and diagnostics remain inspectable without making the candidate canonical.

### 9. Capability delegation cannot widen authority

Create a narrow child/subagent capability from a parent and attempt to add a broader scope/action. Verify rejection.

### 10. External effect uncertainty is preserved

Use a fake connector that accepts a request but simulates loss of the response. Verify the operation becomes `Unknown`, is not blindly retried, and can later be reconciled through an external observation.

### 11. Derived cache cannot bypass confidentiality

Populate a cached summary while using a broad principal, then request it as a restricted principal. Verify cache hit is denied without deleting the reusable cache object.

### 12. Structured denial parity

Trigger the same denied semantic operation through at least the direct application path and protocol/client path. Verify action, scope, reason, and approval-possible semantics agree.

## Audit Reconstruction Test

For one successful candidate, assert that a consumer can reconstruct this chain using semantic references rather than log scraping:

```text
base snapshot
request/proposal
branch/workspace
migration
candidate snapshot
validation evidence
policy evaluation
approval if required
promotion
new canonical snapshot
```

Do not require private model reasoning traces.

## Failure-Mode Assertions

Add explicit regression names matching the Level 1 failure modes where practical:

```text
model output is not automatically authoritative
web/imported text cannot grant capability
validation of A cannot promote B
external file edit cannot overwrite concurrent state silently
restricted cache/search cannot leak content
ambiguous reconciliation cannot create false lineage silently
local write cannot invoke unrelated external service
unknown external outcome is not retried as definite failure
stale validation is not presented as current
product surfaces cannot bypass application policy
```

## Test Quality Rules

- prefer semantic assertions over exact human-formatted strings;
- verify IDs/references point to the exact expected revisions/snapshots;
- never depend on network access;
- use fake validators/connectors with deterministic behavior;
- keep each scenario independently diagnosable;
- do not mark blocked scenarios ignored without an issue/comment explaining the missing prerequisite according to repository conventions.

## Validation

Run the full Rust workspace tests, protocol conformance tests, and web tests/build required by the repository. The task is complete only when trust conformance tests are part of normal CI or the existing aggregate test command.

## Do Not

Do not introduce production bypass hooks solely for testing. Do not test authorization only at UI level. Do not rely on textual logs as proof of provenance. Do not use real secrets or real external side effects.
