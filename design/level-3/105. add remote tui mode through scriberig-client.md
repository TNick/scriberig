# Add Remote TUI Mode Through `scriberig-client`

**Status: [ ] Pending**

## Objective

Allow the same TUI state machine and views to operate against a remote Scriberig server through the public `scriberig-client`/protocol boundary.

This task proves that the TUI is a peer product surface rather than a privileged local database console.

Read first:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`;
2. `design/level-1/015. terminal user interface principles.md`;
3. `design/level-2/011. application operations protocol and runtime boundaries.md`;
4. `design/level-2/021. terminal ui runtime and state architecture.md`;
5. `design/level-2/022. terminal ui views interaction and conformance.md`;
6. `design/level-3/104. wire srig tui to local application composition.md`.

This task is dependency-gated on a usable public client/server protocol for the operations exposed by the TUI.

---

## Command Surface

Extend TUI startup with a mutually exclusive remote form equivalent to:

```text
srig tui --connect <ENDPOINT>
```

The local form remains:

```text
srig tui --db <PATH>
```

Define clear parser behavior when both local and remote selectors are supplied. Prefer a Clap argument group or equivalent parser-level mutual exclusion.

If neither is supplied, retain the documented local default unless product policy changes in a higher-level design.

The CLI crate parses endpoint text. It does not implement the client transport.

---

## Remote Adapter

Add a remote implementation of the TUI service port using `scriberig-client`.

The adapter must preserve the same TUI-facing semantics as the embedded adapter for:

```text
stable references
explicit snapshot/branch context
structured errors
capability discovery
operation IDs/status
cancellation
event observation
pagination/cursors
```

Do not make views branch on HTTP status codes or protocol serialization details. Translate transport/protocol results at the adapter boundary.

Do not depend on `scriberig-server` internals.

---

## Connection State

Add explicit connection presentation states equivalent to:

```text
connecting
connected
reconnecting when supported
disconnected
failed
```

Connection state is product/runtime state, not semantic canonical state.

A disconnected remote client may retain previously loaded view models as visibly stale. It must not present them as current or allow state-changing actions that require a live authority unless the shared client/application model explicitly supports queued/offline operations.

No offline mutation queue is required by this task.

---

## Capability Discovery

After connection, obtain runtime/server capabilities through the public protocol/client path.

The command palette and view actions must use the same capability-driven behavior as local mode.

Do not enable an action in remote mode merely because it exists in local mode.

If the server/protocol version cannot support a required operation, render that operation unavailable with a safe compatibility reason where the client contract provides one.

---

## Authentication and Secrets

Use only authentication mechanisms defined by the public client/server design at implementation time.

Do not invent provider credentials or persist secrets inside TUI view state.

Sensitive authentication values must not appear in debug/status messages, command history, snapshots, or rendered error details.

If interactive credential entry is required, use a dedicated protected input flow defined by the client/auth design; do not implement ad-hoc secret persistence in this task.

---

## Events and Reconnect

Use the public client event-subscription mechanism where implemented.

On reconnect/resubscription:

- treat old cached view models as stale until refreshed;
- do not assume missed events can be replayed unless the protocol guarantees it;
- resolve authoritative visible state again;
- preserve local presentation navigation where the referenced semantic objects remain resolvable.

If the current protocol has no reconnect semantics, fail visibly and let the user retry rather than inventing unsafe replay behavior.

---

## Transport Errors

Separate transport failures from semantic application failures in presentation.

Examples:

```text
transport unavailable / timeout / incompatible protocol
vs.
not found / permission denied / stale base / validation failure
```

The remote adapter performs this mapping. Views should consume a TUI error model that preserves the semantic category when one exists.

---

## Tests

Use an in-process or deterministic test transport from the server/client test infrastructure. Do not require external network access.

Cover at least:

- parser rejects simultaneous `--db` and `--connect`;
- same inspect fixture produces equivalent semantic TUI model in local and remote adapters;
- remote capability absence disables the same action path;
- transport failure is distinct from semantic not-found/permission denial;
- disconnect marks cached state stale;
- reconnect causes authoritative refresh rather than trusting missed events;
- secrets/auth material are not included in formatted TUI errors;
- remote adapter does not depend on server private modules.

---

## Conformance

Where the conformance fixture supports it, compare local-TUI and remote-TUI adapter results for the same semantic operations.

The comparison should use semantic references/result fields, not terminal cell snapshots.

Advance TUI capability entries to `verified` only when these tests and the applicable cross-surface tests actually pass.

---

## Out of Scope

Do not implement:

- offline canonical mutations;
- a private TUI-only protocol;
- direct server-internal calls;
- automatic credential persistence;
- a separate remote-only view hierarchy.

---
