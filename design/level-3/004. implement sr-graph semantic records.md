# Implement `sr-graph` Semantic Records

## Objective

Implement the storage-independent semantic graph records and read-only snapshot view contracts required by the universal knowledge model.

This task owns exact revision payloads, relation values, collection values, descriptions, derived artifacts, and graph-view traits.

It does not own persistence, migrations, search, history, or domain adapters.

## 1. Relation Values

In `relation.rs`, implement the runtime value representation for relations owned by a revision.

A relation value must identify:

- the `RelationTypeId`;
- one or more target `EntityId` values, according to the schema cardinality.

Choose a representation that keeps the relation type separate from its targets.

Do not store:

- target filenames;
- target line numbers;
- reverse edges merely for convenience;
- target revision IDs as the only identity when continuity should point to the target entity.

The graph is interpreted in a snapshot, so entity targets can resolve to their exact revisions through the graph view.

If an exact historical relation must eventually point to a specific revision rather than an entity, leave room for a later explicit reference type instead of overloading ordinary semantic relations now.

---

## 2. Collection Values

In `collection.rs`, implement distinct ordered and unordered collection values.

Use a clear enum or separate types, for example conceptually:

```text
CollectionValue
  Ordered(Vec<EntityId>)
  Unordered(Set<EntityId>)
```

The exact Rust names may differ, but the semantic distinction must be visible in the API.

### Required behavior

- ordered collections preserve exact order;
- unordered collections compare by membership, not insertion order;
- members are semantic entity handles;
- duplicate policy must be explicit and documented;
- collection values are immutable values once placed in a revision record;
- moving an entity within an ordered collection changes the collection value only, not the child entity identity.

Do not attach parent IDs to child entities.

---

## 3. Revision Record

In `revision.rs`, implement a `RevisionRecord` or equivalent immutable data structure representing one exact entity state.

It should contain at least:

```text
entity type
properties
owned relation values
owned collection values
```

Use deterministic map structures where reasonable.

The revision record does not need to contain its own `RevisionId` if the ID is an external key assigned by the future store. If you do include an optional ID for convenience, document clearly that it is metadata about the record, not part of the semantic payload unless a later identity design says otherwise.

### Prohibited fields

Do not include:

- database row IDs;
- a database connection;
- mutable parent pointers;
- a current snapshot pointer;
- reverse-relation caches;
- file paths as universal identity;
- agent/session state unless a future session schema stores it as ordinary domain data.

---

## 4. Implement Schema Validation Subject

Implement the `sr-schema` validation-subject trait for `RevisionRecord`.

The implementation must expose:

- entity type;
- property keys and values;
- relation type and target IDs;
- collection type and member IDs.

Do not create a dependency cycle. `sr-graph` may depend on `sr-schema`; `sr-schema` must continue not to depend on `sr-graph`.

If relation/member target-type validation needs a context, implement the adapter required by the `sr-schema` contract through the graph view or a small caller-provided resolver.

---

## 5. Descriptions

In `description.rs`, implement a derived description object.

A description should contain at least:

- exact `EntityRevisionRef` being described;
- `DescriptionProfileId`;
- textual description;
- `Provenance`;
- optional cost metadata.

Cost metadata may initially support simple estimates such as:

```text
bytes
characters
estimated tokens
```

Use optional fields because exact token estimates may depend on an external tokenizer not present in this crate.

Descriptions are derived navigation aids by default.

Do not add them to `RevisionRecord` as canonical entity state.

---

## 6. Derived Artifacts

In `derived.rs`, implement a generic derived-artifact representation.

It must contain enough information to identify:

- artifact/profile kind;
- exact dependency revisions;
- producer/configuration identity;
- provenance;
- result payload or result reference;
- status if useful.

A practical initial representation may use:

```text
artifact_kind: String
profile: Option<String>
dependencies: Vec<EntityRevisionRef>
producer: Option<ProducerId>
provenance: Provenance
payload: KnowledgeValue
status: DerivedStatus
```

The exact names may differ.

The key invariant is that an artifact explicitly states the immutable inputs that determine its validity.

Do not implement caching, dependency invalidation, or persistence here.

---

## 7. Read-Only Graph View

In `view.rs`, define a trait such as `KnowledgeView` for reading the semantic graph relative to snapshots.

The trait must be storage-independent.

At minimum support conceptually:

```text
resolve(snapshot, entity) -> revision ID
read revision by revision ID
lookup schema/entity-type information
reverse relations through an index/view abstraction
```

Owned forward relations and collections may be read from `RevisionRecord` directly.

### Trait error type

Use an associated error type or similarly generic error boundary so a future SQLite store, in-memory store, remote store, or test double can implement the trait without `sr-graph` knowing backend error types.

### Snapshot semantics

Every operation that depends on current entity state must take an explicit `SnapshotId` or operate on an object already bound to one.

Do not create ambiguous methods equivalent to:

```text
get_current_entity(entity)
```

because the Level 1 model requires graph interpretation within a snapshot.

---

## 8. Reverse Relation Result

Define a small result type for reverse navigation, for example containing:

```text
source entity
relation type
```

and, when needed, source revision as resolved within the requested snapshot.

Reverse relations are a view/index capability. They are not canonical duplicated edges inside child revisions.

---

## 9. Public API

In `lib.rs`, re-export the primary public graph types used by downstream storage and domain crates.

Keep helper implementation details private.

The public surface should make these concepts straightforward to import:

```text
RevisionRecord
RelationValue or relation collection type
CollectionValue
Description
DerivedArtifact
KnowledgeView
ReverseRelation
```

Use actual names consistently.

## 10. Unit Tests

Add focused module tests for:

1. ordered collection order preservation;
2. unordered collection membership equality independent of insertion order;
3. relation values point to semantic entity IDs;
4. a revision record contains no required parent reference;
5. `RevisionRecord` can act as a schema validation subject;
6. descriptions bind to exact entity revisions;
7. derived artifacts hold exact dependency revisions;
8. a mock `KnowledgeView` can resolve an entity differently in two snapshots.

The final integration task will combine these into full cross-crate scenarios.

## Do Not

Do not:

- add SQLite or another store;
- generate `RevisionId` values;
- implement snapshot maps;
- implement writes;
- implement migrations;
- implement history or diff;
- implement general search;
- implement domain schemas;
- implement Markdown/Rust/PDF/session adapters;
- implement agents;
- make reverse edges canonical duplicates;
- make generated descriptions canonical by default.
