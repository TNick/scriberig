## Required Semantics

### 1. Resolve project workspace by ProjectId

There must be one shared application-level operation capable of resolving an imported project into an exact semantic workspace.

The result must contain enough data to construct:

```text
project_id
project_name
canonical project path or safe path metadata
project status
snapshot_id
root entity reference at that snapshot
```

Prefer an existing `project status`, `project get`, or equivalent operation if it can be extended without changing meaning. Add a new `project workspace/open` operation only if existing semantics are unsuitable.

The result must not expose a SQLite row ID as semantic identity.

The root must be the selected project's root, not a generic global root advertised by runtime capabilities.

### 2. Project activation is local client state

Web runtime and TUI state each maintain an active project/workspace.

Do not persist a single server-wide `current project` value.

Two clients connected to one server must be able to activate different projects without changing each other's active workspace.

### 3. Import-to-activation

After successful import:

- resolve authoritative workspace for the imported `ProjectId`;
- activate it in the initiating product runtime;
- replace/reset explorer root to the project root and exact current snapshot;
- clear selection if it belongs to another project/snapshot and cannot be resolved safely;
- show project name/path and snapshot in product context;
- make semantic/raw navigation immediately available.

The web implementation may navigate automatically from Projects to the semantic/raw browser, or expose an explicit `Open project` button after import. Whichever behavior is chosen must be deterministic and covered by Playwright.

### 4. Existing project activation

A user must also be able to open an already imported project from the project list without rescanning/importing it.

Web project list items need an explicit accessible action, e.g. `Open <project-name>`.

TUI startup with an existing `ProjectId`/path/database must resolve the same project-specific root.

### 5. Refresh after project snapshot change

Create a shared runtime/controller method equivalent to:

```text
activateProject(projectId)
refreshActiveProject()
```

Names may differ to fit current code.

`refreshActiveProject` re-resolves authoritative project workspace and replaces snapshot/root state when the project current snapshot advances.

Do not mutate snapshot IDs locally based only on a UI assumption.

### 6. Selection behavior

On activation:

- if there is no selection, leave it empty until user selects an entity;
- if old selection points to another project, clear it;
- if refresh advances the same project and the selected entity still resolves, preserve entity identity at the successor snapshot;
- if it no longer resolves, clear selection and display a non-fatal selection-invalidated state.

Do not silently keep an exact old snapshot selection while labeling it current.

## Web Implementation Requirements

### Runtime

Refactor `web/apps/scriberig/src/runtime.ts` only as needed so the shared runtime owns active workspace state.

It should expose subscription or model state sufficient for React views to react to workspace activation.

Do not create a second transport/client in `ProjectManager`.

The initial generic server root may still be useful before any project is active, but once a project is active the knowledge tree/root used for project work must be the project's exact root.

### ProjectManager

`ProjectManager` must no longer treat import as only local list-state completion.

Inject or acquire the shared workspace controller/runtime action through public app composition.

After import, activate the returned/resolved project.

For existing imported projects, render an accessible open action.

Show active status in the project list or workspace shell.

### App shell/context

Show at least:

```text
active project display name
current snapshot (short display allowed)
```

Path may appear in Projects/detail context.

Do not rely only on a hidden selection summary to tell the user which project is active.

## TUI Implementation Requirements

Find the TUI application state that currently stores project path/context.

Add explicit semantic workspace data rather than only a display path.

When launched with:

```text
srig tui --db <db> --project <path> --git-tracked --import
```

the explorer root must be the imported project's current semantic root before the user begins navigation.

When a matching already imported project exists and import is not requested, resolve its current project workspace rather than falling back to a global root.

Display active project name/path and snapshot in the terminal shell/status area.

Do not make rendering code query SQLite.

## Required Focused Tests

### APP-WORKSPACE-01: project-specific workspace resolution

Create two imported fixture projects in the same temporary database.

Resolve each by `ProjectId`.

Assert:

- both return their own current snapshot;
- both return their own root entity reference;
- project A root/snapshot is not accidentally project B root/snapshot;
- resolving A does not mutate B or any global active state.

### PROTOCOL-WORKSPACE-01: embedded vs remote equivalence

Resolve one project through embedded application operation and through server/client public path.

Assert equivalent project ID, snapshot ID, and root semantic reference.

### WEB-WORKSPACE-01: import activates workspace

Using the real browser E2E harness or, while task `122` is not yet complete, a focused Playwright spec:

1. copy/init fixture;
2. scan/import from Projects;
3. activate/open it;
4. assert active project name is visible;
5. assert current snapshot is visible/non-empty;
6. navigate to raw/semantic explorer;
7. assert the root now belongs to the imported workspace rather than the pre-import bootstrap root.

This test may use a stable project/root label in task `117`; symbol assertions `Calculator/add` belong to `118`.

### WEB-WORKSPACE-02: open existing project without reimport

Reload browser/server against same database, choose imported project from list, open it, and assert the same project current snapshot/root becomes active.

### TUI-WORKSPACE-01: launch imports and opens project

Drive the real PTY TUI with temp db/project and `--import`.

Assert visible project context and current snapshot.

Assert explorer root corresponds to the selected project.

### TUI-WORKSPACE-02: multi-project isolation

Prepare two projects in one database.

Launch TUI targeting project A and verify A context/root; launch another run targeting B and verify B. No "last imported project" global behavior is allowed.

## Failure Cases to Test

- project has no successful imported snapshot: workspace resolution returns structured not-ready error/state;
- unknown `ProjectId`: structured not-found error;
- project path no longer exists: catalog/workspace inspection remains possible, but filesystem-dependent actions report missing/unavailable path explicitly;
- project snapshot changes while active: refresh returns new authoritative snapshot/root;
- activation network failure in web: previous active workspace remains intact or transitions to explicit disconnected/error state; do not install a half-resolved root.
