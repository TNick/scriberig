# Implement Rich Document Domain and Editable DOCX Vertical Slice

## Status

In Progress. The format-independent document crate models ordered sections,
paragraphs, inline runs, tables, rows, cells, hyperlinks, and separate style
references, with typed extension records. DOCX import retains exact source
evidence and stores blocks and table cells as separate semantic entities. A
safe paragraph operation now edits only a single-run, single-text-node target,
preserves other ZIP member contents, creates an exact-base shared project
candidate, validates a staged reopen, and materializes through shared apply.
Complex paragraph structures remain read-only. Candidate creation is exposed
through the embedded application, Rust protocol/client, local HTTP, TypeScript
client, a reusable web paragraph editor, and an application-backed
`document.replace_paragraph` agent tool. A bounded exact-snapshot project tree
reader and Inspect-authorized application method now assemble paragraphs,
tables, rows, and cells. Typed read DTOs are wired through the Rust protocol and
client, local HTTP, and TypeScript client. The reference web app renders the
tree; project/application APIs, HTTP, protocol, and the Rust client also support
case-insensitive, bounded paragraph search by semantic identity. DOCX artifact
fidelity now runs an actual safe-writer probe: a package is marked
editable-with-opaque-preservation only when a structurally simple paragraph can
be rewritten and every package member can be carried through the writer.
Complex-only packages remain read-only with a diagnostic. Named styles from
`word/styles.xml` are imported as typed `DocumentStyle` extensions, persisted
on the semantic document root, and exposed in exact-snapshot tree responses
through Rust and TypeScript clients. Authored DOCX style definitions remain
document semantics; user/view projection style selection remains in the shared
projection style contracts in tasks 151/154. Semantic selection and full
navigation remain open.

## 1. Goal

Implement a reusable rich-document semantic domain plus a DOCX adapter that can safely inspect and edit document paragraphs/tables while preserving unrelated package content and using normal Scriberig candidate/change/materialization semantics.

Minimum scenario:

```text
onboard report.docx
inspect Document
navigate section/paragraph/table
replace one paragraph or table cell semantically
create candidate
validate
review/apply
materialize DOCX
reopen and prove edit + preservation
```

This task depends on task 155. It may reuse generic document semantics from the Markdown domain where appropriate but must not force Markdown-specific representation onto DOCX.

## 4. Architectural Prohibitions

Do not:

- make WordprocessingML XML trees the public canonical document model;
- duplicate Paragraph/TableRow/TableCell concepts unnecessarily if existing shared semantics can be reused cleanly;
- make rendered page number/line wrapping canonical paragraph identity;
- silently discard unsupported DOCX parts, relationships, tracked changes, comments, bookmarks, fields, headers/footers, content controls, or embedded objects;
- claim editable fidelity merely because paragraphs can be parsed;
- mutate DOCX ZIP/XML directly from agent/UI code;
- bypass shared candidate/change/materialization paths.

## 5. Phase A — Define Crate/Schema Ownership

The generic schema lives in `scriberig-domain-document`; ZIP/XML parsing stays
in `scriberig-domain-docx`. The DOCX parser uses pinned `roxmltree` 0.20 and
`zip` 2.2 dependencies. The writer edits only one structurally simple
paragraph, carries other package member contents forward, and proves that
capability with an exact-byte rewrite probe. Complex paragraphs and packages
the writer cannot rebuild remain read-only. The fixture is generated in
focused test code, not checked in as a binary.

Preferred structure:

```text
crates/domains/scriberig-domain-document/
crates/domains/scriberig-domain-docx/
```

If repository audit proves current Markdown semantic types can serve as a generic document layer without pulling Markdown parser/renderer dependencies upward, reuse/refactor those types instead of creating duplicates.

## 7. Phase C — Choose DOCX Library and Create Fixture

Dependency review (2026-10-27): a high-level DOCX object model was not selected.
The adapter needs to preserve package members it does not understand and must
prove the exact simple-paragraph rewrite capability before advertising edits.
The implementation therefore uses `roxmltree` 0.20 as a read-only XML tree
and the `zip` 2.2-compatible API (locked to 2.6.1) for package member
enumeration/copying and the narrowly scoped rewrite. General-purpose DOCX models were rejected for this slice because a
model-and-reserialize path would expand the supported write surface and make
opaque-part preservation harder to prove. Unsupported or complex content is
preserved and/or causes editing to be downgraded, as the exact probe and
reopen tests establish. Neither library requires Word or network access at
runtime.

The selected crates declare `MIT OR Apache-2.0` (`roxmltree`) and `MIT`
(`zip`). These are compatible with this repository's Apache-2.0 project
license. They are dependency-only, not vendored or copied into distributed
source/assets, so the repository's `THIRD_PARTY_NOTICES.md` policy does not
require an additional notice entry.

Dependency selection checks:

- [x] Evaluate practical current Rust DOCX/OpenXML read/write options (read-only XML tree plus ZIP member handling was selected over a broader DOCX object model to enforce opaque preservation and fail-closed editing).
- [x] Record selected library and known unsupported structures (`roxmltree` 0.20 and `zip` 2.2 API, resolved to 2.6.1; complex paragraphs, hyperlink targets, archive features the writer cannot preserve, and unsupported package structures remain read-only unless the exact rewrite probe proves preservation).
- [x] Verify license compatibility and update notices if needed (the selected dependencies are MIT/Apache-2.0 and dependency metadata is sufficient under `THIRD_PARTY_NOTICES.md`).
- [x] Keep dependency types behind adapter-private modules (`zip` and `roxmltree` types do not appear in project/application contracts).

Create deterministic fixture `tests/fixtures/rich-project/report.docx` with anchors:

```text
paragraph: "Existing site area"
paragraph: "Preserve this paragraph"
table cell: parcel 124
header/footer text or another unrelated package structure
at least one style/relationship
```

Add one feature that tests opaque/unsupported preservation if feasible.

- [x] Provide generator/source description (`crates/domains/scriberig-domain-docx/tests/fixtures/rich-project/README.md` identifies the in-memory Rust fixture generators).
- [x] Document expected anchors in fixture README (`README.md` lists both paragraph anchors, the table cell, and opaque preservation members).
- [x] Prove the generated original fixture reopens before editing logic is added (`cargo test -p scriberig-domain-docx --test import imports_docx_content_and_probes_safe_paragraph_capability` imports the original generated package and verifies its semantic anchors and source digest).

Requirements for editable external projection support:

- [x] Reconciliation is bound to the exact prior package bytes and digest (`reconcile_external_docx` validates the supplied baseline digest; the project watcher supplies the previously persisted source bytes/digest before scanning).
- [x] Paragraph/table identity matching uses Word persistent paragraph IDs when present, anchored semantic matching for positional fallback, and exact XML table/row/cell structure rather than ZIP member order (`persistent_paragraph_ids_survive_text_edits_and_detect_reordered_identity`; one positional edit requires an unchanged paragraph anchor).
- [x] Concurrent canonical change uses paragraph-level three-way conflict semantics and applies a disjoint merge through shared candidate validation/materialization (`cargo test -p scriberig-project --test docx_onboarding disjoint_external_docx_edit_materializes_reconciled_candidate`).
- [x] Opaque package members absent from semantic parsing are retained from the exact observed package during merged output materialization (the same test changes and verifies `customXml/opaque.bin` survives).
- [x] Ambiguous moved/split/merged paragraph identity returns a typed conflict when persistent IDs prove reordering, otherwise an ambiguity result when structure or fallback identity evidence is insufficient (`persistent_paragraph_ids_survive_text_edits_and_detect_reordered_identity`, `multiple_changed_positional_paragraphs_are_ambiguous`, and `stale_baseline_and_structural_change_are_ambiguous`).

Conservative behavior for cases that remain unresolved:

- [x] Route external DOCX watcher events through exact-baseline reconciliation before project scan/import (`cargo test -p scriberig-project --test docx_onboarding external_docx_paragraph_edit_is_reconciled_before_project_import`).
- [x] Reject same-paragraph conflicts, ambiguous structure, and package edits unsupported by the loss-preserving writer before replacing the persisted baseline (`cargo test -p scriberig-project --test docx_onboarding same_paragraph_external_conflict_does_not_import_or_overwrite`; domain tests also cover structural ambiguity).
- [x] Materialize a successful merged result that includes both external and concurrent canonical edits through a durable candidate and shared apply path (the project onboarding test validates and applies the merged candidate and reopens the output).
- [x] Prove paragraph continuity for edited moves, splits, and merges with semantic or structural evidence rather than positional IDs: persistent `w14:paraId` IDs identify moves; structural changes without stable IDs and multi-paragraph positional changes fail closed as ambiguous.
- [x] Document remaining limits: DOCX files without persistent IDs support a positional paragraph edit only when an unchanged paragraph anchors identity; ambiguous cases require a user decision, and table topology edits remain read-only until structural reconciliation is added.

Implementation progress: `scriberig-domain-docx::reconcile_external_docx` is
called by the project source watcher with the prior persisted package bytes and
current semantic document. The watcher verifies the observed digest and either
imports a no-conflict external result or creates a durable candidate whose
effect binds canonical base bytes separately from exact observed live bytes.
Shared validation and apply materialize disjoint paragraph edits atomically,
preserving opaque package members from the observed package. Persistent Word
paragraph IDs establish identity across source reordering. Files without those
IDs use anchored fallback and report ambiguity when multiple positions change;
table topology changes remain fail-closed.
