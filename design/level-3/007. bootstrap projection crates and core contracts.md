# Implement: Bootstrap Projection Crates and Core Contracts

## Objective

Create the three projection-related crates prescribed by Level 2 and establish the minimal domain-independent projection model in `sr-projection`.

This task is scaffolding plus core types only. Do not implement filesystem watching or Markdown parsing yet.

## Read first

Read:

1. `design/level-1/006. projections and bidirectional editing.md`
2. `design/level-2/007. projection crate boundaries and core model.md`
3. `design/level-1/003. identity revisions and snapshots.md`
4. `design/level-1/005. changes migrations branches and merge.md`

If persistence/change crates already exist, use their public ID/types instead of duplicating them.

If workspace crates from earlier tasks do not yet exist, do not reimplement their designs here. Add only dependencies that can compile against the repository state available to you.

## Workspace requirements

Add the three crates to the root Cargo workspace.

Dependency direction must be:

```text
lower universal/store/change crates
          ↑
     sr-projection
       ↑        ↑
sr-projection-fs  sr-markdown
```

No dependency from `sr-projection` to either child crate is allowed.

No projection crate may depend on agent, CLI, server, TUI, or web crates.

## `model.rs`

Define strongly typed domain-independent concepts for:

- `ProjectionClass` with `ReadOnly`, `Editable`, `Ephemeral`, `Interactive`;
- `ProjectionKind` as an extensible typed identifier, not a closed enum of Markdown/Rust/etc.;
- `RendererVersion`;
- a projection reference/spec reference type using existing universal IDs where appropriate;
- a semantic scope reference capable of identifying the entity/scope being projected;
- ownership classification needed by the generic layer without filesystem-specific paths.

Do not encode file paths in generic projection identity.

## `capabilities.rs`

Define `ProjectionCapabilities` containing at least:

- renderable;
- parseable;
- editable;
- round-trip capable;
- structure preserving;
- style preserving.

Use a representation that can be extended compatibly.

Add constructor/helper methods that make invalid obvious combinations difficult, for example editable without parseable should be rejected or normalized explicitly.

## `style.rs`

Define only universal style references/identity needed by render contracts.

Do not put Markdown/Rust style fields here.

A render request must be able to refer to an exact immutable style revision or an exact style value supplied by an adapter.

## `render.rs`

Define request/result types sufficient to carry:

- semantic scope;
- base snapshot/exact semantic state reference;
- projection kind;
- style reference;
- renderer version;
- rendering context/extensions;
- exact rendered bytes or text;
- deterministic output hash metadata placeholder/boundary.

Do not implement filesystem writes here.

## `adapter.rs`

Define a domain-adapter trait boundary with separate methods/responsibilities for:

- capabilities;
- render;
- parse external representation;
- reconcile parsed candidate against semantic state;
- validate result where adapter validation is required.

Use associated types or opaque adapter-owned candidate/diagnostic types if that keeps the generic layer free of domain enums.

Do not force one parser AST into the universal layer.

## `reconcile.rs`

Define a generic reconciliation outcome capable of distinguishing:

```text
NoSemanticChange
MigrationProposal
Ambiguous
Conflict
InvalidExternalState
```

Reuse `sr-change` migration/conflict types if available. If a dependency is not implemented yet, create narrow adapter-facing placeholders only where needed to compile and clearly mark them for replacement; do not create a second full migration system.

## `diagnostic.rs`

Define structured stage information:

```text
Render
Observe
Parse
Reconcile
Validate
Commit
Rerender
```

Projection diagnostics must carry stage plus structured domain detail/reference. A `String` message may be included for humans but cannot be the only information.

## `state.rs`

Define generic projection lifecycle/status concepts without filesystem paths:

```text
Synchronized
ExternallyModified
Rendering
ImportPending
ImportFailed
Conflict
Missing
```

Filesystem-specific synchronization records are implemented later.

## Tests

Add tests proving:

- editable projection capabilities require parseability;
- read-only projection can be renderable without parseability;
- projection kind is extensible without changing `sr-projection`;
- reconciliation outcomes are distinguishable without parsing strings;
- generic model types contain no filesystem or Markdown-specific dependency.

## Commands to run

Run:

```text
cargo fmt --check
cargo test --workspace
```

Fix formatting and compilation issues before stopping.

## Do not do

- Do not add a watcher library.
- Do not parse Markdown.
- Do not write files.
- Do not create SQL tables.
- Do not implement agent tools.
- Do not define Rust/source-language ASTs.
- Do not make projection identity depend on path or line number.
