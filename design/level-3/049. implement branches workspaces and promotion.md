# Agent Task: Implement Branches, Workspaces, and Promotion

## Goal

Implement the branch/workspace model and optimistic named-root promotion for `sr-change`.

This task must preserve the Level 1 rule that branches are lines of work over snapshots, not copies of the database.

## Read before editing

Read:

1. `design/level-1/005. changes migrations branches and merge.md`, especially sections 14 through 20, 36 through 39, and 45 through 49.
2. `design/level-2/001. persistence crate boundaries.md` for named-root semantics.
3. `design/level-2/002. change history and merge crate design.md`.
4. Existing `sr-store` named-root compare-and-promote API.

Modify `sr-store` only if a backend-independent atomic compare-and-promote capability is missing. If you extend that trait, update both memory and SQLite conformance expectations rather than calling a concrete backend directly.

## Branch model

Represent branch identity separately from branch head state.

The model must support at least:

```text
stable branch/entity reference
base snapshot
current snapshot
status
optional title
optional purpose
optional short description
optional outcome
optional resulting migration
```

Do not make the descriptive fields part of snapshot identity unless the universal graph model explicitly treats them as canonical branch data.

Use existing universal entity/reference types where available.

## Workspace model

A workspace is an isolated working line with:

```text
base SnapshotId
current SnapshotId
optional target named root
status
provenance
```

Required status transitions should cover the equivalent of:

```text
Active
Ready
Promoted
Abandoned
FailedValidation
```

Keep the status vocabulary small and deterministic. Do not turn validation details into workspace status strings; validation result objects belong elsewhere.

A workspace must be able to advance from one descendant snapshot to another without altering its base.

## Promotion API

Implement a promotion operation equivalent in semantics to:

```text
promote(
    root,
    expected_snapshot,
    result_snapshot,
)
```

The underlying store must perform an atomic compare-and-promote.

Return a typed result that distinguishes:

```text
Promoted
StaleRoot { expected, actual }
InvalidTarget
StoreError
```

If the root points to a newer snapshot than expected, do not retry automatically and do not overwrite it.

The caller decides whether to merge, rebase, create a branch, or abandon.

## Promotion provenance

On successful promotion, preserve enough information to connect the promoted snapshot and migration/workspace to the named-root advance when the surrounding history model supports it.

Do not make named-root movement the only record of history. The migration remains the semantic transition record.

## Branch creation

Creating a branch from snapshot `S` must be O(1) or equivalent in logical state: it records a reference to `S`; it does not enumerate or duplicate all entities in `S`.

Do not implement branch creation as snapshot copying in `sr-change`.

## Failed attempts

Tests must prove that a failed or abandoned workspace does not alter:

- its base snapshot;
- the target named root;
- sibling workspace state.

Failed descendants may remain addressable according to retention policy.

## Concurrent work

Create tests with two workspaces from one base:

```text
S1
├── S2
└── S3
```

Promote one successfully, then attempt to promote the other with `expected = S1`.

The second promotion must fail with the actual current root and preserve both descendant snapshots.

## Branch descriptions

Expose branch title/purpose/description/outcome through compact inspection data without requiring traversal of all workspace history.

Do not generate model-written descriptions in this task. Store or expose the fields only.

## Constraints

- Branches reference snapshots; they never own full snapshot copies.
- Named roots are mutable references; snapshots are immutable.
- No silent last-writer-wins behavior.
- No automatic merge/rebase on promotion failure.
- No agent-specific branch type.
- Do not depend on a concrete store backend.

## Tests

Add tests for:

- branch creation from an existing snapshot;
- workspace base remains fixed while current snapshot advances;
- branch creation does not materialize a copied snapshot mapping;
- successful compare-and-promote;
- stale-root promotion failure reports actual snapshot;
- concurrent workspaces preserve both results;
- abandoned workspace leaves named root untouched;
- failed-validation workspace leaves named root untouched;
- compact branch metadata can be read without opening full history.
