# Implement Server/Client Inspect Transport

## Objective

Implement the first remote-capable vertical slice: inspect one entity through the shared application operation, server adapter, protocol contract, and reusable Rust client.

Read first:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`
2. `design/level-2/011. application operations protocol and runtime boundaries.md`
3. `design/level-3/012. implement application operation primitives.md`
4. `design/level-3/013. implement protocol contract and schema export.md`

This task must prove that remote use preserves the same semantics as embedded use.

---

## Scope

Implement only enough transport/runtime behavior for:

```text
inspect entity
runtime capabilities
operation status
```

Do not implement the whole API surface.

Start with an in-process transport abstraction and server dispatcher so behavior is testable without binding a TCP port. If the repository already has an approved HTTP framework design, add the HTTP adapter behind the same transport-neutral dispatch boundary; otherwise do not choose a framework here.

## Server Application Interface

`scriberig-server` must receive an application service/trait/object through construction.

Do not instantiate the persistence backend inside request dispatch.

The server dispatcher should conceptually perform:

```text
decode protocol request
-> validate protocol compatibility
-> construct application request context
-> invoke application operation
-> map application result/error to protocol form
-> return response
```

Mapping code belongs in the server adapter or a small explicit conversion module if needed.

Do not make `scriberig-protocol` depend on app types to avoid mapping work.

---

## `dispatch.rs`

Implement dispatch for the initial requests:

```text
InspectEntityRequest
RuntimeCapabilitiesRequest
OperationStatusRequest
```

Each request must return a typed protocol response or typed protocol error.

No database query should appear directly in this module.

No semantic diff, migration, or graph traversal algorithm should be implemented here.

---

## `transport.rs` on the Server

Define a small transport-facing boundary that can accept a protocol request and produce a protocol response.

For the first task provide an in-process implementation suitable for tests.

It should preserve:

- request/correlation identity;
- protocol version checks;
- structured errors.

Do not expose private server structs through the public client API.

---

## `client.rs`

Expose semantic client methods for the initial capabilities.

Required methods/concepts:

```text
inspect(...)
capabilities(...)
operation_status(...)
```

The client constructs protocol requests, sends them through its `Transport`, decodes the typed response, and returns structured errors.

Do not require callers to know endpoint names or serialization details.

---

## Client `transport.rs`

Define a client transport trait/interface that is independent of the semantic methods.

Provide an in-process transport implementation that points at the server dispatcher for tests.

The purpose is to establish the boundary that a later HTTP/WebSocket implementation can satisfy without changing client semantics.

Avoid generic abstractions beyond what the initial requests need.

---

## Operation and Subscription Modules

For this task:

- `operation.rs` should wrap polling/querying operation status through the client;
- `subscription.rs` may define the minimal interface needed by later event streaming but must not invent a network streaming protocol if none is designed yet;
- server `operation.rs` may adapt the application operation registry/status provider;
- server `subscription.rs` may remain a documented minimal abstraction until event streaming is implemented.

Do not create fake streaming just to populate these modules.

---

## Protocol Compatibility

The transport path must check protocol major version before executing semantic operations.

Unsupported major versions return a structured protocol error.

The check belongs above semantic application logic.

---

## Snapshot Preservation

The inspect request must support an explicit snapshot.

The remote result must report the same resolved revision and snapshot as direct application-layer inspection against the same test world.

Do not replace exact snapshot identity with "latest" during transport mapping.

---

## Tests

Add server/client integration tests that use the in-process transport.

Required cases:

1. inspect a known entity at a known snapshot;
2. inspect a missing entity and verify structured `NotFound` category;
3. request an unsupported protocol major version;
4. retrieve runtime capabilities;
5. compare direct application inspect result with client/server inspect result for semantic equivalence.

Do not compare terminal formatting strings.

No external network access is allowed in tests.

---

## Do Not Do

- Do not access SQLite directly from server code.
- Do not duplicate inspect semantics in `dispatch.rs`.
- Do not make client depend on server internals.
- Do not add CLI/TUI code.
- Do not implement agent execution.
- Do not choose an HTTP framework unless already prescribed by another accepted design.
- Do not broaden the task to every command/query.
