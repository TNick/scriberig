# Expose Trust Inspection in CLI

## Objective

Add CLI commands/views for inspecting provenance, validation, policy decisions, conflicts, and capability denials through the shared application/protocol model.

The CLI is a product surface. It must not bypass application trust rules or read backend tables directly.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 30, 37–39, 41 and 53–54.
2. `design/level-1/011. runtime libraries protocol and product surfaces.md`.
3. `design/level-3/007. expose trust state through protocol and events.md`.
4. Existing CLI Level 2/3 designs and command conventions.

If the CLI/app operation boundary is not implemented, stop and report the prerequisite.

## Expected Area

Work only in the existing CLI crate and shared client/application abstractions. Typical files may include:

```text
crates/scriberig-cli/src/commands/trust.rs
crates/scriberig-cli/src/commands/inspect.rs
crates/scriberig-cli/src/output/... 
```

Adapt to actual structure. Do not create a second CLI framework.

## Commands / Views

Extend the existing inspect/history command model rather than inventing a disconnected security CLI. Provide ways to inspect:

```text
object provenance
validation evidence
promotion/policy evaluation
approval evidence
projection conflicts
external-effect state/receipts
```

A compact default view should show summary information first, for example:

```text
source: model_generated
validation: current / stale / failed / unknown
accepted via: promotion <id>
```

Then provide an explicit deeper view that follows handles to exact provenance and evidence objects.

## Denials

When a command is denied, print the structured denial with:

```text
requested action
requested scope
reason
narrower alternatives if present
whether approval may grant it
```

Do not print hidden object content or secrets as part of the denial.

Use a distinct non-zero exit status for authorization denial according to the CLI's existing error conventions.

## Machine-Readable Output

If the CLI already supports JSON or another machine-readable mode, ensure trust/validation/denial results are available there using protocol/application types rather than scraping human output.

Do not create a new output format solely for this task.

## Event / Progress Output

For long-running validation/promotion/external-effect operations, use the common event stream if available. Show meaningful states such as validation started/completed, approval required, conflict detected, and promoted.

Do not infer success from process silence.

## Tests

Add CLI tests for:

1. compact provenance summary;
2. deep provenance inspection by handle;
3. failed validation display;
4. stale validation display;
5. policy rejection vs capability denial remain distinct;
6. conflict display includes resolvable IDs;
7. denied operation returns expected exit status;
8. JSON/machine-readable form preserves structured fields;
9. no secret value is printed by receipt/denial fixtures.

## Validation

Run Rust workspace format/check/tests/lint plus any CLI snapshot tests already used by the repository.

## Do Not

Do not query SQLite tables directly. Do not add a CLI-only authorization bypass. Do not flatten provenance into unstructured log text. Do not expose credential material.

## Completion Checklist

- [x] trust information is inspectable from CLI;
- [x] compact and deep views exist;
- [x] denials are structured and distinguishable;
- [ ] machine-readable output stays structured;
- [x] CLI uses shared application behavior;
- [x] tests cover failure and confidentiality cases.
