# Implement project onboarding across product surfaces

## Purpose

Project onboarding registers a filesystem project, captures a reviewable scan
manifest, imports supported source files into immutable semantic state, and
keeps project ownership separate when several projects share one SQLite
database.

The reusable implementation lives in `scriberig-project`. CLI, TUI, HTTP, and
web code call that service; they do not write project tables or semantic
revisions directly.

## Durable model

The database contains one catalog row per project. A project has a stable
`ProjectId`, display name, canonical path, lifecycle status, and optional
current snapshot. Scan files are keyed by `(project_id, relative_path)` and
retain exact bytes, digest, adapter, and classification. Imported semantic
entities are keyed by project ownership records so a later import can remove
entities belonging to deleted files without affecting another project.

Every import creates a successor immutable snapshot and promotes a
project-specific root with compare-and-swap semantics. Snapshot records, the
project root, ownership rows, and project status are committed in one SQLite
transaction. A failed promotion leaves the prior project snapshot and
ownership visible.

## Lifecycle

1. `scan` canonicalizes the path, registers or reuses the project, walks a
   deterministic tree, excludes generated and VCS directories, and persists a
   manifest for review.
2. The caller reviews the manifest and chooses `import`.
3. `import` reads only the persisted manifest, stores source artifacts, invokes
   the Markdown, Rust, and PDF adapters, removes the prior project-owned
   entities, and atomically promotes the resulting snapshot.
4. A subsequent scan replaces the manifest. A subsequent import reconciles
   ownership by source-relative path and remains idempotent for unchanged
   input.
5. `relink` changes the canonical path while retaining the project identity;
   the next scan refreshes its manifest.

## Product surfaces

### Simple command line

`srig project scan PATH [--name NAME]` registers a project and prints the
reviewable manifest. `srig project import PROJECT` promotes it. `list`,
`status`, and `relink` provide catalog inspection and path maintenance. Every
command accepts `--db` and `--json` through the existing CLI conventions.

### TUI

`srig tui --project PATH` scans before startup and shows the selected project
context. Adding `--import` completes onboarding before the TUI is launched.
The project service is shared with the CLI, so the TUI observes the same
manifest, snapshot, and multi-project catalog.

### HTTP and web

The server exposes project list, scan, import, and relink operations. Scan and
relink paths are constrained by repeatable `srig serve --project-root ROOT`
allow-list entries; when no roots are supplied, the server allows its current
working directory. The web project manager presents the scan manifest before
offering import and refreshes project status after promotion.

## Failure and safety rules

- Missing paths and paths outside configured server roots are rejected before
  onboarding.
- Unsupported files remain in the manifest and are retained as source-only
  records rather than silently dropped.
- Import errors are structured and do not replace the last successful project
  snapshot.
- Project IDs and snapshot IDs are immutable; paths and display names are
  mutable catalog metadata.
- A shared database may contain any number of projects. Project roots and
  ownership are never inferred from one global current project.

## Verification

The onboarding integration test covers scan, database reopen, import, and
deleted-file reconciliation. SQLite tests cover multi-project catalog
identity and atomic promotion. Server tests cover root authorization. The
workspace quality gate must pass before release.
