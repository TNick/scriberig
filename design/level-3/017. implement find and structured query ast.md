# Implement Find and the Structured Query AST

## Objective

Implement the universal discovery and structured query vocabulary in `scriberig-query`.

This task adds:

- `find` request/result types for ranked or approximate discovery;
- a storage-independent declarative query AST for exact structural selection;
- a query execution boundary that operates against exact snapshots;
- structured unsupported-query behavior;
- composable semantic results.

This task does not implement application-layer diff/history/render/change composition, protocol transport, UI behavior, or domain-specific high-level edits.

## Files to Create or Modify

Within `crates/scriberig-query/`:

```text
src/lib.rs
src/find.rs
src/query.rs
src/result.rs
src/error.rs

tests/universal_read_model.rs
```

Do not modify concrete storage backends unless an already-defined generic provider trait requires a narrowly scoped test implementation elsewhere.

---

## 1. Implement Find Strategy

In `src/find.rs`, implement an extensible `FindStrategy` or equivalent capable of expressing at least:

```text
ExactText
Token
StructuredName
Semantic
DomainSpecific(String or stable capability id)
```

Do not claim that every provider supports every strategy.

The request/executor must allow a provider to return `UnsupportedCapability` for a strategy it cannot perform.

---

## 2. Implement Find Request

Implement `FindRequest` with conceptual fields:

```text
scope: QueryScope
query: search text/expression
strategy: FindStrategy
page: PageRequest
requested detail: DetailLevel
```

The scope already carries an exact `SnapshotId`.

Do not add a hidden current-snapshot lookup to the query crate.

---

## 3. Implement Find Hits

Implement `FindHit` with at least:

```text
semantic handle
entity type
short label/description
optional preview
optional score/rank
optional projection anchor
optional provenance/derivation summary
```

If a source is only a raw resource and cannot yet be mapped to a semantic entity, model that explicitly rather than inventing a fake entity.

When semantic correspondence exists, the semantic handle is primary; byte/line/page offsets are anchors only.

Implement `FindResult` with:

```text
scope/snapshot
strategy
Page<FindHit>
```

---

## 4. Define the Query Expression AST

In `src/query.rs`, create a small declarative AST.

It must represent at least logical equivalents of:

```text
All
TypeIs
PropertyEq
PropertyExists
Related
MemberOf / ContainedIn
And
Or
Not
```

Use existing universal property values and type/relation/collection identifiers.

Do not embed raw SQL, backend table names, closures, function pointers, or non-serializable storage objects in the public AST.

Keep recursion explicit and bounded by normal memory limits; do not add arbitrary scripting/evaluation.

---

## 5. Query Specification

Implement a `QuerySpec` or equivalent with fields for:

```text
scope
expression
ordering
page/limit
requested detail
```

Provide simple universal ordering concepts such as:

```text
StableDefault
Property { key, direction }
```

Only add ordering variants that can have domain-independent semantics.

Do not promise relevance ranking for exact structural `query`; relevance belongs primarily to `find` unless a specific query predicate defines it.

---

## 6. Relation Traversal Predicates

`Related` must preserve relation identity.

A useful conceptual form is:

```text
Related {
    relation,
    direction,
    target: Box<QueryExpr>,
}
```

This allows expressions like:

```text
TypeIs(Function)
AND
Related(calls, TypeIs(PaymentProvider))
```

Use the schema/graph relation model already implemented.

If reverse traversal requires a derived index that is not available, query execution must return a structured unsupported/derived-data failure rather than silently changing semantics.

---

## 7. Collection Membership Predicates

Provide a collection-membership expression using the established collection identifiers.

The initial AST only needs to express useful membership/containment relationships.

Do not add positional slicing, arbitrary recursive path languages, or XPath-like syntax unless another design explicitly requires it.

Keep the first query model small and composable.

---

## 8. Query Result

Implement a semantic `QueryRow` or `QueryHit` and `QueryResult`.

At minimum return:

```text
semantic handle
entity type
optional compact metadata
```

The result must report the exact snapshot/scope and page continuation.

Avoid returning loosely typed maps as the only result format.

A later query projection may render rows differently, but the core result should remain directly usable by another operation.

---

## 9. Execution Boundary

Expose a `FindService`/`QueryService` trait or integrate with the read-service trait already created.

The executor must operate against graph/index provider abstractions.

Do not put SQL planning inside the public query model.

It is acceptable for the first implementation to execute a limited subset in memory over a graph test provider.

When an AST node is understood by the model but not supported by the provider, return a structured error identifying the unsupported expression/capability.

Do not silently drop predicates.

---

## 10. Determinism and Provenance

`query` should be deterministic for its declared canonical inputs except where it explicitly consumes derived data whose provenance is reported.

`find` may be ranked or approximate.

When semantic or model-derived search is used, return enough provenance/strategy metadata for callers to distinguish it from canonical structural facts.

Do not represent a semantic-similarity rank as a canonical relation.

---

## 11. Tests

Extend `tests/universal_read_model.rs` to cover at least:

1. exact text `find` returns semantic handles in scope;
2. a find hit can be inspected directly without rediscovery;
3. unsupported semantic find strategy returns `UnsupportedCapability` rather than falling back silently;
4. query by `TypeIs` works against an in-memory graph provider;
5. query by property equality works;
6. `And`, `Or`, and `Not` compose correctly;
7. relation traversal can constrain a query;
8. collection membership can constrain a query;
9. reverse relation query without required derived support returns a structured failure;
10. query results report the exact snapshot used;
11. page limits and continuation are preserved;
12. the public AST contains no SQL/backend-specific concepts;
13. malformed/unsupported query expressions produce structured `InvalidQuery` or `UnsupportedCapability` errors;
14. a newer snapshot appearing during/after evaluation does not alter the result's snapshot identity.

Run:

```text
cargo test -p scriberig-query
cargo check --workspace
```

---

## 12. Non-Goals

Do not implement:

- a text query language parser;
- GraphQL;
- SQL generation as a public contract;
- embeddings or model calls themselves;
- diff/history/render;
- branch/apply/commit;
- protocol serialization;
- CLI syntax;
- agent tool schemas.

---

## Completion Criteria

This task is complete when:

- `find` supports extensible discovery strategies and semantic results;
- the structured query AST covers the initial Level 1 structural concepts;
- the AST is independent of storage implementation;
- exact snapshot scope is preserved in every request/result;
- unsupported provider capabilities fail explicitly;
- query/find results return handles reusable by `inspect`, `list`, and `follow`;
- tests demonstrate composability and the `find` versus `query` distinction.
