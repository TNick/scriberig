# Implement: Projection End-to-End Conformance Slice

## Objective

Complete the first executable vertical slice of Scriberig projections by wiring the generic projection layer, filesystem synchronization, Markdown adapter, migration/change layer, and storage backend into one end-to-end conformance scenario.

This task should not add new architecture unless a missing lower-layer contract is proven by the integration work. Prefer fixing the responsible lower layer and adding its local tests.

## Read first

Read all projection Level 2 designs:

1. `design/level-2/007. projection crate boundaries and core model.md`
2. `design/level-2/008. filesystem projection synchronization.md`
3. `design/level-2/009. markdown editable projection adapter.md`

Read Level 3 tasks 007 through 013 and the Level 1 documents they reference.

## Files to create/modify

Create an integration test file at a location consistent with the workspace's existing testing convention. Prefer:

```text
crates/sr-markdown/tests/file_sync.rs
```

If cross-crate integration tests already have a dedicated workspace crate/directory, use that established location instead and document the choice in the test module.

Modify lower-level files only to fix defects revealed by the acceptance scenarios.

Do not create CLI/API/UI/agent code merely to drive this test.

## Test harness

Use:

- temporary filesystem directory;
- in-memory storage backend where possible;
- real `sr-change` migration/diff behavior;
- real generic projection contracts;
- real filesystem projection synchronization service;
- real Markdown parser/renderer/reconciler;
- fake/deterministic observation source instead of relying on OS watcher timing for most tests.

The test must exercise public crate APIs rather than reaching into private internals.

## Acceptance scenario 1: initial projection

Construct canonical Markdown semantic state equivalent to:

```markdown
# Architecture

## Storage

Objects are immutable.

## Rendering

Files are projections.
```

Then:

1. persist/construct the canonical state using existing graph/store APIs;
2. create a managed editable Markdown projection specification;
3. render it to `architecture.md`;
4. verify exact file exists;
5. verify synchronization state records the canonical base and exact rendered digest;
6. verify a synthetic watcher event for the just-written file does not trigger import.

## Acceptance scenario 2: external semantic edit

Externally replace the file contents with:

```markdown
# Architecture

## Storage

Objects are immutable and content addressed.

## Sessions

Sessions use the same object store.

## Rendering

Files are projections.
```

Feed a modification observation.

Verify:

- file is detected as externally changed;
- parser creates a candidate, not canonical identities;
- Storage paragraph keeps its conceptual entity and gets a new revision;
- Sessions section/entities are newly created;
- unchanged Rendering section/entities retain their IDs/revisions where their own state did not change;
- parent collection revisions change only where structure changed;
- a migration records external-projection provenance;
- a new snapshot/result is produced and promoted through normal change rules;
- canonical state is rerendered;
- new exact file digest becomes synchronization base;
- a watcher event for rerendered output does not cause another semantic migration.

## Acceptance scenario 3: formatting-only edit

Modify the synchronized file only in ways the Markdown adapter defines as presentation-equivalent, such as supported list marker/spacing or blank-line differences in a fixture containing those constructs.

Verify:

- byte digest changes;
- parser/reconciler runs;
- result is `NoSemanticChange`;
- no new semantic migration/snapshot is created solely for formatting;
- configured canonical style may rerender the file;
- synchronization returns to a stable base.

## Acceptance scenario 4: invalid transient edit

Write external content that the supported Markdown adapter treats as invalid/unimportable.

Verify:

- canonical snapshot remains unchanged;
- synchronization base remains the previous valid base;
- projection enters `ImportFailed` or equivalent;
- structured diagnostic contains parse/import stage information;
- fixing the file and sending another event retries successfully.

## Acceptance scenario 5: concurrent disjoint changes

From synchronization base B:

1. change canonical Storage paragraph through a normal semantic migration to produce D;
2. independently edit external file to insert a new paragraph/section elsewhere;
3. process the external modification.

Verify:

- reconciliation receives B, D, and F;
- semantic changes are disjoint and merge automatically;
- resulting snapshot contains both changes;
- resulting file is rerendered from merged canonical state;
- new synchronization base points to merged snapshot.

## Acceptance scenario 6: concurrent conflicting change

From a fresh synchronized base:

1. change one paragraph canonically;
2. change the same paragraph externally to incompatible text;
3. process the event.

Verify:

- no canonical overwrite occurs;
- conflict is structured and identifies base/current/external semantic states;
- projection state becomes conflict/attention-required;
- external file is not silently normalized over the user's conflict;
- synchronization base remains the original base until resolved.

## Acceptance scenario 7: unmanaged/read-only safety

Create one unmanaged file and one managed read-only generated file.

Verify:

- unmanaged file is never rewritten or imported;
- read-only file may be generated;
- external modification of read-only file does not create semantic migration;
- behavior is surfaced as drift/regeneration policy rather than semantic import.

## Acceptance scenario 8: rename/path independence

Rename/move the editable Markdown projection to another configured path using the supported mapping operation/event path.

Verify:

- projection/path metadata changes;
- semantic document/paragraph identities do not change solely due to path;
- subsequent rendering/import works from the new location.

## Invariants to assert directly

Where APIs make it possible, assert:

- exact unchanged entity revisions are reused;
- global snapshot changes only for canonical semantic/config changes, not mere external formatting;
- formatting-only edit changes projection bytes but not semantic revisions;
- synchronization state advances only after successful commit and file write;
- failed import leaves recoverable external state/base;
- all canonical writes are represented by normal migration/change APIs.

At minimum:


If the repository has linting configured, run the workspace lint command as well.

## Failure handling while implementing

If an acceptance scenario fails because a lower-layer public API is missing:

1. identify which existing Level 2/3 responsibility owns it;
2. extend that layer minimally;
3. add a focused unit/conformance test there;
4. keep the integration test using the public API;
5. do not add an integration-only bypass.

If a requested feature depends on an unimplemented prerequisite from earlier design work, implement only the minimum prerequisite contract needed and clearly keep it within the earlier design's invariants.

## Do not do

- Do not add agent behavior.
- Do not create HTTP/CLI/UI shortcuts.
- Do not manipulate storage backend tables directly from tests.
- Do not make test-only hidden IDs part of Markdown.
- Do not replace semantic reconciliation with textual diff.
- Do not weaken conflict handling merely to make the acceptance test pass.

## Completion checklist

- [x] Initial Markdown projection renders and synchronizes.
- [x] External semantic edit becomes a normal semantic migration.
- [x] Unchanged entities are reused.
- [x] Formatting-only edit creates no semantic history.
- [x] Invalid edits are recoverable.
- [x] Disjoint concurrent changes merge.
- [x] Conflicting concurrent changes remain structured conflicts.
- [x] Unmanaged/read-only safety rules hold.
- [x] Path move does not redefine semantic identity.
- [x] Full workspace tests pass.

Stop when all acceptance scenarios and checks pass.
