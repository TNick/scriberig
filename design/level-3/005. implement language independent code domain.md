# Implement Language-Independent Code Domain

## Objective

Implement the language-independent source-code vocabulary described by `design/level-1/007. domain modeling and adapters.md` in `scriberig-domain-code`.

This crate defines broad concepts that are genuinely shared across programming languages. It must not pretend that all languages have the same AST and must not absorb Rust-specific syntax.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. `design/level-3/001. scaffold domain adapter crates.md`
4. current public APIs of `scriberig-core`, `scriberig-schema`, `scriberig-graph`, and `scriberig-migration`

If required shared schema APIs are not yet available, stop and report the prerequisite rather than implementing a private substitute.

---

Add tests under:

## Shared Code Vocabulary

Define broad entity concepts for:

```text
CodeProject
Module
Type
Function
Parameter
CodeGroup
Statement
Expression
Comment
Symbol
Reference
```

These types exist only to support operations and navigation that genuinely overlap across languages.

Do not define Rust-specific constructs such as:

```text
match arm
Rust pattern kinds
attribute syntax
macro invocation details
token trees
trait-specific syntax
```

Those belong to the Rust specialization.

---

## Core Structural Relations

Make the schema capable of representing at least:

```text
CodeProject --contains--> Module
Module --contains--> Type/Function/other declarations
Function --parameters--> Parameter
Function --code_groups--> CodeGroup
CodeGroup --contains--> Statement
Statement/Expression --contains--> language-specific syntax children where specialized schemas allow it
Comment --attached_to--> semantic code entity
Reference --targets--> Symbol or semantic entity
```

Where order is meaningful, collections must preserve order.

Do not store reverse parents as canonical child properties solely for navigation.

---

## Canonical and Derived Boundaries

The shared code domain must distinguish broad canonical source structure from derived compiler analysis.

Canonical-capable concepts include:

```text
author-chosen declarations
parameters
statement/expression structure
comments intentionally preserved
meaningful ordering
code groups when they reflect intentionally preserved source grouping
```

Derived concepts include by default:

```text
resolved symbol targets
inferred types
call graph
control-flow graph
data-flow graph
compiler diagnostics
lint diagnostics
model-generated code-group descriptions
```

Do not mark compiler or model output canonical merely because it is stored in the same graph.

---

## Comment Model

Comments must be first-class where the language adapter preserves them.

Support a shared classification vocabulary at least broad enough for:

```text
ordinary
documentation
explanation
invariant
safety
todo
directive
generated
```

Language adapters may extend or refine this classification.

A source-authored comment and a generated description must remain distinguishable.

---

## Code Groups

Define `CodeGroup` as an explicit semantic navigation layer between a function and its statements.

A code group must be able to carry or reference:

```text
ordered statement membership
optional source-authored leading comment or grouping evidence
optional derived description/purpose
provenance/classification indicating which parts are canonical vs inferred
```

The shared domain must not require every function to have generated descriptions.

A function should remain inspectable even when code-group descriptions have not been produced.

---

## Progressive Disclosure

The schema must support this navigation shape:

```text
Project
  -> Module
     -> Function/Type
        -> CodeGroup
           -> Statement
              -> Expression
```

The model must allow consumers to inspect counts, identifiers, names/signatures where available, and descriptions before loading fine-grained syntax.

Do not flatten a function body into one opaque text property.

---

## Semantic Handles

Every important code entity should be referenceable through normal universal entity handles.

The code domain must not use these as primary identity:

```text
file path + line number
byte range
parser node pointer
compiler-internal transient ID
```

External coordinates may be attached as projection/adapter metadata.

---

## Public API

Expose the minimum stable domain API needed for:

```text
register/obtain the code schema
refer to shared code type/relation identifiers
classify shared comment kinds
construct or inspect CodeGroup metadata through universal graph primitives
```

Do not invent a second graph API.

## Tests

Add tests proving:

- every required shared code type is registered;
- ordered parameters, groups, and statements are representable;
- comments are separate semantic entities;
- generated descriptions remain derived;
- language-specific extension points can add specialized entity/relation types without modifying the shared store;
- obvious invalid relation endpoints are rejected if supported by the shared schema layer;
- no file coordinate is required for code identity.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-code
cargo clippy -p scriberig-domain-code --all-targets -- -D warnings
```

---

## Do Not Do

- Do not create a universal AST for every language.
- Do not add Rust syntax here.
- Do not choose a parser.
- Do not implement compiler analysis.
- Do not create source-file persistence tables.
- Do not make generated descriptions canonical.
- Do not depend on agent crates.
- Do not store code only as raw source text.
