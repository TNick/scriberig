# Implement TUI Application Adapter, Explorer, and Inspector

**Status: [ ] Pending**

## Objective

Make the TUI semantically useful for the first time by attaching it to public `scriberig-app` query/capability contracts and implementing semantic selection, progressive explorer navigation, and entity inspection.

This is the first TUI slice that may advance capability-matrix entries from `planned` to `implemented`.

Read first:

1. `design/level-2/011. application operations protocol and runtime boundaries.md`;
2. `design/level-2/012. capability matrix and cross surface conformance.md`;
3. `design/level-2/021. terminal ui runtime and state architecture.md`;
4. `design/level-2/022. terminal ui views interaction and conformance.md`;
5. tasks 099 and 100.

---

## Service Boundary

Create `src/service.rs` with a TUI-facing adapter/port over public application services.

The adapter must expose semantic operations needed by this task without leaking storage internals. At minimum support the currently available equivalents of:

```text
inspect entity/reference
runtime/context capabilities
```

Add list/follow/find only when matching public application operations exist. If they do not yet exist, keep their UI affordances unavailable rather than querying lower crates directly.

Preserve structured application errors and explicit `ApplicationContext`.

Do not open SQLite or construct the concrete store inside `scriberig-tui`.

---

## Semantic Selection

Implement a stable selection model backed by public Scriberig references/identifiers.

For the first slice, entity selection must distinguish:

```text
conceptual EntityId
exact RevisionId when returned
SnapshotId/context when returned or requested
```

Rows and navigation locations store semantic references, not display-row indexes.

A cursor index may identify which visible row is focused, but activation uses the row's stored reference.

---

## Request/Result State

Expand `Effect` and result actions for typed semantic requests.

Use request/generation identifiers so a late inspect result cannot replace a newer selection's inspector.

Represent view loading explicitly:

```text
NotRequested
Loading
Ready
Failed
```

When a refresh fails after prior success, retaining prior data is allowed only when visibly marked stale.

---

## Inspector View Model

Create a TUI-specific inspector view model derived from public application results.

It should contain only presentation-ready data/references such as:

```text
entity id
revision id
snapshot context
kind/schema summary
short description
important public properties
provenance/trust summary
available next operations/capabilities
```

Do not copy private application/domain structs wholesale into TUI state if a small public projection suffices.

Exact identifiers must be available through an inspect/details action even when compact display shortens them.

---

## Explorer

Implement an explorer with semantic root/row models.

If public list/follow operations are not yet implemented, the first explorer may start from explicitly entered/go-to entity identifiers and maintain navigation history of inspected entities. It must not fake relation/collection trees.

When list/follow becomes available during implementation, support expandable rows using those operations and bounded/paginated result models.

Expansion state is keyed by stable semantic references.

---

## Go-To / Inspect Input

Add a palette action equivalent to `Go to entity` or `Inspect entity`.

Collect a valid `EntityId` through an input overlay, then produce the typed inspect effect.

Invalid identifiers stay in input state with a clear parse message; they must not reach application code as fabricated IDs.

Activation of a successful result pushes a semantic navigation location.

---

## Capability-Driven Palette

Attach shared runtime/context capability information to the palette.

At minimum:

- inspect appears only when the application context permits it;
- unavailable semantic actions are absent or visibly disabled according to the metadata available;
- denial returned by the application is still handled even if the palette thought the action was available.

Do not infer authorization from local process ownership.

---

## Error and Trust Presentation

Map structured application error categories into safe presentation states.

Permission denial, not-found, unsupported operation, and internal failure must be distinguishable.

Show trust/provenance summary from public inspect results when available. Use text/symbols in addition to color.

Do not emit untrusted control characters directly to the terminal.

---

## Test Fixture

Use a deterministic in-memory/application fixture where possible. Do not make TUI crate tests depend on a developer SQLite database.

Test at least:

- inspect success renders expected stable identifiers/summary;
- exact revision and snapshot context are not conflated;
- not-found/permission-denied produce distinct states;
- stale late result does not replace a newer inspector request;
- invalid entity input never calls the service;
- semantic activation pushes navigation history;
- capability absence prevents advertising the action;
- rendered external text is sanitized for terminal control characters.

---

## Capability Matrix

Update `capabilities.toml` only for functionality that actually exists after this task.

Expected first progress is for capabilities equivalent to:

```text
inspect_entity
runtime_capabilities
```

Use `implemented`, not `verified`, unless the repository conformance suite actually proves the TUI adapter semantics in this task.

---

## Out of Scope

Do not implement:

- direct database access in the TUI crate;
- canonical mutations;
- history/diff/projection views;
- agent/session views;
- remote client mode;
- fake relation trees when list/follow application APIs are absent.

---

- [ ] Go-to/inspect input validates identifiers.
