# Implement Project-Wide Source Change Candidates

## Objective

Extend the normal candidate/migration path so one exact-base candidate can create, update, and delete multiple project source files as one coherent reviewed change.

The required self-hosting shape is conceptually:

```text
P@S0
-> Candidate C1
   Create crates/domains/scriberig-domain-php/Cargo.toml
   Create crates/domains/scriberig-domain-php/src/lib.rs
   Update workspace Cargo.toml
   Update project scan/import source
   Add tests/fixtures
   Update lock/registry metadata as needed
-> inspect/render/review C1
```

Before Apply:

```text
P.current == S0
live checkout bytes == base checkout bytes
created candidate files do not exist in the live checkout
```

This task creates/reviews the candidate only. Isolated whole-project validation and multi-file Apply/materialization are completed by task `126`.

## Reuse the Canonical Change Type

Do not introduce a canonical `AgentRepositoryPatch`, `TuiPatch`, or `GitPatchCandidate` that bypasses existing migration/proposal semantics.

Extend the normal change representation so one migration/candidate can contain the source effects required by a coherent project change.

A transient provider-facing text patch is acceptable only if it is converted into the shared candidate representation before it becomes durable/reviewable.

---

## Source Effect Semantics

Support shared source effects equivalent to:

```text
Create {
  relative_path,
  expected_absence,
  new_content/projection,
  metadata
}

Update {
  relative_path,
  expected_base_source/digest,
  new_content/projection,
  metadata
}

Delete {
  relative_path,
  expected_base_source/digest,
  metadata
}
```

Fit these concepts into existing migration operations where possible.

Do not accept authoritative client-provided absolute target paths.

Every effect belongs to:

```text
project_id
exact base snapshot
candidate/migration id
```

---

## Exact Base and Per-Path Preconditions

The aggregate candidate must name one exact project base snapshot.

For update/delete, retain the exact source identity/digest expected by the candidate.

For create, retain expected absence/conflict semantics.

Do not defer all source preconditions until filesystem write time if candidate construction can already prove the request is mismatched to its base.

A client request that says "update path X" without sufficient exact base/source context must either be enriched from the exact selected candidate base by trusted application code or rejected as ambiguous.

---

## Project-Relative Path Safety

Normalize/validate project-relative paths through shared project/projection/filesystem helpers.

Candidate creation must reject obvious invalid targets such as:

```text
../outside
absolute paths
empty/invalid paths
paths associated with a different project context
```

Final symlink/external filesystem checks still happen through task `126`/existing apply infrastructure.

Do not duplicate path policy independently in agent runtime and TUI.

---

## Create-New-File Candidate Projection

A proposed new source file must be renderable/reviewable even though it is absent from the live checkout.

Add or extend candidate projection APIs so callers can request conceptually:

```text
candidate C / changed path -> proposed source text
```

The response includes:

```text
candidate/base context
relative path
effect kind = create
new source text/content identity
semantic mapping when candidate reconciliation provides one
```

Do not create the live file early merely to reuse the existing file renderer.

---

## Update Existing File Candidate Projection

For an update effect, review/render must expose:

```text
relative path
base source identity/text
candidate source identity/text
diff
semantic context when available
```

The base content comes from exact project/candidate base state, not from an unchecked fresh read presented as historical truth.

---

## Delete Candidate Projection

For delete effects, review must show:

```text
relative path
effect kind = delete
base source/content identity
candidate absence
```

The live source remains present before acceptance.

---

## Aggregate Candidate Result

Candidate creation returns one durable identity and exact context equivalent to:

```text
candidate/migration id
project id
base snapshot
candidate/result snapshot if constructed
provenance
changed path count
create/update/delete counts
```

If candidate semantic reconciliation creates a candidate snapshot, all source effects must be represented coherently in that candidate state.

Do not make each file its own independently applicable migration when the user's one feature requires all files together.

---

## Candidate Snapshot and New Source Entities

Where the repository's projection/import/reconciliation model supports representing the candidate source semantically before apply, new source files may create candidate-only source/domain entities.

These entities must be reachable only in candidate/result state and must not become current project ownership merely because candidate construction succeeded.

If full semantic reconciliation for a new path is not yet available generically, retain truthful source-level candidate effects and allow validators to operate on the candidate workspace in task `126`. Do not fabricate semantic entities.

---

## Multi-File Request Shape

Extend the public application operation used by human/agent callers to accept a bounded set of source effects or an equivalent structured project edit.

The request must include/resolve:

```text
project id
exact base snapshot
ordered effects
provenance/initiating surface
```

Order should be deterministic for hashing/review even when semantic meaning is set-like.

Enforce reasonable request/result size limits and use content/blob references if existing infrastructure supports large payloads.

---

## Agent Tool Contract

Extend the existing agent change tool rather than adding a privileged write tool.

The provider-facing tool may expose a coarse shape equivalent to:

```text
propose_project_change {
  base project/snapshot,
  files: [create/update/delete ...]
}
```

but it must delegate to the shared application/migration operation.

The tool result returns stable `CandidateId`/migration identity, not merely "patch applied" text.

The implementation branch in the golden scenario does not receive normal Apply authority.

---

## Human/Agent Equivalence

Add conformance proving a project-wide candidate produced through an agent adapter and an equivalent candidate produced directly through public application APIs have the same canonical change meaning.

Random IDs/timestamps/provenance initiator may differ.

Both must be consumable by the same:

```text
change detail
changed path listing
source diff/render
validation
apply
history
```

interfaces.

---

## Aggregate Diff Contract

Extend existing diff/change-summary output to list all changed paths and effect kinds.

Required structure is equivalent to:

```text
Candidate C
Base S0
Changes:
  A path/to/new-file
  M Cargo.toml
  M crates/scriberig-project/src/...
  D optional/old-file
```

Per-path detail exposes old/new text or another faithful source diff representation.

Semantic diff may supplement source diff where reconciliation supports it.

Do not generate semantic claims solely by parsing UI diff strings.

---

## TUI Review Scaling

Extend/reuse the normal TUI change review so it can display a candidate with many changed paths.

Required interaction:

- show candidate/base/provenance summary;
- show changed path list with create/update/delete markers;
- select a path;
- inspect old/new or unified source diff;
- return to path list without losing candidate context;
- show validation placeholder/state from shared candidate even before task `126` adds full project profile;
- no Apply success behavior implemented privately here.

Keep large file content bounded/scrollable.

---

## Protocol and Clients

Extend canonical protocol/client types once so remote/web/TUI adapters can inspect the same project-wide candidate.

Do not serialize a Rust internal enum differently for every surface without a shared protocol contract.

Required public capabilities include conceptual equivalents of:

```text
create project candidate
get candidate detail
list/page candidate changed paths
get candidate path diff/render
```

Preserve backward compatibility/versioning according to existing protocol rules.

---

## Durability and Restart

After candidate creation, close/reopen application/client/session views and prove:

- candidate identity remains valid;
- exact base snapshot remains visible;
- changed paths/effect kinds remain inspectable;
- candidate-only new file content can still be rendered;
- live project root/tree remain base.

Do not rely on an in-memory provider response to reconstruct the patch.

---

## Negative Cases

Cover at least:

- duplicate conflicting effects for the same path in one request -> reject/normalize deterministically, never ambiguous apply;
- create path already represented in exact base when expected absent -> reject;
- update/delete path missing from exact base -> reject unless operation semantics explicitly support that state;
- path escape -> reject;
- project/base mismatch -> reject;
- stale base at review -> mark stale according to existing change rules;
- candidate request cancellation/failure -> no current snapshot/live filesystem mutation;
- oversized source effect -> structured limit/error rather than uncontrolled memory use.

## Required Focused Tests

### PROJECT-CANDIDATE-01 — create + update

Against a temporary project, create one candidate that adds a new Rust source file and updates an existing config/source file. Assert one candidate identity, exact base, live files unchanged, and candidate render contains both effects.

### PROJECT-CANDIDATE-02 — create multiple files

Add a small new crate (`Cargo.toml` + `src/lib.rs`) plus workspace registration in one candidate. Assert created files are candidate-renderable but absent live.

### PROJECT-CANDIDATE-03 — delete

Propose deletion of an owned file. Assert candidate review shows delete and live file still exists.

### PROJECT-DIFF-01 — aggregate and per-path review

Inspect through public APIs; assert effect list/order/types and representative old/new content.

### PROJECT-DURABLE-01 — restart/reopen

Reopen database/application/client and recover candidate plus new-file content from durable state.

### PROJECT-AGENT-01 — agent uses shared candidate

Script deterministic provider to request a two-file project change. Assert normal candidate returned and no direct file write/current-root advance.

### PROJECT-EQUIV-01 — direct vs agent initiation

Compare equivalent direct/agent candidates semantically and prove both use normal review APIs.

### TUI-PROJECT-REVIEW-01 — real PTY

Open a pre-created project-wide candidate through normal TUI UI, browse create/update path diffs, and assert live tree unchanged.
