# Implement Deterministic Self-Hosting Provider Scenario for PHP Ingestion

## Objective

Extend the existing deterministic/scripted agent provider and golden harness so, through normal provider-neutral tool requests, it can perform the semantic discovery and project-wide candidate construction required by the PHP self-hosting scenario.

The scripted provider is test configuration. Production runtime must not contain a literal-prompt shortcut or a privileged PHP patch path.

Required provider behavior after onboarding `P@S0` and receiving:

```text
Add support for ingesting PHP source files.
```

is conceptually:

```text
observe exact P@S0
-> discover semantic tools
-> read project/design guidance semantically
-> run read-only architecture child branch B1
-> receive compact architecture BranchResult
-> run implementation child branch B2
-> inspect exact targets @ S0
-> propose one normal project-wide candidate C1
-> validate C1 through shared profiles
-> inspect C1
-> return terminal result with CandidateId C1
```

No Apply is performed by the agent in this task.

## Provider-Neutral Requirement

The deterministic provider must communicate only through the same normalized model/provider request/response contracts used by real providers.

It may be scripted based on:

- normalized semantic context;
- available tool definitions;
- prior tool results;
- test scenario state.

It must not invoke application Rust internals directly from the provider fixture.

Production agent runtime must not contain code equivalent to:

```rust
if prompt == "Add support for ingesting PHP source files." {
    install_fixture_patch();
}
```

The deterministic behavior belongs in test/provider configuration.

## Exact Scope Assertion

At the first model turn for the PHP command, capture normalized request evidence and assert:

```text
project_id == onboarded P
snapshot_id == S0
root/selection context corresponds to active project
```

The provider should refuse or fail its scripted test if exact project/snapshot context is missing.

A prompt containing the word `scriberig` is not sufficient evidence.

## Initial Tool Discovery

The provider requests trusted capability discovery and verifies it can reach semantic read/branch/change/validation tools appropriate to its current scope.

Expected conceptual catalog includes:

```text
inspect
find
query
render
follow/list as useful
branch.start or normal nested-branch request mechanism
change.propose for implementation branch
change.inspect
validate
```

`change.apply` must be absent from or unused by the implementation branch golden policy.

Direct database/live filesystem mutation tools must not be used.

## Semantic Project Guidance Reads

Before proposing source edits, the provider must use imported project semantics to retrieve governing guidance and relevant design/source precedent.

At minimum the scripted sequence should semantically locate/render:

```text
AGENTS.md
design/AGENTS.md
relevant domain adapter/code-domain design
representative language adapter source
project scan/classification source
project adapter/import dispatch source
workspace Cargo metadata
```

Exact entity IDs are discovered at runtime from `P@S0`; do not bake database-generated IDs into the script.

Source-relative path/name expectations may be used as deterministic search anchors.

## Architecture Discovery Child B1

The provider/orchestrator starts B1 with:

```text
purpose = determine minimal extension points for PHP source ingestion
base = P@S0
capabilities = read-only semantic set
expected result = architecture map
```

B1 performs normal semantic find/inspect/render operations.

The test captures tool invocation evidence proving B1 lacks/does not use mutation tools.

B1 returns a compact result including stable refs for actual current owners such as:

```text
language domain precedent
project scan classifier
project adapter importer
workspace manifest
relevant conformance/test owner
```

The parent receives the `BranchResult`, not the complete transcript.

## Implementation Child B2

```text

```

B2 re-inspects/renders exact edit targets at `S0` before constructing its candidate.

This proves the architecture result is guidance, not a stale unchecked patch coordinate.

If the tool result exposes source diff/path pages separately, the script follows the public pagination/detail operations rather than accessing internal migration tables.

## Validation Tool Sequence

The scripted implementation branch requests shared validation profiles in a sensible order:

```text
php-domain-focused
project-import-focused
rust-workspace
project-ingestion-e2e
```

The exact names may match implementation policy from task `126`.

Observe operations/results through normal application tool path.

On success, retain stable `ValidationId`/operation refs in branch result.

No validation step may write the live project checkout.

---

## Scripted Validation Failure Path

Add a second deterministic scenario that intentionally proposes one known-bad candidate variation or causes a controlled validation failure.

The provider must:

1. receive structured failure;
2. inspect bounded diagnostics;
3. revise/supersede candidate through normal shared change operation;
4. rerun focused validation;
5. continue only after success.

This proves the provider/runtime supports iterative candidate repair without a hidden direct-edit loop.

The failure can be a deterministic source/API mismatch designed solely for test configuration, but production runtime must remain generic.

## Cancellation and Tool Failure

Script focused cases for:

- cancel B1: no candidate/project mutation;
- cancel B2 before candidate: no candidate/current/file mutation;
- fail candidate tool: operation/branch fails structurally;
- validation failure without successful repair: root result must not claim validated candidate;
- stale `S0` before proposal: shared change tool rejects or marks stale according to task `125`; provider must not silently retarget;
- tool capability denied: provider cannot bypass catalog through raw database/filesystem mutation.

### SELFHOST-PROVIDER-05 — candidate validation

Run all required profiles against `C1`; assert durable successful evidence and candidate E2E actually imports/finds/renders PHP.

### SELFHOST-PROVIDER-06 — repair loop

Trigger controlled candidate validation failure, observe structured diagnostic, create corrected candidate through normal change path, and reach success without live write.

### SELFHOST-PROVIDER-07 — durable result

Recreate client/session view after operation completion and recover `C1`/validation refs from durable operation/branch state.

### SELFHOST-PROVIDER-FAIL-01

Provider/tool failure before candidate success cannot change project current snapshot or live checkout.

### SELFHOST-PROVIDER-CANCEL-01

Cancel nested/implementation operation and assert same no-mutation guarantees.
