# Implement Domain Schema and Adapter Version Metadata

## Objective

Implement the version/provenance metadata needed to distinguish domain schema evolution from adapter implementation evolution, as required by `design/level-1/007. domain modeling and adapters.md`.

A schema version defines what stored domain knowledge means. An adapter version/profile defines how an external representation or tool maps to that schema. These must not be conflated.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. current schema, provenance, and derived-knowledge APIs
4. `design/level-3/010. implement domain capability discovery.md`

---

## Files to Create or Update

Prefer shared metadata types in `scriberig-schema` and shared provenance types in the crate that already owns provenance/derived metadata.

Expected files are equivalent to:

```text
crates/scriberig-schema/src/version.rs
crates/scriberig-schema/src/domain.rs
crates/scriberig-schema/src/lib.rs
```

and, only if needed by the established architecture:

```text
<shared provenance crate>/src/producer.rs
<shared provenance crate>/src/profile.rs
```

Do not create a new cross-cutting crate solely for two version structs if an existing owner is clear.

---

## Schema Version

Provide an explicit, serializable domain schema version identifier.

It must be suitable for answering:

```text
which schema defines the meaning of this canonical domain revision?
```

Requirements:

- stable across process runs;
- transport-safe;
- comparable for equality;
- independent of Rust crate version unless the project explicitly aliases them;
- included in domain descriptors/registration.

Do not assume semantic-version ordering alone is sufficient to migrate data. Migration support remains explicit.

---

## Adapter/Producer Identity

Provide metadata capable of identifying a producer/adapter independently from the schema.

At minimum represent:

```text
adapter/producer identifier
adapter version
optional profile/configuration identifier
```

Examples include:

```text
Markdown parser adapter
Rust syntax parser adapter
Rust compiler analyzer
PDF extractor
```

The same schema version may be served by multiple adapter versions or entirely different adapters.

---

## Provenance Integration

Derived results created by adapters/analyzers must be able to record:

```text
producer identity
producer version
producer profile/configuration identifier where interpretation depends on it
exact semantic input revisions/dependencies
```

Do not force credentials, machine-local absolute paths, secrets, or volatile timestamps into reusable producer-profile identity.

Configuration identity should include only values that affect interpretation/result semantics.

---

## Canonical Import Metadata

Where imported canonical knowledge depends on the adapter's interpretation, preserve enough import provenance to know which adapter mapped the external source into the schema.

Do not make adapter metadata itself part of an entity's semantic content unless the domain explicitly requires that producer identity to distinguish canonical meaning.

The common case should keep semantic state and provenance related but distinct.

---

## Schema Migration Boundary

Provide types/metadata sufficient to distinguish:

```text
ordinary user-content migration
```

from:

```text
domain schema migration
```

Do not implement a full schema migration engine in this task unless one already exists and only needs these metadata hooks.

A future schema migration must be able to state:

```text
from schema version
to schema version
migration implementation/profile
input snapshot/scope
result snapshot/scope
```

---

## Capability Discovery Integration

Update domain capability descriptors so clients can observe:

```text
current installed schema version
provider/adapter versions for advertised capabilities where relevant
```

Do not expose implementation details that are not needed by clients.

---

## Tests

Add tests proving:

- schema version and adapter version are distinct types/fields;
- two adapters can target the same schema version;
- one adapter can evolve versions while the schema remains unchanged;
- derived output provenance records adapter version/profile;
- domain descriptor exposes schema version;
- capability provider metadata can expose adapter version;
- schema migration metadata distinguishes schema transitions from ordinary content migrations;
- serialization is deterministic/stable according to project conventions.

Run formatting/tests/clippy for affected crates.

---

## Do Not Do

- Do not equate schema version with Cargo package version automatically.
- Do not make every adapter update force a schema migration.
- Do not put secrets into producer/profile metadata.
- Do not implement automatic schema migration heuristics.
- Do not make provenance disappear when derived data is cached.
- Do not depend on agent crates.

---
