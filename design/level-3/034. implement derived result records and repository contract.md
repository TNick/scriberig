# Implement Derived Result Records and Repository Contract

## Objective

Implement immutable derived-result records and the backend-independent repository contract described by the derived-knowledge Level 2 design.

This task builds on the derivation profiles, dependencies, and keys created by the previous task.

It must make it possible to store, retrieve, and inspect immutable derived results without coupling the derivation layer to SQLite, an agent runtime, or a server.

Do not implement invalidation, selection policy, freshness policy, retention policy, events, or domain-specific derivation execution in this task.

## 1. Derived Result Status

Define a small public status model for an immutable derivation attempt/result.

It must be able to represent at least conceptual equivalents of:

```text
Succeeded
FailedDeterministic
FailedTransient
Cancelled
```

If cancellation is better represented as transient/non-cacheable metadata according to existing project conventions, preserve that distinction clearly.

The key requirement is that consumers can tell whether a failure may safely satisfy a later identical request or should normally be retried.

Do not infer retryability from a human-readable error string.

---

## 2. Derived Result Record

Define `DerivedResultRecord` or the canonical equivalent.

It must bind together:

```text
DerivationKey
DerivedArtifact or exact artifact reference
status
provenance
optional failure metadata
optional observation/creation metadata when the existing shared types support it
```

Do not make the artifact canonical simply by wrapping it in this record.

Do not add a mutable `is_current` field.

Historical results must remain immutable.

Multiple records may exist for derivations that are nondeterministic or intentionally regenerated.

If the existing universal artifact already contains provenance, avoid duplicating contradictory provenance fields. Prefer one authoritative provenance structure and reference it from the result record.

---

## 3. Result Identity

Use existing content/identity abstractions if the project already provides them.

Do not invent a new unrelated hash format.

The repository contract must be able to return one or more stable result handles so later dependency records and selection logic can reference exact historical results.

If no dedicated `DerivedResultId` exists yet, use the narrowest existing immutable object/artifact identifier available and document that choice.

Do not use array indexes or database row numbers as public semantic identity.

---

## 4. Repository Trait

In `repository.rs`, define a backend-independent `DerivedRepository` trait or equivalent.

The first contract must support:

```text
insert immutable result
get exact result by result handle
find all results for exact DerivationKey
find results associated with an entity/revision when indexed
record dependency metadata for a result
read dependency metadata for a result
lookup result handles by dependency
remove disposable derived records when explicitly requested
```

The trait may be synchronous unless the repository already has an established async abstraction at this layer.

Do not add Tokio merely to future-proof the trait.

The trait must describe semantic operations, not SQL.

---

## 5. Duplicate and Concurrent Insert Semantics

Document and implement deterministic semantics for inserting the same immutable result more than once.

At minimum:

- inserting an identical immutable result must not corrupt storage;
- repository implementations may deduplicate exact results;
- multiple distinct results for one derivation key must be allowed;
- no insertion operation may overwrite a previous historical result in place.

The repository abstraction should be compatible with two workers finishing the same derivation concurrently.

Do not require process-local locking in the public API.

---

## 6. Dependency Recording

A result must expose or allow repository lookup of the exact dependencies from its `DerivationKey`.

The repository must not require consumers to reverse-engineer dependencies from arbitrary payload bytes.

If dependency indexing is maintained separately from the result record, make that relationship explicit in the trait.

The final invalidation task will use this lookup.

Do not implement invalidation logic yet.

---

## 7. Entity/Revision Lookup

Provide a narrow lookup path that lets diagnostics and navigation discover derived results associated with an exact entity/revision.

This is not the validity mechanism.

Exact validity still comes from `DerivationKey` dependencies.

The entity/revision association is for discovery, history, and inspection.

Do not implement ambiguous implicit-current entity lookup.

---

## 8. In-Memory Test Repository

If no generic memory repository already exists for derived data, implement a minimal in-memory repository **inside tests or a test-support module**, not as a new production backend crate.

It should be sufficient to verify the repository contract.

Do not introduce a permanent memory backend API unless another design already establishes one.

Required behavior:

- immutable insert;
- exact lookup;
- key lookup returning multiple results;
- dependency lookup;
- explicit removal of a disposable result;
- old records remain unchanged after newer compatible results are inserted.

---

## 9. Public Exports

Update `lib.rs` to expose the intended public equivalents of:

```text
DerivedResultRecord
DerivedResultStatus
DerivedRepository
```

Keep failure metadata types public only if clients need them to inspect results.

Avoid exposing test-support implementations as production API.

---

## Required Tests

Add focused tests for:

1. successful result record creation;
2. deterministic failure record;
3. transient failure record;
4. two distinct results for one exact derivation key coexist;
5. reinserting an identical immutable result is safe;
6. exact result lookup works;
7. exact key lookup returns all matching records;
8. dependency metadata can be retrieved without inspecting payload bytes;
9. reverse dependency lookup returns the stored result handle;
10. entity/revision discovery lookup does not replace exact key validity;
11. explicit deletion/removal affects only derived storage and does not invoke any canonical snapshot operation.

Use fake universal artifacts and test profiles. Do not introduce production domain vocabulary.
