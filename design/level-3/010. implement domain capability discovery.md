# Implement Domain Capability Discovery

## Objective

Implement the generic capability-discovery mechanism required by `design/level-1/007. domain modeling and adapters.md` so clients can inspect an entity and learn what installed domain functionality is available without hard-coding every domain.

Capability discovery must be useful to CLI, API, browser, third-party libraries, and future agent tools. It must not depend on an agent runtime.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. current public APIs of `scriberig-schema`, `scriberig-graph`, `scriberig-projection`, and `scriberig-app`

Do not create a parallel plugin system if the repository already has a schema/domain registry. Extend the established registry instead.

---

## Files to Create or Update

Prefer implementing static domain/type capability metadata in `scriberig-schema` and runtime-installed capability aggregation in the lowest shared layer that already owns installed services.

Expected files are equivalent to:

```text
crates/scriberig-schema/src/domain.rs
crates/scriberig-schema/src/capability.rs
crates/scriberig-schema/src/registry.rs
crates/scriberig-schema/src/lib.rs
```

If runtime capability providers already belong in another existing shared crate, place only the runtime aggregation there and keep schema/type declarations in `scriberig-schema`.

Add tests in the owning crate(s).

---

## Domain Descriptor

Provide a stable descriptor for an installed domain/schema.

It must expose at least:

```text
domain identifier
human-readable name
schema version
entity types provided
relation types provided
```

Where the architecture already has equivalent identifiers, reuse them.

Do not make crate names or Rust `TypeId` values the public domain identity.

---

## Entity Capability Description

For an entity type in a given installed domain configuration, capability discovery should be able to advertise categories equivalent to:

```text
available relations
available child/collection views
available descriptions/summaries
available projections
available semantic commands
available analyses
available validation capabilities
```

Not every capability needs an implementation in this task. The discovery model must support advertising only capabilities that are actually installed/available.

Do not claim a capability merely because a schema concept exists if no provider can execute it.

---

## Capability IDs

Use stable semantic IDs/names for capabilities.

Examples of the shape, not mandatory exact names:

```text
projection.markdown
analysis.rust.references
command.markdown.rename_heading
validation.rust.compile
view.session.branch_tree
```

Capability IDs must be transport-safe and independent of Rust symbol names.

Avoid embedding implementation-specific version numbers into the semantic capability ID. Producer/version metadata belongs beside the capability/provider.

---

## Provider Metadata

When a capability is backed by a specific adapter/analyzer, discovery should be able to expose provider metadata where relevant:

```text
provider/adapter identifier
provider version/profile
availability state
required configuration if known
```

Do not expose secret configuration values.

---

## Generic Inspection Integration

Integrate capability metadata with the existing generic inspect/schema APIs if such APIs exist.

A generic client inspecting a `Function`, `PDFPage`, `Section`, or `Branch` should be able to discover available operations without importing that domain crate directly.

The same mechanism must work for a deployment with only Markdown installed and a full deployment with many domains.

---

## Minimal Deployment Behavior

Test at least two registry configurations:

```text
configuration A:
  universal store/schema + Markdown domain only

configuration B:
  Markdown + code/Rust + PDF + session capabilities
```

Configuration A must not advertise Rust/PDF capabilities.

The absence of an optional domain must not make generic inspection fail.

---

## Tests

Add tests proving:

- domain descriptors are discoverable by stable ID;
- entity types report only installed capabilities;
- a Markdown-only registry does not expose Rust capabilities;
- capability IDs are deterministic and transport-safe;
- provider metadata is attached without leaking private implementation state;
- generic clients can enumerate capability categories without linking agent crates;
- duplicate capability/provider registration is rejected or deterministically resolved according to the established registry policy.

Run workspace formatting/tests/clippy for affected crates.

---

## Do Not Do

- Do not implement agent tools.
- Do not hard-code every domain into `scriberig-core` or `scriberig-store`.
- Do not make optional domain crates mandatory dependencies of the universal store.
- Do not advertise unavailable operations.
- Do not expose Rust implementation type names as wire/public capability IDs.
- Do not put credentials or secret configuration in capability metadata.
- Do not create a second unrelated registry if one already exists.

---

## Completion Checklist

- [ ] Installed domains are discoverable generically.
- [ ] Entity-level capabilities are enumerable.
- [ ] Optional domains remain optional.
- [ ] Capability IDs are stable and transport-safe.
- [ ] Provider/version metadata can be represented.
- [ ] Generic inspection works without agent dependencies.
- [ ] Tests cover minimal and full-style registries.
- [ ] Formatting, tests, and clippy pass.
