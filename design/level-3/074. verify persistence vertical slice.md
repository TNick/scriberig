# Verify: Persistence Vertical Slice

## Objective

Perform the final integration pass for the persistence work derived from Level 1 document 004.

This task should not add a new subsystem. It verifies that the implemented storage slice behaves as one coherent backend-independent platform capability.

## Read first

Read:

1. `design/level-1/004. persistence and storage model.md`
2. all `design/level-2/00*.md` persistence documents created from it;
3. Level 3 tasks 001 through 006.

Inspect the current implementation before making changes. Prefer small corrective changes over redesign.

## Acceptance scenario

Construct the following history through the public `sr-store` API.

### Step 1: canonical revisions

Create entities `A`, `B`, and `C` at revisions:

```text
A -> A1
B -> B1
C -> C1
```

Create snapshot `S1` containing those mappings.

Promote named root `main` to `S1`.

### Step 2: local content change

Create `A2` while keeping `B1` and `C1` unchanged.

Create `S2` from `S1`:

```text
A -> A2
B -> B1
C -> C1
```

Verify:

- `S1` is still readable;
- `S2` differs from `S1`;
- `B1` and `C1` keep the same `RevisionId` values;
- no unrelated entity revision was recreated;
- `main` advances from `S1` to `S2` using compare-and-set.

### Step 3: branch

Starting from `S1`, create `S3` by changing only `B`:

```text
A -> A1
B -> B2
C -> C1
```

Keep `S2` and `S3` simultaneously readable.

Do not implement semantic merge. This step only proves branch storage.

### Step 4: stale promotion

Attempt to promote `main` from expected `S1` to `S3` after it already points at `S2`.

Verify:

- operation fails with the typed stale-root conflict;
- `main` still points to `S2`;
- `S3` remains readable as an immutable snapshot.

### Step 5: durability

Run the scenario using a temporary SQLite database.

Close and reopen it.

Verify:

- `main` still resolves to `S2`;
- `S1`, `S2`, and `S3` remain readable;
- all revision and snapshot IDs match those created before reopen.

### Step 6: cross-backend identity

Run the same logical scenario against the in-memory backend.

Verify the memory and SQLite implementations produce identical logical revision and snapshot IDs for identical canonical content and mappings.

### Step 7: reachability and GC

Treat `main -> S2` as protected and leave `S3` unprotected.

Run GC dry-run.

Verify it identifies only storage that is genuinely unreachable under the implemented retention rules.

If the ancestry/history policy used by the implementation retains `S1`, confirm the report reflects that policy.

Run destructive GC only after recording the dry-run result.

After GC, every protected snapshot must pass integrity verification.

## Implementation corrections allowed

If the scenario exposes a problem, fix it in the owning crate.

Allowed corrections include:

- missing trait methods required by existing Level 2 designs;
- inconsistent error categories;
- backend identity divergence;
- failure to preserve historical snapshots;
- unsafe root promotion;
- structural-sharing implementation bugs;
- integrity or reachability bugs;
- missing tests.

Do not introduce unrelated product features.

## Documentation checks

Ensure public Rust modules have concise documentation explaining:

- entity versus revision versus snapshot;
- immutable revisions;
- named-root compare-and-set behavior;
- backend independence.

Do not duplicate the design documents into API docs; link concepts through concise explanations.

## Commands to run

At minimum:

```text
cargo fmt --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

If the repository has established additional checks by the time this task runs, run them too.

## Final checklist

- [ ] Workspace compiles without higher-level agent/domain dependencies.
- [ ] Memory and SQLite stores implement the same public persistence contract.
- [ ] Immutable historical snapshots remain readable.
- [ ] Deep/local changes preserve unrelated revision identities.
- [ ] Any canonical map change creates a different snapshot identity.
- [ ] Equivalent canonical state produces the same IDs across backends.
- [ ] Named-root promotion is compare-and-set and atomic.
- [ ] SQLite state survives reopen.
- [ ] Reachability and GC preserve protected state.
- [ ] Integrity verification passes on retained state.
- [ ] Formatting, tests, and clippy pass.

When every item is satisfied, stop. Do not proceed into migrations, domain adapters, agents, CLI, server, or web implementation; those belong to later design documents.
