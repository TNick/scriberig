## Rebase model

A rebase takes:

```text
original base snapshot
original result snapshot or migration sequence
new base snapshot
```

and attempts to produce a new descendant of the new base.

Conceptually:

```text
S1 -> S2
 \
  -> S3

rebase S1->S2 onto S3

S3 -> S4
```

`S2` and its migration history remain unchanged.

## Replay order

For each original migration, replay in historical order.

For each change, use this preference order:

1. recorded domain semantic operation through a registered domain replay strategy;
2. recorded universal generic semantic operation;
3. exact entity delta only when it can be applied safely against the new base;
4. structured conflict when intent cannot be preserved safely.

Never fall back to byte offsets, line numbers, or rendered text patches in the universal engine.

## Domain replay strategy

Implement the Level 2 extension point for domain replay.

A domain strategy should receive:

- the semantic operation;
- old base/result references needed to understand it;
- current target snapshot/context.

It should return an equivalent of:

```text
Applied(changes)
Conflict(detail)
NotApplicable
```

The strategy must not mutate historical input state.

## Generic replay

Support replay for universal operations whose semantics remain unambiguous, such as:

- replace entity revision when the target still resolves to the expected old revision;
- insert/remove relation when the precondition still holds;
- collection insertion/removal/move when stable entity identities and anchors still resolve unambiguously.

If a precondition does not hold, return a structured replay conflict instead of guessing.

## Replay preconditions

Each generic operation should define the semantic condition under which it can be safely replayed.

Examples:

```text
ReplaceRevision(E, old, new)
requires target snapshot resolves E -> old

RemoveRelation(A, R, B)
requires relation exists

InsertCollectionMember(after X, Y)
requires X still identifies an unambiguous anchor
```

Do not silently adapt a failed precondition unless a domain strategy explicitly understands the change.

## Rebase result

Return a structure containing at least:

```text
original base
original work/result
new base
new result snapshot if fully applied
new migration records or proposals
conflicts
```

Do not promote the rebased result automatically.

## History preservation

Tests must prove:

- original snapshots and migrations remain readable;
- rebased work receives new result snapshots;
- rebased migration base references the new line of history;
- original and rebased histories are distinguishable even if they converge to the same final state.

## Multi-migration replay

Support replaying a sequence, not only one migration.

Stop or continue after a conflict according to a documented deterministic policy. Prefer stopping at the first unresolved migration unless the implementation can safely isolate independent later work.

Do not partially claim a complete rebase when conflicts remain.

## Tests

Add tests for:

- clean replay of one `ReplaceRevision` onto an unchanged entity;
- replay conflict when the new base already changed that entity differently;
- generic relation operation replay;
- replay of two sequential migrations preserves order;
- domain replay strategy resolves an operation unknown to the generic engine;
- missing domain strategy yields conflict rather than discarded intent;
- original history remains unchanged;
- rebased state is a descendant of the new base;
- same final state through rebase still has distinct history provenance.

## Constraints

- Rebase never rewrites old history.
- Do not use textual patch application.
- Do not silently ignore failed operations.
- Do not automatically promote rebased work.
- Do not introduce domain-specific code into `sr-change`.
