## 7. Delegate Custom Model Properties

Use upstream model/provider metadata for custom and model-specific properties.

This includes current/future upstream equivalents of:

```text
sampling parameters
reasoning maps
compatibility flags
strict-tool support
model input modalities
context window
max output
cost metadata
provider endpoint/public metadata
provider-specific request-shaping values
custom property maps
```

Do not introduce a ScribeRig enum/schema for these fields.

When ScribeRig needs to retain user overrides, store/forward them through an upstream-owned configuration type or an opaque serialized upstream value that upstream validates and resolves.

At the pinned fork revision, `rpi_ai::Model` in
`crates/rpi-ai/src/model.rs` owns `sampling_params` and `provider_options`.
`rpi_model_runtime::models::build_catalog` copies both from
`ModelDefinition` into runtime models. The built-in OpenAI Completions and
Responses adapters merge `sampling_params` into their request bodies in
`crates/rpi-ai/src/providers/openai_completions.rs` and
`openai_responses.rs`; this is upstream request shaping, but is specific to
those adapters. `provider_options` is runtime-only and `#[serde(skip)]`.
Built-in adapters fail closed on non-empty values. The extension ABI accepts an
opt-in `providerOptionsVersion: 1` declaration and sends a versioned
`providerOptions` envelope only to opted-in providers; legacy providers fail
closed. At ScribeRig's current pin, the envelope provides no provider-
application acknowledgment. Fork commit
`9f935d794053bccaf73737b5e2fb67cf3194a761` adds a closed, versioned JSON Schema
for these values and validates them before creating the extension envelope;
the extension still must attest which values it applied. ScribeRig's opt-in
native extension path consumes the older envelope but does not yet consume the
schema/setter API. Do not claim generic custom-option flow through built-in
providers or copy arbitrary properties into ScribeRig DTOs.

## 8. Delegate Provider Authentication and Readiness

Provider authentication, credential resolution, and readiness belong upstream.

ScribeRig may apply product trust/policy around whether a provider can be used, but it must not duplicate credential-source precedence or authentication status resolution.

Required behavior:

```text
upstream provider package/catalog
  -> upstream auth/readiness
  -> safe status projection
  -> ScribeRig TUI/web/server display
```

Acceptance:

- [ ] Provider authentication success/failure status comes from upstream
  runtime evidence. The current readiness response reports only credential
  source availability and must not be presented as a successful auth check.
- [x] Upstream owns the generic protected credential-source APIs. Native
  ScribeRig configuration selects one `SecretRef` and uses upstream's
  `HostSelected` source without adding a parallel precedence chain.
- [ ] Resolved credentials never enter ScribeRig session/protocol state.
- [x] ScribeRig's explicit destination authorization can deny use while the
  upstream protected resolver preserves that denial as an error.
- [ ] Provider reload/auth changes refresh ScribeRig-visible safe status from upstream.

and tools. A provider-attested `applied_settings` report is captured after
request preparation and stored in that projection; the report contains only
upstream-allowlisted values and explicit omitted categories.
The upstream `model_execution_fingerprint` is a versioned digest of a
conservative model-metadata projection, not a complete effective-request
fingerprint. It always excludes the endpoint and may also exclude headers,
runtime `provider_options`, arbitrary sampling parameters, provider-specific
thinking maps, and opaque compatibility data; `complete` is therefore false.
The deprecated `model_configuration_fingerprint` compatibility API delegates
to this digest but returns less coverage metadata. Neither API proves which
configuration the provider applied. Do not persist the full upstream `Model`,
`Debug` output, headers, credentials, or opaque provider options to paper over
this gap.

ScribeRig's request fingerprint is a local identity for the canonical
provider-neutral request projection. It covers provider identity/profile,
model and thinking selection, exact profile/component revisions, compiled
context fingerprint, messages, tools, and local request controls included in
`ModelRequest`. Its context inputs remain ScribeRig-owned and must not be
replaced by an upstream model-configuration digest. It does not include the
upstream `Model` configuration or prove what provider fields were applied.
The active local `ModelCache` key separately identifies the normalized
ScribeRig `ModelRequest` and its cache namespace; neither fingerprint is
output-affecting upstream model-property provenance.

The fork provides `rpi_ai::AppliedRequestSettings`. Built-in OpenAI
Completions, OpenAI Responses, and Anthropic providers report field-typed,
allowlisted values from the final prepared request body. The report omits
credentials, all headers, prompt/transcript, tools/schemas, and opaque fields,
so it remains explicitly incomplete. Extension providers can attest through
their versioned callback; providers without attestation use the
explicitly-incomplete fallback. `upstream_invocation.rs` captures the callback
into `ModelRequestProjection.applied_settings`; persistence and the existing
authorized model-request detail response carry that value to history readers.
This source path is implemented, but focused persistence/omission tests have
not been run. The current `rpi-ai` provider response also has optional
public request/model identifiers, but the runtime path must preserve them to
the embedding application; ScribeRig's current `ProviderMetadata` is discarded
before session persistence. The ScribeRig adapter can copy only declared-safe
applied-configuration provenance alongside its resolved provider/model/thinking
identity and effective-request identity. ScribeRig persists exact profile and
component references, request/context fingerprints, and the partial report in
`ModelRequestProjection.applied_settings`. The projection now also retains the
upstream-defined `SafeModelExecutionConfiguration` and incorporates that

sampling overrides plus explicit omission metadata; it does not prove those
settings appeared in the final provider body. Current request projections exclude
provider configuration credentials and headers, though they intentionally
