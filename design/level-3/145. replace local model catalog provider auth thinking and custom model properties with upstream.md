## 6. Delegate Thinking-Level Semantics Completely

### 17.2 Native upstream catalog composition

`apps/scriberig` pins `rpi-ai` and `rpi-model-runtime` to fork revision
`4a52baf41a19a889ca96c0f38369f7482f26973e`. The native catalog loader now
parses `SCRIBE_AGENT_MODEL_CATALOG` as upstream `ModelsConfig` JSON and calls
`build_catalog` with an empty provider manifest list. The former ScribeRig
`models`/`connections`/`thinking_levels` schema is no longer consumed. When no
provider config is supplied, the host creates a minimal OpenAI Completions
provider config from `SCRIBE_AGENT_MODEL`.

The native runner retains the returned `Vec<rpi_ai::Model>` and passes it to
the TUI and HTTP application services through `with_upstream_models`. A
credential-free `ModelLibrary` remains as a compatibility protocol/UI
projection. Live session and plan assignments carry upstream provider/model
IDs and resolve directly through `rpi_model_runtime`; local profile rows do
not participate in that path. Its thinking list is derived from upstream model
support. The native
provider adapter currently accepts OpenAI Completions models only. The current
protocol has required boolean capability fields, and upstream `Model` lacks
flags for each of those fields; the projected capability booleans are
compatibility-only and non-authoritative.

Session selection mutations and history, plan assignments, and Rust and
TypeScript request/response mappings now carry provider/model pairs. The
server's model-selection history projection returns that pair. Legacy
single-model history cannot be mapped safely without the retired catalog and
remains a migration concern.

Display model IDs and the temporary native adapter lookup key use a versioned
provider/model composite with UTF-8 byte-length-prefixed components in the
form `rpi1:<provider-byte-length>:<provider><model-byte-length>:<model>` for
every catalog entry, even when the model ID is currently unique. This remains
injective when either ID contains separators or Unicode text. Live assignment
identity is the pair itself, not this composite. The adapter lookup key is a
temporary native bridge until provider execution is fully delegated upstream.

The host resolver supports literal values and simple `$NAME`/`${NAME}`
references; it does not execute upstream command expressions. Before calling
`build_catalog`, the loader strips provider/model typed `api_key`,
`auth_header`, and header maps. It rejects catalog configuration that contains
those typed fields with a generic error, so those values are neither resolved
nor retained in `rpi_ai::Model`. Unknown model fields are retained in the
upstream `provider_options` map and are not inspected for credential-like
names; this map is currently neither persisted nor passed to requests, but
must not be treated as safe for durable provenance. Catalog-specific auth
cannot yet be passed through ScribeRig's authorized host credential path. The upstream
`resolve_credential` API and auth store are not wired, so provider credential
precedence/readiness remains unavailable through the catalog. The legacy
`ConfigValueResolver` and `resolve_credential` APIs resolve values as ordinary
`String`s, which cannot satisfy ScribeRig's destination-authorized
`SecretValue` boundary. Fork commit
`4a52baf41a19a889ca96c0f38369f7482f26973e` adds a separate protected-material
source resolver in `rpi-model-runtime` and request-only secret handle in
`rpi-ai`; the ordinary CLI string APIs remain available. ScribeRig does not
consume the new seam yet. Built-in provider request implementations still need
to override the protected request method, and the extension-provider ABI needs
a request path that does not serialize credentials through generic options.
The default protected method fails closed, so callers must not fall back to
legacy `stream_simple` for protected credentials. Until ScribeRig integrates
the seam end to end, it rejects catalog credentials and headers before catalog
construction. The current
OpenAI adapter does not consume all upstream sampling, compatibility, or
arbitrary provider-option fields. Package manifest loading, provider
auth-store/readiness, package refresh/reload, and request-adapter mapping
remain follow-up seams. The pinned `ModelDefinition` preserves opaque values
in its upstream `provider_options` bag, and catalog construction carries those
values into `rpi_ai::Model`; the current native provider adapter does not yet
interpret or route that bag. Unknown properties outside the upstream schema
and `provider_options` are not preserved. Scriberig's separately configured
default endpoint and credential continue through its existing host path. The
older generic server entry point no longer loads the ScribeRig catalog JSON;
product composition must pass its host-loaded projection and upstream models
explicitly.

The pinned fork's `rpi_model_runtime::ModelDefinition` parses typed sampling,
compatibility, reasoning, modality, limit, cost, and header fields, and carries
unknown values in `provider_options`. `provider_to_models` copies these values
to `rpi_ai::Model`; built-in OpenAI adapters apply known sampling settings, but
opaque `provider_options` are not applied generically and extension provider
serialization omits them. ScribeRig currently drops these properties before
request construction: `provider_config.rs::from_connection` reduces the model
to a local connection, and `plan_worker.rs`/`scriberig-agent-runtime` build
`ModelRequest` without upstream sampling or compatibility values. This is a
production deletion/integration gate, not a protocol-only gap.

The fork's `model_configuration_fingerprint` hashes a partial serialized
`rpi_ai::Model` projection after omitting headers. It omits `provider_options`
because that field is skipped during serialization, and it cannot cover
request configuration absent from the serialized model. It also hashes
arbitrary included values without sensitivity classification or secret
scrubbing. Scriberig does not persist this fingerprint; it is not a canonical
effective-request fingerprint or a safe durable provenance value. Task-145
§7 and §11 provenance criteria remain unchecked until upstream provides a
versioned contract that covers applied output-affecting typed and opaque
properties, classifies header sensitivity, and excludes credentials. The
extension provider envelope also needs a versioned property path if extensions
must consume opaque options.

This slice does not complete the task: protocol projections and the legacy
`ModelLibrary` compatibility type remain, historical profile IDs cannot be
recovered from the retired ScribeRig catalog format, and auth/property request
integration remains incomplete. The public
`scriberig_app::model_library_from_json` compatibility helper has no in-repo
production call path, but remains callable by external composition and can
still construct a local catalog; retire it or constrain its visibility in a
follow-up before claiming the catalog authority is fully removed. The current
workspace compiles against the pinned fork. Record final formatter, lint,
typecheck, compile, and diff checks below. No tests were run, as requested.
Keep the relevant acceptance items unchecked.

### 17.3 Implemented consumer slice

`scriberig-app` consumes `rpi-ai` and `rpi-model-runtime` from fork commit
`4a52baf41a19a889ca96c0f38369f7482f26973e`. Its `ThinkingLevelId` is a
transparent wrapper around upstream `rpi_ai::ThinkingLevel`; construction
delegates exact-name parsing to `ThinkingLevel::parse_name`, and display uses
upstream `as_str`. Scriberig session and plan assignments now retain
provider/model pairs rather than local model-profile IDs. Application
validation no longer accepts arbitrary thinking names or rejects a canonical
upstream level because it is absent from the local presentation list. Model
switching preserves a valid current thinking choice and lets upstream clamp it
for the newly selected model; it does not choose the first entry in the display
projection. The service keeps upstream models private and exposes a borrowed
accessor only for trusted runtime composition.

Safe model-library presentation levels are rebuilt from each upstream model's
`supported_thinking_levels`. App selection and plan assignment resolution use
`rpi_model_runtime::resolve_selection` for provider/model matching and
effective thinking-level clamping. The scheduler carries the host catalog to
the assignment resolver. Unassigned runtime fallback models are matched in
the upstream catalog and then passed through `resolve_selection`; missing or
provider-ambiguous fallback IDs fail selection. Existing fixtures now inject
explicit upstream models and use canonical thinking IDs.

`ResolvedPlanExecution` marks when resolution used the host runtime fallback.
The native plan worker selects the same configured `local` adapter used by
ordinary unselected turns, while retaining the upstream provider/model pair
for selection and provenance. Explicit provider/model selections continue to
use their pair-keyed adapter.

Generated display model IDs and temporary native adapter lookup IDs are
versioned, length-prefixed provider/model composites, so embedded separators
cannot alias a different pair. Live assignments store the pair directly.
Existing persisted local profile/model references cannot be mapped safely
without their original catalog: legacy session choices deserialize as empty,
and legacy plan assignments fail decoding. The SQLite store persists unversioned
JSON in `session_records` and decodes it directly in list/load and both CAS
paths. Close this blocker only with a versioned importer that accepts the
archived exact legacy catalog and maps uniquely resolved old assignments to
current upstream provider/model IDs. If that catalog is unavailable or a match
is ambiguous, preserve the raw payload until an operator chooses reset or plan
recreation; do not infer from past `ModelInvocation` records.

The catalog loader strips provider/model typed API keys, auth headers, and
request header maps before `build_catalog`, and rejects catalog configs
containing those typed values. Opaque model `provider_options` are not inspected
for credential-like names and must not be treated as safe for durable records.
The loader does not resolve credential references or copy API-key references
into local adapters. The catalog adapter has no authorized per-provider
credential injection seam yet; catalog-specific auth remains unsupported. The
Scriberig-configured default provider endpoint and credential continue through
its existing host configuration path.

`ThinkingLevelDescriptor` and the local `ModelLibrary` presentation types
remain as compatibility/protocol projections; this slice has not removed them
or migrated all provider request shaping. Do not check task acceptance items
for catalog deletion, custom-property routing, provider auth, persisted legacy
assignment migration, or protocol projection removal based on this slice.
`cargo fmt --all -- --check`, `cargo check --workspace --all-targets`,
`cargo clippy --workspace --all-targets -- -D warnings`,
`python tools/lint_repo.py`, `pnpm --dir web typecheck`, and `git diff --check`
pass. `pnpm` also completed the web package builds. The client error now boxes
its nested protocol error to keep client results compact; server composition
groups the upstream model catalog and display projection into one argument.
No test runners were executed, as requested.
