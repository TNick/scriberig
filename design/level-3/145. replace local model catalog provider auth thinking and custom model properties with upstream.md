## 4. Preserve Scriberig Assignment, Remove Scriberig Catalog Authority

Scriberig still owns the fact that one semantic execution location has one configured execution selection.

Examples:

```text
branch -> execution selection
plan node -> execution selection
session default -> execution selection
agent profile preference -> execution selection
historical invocation -> resolved execution provenance
```

But Scriberig must no longer decide what models exist or what capabilities/properties they expose.

Acceptance:

- [ ] Branch/plan assignment identity remains stable and Scriberig-owned.
- [ ] Assignment resolution reads upstream catalog/runtime state.
- [ ] No branch/plan/session code depends on a Scriberig-owned list of model capabilities.
- [ ] Historical assignment remains inspectable if the live upstream catalog later changes.

---

## 5. Replace `ModelDescriptor` and Local Model Library Authority

Current equivalents of these concepts are migration targets:

```text
ModelDescriptor
ModelCapabilities
ThinkingLevelDescriptor
ModelLibrary as model/provider truth
local provider-profile metadata used as catalog truth
```

Use upstream model descriptors directly at the product/runtime integration boundary or a safe upstream-provided public snapshot/projection.

If upstream lacks a stable safe snapshot type suitable for protocol/history, contribute one upstream rather than defining a second capability schema in Scriberig.

Scriberig may define a narrow historical record containing:

```text
provider public ID
model public ID
upstream catalog/version/fingerprint reference
safe resolved output-affecting selection fingerprint
safe display metadata needed for historical UI
```

That record is provenance, not a live catalog.

Acceptance:

- [ ] Live model availability is queried from upstream.
- [ ] Live model metadata is queried from upstream.
- [ ] Local `ModelDescriptor`/capability definitions are removed or reduced to a compatibility projection with no independent semantics.
- [ ] Local model-library validation no longer rejects/accepts model capabilities independently from upstream.
- [ ] Tests prove an upstream catalog change is reflected without editing Scriberig catalog code.

## 6. Delegate Thinking-Level Semantics Completely

Upstream owns thinking-level support, ordering, mapping, clamping, and provider serialization.

Scriberig must not maintain a separate support table or validation list.

Required behavior:

```text
selected model changes
  -> supported levels come from upstream model
  -> currently requested level is accepted/clamped/rejected according to upstream
  -> provider request receives upstream-mapped value
```

Scriberig may persist the user-selected or resolved public level as execution configuration/provenance, but does not interpret its provider meaning.

Acceptance:

- [ ] Supported thinking values come from upstream API.
- [ ] Thinking-level mapping to provider effort comes from upstream.
- [ ] Unsupported-level fallback/clamping comes from upstream.
- [ ] TUI/web protocol projection does not invent an independent thinking enum/catalog.
- [ ] Existing Scriberig `ThinkingLevelDescriptor` authority is removed.
- [ ] A model switch test proves levels update from the new model's upstream metadata.

## 7. Delegate Custom Model Properties

Use upstream model/provider metadata for custom and model-specific properties.

This includes current/future upstream equivalents of:

```text
sampling parameters
reasoning maps
compatibility flags
strict-tool support
model input modalities
context window
max output
cost metadata
provider endpoint/public metadata
provider-specific request-shaping values
custom property maps
```

Do not introduce a Scriberig enum/schema for these fields.

When Scriberig needs to retain user overrides, store/forward them through an upstream-owned configuration type or an opaque serialized upstream value that upstream validates and resolves.

Acceptance:

- [ ] Scriberig does not define custom model property semantics.
- [ ] Runtime validation of model properties is upstream-owned.
- [ ] Output-affecting properties participate in Scriberig effective-request provenance/fingerprinting through a canonical safe upstream snapshot/hash.
- [ ] Secret headers/credential material are excluded from Scriberig durable records.
- [ ] Unknown future upstream properties can flow through without a Scriberig code change where the upstream public type supports that.

## 8. Delegate Provider Authentication and Readiness

Provider authentication, credential resolution, and readiness belong upstream.

Scriberig may apply product trust/policy around whether a provider can be used, but it must not duplicate credential-source precedence or authentication status resolution.

Required behavior:

```text
upstream provider package/catalog
  -> upstream auth/readiness
  -> safe status projection
  -> Scriberig TUI/web/server display
```

Acceptance:

- [ ] Provider auth status comes from upstream.
- [ ] Credential-source precedence comes from upstream.
- [ ] Resolved credentials never enter Scriberig session/protocol state.
- [ ] Scriberig product policy may deny use without changing upstream auth semantics.
- [ ] Provider reload/auth changes refresh Scriberig-visible safe status from upstream.

Use upstream provider-package and catalog-refresh infrastructure.

## 17. Implementation Notes

### 17.1 Upstream evidence and current gate

The inspected source is pinned to upstream commit
`aab74de0737f4b7c454cd8c8c16ca66e4dfbf898` (`rpi` 0.6.2).

- `rpi-ai/src/model.rs` exposes upstream `Model` metadata, custom properties,
  sampling/configuration fields, cost/context/output metadata, compatibility,
  and thinking maps. `rpi-ai/src/types.rs` defines `ThinkingLevel` and
  `ThinkingLevelMap`; the model API exposes supported thinking levels and the
  provider/runtime owns mapping and clamping.
- `rpi-ai/src/provider.rs` and `rpi-ai/src/providers/` expose provider traits,
  stream options, and provider implementations. Those APIs are the target for
  execution, but do not supply a product model registry/auth configuration
  service.
- `rpi-cli/src/model_registry.rs` is public but is not a reusable catalog
  boundary: `refresh_catalog` reads CLI config directly, and no call site
  outside that module was found in the inspected `rpi-cli` tree.
- The active product resolution path is `rpi-cli/src/provider.rs`:
  `resolve_with_extensions`, `authenticated_catalog`,
  `catalog_with_manifests`, and `execution_catalog_with_manifests`. It depends
  on CLI args/settings/config and `rpi_extensions::ExtensionSession`.
- `rpi-cli/src/credentials.rs` is private. `rpi-cli/src/auth.rs` and
  `config.rs` own credential resolution and source precedence. Scriberig cannot
  consume these as reusable APIs without depending on the CLI product crate.
- `rpi-cli/src/interactive_tui/selectors.rs` and `settings.rs` keep reusable
  selector functions private to the CLI UI.

Task 144 gates G1–G3 therefore remain unsatisfied at the pinned commit. A local
Scriberig catalog replacement or a dependency on the complete `rpi-cli`
product would preserve the ownership problem. The next implementation step
must land or pin an upstream reusable API for host-configured
catalog/provider resolution, host-injected auth/readiness, and selector
components. Catalog/provider resolution and auth extraction were proposed in
[bigfish1913/pi-rust#67](https://github.com/bigfish1913/pi-rust/issues/67), and
the reusable selector boundary in
[bigfish1913/pi-rust#68](https://github.com/bigfish1913/pi-rust/issues/68).
A draft implementation of G3 is pushed at
[TNick/pi-rust `cec852f`](https://github.com/TNick/pi-rust/tree/cec852fbc437c632899e7966313dabc9ee460eb3)
and is pending upstream review; it is not yet a consumable pinned API. A
separate draft on
[TNick/pi-rust `2d75978`](https://github.com/TNick/pi-rust/commit/2d75978)
now maps `models.json` `samplingParams` into the existing upstream
`rpi_ai::Model::sampling_params` field. The pinned upstream CLI previously
dropped that property. This small fix does not extract catalog/auth resolution
or make the new property path consumable before upstream review/merge.

A further draft is pushed on
[TNick/pi-rust `ec71d6d`](https://github.com/TNick/pi-rust/tree/ec71d6d) on
branch `codex/model-runtime-extraction`. It adds `rpi-model-runtime` and moves
model/provider configuration types, conversion to `rpi_ai::Model`, provider
credential precedence, package-default application, and merged catalog
construction out of `rpi-cli`; the CLI now delegates to those APIs. The host
still supplies config/environment resolution and manifests. The draft was
verified with `cargo fmt --all -- --check`,
`cargo check -p rpi-model-runtime -p rpi-cli`, and `git diff --check` (no tests
were run). It remains on the fork branch and is not a merged or pinned upstream
API. It also does not yet extract active model selection, auth/readiness
projection, provider runtime construction, or package catalog refresh from
`rpi-cli`; those remain G1/G2 work. The source audit also confirms
`rpi_ai::Model` has no arbitrary unknown-property map at the inspected pin; do
not claim such fields are preserved unless a reviewed upstream API provides
that behavior. The dependent acceptance criteria in sections 4–12 and 15–16
remain unchecked; no Scriberig catalog deletion is claimed. Section 13's
no-local-selector rule is met; its upstream-selector gate is represented by
G3.

The Scriberig consumers to migrate are
`scriberig-app/src/agent_console/{model,library,configuration,resolution}.rs`,
the `ModelLibrary` application/server/client/protocol flow, native provider
composition in `apps/scriberig`, session execution selection/provenance,
`scriberig-tui/src/state_model_picker.rs`, and
`web/packages/{protocol,client,agent-ui}` model projections.
