## 4. Preserve ScribeRig Assignment, Remove ScribeRig Catalog Authority

ScribeRig still owns the fact that one semantic execution location has one configured execution selection.

Examples:

```text
branch -> execution selection
plan node -> execution selection
session default -> execution selection
agent profile preference -> execution selection
historical invocation -> resolved execution provenance
```

But ScribeRig must no longer decide what models exist or what capabilities/properties they expose.

Acceptance:

- [x] Branch/plan assignment identity remains stable and ScribeRig-owned.
- [x] Assignment resolution reads upstream catalog/runtime state.
- [x] No branch/plan/session code depends on a ScribeRig-owned list of model capabilities.
- [x] Historical assignment remains inspectable if the live upstream catalog later changes.

## 5. Replace `ModelDescriptor` and Local Model Library Authority

Current equivalents of these concepts are migration targets:

```text
ModelDescriptor
ModelCapabilities
ThinkingLevelDescriptor
ModelLibrary as model/provider truth
local provider-profile metadata used as catalog truth
```

Use upstream model descriptors directly at the product/runtime integration boundary or a safe upstream-provided public snapshot/projection.

If upstream lacks a stable safe snapshot type suitable for protocol/history, contribute one upstream rather than defining a second capability schema in ScribeRig.

ScribeRig may define a narrow historical record containing:

```text
provider public ID
model public ID
upstream catalog/version/fingerprint reference
safe resolved output-affecting selection fingerprint
safe display metadata needed for historical UI
```

That record is provenance, not a live catalog.

Acceptance:

- [x] Selection and model-library reads use the host-owned upstream catalog; the app regenerates compatibility rows from every upstream model on each read instead of accepting or caching a caller-supplied catalog projection.
- [x] Live model metadata is queried from upstream.
- [x] The ScribeRig JSON catalog parser, app `ModelProfile`/credential rows, and `ModelLibrary` validator/lookups are removed; exact source searches found no remaining app call sites.
- [x] The app `ModelLibrary` contains only upstream-derived model rows, with no caller-supplied setter; the protocol and web model-library contract no longer exposes retired profile or credential-reference rows.
- [x] The app-owned `ModelCapabilities` type and `ModelDescriptor.capabilities` field are removed; ScribeRig no longer infers local `streaming`, `tool_calls`, or `structured_output` booleans. The `reasoning` boolean that remains in model metadata is copied from upstream's safe snapshot.
- [ ] Tests prove an upstream catalog change is reflected without editing ScribeRig catalog code.

## 6. Delegate Thinking-Level Semantics Completely

Upstream owns thinking-level support, ordering, mapping, clamping, and provider serialization.

ScribeRig must not maintain a separate support table or validation list.

Required behavior:

```text
selected model changes
  -> supported levels come from upstream model
  -> currently requested level is accepted/clamped/rejected according to upstream
  -> provider request receives upstream-mapped value
```

ScribeRig may persist the user-selected or resolved public level as execution configuration/provenance, but does not interpret its provider meaning.

Acceptance:

- [x] Supported thinking values come from upstream API.
- [ ] Thinking-level mapping to provider effort comes from upstream.
- [x] Unsupported-level fallback/clamping comes from upstream.
- [x] TUI/web protocol projection does not invent an independent thinking enum/catalog.
- [ ] Trusted app model rows carry upstream `rpi_ai::ThinkingLevel` values directly, and protocol/web rows expose only ordered scalar level IDs; focused Rust and TypeScript projection tests pass.
- [ ] A model switch test proves levels update from the new model's upstream metadata.

Provider mapping gate (verified against the pinned fork and current call path):
`rpi_model_runtime::ResolvedSelection.effective_thinking` is an upstream
`rpi_ai::ThinkingLevel`, and `rpi_ai::Provider::stream_simple` accepts that
typed value through `SimpleStreamOptions.reasoning`. The provider crates apply
their own model-specific `thinking_level_map` and provider-effort conversion.
`rpi_agent::AgentBuilder::thinking_level` also accepts the enum directly.
ScribeRig currently cannot pass that enum into either API: native selection in
`apps/scriberig/src/native_tui_agent/model_selection.rs` and app resolution in

`ModelRequest.thinking_level: Option<String>`; and ScribeRig's local
`OpenAiCompatibleProvider`/`WireRequest` path does not implement upstream
provider effort mapping. Therefore the thin direct handoff is blocked at the
runtime adapter boundary. Task 146 must connect the resolved upstream model
and effective `ThinkingLevel` to `rpi_ai::Provider`/`rpi_agent`, retaining
ScribeRig's semantic tool/runtime bridge while delegating provider mapping and
serialization. Do not restore a local effort map or mark provider mapping
complete before that call path is integrated and verified.

## 7. Delegate Custom Model Properties

Use upstream model/provider metadata for custom and model-specific properties.

This includes current/future upstream equivalents of:

```text
sampling parameters
reasoning maps
compatibility flags
strict-tool support
model input modalities
context window
max output
cost metadata
provider endpoint/public metadata
provider-specific request-shaping values
custom property maps
```

Do not introduce a ScribeRig enum/schema for these fields.

When ScribeRig needs to retain user overrides, store/forward them through an upstream-owned configuration type or an opaque serialized upstream value that upstream validates and resolves.

At the pinned fork revision, `rpi_ai::Model` in
`crates/rpi-ai/src/model.rs` owns `sampling_params` and `provider_options`.
`rpi_model_runtime::models::build_catalog` copies both from
`ModelDefinition` into runtime models. The built-in OpenAI Completions and
Responses adapters merge `sampling_params` into their request bodies in
`crates/rpi-ai/src/providers/openai_completions.rs` and
`openai_responses.rs`; this is upstream request shaping, but is specific to
those adapters. `provider_options` is runtime-only and `#[serde(skip)]`.
Built-in adapters fail closed on non-empty values. The pinned extension ABI
accepts an opt-in `providerOptionsVersion: 1` declaration and sends a versioned
`providerOptions` envelope only to opted-in providers; legacy providers fail
closed. The envelope forwards opaque values as-is, so it is an extension
handoff, not a safe projection or proof of validation/application. ScribeRig
does not consume it. Do not claim generic custom-option flow through built-in
providers or copy arbitrary properties into ScribeRig DTOs.

`rpi_model_runtime::safe_model_snapshot` is a display projection. The separate
`safe_model_execution_configuration` accepts only allowlisted numeric sampling
keys (`temperature`, `top_p`, `frequency_penalty`, `presence_penalty`, `seed`,
`max_tokens`, and `max_completion_tokens`); unknown or malformed entries are
counted and omitted. It excludes endpoint, headers, opaque `provider_options`,
provider-specific thinking maps, and opaque compatibility values, and always
reports `complete: false`. `model_execution_fingerprint` likewise excludes
sampling parameters and provider options and always reports incomplete coverage
because endpoint identity is omitted. Neither API establishes the complete
configuration a provider actually applied. ScribeRig consumes the display
snapshot, but has no complete, sensitivity-aware effective-configuration
provenance.

After Task 146 routes execution through upstream providers, the required
upstream boundary is a versioned safe configuration/fingerprint contract that
covers output-affecting values applied by the selected provider, with explicit
omission categories for secret or opaque fields. For provider-specific opaque
options, upstream must define a safe provider/extension handoff. The local fork
contribution starts the extension handoff but does not establish built-in
handling or safe applied-configuration provenance. Only after those upstream
APIs exist may ScribeRig persist their safe result as opaque provenance. Keep
custom-property application, unknown-property flow, and canonical provenance
gates open; do not add a second ScribeRig property schema.

Provider-source review confirms that a complete applied-settings snapshot
cannot be produced from `rpi_ai::Model` or `rpi_model_runtime` alone. The
OpenAI Completions and Responses providers build different request bodies in
`rpi-ai/src/providers/openai_completions.rs::build_request` and
`openai_responses.rs::build_request`: they merge configured sampling values,
apply protocol compatibility flags, map thinking levels, and choose output
limits from both model metadata and `SimpleStreamOptions`. Anthropic instead
builds `RequestParams` in `rpi-ai/src/providers/anthropic/build_params.rs::build_params`,
where sampling metadata is not applied, temperature and thinking interact,
thinking budgets can expand output limits, and the context-window estimate can
clamp them. Extension providers receive a model and request options through
`rpi-extensions/src/provider.rs`; the version-1 `providerOptions` envelope
only transports opaque values to opted-in extensions and receives no
provider-applied-settings acknowledgment. Providers may therefore ignore,
transform, clamp, or reject configured values differently, and catalog
metadata alone cannot state what a specific request used.

The current upstream `safe_model_execution_configuration` and
`model_execution_fingerprint` are catalog-derived partial projections; their
exclusion reports correctly leave `complete` false. ScribeRig's
`scriberig-agent-runtime::model_provider::request_projection::capture` runs
before its local adapter and sees only the normalized ScribeRig request, not
the upstream model or provider-prepared request. Do not relabel either
projection as applied configuration or add fields to the ScribeRig request
projection to imitate upstream properties. The Task 146 removal gate is an
upstream provider-owned, versioned per-request applied-settings report emitted
at the final request-preparation boundary, with explicit secret/opaque
exclusions and incomplete status when a provider cannot attest to its effects.
The extension ABI needs its own versioned report contract; the options-v1
request envelope is not that report. Only after that contract is committed,
pinned, and consumed by the ScribeRig upstream execution adapter can safe
applied-settings provenance be persisted. Until then, §7 applied-property
fingerprinting and unknown-property criteria stay unchecked.

The local execution path still has a parallel request-shaping surface that
must be removed as part of Task 146: `scriberig_agent_runtime::provider::ModelRequest`
owns `temperature` and `max_tokens`; the local
`scriberig_agent_runtime::config::CompatibilityProfile` remains declared and
re-exported but currently has no production consumer; and `openai_request.rs`
serializes those values in the ScribeRig `OpenAiCompatibleProvider` path. These
are not safe model-catalog projections; they are local execution controls.
Task 146 must route the
resolved upstream `rpi_ai::Model` and its upstream-owned request/configuration
through the upstream provider/agent boundary, then delete these local fields,
compatibility selection, and serializer. Do not copy `provider_options` or
other arbitrary `Model` properties into a ScribeRig DTO: the existing safe
snapshot APIs do not establish a sensitivity-aware, complete effective
configuration record. After that runtime migration, the fork must expose a
safe, versioned configuration fingerprint/snapshot that covers every
output-affecting value while excluding endpoint, headers, credentials, and
provider-private options; ScribeRig can persist that opaque safe provenance
without interpreting custom property semantics. Unknown-property flow remains
blocked until upstream defines that safe extraction contract.

Acceptance:

- [ ] ScribeRig does not define custom model property semantics.
- [ ] Runtime validation of model properties is upstream-owned.
- [ ] Output-affecting properties participate in ScribeRig effective-request provenance/fingerprinting through a canonical safe upstream snapshot/hash.
- [ ] Secret headers/credential material are excluded from ScribeRig durable records.
- [ ] Unknown future upstream properties can flow through without a ScribeRig code change where the upstream public type supports that.

Durable-secret boundary evidence: `SessionExecutionSelection` and
`ModelAssignment` retain only public provider/model/thinking identifiers.
`ModelInvocation` and `ModelRequestProjection` contain bounded request content,
safe identifiers, profile/component references, and fingerprints; they have no
endpoint, header, credential-source, resolved-secret, or upstream `Model`
fields. The SQLite session store serializes these session types. The native
catalog loader clears and rejects configured provider/model credentials and
headers before building its runtime catalog. Request-time credentials are
wrapped as `SecretValue`/`ResolvedCredential` and are not part of the session
types. The HTTP credential fixture
`scriberig-agent-runtime::provider_secrets_test::credentials_are_headers_only_and_reflections_are_scrubbed`
checks credential-only transport, reflection redaction, and persistence/reload
through `persist_and_assert_secret_absent`. Source inspection supports the
boundary, but the focused fixture has not been run; keep this criterion
unchecked until that verification is complete.

## 8. Delegate Provider Authentication and Readiness

Provider authentication, credential resolution, and readiness belong upstream.

ScribeRig may apply product trust/policy around whether a provider can be used, but it must not duplicate credential-source precedence or authentication status resolution.

Required behavior:

```text
upstream provider package/catalog
  -> upstream auth/readiness
  -> safe status projection
  -> ScribeRig TUI/web/server display
```

Acceptance:

- [ ] Provider auth status comes from upstream.
- [ ] Credential-source precedence comes from upstream.
- [ ] Resolved credentials never enter ScribeRig session/protocol state.
- [ ] ScribeRig product policy may deny use without changing upstream auth semantics.
- [ ] Provider reload/auth changes refresh ScribeRig-visible safe status from upstream.

Current upstream auth integration gate: fork commit
`a40890741880838d02532fd57ec365ade16725d1` adds
`rpi_model_runtime::CredentialResolutionError`, the policy-aware
`ProtectedCredentialResolver::resolve_with_policy`, and
`resolve_credential_protected_with_policy`. Source misses continue precedence;
resolver errors stop it. A host that enforces policy must override
`resolve_with_policy`; its default implementation adapts legacy `resolve` and
cannot distinguish denial from a miss. The legacy
`resolve_credential_protected` API maps an error to a credential-free
`Missing` result and also stops precedence. These are upstream APIs only;
ScribeRig does not call them or use upstream provider execution. The same
crate exposes `readiness_from_catalog`, which projects the resolved upstream
credential source or model-header presence to a safe `CredentialSource` enum;
it does not resolve host credentials, provide a live readiness service, or
refresh status when credentials or providers change. ScribeRig currently
consumes neither this projection nor the protected credential API.

The ScribeRig host credential provider is request-scoped and authorizes the
exact endpoint in `scriberig-secrets::registry::AuthorizedCredential::credential`.
The upstream resolver receives provider/source descriptors but no endpoint or
ScribeRig `SecretUseContext`; a request-scoped resolver can capture those host
values while resolving the protected material. `apps/scriberig/src/agent_config.rs` currently
selects one effective ScribeRig `SecretRef`, while upstream resolution expects
provider-keyed source precedence. A safe integration must bind the effective
provider/model, immutable catalog/config snapshot, exact endpoint, credential
reference, and use context for one provider request, then carry any resolved
`SecretValue` only through upstream's protected request API. The active native
path still constructs the local synchronous OpenAI-compatible adapter, so
there is no upstream provider call to receive that material yet. Keep every
§8 acceptance item unchecked until the endpoint-bound bridge and upstream
provider execution integration exist; do not adapt via ordinary-string
`AuthStore` or map authorization errors to source misses.

The upstream protected request seam is sufficient for transporting a
credential after host authorization: `RequestSecret` accepts opaque
`SecretMaterial`, and built-in providers expose it only while constructing
request headers. Endpoint and `SecretUseContext` are intentionally absent from
that value because the host must authorize the secret before creating the
request handle. `ProtectedCredentialResolver` also has no endpoint/context
parameters; a host can bind those values in a request-scoped resolver instance
without adding ScribeRig semantics upstream. This transport seam is currently
implemented by the built-in Anthropic and OpenAI Completions providers. The
upstream `PluggableProvider` does not override
`Provider::stream_simple_with_request_secret`, so it inherits the trait's safe
unsupported-credential response; extension-provider authentication needs an
upstream extension ABI/runtime path that accepts protected request secrets.
The current extension `options_json` also serializes
`SimpleStreamOptions.api_key` as `apiKey`; ScribeRig must not put an authorized
credential in that ordinary JSON options field. The remaining blocker for
built-in providers is the execution boundary:
`OpenAiCompatibleProvider` implements ScribeRig's local synchronous
`ProviderAdapter`, while the upstream protected provider method is async. Task
146 must move provider execution to upstream before this bridge can be
consumed; do not add an unused local-to-upstream adapter in task 145. Package
provider authentication remains gated on the upstream protected extension
path as well.

Task 146's auth migration boundary is file-specific. Keep
`scriberig-secrets::{SecretRef, SecretUseContext, SecretValue}` and
`scriberig-secrets::registry::AuthorizedCredential` as ScribeRig's destination
authorization and secret-storage owner. Keep the host-side configuration
selection in `apps/scriberig/src/agent_config.rs` only where it chooses the
authorized `SecretRef` and constructs the trusted use context. Replace the
runtime transport of those selections through
`scriberig_agent_runtime::provider::{CredentialSource, ProviderConfig}` and
`scriberig_agent_runtime::config::{resolve_credential, ResolvedCredential}`
with a request-scoped adapter at the upstream `rpi_ai::Provider` boundary.
That adapter must bind the selected provider/model, catalog/config snapshot,
effective endpoint, selected `SecretRef`, and `SecretUseContext`; it must map
upstream credential sources to that authorized reference and return a distinct
resolver error for denial/failure so upstream precedence stops. The value may
cross only through `SecretMaterial`/`RequestSecret`. The current local secret
resolution and HTTP-header construction in
`crates/scriberig-agent-runtime/src/openai_compatible.rs` and
`openai_transport.rs` are commodity provider implementation and are removed
when Task 146 routes the request through upstream providers. Do not remove the
ScribeRig authorization policy or secret registry with that adapter. The
diagnostic path in `apps/scriberig/src/doctor_command.rs` must likewise use
the upstream safe readiness projection after an upstream catalog/provider
session exists; it must not report a local credential-source enum as provider
authentication state.

## 9. Delegate Provider Packages and Catalog Refresh

Use upstream provider-package and catalog-refresh infrastructure.

If install/update/link/reload APIs are currently CLI-only, complete the upstream contribution gate from task 144 before implementing a local package manager.

Current fork API audit at ScribeRig's pin
`a40890741880838d02532fd57ec365ade16725d1`: `rpi_extensions::load_session`
in `crates/rpi-extensions/src/loader.rs` accepts host-selected cdylib
directories, `ExtensionSession` exposes successfully registered
`ProviderManifest` values through `crates/rpi-extensions/src/registry.rs`, and
`rpi_extensions::PluggableProvider::from_session` in
`crates/rpi-extensions/src/provider.rs` creates upstream `rpi_ai::Provider`
adapters. `rpi_model_runtime::build_catalog` in
`crates/rpi-model-runtime/src/catalog.rs` combines host `ModelsConfig` with
those manifests. These are reusable loading, runtime-adapter, and one-shot
catalog-composition APIs, not package lifecycle or refresh services.
`load_session` scans caller-supplied directories; it does not select package
roots from a package registry. The pinned commit does not expose
`ProjectPackage` or `ProjectPackageRegistry`: those types exist only as
uncommitted worktree changes and are not available to ScribeRig at this pin.
In the pinned tree, `rpi_cli::packages` keeps `ProjectPackage` and
`PackageRegistry` inside the CLI; it owns registry parsing/persistence and
selects `.rpi/packages` roots.
The pinned `rpi_extensions::package_resource_dirs` helper, added in commit
`4ced7ab1a581fb6622e476f5fb4687dbe97f4eed` and implemented in
`crates/rpi-extensions/src/package_roots.rs`, joins a caller-provided resource
string to caller-selected package roots, preserving order and retaining
nonexistent paths. It does not constrain the resource to a relative child:
`Path::join` allows an absolute resource to replace the root, and `..` can
escape it. The helper does not read or validate a package registry, authorize
or canonicalize roots, check symlinks, load extensions, or reload a live
catalog. In pinned `rpi-cli/src/packages.rs`, `ProjectPackage` and
`PackageRegistry` are CLI-local, `read_registry`/`write_registry` own JSON
persistence, and `project_package_dirs` chooses
`cwd/.rpi/packages/<name>` before calling the resource-path helper. The pinned
reusable boundary here is only `package_resource_dirs`. ScribeRig has no call
site for that helper or for `load_session`. A future host adapter must
select its package root, validate/canonicalize and authorize every returned
root, pass a fixed resource such as `extensions` only after enforcing that it
is a safe relative child, then pass the resulting paths to `load_session`;
package installation and atomic session/catalog refresh still require
separate host/upstream lifecycle APIs.
`rpi_cli::install::{run_async, installed_native_packages}` in
`crates/rpi-cli/src/install.rs` uses the CLI's global package registry and
installation layout. The separate `rpi_cli::provider::catalog_with_manifests`
in `crates/rpi-cli/src/provider.rs` reads CLI configuration. Reusable parsing
and lexical root resolution do not provide package registry policy,
install/update, or orchestration that atomically replaces a live extension
session and model catalog.

ScribeRig's current native composition in
`apps/scriberig/src/native_tui_agent/provider_config/catalog.rs` does not load
an `ExtensionSession`: `from_environment` calls `build_catalog` with an empty
manifest list. `apps/scriberig/src/native_tui_agent.rs` constructs local
`NativeProvider` adapters rather than upstream `rpi_ai::Provider` objects.
These include the OpenAI-compatible adapter and deterministic/product-specific
providers. Do not add a ScribeRig package manager or copy the CLI's package-path
policy. Revisit a thin host adapter after task 146 can
consume upstream `Provider` objects and after the product supplies an explicit
host-owned package-directory and refresh lifecycle contract. Keep all package
and reload criteria below unchecked until that integration is implemented.

There is no safe type-compatible runtime bridge at the current integration
boundary. Upstream `PluggableProvider::from_session` constructs
`Arc<dyn rpi_ai::Provider>` values using a Tokio `Handle`; that trait streams
asynchronously. ScribeRig's `NativeProvider` in
`apps/scriberig/src/native_provider.rs` instead implements the synchronous
`scriberig_agent_runtime::provider::ProviderAdapter`. The generic
`ProviderModel` and `AgentRuntime` paths in
`crates/scriberig-agent-runtime/src/model_provider.rs` and `runtime.rs` consume
that synchronous model-provider contract. A blocking adapter here would
duplicate streaming/request translation and bypass task 146's upstream
`rpi-agent` migration, so do not add one.

Do not merely pass extension manifests to the existing catalog builder. The
native catalog currently builds with an empty manifest list, filters to
OpenAI-Completions models, and turns each model into a local
