## 4. Preserve ScribeRig Assignment, Remove ScribeRig Catalog Authority

ScribeRig still owns the fact that one semantic execution location has one configured execution selection.

Examples:

```text
branch -> execution selection
plan node -> execution selection
session default -> execution selection
agent profile preference -> execution selection
historical invocation -> resolved execution provenance
```

But ScribeRig must no longer decide what models exist or what capabilities/properties they expose.

Acceptance:

- [x] Branch/plan assignment identity remains stable and ScribeRig-owned.
- [x] Assignment resolution reads upstream catalog/runtime state.
- [x] No branch/plan/session code depends on a ScribeRig-owned list of model capabilities.
- [x] Historical assignment remains inspectable if the live upstream catalog later changes.

## 5. Replace `ModelDescriptor` and Local Model Library Authority

Current equivalents of these concepts are migration targets:

```text
ModelDescriptor
ModelCapabilities
ThinkingLevelDescriptor
ModelLibrary as model/provider truth
local provider-profile metadata used as catalog truth
```

Use upstream model descriptors directly at the product/runtime integration boundary or a safe upstream-provided public snapshot/projection.

```text
provider public ID
model public ID
upstream catalog/version/fingerprint reference
safe resolved output-affecting selection fingerprint
safe display metadata needed for historical UI
```

That record is provenance, not a live catalog.

## 6. Delegate Thinking-Level Semantics Completely

Upstream owns thinking-level support, ordering, mapping, clamping, and provider serialization.

ScribeRig must not maintain a separate support table or validation list.

Required behavior:

```text
selected model changes
  -> supported levels come from upstream model
  -> currently requested level is accepted/clamped/rejected according to upstream
  -> provider request receives upstream-mapped value
```

ScribeRig may persist the user-selected or resolved public level as execution configuration/provenance, but does not interpret its provider meaning.

Acceptance:

- [x] Supported thinking values come from upstream API.
- [x] Thinking-level mapping to provider effort comes from upstream.
- [x] Unsupported-level fallback/clamping comes from upstream.
- [x] TUI/web protocol projection does not invent an independent thinking enum/catalog.
- [ ] Trusted app model rows carry upstream `rpi_ai::ThinkingLevel` values directly, and protocol/web rows expose only ordered scalar level IDs; focused Rust and TypeScript projection tests pass.
- [ ] A model switch test proves levels update from the new model's upstream metadata.

The native path carries the exact upstream `Model` and typed effective
`ThinkingLevel` from selection through `UpstreamBranchInvocation` to
`AgentBuilder::thinking_level` and `SimpleStreamOptions.reasoning`. Provider
crates own model-specific effort mapping and serialization. Durable request
provenance converts the enum to its canonical scalar ID only at the projection
boundary. Protocol projection and model-switch coverage remain unchecked.

## 7. Delegate Custom Model Properties

Use upstream model/provider metadata for custom and model-specific properties.

This includes current/future upstream equivalents of:

```text
sampling parameters
reasoning maps
compatibility flags
strict-tool support
model input modalities
context window
max output
cost metadata
provider endpoint/public metadata
provider-specific request-shaping values
custom property maps
```

Do not introduce a ScribeRig enum/schema for these fields.

When ScribeRig needs to retain user overrides, store/forward them through an upstream-owned configuration type or an opaque serialized upstream value that upstream validates and resolves.

At the pinned fork revision, `rpi_ai::Model` in
`crates/rpi-ai/src/model.rs` owns `sampling_params` and `provider_options`.
`rpi_model_runtime::models::build_catalog` copies both from
`ModelDefinition` into runtime models. The built-in OpenAI Completions and
Responses adapters merge `sampling_params` into their request bodies in
`crates/rpi-ai/src/providers/openai_completions.rs` and
`openai_responses.rs`; this is upstream request shaping, but is specific to
those adapters. `provider_options` is runtime-only and `#[serde(skip)]`.
Built-in adapters fail closed on non-empty values. The extension ABI accepts an
opt-in `providerOptionsVersion: 1` declaration and sends a versioned
`providerOptions` envelope only to opted-in providers; legacy providers fail
closed. At ScribeRig's current pin, the envelope provides no provider-
application acknowledgment. Fork commit
`9f935d794053bccaf73737b5e2fb67cf3194a761` adds a closed, versioned JSON Schema
for these values and validates them before creating the extension envelope;
the extension still must attest which values it applied. ScribeRig's opt-in
native extension path consumes the older envelope but does not yet consume the
schema/setter API. Do not claim generic custom-option flow through built-in
providers or copy arbitrary properties into ScribeRig DTOs.

`rpi_model_runtime::safe_model_snapshot` is a display projection. The separate
`safe_model_execution_configuration` returns a versioned, partial execution
snapshot: it copies allowlisted numeric sampling values (`temperature`,
`top_p`, `frequency_penalty`, `presence_penalty`, `seed`, `max_tokens`, and
`max_completion_tokens`) and only upstream schema-validated scalar
`provider_options`; unknown, malformed, or unsafe entries are counted and
omitted. It excludes endpoint, headers, opaque provider options,
provider-specific thinking maps, and opaque compatibility values, and always
reports `complete: false`. `model_execution_fingerprint` is a separate
canonical SHA-256 identity over stable typed model metadata, including typed
compatibility flags and output limits; it omits endpoint, headers, sampling
parameters, provider options, thinking maps, and opaque compatibility, and
always reports incomplete coverage because endpoint identity is omitted.
Neither API alone establishes the complete configuration a provider actually
applied.

ScribeRig's canonical request capture consumes both upstream-owned
projections. It stores the `SafeModelExecutionConfiguration` JSON as
`ModelRequestProjection.model_execution_configuration`, folds it into the
request fingerprint, and then folds upstream's `ModelExecutionFingerprint`
digest and coverage metadata into the same request fingerprint under a
versioned domain separator. Neither value is redefined as a ScribeRig property
schema. Endpoint URLs, headers, credentials, opaque provider options, and
thinking-map labels never enter the durable record; upstream's omission
metadata is retained. The combined identity records that upstream-reported
safe model settings contributed to invocation provenance, but it still does
not prove effective-request equivalence because upstream reports the
fingerprint as incomplete. Source inspection confirms this capture path; the
focused projection test covering sampling, typed compatibility, and secret
exclusion was added but not run in this turn, so runtime parity remains
unverified.

The pinned upstream boundary now reports versioned applied settings at the
final provider request-preparation boundary, with explicit omitted categories
and truthful completeness. ScribeRig's upstream invocation callback captures
that report into `ModelRequestProjection.applied_settings`; the existing
authorized model-request detail path carries the opaque report to history
consumers. ScribeRig does not interpret the report or infer application from
catalog metadata. Keep custom-property application, unknown-property flow,
and canonical provenance gates open until persistence and omission semantics
are verified; do not add a second ScribeRig property schema.

Provider-source review confirms that a complete applied-settings snapshot
cannot be produced from `rpi_ai::Model` or `rpi_model_runtime` alone. The
OpenAI Completions and Responses providers build different request bodies in
`rpi-ai/src/providers/openai_completions.rs::build_request` and
`openai_responses.rs::build_request`: they merge configured sampling values,
apply protocol compatibility flags, map thinking levels, and choose output
limits from both model metadata and `SimpleStreamOptions`. Anthropic instead
builds `RequestParams` in `rpi-ai/src/providers/anthropic/build_params.rs::build_params`,
where sampling metadata is not applied, temperature and thinking interact,
thinking budgets can expand output limits, and the context-window estimate can
clamp them. Extension providers receive a model and request options through
`rpi-extensions/src/provider.rs`; the version-1 `providerOptions` envelope
only transports opaque values to opted-in extensions and receives no
provider-applied-settings acknowledgment. Providers may therefore ignore,
transform, clamp, or reject configured values differently, and catalog
metadata alone cannot state what a specific request used.

The upstream `safe_model_execution_configuration` and
`model_execution_fingerprint` remain catalog-derived partial projections;
their exclusion reports correctly leave `complete` false. The production
callback captures upstream `rpi_ai::Context`, `Model`, and `ThinkingLevel`
directly into ScribeRig's bounded historical `ModelRequestProjection`. The
normalized local request DTO and model cache have been deleted. Before
provider preparation, the canonical capture stores the upstream safe
configuration JSON and folds both that snapshot and the upstream execution
fingerprint digest into the request identity. The separate upstream callback
then adds the provider-attested applied-settings report to the same
per-request projection. The current adapter folds that safe report into the
request fingerprint using a versioned domain separator, while retaining its
separate report fingerprint. Since each upstream report is partial and the
applied report omits opaque provider options and other request fields, the
resulting identity still does not prove complete effective-request
equivalence. The extension ABI's options-v1 envelope is not this report.
Keep unknown-property and complete-configuration criteria unchecked until
upstream attestation covers those values and focused
persistence/omission verification is available.

The native root and plan-worker request paths use the upstream provider and
agent boundary. Deterministic scenario fixtures use upstream `FauxProvider`
and `FauxScript`; no production `ProviderAdapter` or normalized request DTO
remains. The local OpenAI wire serializer and `CompatibilityProfile` were
deleted. Do not copy `provider_options` or other arbitrary `Model` properties
into a ScribeRig DTO. The applied-settings report is safe, provider-attested,
and partial; it does not make the catalog execution fingerprint complete or
establish a complete effective-request identity. Upstream provides

Acceptance:

- [ ] Unknown future upstream properties can flow through without a ScribeRig code change where the upstream public type supports that.

## 8. Delegate Provider Authentication and Readiness

Provider authentication, credential resolution, and readiness belong upstream.

ScribeRig may apply product trust/policy around whether a provider can be used, but it must not duplicate credential-source precedence or authentication status resolution.

Required behavior:

```text
upstream provider package/catalog
  -> upstream auth/readiness
  -> safe status projection
  -> ScribeRig TUI/web/server display
```

Acceptance:

- [ ] Provider authentication success/failure status comes from upstream
  runtime evidence. The current readiness response reports only credential
  source availability and must not be presented as a successful auth check.
- [x] Upstream owns the generic protected credential-source APIs. Native
  ScribeRig configuration selects one `SecretRef` and uses upstream's
  `HostSelected` source without adding a parallel precedence chain.
- [ ] Resolved credentials never enter ScribeRig session/protocol state.
- [x] ScribeRig's explicit destination authorization can deny use while the
  upstream protected resolver preserves that denial as an error.
- [ ] Provider reload/auth changes refresh ScribeRig-visible safe status from upstream.

Provider lifecycle refresh blocker (2026-10-21): the pinned
`rpi-model-runtime` API `ModelCatalog::refresh_from_configuration` (and its
transactional `refresh_from_configuration_with_commit` variant) rebuilds and
publishes model rows from caller-supplied `ModelsConfig`; its documentation
explicitly assigns configuration loading, credential policy, and refresh
timing to the host. The native ScribeRig loader calls this only during startup
or model-property save. `provider_readiness::project` re-resolves the selected
host credential when invoked, so a credential change is reflected on the next
projection, but the runtime exposes no auth-success/failure evidence or
credential-change notification. The current host configuration loader rejects
catalog-stored auth material and does not retain/reload a new source config.
There is therefore no upstream-only event or safe API to refresh the catalog
and readiness automatically when credentials/provider configuration change.
Do not synthesize a local provider lifecycle/catalog authority; upstream needs
to expose a provider reload/auth lifecycle event (including safe auth result
evidence) or the host needs an explicit refresh invocation source before this
criterion can be implemented.

Current upstream auth integration gate: fork commit
`9f935d794053bccaf73737b5e2fb67cf3194a761` adds
`rpi_model_runtime::CredentialResolutionError`, the policy-aware
`ProtectedCredentialResolver::resolve_with_policy`, and
`resolve_credential_protected_with_policy`. Source misses continue precedence;
resolver errors stop it. A host that enforces policy must override
`resolve_with_policy`; its default implementation adapts legacy `resolve` and
cannot distinguish denial from a miss. The legacy
`resolve_credential_protected` API maps an error to a credential-free
`Missing` result and also stops precedence. The configured one-shot CLI,
native root, and local-config plan-worker paths now create built-in providers
through `create_builtin_provider` and execute through `rpi-agent`. They
resolve the ScribeRig-selected credential only after the exact model endpoint
is fixed, then pass it to the provider through `RequestSecret`. The bridge
invokes upstream's `ProtectedCredentialResolver` through its
`CredentialRequestSource::HostSelected` path, bound to the exact selected
model endpoint. ScribeRig configuration selects one exact `SecretRef`, so the
product must not invoke upstream's independent CLI override, stored auth,
model-config, or environment precedence for that request. Fork commit
`94c2a748f4acfd2211cff4e8d849270e2e7530a5` adds the generic
`CredentialRequestSource::HostSelected` path, its policy-aware protected
resolver, and path-parameterized auth-store read/write/upsert/delete APIs;
these were included in the earlier
`714a778784bc99e982402114265bd99681857a10` fork pin and remain present in
current pin `15a68ef2d69a312122c09c1eccfa0fbd454c48b5`. `HostSelected`
allows a resolver already bound to ScribeRig's authorized `SecretRef` and exact
endpoint to supply protected material without applying provider source
precedence. It does not select ScribeRig's `SecretRef` or authorize the
endpoint/`SecretUseContext`, so those product policy decisions remain
ScribeRig-owned.

The same crate exposes `readiness_from_catalog`, which projects a resolved
upstream source or model-header presence to a safe `CredentialSource` enum. The
native `provider_readiness::project` uses it for catalog headers and uses
`credential_source_for_model` for the same protected host-selected resolver
used at request time. It maps only upstream's safe source/error
classification to `Available`, `Missing`, `Denied`, `NotRequired`, or
`CatalogHeader`; credential material is dropped before projection. Extension
manifest `requires_auth: false` maps from upstream's `Anonymous` source to
`NotRequired`. Catalog headers are rejected by the built-in loader. This
reports whether a host credential can be resolved, not whether the provider
accepted it. The projection is computed from the current catalog snapshot on
demand, but no provider reload/refresh service or response-auth classification
is exposed. For an extension manifest requiring authentication, an upstream
`Headers` classification does not satisfy readiness: the ScribeRig extension
binding requires the authorized host-selected `RequestSecret`, so readiness
remains `Missing` without it. Keep upstream auth-status and refresh acceptance
unchecked; do not treat `Available` as a successful provider authentication.
The HTTP server now receives this projection through a host-injected
