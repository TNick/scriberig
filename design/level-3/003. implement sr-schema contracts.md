# Implement `sr-schema` Contracts

## Objective

Implement the storage-independent schema model that lets domains specialize the universal knowledge graph without hard-coding domain vocabulary into the core libraries.

This task creates schema definitions and schema-level validation contracts only.

---

## 1. Shared Design Rules

Schemas describe domain meaning. They do not store project data.

Do not define concrete production schemas such as Markdown, Rust, PDF, or sessions here.

The crate must support those future domains through generic schema values.

Use identifiers from `sr-core`:

```text
SchemaId
EntityTypeId
PropertyKey
RelationTypeId
CollectionTypeId
KnowledgeClass
KnowledgeValue
EntityId
```

Avoid generic `HashMap<String, Value>` APIs where a typed schema structure can express the concept directly.

---

## 2. Property Value Shapes

In `property.rs`, define a `ValueShape` or equivalent enum describing which `KnowledgeValue` shape a property accepts.

It should cover the universal value variants from `sr-core`, including recursive list/record shapes where reasonable.

Do not attempt to implement a complete type language.

Support enough structure to validate:

- booleans;
- signed integers;
- unsigned integers;
- floats;
- strings;
- bytes;
- lists;
- records;
- optionally `Any` where a schema intentionally leaves shape open.

Define `PropertySchema` containing at least:

- `PropertyKey`;
- human-readable name;
- `ValueShape`;
- required/optional flag;
- `KnowledgeClass` where applicable;
- optional human-readable description.

Do not put actual entity property values inside a schema.

---

## 3. Relation Schemas

In `relation.rs`, define `RelationSchema` with at least:

- `RelationTypeId`;
- human-readable name;
- permitted source entity types;
- permitted target entity types;
- canonical/derived classification;
- cardinality;
- reverse-navigation policy/expectation;
- optional description.

Define a small reusable cardinality representation capable of expressing common cases such as:

```text
zero or one
exactly one
zero or more
one or more
bounded range
```

Do not store reverse relation values here.

The schema may indicate that reverse navigation is expected to be derived from an index, but reverse edges must not become a required canonical duplicate.

---

## 4. Collection Schemas

In `collection.rs`, define `CollectionSchema` with at least:

- `CollectionTypeId`;
- human-readable name;
- owner/source entity type;
- permitted member entity types;
- ordered or unordered semantics;
- cardinality;
- canonical/derived classification;
- optional description.

Represent order semantics explicitly with an enum rather than a boolean if that improves readability.

The collection schema describes membership semantics only. It does not hold actual entity IDs.

---

## 5. Entity Type Schemas

In `entity.rs`, define `EntityTypeSchema` containing at least:

- `EntityTypeId`;
- human-readable name;
- optional description;
- associated property schemas;
- associated relation schemas or references to them;
- associated collection schemas or references to them.

Also define a top-level `Schema` or `DomainSchema` value containing:

- `SchemaId`;
- schema version;
- human-readable name;
- registered entity type schemas;
- relation definitions;
- collection definitions;
- optional description.

Use deterministic map/set structures where practical so debugging and future canonicalization are predictable.

The schema version may initially be a string or small explicit value. Do not design migration semantics for schema versions in this task.

---

## 6. Validation Subject Interface

`sr-schema` must remain independent from `sr-graph`, so it cannot accept `sr_graph::RevisionRecord` directly.

In `validation.rs`, define a small trait such as `ValidationSubject` that exposes the information needed for schema-level validation without depending on graph implementation types.

The trait should provide access to, conceptually:

```text
entity type
property keys and values
relation types and targets
collection types and members
```

Use `sr-core` identifiers and values in the trait.

Later, `sr-graph::RevisionRecord` will implement this trait.

Do not add `sr-graph` as a dependency of `sr-schema`.

---

## 7. Structured Validation Results

Define:

```text
ValidationSeverity
ValidationIssue
ValidationLocation
ValidationReport
```

or equivalent types.

A validation issue must contain:

- severity;
- stable machine-readable code;
- human-readable message;
- optional location.

A location should be able to point to at least:

- the entity/revision as a whole where available;
- a property key;
- a relation type;
- a collection type.

Keep the representation independent of filenames and line numbers.

A validation report should expose whether errors are present without requiring callers to parse messages.

---

## 8. Schema Validation Behavior

Implement schema-level validation capable of checking at least:

1. entity type is declared by the schema;
2. required properties are present;
3. property values match declared value shapes;
4. unknown properties can be rejected or reported according to one documented policy;
5. relation types are allowed for the source entity type;
6. relation target entity types are allowed when target type information is supplied by the validation subject/context;
7. relation cardinality is satisfied;
8. collection types are allowed for the owner type;
9. collection member types are allowed when known;
10. collection cardinality is satisfied.

If target/member type lookup requires external graph context, design a small callback/trait context rather than adding a store dependency.

Keep validation deterministic.

---

## 9. Error Policy

Validation failures are data, not Rust panics.

Return `ValidationReport` for invalid subjects.

Reserve Rust `Result::Err` for inability to perform validation because of malformed schema construction or unavailable required context.

Do not panic for ordinary invalid domain data.

---

## 10. Public API

`lib.rs` should re-export the primary schema and validation types needed by domain crates.

Keep implementation helpers private where possible.

Public API names should make the distinction clear between:

```text
schema definition
actual graph data
validation result
```

---

## 11. Unit Tests

Add tests covering:

- required and optional properties;
- matching and mismatching value shapes;
- ordered/unordered collection schema metadata;
- relation source/target restrictions;
- cardinality checks;
- structured validation codes;
- validation report error detection;
- a custom test entity type proving no production domain types are hard-coded.

Use small local test schemas only.

## Do Not

Do not:

- depend on `sr-graph`;
- add database access;
- add query execution;
- add migrations;
- add parser/compiler validation;
- add concrete Markdown/Rust/PDF/session schemas;
- store actual project entities in schema structs;
- model reverse edges as required duplicated canonical data;
- invent authorization/trust policy.
