# 3. Task A — Terminal Lifecycle Recovery

Exercise and harden the active terminal lifecycle implementation.

Verify restoration behavior for at least:

```text
normal quit
Ctrl-C/requested shutdown
application error returned from event/effect loop
panic inside a controlled test harness where recovery hook/guard can run
remote disconnect causing UI error/recovery
resize during active rendering
```

The exact terminal modes depend on the adopted implementation, but restoration should include applicable state such as:

```text
raw mode
alternate screen
cursor visibility
bracketed paste
keyboard enhancement modes
mouse capture if enabled
```

Acceptance:

- [ ] Normal exit restores terminal state.
- [ ] Error exit restores terminal state.
- [ ] Cancellation/shutdown restores terminal state.
- [ ] Panic recovery guard/hook is covered by the safest deterministic test possible without masking real panics.
- [ ] Recovery is idempotent enough that double-drop/double-cleanup does not panic.
- [ ] Terminal lifecycle code does not perform semantic mutations during cleanup.

# 5. Task C — Hostile Terminal-Content Test Corpus

Create one reusable test corpus for untrusted strings used across conversation and auxiliary renderers.

Include at least:

```text
ANSI CSI color/control sequences
OSC hyperlinks
OSC clipboard sequences
BEL
ESC-only/incomplete escape strings
carriage-return/backspace tricks
NUL and other controls where Rust strings can represent them
malformed Markdown nesting
malformed/fenced code content
terminal-width edge strings
```

Normal renderer behavior may visibly escape, replace, or safely render these values as text according to the kit contract. The test must prove they are not passed through as trusted terminal commands.

Acceptance:

- [ ] Conversation renderer passes hostile corpus.
- [ ] Tool/operation result renderer passes hostile corpus.
- [ ] Projection/source renderer passes hostile corpus.
- [ ] Error/diagnostic renderer passes hostile corpus.
- [ ] Palette/help labels cannot inject terminal controls from external labels.
- [ ] No convenience `raw_ansi(external_string)`-style path remains reachable from untrusted data.

# 8. Task F — Upstream Update Procedure

Make vendor maintenance reproducible.

`third_party/rpi-tui/UPSTREAM.md` and/or repository tooling must explain the update process:

```text
1. choose new exact upstream commit
2. inspect license/security/relevant release changes
3. compare old pinned tree to new tree
4. reapply documented Scriberig patches deliberately
5. update UPSTREAM.md SHA/date
6. update PATCHES.md
7. run TUI-kit focused tests
8. run TUI focused tests
9. review terminal dependency versions/Crossterm coherence
10. commit the vendor update separately where practical
```

Optionally add a small repository tool/check that verifies recorded provenance against a vendored manifest/hash inventory if that fits current tooling conventions. Do not require network access in ordinary CI merely to prove a pin exists.

Acceptance:

- [ ] Another engineer/agent can understand how to update the vendor from repository documentation alone.
- [ ] Exact old/new upstream revisions remain discoverable in Git history/provenance files.
- [ ] Local patches are not hidden in an undocumented copied source tree.
- [ ] Ordinary CI remains deterministic/offline with respect to the vendored source.
