# Implement Protocol Package Boundary

## Objective

Implement the TypeScript public protocol package in `web/packages/protocol` without inventing browser-only semantics.

This package is the stable TypeScript boundary for concepts exposed by the shared Scriberig protocol.

Read before editing:

1. `design/level-1/010. universal query and operation model.md`
2. `design/level-1/011. runtime libraries protocol and product surfaces.md`
3. `design/level-1/012. web platform and integrated editor.md`
4. `design/level-2/001. web workspace packages and integrated editor.md`

Prerequisite: the web workspace scaffold from Level 3 task 001 exists.

If a canonical runtime protocol schema already exists in the repository, use it as the authority. Do not create incompatible parallel definitions.

## Identity Types

Expose serializable protocol identities for at least:

```text
EntityId
RevisionId
SnapshotId
MigrationId
OperationId
ProjectionId
SessionId or session entity reference if the canonical protocol models sessions as entities
BranchId or branch entity reference if applicable
TypeId
RelationTypeId
```

Use the representation prescribed by the canonical shared protocol.

If no encoded representation has yet been standardized, use opaque TypeScript aliases over `string` and do not attach parsing semantics beyond basic type separation.

Do not expose database row IDs.

---

## Object and Relation Shapes

Expose public shapes needed by the web layers for concepts supported by the design, including equivalents of:

```text
EntityRef
RevisionRef
SnapshotRef
ObjectSummary
ObjectDescription
RelationSummary
CollectionPage
ProvenanceSummary
```

Keep summary forms separate from full-content forms where the protocol supports progressive disclosure.

Do not add fields only because they are convenient for one component.

---

## Query Types

Represent the shared query/operation vocabulary needed for:

```text
inspect
list/follow relations
find/search
query/filter
history
diff
```

If the canonical runtime protocol already provides a query AST, mirror or generate that exact shape.

Do not design a second browser-specific query language.

---

## Change and Validation Types

Expose protocol shapes for:

```text
MigrationSummary
MigrationDetail
MigrationProposal
SemanticDiff
ValidationResult
Conflict
StaleBase or equivalent stale-state condition
```

Keep accepted canonical state distinct from proposed/candidate state.

---

## Operation and Event Types

Expose the long-running operation lifecycle:

```text
queued
running
completed
failed
cancelled
```

Represent events needed by the Level 1 design, including equivalents of:

```text
snapshot advanced
entity changed
projection changed
branch/session changed
migration completed
validation completed
operation progress
agent output
operation failed
operation cancelled
connection/resume metadata where protocol supports it
```

Use discriminated unions so consumers can handle event types exhaustively.

---

## Session and Branch Types

Expose public session concepts required for navigation rather than a chat-only model.

At minimum support representations for:

- session summary;
- branch summary;
- branch description/purpose/outcome when present;
- goals;
- decisions;
- tasks;
- tool/result references;
- resulting migration/object references.

Reuse universal entity/revision references when the server models these as normal knowledge entities.

---

## Projection and Capability Types

Expose projection metadata sufficient for a web client to understand:

- projection identity;
- semantic source identity;
- style or rendering identity where public;
- snapshot/base state;
- editable/read-only capability;
- semantic location mappings when supported.

Expose capability descriptors used to determine available operations without hard-coding official-frontend privileges.

---

## Structured Errors

Define typed structured error shapes for conditions the UI must represent explicitly, such as:

- authorization/capability denied;
- not found;
- stale snapshot/base;
- migration conflict;
- reconciliation ambiguity;
- validation failure;
- operation failure;
- unsupported capability;
- protocol incompatibility.

Do not collapse these into plain message strings.

---

## Public Exports

`src/index.ts` must export only supported public protocol types and helpers.

Avoid default exports.

Do not export generated/private implementation details if code generation is used.

---

## Tests

Add compile/runtime-light tests that verify:

- discriminated unions narrow correctly;
- representative protocol fixtures are assignable to exported shapes;
- IDs remain opaque at API boundaries;
- public exports do not require React, DOM, or MUI types.

If canonical JSON fixtures exist from the server protocol, use them directly.

---

## Do Not Do

- Do not add HTTP behavior.
- Do not add React types or hooks.
- Do not add MUI.
- Do not add browser caches.
- Do not create UI-specific fields in protocol models.
- Do not invent endpoint paths.
- Do not mirror database tables directly.
- Do not redefine canonical Rust/runtime protocol semantics when an authoritative schema already exists.
- Do not add application layout state.
