# Implement PDF Import Domain Adapter

## Objective

Implement the first PDF domain/import adapter in `scriberig-domain-pdf`.

PDFs are treated primarily as imported source artifacts whose exact bytes are preserved, while extracted text, layout, tables, figures, and semantic structure are represented as derived knowledge with explicit provenance.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. `design/level-3/001. scaffold domain adapter crates.md`
4. current blob/artifact and provenance APIs in the shared knowledge model

---

## Files to Create or Update

Inside `crates/domains/pdf/`, create or update:

```text
src/lib.rs
src/schema.rs
src/import.rs
src/extract.rs
src/geometry.rs
src/provenance.rs
src/error.rs
```

Add tests under:

```text
tests/import.rs
tests/extraction.rs
```

If exact binary/blob storage is owned by another shared crate, call that API rather than implementing binary storage locally.

---

## Domain Vocabulary

Define or register PDF-domain entities needed for the first implementation slice:

```text
PDFDocument
PDFPage
TextRegion
Paragraph
Table
TableRow
TableCell
Figure
Annotation
```

The extracted `Paragraph`, `Table`, `TableRow`, and `TableCell` concepts may reuse compatible universal/document concepts where the shared schema model supports cross-domain reuse. Do not duplicate concepts merely because they came from a PDF.

---

## Source Artifact

The original PDF bytes must be preservable as an exact imported source artifact.

The PDF document/domain entity must be able to reference that source artifact with provenance.

The exact source bytes are distinct from extracted semantic structure.

Do not treat extracted text as an exact replacement for the PDF.

---

## Extraction Dependency

Choose one mature PDF parsing/extraction library suitable for the first implementation slice, unless one is already selected elsewhere.

Do not add OCR in this task unless the selected parser requires it for all text extraction. OCR should remain a later optional producer because it has different confidence and dependency characteristics.

Parser/extractor private object IDs must not become Scriberig semantic identity.

---

## Pages and Geometry

Represent page-level geometry needed to map semantic entities back to the source.

At minimum support:

```text
page number
page dimensions
bounding region/rectangle for extracted region entities where available
```

Geometry is source/projection metadata used for source highlighting and provenance.

Coordinates must not replace semantic identity.

---

## Extraction Provenance

Every extracted or inferred entity must record enough provenance to identify:

```text
source PDF artifact
source page
extractor/producer
extractor version/profile where relevant
source region/geometry where available
confidence where the producer supplies a meaningful confidence value
```

Do not fabricate confidence values when the extractor does not provide a meaningful score.

---

## Canonical vs Derived Rules

Treat the exact imported source artifact and explicit import relationship as authoritative imported evidence.

Treat these as derived unless a later design explicitly promotes them:

```text
extracted text regions
paragraph segmentation
reading order
table detection
row/cell segmentation
figure classification
semantic summaries
OCR output
```

The store may contain several extraction results from different producers at the same time.

Do not overwrite an older extraction merely because a new extractor produces a better result.

---

## Initial Import API

Expose an API usable without agents that can conceptually:

```text
import PDF bytes/file reference -> PDFDocument/source artifact
run extractor -> derived page/region entities and relations
```

Use universal graph/provenance APIs.

Do not create a PDF-specific persistence database.

---

## Progressive Disclosure

The produced structure should support navigation:

```text
PDFDocument
  -> PDFPage
     -> TextRegion/Paragraph/Table/Figure
        -> TableRow
           -> TableCell
```

A caller should be able to list pages and page child counts without loading all extracted text.

---

## Tests

Use small checked-in PDF fixtures with known content where repository policy permits binary test fixtures; otherwise generate deterministic fixtures during tests.

Test at least:

- original source artifact is preserved/referenced;
- document exposes ordered pages;
- extracted paragraph/region has page provenance;
- region geometry maps back to the source page where available;
- a table extraction produces row/cell structure when supported by the chosen extractor;
- extracted facts are marked derived rather than canonical source bytes;
- two producer profiles can coexist without overwriting each other's derived output;
- semantic identity does not depend on page byte offsets or extractor-private IDs.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-pdf
cargo clippy -p scriberig-domain-pdf --all-targets -- -D warnings
```

---

## Do Not Do

- Do not implement a PDF editor.
- Do not treat extracted text as authoritative exact content.
- Do not add model summaries.
- Do not add OCR unless unavoidable for the selected baseline extractor.
- Do not invent confidence values.
- Do not use page coordinates as semantic IDs.
- Do not create private SQL tables for PDF structure.
- Do not depend on agent crates.

---

## Completion Checklist

- [ ] PDF source artifact can be preserved and referenced.
- [ ] PDFDocument/PDFPage structure uses the universal graph.
- [ ] Extracted regions and semantic structures are derived with provenance.
- [ ] Geometry is available as source mapping metadata where possible.
- [ ] Page/region hierarchy supports progressive disclosure.
- [ ] Multiple extractor outputs can coexist.
- [ ] No PDF-specific persistence architecture exists.
- [ ] Tests, formatting, and clippy pass.
