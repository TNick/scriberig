# Implement Web Boundary and Conformance Tests

## Objective

Add cross-package tests and static boundary checks that enforce the web architecture defined by Level 1 and Level 2.

This task is not about adding new product features. It verifies that the reusable web platform, MUI layer, and reference editor obey their intended dependency and behavior boundaries.

Read before editing:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`
2. `design/level-1/012. web platform and integrated editor.md`
3. `design/level-2/001. web workspace packages and integrated editor.md`
4. Level 3 tasks 001 through 009 for the implemented web files.

Prerequisite: the relevant web packages and reference application exist.

## Dependency-Direction Test

Implement a static/import-graph check that enforces at least:

```text
protocol -> no Scriberig web dependency
client -> protocol only among lower semantic packages
model -> protocol/client
editor-core -> protocol/model and allowed lower packages
react -> lower packages + React, never MUI
components -> reusable lower packages, never MUI
components-mui -> reusable lower packages + MUI
app -> public package entry points only
```

The check must fail when a lower package imports from a higher package.

It must also fail when a package deep-imports another package's `src/` internals.

Prefer a small explicit test over introducing a large architecture-analysis dependency unless one is clearly justified.

---

## MUI Isolation Test

Verify that MUI packages are not imported by:

```text
@scriberig/protocol
@scriberig/client
@scriberig/model
@scriberig/editor-core
@scriberig/react
@scriberig/components
```

The only reusable package allowed to import MUI is `@scriberig/components-mui`.

The reference app may import MUI as a product choice.

---

## Public API Import Test

Scan source imports to ensure cross-package imports use public package names/exports.

Reject patterns equivalent to:

```text
@scriberig/model/src/...
../../packages/model/src/...
server/src/...
crates/... database internals
```

The exact implementation may resolve workspace paths from `package.json` files rather than hard-coding every relative depth.

## Reference Editor Boundary Test

Verify the reference app cannot access:

- SQLite/database code;
- server-private modules;
- Rust implementation source paths;
- private web package modules;
- undocumented private endpoint helpers.

The test should make architectural violations fail CI immediately.

---

## Shared Selection Integration Test

Build an integration fixture using public model/editor-core/React APIs.

Demonstrate:

1. one semantic selection controller instance is provided to multiple views;
2. selecting an entity through a tree-like interaction is observed by an inspector-like consumer;
3. the same selection is available as agent command scope;
4. projection-location metadata may change without losing semantic entity identity;
5. historical exact revision selection remains exact.

This test proves that views are integrated by semantic selection rather than app-specific row/line state.

---

## Snapshot Incrementality Test

Create a fixture containing:

```text
Snapshot A:
Entity X -> Revision X1
Entity Y -> Revision Y1

Snapshot B:
Entity X -> Revision X2
Entity Y -> Revision Y1
```

After applying a snapshot-advanced/entity-changed event sequence, verify:

- current snapshot becomes B;
- X resolves to X2 in current state;
- cached X1 remains available for historical use;
- Y1 is reused and not needlessly replaced/refetched;
- a historical view pinned to A remains on A;
- stale/current status is represented correctly.

This test enforces the Level 1 incremental architecture.

---

## Structured Agent Scope Test

Using the public app/component boundary, simulate a semantic selection and an agent command.

Verify the command operation receives structured context equivalent to:

```text
entity
revision/current-resolution context
snapshot
session
branch when applicable
user request
```

Reject a regression where the UI replaces this with only a file path and line-number prompt when semantic identity is available.

The test may inspect the fake client's invocation payload.

---

## Mutation Path Test

Simulate a user edit/mutation from the web layer.

Verify that the action flows through a public semantic operation/migration proposal and validation/apply path.

The test should fail if the component/app directly mutates canonical model cache entries as though they were server state.

At minimum verify:

- mutation command produces/requests a proposed change;
- validation result is represented separately;
- accepted result advances to a resulting snapshot/event;
- browser-local candidate state is not silently treated as canonical before acceptance.

---

## Operation Lifecycle Test

Create a fake long-running operation.

Verify:

- one panel starts the operation;
- the operation is stored by stable `OperationId`;
- the initiating panel unmounts;
- another operation view can continue observing progress;
- progress/completion events update the same operation record;
- unmount does not imply cancellation;
- explicit cancellation uses the public operation API.

---

## Progressive Disclosure Test

Where practical, add a fixture proving a knowledge tree requests only root/expanded relation pages.

The test should fail if opening a root automatically requests every descendant.

This may live in the package-local editor-core/component tests if already covered there; do not duplicate expensive tests unnecessarily.

---

## Capability Test

Verify a view/command can represent a missing capability without using a private fallback.

Example:

- server fixture does not advertise migration-apply capability;
- apply command is unavailable/disabled;
- UI can render an unsupported/permission state;
- no hidden alternate mutation call occurs.

---

## Test Helpers

`test-helpers.ts` may provide:

- fake transport/client;
- in-memory protocol fixtures;
- workspace model setup;
- fake event stream;
- test runtime/provider factory;
- representative entity/revision/snapshot fixtures.

Keep helpers based on public package APIs where the test is intended to prove public usability.

Do not expose internal test helpers as production package exports.

## Required Checks

Run from `web/`:

```text
pnpm typecheck
pnpm test
pnpm build
```

Run any dedicated conformance script as well if added.

All checks must succeed from a clean install using the committed lockfile.

---

## Do Not Do

- Do not weaken package boundaries simply to make tests pass.
- Do not whitelist deep imports from the reference app.
- Do not make the conformance tests depend on a production database.
- Do not require a live external server unless a separate integration-test tier is explicitly available.
- Do not duplicate every package unit test; test architectural behavior that spans packages.
- Do not introduce MUI into lower packages for test convenience.
- Do not treat source file line positions as universal selection identity.
