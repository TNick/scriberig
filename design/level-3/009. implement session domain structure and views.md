# Implement Session Domain Structure and Views

## Objective

Implement the session-domain structures described by `design/level-1/007. domain modeling and adapters.md` inside the existing `scriberig-session` crate.

Sessions use the same universal entity/revision/snapshot model as documents and code. This task must not create a separate transcript database or model-provider-specific session format.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. `design/level-2/001. workspace and package layout.md`
4. the current `scriberig-session` crate and shared graph/schema APIs

---

## Files to Create or Update

Inside `crates/scriberig-session/`, create or update modules equivalent to:

```text
src/lib.rs
src/schema.rs
src/types.rs
src/branch.rs
src/turn.rs
src/description.rs
src/views.rs
src/error.rs
```

Add tests under:

```text
tests/session_structure.rs
tests/session_views.rs
```

Follow the crate's existing module layout if it already differs, but preserve these responsibilities.

---

## Session Vocabulary

Define session-domain entities for at least:

```text
Session
Branch
Goal
HumanInput
AgentOutput
Observation
Question
Decision
ToolInvocation
ToolResult
BranchResult
Summary
Task
Turn
```

Use shared schema/entity/relation APIs.

Do not model an entire session as one transcript string.

---

## Core Relations

Support at least the following semantic relationships:

```text
Session --contains--> Branch
Branch --contains--> Turn
Branch --touches--> any Entity
Decision --derived_from--> Branch
ToolResult --produced_by--> ToolInvocation
BranchResult --produced_by--> Branch
Goal/Task --belongs_to--> Session or Branch as appropriate
```

Turn ordering within a branch must be explicit.

Cross-domain `touches`/reference relations must point to the real target entities without copying their contents into the session.

---

## Branch Metadata

A branch must be able to expose compact navigation metadata without loading all turns.

Support at least:

```text
title or short description
purpose
outcome when completed
state/status
touched entities
turn count or equivalent cheap structural summary
```

Generated descriptions or summaries must carry provenance and remain derived unless explicitly authored/promoted.

The branch entity must remain useful even when no generated summary exists.

---

## Branch State

Define and validate a minimal branch lifecycle suitable for future agent work.

Use the shared schema/validation mechanisms where possible.

At minimum distinguish states equivalent to:

```text
active
completed
abandoned
```

Do not invent model-provider-specific states.

Invalid state transitions should be rejected by session-domain validation rather than silently accepted.

---

## Session Views

Implement domain views that can project the same underlying session knowledge into structured data suitable for later renderers.

At minimum provide view construction for:

```text
branch tree
chronological turn sequence for a selected branch
compact branch summaries/descriptors
decision log
```

If the generic projection system already defines rendering interfaces, integrate with them. Otherwise expose pure structured view builders and defer textual/UI rendering.

Do not implement an LLM context policy in this task unless an existing design already defines one concretely.

---

## Progressive Disclosure

The domain must support this navigation pattern:

```text
Session
  -> Branch
     -> Turn
        -> HumanInput/AgentOutput/ToolInvocation/ToolResult/etc.
```

A caller should be able to list branches with compact metadata without fetching every turn.

A caller should be able to open one branch and then inspect one turn or tool interaction.

---

## Cross-Domain References

Test that a branch can reference/touch arbitrary semantic entities through universal graph handles, for example:

```text
Function
Paragraph
PDFPage
Migration
Decision
```

Do not create session-owned copies of those objects.

---

## Provider Independence

Do not encode OpenAI-, Anthropic-, Gemini-, or other provider-specific message structures as canonical session schema.

Provider request/response payloads may later be preserved as external artifacts or tool/provider metadata, but the session domain remains provider-neutral.

---

## Tests

Add tests proving:

- a session contains ordered/navigable branches;
- a branch contains ordered turns;
- branch compact metadata can be read without loading turn bodies;
- a completed branch can store outcome/result references;
- a branch can touch a code/document/PDF entity without copying it;
- tool invocation and tool result are separate related entities;
- invalid branch state transitions are rejected;
- session views are deterministic from the same snapshot;
- no model provider is required to use the session crate.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-session
cargo clippy -p scriberig-session --all-targets -- -D warnings
```

---

## Do Not Do

- Do not build an agent runtime.
- Do not call a model.
- Do not store the session only as chat transcript text.
- Do not copy referenced project entities into session storage.
- Do not add provider-specific canonical message types.
- Do not create separate session persistence tables that bypass the universal model.
- Do not implement web UI components.

---

## Completion Checklist

- [ ] Session-domain entities use the universal schema/graph model.
- [ ] Branches have compact semantic metadata.
- [ ] Branch/turn ordering is explicit.
- [ ] Cross-domain references use stable semantic handles.
- [ ] Tool calls/results and decisions are structured entities.
- [ ] Branch lifecycle validation exists.
- [ ] Structured session views support progressive disclosure.
- [ ] No agent/model provider is required.
- [ ] Tests, formatting, and clippy pass.
