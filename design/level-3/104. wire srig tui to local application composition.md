# Wire `srig tui` to Local Application Composition

**Status: [ ] Pending**

## Objective

Replace the existing honest `srig tui` stub with the real local embedded TUI while preserving the repository's composition boundaries.

Read first:

1. `design/level-2/011. application operations protocol and runtime boundaries.md`;
2. `design/level-2/020. repository scaffold conventions and native command surface.md`;
3. `design/level-2/021. terminal ui runtime and state architecture.md`;
4. `design/level-2/022. terminal ui views interaction and conformance.md`;
5. `design/level-3/097. expose srig native command stubs.md`;
6. tasks 099 through 103 as applicable.

The key boundary is:

> `scriberig-cli` parses TUI startup arguments, `apps/scriberig` constructs concrete local dependencies, and `scriberig-tui` owns interactive terminal behavior.

---

## CLI Arguments

Change the `Tui` command from a unit variant to a typed argument structure equivalent to:

```text
srig tui --db <PATH>
```

Use the repository's current local-development database default consistently with other local native commands when practical.

Do not add storage opening or application construction to `scriberig-cli`.

The top-level command name remains exactly `srig tui`.

---

## Composition Root

In `apps/scriberig/src/main.rs` or a focused composition module if the file would become too large:

1. receive parsed TUI args;
2. open the selected concrete local store;
3. construct the required `scriberig-app` services/adapters;
4. create an explicit `ApplicationContext`/principal for local TUI use;
5. grant only the capabilities appropriate for the current implemented TUI feature set/product policy;
6. adapt the application service to the TUI service port;
7. invoke the public `scriberig_tui::run(...)` entry point;
8. propagate a safe error to the process boundary if startup/runtime fails.

The TUI crate itself must not import `scriberig-store-sqlite` just to make this wiring convenient.

---

## Principal and Capabilities

Use an explicit principal equivalent to:

```text
local-tui
```

Do not equate local process access with unrestricted semantic authority.

Construct capability grants through the existing application capability model. Start with the least set required by implemented views/actions, for example inspect/read capabilities first.

When later tasks add mutations or agents, expand product grants deliberately rather than using an unrestricted catch-all grant.

---

## Startup Validation

Before entering raw/alternate-screen terminal mode, fail cleanly for startup problems that can be detected first, including:

```text
invalid database path/configuration
store open failure
application construction failure
non-interactive terminal when interactive mode is required
```

Errors detected after terminal entry must still restore the terminal before surfacing process failure.

Do not print ordinary startup diagnostics on top of an active alternate-screen UI unless they are routed through the TUI status/error model.

---

## Process Exit Behavior

Normal user quit returns success.

Startup or unrecoverable runtime failure returns a non-zero process result through the existing executable error path.

User cancellation of an individual semantic operation is not automatically a process failure.

Do not call `std::process::exit` from deep inside `scriberig-tui`; allow RAII terminal restoration and normal error propagation.

---

## Existing Inspect Composition

The repository already constructs a SQLite store, `ApplicationService`, guarded query service, and explicit capability context for the `inspect` command.

Reuse composition helpers where doing so removes duplication without moving product composition into lower layers. If both inspect and TUI need the same local application construction, extract a focused helper under `apps/scriberig` or another appropriate composition-only module.

Do not make the CLI crate own the concrete store simply to share code.

---

## Tests

Add parser/composition tests where feasible for:

- `srig tui` parses;
- `srig tui --db <PATH>` parses;
- invalid arguments are rejected by Clap;
- TUI command no longer prints the old "not implemented" stub;
- composition gives the TUI an explicit principal/capability context;
- a fake/headless TUI entry can be invoked in tests without taking over the test runner's real terminal;
- startup failure before terminal entry reports cleanly.

Do not make automated tests launch an uncontrolled interactive terminal.

---

## Documentation

Update native help/output and any repository command documentation that still describes `srig tui` as unimplemented.

Do not change the stable command spelling established by Level 2 document 020.

---

## Out of Scope

Do not implement in this task:

- remote `--connect` mode;
- a server inside the TUI process;
- automatic unrestricted capability grants;
- direct SQLite usage from `scriberig-tui`;
- provider-specific agent construction unless a separate owning composition task already defines it.

---
