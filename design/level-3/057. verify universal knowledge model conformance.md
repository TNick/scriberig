# Verify Universal Knowledge Model Conformance

## Objective

Complete the first universal knowledge model implementation with cross-crate conformance tests and public API documentation.

The tests must prove that the shared core, schema, and graph layers satisfy the semantic rules in `design/level-1/002. universal knowledge model.md` without relying on an agent runtime, UI, parser, or specific database backend.

This task should primarily add tests and documentation. Only make small implementation fixes needed to satisfy explicit invariants.

---

Read:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-2/001. universal knowledge model rust libraries.md`
3. `design/level-3/001. extend shared core with knowledge values and provenance.md`
4. `design/level-3/002. implement universal schema contracts.md`
5. `design/level-3/003. implement universal graph semantic records.md`
6. the identity/revision/snapshot design used by the implemented workspace.

Inspect the actual crate names and APIs before writing tests. Reuse the canonical shared crates; do not create alternate versions of them.

## 1. Define a Test-Only Domain Schema

Inside the integration test, define a small schema using names such as:

```text
Document
Section
Paragraph
```

These are test fixtures only.

Suggested test structure:

```text
Document --sections--> Section       ordered collection
Section  --blocks----> Paragraph     ordered collection
Section  --related---> Section       typed relation
Paragraph.text                       required string property
Section.title                        optional string property
```

Use schema/type IDs created through the normal public API.

Do not add `Document`, `Section`, or `Paragraph` as variants or production structs in the universal crates.

---

## 2. Entity Continuity vs Exact Revision

Create one paragraph entity and represent two exact revisions for it.

The test must demonstrate:

```text
same EntityId
+ different RevisionId
= same conceptual entity at different exact states
```

Use the identity/storage APIs already defined by prerequisite work.

Do not invent a second ID implementation in the test.

Assert that `EntityId` and `RevisionId` are distinct public types.

---

## 3. Snapshot-Bound Interpretation

Use the existing in-memory snapshot/store implementation if one exists; otherwise implement a tiny test double for the graph-view trait.

Create two snapshots:

```text
S1: Paragraph P -> Revision R1
S2: Paragraph P -> Revision R2
```

Assert that resolving `P` in `S1` and `S2` returns the different expected revisions.

This test must fail if the graph API silently uses an implicit global current revision instead of the requested snapshot.

---

## 4. Ordered Collection Semantics

Construct an ordered collection containing:

```text
[P1, P2, P3]
```

Assert order is preserved.

Construct another ordered collection:

```text
[P2, P1, P3]
```

Assert the values differ.

The entities `P1`, `P2`, and `P3` must keep the same identities in both collections.

This proves that position belongs to the parent collection rather than the child entity.

---

## 5. Unordered Collection Semantics

Construct two unordered collections containing the same members supplied in different input orders.

Assert they have identical semantic membership/equality according to the public API.

The test must show that callers cannot infer semantic order from insertion or storage order.

---

## 6. No Canonical Parent Requirement

Construct a paragraph revision containing only its own type/property state.

Construct a section revision whose collection contains the paragraph entity.

Assert that the paragraph revision does not require a parent ID or position.

If reverse navigation exists in the graph view, use a test/mock reverse index to find the parent and demonstrate that reverse lookup is a derived/view concern.

---

## 7. Typed Relation Validation

Using the test schema, validate:

```text
Section A --related--> Section B
```

as valid.

Then validate an invalid target type such as:

```text
Section A --related--> Paragraph P
```

Assert the invalid case produces a structured validation issue with a stable machine-readable code.

Do not determine validity by matching the human-readable message string.

---

## 8. Property Validation

Validate at least:

1. a paragraph with required string `text`;
2. a paragraph missing `text`;
3. a paragraph with `text` set to the wrong value shape.

Assert:

- the valid subject has no error-severity issues;
- invalid subjects have error-severity issues;
- issues contain semantic locations where practical;
- validation does not panic for ordinary invalid input.

---

## 9. Provenance

Create provenance examples for:

```text
user-authored knowledge
parser-produced knowledge
model-generated description
```

Assert source kinds remain distinguishable.

Create provenance with exact entity/revision dependencies and assert those dependencies can be inspected directly.

Do not add trust ranking assertions. Provenance records origin only.

## 10. Derived Description

Create a description for one exact paragraph revision.

It must contain:

```text
exact entity/revision reference
description profile
text
provenance
```

Use model-generated provenance for this test.

Assert that the description remains a separate derived object and is not automatically inserted into the canonical revision record.

---

## 11. Derived Artifact Dependencies

Create a generic derived artifact with at least two exact immutable input dependencies.

Example concept:

```text
Section S@R1 summary depends on:
  Section S@R1
  Paragraph P@R3
```

Assert that exact dependency revision IDs remain inspectable.

This proves the future incremental-cache contract: an unrelated global snapshot change need not invalidate a derived result whose declared inputs are unchanged.

Do not implement a cache in this task.

## 13. Reverse Navigation Contract

If the graph-view API exposes reverse relation lookup, verify that:

- forward canonical relation exists only in the owning source revision;
- target revision does not need a duplicate reverse edge;
- reverse lookup can still return the source through the view/index abstraction.

If reverse lookup is not yet implemented because it belongs to a later index design, test the type-level contract as far as currently possible and document the deferred behavior clearly.

Do not add backend-specific indexing solely for this test.

---

## 14. Public Documentation Review

Review public API docs across the three layers.

Ensure they clearly communicate:

```text
EntityId   = conceptual continuity
RevisionId = exact immutable state
SnapshotId = exact consistent graph view
```

Also document:

- property values are not a substitute for semantic relations;
- relations are typed;
- ordered/unordered collections differ semantically;
- child entities do not own parent position;
- canonical and derived knowledge differ;
- descriptions/derived artifacts carry provenance and dependencies;
- graph reads that depend on state are snapshot-bound;
- universal libraries do not depend on the agent runtime.

Keep API docs concise; do not copy whole design documents into Rust comments.
