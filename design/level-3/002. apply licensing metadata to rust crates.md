# Apply Licensing Metadata to Rust Crates

## Objective

Apply the platform/product licensing split to every existing Rust crate without creating new crates or changing runtime behavior.

Read before editing:

1. `design/level-1/014. extensibility ecosystem and licensing.md`
2. `design/level-2/001. licensing artifacts package metadata and notices.md`
3. the current Rust workspace/package-layout design, if present
4. every `Cargo.toml` that will be modified

This task is metadata-only.

---

## Preconditions

Run this task only after Rust crate manifests exist.

If the repository contains no Rust `Cargo.toml` package manifests yet:

- do not create placeholder crates;
- do not create empty manifests solely to satisfy this task;
- report that the task is not yet applicable.

If a workspace root exists, distinguish the workspace manifest from package manifests.

---

## Files to Modify

Inspect all Rust manifests in the repository, including:

```text
Cargo.toml
crates/*/Cargo.toml
```

and any other package manifests discovered by the workspace.

Modify only manifests that need explicit or inherited licensing metadata adjusted.

Do not edit Rust source files in this task.

---

## Classification Rule

Classify each crate by architectural responsibility.

Use this default:

```text
Reusable platform crate -> Apache-2.0
Integrated product/runtime crate -> AGPL-3.0
```

Do not classify solely from the crate name.

Read the crate description, dependencies, public API, and controlling designs before deciding.

---

## Apache-2.0 Crates

A crate should normally be Apache-2.0 when its primary purpose is reusable infrastructure, including responsibilities such as:

- core identity/value types;
- immutable storage abstractions;
- concrete reusable storage backends;
- graph/schema libraries;
- query libraries;
- migration/change libraries;
- projection infrastructure;
- reusable domain adapters;
- protocol definitions;
- reusable client SDKs;
- reusable agent-facing interfaces that do not execute the integrated Scriberig runtime.

The fact that an AGPL product depends on a crate does not make the reusable crate AGPL.

---

## AGPL-3.0 Crates

A crate should normally be AGPL-3.0 when its primary responsibility is operating the integrated Scriberig product, including:

- the reference server application when it is the integrated Scriberig server;
- integrated agent execution/orchestration;
- product-specific workflows that coordinate the complete Scriberig runtime;
- binaries whose purpose is to embed and operate that integrated runtime.

Do not mark a generic server protocol library AGPL merely because a server application uses it.

Do not mark reusable agent interfaces AGPL merely because the integrated agent runtime consumes them.

---

## CLI Classification

Do not assume all binaries are AGPL.

A CLI that primarily acts as a reusable client over public platform/server APIs should normally remain Apache-2.0.

A CLI or executable that embeds substantial integrated AGPL runtime/orchestration behavior should follow the AGPL product layer.

If a CLI mixes both responsibilities and the boundary cannot be determined from current designs, stop and report the ambiguity instead of guessing.

---

## Cargo Metadata

Each distributable crate must have a correct Cargo license declaration.

Use Cargo-supported SPDX license metadata corresponding to the license assigned by the controlling design.

Do not use a dual-license expression unless the design explicitly assigns two licenses to the same crate.

Do not use a repository-wide inherited value if doing so would make a mixed-license workspace inaccurate.

Workspace inheritance is acceptable only for groups of crates whose inherited value is correct.

If workspace package metadata currently defines one license for all members and the workspace contains both Apache and AGPL crates, refactor the metadata so each package resolves to the correct license without changing package behavior.

---

## Dependency-Direction Check

While classifying crates, inspect internal Scriberig dependencies.

Expected direction:

```text
Apache reusable crate
        ^
        |
AGPL integrated product crate
```

AGPL product crates may depend on Apache platform crates.

An Apache reusable crate should not depend on an integrated AGPL product crate.

If such a reverse dependency exists:

- do not hide it by changing the reusable crate's license just to make the graph look consistent;
- do not move code during this metadata task;
- record the dependency and report that an architectural refactor is required.

---

## Preserve Existing Package Information

Do not change:

- package names;
- versions;
- descriptions except where needed to understand classification and separately requested;
- dependency versions;
- features;
- targets;
- workspace membership;
- publish settings;
- edition settings;
- build scripts.

This task changes licensing metadata only.

---

## Verification

After editing:

- enumerate every Rust package in the workspace;
- verify every distributable package resolves to a license;
- verify reusable packages resolve to Apache-2.0;
- verify integrated product/runtime packages resolve to AGPL-3.0;
- verify no package accidentally declares both licenses unless a separate design explicitly requires dual licensing;
- verify workspace inheritance does not erase the mixed-license boundary;
- run Cargo metadata/workspace validation sufficient to prove the manifests still parse;
- if the workspace already builds, run the normal lightweight manifest/build checks without changing code.

---

## Do Not Do

Do not:

- create new crates;
- rename crates;
- move source files;
- change dependency versions;
- add source-file license headers;
- create a CLA or DCO;
- add commercial licensing metadata;
- mark every crate AGPL for simplicity;
- mark the integrated runtime Apache for convenience;
- resolve an architectural dependency violation by silently relicensing a reusable package.

---

## Completion Report

Produce a concise table containing:

```text
crate | architectural role | assigned license | reason
```

Also report:

1. manifests modified;
2. any ambiguous crates left unchanged;
3. any Apache -> AGPL reverse dependency discovered;
4. validation commands run and their results.
