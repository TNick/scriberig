# Implement Style-Aware ECMAScript Source Projection Rendering

## Status

Complete. Rust style rendering is already implemented and verified by task 152.

## 1. Goal

Implement deterministic JavaScript/TypeScript/JSX/TSX projection rendering in the ECMAScript domain using the exact resolved domain style contract already implemented by task 151. Preserve the existing projection boundary and classify unsupported or lossy behavior conservatively.

Task 154 owns loss-aware reverse editing and shared product controls. Until that work proves a lossy representation safe to edit, lossy projections remain read-only.

## 2. Required Reading Before Editing

- Read repository and nearest crate `AGENTS.md` files, `design/CONTEXT.md`, Level-1 006, 007, and 024, Level-2 007 and 034, and tasks 151–152.
- Inspect the current ECMAScript parser/AST model, projection adapter registration, rendering path, and tests before choosing an implementation.
- Check dependency and license policy before adding formatter or code-generation dependencies.

## 3. Architectural Constraints

- Keep source text as a projection, not canonical semantic state.
- Keep ECMAScript formatting semantics in the domain adapter, not generic projection or product layers.
- Pass exact resolved style values into deterministic rendering; do not read ambient formatter configuration.
- Do not interpret style-only byte changes as semantic changes.
- Do not claim loss-aware editability because a renderer can omit source content.

## 4. Select and Integrate a Renderer

The viable Oxc code generator was evaluated at the pinned parser version. `oxc_codegen` 0.153 provides explicit indentation, quote, and comment options, but its crate declares Rust 1.97 while this workspace declares Rust 1.85. Adding it would silently raise the workspace minimum compiler requirement. The current domain-owned printer is small and restricted to the explicitly modeled semantic subset, so retain it until the workspace MSRV or Oxc dependency set changes. It does not attempt to pretty-print arbitrary JavaScript.

The retained renderer consumes exact style values, emits two or more exact variants of indentation and quotes, and rejects syntax that it cannot round-trip. Keep renderer dependencies in the domain layer and do not advertise options the renderer does not honor.

## 5. Preserve Comments, Directives, and Fidelity

Classify ordinary comments, JSDoc, license headers, TypeScript directives, lint/formatter directives, and source-map/tooling directives to the extent supported by the parser. Preserve all content unless the adapter can prove that a narrower view-only option retains mandatory categories. Unsupported syntax or unsafe transformations must produce structured diagnostics or a read-only fidelity result.

Use task 151's exact style and fidelity contracts. Lossless formatting may remain editable when existing reconciliation supports it; lossy rendering remains read-only until task 154 proves safe reconciliation.

## 6. Projection Integration

Route rendering through the existing shared adapter/registry boundary. The result must report the exact style and renderer identity, distinguish cache identities across styles, and retain the semantic scope and snapshot. Add a narrow repository-convention mapping only if it fits an existing owner and feeds the shared style resolver.

## 8. Handoff to Task 154

Task 154 may use an ECMAScript projection only when its exact baseline and fidelity classification satisfy loss-aware reconciliation requirements. It must not infer safe editing from successful rendering alone.
