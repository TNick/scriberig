## Snapshot API

Define backend-independent operations equivalent to:

```text
resolve(snapshot, entity) -> RevisionId?
apply_changes(base_snapshot, changes) -> SnapshotId
iterate(snapshot) -> entity/revision pairs
diff_snapshots(a, b) -> changed entity mappings
```

Snapshot changes are storage-level operations only:

```text
Set(EntityId, RevisionId)
Remove(EntityId)
```

Do not encode semantic migration meaning here.

## Snapshot identity

Snapshot identity must be deterministic for the complete entity-to-revision mapping.

Two snapshots produced through different update orders but containing the exact same mapping must obtain the same `SnapshotId`.

Do not use insertion order, timestamps, allocation IDs, or backend row numbers in snapshot identity.

## Persistent representation

The in-memory implementation must provide structural sharing rather than cloning the entire map for every update.

A simple correctness-first persistent tree or layered immutable map is acceptable. Keep the physical representation private so it can be replaced later.

Add a test or internal instrumentation proving a one-entry update shares unchanged structure with its base. The test should not expose the private representation through the public API.

## Named roots

Implement:

```text
read_root(name)
compare_and_set_root(name, expected_snapshot_or_none, new_snapshot)
```

Rules:

- promotion is atomic within the in-memory backend's synchronization model;
- stale expected values return a typed conflict;
- a failed promotion leaves the root unchanged;
- moving a root never mutates either snapshot.

## Persistent collections

Define a backend-neutral immutable ordered collection abstraction for canonical semantic lists.

Required operations:

```text
create
len
get
iterate
insert
remove
move/replace sequence as justified by implementation
```

The implementation must keep position in the collection rather than in child IDs.

Use a simple immutable chunked sequence or similarly replaceable structure. Do not optimize prematurely.

## Memory revision storage

Complete the memory backend implementation of the revision API from task 002.

Exact duplicate revisions are reused/idempotent.

## Tests

At minimum:

- old snapshot remains readable after creating a descendant snapshot;
- one entity changes while unrelated entity mappings remain identical;
- removing an entity from a new snapshot does not remove it from the base;
- two branches can be created from one base;
- equivalent mappings converge to the same `SnapshotId`;
- root CAS succeeds when expected value matches;
- root CAS fails cleanly when stale;
- failed root CAS leaves root unchanged;
- reordering a collection changes collection state without changing child IDs;
- memory backend revision insertion is idempotent.

## Do not do

- Do not add SQL.
- Do not implement migrations or merges.
- Do not make a section/document/function type.
- Do not use the global snapshot ID as the identity of individual revisions.
