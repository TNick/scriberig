# Implement Principal and Capability Model

## Objective

Add the minimum runtime types needed to represent actors and explicit capabilities without moving authorization policy into the generic store.

This task implements the authority vocabulary required by `design/level-1/013. trust validation capabilities and provenance.md`. It does **not** implement authentication, secrets, policy evaluation, query filtering, or UI.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 7–13 and 46–49.
2. `design/level-1/010. universal query and operation model.md`.
3. `design/level-1/011. runtime libraries protocol and product surfaces.md`.
4. `design/level-2/001. workspace and package layout.md`.
5. `design/level-3/001. extend shared core with knowledge values and provenance.md`.

Inspect the actual workspace before editing. Reuse existing crates and naming. If the Rust workspace or canonical core/application crates do not exist yet, stop and report the missing prerequisite instead of creating a competing layout.

## Ownership

Use the existing shared core crate only for small cross-cutting identity/value types that lower layers may need for attribution. Put capability semantics and enforcement-facing types in the shared application crate.

Expected locations, adjusted to the actual workspace if names differ:

```text
crates/scriberig-core/src/principal.rs
crates/scriberig-core/src/lib.rs
crates/scriberig-app/src/capability.rs
crates/scriberig-app/src/lib.rs
```

Do not create a new authorization crate in this task.

## Principal Types

Define a stable `PrincipalId` newtype, or reuse an equivalent existing type. It identifies an actor for attribution; it does not imply permission.

Add a compact actor-kind vocabulary sufficient to distinguish at least:

```text
Human
Agent
System
Service
Connector
Importer
Validator
ApiClient
Custom
```

Keep custom/extension support so new actor categories do not require changing the core crate.

Do not put credentials, authentication claims, roles, or capability lists inside `PrincipalId`.

## Capability Model

In the application layer, define an explicit capability value with three parts:

```text
scope
actions
constraints
```

Support at least these actions:

```text
Inspect
Query
Render
Propose
ModifyBranch
Validate
Promote
InvokeExternal
```

The scope model must be able to represent project, session, branch, entity, relation/projection, and external-destination scopes without encoding unrestricted filesystem paths as authority.

Constraints must be able to bind authority to an exact snapshot and, where applicable, a branch, domain, operation kind, lifetime, or external destination.

Prefer typed enums/newtypes over arbitrary strings for core actions. Allow extension points where future domains need additional actions.

## Least-Authority Semantics

Implement pure helper functions for checking whether one capability covers a requested operation and whether a delegated capability is no broader than its parent.

Required invariants:

- absence of a capability means denial;
- read authority does not imply write authority;
- branch modification does not imply promotion;
- local semantic modification does not imply external side effects;
- a child/delegated capability may be equal to or narrower than its parent, never broader;
- content stored in the graph cannot create or modify a capability value merely by being read.

Do not add ambient global capability state.

## Structured Denial

Define an application-level denial type containing at least:

```text
principal
requested_action
requested_scope
reason
optional narrower alternatives
approval_possible flag or equivalent
```

Do not expose secrets or hidden object contents in the denial text.

## Tests

Add unit tests proving:

1. inspect does not grant promote;
2. modify-branch does not grant promote;
3. project read can cover a descendant read when the scope rules explicitly allow it;
4. entity-only access does not automatically cover arbitrary relation traversal;
5. external invocation requires an external destination scope;
6. delegated capability cannot widen scope;
7. delegated capability cannot add an action absent from the parent;
8. snapshot constraints are enforced;
9. capability denial is a normal structured result;
10. principal identity alone grants nothing.

## Validation

Run the workspace formatting, check, test, and lint commands already established by the repository.

## Do Not

Do not implement login, OAuth, password handling, cryptographic tokens, secret storage, HTTP middleware, model-specific rules, filesystem sandboxing, or project promotion. Do not add permission fields to ordinary domain entities.
