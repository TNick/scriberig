# Implement Markdown Domain Schema

## Objective

Implement the canonical Markdown domain vocabulary described by `design/level-1/007. domain modeling and adapters.md` inside `scriberig-domain-markdown`.

This task defines what Markdown knowledge means after it is inside Scriberig. It does not implement filesystem watching, external-edit reconciliation orchestration, agent tools, or UI components.

Read before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. `design/level-3/001. scaffold domain adapter crates.md`
4. the current public APIs of `scriberig-core`, `scriberig-schema`, and `scriberig-graph`

Do not create substitute schema or graph frameworks inside the Markdown crate. If required shared APIs are not implemented yet, stop and report the missing prerequisite.

---

## Files to Create or Update

Inside `crates/domains/markdown/`, create:

```text
src/lib.rs
src/schema.rs
src/types.rs
src/classification.rs
```

Add tests either as module tests or under:

```text
tests/schema.rs
```

Do not create parser, renderer, or reconciliation modules in this task.

## Canonical Entity Vocabulary

Define the Markdown domain vocabulary needed for the first implementation slice:

```text
MarkdownDocument
Section
Heading
Paragraph
List
ListItem
Table
TableRow
TableCell
CodeBlock
QuoteBlock
Link
ImageReference
InlineContent
```

Use the shared schema system rather than defining an unrelated local type registry.

The schema must make the following structural intent representable:

```text
MarkdownDocument
  contains ordered top-level blocks/sections

Section
  has optional heading/title structure
  contains ordered blocks and nested sections

List
  contains ordered ListItem entities

Table
  contains ordered TableRow entities

TableRow
  contains ordered TableCell entities
```

`Paragraph`, `Heading`, `CodeBlock`, `QuoteBlock`, `Link`, `ImageReference`, and `InlineContent` must be independently addressable semantic entities where the shared model supports entity identity.

---

## Canonical, Derived, and Projection-Only Classification

Create an explicit Markdown-domain classification that communicates which information belongs to canonical state.

At minimum, encode or expose the following decisions:

Canonical:

```text
section/block structure
paragraph text/content
list/item structure and order
table/row/cell structure and order
code block semantic content
links and image references
meaningful inline structure needed for faithful round-trip behavior
```

Projection-only by default:

```text
indentation width
line wrapping
blank-line count used only for formatting
table column padding/alignment spacing
other whitespace with no Markdown semantic meaning
```

Derived by default:

```text
summaries
topic labels
generated outlines
model-generated descriptions
search indexes
```

Do not mark a generated description canonical.

The concrete representation of this classification must use existing shared schema metadata if available. If no shared mechanism exists yet, expose a small Markdown-local function or constants that describe the classification without inventing a second persistence model.

---

## Relations and Collections

Use universal relations/collections rather than embedding opaque nested JSON when shared graph primitives exist.

The schema should support at least these semantic relations:

```text
MarkdownDocument --contains--> Section/Block
Section --contains--> Section/Block
List --contains--> ListItem
Table --contains--> TableRow
TableRow --contains--> TableCell
```

Containment must be ordered where document order is meaningful.

Do not store reverse parent IDs as canonical child properties solely for navigation. Reverse traversal should use shared graph/index behavior.

---

## Navigation Expectations

The schema must support progressive disclosure:

```text
Document
  -> top-level Section/Block
     -> nested Section/Block
        -> Paragraph/Table/List/etc.
           -> Row/Cell/Item/InlineContent
```

A future consumer must be able to inspect a document or section and learn child counts/types without loading the full document body.

This task does not implement the query surface, but the schema must not prevent that access pattern.

---

## Public API

Expose only the minimum public API necessary for other crates to obtain/register the Markdown schema and refer to Markdown domain type/relation identifiers.

Prefer a shape equivalent to:

```text
markdown_schema()
```

or the established registration pattern already used by `scriberig-schema`.

Do not invent a parallel registration mechanism.

`lib.rs` should re-export the stable Markdown schema entry point and domain identifiers needed by later adapter tasks.

---

## Tests

Add tests proving at least:

- every required Markdown entity type is present;
- ordered containment is defined for lists, tables, rows, sections, and document blocks;
- a paragraph can exist as an independently addressable entity;
- canonical/projection-only/derived classification matches this task;
- invalid obvious relations are rejected if the shared schema system supports endpoint validation;
- schema registration is deterministic.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-markdown
cargo clippy -p scriberig-domain-markdown --all-targets -- -D warnings
```

## Do Not Do

- Do not parse Markdown text yet.
- Do not render Markdown text yet.
- Do not implement external-edit reconciliation.
- Do not add summaries or model calls.
- Do not add filesystem code.
- Do not add SQL tables.
- Do not depend on agent crates.
- Do not treat source byte ranges as semantic identity.
- Do not make formatting whitespace canonical unless required by Markdown semantics.
