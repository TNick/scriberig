# Implement Universal Schema Contracts

## Objective

Implement the universal schema layer that lets domain crates define strongly typed semantic concepts without changing the storage architecture.

This task owns schema definitions and schema-level validation contracts only.

It must reuse the already-established shared core crate and must not create a second workspace, core, store, or graph implementation.

---

## Read First

Read:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-2/001. universal knowledge model rust libraries.md`
3. `design/level-3/001. extend shared core with knowledge values and provenance.md`
4. the repository-wide workspace/package-layout design.

Inspect the actual workspace before editing.

Use the universal schema crate already established by the workspace if it exists. If it does not exist yet, create the crate at the canonical workspace path prescribed by the repository-wide layout rather than inventing an alternative prefix.

Do not create concrete Markdown, Rust, PDF, or session schemas in this task.

---

## Files to Create or Modify

Inside the canonical universal schema crate:

```text
Cargo.toml
src/lib.rs
src/entity.rs
src/property.rs
src/relation.rs
src/collection.rs
src/validation.rs
```

If these files already exist as skeletons, fill them in instead of duplicating modules.

The schema crate must depend on the shared core crate only for universal IDs/values/provenance needed by the schema model.

It must not depend on the universal graph crate, because graph records need to be able to implement schema validation without creating a dependency cycle.

---

## 1. Property Value Shapes

In `property.rs`, define a public `ValueShape` or equivalent type describing the accepted shape of the shared `KnowledgeValue` type.

Support at least:

```text
Any
Null
Bool
SignedInteger
UnsignedInteger
Float
String
Bytes
List
Record
```

Recursive list/record shape constraints are desirable if they remain simple and deterministic.

Do not turn this into a general-purpose type language.

Define `PropertySchema` with at least:

```text
key
name
description              optional
value_shape
required                  bool or equivalent
knowledge_class           Canonical / Derived
```

If the project already has a common cardinality/requiredness type, reuse it.

---

## 2. Cardinality

Define one reusable cardinality representation for relation and collection schemas.

It must express common cases:

```text
zero or one
exactly one
zero or more
one or more
bounded min/max
```

A compact representation such as `min` plus optional `max` is acceptable if invariants are validated at construction time.

Do not encode cardinality only as documentation text.

---

## 3. Relation Schemas

In `relation.rs`, define `RelationSchema` or equivalent.

Required semantic fields:

```text
relation type ID
human-readable name
optional description
permitted source entity types
permitted target entity types
knowledge class
cardinality
reverse-navigation expectation
```

The reverse-navigation setting should indicate whether reverse lookup is expected to be derived/index-backed.

Do not require reverse relations to be duplicated in canonical child state.

Use semantic entity-type IDs, not Rust `TypeId`, filenames, or module names unless an existing core type intentionally represents schema type identity.

---

## 4. Collection Schemas

In `collection.rs`, define `CollectionSchema` or equivalent.

Required semantic fields:

```text
collection type ID
human-readable name
optional description
owner entity type
permitted member entity types
order semantics
cardinality
knowledge class
```

Represent order semantics explicitly, for example:

```text
Ordered
Unordered
```

Do not collapse collections into generic relations: order/membership semantics are part of the Level 1 model.

---

## 5. Entity-Type and Domain Schemas

In `entity.rs`, define an `EntityTypeSchema` containing:

```text
entity type ID
human-readable name
optional description
property definitions/references
relation definitions/references
collection definitions/references
```

Also define a top-level `Schema`/`DomainSchema` containing:

```text
schema ID
schema version
human-readable name
optional description
registered entity types
relation definitions
collection definitions
```

Use deterministic map/set containers where practical.

The schema version can initially be a small explicit value/string. Do not design schema migrations in this task.

No production domain type may be hard-coded into these enums/structs.

---

## 6. Validation Subject Trait

In `validation.rs`, define a small trait such as `ValidationSubject` that exposes graph-shaped data using only shared core types.

It should allow schema validation to inspect, conceptually:

```text
entity type
properties and values
relations and target entity IDs
collections and member entity IDs
```

If target/member entity types are needed, define a separate lightweight validation context/resolver trait that can answer:

```text
entity ID -> entity type, within a caller-provided context
```

The schema crate must not depend on the graph or store crates.

Later the universal graph `RevisionRecord` will implement `ValidationSubject`.

---

## 7. Structured Validation Results

Define public equivalents of:

```text
ValidationSeverity
ValidationLocation
ValidationIssue
ValidationReport
```

A validation issue must include:

```text
severity
stable machine-readable code
human-readable message
optional semantic location
```

Semantic location must be able to identify at least:

```text
whole subject/entity
property key
relation type
collection type
```

Do not make file path or line number mandatory for validation locations.

A `ValidationReport` must expose a direct `has_errors()`-style API so callers never need to parse message text.

---

## 8. Required Validation Behavior

Implement deterministic schema-level validation for at least:

1. entity type is declared;
2. required properties are present;
3. property values match declared value shape;
4. unknown properties are handled by one documented deterministic policy;
5. relation types are valid for the source entity type;
6. relation cardinality is valid;
7. relation target types are valid when target-type context is available;
8. collection type is valid for the owner;
9. collection cardinality is valid;
10. collection member types are valid when member-type context is available.

Ordinary invalid data must produce `ValidationReport` issues, not panics.

Use Rust errors only when validation cannot be performed because the schema/context itself is unusable.

---

## 9. Public Exports

`lib.rs` should expose the primary schema and validation types without forcing downstream crates through deep private paths.

Keep helper functions private unless they are genuinely part of the domain-adapter API.

The public API should make a clear distinction between:

```text
schema definitions
runtime graph data
validation results
```

The schema crate should contain only the first and third categories.

---

## 10. Unit Tests

Add focused tests for:

- required vs optional properties;
- each relevant value-shape match/mismatch;
- relation source/target restrictions;
- relation cardinality;
- ordered/unordered collection schema metadata;
- collection cardinality;
- structured validation locations;
- stable machine-readable issue codes;
- `has_errors()` behavior;
- a custom test-only entity vocabulary proving production domains are not hard-coded.

Use test-local IDs such as `test.document`, `test.section`, and `test.paragraph` only inside test code.

---

## Documentation

Document these invariants:

- schemas add domain meaning; they do not store project instances;
- universal schemas remain domain-independent;
- relations and collections are typed explicitly;
- reverse navigation can be derived rather than canonically duplicated;
- ordered and unordered collection semantics differ;
- validation issues are semantic and machine-readable;
- parser/compiler/product validity belongs to higher layers.

## Do Not

Do not:

- create a new core crate;
- depend on the graph crate;
- add database access;
- add parser/compiler validation;
- add migrations;
- add queries/search;
- add concrete Markdown/Rust/PDF/session schemas;
- store actual project entities inside schemas;
- require canonical reverse edges;
- add agent/UI/server behavior.
