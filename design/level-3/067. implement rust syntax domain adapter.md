# Implement Rust Syntax Domain Adapter

## Objective

Implement the Rust-specific source syntax specialization and adapter in `scriberig-domain-rust` on top of `scriberig-domain-code`.

This task represents Rust source syntax faithfully enough for semantic inspection, editing, and later projection reconciliation. It does not implement compiler-derived analysis; that is a separate task.

Read before editing:

1. `design/level-1/007. domain modeling and adapters.md`
2. `design/level-3/005. implement language independent code domain.md`
3. current public APIs of `scriberig-schema`, `scriberig-graph`, `scriberig-migration`, and `scriberig-projection`

---

## Files to Create or Update

Inside `crates/domains/rust/`, create or update:

```text
src/lib.rs
src/schema.rs
src/syntax.rs
src/parse.rs
src/render.rs
src/mapping.rs
src/comments.rs
src/code_groups.rs
src/error.rs
```

Add tests under:

```text
tests/parse_render.rs
tests/schema.rs
tests/comments_and_groups.rs
```

Do not create compiler-analysis modules in this task.

---

## Parser Dependency

Choose one mature Rust parser that preserves source-level syntax needed for round-trip semantics, including attributes, patterns, macros/token trees, comments or source ranges sufficient to recover comments, and nested expressions/statements.

Prefer an already-selected workspace dependency if one exists. Do not introduce multiple competing Rust syntax parsers.

Parser-specific types must remain private to the adapter.

---

## Rust Schema Specialization

Extend the language-independent code domain with Rust-specific constructs needed for the supported syntax slice.

At minimum represent:

```text
functions
parameters
patterns
type syntax
let statements
expression statements
path expressions
call/method-call expressions
binary/unary expressions
blocks
if expressions
match expressions and arms
return/break/continue where relevant
structs/enums where needed for module inspection
impl blocks
attributes
macro invocations
token trees or equivalent concrete syntax for macros
comments
```

Use language-independent `Module`, `Function`, `Parameter`, `CodeGroup`, `Statement`, `Expression`, and `Comment` concepts where appropriate, and Rust-specific types where semantics differ.

Do not normalize Rust into a generic compiler IR.

---

## Canonical Syntax Rules

Canonical state must preserve author-chosen syntax that matters to source-level meaning or faithful reconstruction.

Preserve at least:

- declaration structure and order;
- parameter patterns and type syntax;
- statement/expression structure;
- attributes;
- macro invocation syntax and token trees where normalization would lose information;
- source-authored comments that can be reliably attached;
- meaningful grouping and ordering.

Do not make ordinary indentation, line wrapping, or spacing semantic identity.

---

## Comments

Recover comments from source and represent them through the shared code-domain comment model.

Attach comments to the nearest domain object only when the attachment is deterministic enough to preserve author intent.

When attachment is ambiguous, preserve source-location metadata and avoid inventing a false semantic attachment.

Distinguish source-authored comments from future generated descriptions.

---

## Code Groups

Create initial deterministic code groups from source evidence only.

Use signals such as:

```text
blank-line boundaries
leading explanatory comments
explicit block boundaries
statement sequence
```

Do not call a model to name groups.

A group may have no human-readable purpose description yet. Preserve the group boundary/provenance separately from any later derived summary.

---

## Rendering

Implement deterministic source rendering for the supported canonical syntax.

The renderer may use an existing pretty-print/formatting library if compatible with the projection architecture, but must render from Scriberig semantic state rather than retaining the original source file as the authoritative representation.

Macros/token structures that cannot be safely normalized must round-trip without semantic loss.

Do not silently replace unsupported constructs with placeholders.

---

## Source Coordinates

Parser source spans, filenames, line numbers, and byte positions are adapter/projection metadata.

They may support diagnostics, external editing, and UI highlighting, but they must not be the primary semantic identities of functions, statements, expressions, or comments.

---

## Adapter API

Expose syntax-domain operations through existing domain/projection abstractions where available:

```text
parse/import Rust source -> candidate semantic objects
render Rust semantic scope -> source text
```

Do not expose parser AST types publicly.

Do not write directly to persistence from parse/render operations.

---

## Tests

Include fixtures covering at least:

```text
simple functions
patterns and typed parameters
nested expressions
if/match
attributes
impl blocks
macros
comments
blank-line/comment code grouping
```

Test:

- parse produces expected semantic structure;
- shared code-domain concepts are reused;
- Rust-specific syntax remains specialized;
- comments are preserved without becoming parser trivia;
- macro/token syntax survives round trip;
- parse -> render -> parse preserves equivalent canonical syntax for supported fixtures;
- formatting-only differences do not change canonical semantics;
- no semantic identity depends on line numbers.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-rust
cargo clippy -p scriberig-domain-rust --all-targets -- -D warnings
```

---

## Do Not Do

- Do not implement symbol resolution or type inference.
- Do not implement call/CFG/data-flow graphs.
- Do not use rustc IR as canonical storage.
- Do not flatten macros into expanded compiler syntax as the only representation.
- Do not add agent dependencies.
- Do not create Rust-specific persistence tables.
- Do not make formatting whitespace canonical.
- Do not silently discard unsupported syntax.

---

- [ ] Rust-specific schema extends the shared code domain.
- [ ] Source syntax is represented semantically rather than as one text blob.
- [ ] Comments are preserved as first-class knowledge where deterministic.
- [ ] Initial code groups come from source evidence only.
- [ ] Macros/token trees preserve author syntax.
- [ ] Rendering is deterministic for supported syntax.
- [ ] Parser implementation details remain private.
- [ ] No compiler-derived analysis is mixed into canonical syntax.
