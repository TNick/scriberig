# Add Universal Model Conformance Tests

## Objective

Finish the first universal knowledge model implementation by adding cross-crate integration tests and public API documentation that prove the Level 1 invariants are represented correctly without relying on a database or agent runtime.

This task should not add new architecture unless a missing API is required to satisfy an explicit invariant from the Level 1 or Level 2 design.

Inspect the actual APIs implemented by previous agents before writing tests. Prefer small fixes to naming or visibility over redesigning the crates.

## 1. Build a Local Test Schema

Inside the integration test, define a small schema using generic example domain names only for testing:

```text
Document
Section
Paragraph
```

Suggested properties and relations:

```text
Paragraph.text: required string
Section.title: optional string
Document.sections: ordered collection of Section
Section.blocks: ordered collection of Paragraph
Section.related: optional relation to Section
```

These names must exist only in tests. Do not add them to `sr-core`, `sr-schema`, or `sr-graph` as production domain types.

Use explicit test identifiers such as:

```text
EntityId("doc-1")
EntityId("section-a")
RevisionId("rev-section-a-1")
SnapshotId("snapshot-1")
```

The exact constructor syntax should match the implemented API.

---

## 2. Prove Entity and Revision Separation

Create one conceptual paragraph entity and two hypothetical revisions for it.

The test must demonstrate through types/data that:

```text
same EntityId
+ different RevisionId
= same conceptual entity at two exact states
```

Do not implement persistence or mutation to prove this. Construct the values directly or through an in-memory test view.

Add assertions that entity and revision identifiers are never represented by one interchangeable alias.

---

## 3. Prove Snapshot-Bound Interpretation

Implement a minimal in-test `KnowledgeView` or mock view with two snapshots.

For example:

```text
Snapshot S1: Paragraph P -> Revision R1
Snapshot S2: Paragraph P -> Revision R2
```

Assert that resolving `P` against different snapshots returns the correct exact revision.

This is the most important test for preventing accidental implicit-current-state APIs.

Do not introduce a production in-memory database just for this test. A small test double is enough.

---

## 4. Prove Ordered Collection Semantics

Construct a document or section revision containing an ordered collection:

```text
[P1, P2, P3]
```

Assert that order is preserved exactly.

Then construct:

```text
[P2, P1, P3]
```

and assert that it is a different ordered collection value.

Do not change any paragraph identities to represent the reorder.

This proves that position belongs to the containing collection rather than to the child entity.

---

## 5. Prove Unordered Collection Semantics

Construct two unordered collection values containing the same entity IDs inserted in different orders.

Assert they are semantically equal or otherwise expose identical membership according to the API.

The test must make it impossible for callers to mistake physical insertion order for semantic order.

---

## 6. Prove No Canonical Parent Requirement

Construct a child paragraph revision without any parent identifier.

Construct a section collection that contains the paragraph entity.

Assert the relationship is fully representable without modifying the paragraph revision to add a parent pointer.

If the graph API exposes reverse-navigation results, use the mock view to demonstrate that the parent can be discovered through derived/index behavior rather than child canonical state.

---

## 7. Prove Typed Relations

Construct a typed relation such as:

```text
Section A --related--> Section B
```

Validate it against the test schema.

Also construct an invalid target type such as:

```text
Section A --related--> Paragraph P
```

and assert that schema validation returns a structured issue with a machine-readable code.

Do not inspect the human-readable message to determine validity.

---

## 8. Prove Property Validation

Validate:

- a paragraph with required string `text`;
- a paragraph missing `text`;
- a paragraph whose `text` property contains the wrong `KnowledgeValue` shape.

Assert:

- valid subject produces no error-severity issues;
- invalid subjects produce structured validation issues;
- validation failure does not panic.

---

## 9. Prove Derived Description Semantics

Create a description for an exact paragraph revision.

The description must include:

- `EntityRevisionRef`;
- description profile;
- provenance;
- generated text.

Use model-generated provenance in the test.

Assert that the description is a separate derived object and is not inserted into the canonical `RevisionRecord` merely by being associated with it.

---

## 10. Prove Derived Artifact Dependencies

Create a derived artifact whose dependencies include two exact entity/revision references.

For example:

```text
summary of Section S@R1
using Paragraph P@R3
```

Assert that those exact dependency revision IDs remain inspectable from the artifact.

This demonstrates the future cache invariant: unrelated snapshot changes do not invalidate an artifact whose declared inputs remain unchanged.

Do not implement a cache in this task.

---

## 11. Prove Domain Independence

Add at least one assertion or compile-time usage pattern showing that all test domain names are supplied as schema identifiers at runtime/test construction.

Search the production crates before finishing and confirm they do not contain hard-coded production definitions for:

```text
MarkdownSection
RustFunction
PdfPage
SessionBranch
```

Documentation may mention these as examples, but public model enums must not contain them as variants.

---

## 12. Public Documentation Review

Review public types introduced in the three crates.

Ensure generated Rust documentation clearly states:

- `EntityId` means conceptual continuity;
- `RevisionId` means one exact immutable state;
- `SnapshotId` means one exact consistent graph view;
- relations are typed semantic edges;
- collection ordering is explicit;
- reverse navigation is not required to be canonical duplication;
- descriptions and derived artifacts carry provenance/dependencies;
- the crates are storage-independent and agent-independent.

Do not add long architecture essays to every type. Link concepts through concise module/type docs.
