# Implement: Observability and Shared Store Conformance

## Objective

Create one backend-neutral conformance suite and one backend-neutral observability/error model, then run the same behavior tests against the in-memory and SQLite backends.

This task proves that higher layers can depend on `sr-store` rather than on a particular backend.

## Read first

Read:

1. `design/level-1/004. persistence and storage model.md`
2. `design/level-2/006. persistence observability and conformance.md`
3. All earlier Level 3 persistence tasks.

## Files to create or update

In `sr-store`:

```text
crates/sr-store/src/
├── error.rs
├── stats.rs
└── conformance.rs
```

Add or update:

```text
crates/sr-store/tests/conformance.rs
```

Backend crates may add small test adapters, but expected behavior must live in shared conformance logic rather than duplicated test bodies.

## Error model

Ensure storage errors have machine-readable categories for at least:

- not found;
- invalid identifier or encoding;
- unsupported encoding/storage version;
- stale named-root compare-and-set;
- integrity failure;
- invalid operation;
- backend transaction/I/O failure.

Backend-specific errors may be retained as sources, but callers must not need to parse backend-specific strings to determine category.

## Observability types

Implement backend-neutral data types equivalent to:

```text
StoreStats
RootStatus
IntegrityReport
GcReport
IndexStatus
```

Do not require every backend to provide every numeric statistic. Use optional values when a metric cannot be determined cheaply or meaningfully.

At minimum, expose where possible:

- revision count;
- snapshot count;
- named-root count;
- reachable/unreachable counts after reachability analysis;
- backend storage byte count if meaningful;
- integrity issue counts;
- GC candidate/deleted counts.

Observability values must not participate in canonical revision or snapshot identity.

## Shared conformance harness

Build reusable test functions that accept a backend factory or test-store instance implementing the public storage traits.

The suite must verify at least:

1. put/get immutable revision;
2. duplicate revision insertion is idempotent;
3. create/read snapshot;
4. historical base snapshot remains readable after descendant creation;
5. branch two snapshots from one base;
6. deterministic snapshot identity for equivalent maps;
7. named-root compare-and-set success;
8. stale compare-and-set conflict and unchanged root;
9. reopen/durability test when backend declares durable capability;
10. reachability from protected roots;
11. integrity verification of healthy data.

Use backend capabilities to skip only behavior that is genuinely inapplicable, such as reopening an in-memory-only store. Core semantic behavior must not be skipped.

## Cross-backend fixtures

Create deterministic fixture histories such as:

```text
S1: A -> R1, B -> R1
S2: A -> R2, B -> R1
S3: A -> R1, B -> R2
```

Run the same fixture against memory and SQLite.

Assert that logical `RevisionId` and `SnapshotId` values are identical across backends for the same canonical content and complete mapping.

This test is critical: a backend must not influence semantic identity.

## Tests

- memory backend passes shared suite;
- SQLite in-memory database passes shared suite;
- SQLite temporary file database passes durable parts of suite;
- fixture IDs match across memory and SQLite;
- error categories match for equivalent failures;
- observability calls do not change snapshots or roots.

## Commands to run

```text
cargo fmt --check
cargo test --workspace
```

Run any stricter lint command already established by the repository. Do not introduce a new CI system in this task.

## Do not do

- Do not add HTTP/CLI observability surfaces.
- Do not add Prometheus or telemetry dependencies yet.
- Do not let conformance tests import SQLite internals.
- Do not loosen semantics merely to make both backends pass.

## Completion checklist

- [ ] Shared conformance suite exists.

- [ ] Cross-backend logical IDs match.
- [ ] Error categories are backend-neutral.
- [ ] Observability models are backend-neutral.
