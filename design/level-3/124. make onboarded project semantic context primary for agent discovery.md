# Make Onboarded Project Semantic Context Primary for Agent Discovery

## Objective

After task `123` onboards the current checkout, make the resulting exact project workspace the authoritative context for subsequent agent work, and prove that nested agent branches can discover repository architecture semantically while returning compact durable results to their parent.

Required transition:

```text
bootstrap environment path
    -> onboard project P@S0
    -> continuation bound to P@S0
    -> semantic find/inspect/render/follow
    -> nested read-only discovery branch
    -> compact BranchResult
```

This task does not implement project-wide source changes yet. It prepares exact semantic discovery/context so task `125` can build changes from reliable targets.

## Exact Continuation Scope

When onboarding completes, subsequent agent continuation in the same TUI session must carry exact semantic project context equivalent to:

```text
project_id = P
snapshot_id = S0
root_entity_id = R
optional current semantic selection
```

This structured scope is authoritative.

Do not reduce it to prompt text such as:

```text
"we are in /tmp/scriberig"
```

or to a mutable implicit global project.

The continuation may still retain trusted environment metadata as supplementary context, but project semantic operations resolve against the exact project/snapshot.

---

## Context Compiler Behavior

Extend/reuse the existing branch context compiler so it can compile a project-oriented model request containing a bounded orientation summary such as:

```text
active project identity/display name
exact current/base snapshot
semantic root/selection handles
relevant recent parent branch result(s)
small capability catalog
```

Do not inject the entire imported repository, entire raw semantic graph, or entire onboarding transcript into the provider request.

The model should discover details through tools.

Context/cache keys must include exact semantic/project/branch/tool-catalog inputs according to existing cache design. A cached request built for a different snapshot must not be reused as if it described `S0`.

## Semantic Read Catalog

For an onboarded source project, the authorized agent should be able to discover/use shared operations equivalent to:

```text
capabilities
inspect
list
follow
find
query
render
history where useful
```

Use existing public application/query/projection operations.

Do not add a second agent-only semantic search engine.

Tool results should return stable handles plus bounded summaries and pagination rather than unbounded source/graph dumps.

## Project Guidance Discovery

The golden repository task must be able to discover repository guidance through the imported semantic project.

The deterministic provider should locate objects corresponding to:

```text
AGENTS.md
design/AGENTS.md
relevant Level 1/2 design documents
```

through semantic find/navigation and render their source projection as needed.

The proof must establish that the agent can retrieve the exact imported project source representation at `S0`.

A direct raw filesystem read may remain available as an explicitly authorized fallback for unsupported cases, but the golden discovery path must use semantic project operations after onboarding.

## Architecture Discovery Target

For the later PHP extension, the agent must be able to discover semantic/source references for at least:

```text
shared code domain
representative Tree-sitter language adapter (Python is a useful precedent)
project scan/classification logic
project adapter/import dispatch
workspace Cargo metadata
domain conformance/test support
relevant capability/format registry metadata
```

The test should not hard-code entity IDs. It may use stable names/text/kinds and then inspect the returned semantic handles.

Path strings may appear in results as human/source context, but semantic identity/snapshot remain attached.

## Nested Read-Only Discovery Branch

The parent branch starts a child branch with an explicit request equivalent to:

```text
purpose = determine minimal extension points for PHP source ingestion
base project = P
base snapshot = S0
selection = project/root or relevant semantic scope
capabilities = read-only semantic operations
expected result = architecture map
```

The child must not receive:

```text
change.propose
change.apply
direct filesystem write
direct database mutation
```

unless some unrelated existing policy explicitly grants them; the golden child test must verify they are absent/denied.

---

## Child Branch Context Isolation

The child receives only deliberately inherited context plus its own task.

At minimum, tests must prove:

- child project/snapshot equals `P@S0`;
- child tool catalog is the requested bounded read-only subset;
- child does not see unrelated parent-only secret/transient model data;
- child operations are durably associated with child `BranchId`;
- child can inspect project semantic references returned by its own tools;
- cancellation/failure does not mutate parent/project state.

Reuse existing branch isolation mechanisms instead of adding self-hosting-specific branch storage.

---

## Architecture `BranchResult`

On successful completion, the child produces a durable compact result equivalent to:

```text
purpose
base project P
base snapshot S0
conclusion = use shared code-domain language adapter pattern
required integration areas = [...]
important semantic/source refs = [...]
notable constraints = [...]
outcome = success
```

The important references should remain addressable by the parent without converting them into bare unscoped file paths.

The result may contain source-relative paths for human readability, but where semantic handles exist they should be included.

---

## Parent Continuation Must Use Result, Not Full Transcript

After child completion, compile the next parent model context from:

```text
parent's prior context
child BranchResult
relevant stable refs
new user/task state
```

Do not automatically append every child model request, response, tool invocation, and tool result into the parent's active transcript.

Those details remain retrievable through session/branch inspection if the parent explicitly needs them.

Add an assertion/captured provider request proving bounded result inheritance.

---

## Staleness Rules

The discovery result is bound to `S0`.

If the project current snapshot advances before the parent uses the result to construct a change, the parent must not treat old source mappings/revisions as silently current.

Later code-edit operations must re-resolve important targets against the intended exact base.

The branch result may remain useful historical evidence, but its exact base remains visible.

Do not rewrite stored branch result references to a newer snapshot.

---

## TUI Session Behavior

After task `123` onboarding, the user can submit a second agent instruction in the same session without manually selecting a project again.

The TUI/session view should make it possible to inspect:

```text
active project P
snapshot S0
parent branch
nested discovery branch
branch status/result
```

The TUI does not need to render every child token stream inline by default.

A compact nested activity/result presentation is preferred, with explicit navigation into child detail when requested.

---

## Semantic-First Regression Rule

The golden provider trace for this task must demonstrate that after onboarding it uses semantic operations to locate repository guidance/architecture.

An implementation fails the golden intent if the provider is handed a universal unrestricted `grep/read/write filesystem` tool and solves all discovery outside Scriberig semantic state while `P@S0` is ignored.

This does not ban all filesystem capabilities in Scriberig. It makes the semantic project useful and primary for this scenario.

## Deterministic Provider Behavior

Extend the existing scripted provider configuration, not production prompt branching.

For this test world, after receiving the second instruction it should:

1. observe exact `P@S0` context;
2. request capability discovery as needed;
3. find/render project guidance semantically;
4. start the read-only child branch through normal branch tool/operation if that is provider-visible, or follow existing orchestrator policy that creates it from provider request;
5. child finds/inspects/render relevant architecture objects;
6. child returns compact architecture result;
7. parent produces a concise terminal response or proceeds to the next scripted stage in later tasks.

Capture trace evidence for exact scope and catalog.

No external model service is required.
