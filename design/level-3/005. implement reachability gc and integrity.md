# Implement: Reachability, Garbage Collection, and Integrity

## Objective

Implement storage maintenance features required by the Level 1 persistence model without changing canonical semantics.

This task adds backend-neutral reachability and integrity reporting plus SQLite garbage-collection support.

## Read first

Read:

1. `design/level-1/004. persistence and storage model.md`
2. `design/level-2/005. indexes reachability gc and integrity.md`
3. Level 3 tasks 001 through 004.

## Reachability API

Define backend-neutral types for:

- protected roots;
- reachable canonical object enumeration;
- unreachable candidate reporting.

Reachability must begin from an explicit stable set of protected roots/snapshots.

Traversal must retain every immutable storage object required to read a protected snapshot completely, including snapshot-map structure, revisions, and persistent collection/storage nodes.

Do not automatically retain rebuildable caches merely because they mention a protected object.

## Integrity report

Define a structured `IntegrityReport` or equivalent with machine-readable issues.

At minimum detect/report:

- revision ID does not match stored canonical content;
- referenced persistent node missing;
- invalid snapshot-map structure;
- named root points to missing/invalid snapshot;
- protected snapshot cannot be read completely;
- persistent collection invariant violation;
- derived/backend index points to missing authoritative data;
- unreachable but otherwise valid immutable object.

Keep `unreachable` separate from `corrupt`.

## Index rebuild

Implement rebuilding of any backend-derived indexes introduced so far.

A rebuild must derive results from authoritative persisted data and must not modify canonical revision bytes or snapshot meaning.

## Garbage collection

Implement conservative mark-and-sweep for SQLite.

Required API behavior:

```text
gc_dry_run(protected_roots) -> report
gc_sweep(protected_roots) -> report
```

Rules:

- capture a stable protected-root set before marking;
- dry run deletes nothing;
- sweep deletes only objects proven unreachable under the captured root set and retention policy supported so far;
- sweep must not make any protected snapshot unreadable;
- when uncertain, retain rather than delete.

The first implementation does not need concurrent online GC. It may require exclusive/serialized maintenance access if documented internally.

## Integrity repair policy

Safe automatic repair is limited to rebuildable derived indexes.

Do not silently rewrite or synthesize canonical revisions to repair corruption.

## Tests

Create tests for:

- reachability from one root marks all required canonical storage;
- two protected roots preserve the union of their reachable state;
- abandoned branch becomes a GC candidate only after no protected root reaches it;
- dry run reports candidates and deletes nothing;
- sweep removes an unreachable candidate;
- sweep preserves all data required by protected snapshots;
- altered stored canonical revision bytes are reported as corruption;
- missing snapshot-map node is corruption;
- unreachable valid record is not categorized as corrupt;
- derived index can be deleted and rebuilt without changing canonical IDs.

After destructive GC tests, run integrity verification against every protected snapshot.

## Commands to run

```text
cargo fmt --check
cargo test --workspace
```

## Do not do

- Do not add retention policy UI or CLI.
- Do not implement distributed GC.
- Do not compact or rewrite canonical identities.
- Do not automatically repair canonical corruption.
- Do not make GC dependent on an agent runtime.

## Completion checklist

- [ ] Reachability API exists.
- [ ] Structured integrity report exists.
- [ ] SQLite dry-run GC works.
- [ ] SQLite sweep preserves protected snapshots.
- [ ] Derived index rebuild works.
- [ ] Corruption and unreachability are distinguished.
- [ ] Memory and SQLite behavior remain consistent where public APIs overlap.
- [ ] Workspace tests pass.

Stop after these conditions are met.
