# Implement Validation Evidence and Exact Input Binding

## Objective

Represent validation as structured, provenance-bearing knowledge bound to exact immutable inputs. A validator produces evidence; it does not grant permission or promote a candidate.

## Read First

1. `design/level-1/013. trust validation capabilities and provenance.md`, especially sections 16–18, 32–35 and 64.
2. `design/level-1/008. derived knowledge caching and incrementality.md`.
3. `design/level-1/005. changes migrations branches and merge.md`.
4. `design/level-3/001. extend shared core with knowledge values and provenance.md`.
5. Existing schema/graph/application designs and implementations.

If exact revision/snapshot references or graph/schema persistence are not implemented yet, stop and report the missing prerequisite.

## Expected Area

Use the existing schema/graph mechanisms to persist validation results as knowledge objects, and the application layer to orchestrate validators.

Likely modules:

```text
crates/scriberig-app/src/validation.rs
crates/scriberig-schema/... validation schema registration if required
crates/scriberig-app/src/lib.rs
```

Do not invent a separate database table that bypasses the universal graph unless an existing lower-level design explicitly requires one.

## Validation Result Model

Represent at least:

```text
validator identity
validator version/profile/configuration
subject entity/revision or candidate snapshot
explicit dependency set
status
structured diagnostics
produced artifact references
provenance
```

Status must distinguish at least:

```text
Passed
Failed
Error
Skipped
Unknown
```

Do not reduce all results to a boolean.

## Exact Input Binding

A validation result must identify the exact candidate snapshot or exact immutable dependency revisions it checked.

Provide one reusable function that decides whether prior evidence is applicable to a later candidate. It may reuse evidence only when its declared dependencies are still identical. If dependency information is incomplete, return not-applicable conservatively.

Never infer that validation for snapshot A applies to snapshot B merely because their rendered files look similar.

## Validator Interface

Define an application-facing validator trait/interface using the conventions already present in the repository. It should receive an explicit candidate/context and return structured validation evidence.

Validators must not directly promote candidates.

A validator may be deterministic or interpretive, but its provenance/configuration must make the distinction inspectable where known.

## Diagnostics

Keep diagnostics structured enough for CLI, protocol, web, and agents to consume the same evidence. At minimum support severity/category, message, optional subject reference, and optional source coordinates.

Do not require every validator to produce source coordinates.

## Tests

Add tests proving:

1. a passing result is bound to the exact candidate;
2. a candidate revision change invalidates evidence when that revision is a dependency;
3. unrelated snapshot changes do not invalidate evidence when all declared dependencies are unchanged;
4. unknown dependency coverage causes conservative non-reuse;
5. failed validation remains stored/inspectable;
6. validator error is distinct from validation failure;
7. two validator configurations produce distinguishable evidence;
8. structured diagnostics survive persistence/round-trip;
9. validation does not mutate canonical roots;
10. validation does not imply a capability to promote.

## Validation

Run workspace format/check/tests/lint. Include at least one application-level test using an in-memory or test store if the repository provides one.

## Do Not

Do not implement project promotion policy here. Do not hard-code Rust compiler commands or Markdown validators into the universal interface. Do not attach a mutable `validated=true` field to snapshots. Do not erase failed evidence.

## Completion Checklist

- [ ] validation is structured knowledge;
- [ ] exact inputs/configuration are recorded;
- [ ] reuse is dependency-based and conservative;
- [ ] failed/error results remain inspectable;
- [ ] validators cannot promote candidates;
- [ ] protocol/UI-specific rendering is deferred.
