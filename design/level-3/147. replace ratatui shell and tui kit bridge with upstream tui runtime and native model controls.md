## 5. Remove the Double-Rendering Bridge

The current path that uses upstream components internally and then strips/reconstructs their output through Ratatui must be removed from the normal product path.

Forbidden final pattern:

```text
rpi-tui component.render()
  -> strip ANSI / flatten lines
  -> Ratatui Text/Paragraph/Block
```

Required final pattern:

```text
Scriberig semantic component
  + upstream components
  -> upstream TUI child/overlay composition
  -> upstream render/runtime
```

Acceptance:

- [ ] Composer renders directly as an upstream component.
- [ ] Markdown/message rendering remains upstream-rendered through the final terminal path.
- [ ] Selection/list components render directly through upstream.
- [ ] Upstream theme/style output is not flattened and recreated in Ratatui.
- [ ] No normal render frame is built with Ratatui widgets.

---

## 6. Move the Composer to the Upstream Product Path

Use the upstream editor/composer directly as the active input component.

Preserve Scriberig submission semantics:

```text
ordinary prompt -> shared Scriberig branch operation
recognized slash command -> local/upstream command dispatch
historical reply target -> stable Scriberig ContinuationAnchor
multiline draft -> local UI state until submit
```

Acceptance:

- [ ] Startup composer is an upstream component.
- [ ] Cursor/IME/Unicode behavior comes from upstream.
- [ ] Paste goes through upstream terminal/editor behavior and Scriberig safety policy.
- [ ] Scriberig stable reply anchor remains independent of editor cursor/focus.
- [ ] Submission does not bypass shared Scriberig application operations.

---

## 7. Use Upstream Provider/Model/Thinking Controls

Provider/model/thinking selection must use upstream product/UI machinery rather than Scriberig selectors built from upstream data.

If selectors currently live only inside `rpi-cli`, consume the extracted reusable upstream components produced by the contribution gate from tasks 144/145.

Acceptance:

- [ ] Model selector is upstream UI.
- [ ] Provider selector is upstream UI where product-exposed.
- [ ] Thinking selector is upstream UI and shows levels from upstream selected-model metadata.
- [ ] Model switch updates thinking options using upstream behavior.
- [ ] Provider authentication/readiness is rendered from upstream state.
- [ ] No Scriberig-local model selector/picker remains on the normal terminal path.

## 12. Keep Scriberig State Machine Only Where It Owns Product Semantics

The current event/action/reducer/effect architecture may retain semantic product state if useful, but it must no longer duplicate upstream terminal state.

Candidates to remain Scriberig-owned:

```text
current semantic selection
current branch/reply anchor
plan coordinator cursor
expanded semantic branch IDs
candidate review state
operation correlation
presentation preferences tied to Scriberig activity
```

Candidates to delegate/remove:

```text
terminal focus engine
editor cursor state outside upstream component
raw terminal event parsing
resize mechanics
widget selection internals
overlay stack mechanics
terminal theme internals
```

Acceptance:

- [ ] Remaining Scriberig reducer state is semantic/product state, not a duplicate terminal engine.
- [ ] Upstream input/focus/component events are translated only where a Scriberig intent is produced.
