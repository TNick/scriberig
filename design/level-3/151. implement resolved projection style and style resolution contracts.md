# Implement Resolved Projection Style and Style Resolution Contracts

## Status

Planned.

All completion items remain unchecked until implemented and verified.

## 1. Goal

Implement the generic and shared-application foundation from:

- `level-1/024. projection styles personalized representations and materialization policy.md`;
- `level-2/034. projection style resolution loss-aware reconciliation and cross-surface contracts.md`.

This task establishes exact renderer-consumable resolved styles, domain style-schema/discovery seams, purpose-aware style resolution, provenance, and exact-style fidelity queries.

It does **not** implement the full Rust/ECMAScript renderers or TUI/web controls. Those belong to tasks 152 and 153.

## 3. Architectural Constraints

Preserve these invariants:

```text
canonical semantic code != source projection bytes

StyleRef = exact identity/provenance boundary
ResolvedStyle = exact renderer-consumable value

domain adapter owns style meaning
shared application layer owns selection/resolution semantics
product surfaces do not own formatting rules

InteractiveView resolution != SharedMaterialization resolution

style change alone != semantic source migration
```

Do not:

- make `sr-projection` know TypeScript/Rust style properties;
- let renderers read ambient user settings;
- create a TUI-only style store/resolver;
- use terminal theme types as source projection styles;
- make filesystem/project source bytes canonical;
- bypass candidate/migration/change semantics for project configuration that is canonical knowledge.

## 5. Add an Exact `ResolvedStyle` Contract

Add a generic domain-neutral type equivalent in responsibility to:

```rust
ResolvedStyle {
    reference: StyleRef,
    value: StyleValue,
    schema: Option<StyleSchemaRef>,
}
```

Exact names/field arrangement may change to fit the existing public API.

Requirements:

- preserves exact `StyleRef` provenance;
- carries exact canonical adapter-owned style bytes;
- can identify the schema/version when required for validation;
- is immutable after construction;
- participates in equality/hash/cache identity as required;
- supports deterministic construction for inline style values;
- does not depend on any domain crate;
- does not contain mutable application/user-setting handles.

If resolving a revision reference requires storage/application access, perform that resolution before the domain renderer is invoked.

Do not give projection renderers hidden store access merely to resolve style preferences.

---

## 6. Refine Render Identity

Update the render contract so the exact canonical resolved style consumed by a renderer is part of the declared render input.

A compatibility transition is acceptable, but the resulting API must make it impossible for a migrated renderer to receive a `StyleRef::Revision` while lacking the exact value it is supposed to apply.

Ensure render/cache identity changes when the canonical resolved style value changes.

Detect inconsistent reference/value pairs where the current storage/identity model makes such validation possible.

Keep renderer version and rendering context separate from style.

---

## 7. Add Domain Style-Schema Seams

Add or refine a narrow extension seam through which a domain projection adapter can describe and validate style.

It must support responsibility equivalent to:

```text
schema for projection kind
normalize style input
merge style values according to domain rules
provide exact defaults
classify fidelity for exact resolved style/purpose
```

Do not require one universal schema property enum across all domains.

Generic schema descriptors may include stable keys/value kinds/allowed values/defaults/documentation/purpose applicability, but domain code remains authoritative for validation and interpretation.

Use structured diagnostics for invalid/unsupported properties.

---

## 8. Add Projection Purpose and Fidelity

Introduce shared domain-neutral types equivalent to:

```text
ProjectionPurpose
  InteractiveView
  SharedMaterialization
  ExplicitExport

ProjectionFidelity
  LosslessEditable
  LossAwareEditable
  ReadOnlyLossy
```

Names may vary, but callers must be able to distinguish these cases without inferring them from style bytes.

Fidelity is evaluated for the exact resolved style/projection/purpose, not only for the projection kind.

Do not make `Editable` on a generic projection specification override an adapter's determination that one resolved style is too lossy to edit safely.

---

## 9. Implement Shared Purpose-Aware Resolution

Place style selection/resolution in the current shared application/configuration owner after inspecting existing code.

Implement deterministic source resolution equivalent to:

### Interactive view

```text
DomainDefault
< RepositoryConvention / ProjectPolicy
< UserPreference
< ViewOverride
```

### Shared materialization

```text
DomainDefault
< RepositoryConvention / ProjectPolicy
< WorkspaceMaterializationPolicy
```

`UserPreference` must not enter shared materialization by default.

### Explicit export

Require explicit selection of any personal/view override used for the export; do not borrow it from ambient UI state invisibly.

Use domain-defined merge/normalization rather than generic last-write-wins JSON merging.

---

## 10. Preserve Style Provenance

Return enough provenance from resolution to explain effective choices.

At minimum preserve ordered exact source identities/revisions/values used to derive the result.

Per-property winning-source provenance may be added if it fits cleanly and deterministically.

Do not include secrets or unrelated user configuration.

Provenance is inspectable derived/configuration evidence, not semantic source-code content.

---

## 11. Add Shared Application Operations

Extend current application capability/operation owners with operations equivalent in responsibility to:

```text
query style schema
query available profiles
query effective style + provenance
query exact fidelity/editability
set/clear user preference
set/clear view override
set materialization policy
```

Follow existing operation/capability naming and result conventions rather than introducing a parallel API family solely because the Level-2 document uses conceptual names.

Ensure local embedded callers can use the same semantics later exposed remotely.

A view override is presentation/user configuration and must not create a source-code migration.

---

## 12. Repository Convention Boundary

This task only establishes a pluggable source/provenance boundary for repository/project conventions.

Do not attempt to fully implement every `.editorconfig`, rustfmt, Prettier, or Biome option in this task.

If an existing configuration reader already owns relevant behavior, adapt it into the shared resolver rather than duplicating parsing.

Use deterministic fixtures for at least one synthetic repository-convention source so precedence can be tested.

---

## 13. Compatibility Strategy

Migrate incrementally.

Existing adapters that do not yet expose a style schema may resolve to one fixed canonical default style and conservative fidelity.

Do not break unrelated Markdown/filesystem projection workflows merely to force all adapters to implement rich style discovery immediately.

Task 152 will migrate Rust and ECMAScript source rendering to the new contract.

## 14. Tests

Add tests at the lowest layer that owns each behavior.

### Generic projection tests

Prove:

- resolved style retains reference and exact value;
- different canonical style values produce different render/cache identity;
- deterministic repeated style resolution produces equal exact values;
- projection fidelity variants remain distinguishable;
- no domain-specific property names leak into generic projection tests/types.

### Application resolution tests

Prove:

- interactive view includes user preference;
- shared materialization excludes user preference;
- explicit view override wins only in the intended view scope;
- two users may resolve different interactive styles for the same semantic scope;
- those users resolve the same shared materialization style under one workspace policy;
- invalid domain merge produces a structured diagnostic;
- effective provenance identifies applied sources.

### Regression test

Add a test demonstrating that changing a user preference does not create or request a semantic source-code migration.
