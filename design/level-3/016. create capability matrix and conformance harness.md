# Create Capability Matrix and Conformance Harness

## Objective

Create the concrete planning and test artifacts prescribed by:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`
2. `design/level-2/012. capability matrix and cross surface conformance.md`

This task creates the repository-visible capability matrix and a dedicated non-published conformance crate.

The harness must verify semantic equivalence across public boundaries without depending on external services.

---

## Prerequisites

The following should already exist or be in progress:

- `scriberig-app` operation primitives;
- `scriberig-protocol` contract;
- `scriberig-server` and `scriberig-client` in-process transport path;
- CLI and agent inspect adapters.

If some surfaces are not implemented yet, record them truthfully as `planned`. Do not create fake implementations just to make the matrix green.

---

## Files to Create

Create:

```text
capabilities.toml

crates/scriberig-conformance/Cargo.toml
crates/scriberig-conformance/src/lib.rs
crates/scriberig-conformance/tests/inspect.rs
crates/scriberig-conformance/tests/protocol.rs
crates/scriberig-conformance/tests/operations.rs
crates/scriberig-conformance/tests/events.rs
```

Add `crates/scriberig-conformance` to the root Cargo workspace.

Set:

```toml
publish = false
```

Production crates must not depend on this crate.

---

## `capabilities.toml`

Create entries for exactly these initial capabilities:

```text
inspect_entity
runtime_capabilities
operation_status
operation_cancel
event_subscription
```

Each entry has:

```text
id
description
semantic_owner
surface status table
```

Use these surface keys exactly:

```text
library
app
protocol
server
client
cli
tui
web
agent
```

Use only these status values:

```text
not_applicable
planned
implemented
verified
```

Do not mark a surface `implemented` unless the corresponding code exists.

Do not mark a surface `verified` unless an appropriate test proves the semantic behavior.

At the end of this task `inspect_entity` should normally be the most complete entry. TUI and web may remain `planned`.

---

## Conformance Crate Dependencies

The conformance crate may use public APIs from runtime packages under test, including:

```text
scriberig-app
scriberig-protocol
scriberig-client
scriberig-server
scriberig-agent-core
```

It may also use foundational test fixtures needed to build a deterministic semantic world.

Do not depend on private module paths.

Do not make any production crate depend on `scriberig-conformance`.

---

## Deterministic Fixture

Implement fixture helpers in `src/lib.rs` or a small internal module.

The fixture must create:

- deterministic temporary/in-memory semantic storage using the supported test backend;
- one explicit snapshot;
- at least one inspectable entity with a known revision;
- an application instance bound to that state;
- a server dispatcher;
- an in-process client transport;
- an agent inspect adapter when available.

The fixture must not use:

- external HTTP;
- a model provider;
- user home-directory configuration;
- real project files outside the test temp area;
- current time as semantic identity unless explicitly controlled.

---

## `tests/inspect.rs`

Use the same fixture to invoke inspect through each implemented surface that exposes a callable public API.

At minimum compare:

```text
application inspect
server/client inspect
agent inspect adapter
```

If the CLI library exposes a structured dispatch path that can be called without scraping process output, include it as well.

Verify semantic equality of:

- entity ID;
- resolved revision ID;
- snapshot ID;
- semantic type/name/description fields supported by the current API;
- structured error category for a missing entity.

Do not require byte-identical presentation strings.

---

## `tests/protocol.rs`

Verify public contract stability basics:

- inspect request/response round trip;
- capability response round trip;
- structured error round trip;
- operation status round trip;
- representative event round trip;
- protocol major version metadata;
- schema exporter runs successfully if exposed as callable tooling or subprocess in tests.

Do not snapshot Rust `Debug` output as the wire contract.

---

## `tests/operations.rs`

Create a deterministic fake/test operation using the public application operation mechanism.

Verify:

- one stable operation ID is used throughout its lifecycle;
- legal status progression reaches a terminal state;
- terminal states do not regress;
- operation status survives server/client transport;
- cancellation produces a structured status/result when cancellation support is implemented;
- a disconnected observer is not required for the final result to exist.

If cancellation has not been implemented yet, keep the relevant capability `planned` and test only implemented lifecycle behavior.

---

## `tests/events.rs`

Using the public event path available at the time of implementation, verify:

- event subject IDs survive adapter/transport conversion;
- an event can be associated with the operation or entity that caused it;
- a consumer can resolve authoritative state through normal application/client queries after the event;
- the event payload is not treated as an independently mutable copy of canonical state.

If streaming transport has not yet been implemented, test the application/server event conversion boundary and leave `event_subscription` surfaces truthfully marked `planned` where necessary.

---

## Matrix Validation Test

Add a test/helper that parses the root `capabilities.toml` and rejects:

- duplicate capability IDs;
- unknown surface keys;
- unknown status values;
- missing semantic owner;
- empty descriptions.

Use a normal TOML parser already present in the workspace when possible.

Do not make `capabilities.toml` control runtime permissions or Cargo features.

---

## Updating Statuses

After all tests pass, update matrix statuses truthfully.

A useful rule:

```text
implemented = code path exists
verified = code path exists and the conformance harness exercises it
```

Do not use `verified` merely because a unit test exists in the implementation crate if the matrix is intended to claim cross-surface equivalence.

---

## Do Not Do

- Do not build a web UI.
- Do not build a TUI just for test coverage.
- Do not add a network dependency to the fixture.
- Do not weaken semantic assertions to make differing implementations pass.
- Do not make presentation formatting part of semantic equality.
- Do not use the capability matrix as authorization configuration.
- Do not add runtime business logic to the conformance crate.

---

## Required Checks

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-conformance
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

Also inspect `cargo tree -p scriberig-conformance` and verify no production crate has acquired a reverse dependency on the conformance crate.
