# Implement Geospatial Datasets, Spatial Query, and QGIS Project Integration

## Status

In Progress. A provider-neutral geospatial crate now models datasets, ordered
layers, schema, explicit CRS context, exact coordinate text, typed geometry,
feature attributes, bounded feature paging, and domain-level snapshot-scoped
attribute/envelope queries with arbitrary-width exact decimal comparisons that
reject CRS mismatches. A read-only GeoPackage adapter reads catalog metadata
without loading feature tables into the catalog, pages common WKB
point/line/polygon and collection geometry, and imports dataset/layer summaries
plus canonical Feature revisions in bounded source pages. Project
onboarding resolves project-relative QGIS references against that exact
persisted scan; missing references remain semantic entities with diagnostics.
Authorized application reads expose bounded GeoPackage layer catalogs and
feature pages from the exact source revision visible in a requested snapshot.
Rust and web protocol clients carry bounded typed catalog/feature pages with
host-injected Inspect grants. The shared application QueryService and Rust
protocol/client now expose bounded attribute and explicit-CRS envelope queries
with source revision, digest, CRS, and execution provenance.
Exact-base feature attribute edits now return shared candidate handles through
the protocol, HTTP operation mapping, server authorization boundary, and Rust
client; schema validation and staging remain owned by the project/domain layers.
QGS/QGZ inspection imports project CRS, layer order, group membership, and
visibility, while retaining the authored datasource as a typed reference.
Spatial query results now include feature summaries through the shared query
service, protocol/client, and RPI-TUI. Shared-query indexing, editing fidelity
and materialization, and broader product integration remain open.
Incomplete Shapefile groups now produce a structured missing-sidecar diagnostic
and `InspectOnly` fidelity; complete groups remain read-only until a safe
provider writer is connected to the verified shared compound materializer.

## 1. Goal

Implement geospatial dataset semantics, bounded spatial/attribute query, editable vector-layer operations, and a distinct QGIS project domain that references those datasets rather than absorbing them.

Minimum scenario:

```text
onboard QGIS project + parcels.gpkg
inspect QGIS project
resolve referenced parcels layer
find parcel_id=124
inspect feature
change area attribute or geometry semantically
create candidate
validate
review/apply
materialize dataset
reopen dataset
refresh QGIS project view/reference without rewriting unrelated project configuration
```

This task depends on task 155. It may use optional system/native geospatial libraries, but universal/public semantic contracts must remain provider-neutral.

## 4. Architectural Prohibitions

Do not:

- make QGIS project XML the canonical GIS dataset model;
- copy every feature from referenced datasets into the QGIS project entity;
- make GDAL/QGIS/native library types public protocol/domain types;
- make provider feature IDs equal Scriberig `EntityId`;
- use screen/map pixel coordinates as canonical geometry;
- serialize an entire large layer into one inspect/list response;
- mutate GeoPackage SQLite tables directly from agent/UI code as the normal semantic write path;
- treat Shapefile component files as unrelated independent artifacts when the adapter understands them as one dataset;
- require a remote network service for acceptance tests;
- bypass candidate/validation/materialization because a geospatial library has an update API.

Prefer a provider capable of GeoPackage/Shapefile read/write and spatial metadata. GDAL-compatible integration is expected when practical, but keep it adapter-private.
