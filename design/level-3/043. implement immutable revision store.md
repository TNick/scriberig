# Implement Immutable Revision Store

## Mission

Create the first `sr-store` crate and implement immutable canonical revision values plus an in-memory revision store.

This task proves content-addressed revision storage independently from snapshot logic.

Do not implement snapshots, roots, migrations, SQLite, or agents in this task.

## Revision Value

Implement a public immutable `Revision` value containing exactly the canonical fields needed by this stage:

```text
EncodingVersion
TypeId
canonical payload bytes
RevisionId
```

The `RevisionId` must be computed by `sr-core` revision hashing from:

```text
revision domain tag
encoding version
type ID
payload
```

Do not accept an arbitrary caller-provided `RevisionId` in the normal constructor.

The constructor must compute the ID itself.

The revision must not contain:

- [x] `EntityId`;
- [x] parent identity;
- [x] child position;
- [x] mutable root name;
- [x] current snapshot;
- [x] cache data;
- [x] derived summary data;
- [x] incidental timestamps.

Expose read-only accessors.

## Revision Store Trait

Define a small backend-independent trait with behavior equivalent to:

```text
put(revision) -> Result<RevisionId, StoreError>
get(id) -> Result<Option<Revision>, StoreError>
contains(id) -> Result<bool, StoreError>
```

The exact ownership form may use `Arc<Revision>` if useful, but do not expose internal map locks.

`put` must be idempotent.

Putting an already present exact revision returns the same `RevisionId` and does not create a logically distinct record.

## In-Memory Implementation

Implement `MemoryRevisionStore` using an internal map keyed by `RevisionId`.

It should be safe for ordinary concurrent callers if this can be achieved with a standard `RwLock` without complicating the public API.

Requirements:

- [x] exact existing value is reused;
- [x] missing ID returns `None`;
- [x] callers cannot mutate a stored revision through a returned handle;
- [x] a digest collision with different canonical bytes is treated as an integrity error, not as overwrite behavior.

The collision branch may be practically unreachable, but it must exist logically.

## Store Error

Create a compact typed error enum.

Include an integrity/collision case.

Do not use panic for normal store errors.

A poisoned synchronization primitive may be mapped into a store error if necessary.

## Tests

In `crates/sr-store/tests/revisions.rs`, add integration tests for:

- [x] creating a revision computes the same ID as the core hash helper;
- [x] same type/version/payload creates the same `RevisionId`;
- [x] different payload creates a different ID;
- [x] different `TypeId` creates a different ID;
- [x] `put` followed by `get` returns equal canonical fields;
- [x] putting the same revision twice is idempotent;
- [x] missing revision returns `None`;
- [x] `contains` changes from false to true after insertion;
- [x] the store exposes no mutable route that can change stored revision bytes in place.

If practical, include a unit test for the integrity mismatch branch using a test-only helper rather than weakening production APIs.

## Public API Rule

`sr-store` may depend on `sr-core`.

`sr-core` must not depend on `sr-store`.

No code in this task may depend on agents, server code, CLI code, domains, or projections.
