# Extend Shared Core with Knowledge Values and Provenance

## Objective

Extend the **existing** shared core crate with the domain-independent value and provenance types required by the universal knowledge model.

Do not bootstrap a new workspace and do not create a second core crate.

This task is intentionally narrow: it adds universal property values, canonical/derived classification, and provenance. Identity generation, content addressing, canonical encoding, revision hashing, and snapshot storage are owned by other designs.

---

## Read First

Read these documents before editing:

1. `design/level-1/002. universal knowledge model.md`
2. `design/level-2/001. universal knowledge model rust libraries.md`
3. the repository-wide workspace/package-layout Level 2 design;
4. the identity/revision/snapshot Level 2 design that owns `EntityId`, `RevisionId`, and `SnapshotId`.

Inspect the root Cargo workspace before editing.

Use the core crate already registered there. The workspace design may call it `scriberig-core`; earlier identity work may have used another provisional name. **Do not create another core crate to resolve a naming mismatch.** Extend the canonical crate that actually exists in the workspace.

If no shared core crate exists yet, this task's prerequisite has not been implemented. Do not invent a competing workspace; report the unmet prerequisite.

## Files to Create or Modify

Inside the established shared core crate:

```text
src/value.rs
src/provenance.rs
src/lib.rs
Cargo.toml            # only if a narrowly required dependency/feature is needed
```

If `value.rs` or `provenance.rs` already exists, extend it instead of creating a parallel module.

Do not modify identity-generation or canonical-encoding code unless a tiny public re-export is required to use the existing types.

---

## 1. Universal Property Value

Implement a public domain-neutral enum named `KnowledgeValue` or the equivalent name already chosen by the crate.

It must represent at least:

```text
Null
Bool
SignedInteger
UnsignedInteger
Float
String
Bytes
List
Record
```

### Semantics

- `List` preserves element order.
- `Record` uses string keys and should use deterministic iteration ordering where practical.
- The type represents local property payloads, not semantic graph edges.
- Do not add an `EntityRef` variant merely for convenience; semantic references belong in typed relations/collections.
- Do not add domain-specific variants such as `RustExpression`, `MarkdownParagraph`, `PdfPage`, or `SessionBranch`.

### Traits

Provide sensible traits such as:

```text
Clone
Debug
PartialEq
```

If floating-point values prevent honest total equality or hashing, do not invent misleading `Eq`/`Hash` semantics.

Provide only obvious small `From` conversions. Avoid a large conversion framework.

---

## 2. Canonical vs Derived Classification

Define one shared public classification enum, using a clear name such as `KnowledgeClass`:

```text
Canonical
Derived
```

This type only classifies how a field/artifact participates in semantic state.

It does not decide whether a particular domain value is canonical. Schemas make that decision.

---

## 3. Provenance Inputs

Use the existing identity types from the shared core crate.

Define an exact dependency/reference structure if the core does not already have one, conceptually:

```text
EntityRevisionRef {
    entity_id: EntityId,
    revision_id: RevisionId,
}
```

If another design already defines an equivalent exact reference type, reuse it.

Do not redefine `EntityId` or `RevisionId`.

---

## 4. Provenance Source

Define an extensible public source-kind representation capable of expressing at least:

```text
User
AuthoritativeImport
Parser
Compiler
StaticAnalysis
Agent
ModelGenerated
System
ExternalTool
Migration
Custom(String)
```

The exact enum/type name may follow existing project naming.

The custom case is important so introducing a new producer category does not always require changing the core crate.

Provenance source records **origin**, not trust level.

Do not add trust scores, authorization decisions, or policy evaluation here.

---

## 5. Provenance Record

Implement a `Provenance` record containing enough data to answer:

- what kind of source produced this knowledge?
- what producer/tool/model produced it, if known?
- which exact immutable entity revisions were inputs, if known?
- which profile/configuration produced it, if relevant?
- is there a short explanatory note?

Required conceptual fields:

```text
source
producer              optional
inputs                zero or more exact entity/revision refs
profile/config        optional
note                  optional
```

Use an existing shared producer/profile identifier type if one already exists. Otherwise use a narrowly scoped string/newtype without inventing persistence semantics.

Do not include timestamps merely because provenance often has timestamps. Timestamps are not required by the Level 1 semantic model and may be added later by a history/audit design.

---

## 6. Public Exports

Update the shared core `lib.rs` so downstream schema/graph crates can import the new types from a stable public path.

Expose at least the equivalents of:

```text
KnowledgeValue
KnowledgeClass
Provenance
ProvenanceSource
EntityRevisionRef      if newly defined here
```

Do not disturb existing public exports from identity/storage work.

---

## 7. Unit Tests

Add focused tests for:

1. nested `List` values;
2. nested `Record` values;
3. list order preservation;
4. deterministic record behavior where promised by the implementation;
5. canonical vs derived classification;
6. provenance with no inputs;
7. provenance with multiple exact revision inputs;
8. a custom provenance source;
9. proof that semantic entity references are represented by provenance/reference types rather than encoded as arbitrary property-value variants.

Do not add database-backed tests.

---

## 8. Documentation

Public docs must state:

- property values are domain-neutral payloads;
- semantic relationships are not encoded as arbitrary values;
- provenance records origin and exact dependencies where available;
- provenance does not imply trust;
- canonical/derived classification is shared vocabulary, while schemas decide actual domain meaning.

Keep documentation concise and API-focused.
