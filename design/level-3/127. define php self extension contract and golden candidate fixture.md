# Define PHP Self-Extension Contract and Golden Candidate Fixture

## Objective

Create the checked-in reference/test material that defines exactly what the self-hosting agent must add for first-class PHP ingestion, while preserving a production baseline that does **not** already register PHP as a first-class adapter.

This task translates `design/level-2/028. php code domain source adapter target.md` into executable fixtures, expected candidate structure, and candidate-workspace validation assertions.

It must not satisfy the golden prompt in advance by wiring PHP into normal production scan/import dispatch.

Required baseline invariant after this task:

```text
normal baseline Scriberig runtime:
  .php -> current generic/unsupported policy

golden candidate fixture/spec:
  describes/builds proposed .php -> PHP adapter implementation
```

Task `128` will make the deterministic self-hosting provider construct this candidate through normal agent/change tools.

## Complete Syntax Fixture Expectations

Provide representative valid PHP source containing at least:

```php
<?php

namespace App;

class Greeter
{
    public function greet(string $name): string
    {
        // greeting comment
        return "Hello, " . $name;
    }
}

function helper(int $value): int
{
    return $value + 1;
}
```

Also provide a mixed inline-HTML/PHP fixture.

Golden domain assertions must prove complete/nested syntax retention rather than only detecting declaration names.

Use normalized deterministic assertions suitable for Tree-sitter version behavior; do not make tests depend on unstable debug formatting when a structured tree model exists.

## Expected Candidate Assertions

Add helper/test code able to validate a produced candidate structurally before running expensive validation.

At minimum assert:

- required create/update effects exist;
- no unexpected direct DB/TUI/web implementation path was added solely for PHP;
- scanner and importer refer to the same PHP adapter identity;
- workspace/dependency integration exists;
- candidate includes required PHP tests;
- candidate base is exact expected project snapshot;
- live baseline still lacks the proposed created files/first-class registration before Apply.

Do not require byte-for-byte equality to one fixture implementation if multiple correct implementations satisfy the semantic contract, unless deterministic provider golden tests intentionally use one exact fixture. Separate semantic acceptance from scripted fixture exactness.

---

## Two Layers of Test Data

Keep these concepts distinct:

### Scripted-provider fixture

May contain exact source texts/edits used by the deterministic provider to exercise the normal tool loop reproducibly.

### Product acceptance assertions

Must verify semantic behavior of the resulting candidate/build, not merely equality to the scripted texts.

This prevents the final gate from becoming a tautology where a stored patch is copied and considered successful without running PHP ingestion.

## Baseline Guard Test

Add a focused test that runs against the normal repository baseline **before applying the golden candidate** and proves first-class PHP ingestion is absent.

The exact assertion should match current policy, for example:

```text
scan fixture with example.php
adapter != php / currently generic text
```

The purpose is not to freeze generic text forever; it protects the meaning of this specific self-hosting milestone.

If this guard starts failing because production gains PHP for another reason, do not simply delete it and leave the golden prompt unchanged. Revisit the golden absent-format choice/design.
