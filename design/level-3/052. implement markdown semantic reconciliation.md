# Implement Markdown Semantic Reconciliation

## Objective

Implement the Markdown-specific reconciliation logic required to interpret an externally edited Markdown projection as semantic changes against an existing canonical Markdown state.

This task does not own file watching, snapshot storage, or generic three-way merge orchestration. It implements the domain-specific comparison and identity-matching step that `scriberig-projection` can invoke.

## Inputs and Output

The reconciliation layer must be able to accept conceptually:

```text
base semantic Markdown state
newly parsed candidate Markdown state
```

and produce:

```text
semantic change proposal / migration operations
plus ambiguity/conflict information
```

Use existing shared migration types where available. Do not invent a Markdown-only history format.

The adapter must not write directly to persistence.

---

## Identity Matching Strategy

Implement deterministic matching before any model-assisted behavior exists.

Use domain evidence in this order where practical:

1. exact semantic subtree equality;
2. exact canonical content equality;
3. same structural role under an already matched parent;
4. sibling sequence alignment;
5. heading/title identity for sections when sufficiently distinctive;
6. text/content similarity for paragraphs and simple blocks;
7. structural similarity for lists and tables.

The implementation may use a simpler subset initially, but exact equality, parent context, sibling order, and heading/paragraph similarity must be covered.

Never use source byte offsets as the primary identity signal.

---

## Required Change Classes

Support at least:

```text
unchanged entity reuse
content revision of an existing paragraph
heading/section title revision
block insertion
block deletion
block reordering
section insertion
section deletion
list-item insertion/deletion/reordering
table-row insertion/deletion/change
cell content change
```

Where the shared migration model has generic operations, map Markdown changes onto those operations rather than creating a parallel history mechanism.

---

## Ambiguity Rules

False continuity is worse than creating a new entity.

When two or more old entities are equally plausible predecessors for one candidate entity, return explicit ambiguity instead of silently choosing one.

Examples include:

- duplicate paragraphs reordered around each other;
- repeated identical headings under similar parents;
- repeated table rows with no stable distinguishing content.

The result must allow the caller to decide whether to create new entities, request manual resolution, or use a later assisted reconciliation layer.

Do not call an LLM in this task.

---

## Semantic vs Formatting-Only Changes

Formatting-only edits classified as projection-only by the Markdown schema must not produce semantic revisions.

Examples include changes only to:

```text
line wrapping
blank-line count
non-semantic indentation
table padding/alignment spacing
```

Add explicit tests proving these do not generate semantic changes for supported syntax.

---

## Migration Construction

The reconciliation result must preserve the universal change model.

For example, changing:

```markdown
A

B
```

to:

```markdown
A changed

C

B
```

must be representable as:

```text
revise existing A entity
create/insert C entity
reuse B entity
```

not as "replace entire document blob."

Unchanged entities must be reusable by identity.

## Tests

Cover at least:

1. unchanged document -> no semantic operations;
2. paragraph edit -> existing entity receives a new semantic revision/change;
3. inserted paragraph -> one new entity plus collection change;
4. moved unchanged paragraph -> reuse entity plus order change;
5. renamed heading -> section continuity when unambiguous;
6. inserted nested section;
7. table row edit with unchanged surrounding rows reused;
8. formatting-only edit -> no semantic change;
9. duplicate/ambiguous content -> explicit ambiguity;
10. large unchanged sibling region -> unchanged identities reused.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-markdown
cargo clippy -p scriberig-domain-markdown --all-targets -- -D warnings
```

---

## Do Not Do

- Do not watch files.
- Do not commit snapshots directly.
- Do not create Markdown-specific migration tables.
- Do not treat every edited file as a replacement document.
- Do not use line numbers or byte offsets as semantic identity.
- Do not silently resolve ambiguous identity matches.
- Do not call an agent/model.
- Do not implement generic merge logic owned by `scriberig-migration` or `scriberig-projection`.
