# Deliver Native TUI Agent Self-Extension Workflow for PHP Ingestion

## Objective

Compose tasks `123` through `128` into the exact native-TUI two-command workflow that the user will experience:

```text
fresh DB, no project
> Onboard the current project.

active Scriberig project P@S0
> Add support for ingesting PHP source files.

validated normal project-wide candidate C1
-> Review candidate
-> user Apply
-> authoritative P@S1
```

This task owns the product integration and real-PTY interaction for the workflow. It must not add a TUI-only onboarding, patching, validation, or filesystem-write implementation.

Task `130` turns this flow into the final strict product gate.

## Golden Launch

The primary focused PTY scenario launches the real built executable from a temporary copy of the Scriberig repository:

```text
cd <temp-scriberig-copy>
srig tui --db <fresh-db>
```

Do not pass:

```text
--project
--import
precomputed ProjectId
precomputed EntityId
```

The test must begin with no active project and prove the agent can bootstrap it.

Use the deterministic self-hosting provider configuration from task `128` through normal provider selection/runtime configuration.

---

## Initial TUI State

The TUI must clearly support agent input before a project is active.

Required observable state is equivalent to:

```text
Agent
No active project
> _
```

Exact layout/copy may follow current native UI conventions.

Do not block the entire agent/session surface behind `ActiveProjectWorkspace::Some`.

Project-specific semantic/editor actions may remain disabled until onboarding completes.

## First Command Interaction

The PTY/user types exactly:

```text
Onboard the current project.
```

The TUI starts the shared agent application operation and observes normal status/events.

Useful progress may include summaries such as:

```text
scanning project
reviewing manifest
importing project
resolving workspace
semantic verification
```

These are display states derived from operation/tool activity. The TUI must not duplicate the business logic.

---

## Onboarding Completion UX

After successful deterministic agent onboarding, the TUI must visibly transition to an active workspace containing at least:

```text
project display name = scriberig or fixture name
non-empty current snapshot representation
semantic/project navigation enabled
```

The session/agent result remains inspectable.

The user should not need to restart or manually open/import the project again.

If onboarding fails, the UI remains without a fake successful active project and shows inspectable structured failure.

---

## Second Command Interaction

Without restarting the TUI, the user types exactly:

```text
Add support for ingesting PHP source files.
```

The operation continues from exact active `P@S0` through the deterministic provider scenario from task `128`.

The TUI may show nested branch/operation activity, but does not need to stream every child branch token inline.

At minimum the user can tell that work is proceeding and later inspect the relevant child results.

---

## Nested Branch Presentation

Represent architecture discovery and implementation branches through existing session/operation UI concepts.

Required observable semantics:

```text
parent PHP request
  child: architecture discovery -> completed result
  child: implementation/validation -> completed result containing candidate
```

The user should be able to inspect branch status/purpose and resulting candidate references.

Do not flatten child transcripts into an enormous single terminal log as the only usable representation.

Do not invent a second TUI-only branch tree that is not backed by durable session/branch records.

---

## Candidate Result Action

When the root agent operation finishes successfully, its normal durable result exposes `CandidateId C1`.

The TUI presents an action equivalent to:

```text
Review candidate
```

Activating it navigates to the existing/shared migration/change review using `C1`.

Do not render a fake diff from assistant text.

---

## Project-Wide Candidate Review UX

The review view must handle the multi-file candidate from task `125`.

Required visible data includes:

```text
candidate id/reference
base snapshot S0
validation status
stale/conflict status
changed paths with effect kind
```

The user can navigate representative paths such as:

```text
new PHP domain Cargo.toml
new PHP domain src/lib.rs
workspace Cargo.toml
project scanner/import source
PHP tests/fixtures
Cargo.lock when changed
```

For selected path, show old/new or unified source diff appropriate to create/update/delete.

Large diffs may be paginated/scrollable.

---

## Validation UX

The deterministic provider will normally already have run required validation before returning `C1`.

The TUI review must display authoritative validation evidence/status, not infer success from agent prose.

At minimum show the equivalent of:

```text
PHP domain focused      passed
project import focused  passed
Rust workspace          passed
PHP ingestion E2E       passed
```

Exact labels may reflect profile registry names.

The user can inspect bounded failure diagnostics in negative tests.

Apply remains unavailable when required validation failed/stale according to shared policy.

---

## Pre-Acceptance Live-Tree Proof

Before invoking Apply, the real PTY harness must inspect the temporary Scriberig checkout externally and prove:

- candidate-created PHP domain production path is absent live;
- expected updated source/config files still match baseline bytes;
- current project snapshot remains `S0` through public state;
- candidate `C1` remains separately inspectable.

This assertion is mandatory. It catches agent/TUI implementations that secretly wrote source before review.

---

## User Apply Interaction

The PTY/user invokes the normal review Apply action.

The TUI calls the shared application apply operation with exact candidate/base context and observes terminal result.

Do not run `git apply`, write files, update SQLite, or construct successor IDs in terminal UI code.

---

## Apply Progress and Result UX

During Apply, product may show states such as:

```text
checking candidate base
checking filesystem preconditions
promoting canonical state
materializing source effects
refreshing workspace
```

On full success, the TUI displays enough authoritative result to establish:

```text
new current snapshot S1
S1 != S0
required external materialization succeeded
```

If canonical/materialization states diverge, display explicit recovery/effect failure rather than generic success.

---

## Post-Apply Source Verification

After full success, external PTY harness verifies intended candidate-created/updated files now exist on disk.

The TUI refreshes project workspace through shared application/client state and can open history/diff showing the transition.

Stable semantic selections may be re-resolved to `S1` according to existing workspace rules; stale `S0` cached content must not be presented as current.

---

## History UX

Normal TUI History/Diff should make the accepted self-hosted change discoverable.

The user can inspect:

```text
base S0
candidate/migration C1
successor S1
changed project paths
provenance/session when available
```

Historical source from `S0` remains renderable according to existing history/projection design.

---

## Restart Persistence

The focused PTY flow exits cleanly and restarts:

```text
srig tui --db <same-db>
```

against the same temporary checkout.

The product must recover/open existing project state according to current active-project/session policy and prove:

```text
P current = S1
accepted change/history persists
session/branch/candidate/validation references are inspectable
materialized source remains present
```

If active workspace selection itself is intentionally session-local, the test may explicitly reopen the existing project through normal UI; it must not re-import it as a new unrelated project.

---

## Negative TUI Scenario — Validation Failure

Use deterministic provider failure variation from task `128` or a controlled invalid candidate.

Required outcome:

- normal review shows validation failure/diagnostic;
- Apply unavailable or shared operation rejects clearly;
- `P.current` remains `S0`;
- live checkout remains baseline;
- TUI never reports full PHP support/materialization success.

---

## Negative TUI Scenario — External Conflict

After validated `C1` exists but before Apply, externally modify one intended update target in the temporary Scriberig checkout.

Then invoke Apply.

Required outcome:

- shared precondition detects conflict;
- TUI displays stale/conflict/reconciliation-required state;
- external marker/content remains on disk;
- candidate does not silently overwrite it;
- UI does not claim full successful materialization;
- canonical/effect state is shown truthfully according to task `126` ordering.

---

## Negative TUI Scenario — Create Conflict

Before Apply, externally create one path that `C1` expects to create, such as the candidate PHP crate path/file.

Required outcome:

- explicit create-target conflict;
- external file remains;
- no silent replacement;
- no misleading full success.

---

## Cancellation

Test cancelling:

- initial onboarding agent operation;
- architecture discovery child;
- implementation branch before candidate completion;
- validation operation where cancellable.

In all cases, TUI remains usable and durable operation state records cancellation.

No cancellation path may leave hidden live source writes or a fake current successor snapshot.

---

## No Network Model Requirement

The entire TUI scenario uses the deterministic provider and must run without external model-provider credentials/network.

If Cargo dependency resolution for the candidate is allowed/needed by validation, that remains an explicit separate validation capability and should be test-environment controlled.

The TUI must not prompt for an external model API key in the golden test configuration.

## Required Focused Real-PTY Tests

### TUI-SELFHOST-01 — empty DB onboarding

1. fresh temp Scriberig checkout and DB;
2. launch real `srig tui --db` with deterministic provider;
3. assert no active project;
4. type exact onboarding command;
5. wait for normal agent completion;
6. assert active project and `S0` visible/inspectable;
7. assert semantic navigation works.

### TUI-SELFHOST-02 — PHP candidate generation

Continue from `P@S0`:

1. type exact PHP command;
2. observe nested branch completion;
3. wait for terminal agent result;
4. open `Review candidate`;
5. assert multi-file PHP candidate paths/diffs;
6. assert required validation success;
7. externally assert live checkout remains baseline and project current is `S0`.

### TUI-SELFHOST-03 — Apply and successor

Continue/recreate validated candidate:

1. invoke normal Apply;
2. wait for explicit full canonical/materialization success;
3. assert current snapshot becomes `S1 != S0`;
4. external harness asserts PHP candidate files/updates on disk;
5. open History/Diff and assert transition/candidate;
6. ensure active workspace source/state reflects `S1`.

### TUI-SELFHOST-04 — restart

Restart against same DB/checkout. Assert project/history/session result and `S1` remain inspectable without rerunning onboarding/PHP agent commands.

### TUI-SELFHOST-05 — validation failure

Run controlled failing candidate; assert diagnostic, no Apply-ready success, `S0`/live baseline unchanged.

### TUI-SELFHOST-06 — update conflict

Externally edit update target before Apply; assert conflict and preservation.

### TUI-SELFHOST-07 — create conflict

Externally create proposed new target before Apply; assert conflict and preservation.

### TUI-SELFHOST-CANCEL-01

Cancel representative onboarding/implementation operation and assert no hidden project/file mutation.
