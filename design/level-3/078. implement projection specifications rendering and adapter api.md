# Implement: Projection Specifications, Rendering, and Adapter API

## Objective

Complete the domain-independent `sr-projection` API so higher layers can define persistent projection specifications, render deterministic outputs, and plug in editable domain adapters without depending on filesystem or agent code.

This task builds on the projection scaffolding task and should leave `sr-projection` usable by a non-agent embedding application.

## Read first

Read:

1. `design/level-1/006. projections and bidirectional editing.md`
2. `design/level-2/007. projection crate boundaries and core model.md`
3. `design/level-3/007. bootstrap projection crates and core contracts.md`

Also inspect existing public APIs in `sr-core`, `sr-store`, and `sr-change` before adding types.

## Projection specification

Implement a public projection specification structure that can express:

- stable projection/spec identity or entity reference;
- semantic scope to render;
- `ProjectionKind`;
- `ProjectionClass`;
- exact style revision/reference;
- adapter identity/version;
- renderer version;
- ownership policy at the generic level;
- adapter/domain configuration through a typed/opaque extension mechanism.

Do not store runtime dirty state inside the immutable user-meaningful specification.

Do not use a path as the projection ID.

## Deterministic render request

Create a request type that contains every generic input needed to reproduce output:

```text
projection specification/reference
semantic scope
exact snapshot or exact resolved revisions
style revision
renderer version
rendering context
```

The API should make it obvious when a caller supplies only a moving/current reference rather than an exact snapshot. Deterministic render/cache paths should use exact inputs.

## Rendered output

Create a result type containing:

- bytes or an adapter-neutral payload capable of text/binary representation;
- media/projection kind metadata;
- exact output digest/hash;
- exact semantic/style/renderer inputs used;
- optional fragment/cache metadata owned by the adapter;
- deterministic/non-deterministic marker if the API supports non-reproducible renderers.

For the first implementation, deterministic renderers are the default and preferred case.

Use a stable digest mechanism already selected by the project; do not invent a different hash family unless necessary.

## Style reference behavior

Style used for deterministic output must resolve to exact immutable configuration.

If the system supports aliases such as `user-default`, resolve the alias before constructing the final render-cache identity. The alias itself must not be treated as immutable input if it can move.

Add tests proving two style revisions can produce distinct cache/input identities without changing the semantic object revision.

## Adapter trait

Implement the adapter trait so one domain adapter can provide:

```text
capabilities()
render(...)
parse(...)
reconcile(...)
validate(...)
```

Requirements:

- parsing and reconciliation are separate calls/responsibilities;
- candidate parsed structures remain adapter-owned;
- the generic trait does not require Markdown/source AST types;
- reconciliation can return no-op, migration proposal, ambiguity, conflict, or invalid state;
- validation can return structured diagnostics;
- read-only adapters are not forced to implement meaningful parse/reconcile behavior beyond an explicit unsupported result.

Prefer compile-time separation/associated types where practical over `Any` downcasting.

## Reconciliation context

Provide a context type containing references needed for bidirectional editing:

- last synchronization base snapshot/state;
- current canonical snapshot/state;
- semantic scope;
- projection specification;
- adapter/domain metadata needed to interpret the candidate.

Do not include filesystem watcher events in this type.

## Error model

Use structured error enums with sources.

At minimum distinguish:

- unsupported operation;
- bad projection configuration;
- rendering failure;
- parse failure;
- reconciliation ambiguity/conflict;
- validation failure;
- stale/missing synchronization base;
- storage/change-layer failure where propagated.

Do not use panics for malformed external content or unsupported adapter capabilities.

## Conformance tests

Add fake adapters in tests rather than using Markdown yet.

Cover:

- deterministic render call returns exact input metadata;
- exact same render request can produce identical digest;
- different style revision is visible in render identity;
- read-only adapter rejects edit import cleanly;
- editable fake adapter performs parse then reconciliation as distinct operations;
- `NoSemanticChange` carries no migration;
- conflict/ambiguity remains structured;
- no agent/server/filesystem dependency appears in `sr-projection`.

## Commands to run

```text
cargo fmt --check
cargo test -p sr-projection
cargo test --workspace
```

## Do not do

- Do not add actual filesystem synchronization.
- Do not add Markdown parsing.
- Do not define HTTP types.
- Do not add model/provider or agent dependencies.
- Do not bypass `sr-change` with an independent commit mechanism.

## Completion checklist

- [x] Projection specs separate immutable configuration from runtime state.
- [x] Render requests use exact reproducible inputs.
- [x] Output digest and input metadata are available.
- [x] Style aliases are resolved before exact render identity is formed.
- [x] Adapter parse/reconcile lifecycle is explicit.
- [x] Structured outcomes/errors are tested.
- [x] Workspace tests pass.

Stop after these conditions are met.
