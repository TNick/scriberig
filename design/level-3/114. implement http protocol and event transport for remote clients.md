# Implement HTTP Protocol and Event Transport for Remote Clients

**Status: [x] Complete**

## Objective

Implement the concrete remote transport required by the web application and future remote TUI/third-party clients: JSON protocol requests over HTTP plus resumable semantic event streaming.

Read first:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`;
2. `design/level-1/016. model driven agent execution and branch isolation.md`;
3. `design/level-2/011. application operations protocol and runtime boundaries.md`;
4. `design/level-2/024. agent operations protocol and cross surface product contract.md`;
5. `design/level-3/111. expose agent execution through application protocol server and clients.md`;
6. `web/packages/client/src/http-transport.ts` and `event-stream.ts`.

The existing web transport already assumes operation requests under `/protocol/{operation}` but event subscription is still transport-owned/unimplemented. This task makes that public transport real without moving semantics into HTTP routing.

---

## Scope

Implement remote transport in:

```text
crates/scriberig-server/
crates/scriberig-client/        # Rust remote transport where appropriate
crates/scriberig-cli/           # serve composition/options only as needed
apps/scriberig/                 # server composition root
web/packages/client/
```

Do not change semantic ownership of application operations.

---

## Server Framework

Use a small asynchronous Rust HTTP stack suitable for JSON request handling and streaming.

Preferred first implementation:

```text
Tokio
Axum
Serde / serde_json
```

A different framework requires an explicit implementation justification but must preserve the wire contract described here.

Async/server framework dependencies remain in server/product layers. Do not propagate them into foundation/domain crates merely for transport convenience.

---

## Request Endpoint

Support the existing web-client shape:

```text
POST /protocol/{operation}
Content-Type: application/json
```

The `{operation}` segment maps to a stable public protocol operation identifier.

Logical flow:

```text
HTTP request
-> authentication/request context
-> decode typed public request
-> protocol/server dispatcher
-> scriberig-app operation
-> typed protocol response/error
-> JSON HTTP response
```

Routing must not implement semantic behavior that bypasses the existing dispatcher/application service.

---

## Operation Registry and Routing

Do not create a giant stringly typed switch disconnected from `scriberig-protocol`.

Use a centralized operation mapping where:

- stable operation ids are defined/exported by the protocol layer;
- route decoding maps operation id to a typed request variant;
- dispatch maps the typed request to the existing server dispatcher;
- response encoding preserves structured protocol errors.

Unknown operation ids return a structured unsupported-operation/not-found protocol failure.

---

## HTTP Response Semantics

Use predictable status mapping while keeping the body as the authoritative structured protocol result/error.

Recommended classes:

```text
2xx successful protocol response
400 malformed JSON/request
401 unauthenticated when authentication configured
403 capability/permission denied
404 unknown public operation/resource where appropriate
409 stale/conflict semantic failure where mapping is stable
422 schema/validation request failure where appropriate
429 rate-limited transport/runtime failure when known
5xx internal/server/provider-host failure
```

Do not force every semantic failure into HTTP status alone. Clients must parse the structured error body.

---

## Request Correlation

Preserve/generate a correlation identifier for each HTTP request.

Expose it safely through:

```text
protocol response metadata and/or
X-Request-Id style HTTP header
```

Internal/provider request ids remain separate.

Logs and safe error messages may use the correlation id without dumping request bodies.

---

## Event Stream Endpoint

Add a streaming endpoint conceptually equivalent to:

```text
GET /protocol/events
Accept: text/event-stream
```

Support optional query/filter parameters such as:

```text
after=<cursor>
operation=<OperationId>
session=<SessionRef>
```

The exact filter combination may be restricted initially, but the public event envelope must always identify its correlation scope.

Use Server-Sent Events for the first implementation because the traffic is server-to-client observation rather than bidirectional command transport. Commands continue to use ordinary POST requests.

The browser implementation should consume SSE using `fetch()` streaming rather than requiring the native `EventSource` API, so existing dynamic authorization headers can still be supplied.

---

## Event Envelope

Each emitted event must contain a serialized `ProtocolEvent` plus stable stream metadata equivalent to:

```text
event id / cursor
operation-local or global sequence
kind
operation/session/branch references when relevant
payload
```

Use the SSE `id:` field for the resumable cursor where possible.

Do not encode canonical state only in event text. Durable referenced objects remain queryable through ordinary protocol requests.

---

## Event Buffer and Resume

Implement a bounded replay buffer or event-log adapter sufficient for reconnect.

Requirements:

- assign monotonically ordered cursors in the stream scope;
- retain a bounded recent replay window;
- accept `after=<cursor>` and replay later retained events before switching to live delivery;
- report a structured `cursor_too_old`/resume-unavailable condition when requested history is outside retention;
- clients then refresh operation/session state and subscribe from the current cursor.

Do not retain unbounded token-delta streams solely for reconnection.

Replay retention is transport/observation policy, not canonical session retention.

---

## Backpressure

A slow/disconnected client must not block agent/model/application execution.

Use bounded per-connection queues/broadcast semantics.

When a subscriber falls behind beyond the safe buffer:

- terminate/restart the stream with an explicit gap/resync condition, or
- emit a gap marker supported by the protocol;
- require authoritative refresh.

Do not grow an unbounded in-memory queue for a slow browser.

---

## Heartbeats and Idle Connections

Send bounded heartbeat comments/events during long silent operations when useful to keep intermediaries from closing the connection.

Heartbeats are transport frames, not semantic `ProtocolEvent` objects.

Clients ignore them for session/operation state.

---

## Authentication and CORS

Keep authentication pluggable through server request-context construction.

For the first local browser-host use case:

- default bind remains loopback unless user explicitly chooses otherwise;
- CORS should be restrictive by default;
- configure exact allowed origin(s) for separately hosted development web app;
- never use credentialed wildcard CORS.

If authentication is not yet implemented, keep the transport boundary ready for it and document the security implications of binding beyond loopback.

Provider credentials remain server-side and are unrelated to browser authentication.

---

## Request Limits

Configure bounded limits for:

```text
HTTP request body size
JSON nesting/parse failures
header sizes through framework defaults/config
stream event payload size
concurrent connections where practical
```

Large semantic artifacts should be accessed through bounded query/projection operations rather than huge agent request bodies.

---

## Server Shutdown

`srig serve` must support graceful shutdown.

On Ctrl-C/shutdown:

- stop accepting new connections;
- close event streams cleanly where practical;
- preserve application/agent operation consistency;
- use shared runtime cancellation policy only when product shutdown policy requires operations to stop;
- flush required durable state before process exit.

Transport shutdown and agent-operation cancellation are related but not identical.

---

## Web `HttpTransport.request`

Keep the existing request shape unless protocol generation requires a compatible refinement:

```text
POST `${baseUrl}/protocol/${operation}`
JSON payload
AbortSignal support
structured protocol error decode
```

Add tests for:

- base URL normalization;
- structured errors/statuses;
- abort behavior;
- correlation metadata if surfaced;
- no accidental provider endpoint usage.

---

## Web `HttpTransport.subscribe`

Replace the current no-op subscription with a fetch-backed SSE consumer.

It must:

```text
open GET /protocol/events
send dynamic auth/application headers
parse SSE framing incrementally
parse ProtocolEvent JSON
track latest cursor/id
support AbortSignal/unsubscribe
reconnect according to caller/policy
resume with last cursor when supported
surface/handle cursor-too-old by triggering authoritative refresh
```

Do not use provider streaming protocols in this transport. This stream contains Scriberig protocol events only.

Split the SSE parser into a focused transport utility with deterministic byte/chunk tests rather than implementing parsing inside one oversized method.

---

## Rust Remote Client Transport

Where `scriberig-client` remote mode is part of the same milestone, add an HTTP transport implementing the public client boundary.

It should support:

```text
request/response protocol operations
event subscription or event-stream handle
cancellation/shutdown
structured error mapping
```

If the existing Rust `ProtocolTransport` is synchronous and cannot correctly express streaming, introduce a separate asynchronous remote transport/subscription abstraction rather than forcing async behavior through a blocking fake API.

Preserve the in-process transport for tests/embedded use.

---

## TUI Remote Compatibility

Do not alter TUI semantic state/reducer for remote mode.

The future/current task 105 remote adapter should consume `scriberig-client` and implement the same TUI service port used by local mode.

This transport task must provide enough client support that agent/session event observation can work remotely without giving the TUI provider credentials.

---

## Static Web Hosting

Hosting the built reference web application from `srig serve` is optional for this task unless already required by repository product design.

If implemented, keep static-file hosting separate from `/protocol/*` routing and do not make the web application depend on co-hosting; a separately hosted frontend must still work under configured CORS/auth rules.

## Tests

Use localhost/in-process server tests only. No public internet/model endpoint is allowed.

Cover at least:

### Request transport

- known operation round-trips typed request/response;
- malformed JSON returns structured error;
- unknown operation is rejected;
- semantic application error preserves category/body;
- cancellation/AbortSignal closes client request;
- correlation id is stable per request.

### Event stream

- live `ProtocolEvent` arrives in browser/Rust client;
- SSE framing survives arbitrary network chunk boundaries;
- event ids/cursors are monotonic;
- reconnect with recent cursor replays missing retained events;
- too-old cursor produces explicit resync behavior;
- slow subscriber cannot grow unbounded server memory;
- heartbeat frames are ignored semantically;
- cancelling subscription closes network task cleanly.

### Agent vertical slice

With deterministic fake agent runtime:

```text
POST agent_start
-> receive operation/session/root branch
-> subscribe events
-> observe child branch/model/tool progress
-> query terminal operation/session result
```

Prove the terminal result remains correct after intentionally dropping the event connection mid-operation and reconnecting/refreshing.

## Do Not Do

- Do not put semantic agent logic in Axum route handlers.
- Do not expose provider credentials or provider HTTP endpoints to the browser.
- Do not make WebSocket a requirement when server-to-client SSE is sufficient.
- Do not use unbounded subscriber queues or replay buffers.
- Do not make event delivery authoritative over queryable durable state.
- Do not bind publicly by default without explicit user intent/security guidance.
- Do not create a second browser event model unrelated to `ProtocolEvent`.
