# Implement Style-Aware Rust and ECMAScript Source Projection Rendering

## Status

Planned.

Prove the projection-style architecture in real source-code domains by making Rust and ECMAScript/TypeScript rendering consume exact resolved style inputs.

This task depends on task 151.

## 3. Architectural Constraints

Preserve:

```text
semantic source model
  + exact resolved domain style
  -> deterministic source projection
```

Do not:

- make rendered source text canonical state;
- put Rust/ECMAScript properties into `sr-projection`;
- read ambient formatter configuration from the renderer;
- interpret a style-only byte difference as a semantic program change;
- make the TUI/web own source formatting;
- use raw file editing as the normal semantic source mutation path.

The renderer may delegate formatting/code generation to a suitable library, but the Scriberig domain adapter remains responsible for exact input declaration, semantic safety, style normalization, and fidelity classification.

## 4. Rust: Establish a Domain Style Schema

Add a Rust source-projection style type/schema in the Rust domain owner.

The first required property is indentation.

Support at least an exact normalized distinction equivalent to:

```text
spaces(width = 2)
spaces(width = 4)
```

The schema may also include line width or another already-supported representational property if doing so is small and naturally supported, but do not inflate this task by implementing a complete rustfmt configuration model.

Requirements:

- deterministic canonical encoding into the style value used by task 151;
- structured validation for invalid widths/values;
- documented defaults;
- purpose applicability compatible with shared style resolution;
- fidelity classification for the styles actually supported.

---

## 5. Rust: Remove Hard-Coded Indentation

The current renderer emits a literal four-space prefix for function-body statements.

Replace hard-coded indentation with the exact resolved Rust style.

The renderer must accept the resolved style through the projection/domain render path rather than by reading a process-global/user-global setting.

Preserve deterministic behavior for the default style so existing tests/fixtures change only where intentionally required.

Add tests proving:

```text
same RustFile + 2-space style -> bytes A
same RustFile + 4-space style -> bytes B
A != B
semantic RustFile unchanged
```

Also prove repeated rendering under one exact style is byte-identical.

---

## 6. Rust: Do Not Confuse Attributes, Docs, and Comments

Before adding any Rust comment-visibility control, audit how the current Rust semantic/syntax model represents:

```text
ordinary comments
doc comments
attributes/tool directives
raw token-preserved items
```

If the current semantic model cannot reliably distinguish safely hideable comments from behavior/documentation-affecting forms, do **not** implement a generic `strip_comments` switch.

Instead:

- document the unsupported capability through the style schema/fidelity result;
- preserve all currently representable content;
- leave comment-hiding support for a model that can classify it safely.

Task success does not require lossy Rust comment projection if the semantic model is not ready.

## 7. ECMAScript: Audit Rendering Options Before Selecting an Engine

The existing ECMAScript domain uses Oxc for parsing JavaScript/TypeScript/JSX/TSX.

Before adding a dependency or custom printer, evaluate the current viable code-generation/formatting options against:

```text
JS/TS/JSX/TSX syntax coverage
integration as a Rust/library dependency
explicit configuration control
deterministic output
comment and directive preservation
source range/source-map support
ability to avoid undeclared ambient config
round-trip/parser compatibility
license compatibility
maintenance cost
```

Prefer reusing an established renderer/formatter over implementing a large handwritten JavaScript pretty-printer.

If current Oxc crates provide a suitable code generator/formatter at the pinned ecosystem version, prefer the smallest coherent Oxc-based path unless evidence favors another existing dependency.

Record the chosen engine and why in code/module documentation or the task/commit notes.

## 8. ECMAScript: Add Source Projection Rendering

Add a domain-owned rendering path for JavaScript/TypeScript/JSX/TSX semantic/syntax structures supported by the current adapter.

It must consume the exact resolved ECMAScript style from task 151.

At minimum support one visible style dimension with two exact variants, preferably indentation width if the chosen engine exposes it deterministically.

Where the chosen engine supports them safely and cheaply, additional properties may include:

```text
line width
quote preference
semicolon preference
trailing comma preference
```

Do not promise a style property through discovery unless the renderer actually honors it for the supported syntax set.

---

## 9. ECMAScript Comment and Directive Classification

Audit how Oxc/current AST data exposes comments/trivia/directives.

Create a domain-level classification boundary capable of distinguishing, where supported:

```text
ordinary comments
documentation/JSDoc
license/header comments
TypeScript compiler/type-check directives
lint directives
formatter directives
source-map/tooling directives
```

Do not assume all comment-syntax content is safely hideable.

A first implementation may expose only:

```text
PreserveAll
HideOrdinaryCommentsInView
```

if and only if the adapter can prove that the second option preserves mandatory/directive categories.

If that proof is not practical in this task, keep comments preserved and expose the limitation explicitly. Do not implement unsafe stripping to satisfy a checkbox.

---

## 10. Fidelity Classification

For each implemented Rust/ECMAScript style, return the exact fidelity state defined by task 151.

Examples:

```text
indentation-only style
  -> LosslessEditable, assuming existing parse/reconcile capabilities support it

hide ordinary comments
  -> LossAwareEditable only after task 153 implements and proves loss-aware reconciliation
  -> otherwise ReadOnlyLossy
```

Task 152 must not claim loss-aware editability merely because rendering can omit content.

A lossy renderer may land before loss-aware editing as long as the projection is conservatively read-only.

---

## 11. Repository Convention Mapping

Add only narrowly justified mappings required to prove the style-resolution path.

For example, if `.editorconfig` support already exists or is small and owned in a suitable configuration/domain layer, map indentation settings into the Rust/ECMAScript domain style input.

Do not implement full Prettier/Biome/rustfmt configuration parsing in this task unless an existing library/current owner already provides it with little duplication.

The important proof is:

```text
external/project convention
  -> typed style source
  -> task-151 resolver
  -> exact resolved domain style
  -> renderer output
```

not exhaustive ecosystem compatibility.

---

## 12. Adapter and Projection Integration

Ensure normal application projection rendering can reach the new domain renderers through the existing adapter/registry path.

Do not leave the style-aware renderer as an isolated helper tested only directly.

A render request through the public/shared projection boundary must:

1. resolve/receive an exact style;
2. dispatch to the correct domain renderer;
3. return `RenderedProjection` or current equivalent with exact style/renderer metadata;
4. produce cache identity that differs for different exact styles;
5. preserve semantic scope/snapshot identity.

## 13. Tests

### Rust

Add tests for:

- default style reproduces expected deterministic source;
- 2-space and 4-space styles produce expected distinct bytes;
- repeated render is deterministic;
- invalid style input returns structured diagnostics;
- style-only difference does not alter semantic source identity/state.

### ECMAScript

Add tests for at least JavaScript and TypeScript, and JSX/TSX when the renderer claims those kinds:

- parse supported source into the current semantic/syntax model;
- render deterministically;
- render the same semantic structure with two styles into different expected bytes;
- parse rendered output successfully;
- preserve behavior-significant directives/comments supported by the adapter;
- invalid/unsupported style input produces structured diagnostics.

### Projection integration

Add tests proving:

- public render path carries exact style metadata;
- render/cache keys differ by style;
- same semantic snapshot is reused across style variants;
- unsupported lossy editing is classified read-only.

## 14. Dependency and Licensing Discipline

If adding a new formatter/codegen crate or external library:

- follow the repository licensing design and notices process;
- verify license compatibility;
- prefer maintained library APIs over subprocess-only integration when practical;
- keep the dependency in the domain layer rather than generic projection/application/TUI layers;
- avoid a dependency that implicitly reads the filesystem/global config during deterministic rendering unless that behavior can be disabled and exact inputs supplied.

Do not vendor a large formatter into Scriberig merely to avoid declaring a normal compatible dependency.
