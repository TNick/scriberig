# Implement: Markdown Model, Parser, Renderer, and Style

## Objective

Implement the first concrete projection adapter in `sr-markdown` up to deterministic parse/render/equivalence. Do not implement identity reconciliation or migration generation in this task.

The result must be able to parse ordinary Markdown into an adapter-owned candidate structure, render canonical Markdown semantic objects deterministically, and determine when two supported Markdown representations are semantically equivalent despite formatting differences.

Read:

Inspect any existing universal graph/schema crates and use their public entity/revision representation rather than creating a competing store model.

## Parser dependency

Select a mature CommonMark-compatible Rust parser unless the repository already chose one.

Keep parser-library types inside `sr-markdown`.

Do not expose parser-library AST node types in public Scriberig APIs.

Record the dependency normally in `Cargo.toml`; no Level 1 design update is needed for the parser choice.

## `model.rs`

Define the Markdown semantic vocabulary required by Level 2.

Support at least:

```text
MarkdownDocument
Section
Heading
Paragraph
List
ListItem
Table
TableRow
TableCell
CodeBlock
QuoteBlock
Link
```

Choose a representation that separates block structure from inline content cleanly enough to preserve links and basic author-significant inline structure.

Requirements:

- order belongs to parent collections;
- line numbers/source offsets are not semantic identity;
- model does not store an original Markdown blob as canonical content;
- no hidden file-specific IDs are required;
- types are deterministic/serializable according to existing project conventions.

If the universal graph layer expects schemas rather than Rust enums as canonical representation, implement conversion/builders between these domain values and that graph instead of making this model a second source of truth.

## `candidate.rs`

Define parser-owned candidate nodes distinct from canonical `EntityId`.

Candidate nodes need:

- local candidate identifier/path for diagnostics;
- semantic kind;
- ordered children;
- parsed content/properties;
- optional source span/line information for error reporting only.

A candidate node must not pretend to be an existing canonical entity.

## `style.rs`

Implement an immutable-value `MarkdownStyle` with only supported deterministic options.

Initial fields should cover:

```text
list_marker
ordered_list_delimiter
blank_lines_between_blocks
final_newline
code_fence_preference
table_spacing
```

Validate style values at construction where needed.

Do not add options that merge/split paragraphs, alter headings, rewrite URLs, or change code contents.

## `parser.rs`

Parse exact input bytes/text into `CandidateDocument`.

Requirements:

- preserve document/section hierarchy derived from headings;
- parse paragraphs;
- parse ordered/unordered lists and items;
- parse fenced/indented code as supported by the chosen library into code-block semantics;
- parse block quotes;
- parse links;
- parse tables if the selected parser requires enabling a standard extension; document that capability in adapter metadata;
- produce structured diagnostics on unsupported/invalid constructs rather than panicking;
- retain source spans only for diagnostics.

Markdown often permits partially recoverable content. Define clearly which parse conditions produce a candidate with warnings and which produce `InvalidExternalState`.

## `render.rs`

Implement deterministic rendering from canonical/domain Markdown semantics plus exact `MarkdownStyle`.

Requirements:

- headings/section nesting render deterministically;
- block ordering follows canonical collection order;
- style controls only approved formatting choices;
- tables render deterministically for the supported table model;
- code blocks preserve semantic language/info string/content;
- links preserve target and label semantics;
- final newline follows style;
- same semantic input/style/renderer version produces identical bytes.

Implement the `sr-projection` render side of the Markdown adapter.

Do not render by patching the old file. Generate from semantic state.

## `equivalence.rs`

Implement semantic-equivalence comparison for supported candidate/canonical structures.

It must identify formatting-only differences such as supported list marker/spacing choices while still detecting changes to semantic block structure or content.

Use this layer later to return `NoSemanticChange` before migration generation.

Do not treat all syntactic differences as formatting. Preserve the domain boundary from Level 2.

## Diagnostics

`diagnostic.rs` should convert parser/render domain failures into structured Markdown diagnostics that can be embedded in generic projection diagnostics.

Include source span where available but do not make it canonical identity.

## Tests

Create representative fixtures inline or under `tests/fixtures/` if that makes tests clearer.

Cover at least:

- document with nested headings/paragraphs;
- unordered and ordered lists;
- table with rows/cells;
- fenced code block;
- block quote;
- links;
- parse -> semantic/candidate -> render -> parse semantic equivalence;
- two style configurations render differently but parse as semantically equivalent where expected;
- whitespace/list-marker-only change is equivalent;
- paragraph text change is not equivalent;
- heading structure change is not equivalent;
- line/source positions do not appear in semantic equality/identity.

## Do not do

- Do not assign canonical entity IDs during parsing.
- Do not implement migration generation.
- Do not implement filesystem watchers.
- Do not preserve formatting by storing the original entire file as canonical data.
- Do not add agent/CLI/server/web dependencies.
- Do not normalize author-significant document structure just for prettier output.

## Completion checklist

- [x] Supported Markdown semantic model exists.
- [x] Candidate model is distinct from canonical identity.
- [x] Parser handles required constructs.
- [x] Renderer is deterministic.
- [x] Style changes representation without changing semantics.
- [x] Semantic equivalence distinguishes formatting-only from meaningful changes.
- [x] Round-trip tests pass.

Stop after these conditions are met.
