# Implement Application Operation Primitives

## Objective

Implement the first shared application-layer primitives in `scriberig-app`.

Read first:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`
2. `design/level-2/011. application operations protocol and runtime boundaries.md`
3. the Level 1 identity/snapshot and change/migration documents that define the canonical ID and migration concepts already implemented by lower crates.

This task creates the reusable operation boundary. It does not implement HTTP, CLI parsing, agent model execution, or domain-specific editing.

---

## Prerequisites

The runtime crate scaffold must exist.

The foundational crates must already expose the real identifier and snapshot types required by this task.

Reuse those types. Do not create duplicate `EntityId`, `RevisionId`, `SnapshotId`, `MigrationId`, or branch identifiers inside `scriberig-app`.

If an upstream type is not yet implemented, implement only the portions that can compile without inventing a competing identity model.

---

## Files to Create or Replace

Inside `crates/scriberig-app/src/` create:

```text
lib.rs
error.rs
context.rs
query.rs
command.rs
operation.rs
event.rs
capability.rs
```

Keep modules small and documented.

---

## `context.rs`

Define an application request context carrying the semantic base under which an operation runs.

It must be able to express:

- exact snapshot when one is required;
- caller/actor provenance in a generic form if the lower-level provenance model already exists;
- capability/authorization context without embedding UI concepts;
- a correlation/request identifier where useful.

Do not put HTTP headers, CLI arguments, or model prompts in this type.

Prefer explicit immutable values.

---

## `error.rs`

Define one structured application error enum with variants corresponding to these semantic classes:

```text
NotFound
SchemaViolation
StaleBaseSnapshot
SemanticConflict
ValidationFailure
PermissionDenied
UnsupportedOperation
ProjectionOutOfSync
OperationCancelled
Internal
```

Use structured fields where existing lower-layer types make that useful.

Each error must implement normal Rust error/display behavior without requiring callers to parse its display string to discover the category.

Do not include HTTP status codes here.

---

## `operation.rs`

Define the application-level long-running operation model.

Required concepts:

```text
OperationId
OperationKind
OperationStatus
OperationProgress
OperationResult reference/summary
```

Reuse a shared `OperationId` from `scriberig-core` if it already exists. If Level 2/3 identity work has not provided it, add it only in the canonical low-level crate, not locally in `scriberig-app`.

`OperationStatus` must represent at least:

```text
Queued
Running
Completed
Failed
Cancelled
```

Ensure terminal states are distinguishable with a helper such as `is_terminal()`.

Do not implement scheduling or threads in this task.

---

## `event.rs`

Define a transport-independent application event enum or equivalent typed model.

Include categories equivalent to:

```text
SnapshotChanged
EntityChanged
ProjectionChanged
BranchChanged
MigrationCreated
OperationStarted
OperationProgressed
OperationCompleted
ValidationCompleted
AgentOutputProduced
```

Payloads should contain stable handles and concise metadata.

Do not copy full mutable entity state into events.

Do not use server/WebSocket types here.

---

## `capability.rs`

Define a small runtime capability vocabulary suitable for discovery.

The first implementation only needs to express:

- a stable capability identifier/name;
- short description;
- whether it is available in the current application configuration;
- optional domain/scope metadata if already supported cleanly.

Do not turn this into authorization policy or the repository capability matrix.

Those are separate concerns.

---

## `query.rs`

Define application-level read request/result forms for the first vertical capability: entity inspection.

Required semantic input:

```text
entity
snapshot resolution mode
requested detail level if the existing graph API supports it
```

The result must identify:

- the requested entity;
- exact resolved revision;
- exact snapshot used;
- semantic type/summary information exposed by the graph layer.

Do not render terminal text here.

Do not serialize protocol DTOs here.

Use graph/query APIs already defined below the application layer.

If the lower graph API is not yet capable of inspection, keep request/result types and orchestration interfaces minimal rather than bypassing it.

---

## `command.rs`

Define command request boundaries, but do not implement broad mutations yet.

At minimum provide typed placeholders/interfaces for commands whose semantics already exist below the app layer, such as applying a migration against an explicit base snapshot.

Do not create an alternative mutation representation.

A command must delegate canonical change to `scriberig-migration`/snapshot infrastructure.

If those APIs are not ready, keep the module documented with only types that are justified by implemented lower layers.

---

## `lib.rs`

Re-export only stable application-facing types that callers actually need.

Do not glob-export internal implementation helpers.

Crate documentation should state clearly:

> `scriberig-app` is the shared semantic operation boundary for CLI, server, TUI, clients, and agent adapters.

---

## Tests

Add unit tests for:

- every application error category being inspectable without string parsing;
- `OperationStatus::is_terminal()` or equivalent;
- event payloads retaining stable IDs and not owning canonical state;
- inspect request/result preserving snapshot identity;
- application types not depending on transport-specific data.

Use compile-time dependencies and normal Rust tests; do not require a network.

---

## Do Not Do

- Do not add server routes.
- Do not define protocol serialization here.
- Do not add a CLI command.
- Do not add a model provider.
- Do not access SQLite directly.
- Do not duplicate core identifiers.
- Do not mutate canonical state outside shared migration APIs.
- Do not implement a general job scheduler.

---
