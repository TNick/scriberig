# Implement Universal Query Handles, Scope, and Pagination

## Objective

Implement the foundational data types in `scriberig-query` required by the universal query and operation model.

This task creates semantic handles, selection/anchor types, explicit query scope, opaque pagination, and progressive-detail vocabulary. It does **not** implement graph traversal, search execution, the structured query AST, application operations, protocol serialization, or UI behavior.

## 1. Reuse Existing Identity Types

Import the existing canonical identifiers rather than redefining them.

Use the established equivalents of:

```text
EntityId
RevisionId
SnapshotId
RelationTypeId
CollectionTypeId
ProjectionId
```

If one optional identifier such as `ProjectionId` is owned by another crate not yet available, isolate that dependency behind a small generic/opaque reference instead of inventing a competing global ID type.

The query crate must not own hashing or identifier generation.

---

## 2. Implement Semantic Handle Types

In `src/handle.rs`, implement lightweight public types for the semantic targets needed by queries.

Required concepts:

```text
EntityRef
RevisionRef
SnapshotRef
RelationRef
CollectionRef
ProjectionRef
OperationRef
```

Prefer newtypes or small structs/enums that preserve type distinction.

Do not collapse all identifiers to `String`.

Provide an exact entity/revision target equivalent to:

```text
EntityAtRevision {
    entity: EntityId,
    revision: RevisionId,
}
```

Provide a snapshot-relative entity target equivalent to:

```text
EntityInSnapshot {
    entity: EntityId,
    snapshot: SnapshotId,
}
```

A unified `TargetRef` enum is allowed if it makes APIs simpler, but exact revision and snapshot-relative meanings must remain distinguishable.

Add sensible traits such as `Clone`, `Debug`, `PartialEq`, `Eq`, and `Hash` where the wrapped canonical identifiers support them honestly.

---

## 3. Implement Relation Paths and Selection

Add a semantic relation-path representation suitable for recording context inside a graph without turning physical storage paths into identity.

A relation-path step should be able to identify a typed relation or collection traversal.

Implement `Selection` with conceptual fields equivalent to:

```text
snapshot: SnapshotId
entity: EntityId
revision: Option<RevisionId>
relation_path: Vec<RelationStep>
projection_anchor: Option<ProjectionAnchor>
```

Keep `ProjectionAnchor` transport/UI neutral.

A safe first implementation is an enum or tagged structure that can represent opaque anchor data such as:

```text
TextRange
PageRegion
Opaque { kind, value }
```

Do not import DOM, terminal, editor, or browser types.

Document clearly that projection anchors are convenience mappings, not canonical identity.

---

## 4. Implement Query Scope

In `src/scope.rs`, implement an explicit `QueryScope` or equivalent.

It must support at least:

```text
Snapshot(SnapshotId)
Entity {
    snapshot: SnapshotId,
    entity: EntityId,
}
ExplicitEntities {
    snapshot: SnapshotId,
    entities: Vec<EntityId>,
}
```

If the graph layer already defines a subtree/container abstraction, reuse it rather than duplicate it.

Every scope variant must identify one exact snapshot.

Do not add a `Current` variant inside the query crate. Resolving “current” to an exact snapshot is an application-layer responsibility.

Add helper methods for retrieving the bound `SnapshotId`.

---

## 5. Implement Opaque Pagination

In `src/pagination.rs`, implement:

```text
PageRequest
ContinuationToken
Page<T>
```

Requirements:

- `PageRequest` includes a bounded `limit` and optional continuation.
- Choose a conservative default and maximum limit, but keep constants easy to change.
- Reject zero or obviously unreasonable limits through a constructor/validation method instead of relying on every caller.
- `ContinuationToken` is opaque to callers.
- Do not expose SQL offsets, row IDs, or backend cursor fields in the public type.
- `Page<T>` carries `items` and optional `next` continuation.

A token may internally wrap bytes or a string in the first version.

Do not promise that tokens remain valid across different snapshots. Document that continuation belongs to the operation/snapshot context that produced it.

---

## 6. Implement Progressive Detail

In `src/detail.rs`, implement a small universal detail enum equivalent to:

```text
Identity
Compact
Structure
Full
```

Keep this universal.

Do not add variants such as `CodeGroups`, `PdfLayout`, or `SessionTurns`; those are domain views/capabilities.

Add an optional `InformationCost` structure capable of expressing coarse estimates such as:

```text
items
bytes
approx_tokens
```

All fields may be optional.

Information cost is advisory only; do not use it for authorization or correctness.

---

## 7. Public Exports

Update `src/lib.rs` to expose stable public paths for the implemented types.

The crate should allow downstream code to import the common types without reaching into private implementation details.

Avoid a giant prelude if the project does not already use that pattern.

---

## 8. Tests

Add focused unit tests in the module files or an appropriate crate test file covering:

1. exact revision and snapshot-relative targets remain distinguishable;
2. a `Selection` can represent semantic-only selection with no projection anchor;
3. a `Selection` can carry a projection anchor without changing entity/revision identity;
4. every `QueryScope` exposes one exact `SnapshotId`;
5. explicit entity-set scope preserves entity order only if the API promises order; otherwise document/order-normalize appropriately;
6. pagination rejects invalid limits;
7. `Page<T>` carries a continuation independently of item content;
8. continuation token internals are not exposed through public fields;
9. progressive detail values remain domain-independent;
10. information-cost fields are optional.

Run:

```text
cargo test -p scriberig-query
cargo check --workspace
```

If workspace prerequisites are incomplete, run the narrowest available checks and report the exact unmet prerequisite.

---

## 9. Non-Goals

Do not implement:

- `inspect`, `list`, `follow`, `find`, or `query` execution;
- SQL/index lookups;
- diff/history/render;
- branch/apply/commit;
- HTTP/JSON schemas;
- CLI parsing;
- React selection state;
- agent tools.

---

## Completion Criteria

This task is complete when:

- `scriberig-query` has reusable semantic handle types;
- exact revision versus snapshot-relative entity targeting is explicit;
- semantic selections can carry optional projection anchors;
- every query scope is bound to one exact snapshot;
- pagination is bounded and storage-independent;
- progressive detail and optional information-cost hints exist;
- public docs explain the identity and snapshot semantics;
- unit tests pass without requiring a database backend.
