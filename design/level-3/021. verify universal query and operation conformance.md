# Verify Universal Query and Operation Conformance

## Objective

Add the end-to-end conformance tests that prove the universal query and application-operation model behaves consistently across the reusable Rust layers.

This task does not add new product features. It verifies that the implementation created by the previous Level 3 tasks preserves the architectural invariants in `design/level-1/010. universal query and operation model.md`.

The test suite must remain usable without an HTTP server, CLI, TUI, web application, agent runtime, or SQLite backend.

## 1. Build a Small Multi-Domain-Like Fixture

Create a generic graph fixture using universal entities rather than requiring real Rust/Markdown/PDF parsers.

The fixture should contain at least:

```text
Project P
  collection modules/documents -> E1, E2

Entity E1
  type: Function-like test type
  relation calls -> E3
  collection groups -> E4, E5

Entity E2
  type: Section-like test type
  collection paragraphs -> E6, E7

Entity E3
  type: Function-like test type

Branch/workspace B
  based on Snapshot S1
```

Create at least two snapshots so one entity changes between `S1` and `S2` while another remains unchanged.

Use real canonical identity/snapshot types and the actual in-memory graph/store helpers.

Do not hard-code production domain adapters merely for this test.

---

## 2. Prove Snapshot-Bound Reads

Test:

1. inspect `E1` at `S1`;
2. advance a named root to `S2`;
3. verify the completed result still reports `S1` and the `S1` revision;
4. inspect through a named-root selector after advancement and verify the application service resolves it to `S2` exactly once;
5. verify an exact `RevisionRef` remains readable regardless of the newer root.

The test must fail if query execution silently follows a moving named root.

---

## 3. Prove Progressive Disclosure

Test that compact `inspect(E1)` returns orientation data such as:

```text
type
short description/counts
available collections
available relations
available views/operations
```

without requiring the full semantic body.

Then:

1. list the `groups` collection;
2. inspect one returned group handle;
3. follow the `calls` relation;
4. inspect the returned target.

The same semantic handles returned by one operation must be accepted by the next operation directly.

---

## 4. Prove Pagination

Create a collection larger than one page.

Verify:

- first request respects the requested limit;
- continuation is returned;
- second request continues without duplicating or skipping items;
- the continuation is bound to the same semantic operation/snapshot context;
- invalid or corrupted continuation returns a structured error;
- public test assertions do not rely on the internal token encoding.

---

## 5. Prove Find Versus Query Semantics

For `find`:

- execute exact/structured-name discovery in the fixture;
- verify results include semantic handles and optional previews;
- verify unsupported semantic strategy fails explicitly.

For `query`:

- select by type;
- select by property;
- constrain through a relation;
- constrain through collection membership;
- combine predicates with `And`/`Or`/`Not`;
- verify exact snapshot identity in the result.

The test should demonstrate that `find` may be discovery/ranked while `query` remains structural and declarative.

---

## 6. Prove Diff, History, and Render Delegation

Use provider test doubles that record calls.

Execute application requests for:

```text
Diff
History
Render
```

Verify:

- the application layer calls the canonical provider exactly once;
- it does not perform competing graph diff/history/render logic;
- structured semantic result objects survive wrapping;
- render does not invoke root promotion or canonical mutation;
- the result retains exact subject/snapshot/revision context.

---

## 7. Prove Branch, Apply, Commit Semantics

Use a change-service test double with observable state.

Scenario:

```text
base S1
branch -> B1
apply change -> candidate S2
commit -> promoted/retained S2
```

Assertions:

- branch records `S1` exactly;
- apply produces candidate/change data but does not promote the named root;
- validation/conflict details survive the app boundary;
- commit is the explicit promotion call;
- accepted migration/base/result handles remain available after commit.

Add a failing-conflict apply case and verify the canonical root remains unchanged.

---

## 8. Prove Capability Discovery

Register two fake domain capability providers.

Verify `inspect` can advertise:

```text
relation capability
collection capability
view capability
find strategy
high-level domain operation
```

without adding domain-specific branches to core application dispatch.

Test duplicate IDs according to the deterministic rule chosen by the implementation.

Test a capability requiring missing derived data and ensure its availability is reported honestly or it is omitted according to the implemented contract.

---

## 9. Prove High-Level Operation Convergence

Register one dummy high-level operation such as:

```text
replace_test_label
```

Execute it against a branch/workspace.

Verify that the provider produces/applies a canonical migration/change through the normal change service.

The test must fail if the provider can directly mutate a root/store outside that boundary.

No real Markdown or Rust editing is required.

---

## 10. Prove Structured Failures

Cover at least:

```text
NotFound
InvalidRequest
UnsupportedCapability
Conflict
ValidationFailed
Ambiguous
SnapshotUnavailable
OperationFailed
```

For conflict and ambiguity, verify exact semantic handles/revisions/candidates are present.

Do not assert only on human-readable error strings.

---

## 11. Prove Operation Handle Semantics

Create a fake delegated operation.

Verify:

1. request returns `OperationStarted(OperationRef)`;
2. status can be represented as queued/running/completed;
3. completed status exposes structured result handles;
4. failed and cancelled are distinct terminal states;
5. ordinary fast reads may still return immediate results without creating operation records.

No real thread or process scheduler is required.

---

## 12. Prove Layer Independence

Add compile/test checks where practical to ensure:

- `scriberig-query` does not depend on `scriberig-app`, server, CLI, agent, TUI, or web layers;
- `scriberig-app` does not depend on server, CLI, agent-runtime, TUI, or web packages;
- no test requires SQLite;
- no universal result uses presentation-formatted text as its only semantics;
- query AST/public pagination contains no SQL/backend-specific fields.

If dependency-graph testing infrastructure does not exist, inspect `Cargo.toml` dependencies in the test task and add a documented manual assertion rather than introducing a large new tool.

## Completion Criteria

This task is complete when the test suite demonstrates that:

- all universal reads are exact-state/snapshot bound;
- semantic handles compose across operations;
- progressive disclosure avoids mandatory full-object reads;
- traversal is bounded/pageable;
- find and query have distinct, correct semantics;
- diff/history/render delegate to canonical subsystems;
- branch/apply/commit preserve explicit candidate and promotion boundaries;
- capabilities are discoverable and extensible without core domain branching;
- structured conflicts/errors retain semantic context;
- long-running work has operation-handle semantics;
- the query and app libraries remain useful without agents or product surfaces.
