# Implement Canonical Encoding and Revision Hashing

## Mission

Implement deterministic canonical byte encoding in `sr-core` and the exact hashing rule used to produce `RevisionId` values.

This task must make revision hashing deterministic across runs, platforms, map insertion orders, and unrelated Rust implementation details.

Do not implement revision storage or snapshots yet.

## Canonical Writer

Create a deterministic `CanonicalWriter` backed by `Vec<u8>`.

It must provide explicit methods for at least:

- [ ] writing a fixed byte/domain tag;
- [ ] `u8`;
- [ ] `u16`;
- [ ] `u32`;
- [ ] `u64`;
- [ ] booleans with fixed discriminants;
- [ ] raw bytes with an explicit length prefix;
- [ ] UTF-8 strings with byte-length prefix;
- [ ] optional values with explicit present/absent discriminant;
- [ ] sequence length before sequence contents.

Use one specified endian order for multi-byte integers. Use big-endian unless the Level 2 design is updated before implementation.

Lengths must use a fixed-width integer representation. Use `u64` for encoded lengths unless there is a compelling implementation blocker.

Do not serialize `usize` directly because it is platform-sized.

## `CanonicalEncode`

Expose:

```rust
pub trait CanonicalEncode {
    fn encode_canonical(&self, out: &mut CanonicalWriter);
}
```

Implement it where useful for the primitive identity/configuration types, but do not create a blanket serde-based implementation.

The trait must make ordering an explicit caller responsibility for maps or sets.

Document that unordered containers must be sorted before encoding.

## Revision Hashing

Add BLAKE3 as a dependency.

Define one fixed revision-domain tag in code. Keep it private or crate-visible unless callers need it for conformance tests.

Provide one public helper with behavior equivalent to:

```text
hash_revision(
  encoding_version,
  type_id,
  canonical_payload
) -> RevisionId
```

The hash input must be exactly the canonical encoding of:

```text
revision domain tag
encoding version
type ID
canonical payload bytes
```

The `EntityId` must not participate in this hash.

No timestamps, pointers, process IDs, random values, insertion-order artifacts, or mutable aliases may participate.

## Encoding Version

Version 1 must be encoded into every revision hash.

Do not hard-code a raw integer in multiple places. Use the `EncodingVersion` type from task 001.

## Determinism Tests

Add focused tests proving:

- [ ] the same inputs produce the same bytes;
- [ ] the same revision inputs produce the same `RevisionId`;
- [ ] changing payload changes `RevisionId`;
- [ ] changing `TypeId` changes `RevisionId`;
- [ ] changing `EncodingVersion` changes `RevisionId`;
- [ ] `EntityId` is not an input to revision hashing;
- [ ] encoding a fixed sequence produces an expected fixed byte vector;
- [ ] strings use byte length, not character count;
- [ ] the implementation does not depend on native endianness.

At least one canonical encoding test must assert exact bytes, not merely compare two runs of the same function.

## Public Documentation

Add rustdoc explaining:

- why canonical encoding exists;
- why general JSON serialization is not used for identity;
- why map/set ordering must be canonicalized by callers;
- why changing encoding rules requires a new encoding version.

## Do Not

- Do not hash `Debug` output.
- Do not hash serde JSON text.
- Do not hash Rust memory layout.
- Do not use `HashMap` iteration order.
- Do not include `EntityId` in `RevisionId`.
- Do not implement `SnapshotId` hashing in this task.
- Do not create `sr-store` in this task.
