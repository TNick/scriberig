## Controlling Rules

These rules are mandatory for every subtask.

### Rule 1: no private shortcuts

Do not make the web app, TUI, CLI, or agent mutate database tables directly.

Do not add web-only server endpoints.

Do not deep-import private package source.

Do not let the agent patch files directly as a privileged alternative to the migration path.

### Rule 2: active project is not a global server variable

The server/database may store project catalog/current project snapshot data, but each client chooses its own active workspace.

Do not implement one mutable server-wide `current_project` setting.

### Rule 3: named semantic data comes from shared semantics

Do not solve explorer labels by parsing Rust source separately in React or the TUI.

The shared adapter/object summary/navigation result must expose meaningful names/kinds.

### Rule 4: a source projection is real source

Do not satisfy the projection step with the generic object inspector.

For the supported Rust golden fixture, source projection must expose `src/lib.rs` and the actual expression `left + right`.

### Rule 5: editing creates a candidate first

Before user acceptance:

- current canonical project snapshot is unchanged;
- fixture working-tree source is unchanged.

A source edit becomes a candidate migration based on an exact base snapshot.

### Rule 6: accepted change uses shared apply/write-back infrastructure

Do not write the file from a React click handler or TUI widget.

Use application/change/projection/filesystem infrastructure and expose effect status.

### Rule 7: tests must prove user outcomes

An HTTP `200`, `status=imported`, rendered route, reducer action, or database row is not enough.

Use the exact WEB-GOLDEN and TUI-GOLDEN outcome assertions from Level 2.

### Rule 8: deterministic CI

No network model service.

No external Cargo dependencies in the golden fixture.

No edits to Scriberig's own tracked source during E2E.

### Rule 9: do not claim partial success as completion

If a required golden scenario does not pass, this master task remains incomplete.

Older `[x]` checklists prove only their historical subsystem scope.

## Golden Fixture

Task `117` must establish/reuse one deterministic fixture with this semantic shape:

```rust
pub mod math {
    pub struct Calculator;

    impl Calculator {
        pub fn add(&self, left: i32, right: i32) -> i32 {
            left + right
        }
    }
}
```

The target accepted replacement is:

```rust
left.saturating_add(right)
```

If an existing fixture already has these exact stable anchors and is appropriate for both web and native E2E, reuse it instead of duplicating it.

All product E2E tests copy the fixture into a fresh temp directory.

## Stop Conditions

Do not work around these conditions. Fix them.

- If import succeeds but project root cannot be resolved: fix public project workspace contract.
- If `Calculator`/`add` cannot be named without UI parsing: fix shared semantic summaries/adapter data.
- If source cannot be rendered from semantic selection: fix projection/application operation.
- If edit can only directly overwrite file: fix candidate/reconciliation path.
- If migration cannot expose source diff/validation: fix shared change/review result.
- If apply advances DB but filesystem effect is invisible: expose materialization/effect status and recovery.
- If agent can only chat without producing a shared candidate: connect agent tools to the same change operation.
- If product tests require a real network model: add/reuse deterministic provider.
- If E2E is flaky because of sleeps: wait on explicit operation/DOM/PTY state instead of relaxing assertions.
