## 1. Goal

Migrate domain source renderers to consume one exact resolved style, per
`design/level-2/034. projection style resolution loss-aware reconciliation and
cross-surface contracts.md` (§29 ordered work, migration step "migrate one
domain renderer (Rust) to prove the contract").

Required outcome: the same semantic source renders under at least two different
exact styles, semantic identity is unchanged, and style choice never changes
canonical state.

---

## 2. Architectural Constraints

- Style meaning belongs to the domain. The shared layer resolves; it does not
  format.
- A domain declares its style schema, normalizes and merges style input, supplies
  an exact default, and states fidelity through `ProjectionStyleAdapter`.
- Unsupported style values are refused with a structured diagnostic, never
  approximated.
- Style changes never create a candidate, migration, or change operation.

## 3. Implemented: Rust Domain

- `crates/domains/scriberig-domain-rust/src/style.rs`
  - `RustStyle { indent, indent_width, blank_lines_between_items }` with a
    canonical text encoding, `validate`, and a `Default` equal to the output the
    renderer produced before styles existed.
  - `RustStyleAdapter` implementing `ProjectionStyleAdapter` for kind `rust`:
    three-property schema, exact default style, field-validating normalize,
    field-level merge, and fidelity for one exact resolved style.
- `crates/domains/scriberig-domain-rust/src/render.rs`
  - `render_with_style(file, style)` renders through the style; `render(file)`
    delegates to the canonical style for compatibility.
- `crates/domains/scriberig-domain-rust/tests/style_rendering.rs` (11 tests):
  two exact styles produce different text; every supported style re-parses to the
  identical semantic file; an unsupported width is refused by both renderer and
  adapter with a named-field diagnostic; unknown and repeated fields are refused;
  merge overrides only named fields; the declared default equals the domain default and
  is lossless-editable; an unreadable style is read-only; the schema is declared
  only for the Rust kind; a resolved style renders with no further lookup.

Verified 2026-10-23 on Linux: `cargo test -p scriberig-domain-rust`,

## 5. Preserved Gap: Rust Function Signature Fidelity (not task-152 scope)

The Rust model records a function as a name, attribute tokens, typed parameter
patterns, and body statement tokens (`RustFunction` in
`crates/domains/scriberig-domain-rust/src/syntax.rs`), and the renderer emits
exactly those fields (`crates/domains/scriberig-domain-rust/src/render.rs`).
Every other signature category a top-level `fn` can carry disappears at parse
time: the return type, visibility, `const`/`async`/`unsafe`, the generic
parameter list, and a `where` clause. Measured at HEAD `bce4442` by parsing and
rendering one module of such functions through a throwaway probe (run, recorded,
deleted; nothing was committed):

- `pub fn plain(a: u64) -> u64 { a }` renders `fn plain(a: u64) {` then `    a`;
- `pub(crate) async fn wrapped(a: u64) -> Result<u64, ()> { Ok(a) }` renders
  `fn wrapped(a: u64) {` then `    Ok (a)`;
- `fn generic<T: Clone>(v: T) -> T { v }` renders `fn generic(v: T) {`.

Struct, enum, and impl items are carried as verbatim token streams, so a method
signature inside an `impl` keeps its `pub` and its `-> u64`. The loss is specific
to the structured `RustItem::Function` path, and it is the same in both
directions: `parse` omits those categories and `render` therefore has none to
emit.

This is not style behaviour and it is not task-152 work:

- It predates styles and is identical under every style, so the task-152 claims
  stand. `every_supported_style_parses_back_to_one_semantic_file` compares one
  `RustFile` model with itself, and its `SOURCE` really does carry `-> u64`: the
  category is absent from both sides of the comparison, which proves style does
  not move semantic identity, not that the model is source-complete.
- The task-152 outcome is unaffected and still proven: two exact styles render
  one semantic file as different bytes, every supported style re-parses to the
  identical semantic model, and style choice never changes canonical state.
- What task 152 does **not** claim, and what would be false if a reader
  imported it that way, is that the Rust renderer reproduces Rust source. The
  declared Rust entity schema (`RUST_ENTITY_TYPES` in `src/schema.rs`) names no
  return-type, visibility, or generic category, so
  `RustStyleAdapter::classify` reporting `LosslessEditable` is a statement about
  the style round trip over the categories the kind models — matching
  `ProjectionFidelity`, which is defined over "canonical categories the kind
  supports" in `crates/sr-projection/src/fidelity.rs` — and not about
  source-text completeness.

Disposition: task 156. That task owns loss-aware reconciliation, baseline
artifact retention, and the decision about representations that omit canonical
content (level-2/034 §28 migration steps 6 and 7). No `design/level-3/156.`
sheet exists at this head — level-2/034 §29 names the task — so this section, not
a checked box, is where the gap has to travel into it. Task 152 leaves the Rust
semantic model untouched so the style contract is not entangled with a change
that moves the rendered bytes of every Rust projection at once.

Two consequences task 156 must carry, stated here so they are not lost:

- The Rust adapter accepts these functions silently, while the ECMAScript domain
  refuses every node outside its documented subset with a structured `EcmaError`
  (`crates/domains/scriberig-domain-ecma/src/extract/mod.rs`). Task 156 must
  either record the dropped categories or refuse them; silently dropping them
  cannot stay `LosslessEditable` once a projection is opened for editing.
- Nothing can write a Rust file through this renderer today, so no surface loses
  a return type in the product yet. `ApplicationService::materialize_projection`
  is exercised only by `crates/scriberig-app/tests/projection_materialization.rs`,
  whose `StyleEchoAdapter` echoes the style bytes rather than rendering Rust, and
  no composition installs a Rust `ProjectionAdapter` or builds a
  `SyncCoordinator` (in product code `SyncCoordinator` appears only as a
  parameter of that operation). Materializing real Rust files must stay gated
  until task 156 resolves this gap.

## 5b. Style Seams As Wired Today

The wiring reconnaissance that this section held described the pre-slice state
and is closed by §4; its line references (`main.rs:116,197`,
`tui_command.rs:129`, `server/src/lib.rs:191`, `import.rs:68,218`) no longer

  (`crates/scriberig-app/src/service_render_style.rs`) turns a configured or
  exact selection into the `Applied` variant with recorded provenance, `execute`
  resolves before dispatch, and provider-side `resolve_render`
  (`crates/scriberig-app/src/operation_backend.rs`,
  `crates/scriberig-app/src/composite_backend.rs`) refuses an unresolved
  selection.
- Domain adapters are installed by `domain_projection_style_configuration`
  (`apps/scriberig/src/projection_style_composition.rs`) for `rust`,
  `javascript`, and `typescript`, and that one helper is called at every product
  composition site: `apps/scriberig/src/main.rs:96` (serve, handed to

  (embedded run), and `apps/scriberig/src/tui_command.rs:132-133` (TUI).
  `crates/scriberig-server/src/lib.rs:210,234` receives the configuration instead
  of building its own.
- Filesystem materialization takes the exact value from its caller:
  `SyncCoordinator::render_managed_projection_with_style`
  (`crates/sr-projection-fs/src/import.rs`).
- What is still missing is a remote surface that can name a selection.
  `crates/scriberig-server/src/server_commands.rs:59` decodes the Rust
  `RenderRequest` shape verbatim, but `scriberig-protocol` declares only
  `OperationKind::Render` with no render payload schema
  (`crates/scriberig-protocol/src/operation.rs`), the web client posts an
  untyped payload (`web/packages/client/src/semantic-client.ts:109`), and no CLI
  path names a style. That is exactly the task-156 parity item.
