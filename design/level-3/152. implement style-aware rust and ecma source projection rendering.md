# Implement Style-Aware Rust and ECMAScript Source Projection Rendering

## Status

In Progress.

The Rust slice is implemented and verified: the Rust domain owns an exact source
style, implements the shared projection style seam, and renders one semantic file
under several exact styles without changing semantic identity.

The ECMAScript slice is not implemented: `scriberig-domain-ecma` currently
provides only a parser (`parse` in `src/lib.rs`), so there is no source renderer
to make style-aware. A deterministic ECMA renderer is a prerequisite for the
second half of this task.

## 1. Goal

Migrate domain source renderers to consume one exact resolved style, per
`design/level-2/034. projection style resolution loss-aware reconciliation and
cross-surface contracts.md` (§29 ordered work, migration step "migrate one
domain renderer (Rust) to prove the contract").

Required outcome: the same semantic source renders under at least two different
exact styles, semantic identity is unchanged, and style choice never changes
canonical state.

---

## 2. Architectural Constraints

- Style meaning belongs to the domain. The shared layer resolves; it does not
  format.
- A domain declares its style schema, normalizes and merges style input, supplies
  an exact default, and states fidelity through `ProjectionStyleAdapter`.
- Unsupported style values are refused with a structured diagnostic, never
  approximated.
- Style changes never create a candidate, migration, or change operation.

---

## 3. Implemented: Rust Domain

- `crates/domains/scriberig-domain-rust/src/style.rs`
  - `RustStyle { indent, indent_width, blank_lines_between_items }` with a
    canonical text encoding, `validate`, and a `Default` equal to the output the
    renderer produced before styles existed.
  - `RustStyleAdapter` implementing `ProjectionStyleAdapter` for kind `rust`:
    three-property schema, exact default style, field-validating normalize,
    field-level merge, and fidelity for one exact resolved style.
- `crates/domains/scriberig-domain-rust/src/render.rs`
  - `render_with_style(file, style)` renders through the style; `render(file)`
    delegates to the canonical style for compatibility.
- `crates/domains/scriberig-domain-rust/tests/style_rendering.rs` (10 tests):
  two exact styles produce different text; every supported style re-parses to the
  identical semantic file; an unsupported width is refused by both renderer and
  adapter with a named-field diagnostic; an unknown field is refused; merge
  overrides only named fields; the declared default equals the domain default and
  is lossless-editable; an unreadable style is read-only; the schema is declared
  only for the Rust kind; a resolved style renders with no further lookup.

Verified 2026-10-23 on Linux: `cargo test -p scriberig-domain-rust`,
`cargo clippy -p scriberig-domain-rust --all-targets`,
`python3 tools/lint_repo.py`.

## 5. Known Renderer Gap (not style-related)

The Rust renderer emits no return type for functions, and the parser records
none, so `-> u64` is lost across parse/render today. This is a semantic-fidelity
gap in the Rust syntax model, tracked here so it is not mistaken for style
behaviour; the style tests assert indentation, not the full text.

## 5b. Wiring Reconnaissance (for the next slice)

Where the resolved style has to be injected, as found on this branch:

- The universal application render request is `scriberig_app::RenderRequest {
  snapshot, view }` (`src/request.rs`) and carries **no style**. The shared
  `sr_projection::RenderRequest` already requires an exact `ResolvedStyle`.
- The gap is therefore in the request model plus the operation path:
  `resolve_render` in `src/operation_backend.rs` and `src/composite_backend.rs`
  only resolves the snapshot selector, and those helpers run over an
  `OperationProvider`, which cannot see `ApplicationService::projection_style`.
  Threading style into the render operation needs: a style field (or explicit
  style-selection variant) on `RenderRequest` in `scriberig-app`, `scriberig-protocol`,
  and the web/TUI callers, plus a resolution step with authority to read the
  style configuration for the caller's purpose.
- Host composition sites that would install a domain style adapter:
  `apps/scriberig/src/main.rs:116,197`, `apps/scriberig/src/tui_command.rs:129`,
  and `crates/scriberig-server/src/lib.rs:191` — each builds
  `ApplicationService::new(backend)` today and would call
  `with_projection_style_configuration(...)`. None of them currently depends on
  `scriberig-domain-rust`, so the adapter install belongs with the domain
  registry those compositions already use.
- Filesystem materialization builds its own request in
  `crates/sr-projection-fs/src/import.rs:68,218`; that is where the workspace
  materialization style must be resolved (purpose `SharedMaterialization`) so
  materialized files never pick up personal state.
