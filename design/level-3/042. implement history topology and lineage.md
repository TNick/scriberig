# Agent Task: Implement History Topology and Lineage

## Goal

Implement explicit change-history topology for `sr-change` so history is represented as a DAG of immutable snapshots and migrations rather than inferred from write order.

This task does not implement branch promotion, merge algorithms, or domain-specific history views.

## Read before editing

Read:

1. `design/level-1/005. changes migrations branches and merge.md`, especially sections 3, 12, 13, 28, 33, 34, 40, 41, 42, and 49.
2. `design/level-2/002. change history and merge crate design.md`.
3. The completed migration/provenance implementation from Level 3 task 002.
4. `sr-store` ancestry/history capabilities.

## Files to modify

Primary files:

```text
crates/sr-change/src/history.rs
crates/sr-change/src/migration.rs
crates/sr-change/src/query.rs
crates/sr-change/src/lib.rs
```

Tests may be placed beside the code or in `crates/sr-change/tests/change_conformance.rs` following repository convention.

## Required concepts

Implement explicit representations for:

- a committed migration reference;
- migration parent relationships;
- base and result snapshot relationships;
- merge history with more than one parent line;
- lineage of an entity revision through migrations;
- semantic replacement lineage such as `replaces`, `split_into`, `merged_from`, `supersedes`, or `extracted_from` when represented by higher layers.

Do not encode topology using timestamps or integer insertion order.

## History access abstraction

If migration persistence is not already part of `sr-store`, define a backend-independent read abstraction in `sr-change` for history records.

It must be possible for query/merge code to request:

```text
migration by id/reference
migrations producing a snapshot
migrations touching an entity
parents of a historical transition
children/descendants where the implementation can provide them
```

Do not add SQL or concrete memory-store internals to `sr-change`.

If durable persistence of migration objects requires a new generic storage capability, add the smallest backend-independent trait extension and conformance requirements. Do not bypass `sr-store`.

## Snapshot ancestry

Implement reusable helpers for ancestry operations required later by merge:

```text
is_ancestor(candidate, descendant)
ancestors(snapshot)
common_ancestor(left, right)
```

Prefer storage-provided ancestry indexes when exposed, but keep correctness independent of optional acceleration indexes.

If multiple common ancestors are possible, document and implement the deterministic rule for choosing the merge base or return enough information for the merge layer to decide. Do not silently pick based on timestamp.

## Entity lineage

Provide a queryable lineage model for one `EntityId` across migrations.

It should expose facts such as:

```text
revision before
revision after
migration that introduced the transition
snapshot where the new revision became visible
branch/workspace provenance if available
```

Do not treat moving an entity as creating unrelated identity when migration data says continuity is preserved.

## State equality versus history equality

Add helpers or documentation that preserve this distinction:

- equal `SnapshotId` means equal canonical state;
- equal snapshot state does not imply identical historical path.

Tests must include two histories that converge to the same snapshot state through different transitions.

## Creation and removal

History traversal must preserve the difference between:

```text
entity absent in result snapshot
```

and:

```text
physical revision destroyed
```

Never assume semantic removal makes old revisions unreadable.

## Tests

Add tests for:

- linear history `S1 -> S2 -> S3`;
- sibling history `S1 -> S2` and `S1 -> S3`;
- merge topology with two parent lines;
- common ancestor discovery;
- history queries unaffected by insertion order;
- entity lineage across multiple revision replacements;
- semantic removal while old snapshot still resolves the old revision;
- two distinct histories converging to the same current snapshot;
- move/replacement lineage retaining semantic continuity when explicitly recorded.

## Constraints

- No timestamps as authoritative topology.
- No backend-specific queries.
- No textual file history assumptions.
- No mutation of committed migration records.
- Do not implement merge resolution in this task.
