# Apply Licensing Metadata to Web Packages

## Objective

Apply the platform/product licensing split to every existing TypeScript/JavaScript package and application manifest without changing application behavior.

Read before editing:

1. `design/level-1/014. extensibility ecosystem and licensing.md`
2. `design/level-2/001. licensing artifacts package metadata and notices.md`
3. `design/level-2/001. web workspace packages and integrated editor.md`, if present
4. every `package.json` that will be modified

This task is metadata-only.

---

## Preconditions

Run this task only after web/package manifests exist.

If the repository contains no relevant `package.json` files yet:

- do not create placeholder packages;
- do not create an empty web workspace solely for licensing;
- report that the task is not yet applicable.

Ignore package-manager cache directories and generated dependency trees such as `node_modules`.

---

## Files to Inspect

Inspect the web workspace root and all workspace package/application manifests, including patterns such as:

```text
web/package.json
web/packages/*/package.json
web/apps/*/package.json
```

Also inspect any other first-party package manifests included by the workspace configuration.

Modify only first-party package manifests that need licensing metadata added or corrected.

Do not edit TypeScript/React source files in this task.

---

## Classification Rule

Use architectural responsibility, not framework or directory name, to classify each package.

Default rule:

```text
Reusable package -> Apache-2.0
Complete integrated Scriberig product/application -> AGPL-3.0
```

Do not assume that every package under `apps/` is AGPL or that every package under `packages/` is Apache without checking its purpose.

---

## Apache-2.0 Web Packages

Reusable web/platform packages should normally be Apache-2.0.

This includes responsibilities such as:

- protocol types;
- transport clients;
- client-side semantic models;
- framework bindings;
- headless editor/navigation controllers;
- selection, command, history, diff, and editing behavior intended for reuse;
- neutral reusable components;
- reusable MUI-based component libraries;
- reusable agent UI abstractions that do not embed the integrated Scriberig runtime.

MUI usage does not make a package AGPL.

React usage does not make a package AGPL.

Being consumed by the complete Scriberig editor does not make a reusable package AGPL.

---

## AGPL-3.0 Web Applications

The complete reference Scriberig editor application should normally be AGPL-3.0.

An application belongs on the AGPL side when its primary role is to operate the integrated Scriberig product rather than provide reusable UI infrastructure.

Product-specific workflows embedded only in the complete editor should follow the product license.

If product-specific behavior has been placed in a package presented as a reusable library, do not solve the architectural mistake by blindly relicensing the library. Report the boundary problem so the product-specific behavior can be separated later.

---

## Package Metadata

Every distributable first-party package must declare its license in `package.json` using the package ecosystem's normal license metadata.

Private first-party packages should also declare a license when doing so clarifies the product/platform boundary.

Do not use a dual-license expression unless a separate design explicitly assigns both licenses to that package.

Do not add publication configuration merely to expose license information.

Do not alter `private`, `exports`, `files`, `type`, scripts, or dependency fields unless another task requires it.

---

## Expected Reference Workspace Classification

If the workspace contains the reusable package structure described by the current web design, classify these responsibilities as Apache-2.0:

```text
protocol
client
model
editor-core
react bindings
neutral components
components-mui
```

Classify the complete reference Scriberig editor application as AGPL-3.0.

Use actual package purpose as the final authority. Do not create missing packages merely because they are named in a design document.

---

## Dependency-Direction Check

While reviewing package metadata, inspect first-party package dependencies.

The expected direction is:

```text
Apache reusable web libraries
             ^
             |
AGPL integrated editor application
```

The reference editor may depend on reusable Apache packages.

Reusable Apache packages must not depend on the complete AGPL editor application or product-only code.

If a reverse dependency exists:

- do not hide it with a license change;
- do not move source in this task;
- report the architectural violation.

---

## Preserve Existing Package Behavior

Do not change:

- package names;
- versions;
- dependencies;
- peer dependencies;
- workspace ranges;
- build scripts;
- test scripts;
- TypeScript configuration;
- bundler configuration;
- package exports;
- publication settings.

The only expected modification is license metadata, except for formatting needed to preserve valid JSON.

---

## Verification

After editing:

- enumerate all first-party web workspace packages/applications;
- verify each applicable manifest has the intended license declaration;
- verify reusable packages are Apache-2.0;
- verify the complete reference editor is AGPL-3.0;
- verify MUI reusable libraries remain Apache unless they contain integrated product behavior;
- verify no reusable package depends on the integrated editor application;
- run the package manager command needed to verify workspace/package manifests are valid;
- if the existing web workspace has typecheck/build checks, run the lightweight normal checks to ensure metadata edits did not break package parsing.

---

## Do Not Do

Do not:

- create the web workspace;
- create missing packages;
- move source files;
- add dependencies;
- change package visibility;
- add source-file SPDX headers;
- mark all web code AGPL;
- mark the complete editor Apache for convenience;
- assume MUI is a product-only layer;
- introduce a new component library;
- publish packages;
- add protocol or UI functionality.
