Planned.

## 3. Architectural Constraints

Preserve these rules:

```text
lossy projection absence != semantic deletion

editable reconciliation
  = exact baseline semantic state
  + exact baseline representation
  + exact baseline style
  + current canonical state
  + edited representation

if loss-aware reconciliation is not proven
  -> lossy projection is read-only

TUI/web controls
  -> shared application intent
  -> shared style resolver
  -> exact projection render/reconcile
```

Do not:

- hide baseline/style identity in an untyped metadata bag when correctness depends on it;
- infer deletion of style-hidden entities from parser absence;
- let a new user preference reinterpret an edit created under an old style;
- create a TUI-specific source-style persistence/resolution system;
- create a parallel web source-style semantics layer;
- use `rpi-tui` theme/style objects as canonical source projection styles;
- let UI edits bypass candidate/migration/validation/conflict/promotion semantics.

## 4. Introduce a Typed Exact Reconciliation Baseline

Refine the current reconciliation boundary with a typed baseline equivalent in responsibility to:

```text
ReconciliationBaseline
  base semantic state/snapshot
  semantic scope
  projection specification
  exact resolved style
  renderer version
  adapter version
  exact rendered output reference/hash
  exact projection fidelity
  optional adapter mapping/loss evidence
```

Update `ReconciliationContext` or its current replacement to contain this baseline plus current canonical state and any truly auxiliary metadata.

Do not duplicate base/scope/specification fields indefinitely after callers are migrated unless compatibility requires a temporary transition.

The type must make it difficult to accidentally reconcile edited bytes without knowing the style/renderer/output that produced the edit baseline.

---

## 5. Retain Exact Baseline Output

For editable managed projections, synchronization state must identify an exact retrievable baseline representation, not only a hash when reconciliation needs content.

Prefer content-addressed projection artifact storage or an existing immutable blob/content facility if one already fits.

Requirements:

- exact bytes can be retrieved for the baseline after canonical state advances;
- baseline identity remains valid after user style preferences change;
- baseline identity remains valid after materialization policy changes;
- the stored reference is bound to style/renderer/adapter/base-state metadata;
- hashes remain available for dirty/self-write detection;
- old baseline content is retained according to existing reachability/GC policy rather than an ad-hoc permanent leak.

Do not make baseline bytes canonical semantic source knowledge merely because they are retained for synchronization evidence.

---

## 6. Add Optional Projection Mapping/Loss Evidence

Allow domain renderers/adapters to attach exact output-bound derived evidence where needed.

Examples:

```text
rendered token/range -> semantic entity/revision
hidden semantic entity/category set
structural anchors used for reconciliation
adapter-specific source-map data
```

This evidence must be bound to the exact baseline state/style/renderer/output.

Use semantic handles for durable identity. Do not persist TUI rows, editor line numbers, parser pointers, or other unstable presentation identities as canonical mapping keys.

An adapter that does not need mapping metadata may omit it.

## 7. Implement Loss-Aware Reconciliation for One Proven Safe Style

Choose the narrowest domain/style combination from task 155 that can safely demonstrate loss-aware editing.

A preferred example is an ECMAScript/TypeScript style that hides **only ordinary comments** while preserving all compiler/tooling/license/directive categories the domain model can reliably identify.

If task 155 determined that no current domain model can distinguish safely hideable content, do not force a lossy editable implementation. In that case:

- keep all lossy styles read-only;
- implement the typed baseline/fidelity infrastructure;
- add tests proving read-only enforcement;
- leave the loss-aware-editable checklist items unchecked and record the blocking semantic-model gap.

Never implement unsafe comment stripping merely to complete this task.

## 8. Required Loss-Aware Behavior

For a safely supported lossy style, prove this scenario:

```text
canonical base B
  ordinary comment C
  statement S = foo()

baseline style H
  hides C

baseline rendered bytes
  foo()

user edits visible representation
  bar()

current canonical state D
  still contains C

reconciliation result
  preserves C
  proposes semantic change S: foo() -> bar()
```

The adapter must identify that `C` was absent because the baseline style omitted it, not because the user deleted it.

Also distinguish a represented element that was visible in baseline output and is actually removed by the user.

When evidence is insufficient, return ambiguity/conflict rather than inventing lineage or deletion.

---

## 9. Preserve Three-Way Reconciliation

Loss-aware handling does not replace the existing three-way model.

Reconciliation still reasons over:

```text
B = last synchronized semantic baseline
D = current canonical state
F = current edited external/view representation
```

with additional exact evidence:

```text
B_rendered
B_style
B_renderer
B_mapping/loss metadata
```

Concurrent canonical changes between `B` and `D` must still participate in ordinary merge/conflict logic.

Do not special-case lossy styles by overwriting current canonical state with a candidate parsed from `F`.

---

## 10. Style Changes During an Active Edit

An active edit remains bound to its baseline style.

Implement safe behavior equivalent to one of:

```text
reconcile under old baseline -> rerender new style
```

or a typed explicit rebase operation if the current editor/application architecture supports it safely.

Do not silently switch the baseline style while dirty edits exist.

For managed filesystem materialization, a deliberate materialization-style change must:

1. render from canonical semantic state with the new resolved style;
2. atomically write using the normal projection sync path;
3. record exact new output/style/renderer metadata;
4. establish a new synchronization baseline only after successful write.

Personal user preference changes must not trigger this shared-file path.

## 11. Expose Shared Protocol/Client Models

Where remote/web/TUI-remote behavior requires transport, extend the existing protocol/client models with the minimum shared data for:

```text

```

Follow existing request/result/event/versioning conventions.

Do not expose raw internal trait objects or arbitrary unvalidated style bytes to UI code when a structured descriptor/reference suffices.

Ensure embedded/local and remote paths produce equivalent semantic results.

## 12. TUI Integration Must Follow the Current RPI Target

Level-2 032 supersedes the old final ownership target from Level-2 031.

Implement the Scriberig-specific source-style UI as a custom semantic component/adapter on the **current upstream `rpi-tui` component/runtime architecture**.

Conceptual flow:

```text
upstream rpi-tui setting/select/overlay primitives
  -> Scriberig source projection style intent
  -> shared application operation
  -> style resolver
  -> exact render/fidelity result
  -> Scriberig projection/source component renders result
```

Upstream remains owner of:

```text
terminal lifecycle
input normalization
focus
overlays
selection/settings widgets
theme/colors/layout primitives
scrolling/editor primitives
```

Scriberig remains owner of:

```text
which semantic scope is projected
which source style/profile is selected for that user/view
purpose-aware resolution
projection fidelity
semantic edit/reconciliation behavior
materialization policy
```

Do not add a new Ratatui shell, independent key/event framework, independent theme system, or local TypeScript/Rust formatter settings engine.

If generic settings UI is missing upstream, follow the upstream-first rule from Level-2 032.

## 13. Keep Terminal Theme and Source Style Distinct in UX/State

The UI must not conflate:

```text
Terminal theme
  dark/light/colors/emphasis/chrome
```

with:

```text
Source projection style
  indentation/wrapping/comment visibility/etc.
```

Changing the terminal theme must not alter rendered source bytes or projection cache identity.

Changing source projection style may alter source projection bytes/cache identity but must not change terminal theme state.

Add a regression test at the shared/TUI presentation boundary proving this independence.

```text

see whether the resulting projection is editable/read-only
```

Exact slash commands, overlays, palette actions, or settings placement must follow the current RPI product design at implementation time. Do not freeze obsolete task-031 UI shapes into this task.

Changing these personal view settings must not:

- move reply/navigation/coordinator cursors;
- alter branch/session topology;
- rerun model invocations;
- change plan scheduling;
- rewrite shared files;
- create semantic source migrations.

## 15. Web Reusable Package Integration

Expose the same semantics through existing reusable web layers.

Follow the current direction:

```text
protocol -> client -> model -> react/editor/components -> app
```

Add reusable model/hooks/components only at the layer that owns them.

A third-party web client should be able to:

```text
query style schema/effective style/fidelity
select a user/view style
request/render a projection
know whether editing is allowed
```

without importing `web/apps/scriberig`.

Opinionated MUI controls may wrap reusable semantics in the integrated app/library, but MUI must not own precedence or language-style meaning.

## 18. Agent and Model Context Safety

If any current agent inspection/context path includes rendered source projections, ensure it can carry exact projection identity/style metadata where required for reproducibility.

A personal UI style change must not mutate historical effective model requests.

If a new invocation intentionally includes a differently styled source projection, the resulting effective context is different and should participate in the normal context fingerprint/continuation validity logic.

Do not add style preferences to provider requests when no rendered styled projection or other execution-semantic input depends on them.

## 22. Completion Result

When this task is complete, Scriberig should support the architectural scenario that motivated this design:

```text
one canonical TypeScript/Rust semantic program
        |
        +-- User A personal source projection
        |     e.g. 2 spaces, comments shown
        |
        +-- User B personal source projection
        |     e.g. 4 spaces, safely hideable comments omitted
        |
        +-- shared repository materialization
              repository/workspace policy
```

All three representations remain tied to exact declared styles and one semantic source of truth. Personal representation changes remain presentation/configuration behavior, shared materialization remains deterministic, and any editable lossy representation preserves canonical content that its style intentionally did not show.
