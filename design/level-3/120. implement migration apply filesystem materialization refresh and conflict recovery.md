# Implement Migration Apply, Filesystem Materialization, Refresh, and Conflict Recovery

## Objective

Complete the human change path by applying a validated candidate through shared migration semantics, materializing the accepted Rust projection to the project's working tree, refreshing the active workspace to the authoritative successor snapshot, and preventing silent overwrite of external edits.

This task starts with a validated candidate from task `119`.

Required successful outcome:

```text
base source on disk:       left + right
candidate source:          left.saturating_add(right)
user accepts
canonical project advances to successor snapshot
working tree src/lib.rs contains left.saturating_add(right)
web/TUI refresh to successor snapshot
history shows the transition
```

Required conflict outcome:

```text
candidate created from base
external process changes src/lib.rs
user attempts accept/materialize
external content is NOT silently overwritten
product reports stale/conflict/effect state
recovery is explicit
```

## Core Invariants

### 1. Apply uses exact base compare-and-swap

The accepted candidate carries an exact base project snapshot.

Application must fail as stale/conflicted if the project's authoritative current snapshot no longer equals the candidate's required base, unless existing merge/rebase semantics explicitly create a new reviewed candidate.

Do not silently retarget the migration to a newer snapshot.

### 2. Apply is an application operation

Web/TUI call the shared public application apply operation.

Do not update project snapshot tables from product code.

Do not let product code manually create successor snapshot IDs.

### 3. Filesystem materialization is shared projection infrastructure

Do not use `fs.writeFile` in the web app, terminal renderer code, or agent runtime.

The application/projection/filesystem layer owns materialization and safety checks.

### 4. External filesystem effect is observable

The final operation/result must make it possible to distinguish at least:

```text
canonical apply failed
canonical apply succeeded + materialization succeeded
canonical apply succeeded + materialization failed/requires recovery
candidate rejected as stale/conflicting before unsafe overwrite
```

Do not report a generic `completed` result that hides a failed required write-back.

### 5. No silent overwrite

A source file whose expected base digest/content changed externally after candidate creation must not be silently replaced.

## Decide and Preserve Existing Effect Ordering

Database canonical-state promotion and filesystem write cannot be one atomic transaction.

Before implementing, inspect the repository's chosen external-effect receipt/materialization design.

Use that design rather than inventing a second transaction protocol.

The accepted implementation must document in code/tests which of these conceptual orders it uses:

```text
A. validate expected filesystem state
   -> canonical compare-and-swap apply
   -> materialize projection
   -> record effect receipt/status

or

B. stage/materialize through existing safe protocol
   -> canonical apply/finalize
   -> record effect receipt/status
```

Either can be acceptable only if existing architecture supports it and failure recovery is explicit.

Do not claim database + filesystem are fully atomic.

## Filesystem Preconditions

Before writing `src/lib.rs`, verify through shared filesystem projection rules:

- active/project identity matches candidate target;
- target relative path is `src/lib.rs` or another registered owned path;
- canonicalized target remains under project root;
- path traversal is rejected;
- symlink escape is rejected according to existing security design;
- current filesystem digest/state matches expected projection/base state unless reconciliation has produced a new candidate;
- target ownership/projection identity matches the accepted candidate;
- write is limited to intended file(s).

Do not trust a client-supplied absolute path.

---

## Atomic Local Write

Use existing atomic I/O helper/contract from filesystem projection infrastructure.

Expected successful pattern is equivalent to:

```text
write temporary sibling/staging file
flush as required by existing durability contract
atomic rename/replace
record resulting digest/effect receipt
```

Do not truncate the target in place if the existing design requires atomic replacement.

Preserve required permissions/metadata according to existing projection design.

## Web Apply Behavior

In `MigrationReviewView` or the reusable review primitive:

1. Apply is available only for validated, non-stale candidate;
2. clicking Apply invokes public application/client operation;
3. show operation progress/status;
4. on canonical+materialization success, call shared runtime `refreshActiveProject()` equivalent;
5. resolve/preserve selected `add` entity against successor snapshot when possible;
6. show successor snapshot/current status;
7. Projection reload shows accepted source;
8. History route shows migration/snapshot transition;
9. close/reject after successful apply must not roll state back.

If materialization fails after canonical apply, show a distinct error/out-of-sync state with recovery information. Do not simply display `Migration applied` while source file is unchanged.

## Post-Apply Selection Resolution

When `add` retains stable entity identity:

- keep its `EntityId` selected;
- replace exact snapshot context with successor current snapshot only after authoritative refresh;
- refresh object/projection caches keyed by snapshot;
- do not reuse base-snapshot source text as if current.

If identity no longer exists, clear selection and show `selection no longer exists in current snapshot` or equivalent explicit state.

## Stale Canonical Snapshot Scenario

Test separately from filesystem conflict.

1. create candidate against base snapshot A;
2. advance the project canonical snapshot to B through another valid operation;
3. attempt to apply candidate based on A;
4. assert structured stale/conflict rejection;
5. assert project remains B, not candidate result;
6. assert candidate is not silently rebased;
7. product shows stale state and requires new/reconciled candidate.

---

## External Filesystem Conflict Scenario

Required sequence:

1. import fixture at base snapshot;
2. create valid saturating-add candidate;
3. before candidate apply/materialization, modify live temp `src/lib.rs` externally to a known marker, e.g. add a comment:

```rust
// external edit
```

while retaining or altering the expression as needed for deterministic digest mismatch;
4. attempt accepted change;
5. shared filesystem layer detects source mismatch before unsafe overwrite or records conflict according to projection sync design;
6. externally edited file remains present and is not replaced by stale candidate output;
7. operation/product reports conflict/stale/reconciliation-required state;
8. recovery path allows rescan/reconcile/new candidate rather than force-overwriting by default.

The test must read the file after the failed/conflicted operation and assert the external marker still exists.

---

## Materialization Failure Scenario

Create a deterministic failure without relying on platform-specific permission hacks when possible. Examples:

- inject a filesystem implementation/test fault at the shared I/O boundary;
- replace target parent with controlled invalid state in a test fixture;
- use an existing fault-injection hook.

Assert:

- operation distinguishes canonical and external-effect state;
- receipt/recovery record exists when architecture requires it;
- product can inspect/report failure;
- retry/recovery follows existing design;
- no unrelated file is changed.

Do not add production-only global environment flags merely for testing if dependency injection/fault abstraction already exists.

---

## Multi-Project Isolation

With projects A and B in one database:

- candidate/apply for A advances only A root;
- only A filesystem path is targeted;
- B snapshot/root/files remain unchanged;
- events identify A sufficiently for client A to refresh and client B not to adopt A state.

Add a conformance test for this.
