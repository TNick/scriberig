# Implement Projection Edit Candidate Review and Validation

## Objective

Turn a real Rust source projection edit into a reviewable, validated candidate migration without changing current canonical state or the working tree before acceptance.

This task starts from the named `add` selection and source projection delivered by task `118`.

Required human edit:

```text
left + right
```

becomes:

```text
left.saturating_add(right)
```

Before the user presses Apply/Accept:

- the active project's current canonical snapshot must still be the base snapshot;
- the temporary fixture's `src/lib.rs` on disk must still contain `left + right`;
- a candidate/migration with exact base snapshot, source/semantic diff, and validation results must exist.

This is prerequisite `119`. Do not implement direct filesystem write-back here; that belongs to task `120`.

## Shared Candidate Creation Contract

### 1. Input

A projection edit request must identify at least:

```text
project/workspace identity
projection identity
exact base snapshot
source-relative path
edited projection text or a structured semantic edit equivalent
provenance / initiating surface
```

When editing a selected region rather than an entire file, include enough mapping/base information to reject a stale or mismatched range.

Do not accept a request that means "edit whatever is current now" without an exact base snapshot.

### 2. Reconciliation

Use the shared Rust projection/reconciliation implementation to parse the edited representation and derive semantic changes.

Do not create a web-only text patch format that bypasses semantic reconciliation.

Do not create a TUI-only direct source patch path.

Reconciliation output must become the repository's normal migration/proposal representation.

### 3. Candidate state

Candidate creation must not advance the project's current root.

It may create immutable candidate snapshot/revisions according to existing change architecture, but the project current snapshot remains base until apply.

### 4. Candidate identity and provenance

Candidate/migration must have stable identity addressable by web/TUI/agent/operation results.

Record provenance sufficient to distinguish at least human web, human TUI, agent, or other caller according to existing provenance model.

Do not use provenance as a separate mutation path.

---

## Diff Contract

For the golden edit, the review model must expose both semantic and source-representation information where available.

Required user-observable information:

```text
base snapshot
candidate/result snapshot or candidate identity
src/lib.rs
selected/affected add entity when identity survives
old expression: left + right
new expression: left.saturating_add(right)
```

The source diff may be a unified diff, structured before/after range, or equivalent reusable representation.

The semantic diff must not be fabricated by comparing UI strings. Use shared change/diff semantics.

If reconciliation replaces/reidentifies a lower-level syntax entity, review must still present the stable human context `add`/`src/lib.rs` when available.

---

## Validation Contract

### Layer 1: semantic/reconciliation validation

Candidate must prove:

- edited Rust parses;
- required semantic extraction/reconciliation succeeds;
- candidate change has exact base;
- projection mapping is internally consistent enough for candidate rendering/diff;
- any migration schema/invariant validation passes.

### Layer 2: project validation

For the deterministic Rust golden fixture, run `cargo check` without network dependencies before normal acceptance is enabled.

Use existing validation/operation architecture. Do not spawn Cargo directly from React/TUI code.

The validator receives an isolated candidate materialization/workspace or another safe representation that validates candidate source without modifying the user's live working tree.

The command must be bounded/cancellable according to existing operation conventions where applicable.

Capture structured result:

```text
status
exit/result category
diagnostics/stdout/stderr in bounded form
candidate/migration identity
base/candidate snapshot context
```

Do not treat the literal text "Finished" as the semantic validation API.

### Validation gating

Normal Apply/Accept action is enabled only when required validation is successful and candidate is not stale/conflicted.

If product architecture allows privileged force-apply in the future, it is outside this milestone and must not be exposed by the golden path.

## Invalid Candidate Scenario

Create a deterministic invalid edit, for example replacing the expression with malformed Rust such as:

```text
left +
```

or another edit that reliably fails parsing/validation.

Required outcome:

- candidate creation returns structured parse/reconcile/validation failure or a non-applicable invalid candidate according to existing architecture;
- product displays diagnostic;
- Apply remains unavailable or application apply rejects it;
- active project current snapshot remains unchanged;
- live fixture file remains unchanged.

Do not silently repair the invalid human edit through the agent in this test.

## Web Interaction Requirements

### Editable source projection

For supported current Rust projection, provide a clear editable control.

The first implementation may use a textarea/code editor component appropriate to current web dependencies. Do not add a heavyweight editor dependency unless necessary.

The control must preserve exact loaded base snapshot/projection identity.

Show dirty state when local buffer differs from loaded projection.

### Propose/Review action

Editing the buffer does not mutate canonical state.

Provide an explicit action such as:

```text
Review change
Propose change
```

The action invokes the public candidate/reconcile operation.

On success, navigate/open the normal `MigrationReviewView` using returned migration identity.

Do not construct a private in-memory fake migration in the React component.

### MigrationReviewView

Extend/reuse this view so the live candidate displays:

- base snapshot;
- candidate/result identity;
- changed path;
- semantic/source diff old/new expressions;
- validation progress/result;
- stale/conflict state;
- Apply disabled until validation success;
- Reject/close local review without changing canonical state.

If validation is a long-running operation, show operation status and update from public operation/events.

## Candidate Render Isolation for cargo check

The golden fixture validator must not overwrite live workspace while validating.

Choose the smallest architecture-consistent method, e.g.:

- materialize candidate project projection into a temporary validation directory derived from base project plus candidate changes;
- use an existing projection staging area;
- use a repository-defined candidate checkout/worktree abstraction if it already exists.

Requirements:

- no network dependency;
- no mutation of live fixture source;
- candidate exact content is what Cargo checks;
- temporary validation artifacts are cleaned normally;
- failure diagnostics are retained in validation result.

Add a test that reads live `src/lib.rs` during/after validation and proves it remains base content.

## Negative and Concurrency Tests

- request uses base snapshot that is not active/current: candidate may still be inspectable but must be marked stale/not normally applicable;
- edited projection identity does not match base/project: reject structured invalid request;
- source path escapes project root: reject before any validation/materialization;
- selected mapping/range no longer matches loaded projection: reject stale edit rather than patch a different location;
- validation process fails to start: candidate remains unapplied and shows operation failure;
- user closes review: candidate/current state behavior follows existing retention policy, but current project root and disk remain unchanged.
