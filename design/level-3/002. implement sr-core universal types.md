# Implement `sr-core` Universal Types

## Objective

Implement the domain-independent core types required by the universal knowledge model in `crates/sr-core`.

This task owns only identifiers, universal property values, provenance primitives, and small model-local errors.

The implementation must remain storage-independent and domain-independent.

## 1. Identifier Types

In `ids.rs`, implement opaque newtypes for:

```text
EntityId
RevisionId
SnapshotId
EntityTypeId
PropertyKey
RelationTypeId
CollectionTypeId
SchemaId
DescriptionProfileId
ProducerId
```

Also implement a small exact reference type:

```text
EntityRevisionRef
```

containing an `EntityId` and a `RevisionId`.

### Requirements

Each identifier type must:

- have a private internal representation;
- be cloneable;
- support equality;
- support ordering when needed by maps/sets;
- support hashing;
- have useful `Debug` output;
- implement `Display` or expose `as_str()` so diagnostics are readable;
- provide a constructor from a string-like value without implying how production IDs will eventually be generated.

A private `String` representation is acceptable for this initial model library because generation/content-addressing semantics are intentionally deferred. Keep the representation private so later identity work can change it without exposing fields.

Do not:

- generate UUIDs automatically;
- hash content;
- parse database row identifiers;
- assume IDs are globally content-addressed yet;
- alias one ID type to another.

`EntityId` and `RevisionId` must remain different Rust types.

## 2. Universal Knowledge Value

In `value.rs`, implement a universal property value enum capable of representing:

```text
Null
Bool
SignedInteger
UnsignedInteger
Float
String
Bytes
List
Record
```

Use recursive values for `List` and `Record`.

For a record, use string keys because this is a value payload, not a semantic relation map.

### Requirements

- The type must be domain-neutral.
- Do not add variants for source code, Markdown, PDFs, sessions, dates, URLs, or semantic references.
- Semantic entity references belong in graph relations, not in generic property values.
- Preserve list order.
- Use a deterministic map type for records if it simplifies later canonicalization.
- Derive or implement useful `Debug`, `Clone`, and `PartialEq` support.

If floating-point values prevent deriving total equality or hashing, do not force incorrect semantics. Keep the API honest and document the limitation.

Provide a few convenient `From` conversions only for obvious primitive cases. Do not build a large conversion framework.

---

## 3. Canonicality Classification

Add a small universal classification type that can distinguish:

```text
Canonical
Derived
```

Use a neutral name such as `KnowledgeClass` or `DataClass`.

This classification will be used by schema definitions and derived records. It does not itself decide whether a particular domain field is canonical.

Expose it from `sr-core` so `sr-schema` and `sr-graph` can share the same vocabulary.

---

## 4. Provenance

In `provenance.rs`, implement provenance primitives.

Define an extensible source-kind representation that can express at least these known categories:

```text
User
AuthoritativeImport
Parser
Compiler
StaticAnalysis
Agent
ModelGenerated
System
ExternalTool
Migration
Custom(String)
```

Define a `Provenance` record with fields sufficient to express:

- source kind;
- optional `ProducerId`;
- exact input dependencies as zero or more `EntityRevisionRef` values;
- optional profile/configuration name or identifier;
- optional human-readable note.

### Requirements

- Provenance must be ordinary data, not a logging side channel.
- Input dependencies must refer to exact revisions where known.
- Do not include trust scores or authorization policy.
- Do not depend on an agent crate.
- Do not assume that `Agent` or `ModelGenerated` is less or more trustworthy than another kind; provenance records origin, not policy.

Provide constructors/helpers only where they clearly reduce boilerplate.

---

## 5. Local Errors

In `error.rs`, define small errors only for invalid local construction in `sr-core` if needed.

Examples may include:

- empty identifier text when the constructor forbids it;
- invalid locally constrained value creation.

Do not define errors for:

- databases;
- networking;
- parsers;
- schema validation;
- agents;
- migrations.

If no custom error is needed after implementing the types cleanly, keep the module minimal and document that higher layers own semantic validation.

---

## 6. Public API

In `lib.rs`:

- declare all modules;
- re-export the main public types so downstream crates do not need deep module paths for fundamental identifiers and values;
- keep module boundaries visible in generated documentation.

Suggested externally convenient types include:

```text
EntityId
RevisionId
SnapshotId
EntityRevisionRef
EntityTypeId
PropertyKey
RelationTypeId
CollectionTypeId
SchemaId
DescriptionProfileId
ProducerId
KnowledgeValue
KnowledgeClass
Provenance
ProvenanceSource
```

Use the actual names chosen in code consistently.

---

## 7. Unit Tests

Add unit tests inside the relevant modules for at least:

1. Different identifier types cannot be substituted accidentally at compile-time through aliases.
2. Equal identifier values of the same type compare equal.
3. IDs can be used as map/set keys.
4. Nested `KnowledgeValue::List` works.
5. Nested `KnowledgeValue::Record` works.
6. List order is preserved.
7. Provenance records exact revision dependencies.
8. A custom provenance source can be represented without modifying the enum again.

Do not add database-backed tests.

---

## 8. Documentation

Add module-level and public-type documentation that explains semantic purpose, not implementation trivia.

Important wording to preserve:

```text
EntityId: conceptual identity
RevisionId: exact immutable state identity
SnapshotId: exact consistent knowledge-world identity
```

Also state that this crate does not define how those identities are generated.

## Do Not

Do not:

- add persistence;
- add hashing/content addressing;
- add snapshot maps;
- add generic graph traversal;
- add schemas here;
- add concrete domain types;

- add agent runtime types;
- add HTTP/JSON protocol decisions merely for convenience.
