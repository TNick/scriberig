# Agent Task: Implement Three-Way Merge and Structured Conflicts

## Goal

Implement the universal three-way merge engine and structured conflict model for `sr-change`.

This task consumes exact snapshots and universal diffs. It must merge independent changes automatically and preserve ambiguity as semantic conflicts.

## Merge input

Expose a public merge request equivalent in meaning to:

```text
MergeInput {
    base: SnapshotId,
    left: SnapshotId,
    right: SnapshotId,
}
```

The caller may supply the base explicitly. If a convenience API derives it, use explicit history topology and common-ancestor logic rather than timestamps.

## Base validation

When the merge API is given an explicit base, verify that it is a valid ancestry base when the operation requires ancestry.

Return a typed error for an invalid base rather than silently substituting another snapshot.

## Universal merge rules

Apply these rules in order:

1. Compute `base -> left` and `base -> right` diffs.
2. If an entity changed on only one side, adopt that side.
3. If both sides resolve an entity to the same exact revision, converge without conflict.
4. If neither side changes an entity, omit it from the merge change set.
5. If both sides make different changes to the same entity, attempt deeper generic merge only when the available structure proves it is safe.
6. If safe resolution is not possible, create a structured conflict.

Do not choose left or right by default.

## Structured conflict model

Implement a universal conflict type with at least:

```text
entity: EntityId
base: Option<RevisionId>
left: Option<RevisionId>
right: Option<RevisionId>
kind: ConflictKind
```

Initial `ConflictKind` values must cover:

```text
BothModified
DeleteModify
CompetingCreate
RelationConflict
CollectionConflict
DomainConflict
```

Allow optional structured detail for an affected generic field/relation/collection path and optional domain detail.

Do not store textual conflict markers as the canonical conflict.

## Minimal conflict scope

If only one entity conflicts, preserve all other automatically resolved entity changes in the merge result.

The result should separate:

```text
resolved entity deltas
unresolved conflicts
```

A conflict must not erase unrelated successful merge work.

## Merge result

Return a structure equivalent in meaning to:

```text
MergeResult {
    base,
    left,
    right,
    resolved_deltas,
    conflicts,
}
```

Do not automatically promote the result to a named root.

If creating a provisional result snapshot is supported, it must be a new immutable snapshot and must clearly remain provisional when unresolved conflicts exist.

## Domain merge strategy

Implement the extension point prescribed by Level 2.

A domain strategy receives exact base/left/right state for one conflicted semantic area and may return either:

```text
Resolved(delta or revision)
Conflict(domain detail)
NotApplicable
```

Domain strategies must not mutate input snapshots.

The generic merge engine must work with zero registered domain strategies.

## Generic collection merge

Only implement generic collection resolution where the intent is mechanically unambiguous.

Examples that may be safe:

- independent insertion at distinct stable positions;
- identical insertion by both sides;
- independent changes to different members when identity and order are unambiguous.

If ordering intent is ambiguous, emit `CollectionConflict`.

Do not implement a large domain-specific list algorithm in this task.

## Merge provenance

Provide enough output for a later migration record to retain:

```text
merge base
left input
right input
automatically resolved entities
explicit/domain resolutions
unresolved conflicts
```

Do not require history persistence to be performed inside the pure merge algorithm.

## Tests

Add tests for:

- left-only change merges;
- right-only change merges;
- disjoint changes to two entities merge;
- both sides produce same revision and converge;
- different edits to same entity produce `BothModified`;
- left delete/right modify produces `DeleteModify`;
- competing creation of same semantic entity produces `CompetingCreate` when revisions differ;
- one conflict does not discard unrelated resolved changes;
- domain strategy can resolve one same-entity change;
- no domain strategy still returns structured conflict;
- ambiguous collection order produces `CollectionConflict`;
- merge does not mutate base/left/right snapshots.

## Constraints

- No textual merge as the canonical algorithm.
- No left-wins/right-wins fallback.
- No timestamp-based base selection.
- No automatic named-root promotion.
- Domain-specific code must stay outside `sr-change`.
