# Document Contribution Licensing and Third-Party Notices

## Objective

Create contributor-facing licensing guidance and preserve third-party attribution required by material that is actually present in distributed Scriberig components.

Read before editing:

1. `design/level-1/014. extensibility ecosystem and licensing.md`
2. `design/level-2/001. licensing artifacts package metadata and notices.md`
3. `LICENSING.md`, if it already exists
4. existing contributor documentation, if any
5. existing dependency manifests and notice files relevant to distributed components

This task does not create a CLA, DCO, copyright assignment, or commercial licensing program.

---

## Files to Create or Update

Create or update:

```text
CONTRIBUTING.md
```

Create or update this file only when there are third-party notices or attribution that should be surfaced centrally, or when the project intentionally wants an empty/initial notice registry:

```text
THIRD_PARTY_NOTICES.md
```

Do not fabricate dependency entries merely to populate the notice file.

---

## Contributor Licensing Section

`CONTRIBUTING.md` must contain a clear section explaining how licensing follows the component being modified.

The content must preserve these rules:

- contributions to Apache-licensed reusable platform components are contributed under terms compatible with Apache-2.0;
- contributions to AGPL-covered integrated product components are contributed under terms compatible with AGPL-3.0;
- contributors must preserve applicable licenses, notices, and attribution for third-party material they add;
- contributors should check the target package's own metadata and `LICENSING.md` before assuming its license;
- contribution to one side of the repository does not silently relicense code on the other side;
- current contribution terms do not implicitly grant the project rights for future commercial relicensing beyond the rights actually provided by the component license and any explicit contributor terms in force.

Keep the language factual and tied to the repository design.

Do not present speculative legal interpretation as established policy.

---

## No Implicit CLA or DCO

Do not add statements such as:

```text
By contributing you assign copyright...
By contributing you agree to a CLA...
All commits must carry a Signed-off-by line...
The project may relicense your contribution under any terms...
```

unless a separate approved design introduces that policy.

The Level 1 design explicitly leaves future commercial dual licensing as a possible later decision and warns against assuming relicensing rights that were never obtained.

If an existing `CONTRIBUTING.md` already contains a CLA, DCO, assignment, or relicensing statement, do not silently remove or rewrite it. Report the conflict for project-owner review.

---

## Third-Party Material Review

Inspect first-party distributable components and their dependency manifests that currently exist.

Relevant sources may include:

```text
Cargo.toml / Cargo.lock
package.json / lockfiles
bundled assets
fonts
copied/generated source
parser grammars
embedded fixtures
vendored code
```

The purpose is not to produce a full legal opinion on every dependency.

The task is to identify notices or attribution that the repository must preserve or that existing third-party material already includes and requires to travel with distribution.

Do not assume that every dependency requires an entry in `THIRD_PARTY_NOTICES.md`.

Do not copy entire third-party licenses into the notice file unless their terms or existing distribution practice require it.

Preserve upstream notice files when they are required.

---

## `THIRD_PARTY_NOTICES.md` Structure

If the file is needed, use a simple structure such as:

```text
# Third-Party Notices

This file records third-party notices and attribution that must accompany Scriberig distributions. Third-party components remain licensed under their own terms.

## <component or asset>

- component/version or source
- license
- required notice/attribution
- location of full third-party license or upstream notice when applicable
```

Only include verified entries for material actually present in or distributed with the repository/product.

If no current dependency requires a central notice but the project chooses to create the file as a registry, state that there are currently no centrally recorded notices and that dependency-specific obligations remain governed by their own licenses. Do not imply that no dependency has licensing obligations at all.

---

## Relationship to `LICENSING.md`

Do not duplicate the entire platform/product explanation in `CONTRIBUTING.md`.

Instead:

- summarize the rule contributors need;
- link to `LICENSING.md` for the complete repository licensing explanation;
- link to the relevant files under `LICENSES/` where useful.

`LICENSING.md` remains the main repository-level explanation of the split.

`CONTRIBUTING.md` explains what that split means for a contributor.

`THIRD_PARTY_NOTICES.md` records third-party notice obligations; it does not redefine Scriberig's own license.

---

## Package Boundary Check

While reviewing contributions and notices, verify that the repository's current packaging makes it possible to identify whether a target component is Apache or AGPL.

If a component's package metadata is missing or ambiguous:

- do not guess in contributor documentation;
- record the ambiguity;
- point to the appropriate package-metadata implementation task.

Contributor policy must not become a substitute for missing package metadata.

---

## Verification

Before completing the task:

- verify `CONTRIBUTING.md` links to `LICENSING.md` if the latter exists;
- verify it states the contribution-license rule for both Apache and AGPL components;
- verify it does not create a CLA, DCO, assignment, or commercial relicensing grant;
- verify it tells contributors to preserve third-party notices and attribution;
- verify every entry in `THIRD_PARTY_NOTICES.md`, if present, corresponds to material actually present or distributed;
- verify third-party notice entries do not claim Scriberig owns or relicenses the third-party component;
- verify no repository dependency is being assigned an Scriberig license merely because Scriberig uses it.

---

## Do Not Do

Do not:

- create a CLA;
- require sign-off/DCO without a separate design;
- claim copyright assignment;
- promise commercial dual licensing;
- add a commercial license;
- fabricate third-party dependencies;
- bulk-copy every dependency license into one file without need;
- alter dependency versions;
- alter package licenses in this task;
- create source-file SPDX headers;
- give legal conclusions beyond the controlling repository policy.
