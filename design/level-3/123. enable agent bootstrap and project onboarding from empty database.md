# Enable Agent Bootstrap and Project Onboarding From an Empty Database

## Objective

Make the native TUI capable of starting a normal agent operation when no project exists, and let that agent onboard the TUI's current working directory through shared project scan/import/workspace operations.

Required user-level result:

```text
fresh SQLite database
+ launch `srig tui --db <db>` from a project checkout
+ no active project
+ type "Onboard the current project."
-> agent discovers onboarding capability
-> scans the trusted current working directory
-> reviews the persisted manifest
-> imports that exact manifest
-> resolves/activates the new project workspace P@S0
-> returns a durable onboarding result
```

Do not require `--project`, `--import`, a preexisting `ProjectId`, or manual entity IDs for this flow.

This task is prerequisite `123` for the self-hosting sequence. Complete it before task `124` relies on semantic-first post-onboarding context.

## Required Starting State

The focused test starts from:

```text
working directory = temporary copy of a Git-backed project
database path = new nonexistent/empty SQLite path
project catalog = empty
active project = none
```

Launch the real/native composition equivalent to:

```text
srig tui --db <fresh-db>
```

The TUI must start successfully and allow entering agent mode/input even though no active project exists.

A blank project catalog is normal bootstrap state, not a fatal application error.

---

## Trusted Bootstrap Context

The local application composition must provide a bounded runtime context that an authorized onboarding tool can use.

It must contain or be able to resolve at least:

```text
current working directory
selected database/runtime identity
principal/capability context
agent/provider profile
```

Do not encode the current working directory into prompt text as the only authoritative source.

Do not create a fake `ProjectId`/root for it before scan.

The path is trusted local environmental context supplied by the product composition and remains distinct from semantic project identity until onboarding completes.

Remote agent surfaces must not inherit an arbitrary server process working directory as an authorized project path unless existing server root authorization explicitly permits it.

## Agent Start Without Project Scope

Review existing agent start validation.

The durable operation/session/branch still exists normally:

The operation input should record that no active semantic project existed at start plus the trusted bootstrap environment reference necessary for authorized tools.

Do not weaken the normal requirement for exact semantic scope on operations that actually target existing project entities. This exception is for bootstrap capability discovery/onboarding, not for arbitrary project mutation.

If project scan/import are not currently registered as agent tools, add adapters that delegate to the shared `scriberig-project`/application operations. They must not reimplement scan/import in `scriberig-agent-runtime`.

## `project.scan` Agent Contract

The agent-facing scan tool accepts a trusted/resolved path reference or a path allowed by the local capability context and existing security policy.

For the golden command, the model should be able to request conceptually:

```text
project.scan {
  path: current_working_directory,
  name: "scriberig" or inferred/default,
  selection_policy: git_tracked
}
```

Use the existing deterministic scan service.

The result exposed to the model is bounded but includes stable references:

```text
ProjectId
manifest/scan identity
canonical project metadata
file/classification summary
diagnostics
```

The complete persisted manifest remains inspectable through stable references rather than injected wholesale into model context.

---

## Manifest Review Contract

Before import, the scripted/deterministic golden agent must inspect enough persisted manifest state to prove it is importing the intended checkout.

Provide existing or minimal shared read operations for:

```text
manifest summary
bounded/paginated file listing
classification/diagnostics
```

The agent must be able to establish at least:

- manifest is non-empty;
- repository-defining files such as `Cargo.toml` are present for the Scriberig fixture;
- root/project identity is intended;
- no blocking scan error exists.

Do not require loading every file body into the model to review a manifest.

---

## `project.import` Agent Contract

The import tool receives the exact persisted manifest/scan reference returned by scan.

It must delegate to the existing project import service and inherit all existing guarantees:

- import only persisted manifest data;
- preserve exact source artifacts;
- invoke selected adapters;
- record ownership;
- create immutable successor state;
- atomically promote the project root/status according to existing transaction rules;
- preserve prior valid state on import failure.

For the first successful import, return stable references including:

```text
ProjectId P
SnapshotId S0
project semantic root where available
structured diagnostics
```

## Resolve and Activate Workspace

After import, the agent or application flow must call the same project workspace resolution used by product activation.

Resolve authoritative:

```text
project_id = P
snapshot_id = S0
root_entity_id = R
```

Then activate it in the TUI's client/product state using the existing `ActiveProjectWorkspace` path.

Do not create a TUI-only project activation mutation.

The agent's operation result and the TUI state may both reference the workspace, but server/application project state remains canonical.

---

## Minimal Semantic Smoke Check

The deterministic golden provider for this task should, after workspace resolution, request at least one normal semantic inspection/search proving the imported root is useful.

Use existing public operations such as:

```text
inspect root R at S0
find a known project source/package/config entity
```

Do not complete the onboarding golden response immediately after receiving `status=imported`.

The agent's terminal response should only claim onboarding after semantic workspace resolution/check succeeds.

## Durable Branch Result

Persist a compact branch/operation result equivalent to:

```text
purpose = onboard current project
project_id = P
snapshot_id = S0
root_entity_id = R
manifest_ref = M0
outcome = success
important refs = [...]
```

Reuse existing `BranchResult`/operation result types where possible.

Do not store the only copy of these references in TUI local state or transient streaming events.

After disconnect/reopen, session inspection must recover them.

## TUI Behavior

Required visible behavior:

1. launch with fresh DB;
2. agent input is available;
3. UI indicates no active project initially;
4. submit `Onboard the current project.`;
5. operation/progress is observable;
6. on success, active project name/context and non-empty current snapshot become visible;
7. agent response confirms onboarding succinctly;
8. semantic explorer/navigation can use the newly activated root without restart.

The TUI may summarize scan/import progress, but must not implement scan/import logic itself.

- remote/server composition cannot use an unauthorized arbitrary cwd/path;
- path escape/invalid path errors are structured;

- import tool cannot import a manifest belonging to a different unauthorized project/context;

## Required Focused Tests

### BOOTSTRAP-AGENT-01 — project-less agent start

Create a fresh DB with no project. Start agent operation through public application API with bootstrap context. Assert normal session/branch/operation identities exist and no fake active project is created merely by starting.

### BOOTSTRAP-CATALOG-01 — bounded onboarding catalog

Assert authorized bootstrap agent can discover scan/import/workspace operations and cannot see direct storage mutation tools.

### BOOTSTRAP-SCAN-01 — trusted cwd scan

Use a temporary Git project, set runtime cwd context, call agent scan tool, and assert returned persisted manifest points to the intended project and Git-tracked set.

### BOOTSTRAP-IMPORT-01 — exact manifest import

Scan, record manifest identity, then import through agent tool. Assert import consumed that manifest and returned a project snapshot/root.

### BOOTSTRAP-WORKSPACE-01 — import becomes active semantic workspace

Resolve/open workspace after import and assert TUI/client state uses exact returned `ProjectId`/`SnapshotId`/root.

### BOOTSTRAP-DURABLE-01 — result survives operation stream

Complete onboarding, recreate client/session view, and recover project/snapshot/manifest refs from durable operation/session data.

### BOOTSTRAP-FAIL-01 — import failure does not fake success

Use deterministic failing source/import case. Assert no successful active workspace transition, structured diagnostic, and terminal agent result is failure/bounded explanation.

### TUI-BOOTSTRAP-01 — real PTY

Using real built `srig` and a fresh DB:

1. launch from temporary Git project without `--project`;
2. assert no active project;
3. enter agent prompt;
4. deterministic provider uses normal onboarding tools;
5. wait for operation completion;
6. assert active project and snapshot visible;
7. assert semantic view can be opened;
8. exit cleanly.

Do not satisfy this with reducer/component-only tests.

## Deterministic Provider

Extend/reuse the existing deterministic/scripted provider through normal provider contracts.

For this focused task it should behave like a tool-using model:

1. request capability discovery;
2. call project scan for current runtime context;
3. inspect manifest summary/files;
4. call exact-manifest import;
5. resolve workspace;
6. inspect/find a semantic object;
7. return terminal success with stable project/snapshot refs.

Do not special-case production agent runtime code on the literal prompt string.

No external model/network service is required for these tests.
