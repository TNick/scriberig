# Implement Semantically Scoped Agent Candidate Through Shared Change Path

## Objective

Prove that the agent is a consumer of the same active project, semantic selection, projection, migration, validation, and review machinery as a human.

The required golden scenario is:

```text
active golden project
-> select semantic entity add
-> start agent with exact selected entity + snapshot scope
-> deterministic provider requests/uses shared semantic tools
-> agent proposes saturating-add change
-> result is a normal candidate/migration
-> normal review shows old/new source and validation
-> working tree remains unchanged until user accepts
```

This task does not permit an agent-only file patch path.

This is prerequisite `121`. Do not begin final product gate task `122` until every required test here passes.

## Semantic Scope Contract

When the user starts the golden agent operation with `add` selected, the agent request/session operation must carry structured semantic selection equivalent to:

```text
project_id or resolvable project context
entity_id = selected add entity
snapshot_id = active exact/current project snapshot
optional revision_id when available
optional projection mapping/location
```

The selected entity and snapshot are authoritative scope.

Do not reduce scope to:

```text
"src/lib.rs line 6"
```

or to prompt text such as:

```text
"please look at add"
```

Path/range may be derived supplementary context, but semantic identity must survive in operation/session/tool context.

---

## Agent Tool Use Contract

The agent runtime may expose coarse agent-oriented tools, but they must delegate to shared application operations.

For the golden scenario, the agent must be able to do the conceptual equivalent of:

```text
inspect selected semantic entity
render/read source projection for selection
propose/reconcile edited projection or structured semantic change
return stable migration/candidate reference
```

If the current agent catalog already exposes generic inspect/render/migrate/reconcile tools, reuse them.

Do not add a tool that directly opens SQLite.

Do not add a tool that directly writes `src/lib.rs` and then asks the project importer to notice later.

Do not allow the deterministic provider itself to insert a migration by calling test internals outside the agent tool/runtime contract.

## Deterministic Provider Scenario

### Required prompt

Use a stable user prompt such as:

```text
Change add so overflow saturates instead of wrapping.
```

### Required deterministic behavior

Configure the existing fake/scripted provider so it behaves like a small tool-using model for this exact test world.

The provider should, through normal runtime messages/tool requests:

1. observe that structured semantic selection exists;
2. request inspection/source for the selected entity when the runtime protocol expects tools;
3. receive source containing `left + right`;
4. request the normal edit/candidate operation to change it to `left.saturating_add(right)`;
5. return a concise terminal response referencing the candidate/migration;
6. allow the session/operation result to expose the candidate reference to product surfaces.

The exact provider message format follows existing provider-neutral contracts.

Do not special-case production agent runtime code on the literal prompt string. The scripted behavior belongs in deterministic test provider configuration/fixture.

## Capturable Scope Evidence

Tests must be able to prove exact semantic scope reached the agent/provider/tool layer.

Use an existing event/trace/session record where possible.

Acceptable evidence includes:

- deterministic provider captured normalized model request containing structured selection context;
- agent tool invocation record contains `EntityId` and `SnapshotId` matching the selected `add`;
- durable agent operation input/session episode records preserve the selection.

Not acceptable by itself:

- prompt contains word `add`;
- UI selected row text happened to be `add`;
- source path was included without semantic identity.

Keep captured test data bounded and free of secrets.

## Candidate Result Contract

A successful agent operation that proposes a change must expose a stable result reference that product surfaces can navigate to.

Prefer existing operation result/session activity concepts.

Required semantics:

```text
operation_id
session_id
branch_id when applicable
selected semantic scope
candidate/migration id
base snapshot
result status
```

The migration itself is the same type used by human editing.

Do not create `AgentPatch` as a separate canonical mutation type unless it is only a transient provider-facing representation converted into the shared migration before product review.

## Review and Validation Integration

After the agent operation finishes, web and TUI must open/navigate to the normal migration review used by task `119`.

Review must show:

```text
src/lib.rs
add
left + right
left.saturating_add(right)
validation success
```

Before user Apply:

- project current snapshot remains base;
- live fixture file remains base;
- agent result may be durable, but it has not silently committed canonical project change.

Applying later uses task `120` unchanged.

## Web Requirements

`SessionAgentView` already passes a semantic selection shape to agent start/continue operations. Verify and extend rather than replacing this path.

Required browser flow:

1. user selects `add` in semantic explorer;
2. Session/Agent view visibly indicates selected scope or otherwise preserves it;
3. user submits golden prompt;
4. deterministic agent operation runs through normal API/events;
5. terminal operation result exposes migration candidate;
6. `Review candidate` action opens normal `MigrationReviewView`;
7. normal review/validation data is visible;
8. source file is unchanged before Apply.

If the current UI changes selection while opening agent result, fix shared selection/navigation rather than creating a second agent selection store.

5. navigate to resulting candidate through normal TUI review view;

7. verify disk remains unchanged before Apply.

## Branch/Session Behavior

The golden agent operation should use existing durable session/branch semantics.

Required assertions:

- operation belongs to expected session;
- resulting candidate link remains inspectable after live streaming ends;
- refreshing/reopening the product can recover operation/session result from durable state;
- continuing a branch preserves explicit selected/current context rules rather than accidentally using an obsolete implicit project root.

Do not make ephemeral SSE/WebSocket stream data the only location of the candidate reference.

---

## Cancellation and Failure

Add focused tests for:

- agent operation cancelled before candidate creation: no candidate/current snapshot/file change;
- provider/tool failure: operation failed with structured error; no current snapshot/file change;
- selected entity cannot be resolved at requested snapshot: agent operation/tool fails or requests explicit refresh; do not silently inspect a different current entity;
- candidate becomes stale before review/apply: normal migration review shows stale state and task `120` protections apply.

## Required Focused Tests

### AGENT-SCOPE-01: exact semantic scope reaches runtime/tool/provider

1. import/activate golden fixture;
2. resolve/select `add`;
3. start agent with golden prompt through application operation;
4. inspect deterministic provider/tool/session trace;
5. assert `EntityId` equals selected `add`;
6. assert `SnapshotId` equals active base snapshot;
7. assert project context resolves to golden project.

### AGENT-CANDIDATE-01: agent uses shared candidate operation

Run deterministic scenario to completion.

Assert:

- result contains normal migration/candidate ID;
- candidate base equals selected snapshot;
- candidate diff is same saturating-add change;
- live project snapshot remains base;
- live file remains `left + right`.

### AGENT-CANDIDATE-02: human and agent candidate semantics are equivalent

Create one human candidate and one agent candidate from fresh equivalent bases using same edit.

Compare semantic/source change meaning, not random IDs/timestamps.

Assert both are consumable by same migration detail/validation/apply operation types.

### AGENT-DURABLE-01: result survives stream/view lifetime

After operation completes, disconnect/recreate client or reopen session and recover candidate reference from durable operation/session state.

### AGENT-FAIL-01

Script provider/tool failure and assert no migration/current snapshot/filesystem mutation.

### AGENT-CANCEL-01

Cancel operation before candidate creation and assert same no-mutation guarantees.

### WEB-AGENT-01

Real Playwright:

1. activate golden fixture;
2. navigate/select `add`;
3. open Session/Agent;
4. submit golden prompt;
5. wait for deterministic operation completion;
6. click/open candidate review through product UI;
7. assert `src/lib.rs`, old expression, new expression, and validation result;
8. assert harness-captured scope is exact selected entity/snapshot;
9. assert live file remains base before Apply;
10. assert browser diagnostics clean.

### TUI-AGENT-01

Real PTY:

1. launch/select `add`;
2. submit golden prompt;
3. wait for operation result;
4. open candidate review;
5. assert old/new expressions and validation;
6. inspect captured deterministic trace after run for exact entity/snapshot;
7. assert live file remains base before Apply.
