# Implement Rust Semantic Reconciliation

## Objective

Implement Rust-specific reconciliation that compares an existing canonical Rust syntax graph with newly parsed externally edited Rust source and produces shared semantic migration/change operations.

This task is the reverse-editing half of the Rust syntax adapter. It must preserve stable conceptual identity when the evidence is strong and report ambiguity when it is not.

Read before editing:

1. `design/level-1/006. projections and bidirectional editing.md`
2. `design/level-1/007. domain modeling and adapters.md`
3. `design/level-3/005. implement language independent code domain.md`
4. `design/level-3/006. implement rust syntax domain adapter.md`
5. current public APIs in `scriberig-migration` and `scriberig-projection`

## Inputs and Output

The reconciliation layer must accept conceptually:

```text
base canonical Rust semantic state
newly parsed candidate Rust semantic state
```

and return:

```text
shared semantic migration/change proposal
identity matches/reuse information
ambiguities/conflicts
```

It must not commit persistence directly.

---

## Matching Strategy

Use deterministic structural evidence first.

For declarations/functions/types, use signals such as:

```text
exact semantic subtree equality
kind/declaration type
name
signature/parameter structure
containing module/impl context
sibling/declaration order
body similarity
attributes
```

For statements/expressions, use:

```text
exact subtree equality
matched parent context
sibling sequence alignment
syntax kind
semantic content similarity
```

For comments/code groups, use source grouping and matched surrounding syntax.

Line numbers and byte offsets may be tie-breaking metadata but must not be primary identity.

---

## Required First-Slice Changes

Support at least:

```text
function body expression change
statement insertion
statement deletion
statement reorder within one block
parameter rename/change when continuity is unambiguous
function signature change
function insertion/deletion
function move within the same module when detectable
comment edit/insertion/deletion
code-group boundary changes caused by source grouping
```

Preserve unchanged child entities wherever possible.

Changing one expression must not force unrelated sibling functions to become new conceptual entities.

---

## Example

Changing:

```rust
let result = a + b;
```

to:

```rust
let result = a * b;
```

must produce a semantic change at the relevant expression path while reusing unchanged surrounding function/module entities as conceptual identities according to the shared revision model.

Do not represent this as replacing the entire source file.

---

## Rename vs Delete/Create

When a local binding, parameter, or declaration changes name, preserve conceptual continuity only when structural/context evidence makes the match strong.

Do not infer a rename merely because one old name disappeared and one new name appeared.

If matching is ambiguous, return explicit ambiguity and let a higher layer decide whether to treat the candidate as new entities or request resolution.

---

## Moves

A source entity may move without semantically changing.

For a confidently detected move:

- preserve the conceptual entity;
- update collection/containment structure through shared migration operations;
- do not rewrite the entity merely because its line/file coordinates changed.

Cross-file/module moves may be deferred unless the projection orchestration already provides both affected modules as one reconciliation scope.

---

## Formatting-Only Changes

Changes only to formatting/style must not create semantic source revisions when parsing maps both versions to the same canonical syntax.

Add tests for:

```text
indentation changes
line wrapping
spacing around operators
brace/formatting changes that do not change chosen syntax semantics
```

Use canonical parse structure, not textual diff, to decide this.

---

## Macro Safety

Macros and token trees may be difficult to reconcile structurally.

For unsupported or ambiguous macro-internal changes:

- preserve the macro invocation as the smallest safe replacement unit;
- do not pretend individual expanded compiler nodes are stable source entities;
- return ambiguity rather than inventing continuity inside opaque token structures.

A future task may add more precise macro reconciliation.

---

## Migration Output

Map Rust changes onto shared migration operations.

Do not create a Rust-only history representation.

The output must be usable by generic validation/branch/snapshot code.

The adapter may attach domain-specific explanation metadata to operations where the shared migration model supports it.

---

## Tests

Cover at least:

1. unchanged source -> no semantic migration;
2. expression operator change -> local semantic change;
3. statement insert/delete/move -> structural operations with unchanged siblings reused;
4. function signature edit -> function continuity where unambiguous;
5. formatting-only edit -> no semantic change;
6. function reorder -> move/reorder rather than delete/create where unambiguous;
7. comment edit -> comment revision/change without unrelated AST churn;
8. ambiguous similar functions/declarations -> explicit ambiguity;
9. macro token change -> safe macro-level replacement or explicit ambiguity;
10. unrelated functions retain identity across one-function edit.

Run:

```text
cargo fmt --all -- --check
cargo test -p scriberig-domain-rust
cargo clippy -p scriberig-domain-rust --all-targets -- -D warnings
```

---

## Do Not Do

- Do not reconcile by textual line diff alone.
- Do not use line numbers as semantic identity.
- Do not replace the whole module/file for every local edit.
- Do not inspect compiler-expanded macro AST as if it were canonical source identity.
- Do not silently guess ambiguous renames/moves.
- Do not call an LLM.
- Do not commit snapshots directly.
- Do not create Rust-specific migration storage.
