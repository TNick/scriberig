# Verify Identity Subsystem Conformance

## Mission

Review the completed `sr-core` and `sr-store` identity subsystem as one integrated unit, add any missing conformance coverage, and fix only defects that violate the Level 1 or Level 2 identity contracts.

This task is not an opportunity to add new product features. Its purpose is to prove that the implementation created by Level 3 tasks 001 through 005 actually satisfies the architecture before higher layers depend on it.

## Required End-to-End Scenario

Add an integration test that performs this exact logical sequence.

### Step 1: Create entities

Create stable entities:

```text
F
P1
P2
B
```

Create canonical revisions:

```text
FR7
PR3
PR8
BR2
```

Store all revisions.

### Step 2: Build snapshot S1

Build a snapshot containing:

```text
F  -> FR7
P1 -> PR3
P2 -> PR8
B  -> BR2
```

Record `S1` and its `SnapshotId`.

### Step 3: Change only P2

Create a new revision for the same entity `P2`:

```text
PR9
```

The `EntityId` of `P2` must stay unchanged.

Create successor snapshot `S2` with only:

```text
P2 -> PR9
```

changed.

### Step 4: Assert local stability

Verify:

- [x] `F` still resolves to `FR7` in `S2`;
- [x] `P1` still resolves to `PR3` in `S2`;
- [x] `B` still resolves to `BR2` in `S2`;
- [x] `P2` resolves to `PR8` in `S1`;
- [x] `P2` resolves to `PR9` in `S2`;
- [x] no semantic parent revision was manufactured merely because `P2` changed.

### Step 5: Assert global certainty

Verify:

- [x] `S1.id() != S2.id()`;
- [x] rebuilding `S1` in another insertion order produces the same `SnapshotId`;
- [x] rebuilding `S2` in another insertion order produces the same `SnapshotId`.

### Step 6: Assert exact history

Verify that `S1` remains readable after `S2` exists and still resolves every entity to the original revisions.

No operation may retarget `S1`.

### Step 7: Assert semantic snapshot diff

Verify `S1.diff(S2)` contains exactly one change:

```text
Changed {
  entity: P2,
  from: PR8,
  to: PR9
}
```

No unchanged entity may appear.

### Step 8: Assert named-root concurrency semantics

Set:

```text
main -> S1
```

Advance it with compare-and-swap:

```text
expected S1
new S2
```

Verify success.

Then try another update still expecting `S1`.

Verify:

- [x] it fails as stale;
- [x] `main` remains at `S2`;
- [x] neither `S1` nor `S2` changed.

## Additional Invariant Audit

Check the implementation manually and with tests for every item below.

### Identity separation

- [x] `EntityId`, `RevisionId`, and `SnapshotId` are distinct Rust types.
- [x] An `EntityId` is not computed from current content.
- [x] A `RevisionId` is content-derived.
- [x] A `SnapshotId` is content-derived from global mapping state.

### Historical exactness

- [x] Revisions have no mutable update method.
- [x] Snapshots have no mutable update method that changes an existing value in place.
- [x] Named roots are pointers, not snapshot identities.

### Canonical hashing

- [x] Encoding version is included in revision hashes.
- [x] Type ID is included in revision hashes.
- [x] Entity ID is not included in revision hashes.
- [x] Snapshot internal node hashes use domain separation.
- [x] Snapshot root hash uses separate root domain separation.
- [x] No unordered map iteration participates in canonical identity.

### Change propagation

- [x] One entity update does not copy the full entity-to-revision mapping.
- [x] An update copies only the bounded trie path plus the new leaf/state required.
- [x] Unaffected branches are structurally shared.

### Determinism

- [x] Equivalent revision values have equivalent IDs.
- [x] Equivalent snapshot mappings have equivalent IDs regardless of insertion order.
- [x] Diff order is deterministic.
- [x] ID textual forms round-trip exactly.

### Dependency direction

- [x] `sr-core` does not depend on `sr-store`.
- [x] Neither crate depends on agent, server, UI, domain, filesystem watcher, or database-driver crates.

## Test Organization

If existing tests already prove an invariant clearly, do not duplicate them unnecessarily.

The new conformance test should focus on cross-module behavior that individual unit tests cannot prove alone.

Use fixed `EntityId::from_bytes(...)` values for most deterministic tests. Use `EntityId::new()` only when testing fresh identity generation.

## Documentation Check

Ensure the public APIs make these distinctions understandable without reading implementation internals:

```text
EntityId = conceptual continuity
RevisionId = exact immutable local state
SnapshotId = exact immutable global state
named root = mutable pointer to SnapshotId
```

Add short rustdoc where the distinction is unclear.

Do not add long architectural essays to source files; the design documents remain authoritative.
