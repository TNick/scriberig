# Implement Inspect, List, and Follow Read Operations

## Objective

Implement the universal orientation and traversal contracts in `scriberig-query`.

This task adds `inspect`, `list`, and `follow` request/result types and the read-service boundary that resolves them against exact snapshots. It must preserve progressive disclosure, semantic handles, typed relation/collection meaning, and bounded traversal.

This task does not implement search, the structured query AST, application-layer composition, transport schemas, or write operations.

## 1. Inspection Request

In `src/inspect.rs`, implement an `InspectRequest` or equivalent containing:

```text
target
resolved snapshot or exact revision context
detail level
optional requested view
```

Do not support an unresolved `Current` snapshot in this crate.

If the target is only an `EntityId`, require a snapshot-bound target type from the previous task.

---

## 2. Inspection Result

Implement an `Inspection` result capable of representing the Level 1 orientation data without forcing every field to exist.

Required conceptual fields:

```text
subject handle
snapshot
revision
entity type
short label/title
short description
important properties
counts
relation capabilities
collection capabilities
view capabilities
operation capabilities
provenance summary
information cost
```

Use reusable domain-neutral property/value types already owned by core/graph libraries.

Do not encode rich domain objects as arbitrary JSON strings.

Keep the default result compact. A full semantic revision body should be returned only for an explicit full-detail request or domain view.

---

## 3. Capability Descriptors Used by Inspection

If `scriberig-app` capability descriptors do not exist yet, define only the read-side capability metadata needed here in a way that can later be reused/re-exported by the application layer.

At minimum distinguish:

```text
relation
collection
view
operation
```

Each descriptor should include a stable identifier and short description.

Where schema data exists, include target type/cardinality/ordering/canonical-vs-derived metadata without hard-coding domain names.

Do not implement execution of high-level operations in this task.

---

## 4. List Request and Result

In `src/traverse.rs`, implement `ListRequest` or equivalent.

It must specify:

```text
snapshot-bound subject
collection identifier
PageRequest
detail level for entries
```

Implement a compact `NavigationEntry` containing at least:

```text
semantic handle
entity type
short label/description
optional compact metadata/count
```

Implement `ListResult` containing:

```text
subject
snapshot
collection identity
Page<NavigationEntry>
```

Collection order must be preserved when the schema says the collection is ordered.

Do not sort semantic collections merely for display convenience.

---

## 5. Follow Request and Result

Implement `FollowRequest` or equivalent with:

```text
snapshot-bound subject
relation identifier
direction if supported
PageRequest
detail level for entries
```

Implement `FollowResult` containing:

```text
subject
snapshot
relation identity
relation metadata
Page<NavigationEntry>
```

Preserve typed relation meaning.

Do not return generic unlabeled graph edges when a relation type is known.

If reverse traversal is unavailable because no index/derived provider exists, return `UnsupportedCapability` or `DerivedDataUnavailable` as appropriate rather than scanning hidden storage structures or fabricating reverse edges.

---

## 6. Read Service Trait

Expose a transport-independent service trait or small set of traits covering:

```text
inspect
list
follow
```

Choose async versus sync consistently with existing project conventions. Do not introduce an async runtime dependency merely for hypothetical future networking.

The service implementation should depend on graph/schema/store-facing traits rather than one concrete backend.

The service must resolve each operation entirely within the request's exact snapshot.

---

## 7. Snapshot Resolution Rules

For snapshot-relative targets:

```text
EntityInSnapshot(E, S)
```

resolve `E -> Revision` once for `S` and use that exact result throughout the operation.

For exact revision targets:

```text
EntityAtRevision(E, R)
```

use `R` directly for local revision content.

If surrounding traversal requires collection/relation membership, require or retain a snapshot context rather than guessing current state.

A query must not start in one snapshot and finish against a newer named root.

---

## 8. Structured Errors

In `src/error.rs`, add or extend semantic errors required by these operations:

```text
NotFound
InvalidTarget
WrongType
UnsupportedCapability
SnapshotUnavailable
DerivedDataUnavailable
InvalidContinuation
Internal
```

Errors should carry the operation kind and relevant subject/snapshot/relation/collection handles when useful.

Do not expose raw database-driver error strings as the public API.

---

## 9. Unknown and Partially Adapted Entities

`inspect` must succeed for entities that have only generic graph/schema metadata whenever possible.

For an unsupported blob-like entity, an inspection may expose:

```text
type
size/metadata if known
available generic relations
available raw projection/view if registered
```

It must not claim domain capabilities that are unavailable.

This behavior is important for forward-compatible domain adapters.

---

## 10. Tests

Extend `tests/universal_read_model.rs` using memory/test-double graph data.

Cover at least:

1. `inspect` resolves an entity against the exact requested snapshot;
2. newer snapshots do not alter a completed inspection result;
3. default inspection is compact and advertises deeper capabilities;
4. ordered collections preserve order;
5. unordered collections are not accidentally given semantic order guarantees;
6. `list` respects page limits and continuation;
7. `follow` returns typed relation identity and semantic handles;
8. reverse traversal unavailable from the provider returns a structured capability/derived-data error;
9. handles from `list` can be passed directly to `inspect`;
10. unknown entity types remain generically inspectable;
11. full content is not required merely to list children;
12. invalid collection/relation identifiers produce structured errors.

Run:

```text
cargo test -p scriberig-query
cargo check --workspace
```

---

## 11. Non-Goals

Do not implement:

- text/semantic `find`;
- the query AST/executor;
- semantic diff or history engines;
- render/projection execution;
- branch/apply/commit;
- HTTP or CLI adapters;
- agent tools;
- domain-specific operations such as `rename_symbol`.

---

## Completion Criteria

This task is complete when:

- `inspect`, `list`, and `follow` have reusable Rust contracts;
- every operation is bound to one exact snapshot/revision context;
- inspection advertises useful next relations/collections/views/operations;
- list/follow results are compact, semantic, and pageable;
- typed relation/collection meaning is preserved;
- unsupported capabilities and derived-data absence are structured failures;
- no concrete database backend or product surface is required.
