# Universal Knowledge Model Rust Libraries

## 1. Purpose

This document translates the Level 1 universal knowledge model into the first reusable Rust library boundaries and source files.

It is intentionally limited to the domain-independent semantic model described by `design/level-1/002. universal knowledge model.md`.

It does not choose a database backend, content-addressing algorithm, snapshot-map implementation, HTTP transport, parser library, renderer, agent runtime, or UI framework. Those decisions belong to other designs.

The implementation created from this document must be useful to ordinary Rust applications without an agent runtime.

---


The names above are prescribed by this design for the initial implementation. Later designs may add crates, but implementation agents must not merge persistence, domain adapters, or agent-specific behavior into these crates.

## 3. Dependency Direction

The dependency direction is:

```text
sr-core
   ↑
   ├──────── sr-schema
   │
   └──────── sr-graph
                ↑
                └── may use schema types only through explicitly declared dependency
```

For the initial implementation, `sr-schema` depends on `sr-core` and `sr-graph` depends on both `sr-core` and `sr-schema`.

No crate in this design may depend on:

- a database driver;
- an async runtime;
- an HTTP framework;
- an agent SDK;
- a parser for Markdown, Rust, PDF, or another domain;
- a UI toolkit.

These crates define semantic contracts only.

## 4. `sr-core`

`sr-core` contains the smallest domain-independent types that other Scriberig crates can share without pulling in graph or schema behavior.

### 4.1 `ids.rs`

Define opaque identifier newtypes for concepts required by the Level 1 model:

```text
EntityId
RevisionId
SnapshotId
EntityTypeId
PropertyKey
RelationTypeId
CollectionTypeId
SchemaId
DescriptionProfileId
ProducerId
```

At this stage these types are opaque identifiers only.

Do not decide how IDs are generated, hashed, encoded on disk, or assigned. The identity design will define those rules later.

Requirements:

- identifiers must not be accidentally interchangeable;
- identifiers must support equality and hashing;
- identifiers must have a readable debug representation;
- serialization support may be feature-gated or added if it can be done without defining persistence semantics;
- no identifier type may contain database-specific handles.

### 4.2 `value.rs`

Define the universal scalar/structured property value representation used by schemas and revision records.

The value model must be capable of representing at least:

- null/absent-compatible value where useful;
- boolean;
- signed and unsigned integers;
- floating-point number;
- string;
- bytes;
- lists of values;
- string-keyed records/maps.

Do not use property values to encode entity relationships when a relation or collection is appropriate.

The type should be domain-neutral. It must not contain Rust-AST, Markdown, PDF, or session-specific variants.

### 4.3 `provenance.rs`

Define reusable provenance vocabulary without embedding policy.

At minimum represent:

- a provenance source kind;
- an optional producer identifier;
- exact input entity/revision references when known;
- optional profile/configuration identity;
- optional human-readable note.

Source kinds must be extensible. The model must be able to distinguish examples such as user-authored, imported, parser-produced, compiler-produced, static-analysis-produced, agent-produced, model-generated, system-generated, and external-tool-produced knowledge.

Do not assign trust scores in this crate.

### 4.4 `error.rs`

Define small model-layer error types for invalid local construction where necessary.

Do not create backend or transport errors here.

## 5. `sr-schema`

`sr-schema` defines how a domain gives strong meaning to the universal graph.

The universal model must not become an untyped bag of properties and edges. Schemas describe valid domain concepts while remaining independent of storage.

### 5.1 `entity.rs`

Define an entity type schema.

It must support:

- the entity type identifier;
- a human-readable name;
- an optional description;
- schema version association;
- references to declared property, relation, and collection definitions.

Do not define concrete domain types such as `Function` or `Paragraph` in this crate. Domain adapters will instantiate schema definitions later.

### 5.2 `property.rs`

Define property schema information.

It must represent:

- property key;
- expected value shape/type;
- required versus optional;
- whether the value is canonical or derived where this distinction is meaningful;
- optional constraints that are purely schema-level.

Avoid building a general programming language for constraints in this stage.

### 5.3 `relation.rs`

Define typed relation schemas.

A relation schema must be able to express:

- relation type identifier;
- semantic name;
- permitted source entity types;
- permitted target entity types;
- canonical versus derived classification;
- cardinality information when known;
- whether reverse navigation is expected to be index-derived.

The relation model must not require reverse edges to be stored canonically.

### 5.4 `collection.rs`

Define collection schemas separately from generic relations because ordered membership has semantics that a plain set of edges does not capture.

A collection schema must represent:

- collection type identifier;
- owner entity type;
- permitted member entity types;
- ordered versus unordered semantics;
- cardinality constraints when known;
- canonical versus derived classification.

### 5.5 `validation.rs`

Define validation result types and a schema-level validation interface.

Validation results must be structured rather than plain strings.

At minimum a validation issue should contain:

- severity;
- machine-readable code;
- human-readable message;
- optional entity/property/relation/collection location.

This module validates only schema-level structure. Parser validity, compiler validity, tests, and application policy belong to domain or product layers.

## 6. `sr-graph`

`sr-graph` defines immutable semantic revision records and a read-only graph interface interpreted within a snapshot.

It does not persist data.

### 6.1 `revision.rs`

Define a revision record that represents one exact state of an entity.

A revision record must include:

- entity type;
- property values;
- canonical relation values owned by the revision;
- canonical collection values owned by the revision;
- optional canonical provenance only where provenance itself is part of the domain state.

The record must not contain a mutable parent pointer merely to support reverse navigation.

The record must not contain a database connection, row ID, or current-snapshot pointer.

### 6.2 `relation.rs`

Define relation values held by a revision.

A relation value targets semantic entities by `EntityId` or another universal semantic reference, not filenames or line positions.

Preserve the distinction between relation type and target identity.

Derived relations may be represented by derived artifacts rather than inserted into canonical revision payloads.

### 6.3 `collection.rs`

Define ordered and unordered collection membership values.

Requirements:

- ordered collections preserve member order exactly;
- unordered collections do not expose incidental storage order as semantic order;
- membership uses semantic entity handles;
- moving a member changes collection state but does not require changing the member's own semantic identity;
- collection values are immutable values suitable for later revision identity calculation.

### 6.4 `description.rs`

Define descriptions and progressive representations as derived navigation objects.

A description must identify:

- the entity/revision it describes;
- the description profile;
- provenance;
- textual content;
- optional information-cost metadata such as approximate token or byte size.

Generated descriptions are derived knowledge by default and must not silently become canonical revision content.

### 6.5 `derived.rs`

Define a generic derived artifact record.

It must represent:

- artifact kind/profile;
- exact input dependencies;
- producer/configuration identity;
- provenance;
- result payload or a typed reference to a result;
- validation/status metadata if needed.

The exact dependency list is important because derived results should remain reusable when unrelated entities change in another snapshot.

Do not implement a cache or persistence backend here.

### 6.6 `view.rs`

Define the minimal read-only interface higher layers need to inspect the universal graph relative to a snapshot.

The interface must support, conceptually:

```text
resolve entity to revision in a snapshot
read a revision
read properties
follow owned relations
read collections
obtain reverse relations through a view/index abstraction
obtain schema information
```

The interface should be trait-based so future stores can implement it.

Do not implement universal search, history, diff, migrations, or writes in this file. Those belong to later designs.

## 7. Canonical Versus Derived Data

The code must make the distinction visible in types or metadata.

Canonical data participates in semantic state and snapshots.

Derived data is computed from canonical data or external evidence and must identify its exact dependencies and provenance.

Implementation agents must not simplify the design by inserting model-generated descriptions, compiler call graphs, reverse indexes, or cached render output directly into canonical revision records.

---

## 8. Entity Continuity Versus Exact State

These crates must preserve the distinction between:

```text
EntityId   = what conceptual thing is this?
RevisionId = what exact immutable state is it in?
SnapshotId = what exact consistent world is being viewed?
```

However, this Level 2 design deliberately does not define how these IDs are generated or how snapshots map entities to revisions.

APIs must keep the types separate so later identity and persistence designs can implement the required semantics without breaking domain code.

---

## 9. No Hard-Coded Domain Vocabulary

The following kinds of types must not be added to these crates:

```text
MarkdownSection
RustFunction
PdfPage
SessionBranch
```

Those belong to domain crates.

The universal model may contain examples in documentation and tests, but core APIs must operate on schema-defined entity and relation types.

## 10. Tests

`crates/sr-graph/tests/universal_model.rs` must exercise the model without any persistence backend.

The tests should define a small test schema with generic entity types such as `Document`, `Section`, and `Paragraph` only inside the test.

Required scenarios:

1. Construct two entities with different entity types.
2. Construct an ordered collection and verify order is preserved.
3. Construct an unordered collection and verify callers cannot rely on insertion order as semantic order.
4. Construct a typed relation between two entities.
5. Verify a child revision does not require a parent pointer.
6. Create a derived description that references an exact entity revision and provenance.
7. Create a derived artifact with explicit input dependencies.
8. Validate a correct revision against a schema.
9. Produce structured validation issues for an invalid property or relation.
10. Demonstrate that domain-specific names are supplied by test schemas rather than hard-coded in the core crates.

Tests must not require SQLite, networking, an agent, or a parser.

---

## 11. Documentation Requirements

Each public module must contain module-level documentation explaining:

- what semantic concept it represents;
- whether its content is canonical, derived, or either depending on schema;
- what it deliberately does not decide;
- which Level 1 invariant it protects when that is not obvious.

Public types should have short documentation suitable for generated Rust API docs.

Avoid comments that merely restate field names.

---

## 12. Completion Criteria

This design is implemented when all of the following are true:

- [ ] the repository is a valid Cargo workspace;
- [ ] `sr-core`, `sr-schema`, and `sr-graph` compile independently according to their dependency direction;
- [ ] identifiers are strongly typed and opaque;
- [ ] universal property values exist without domain-specific variants;
- [ ] schemas describe entity, property, relation, and collection semantics;
- [ ] canonical relation direction does not require canonical reverse edges;
- [ ] ordered and unordered collections are distinct;
- [ ] immutable revision records contain no persistence-specific state;
- [ ] provenance is represented explicitly;
- [ ] derived artifacts declare exact dependencies;
- [ ] descriptions are derived navigation data by default;
- [ ] a trait-based snapshot-bound graph view exists;
- [ ] schema-level validation returns structured issues;
- [ ] integration tests demonstrate the Level 1 invariants without a database or agent runtime;
- [ ] no Markdown, Rust, PDF, session, agent, HTTP, or database implementation is introduced by this work.

---

## 13. Work Decomposition

The implementation should be performed as focused Level 3 tasks in this order:

1. bootstrap the Rust workspace and crate manifests;
2. implement `sr-core` identifiers, values, provenance, and local errors;
3. implement `sr-schema` definitions and schema-level validation contracts;
4. implement `sr-graph` revision, relation, collection, description, derived-artifact, and view types;
5. add universal-model integration tests and API documentation.

Each task must leave the workspace compiling and must not pull later-layer concerns into these libraries.
