# Terminal UI Runtime and State Architecture

## 1. Purpose

This document turns `design/level-1/015. terminal user interface principles.md` into a concrete Rust architecture for the native terminal interface.

It also depends on:

1. `design/level-1/011. runtime libraries protocol and product surfaces.md`;
2. `design/level-2/011. application operations protocol and runtime boundaries.md`;
3. `design/level-2/012. capability matrix and cross surface conformance.md`;
4. `design/level-2/020. repository scaffold conventions and native command surface.md`.

The first implementation milestone is an embedded local TUI started by `srig tui`. The design deliberately keeps the semantic-access boundary replaceable so a later remote mode can use `scriberig-client` without replacing the state machine or views.

The controlling implementation rule is:

> Terminal code owns interaction state and rendering; shared application services own semantic meaning and canonical state.

---

## 2. Package Boundary

The existing package remains:

```text
crates/scriberig-tui/
```

Its responsibility is terminal-specific interaction and presentation. It may depend on public application/client contracts, terminal UI libraries, and small presentation utilities.

It must not depend directly on:

```text
scriberig-store
scriberig-store-memory
scriberig-store-sqlite
scriberig-graph internals
scriberig-migration internals
SQLite APIs
server implementation internals
agent provider internals
```

The native composition root under `apps/scriberig` remains responsible for constructing concrete local storage/application services and passing an appropriate TUI-facing adapter into `scriberig-tui`.

The initial crate may continue to depend on `scriberig-app`. A later remote adapter may add a dependency on `scriberig-client`; it must not make the TUI depend on `scriberig-server`.

---

## 3. Terminal Stack

Use Ratatui for terminal layout/rendering and Crossterm for the native terminal backend and events.

Reasons:

- Ratatui provides a presentation model suitable for pure frame rendering;
- Crossterm supports the platforms targeted by the native Rust product;
- Ratatui provides a `TestBackend` suitable for deterministic rendering tests;
- the ecosystem already supports raw mode, alternate screen, resize, keyboard, mouse, and bracketed-paste workflows.

The workspace must resolve one compatible Crossterm line. Do not accidentally depend on incompatible Crossterm versions through separate direct/transitive paths because terminal event queues and raw-mode state are process-global concerns.

Exact dependency versions belong to the implementation task and lockfile, not this design document.

## 5. Runtime Ownership

The TUI runtime owns exactly these classes of state:

```text
terminal lifecycle
input/event decoding
view/pane focus
navigation history
current semantic selection
cached presentation models
loading/error states
open overlays
scroll/cursor offsets
operation observation state
notifications
```

It does not own:

```text
canonical entities or revisions
snapshot creation
branch semantics
validation policy
capability grants
projection reconciliation semantics
session persistence
agent tool semantics
```

A cached presentation model is always derived from a result returned by an application/client operation.

---

## 6. Event -> Action -> Effect Architecture

The implementation must keep terminal events, UI state changes, and semantic side effects separate.

The logical flow is:

```text
terminal event / service result / app event
                    |
                    v
                 Action
                    |
                    v
          reduce(current state)
             /             \
            v               v
      next UI state       Effects
                              |
                              v
                     application/client
                              |
                              v
                        result Action
```

### Events

Events are observations from outside the reducer, including:

- key presses;
- paste events;
- resize events;
- periodic ticks when needed;
- semantic operation results;
- operation progress;
- application/client events;
- worker failures;
- shutdown signals.

### Actions

Actions express interaction intent or the arrival of a typed result. Examples include:

```text
MoveSelection
ActivateSelection
GoBack
GoForward
ChangeFocus
OpenPalette
CloseOverlay
RunContextAction
InspectLoaded
HistoryLoaded
OperationUpdated
RequestQuit
```

Actions must not contain terminal-library handles or database connections.

### Reducer

The reducer updates TUI state and returns zero or more semantic/presentation effects. It should be deterministic for a given state/action pair.

### Effects

Effects describe work outside pure state reduction, for example:

```text
Inspect(reference)
List(reference, page)
Follow(reference, relation, page)
Find(query, scope)
History(reference)
Diff(left, right)
RenderProjection(reference, style)
DiscoverActions(context)
StartOperation(command)
CancelOperation(operation_id)
Refresh(reference)
```

No Ratatui widget may execute an effect directly.

## 7. Service Port

`scriberig-tui` needs a narrow presentation-facing service boundary so its state machine does not care whether operations are embedded or transported remotely.

Define a TUI service port whose methods correspond to public application operations, not storage primitives. The port may initially be implemented only by an embedded adapter over `scriberig-app`.

The port must preserve:

- explicit application context;
- snapshot or branch context;
- structured application errors;
- capability discovery;
- stable operation identifiers;
- pagination/cursors where the application API provides them;
- cancellation and event observation when supported.

Do not create a TUI-specific semantic request language when an application request/result already exists. The service port should be an adapter that makes existing contracts convenient to consume from the runtime.

A future remote adapter should implement the same TUI service port through `scriberig-client` and protocol types.

---

## 8. Semantic Selection

The TUI keeps one primary semantic selection with optional comparison or parent context.

Represent selection using stable public references. Conceptually it must be able to point at at least:

```text
entity
exact revision
snapshot
relation/list result item
projection
session object
operation
change or conflict object
```

Do not encode selection as a table row index. A view may maintain a cursor index, but activating that row resolves to the stable semantic reference stored in the row model.

Selection carries enough context to explain what is being observed, such as the active snapshot or branch. Exact-revision selections remain exact even when the current branch advances.

---

## 9. Navigation Model

Navigation history and focus are independent concepts.

### Navigation history

Activating semantic references pushes locations onto a back/forward stack similar to a browser. A location includes:

```text
semantic selection
active primary view
snapshot/branch context needed by the view
optional comparison target
```

Going back must not invoke a semantic mutation.

### Focus

Focus identifies which visible interactive region receives navigation input. Focus moves among panes/overlays without changing semantic history unless the user activates a different semantic object.

### Cursor state

Each list-like view may retain presentation cursor/scroll state keyed to its navigation location. This state is disposable and must never become semantic identity.

---

## 10. Rendering Contract

Rendering is a pure read of `TuiState` and the current terminal rectangle.

Rendering must not:

- call application services;
- read the filesystem;
- sleep or wait on channels;
- mutate canonical state;
- update navigation history as a side effect;
- change state merely because a region was too small.

The render layer may derive temporary layout rectangles and shortened display strings from state.

Where possible, views should render from small view models rather than domain-internal structures. This makes `TestBackend` assertions stable and keeps product presentation independent from storage representation.

---

## 11. Terminal Lifecycle

The terminal wrapper owns setup and restoration as one RAII-style responsibility.

Startup should perform the supported equivalents of:

```text
verify interactive terminal when required
enable raw mode
enter alternate screen
hide cursor when appropriate
enable bracketed paste when input uses it
optionally enable mouse capture
clear/draw initial frame
```

Normal teardown performs the inverse.

The implementation must attempt restoration on:

- normal quit;
- an error returned by the event loop;
- Ctrl-C/shutdown handling;
- panic, by using a panic hook or another robust restoration strategy that composes with the process's existing hook.

Teardown must be idempotent enough that an error during shutdown does not intentionally skip the remaining restoration steps.

Do not put application/business cleanup into the terminal guard.

---

## 12. Event Loop and Responsiveness

The event loop should redraw when state changed, the terminal resized, or a bounded periodic refresh is required. It should not busy-spin at terminal frame rate when nothing changed.

Semantic work must happen outside the render function. The first local implementation may use a small worker/executor abstraction rather than committing the whole product to a specific async runtime.

The runtime must be able to accept result/progress events while the user continues navigating local UI state.

For request/result pairs where stale responses are possible, include a generation/request token in TUI state. A response for an obsolete view must not overwrite a newer selection's view model.

Cancellation should use the application's operation/cancellation mechanism when one exists. Dropping a TUI view alone must not falsely report an application operation as cancelled.

---

## 13. Loading and Error State

Every effect-backed view uses an explicit load state equivalent to:

```text
NotRequested
Loading { request }
Ready { data, freshness }
Failed { structured_category, message }
```

Long-running operations use shared operation lifecycle states rather than inventing another terminal-only lifecycle.

A failed refresh may retain the last successful data as visibly stale if doing so is useful. Stale data must be labeled; it must not silently masquerade as current.

Structured error categories should drive presentation such as permission denied, stale base, conflict, validation failure, unsupported operation, cancellation, and internal failure.

---

## 14. Capability Discovery

The TUI maintains capability/action availability for the current context.

Global UI actions such as help, focus movement, and quit are local presentation commands. Semantic actions such as inspect, follow, diff, branch, validate, apply, reconcile, start agent work, or cancel an operation come from the shared operation/capability model.

A contextual action should carry:

```text
stable action identifier
human label
whether it is currently available
reason when unavailable, when safe to disclose
input requirements
whether it is read-only or state-changing
```

If the application layer does not yet expose sufficient contextual action metadata, add that capability there rather than hard-coding privileged semantic decisions into the TUI.

## 15. Local Composition

The first supported product path is:

```text
srig tui
   |
   v
scriberig-cli parses TUI arguments
   |
   v
apps/scriberig builds local store/application composition
   |
   v
embedded TUI service adapter
   |
   v
scriberig-tui::run(...)
```

`s‍criberig-tui` must not open the SQLite database itself. The composition root does so because concrete persistence selection is product composition.

The local principal should be explicit, for example a principal equivalent to `local-tui`, and its capabilities should be constructed by the same application capability model used elsewhere.

Do not grant unrestricted mutation capability merely because the caller is local.

---

## 16. Remote Composition

A later remote path may be:

```text
srig tui --connect <endpoint>
   |
   v
scriberig-client
   |
   v
public server protocol
   |
   v
same TUI service port/state/views
```

Remote mode may add connection/authentication UI, latency states, reconnect behavior, and event-stream resubscription. It must not change the meaning of semantic actions.

Local-only actions, if any, are reported through capabilities and remain visibly local-only.

---

## 17. Public Crate Entry Point

The public API should be small. It should converge on concepts equivalent to:

```text
TuiConfig
TuiService or adapter trait
run(service, context, config) -> Result<RunOutcome, TuiError>
```

`RunOutcome` should distinguish a normal user exit from any intentional product-level handoff if such handoffs are added later.

Do not expose Ratatui widget types as the main public integration contract. Ratatui is an implementation choice inside the product adapter.

---

## 18. Testing Boundary

The architecture must support four classes of tests:

1. **Reducer tests**: actions produce expected state/effects without a terminal.
2. **Rendering tests**: `TestBackend` frames for representative dimensions and states.
3. **Service-adapter tests**: fixed semantic fixtures return the same references/errors as direct application operations.
4. **Runtime/lifecycle tests**: terminal setup/teardown and event routing through abstractions that do not require corrupting the developer's real terminal.

Cross-surface semantic conformance remains owned by `scriberig-conformance`; TUI tests may provide a callable adapter/model so conformance does not scrape ANSI terminal text.

---

## 19. Initial Milestone Boundary

The first useful milestone includes:

```text
terminal lifecycle
responsive shell
navigation/focus
semantic explorer + inspector
contextual command palette
structured errors
local embedded composition
help
rendering/reducer tests
```

History, diff, projection, change review, sessions, agents, remote mode, and richer operation observation may land in later Level 3 slices without redesigning the runtime.

The first milestone must not fake unsupported semantic operations merely to fill panels.

---

## 20. Implementation References

Current Ratatui guidance should be consulted when implementing terminal lifecycle, event handling, backend selection, and `TestBackend` tests. The design intentionally follows Ratatui's separation between application state/event handling and frame rendering while preserving Scriberig's stricter semantic-operation boundary.
