# Licensing Artifacts, Package Metadata, and Notices

## 1. Purpose

This document turns the licensing requirements in `design/level-1/014. extensibility ecosystem and licensing.md` into concrete repository artifacts and package-level rules.

It is intentionally limited to files and metadata required to make the platform/product licensing boundary visible and enforceable in the repository.

It does not redesign the architecture, introduce a plugin registry, define commercial licensing terms, or choose package names beyond packages that already exist when the implementation task runs.

The controlling rule is:

> Reusable infrastructure is Apache-2.0. The integrated Scriberig product and runtime are AGPL-3.0. The repository must make that boundary obvious from documentation and package metadata.

---

## 2. Required Repository Artifacts

The repository must contain complete license texts for every license used by Scriberig components.

Create:

```text
LICENSES/Apache-2.0.txt
LICENSES/AGPL-3.0.txt
```

The files must contain the complete authoritative license texts, not summaries or modified versions.

The repository must also contain a human-readable explanation of the licensing split.

Create:

```text
LICENSING.md
```

`LICENSING.md` is the repository-level guide required by the Level 1 design. It explains how to determine the license of a component and links the architectural platform/product split to package metadata.

The repository should also expose contribution expectations in a normal contributor-facing location.

Create or update:

```text
CONTRIBUTING.md
```

The contribution text must preserve the Level 1 rule that contributions are accepted under terms compatible with the component being modified. It must not silently introduce copyright assignment, a CLA, a DCO, or permission for future commercial relicensing unless a separate design explicitly adopts such a policy.

---

## 3. Repository-Level Licensing Guide

`LICENSING.md` must explain the following points in plain language.

### 3.1 Reusable platform

Reusable infrastructure is licensed under Apache-2.0 by default.

This category includes reusable capabilities such as:

- identity and core types;
- storage abstractions and implementations;
- graph and schema libraries;
- query and migration libraries;
- projection libraries;
- domain adapters;
- protocol definitions;
- Rust and TypeScript clients;
- client-side models;
- framework bindings;
- headless editor libraries;
- neutral reusable UI components;
- reusable opinionated component libraries such as MUI integrations;
- reusable agent-facing interfaces that do not implement the integrated Scriberig runtime.

### 3.2 Integrated product

The integrated Scriberig product is licensed under AGPL-3.0 by default.

This category includes:

- the reference Scriberig server application;
- the integrated agent execution and orchestration runtime;
- the complete Scriberig editor application;
- product-specific workflows whose purpose is to operate the integrated Scriberig product.

### 3.3 Boundary rule

Licensing follows architectural responsibility, not file extension, programming language, or whether an artifact is a binary.

A CLI or executable that is only a reusable client may remain Apache-2.0. A component that embeds substantial integrated AGPL runtime behavior belongs on the AGPL side.

Reusable functionality must not be moved into AGPL packages merely to make the licensing boundary more restrictive.

### 3.4 Third-party applications

`LICENSING.md` must make clear that a third-party application using Apache-licensed Scriberig platform components does not become part of the AGPL Scriberig product merely because it uses those components or interoperates with Scriberig.

### 3.5 Package metadata is authoritative at package scope

The guide must state that every distributable crate or package declares its own license in its package metadata.

Repository documentation explains the rule; package metadata identifies the license of a particular distributable component.

### 3.6 Third-party dependencies

The guide must state that Scriberig licenses do not replace dependency licenses and that required notices and attribution must be preserved.

### 3.7 Future dual licensing

The guide must not promise commercial dual licensing.

It may state that commercial dual licensing of AGPL-covered components is a possible future decision, and that contributor terms would have to be designed deliberately before relying on that model.

## 4. Rust Package Metadata

Every distributable Rust crate must declare a license in `Cargo.toml`.

The implementation agent must classify the crate by architectural responsibility rather than by name alone.

Default classification:

```text
Reusable platform crate -> Apache-2.0
Integrated product/runtime crate -> AGPL-3.0
```

Examples of reusable platform responsibilities:

```text
core identities
storage
schemas
graph
queries
migrations
projections
domain adapters
protocol types
client SDKs
reusable agent interfaces
```

Examples of integrated product responsibilities:

```text
reference server application
integrated agent runtime/orchestration
product-specific integrated workflows
```

A Rust CLI remains Apache-2.0 when it is primarily a reusable client over public APIs. If it embeds the integrated AGPL runtime, its classification must follow that responsibility.

Workspace-level inherited license metadata may be used only when all inheriting packages have the same correct license. Mixed-license workspaces must not hide the distinction behind one incorrect workspace-wide value.

---

## 5. TypeScript and Web Package Metadata

Every distributable TypeScript/JavaScript package must declare its license in `package.json`.

Default classification:

```text
Reusable package -> Apache-2.0
Complete integrated Scriberig application -> AGPL-3.0
```

Reusable packages include protocol types, clients, semantic models, framework bindings, headless editor logic, neutral components, and MUI-based reusable component libraries.

The complete reference editor application belongs to the AGPL product layer.

Private packages should still declare their license when doing so clarifies the architectural boundary.

The implementation must not make MUI usage itself an AGPL boundary. Reusable MUI components remain part of the Apache platform unless they contain integrated product/runtime behavior.

---

## 6. SPDX Source Identifiers

The Level 1 design permits SPDX identifiers in source files where appropriate, but does not require a repository-wide source-header migration.

Therefore this design does not require adding headers to every source file.

Package metadata and complete license texts are mandatory. Source SPDX headers may be added later under a separate focused task if the repository adopts that convention.

---

## 7. Third-Party Notices and Attribution

The project must preserve notices and attribution required by third-party dependencies, assets, generated code, fonts, parsers, UI frameworks, and other distributed material.

The implementation must not invent attribution obligations where dependencies do not require them.

Use the following repository artifact when there is material that must or should be surfaced centrally:

```text
THIRD_PARTY_NOTICES.md
```

If the initial repository has no distributable third-party material requiring a notice, the file may contain a short statement that dependency-specific notices will be added as distributable dependencies are introduced, or creation may be deferred until such material exists. The implementation agent must not fabricate a list of dependencies that are not present.

Dependency license review is required when adding a new externally distributed component.

---

## 8. Contribution Policy

`CONTRIBUTING.md` must include a licensing section with these rules:

- contributions to Apache-licensed components are contributed under terms compatible with Apache-2.0;
- contributions to AGPL-covered product components are contributed under terms compatible with AGPL-3.0;
- contributors must not add third-party material without preserving its applicable license and notices;
- the repository does not implicitly obtain rights to commercially relicense third-party contributions beyond the licenses and contributor terms actually in force;
- no CLA, DCO, copyright assignment, or commercial relicensing grant is implied by this document.

If the project later adopts a formal CLA, DCO, or commercial relicensing policy, that must be introduced deliberately and the contributor documentation must be updated explicitly.

---

## 9. Protocol Specifications, Schemas, and Fixtures

The Level 1 design requires public protocol specifications, schemas, and conformance fixtures to live with the reusable platform rather than only inside the AGPL reference server.

This document does not create those protocol artifacts because their content is defined by protocol designs, not by licensing policy.

When those files are created, they must live in an Apache-licensed reusable package or platform directory and must not require the AGPL product runtime merely to be consumed.

No Level 3 implementation task in this licensing stream should invent protocol semantics merely to satisfy this placement rule.

---

## 10. Dependency Direction

The expected licensing dependency direction matches the architecture:

```text
Apache reusable platform
        ^
        |
AGPL integrated product
```

AGPL product components may depend on Apache platform components.

Reusable Apache platform components must not depend on integrated AGPL product components.

This is an architectural rule first and a licensing clarity rule second.

An implementation agent that discovers such a reverse dependency must report it rather than hiding it with metadata changes.

---

## 11. Implementation Order

Apply this design in four focused steps.

1. Create the repository license texts and `LICENSING.md`.
2. Apply license declarations to Rust crates once their manifests exist.
3. Apply license declarations to web/TypeScript packages once their manifests exist.
4. Create or update contributor licensing guidance and preserve third-party notices required by dependencies that actually exist.

These steps are intentionally separable so a simple implementation agent does not have to classify the whole repository while also retrieving legal text.

---

## 12. Acceptance Criteria

This design is implemented when all applicable statements below are true.

- `LICENSES/Apache-2.0.txt` contains the complete Apache License 2.0 text.
- `LICENSES/AGPL-3.0.txt` contains the complete GNU Affero General Public License version 3 text selected by the project.
- `LICENSING.md` explains the platform/product split and points developers to package metadata for component-level licensing.
- Every existing distributable Rust crate declares the license appropriate to its architectural responsibility.
- Every existing distributable web package declares the license appropriate to its architectural responsibility.
- The integrated server/runtime/editor are not accidentally labeled as permissive platform components.
- Reusable libraries are not accidentally labeled AGPL merely because the reference product consumes them.
- Contributor documentation preserves the two-license model without inventing relicensing rights.
- Required third-party attribution is preserved for dependencies and assets actually present in distributed components.
- No reusable Apache component depends on an integrated AGPL product component.

---

## 13. Non-Goals

Do not use this design to:

- introduce a plugin registry;
- define package publication policy;
- define protocol semantics;
- add a CLA or DCO;
- promise commercial licensing;
- choose a legal entity or copyright holder;
- rewrite dependency licenses;
- add speculative third-party notices;
- make every source file carry a license header;
- move reusable functionality into AGPL packages for licensing leverage.

Those decisions require separate designs when they become necessary.
