# Persistence Observability and Conformance

## Purpose

The Level 1 persistence model requires the store to be inspectable, verifiable, and replaceable across backends. This document defines the shared conformance and observability surface needed to enforce those guarantees.

## Shared conformance suite

`sr-store` must expose a backend conformance test harness or reusable test functions.

Every backend implementation must pass the same behavior tests for:

- immutable revision insertion and retrieval;
- deterministic duplicate handling;
- snapshot creation and lookup;
- snapshot branching;
- named-root compare-and-set;
- stale-root conflict behavior;
- historical snapshot readability;
- reachability;
- integrity verification;
- transaction semantics that are visible through the public API.

The in-memory backend is not a weaker mock. It is an implementation of the same contract.

## Observability model

Storage observability must expose semantic operational facts without requiring consumers to know backend internals.

Initial concepts:

```text
StoreStats
RootStatus
IntegrityReport
GcReport
IndexStatus
```

`StoreStats` should be able to report counts and sizes where the backend can provide them, such as:

- revisions;
- snapshots;
- named roots;
- reachable canonical objects;
- unreachable candidate objects;
- backend storage bytes where meaningful.

Metrics that are unavailable for a backend should be optional rather than fabricated.

## Diagnostics

Errors returned by storage APIs must distinguish at least:

- not found;
- invalid identifier;
- unsupported encoding/storage version;
- stale root / compare-and-set conflict;
- integrity failure;
- backend I/O or transaction failure;
- invalid operation.

Error types should preserve machine-readable categories while still producing useful human messages.

## Conformance fixtures

The repository should contain deterministic fixtures that describe small histories such as:

```text
S1: A->R1, B->R1
S2 from S1: A->R2
S3 from S1: B->R2
```

The same fixture should be loadable against memory and SQLite implementations and yield the same logical IDs and results.

## Files prescribed by this design

Within `sr-store`:

```text
crates/sr-store/src/
├── error.rs
├── stats.rs
└── conformance.rs
```

Shared integration tests:

```text
crates/sr-store/tests/
└── conformance.rs
```

Backend tests may live in each backend crate, but they should call the shared conformance suite rather than duplicate expected behavior.

## Required tests

- Memory backend passes all conformance cases.
- SQLite backend passes the same conformance cases.
- Equivalent fixture histories produce equivalent logical IDs across backends.
- Stale-root conflicts have the same error category across backends.
- Integrity reports use the same backend-neutral model.
- Optional statistics do not change semantic behavior.

## Non-goals

This document does not define a CLI command, HTTP endpoint, metrics exporter, or web diagnostics panel. Those surfaces can later consume the backend-neutral observability objects.
