# Semantic Plan Graph Persistence, Rollups, Evidence, and Gates

## 1. Purpose

This document turns the plan refinements in:

- `design/level-1/018. durable plans dependency scheduling and multi-model execution.md`;
- `design/level-1/023. semantic plan entities evidence gates and recoverable execution.md`;

into concrete subsystem, storage, mutation, query, and migration design for the current Rust repository.

It also depends on:

- `design/level-1/003. identity revisions and snapshots.md`;

> Planning remains owned by Scriberig session/application semantics, but canonical plan state is persisted as independently revisioned semantic objects and relations in the universal knowledge store. Product DTOs and aggregate Rust views are projections over that state.

## 2. Current Implementation and Target

The current implementation contains a useful domain model in `scriberig-session` with concepts equivalent to:

```text
Plan
PlanNode
PlanDependency
PlanNodeStatus
PlanStatus
WorkerClaim
CoordinatorClaim
```

It also has useful operations equivalent to:

```text
add_node
add_dependency
replan
set_assignment
claim/start node
settle workers
complete node
fail node
refresh readiness
```

Those semantic operations should be preserved/refactored rather than discarded.

The persistence shape is the part that changes.

Current transitional shape is conceptually:

```text
Session
  plans: Vec<Plan>

Plan
  nodes: Vec<PlanNode>
  dependencies: Vec<PlanDependency>
  history: Vec<PlanRevision>
```

with session SQLite persistence serializing the complete graph payload.

Target shape is:

```text
universal semantic store
  EntityId -> RevisionId in Snapshot

Plan entity
PlanNode entities
PlanDependency relation/entities
PlanGate entities
summary relations
attempt/result relations
branch/session references
```

and separately:

```text
rebuildable plan indexes / rollup cache
```

## 3. Crate Ownership

### 3.1 `scriberig-session`

`scriberig-session` remains the semantic owner of session/branch/plan vocabulary and lifecycle rules.

It should own or expose concepts equivalent to:

```text
PlanRecord / PlanRevisionPayload
PlanNodeRecord / PlanNodeRevisionPayload
PlanNodeStatus
PlanStatus
PlanDependencyRecord
PlanGateRecord
PlanGateRequirement
PlanGatePhase
PlanGateWaiver
PlanAttemptReference or equivalent relation shape
plan mutation validation
status transition rules
rollup semantics
readiness/completion semantics
plan view assembly contracts
```

It must not own SQLite SQL.

### 3.2 `scriberig-app`

`scriberig-app` remains the mutation/query operation boundary used by agents, CLI, server, TUI, and web.

It owns application operations equivalent to:

```text
plan_create
plan_add_node
plan_decompose
plan_add_next_step
plan_add_dependency
plan_add_gate
plan_attach_evidence
plan_update_summary
plan_set_assignment
plan_retry_node
plan_replan
plan_start/pause/resume/stop
plan_inspect
plan_node_inspect
```

Exact public operation names may preserve existing APIs for compatibility.

### 3.3 Universal graph/store crates

Use existing universal entity/revision/snapshot/relation/change infrastructure for canonical persistence.

Do not add a planning-specific canonical database beside `scriberig-store`.

Foundation store crates must not depend on `scriberig-session`.

### 3.4 `scriberig-session-sqlite`

The existing session-specific SQLite crate may own session/plan-specific compatibility persistence, derived indexes, or trigger-backed acceleration because it is allowed to know session semantics.

It must not become a second canonical revision store.

Its target role is one or more of:

```text
legacy aggregate migration
session-specific derived indexes
backend-specific plan rollup acceleration
compatibility fixtures/tests
```

The exact role should shrink as universal semantic persistence becomes authoritative.

### 3.5 Product surfaces

`scriberig-protocol`, `scriberig-client`, web model packages, and terminal components consume shared application views/DTOs.

They do not inspect database tables.

## 4. Semantic Object Types

Register/use stable semantic object types equivalent to:

```text
scriberig.session.plan
scriberig.session.plan-node
scriberig.session.plan-dependency
scriberig.session.plan-gate
scriberig.session.plan-attempt     # only if existing branch/execution records are insufficient
```

Prefer relation types for pure references when the universal graph already supports revisioned relation state adequately.

Do not introduce a `plan-attempt` entity solely because it is convenient in one serializer. Reuse branch/claim/result execution records when they provide stable independent identity and exact history.

---

## 5. Plan Revision Payload

A canonical Plan revision should remain small.

Conceptually:

```text
PlanRevisionPayload {
    session: EntityId
    anchor: ContinuationAnchor or semantic reference
    goal: String
    status: PlanStatus
    mutation_revision: u64
    coordinator: optional semantic/branch reference
    coordinator_cursor: optional PlanNode EntityId
    coordinator_generation: u64
    coordinator_claim: optional safe claim reference/state
    default policy/assignment references when applicable
}
```

Do not embed all plan nodes, dependencies, gates, or complete historical plan copies.

`mutation_revision` preserves the existing optimistic concurrency/coordinator mechanism.

Every accepted plan mutation increments it exactly once unless an existing operation explicitly batches multiple logical mutations as one accepted revision.

---

## 6. PlanNode Revision Payload

A node revision contains node-local canonical state only.

Conceptually:

```text
PlanNodeRevisionPayload {
    plan: EntityId
    title: String
    purpose: String
    status: PlanNodeStatus
    expected_result: optional ExpectedResult
    semantic_scope: semantic references
    assignment: optional execution assignment reference
    branch: optional EntityId
    result: optional EntityId
    superseded_by: optional EntityId
    claim_generation: u64
    active_claim: optional WorkerClaim
    abandon_reason: optional PlanAbandonReason
    last_failure: optional exact attempt/result/evidence reference
}
```

The exact payload should avoid copying data already represented as independent relations/entities.

In particular, do not embed:

```text
children arrays solely for reverse navigation
dependency arrays
all evidence objects
all gates
full attempt history
subtree rollup counters
contains_ignored
contains_abandoned
```

Those are relations or derived views.

---

## 7. Structural Plan Relations

Plan membership and decomposition must support exact traversal.

Prefer canonical relations equivalent to:

```text
Plan --contains_plan_node--> PlanNode
PlanNode --decomposes_to--> PlanNode
```

The relation representation must preserve enough history to answer:

```text
which nodes belonged to plan P at snapshot S?
what was N's structural parent at snapshot S?
what are the current direct children of N?
```

Do not require a child content revision merely because it is moved between parents unless the domain deliberately stores parent identity inside the child payload.

If existing graph collection/relation primitives support this better than a `parent` field, prefer them.

---

## 8. Dependency Representation

Represent dependency semantics independently from structural relations.

Target conceptual record:

```text
PlanDependencyRecord {
    id
    plan
    prerequisite
    dependent
    expected_result override/policy when needed
    fulfilled_by: optional exact BranchResult/result reference
    provenance
}
```

Initial policy remains strict successful dependency fulfillment.

Dependency mutations include:

```text
add
remove/supersede
fulfill
clear/rebind only through explicit retry/replan rules
```

A node retry does not erase a prior failed attempt and does not fabricate fulfillment.

The dependency becomes fulfilled only after an accepted result satisfies its contract.

---

## 9. PlanNodeStatus and Direct Transition Rules

Keep one enum equivalent to:

```text
Planned
Ready
Running
Completed
Failed
Abandoned
```

Do not add `PlanNodeWorkState`.

Initial direct transition rules should support at least:

```text
Planned -> Ready
Planned -> Abandoned

Ready -> Running
Ready -> Planned          # dependency/gate became unavailable before claim
Ready -> Abandoned

Running -> Completed
Running -> Failed
Running -> Abandoned      # only through explicit cancellation/settlement policy

Failed -> Ready           # explicit retry/repair operation
Failed -> Abandoned

Completed -> Completed    # idempotent inspection/no-op only; do not silently reopen
Abandoned -> Abandoned
```

If a completed node later reveals required follow-up work, prefer adding a required repair/decomposition child or explicit superseding node rather than silently erasing the completed result.

---

## 10. PlanStatus Recovery Rules

Plan lifecycle may retain the existing vocabulary equivalent to:

```text
Draft
Planned
Running
Paused
Completed
Failed
Cancelled
```

Refine mutation guards so `Failed` is recoverable.

Required explicit recovery path:

```text
Failed -> Paused
Paused -> Running
```

or one equivalent atomic recovery operation that performs the same semantic transition.

`Completed` and `Cancelled` remain terminal for ordinary mutation.

A failed plan must retain all completed nodes/results and failure provenance.

---

## 11. Summary Representation

Use the common session/semantic `Summary` model when available.

Represent current node summary through an explicit relation/reference equivalent to:

```text
PlanNode --summarized_by--> Summary
```

The summary record should retain or be derivable from exact source dependencies.

Application operations:

```text
plan_update_summary(node, summary content/source)
plan_clear_or_supersede_summary(node, ...)
```

must create ordinary semantic revisions/relations.

A node's final result remains independent from its current summary.

---

## 12. Evidence Representation

Evidence is primarily a relation from a node or gate to an existing exact semantic object.

Use an association shape equivalent to:

```text
PlanEvidenceAssociation {
    owner: PlanNode | PlanGate
    role: Supports | Contradicts | Informational
    evidence: SemanticRef
    note/summary: optional
    provenance: operation/user/agent reference
}
```

If the graph layer supports relation properties/revisions, use that mechanism.

If it does not, model the association as a small semantic entity rather than embedding copied evidence payloads.

Evidence references must preserve exact revision/snapshot identity where applicable.

Examples:

```text
node -> BranchResult
node -> ValidationResult
gate -> Decision
gate -> HumanApproval
node -> Candidate
node -> exact entity revision
```

---

## 13. Gate Representation

A gate is a semantic object with stable identity.

Conceptually:

```text
PlanGateRevisionPayload {
    owner: PlanNode
    phase: Entry | Completion
    requirement: PlanGateRequirement
    waiver: optional PlanGateWaiver
    provenance
}
```

Initial typed requirements:

```text
ValidationPassed(reference/profile)
EvidencePresent(kind/reference policy)
DecisionResolved(decision)
HumanApproval(policy/role)
SemanticCondition(reference + safe typed predicate)
RequiredChildCompleted(child)
```

Avoid arbitrary user-supplied executable expressions.

Gate definition and waiver are canonical.

Gate evaluation is derived.

---

## 14. Gate Evaluation

Define a deterministic evaluator:

```text
evaluate_gate(snapshot, gate) ->
    Pending | Satisfied | Failed | Waived
```

Evaluation returns supporting exact evidence references and a bounded reason.

A gate evaluation may be cached/materialized, but cache identity must include the smallest exact inputs that determine it.

The scheduler must never accept a gate cache from a different source snapshot without validation.

Entry gates participate in readiness.

Completion gates participate in completion.

A waived gate is considered satisfied for scheduling/completion but remains visibly waived with provenance.

---

## 15. Required Decomposition

Expose explicit semantic operations for decomposition rather than overloading generic node insertion.

Conceptually:

```text
plan_decompose(parent, children, required=true|false)
plan_add_next_step(anchor/plan, node)
```

`plan_decompose(... required=true)`:

1. creates child node entities;
2. creates structural child relations;
3. creates `RequiredChildCompleted(child)` completion gates or an equivalent grouped gate on the parent;
4. does not create sibling dependency edges unless explicitly requested.

Optional decomposition omits the completion obligation.

The lower-level implementation may group multiple required children into one gate if the semantics remain exact and individually inspectable.

---

## 16. Execution Attempt Provenance

Audit existing branch, claim, model invocation, operation, and `BranchResult` records before introducing a new attempt object.

The system must be able to answer:

```text
how many times was node N attempted?
which branch did each attempt execute?
which claim/generation owned it?
what was each outcome?
what result/failure evidence did it produce?
which attempt produced the accepted node result?
```

Preferred mapping when existing records are sufficient:

```text
PlanNode --attempted_on--> Branch
PlanNode --attempt_result--> BranchResult / failure result
claim generation recorded in execution provenance
```

Introduce `PlanAttempt` only if those relations cannot represent independent retry history safely.

---

## 17. Retry Operation

Add an explicit retry operation rather than making ordinary `start_node` accept failed nodes implicitly.

Conceptually:

```text
plan_retry_node(node, policy)
```

Validation:

- node is currently `Failed`;
- no active claim owns it;
- plan is not completed/cancelled;
- failed result has not satisfied dependencies;
- retry branch policy is valid;
- required dependencies and entry gates can be re-evaluated.

Mutation:

- preserve prior attempt/failure references;
- clear only active claim/current failed-execution binding that must not carry into the next attempt;
- create/bind the next attempt branch according to policy;
- transition direct status to `Ready` when readiness inputs are satisfied, otherwise `Planned`;
- increment plan mutation revision once;
- preserve exact failure evidence.

The next worker claim then uses the normal ready-node claim/start path.

---

## 18. Normal Plan Growth While Running

Refactor mutation guards so a `Running` plan may accept safe ordinary evolution operations.

Allowed while running, subject to coordinator/user authorization and optimistic concurrency:

```text
add node
add next step
decompose existing node
add dependency that does not invalidate already accepted completed work
add gate
attach evidence
update summary
retry failed node
change assignment of unstarted node
```

Operations that invalidate or replace already accepted structure/results use explicit replan/supersession semantics.

Do not require `Paused | Failed` merely to discover and add new work.

---

## 19. Atomic Plan Mutation Batch

Preserve the current plan mutation/CAS concept, but make the durable write a semantic change batch.

An accepted mutation is conceptually:

```text
PlanMutation {
    plan
    expected_plan_mutation_revision
    base_snapshot
    operation/provenance
    entity revision writes
    relation writes/removals/supersessions
    derived-index invalidation/update intents
}
```

Commit flow:

```text
load exact plan/node/relation state at base snapshot
validate operation and expected plan mutation revision
construct immutable successor revisions
construct semantic changes/migration
validate graph/lifecycle/gate/dependency invariants
apply/promote successor snapshot with ordinary conflict handling
refresh or mark derived plan indexes for the resulting snapshot
publish shared application event/result
```

No UI/agent/backend caller receives a direct SQL mutation path.

---

## 20. Plan Mutation Revision and Snapshot CAS

The existing plan-local revision remains useful for focused stale-write detection even though the universal root/snapshot also changes.

Use both identities deliberately:

```text
base snapshot
  proves the exact semantic world observed

plan mutation revision
  provides compact plan-local optimistic concurrency/coordinator generation
```

An application operation should normally reject or reconcile when either required expectation is stale.

Do not use plan mutation revision as a replacement for exact semantic revisions/snapshots.

## 21. Derived PlanNode Aggregate

Define a backend-neutral derived view equivalent to:

```text
PlanNodeAggregate {
    node
    source_snapshot
    effective_status: PlanNodeStatus
    direct_child_counts_by_status
    descendant_failed_count or sufficient equivalent
    descendant_abandoned_count or sufficient equivalent
    ignored_descendant_count
    pending_entry_gate_count
    failed_entry_gate_count
    pending_completion_gate_count
    failed_completion_gate_count
}
```

The exact stored counters may differ if a smaller set is sufficient to update incrementally.

The semantic rollup precedence comes from Level 1 document 023.

This aggregate is not part of PlanNode revision identity.

## 22. Incremental Ancestor Propagation

When one node direct status, structural relation, abandon reason, or gate-derived completion condition changes:

1. recompute/update the affected node aggregate;
2. update the direct parent aggregate;
3. continue upward only while the parent's aggregate changes;
4. stop at the root or first unchanged ancestor.

The normal complexity is `O(depth)` plus local child-counter maintenance, not `O(subtree size)` per read.

Structural reparenting may require updating both old and new ancestor chains.

Bulk import/rebuild may use a bottom-up batch algorithm instead of repeated single-node propagation.

## 23. SQLite Strategy and Triggers

SQLite triggers are permitted but not required.

The generic `scriberig-store-sqlite` revision table stores opaque typed revision payloads and must not gain a dependency on session plan semantics merely to implement triggers.

Therefore trigger-backed rollups are appropriate only if a session-specific SQLite layer maintains normalized derived/index rows such as:

```text
plan_node_index
  plan_id
  node_id
  parent_node_id
  current_revision_id
  direct_status
  abandon_reason
  source_snapshot

plan_node_rollup
  node_id
  effective_status
  status counters
  ignored/abandoned counts
  gate counters
  source_snapshot
```

A trigger may update parent counters when `plan_node_index` changes.

Alternative initial implementation:

```text
session semantic layer computes changed ancestor aggregates
-> session-specific SQLite index transaction writes them
```

Both approaches are valid if they preserve the same backend-neutral semantics.

Do not parse opaque canonical revision blobs inside fragile SQL triggers.

## 24. Derived Index Consistency

Every derived plan index/cache record must identify the canonical state it represents, normally by exact source snapshot and relevant schema/evaluator version.

Scheduler correctness rule:

> Never dispatch work from a derived readiness/rollup record that is known to be stale relative to the authoritative plan snapshot.

If the materialized index is missing/stale:

- recompute the smallest affected plan/ancestor path synchronously when needed for correctness; or
- return a structured temporary-not-ready/index-rebuild condition;
- then refresh the cache.

Do not silently use stale rollups for scheduling decisions.

## 26. Readiness

Refactor readiness to query exact canonical dependency/gate state rather than only fields embedded in one aggregate plan.

Conceptually:

```text
ready(node, snapshot) =
    direct status in {Planned, Ready}
    AND branch/claim policy permits start
    AND every required dependency has exact accepted successful fulfillment
    AND every entry gate evaluates Satisfied or Waived
```

The operation may use validated derived indexes to accelerate the answer.

When readiness changes:

```text
Planned <-> Ready
```

write the direct status transition as ordinary canonical node state when the scheduler currently persists `Ready` explicitly.

Do not introduce a second hidden readiness state machine.

---

## 27. Completion

Node completion requires:

```text
successful accepted BranchResult/result contract
AND all completion gates Satisfied or Waived
```

Completing one node:

1. writes the accepted result reference;
2. writes node status `Completed`;
3. fulfills compatible outgoing dependencies;
4. creates/updates evidence associations as appropriate;
5. invalidates/evaluates dependent readiness;
6. updates affected parent rollups;
7. may complete the whole plan if plan completion policy is satisfied.

A completed node must not retain an active worker claim.

---

## 28. Failure Settlement

Settling a failed attempt:

1. clears the active claim;
2. records exact failure attempt/result/evidence provenance;
3. writes node direct status `Failed`;
4. leaves successful outgoing dependencies unfulfilled;
5. updates ancestor rollups;
6. surfaces failure to the coordinator;
7. does not automatically mark the whole plan irrecoverably terminal.

Coordinator policy may then choose retry, repair child, alternative sibling, replan, pause, or explicit stop.

---

## 29. Abandoned / Ignored Semantics

Use `Abandoned` as the lifecycle status and add a typed reason when needed.

Initial reasons may include:

```text
Ignored
Superseded
Cancelled
NoLongerNeeded
Duplicate
Other
```

Do not require all reasons in the first implementation if only `Ignored`, `Superseded`, and `Cancelled` are needed.

An abandoned descendant does not automatically propagate `Abandoned` to the parent.

Derived plan views expose:

```text
contains_abandoned
contains_ignored
```

Completion policy decides whether an abandoned required child requires a gate waiver/replan before the parent can complete.

## 34. Legacy Aggregate Migration

Provide deterministic migration from stored aggregate plans.

For each stored legacy plan:

1. preserve `Plan.id`;
2. preserve every `PlanNode.id`;
3. create independent Plan/PlanNode revisions;
4. convert parent structure to semantic relations;
5. convert dependencies to independent relation/entities;
6. preserve branch/result/assignment/supersession/claim-generation data that remains valid;
7. preserve plan mutation revision/coordinator generation;
8. record migration provenance;
9. rebuild derived rollup/index state from canonical entities;
10. verify assembled `PlanView` is semantically equivalent to the legacy plan before promotion.

Historical `history: Vec<PlanRevision>` snapshots must not simply be discarded.

Migration should retain them as historical import/provenance records or convert them to snapshot/change history when feasible. The implementation task must inspect current retained data and choose the least lossy representation.

---

## 35. No Uncontrolled Dual Write

During migration, do not let aggregate session-plan storage and universal semantic plan storage both independently accept writes.

Use one of these bounded strategies:

```text
A. one-time migration then semantic store authoritative
B. semantic store authoritative + legacy aggregate regenerated as read-only compatibility projection
C. short explicit compatibility phase with one canonical write path and deterministic projection into the other representation
```

Never accept conflicting writes to both representations.

---

## 36. Concurrency and Coordinator Safety

The single auto-advancing coordinator invariant remains unchanged.

Every coordinator mutation must validate:

```text
plan identity
expected plan mutation revision
coordinator claim/generation
exact base snapshot when required
node/claim generation for worker settlement
```

Independent node entities do not authorize independent global plan coordinators.

Multiple worker branches may still settle independent nodes concurrently through conflict-aware semantic changes. The application layer must retry/rebase disjoint mutations safely rather than serializing all workers through one giant session blob when the underlying semantic changes are non-conflicting.

---

## 37. Implementation Order

Implement in this order:

1. define semantic plan codecs/schemas and relation vocabulary;
2. build plan graph read/view assembly over universal snapshots;
3. implement semantic mutation batch/CAS for Plan + PlanNode;
4. migrate add-node/dependency/assignment operations;
5. add summary/evidence/gate semantic objects and evaluation;
6. add required-decomposition completion gates;
7. make `Failed` recoverable and add explicit retry/attempt provenance;
8. add backend-neutral rollup semantics and in-memory/reference implementation;
9. add session-specific SQLite derived index/optional triggers;
10. migrate worker settlement/readiness/coordinator flows;
11. add aggregate-plan legacy migration/compatibility projection;
12. update protocol/client/web/TUI shared views on top of the merged upstream-first TUI design;
13. remove canonical aggregate plan persistence after conformance proves the semantic path.

---

## 38. Completion Criteria

This Level 2 design is satisfied when:

- `Plan` and each `PlanNode` are independently addressable semantic entities with immutable revisions;
- current snapshots resolve exact plan/node revisions;
- plan membership, decomposition, and dependencies are traversable without deserializing one full plan blob;
- plan mutation revision and coordinator claim semantics remain intact;
- one accepted application mutation atomically promotes the corresponding semantic changes;
- running plans can add safe new work without mandatory replan mode;
- summaries are first-class semantic references distinct from purpose/result;
- evidence references exact existing semantic objects;
- gates are first-class typed requirements with exact evidence and explicit waivers;
- readiness checks dependencies plus entry gates;
- completion checks result contracts plus completion gates;
- `Failed` nodes can be explicitly retried without erasing failed-attempt provenance;
- plan-level `Failed` can recover through an explicit repair/replan path;
- parent effective status and ignored/abandoned flags are derived, rebuildable, and excluded from canonical node revision identity;
- repeated parent-status reads do not require full-subtree traversal;
- SQLite-specific acceleration does not leak into public semantic contracts;
- legacy aggregate plan data can be migrated deterministically without changing stable plan/node identities;
- no uncontrolled dual-write canonical plan representations remain;
- protocol/web/TUI consume the same shared Plan/PlanNode views and operations;
- TUI changes, if implemented, sit on top of the upstream-first RPI component design from Level 2 document 032 and task 148.
