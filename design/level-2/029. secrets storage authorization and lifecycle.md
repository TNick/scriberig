# Secrets Storage, Authorization, and Lifecycle

## Contract

Follow the trust boundary in Level 1 document 013 and the provider/session
boundaries in Level 2 documents 023 and 024. `scriberig-secrets` is an
Apache-2.0 reusable crate without semantic storage or runtime dependencies.

Configuration contains an atomic nullable `credential` reference with a tagged
`source`: `keyring` plus `name`, `environment` plus `name`, or `file` plus an
absolute `path`. Normalize `api_key_env` aliases within each source layer.
Conflicting aliases fail before merging. No inline values or interpolation.

Credential use requires an exact normalized base URL, canonical project root,
provider purpose, and execution mode binding in a protected user registry.
System policy, when present, is a second mandatory allowlist. A project cannot
write either policy. Explicit CLI environment-reference and base-URL pairs may
grant a process-local binding, subject to system restrictions. Bindings are
checked before reading a credential or making a network request.

## Storage and lifecycle

Use Windows Credential Manager, Apple Keychain, or Linux Secret Service with
explicit platform features. Headless deployments may use environment or
protected mounted-file references. Backend failure never selects plaintext.
Protected buffers zeroize on drop; HTTP-library copies are outside that promise.

Registry metadata lives at the conventional user config directory under
`secrets/registry.json`. System restrictions live under the corresponding
system directory at `secrets/policy.json`. Atomic registry replacement is
serialized by an OS file lock in the protected directory. No values or value
hashes enter the registry. Lifecycle failures must leave authorization disabled
or report an actionable partial operation. Management is local CLI only.

HTTPS is mandatory except explicitly bound numeric loopback HTTP. URLs cannot
contain user information, queries, or fragments. Redirects are disabled for
streaming and buffered calls. Resolve again before each request for rotation.

## Disclosure boundaries

No value enters sessions, protocol DTOs, events, model context, fingerprints,
configuration output, or audit metadata. Only safe categories leave adapters.
Known sensitive files and registered secret paths are excluded at scan, import,
candidate, and project-copy boundaries. Child processes receive an allowlisted
environment. Arbitrary code under the credential owner's OS identity remains
outside this protection: untrusted builds require a separate isolated identity.

## Migration

Legacy environment flags remain supported. Implicit credentials combined with
project-selected destinations require a binding. Existing stored secrets need
issuer-side rotation and an explicit database/backup purge or rebuild procedure;
immutable history must never be silently rewritten.
