# Terminal UI Views, Interaction, and Conformance

## 1. Purpose

This document defines the concrete product-facing view model and interaction contract for the Scriberig TUI.

It builds on:

1. `design/level-1/015. terminal user interface principles.md`;
2. `design/level-2/021. terminal ui runtime and state architecture.md`;
3. `design/level-2/010. universal query and operation implementation.md`;
4. `design/level-2/012. capability matrix and cross surface conformance.md`;
5. `design/level-2/020. repository scaffold conventions and native command surface.md`.

This document is intentionally concrete about panes, views, default key behavior, responsive layout, contextual operations, and acceptance behavior. It does not move semantic ownership into the TUI.

---

## 2. Workspace Shell

The default shell has five logical regions:

```text
+---------------------------------------------------------------+
| context bar: project / branch-or-snapshot / selection / state |
+------------------+-------------------------+------------------+
|                  |                         |                  |
| explorer         | primary view            | inspector        |
|                  |                         |                  |
|                  |                         |                  |
+------------------+-------------------------+------------------+
| status / operation / diagnostics                              |
+---------------------------------------------------------------+
| contextual key hints                                          |
+---------------------------------------------------------------+
```

The three body regions are logical panes, not permanent rectangles. Responsive layout may collapse or replace them.

### Context bar

Shows enough context to answer:

```text
Where am I?
What semantic object is selected?
Am I observing a branch, current snapshot, or exact historical revision?
Is the view stale, loading, conflicted, or validating?
```

Do not display full identifiers by default when a useful short form exists, but provide a way to reveal/copy the exact identifier.

### Status region

Shows transient application status, structured errors, long-running operation progress, and connection state in remote mode.

### Key-hint region

Shows a small set of actions relevant to the focused view. It is not the complete help system.

---

## 3. Responsive Layout

Use these initial width classes unless implementation testing demonstrates that a nearby threshold is materially better:

```text
>= 120 columns: three-pane layout
80..119 columns: explorer + primary, inspector available as a view/overlay
< 80 columns: one primary pane, other regions become navigable views/overlays
```

At low height, remove decorative spacing and reduce status/key-hint rows before making semantic content unusable.

When the terminal is too small for safe interaction, render a clear minimum-size message that still permits help and quit. Do not panic because a layout region reached zero width or height.

Resize changes presentation only. It must not reset semantic selection or navigation history.

---

## 4. Focus and Overlay Rules

At most one pane or overlay owns keyboard focus at a time.

Focus order for the wide shell is:

```text
Explorer -> Primary -> Inspector -> Explorer
```

An overlay temporarily owns focus until it closes. The underlying semantic selection remains visible where practical and is restored without a new semantic request unless refresh is required.

Overlay precedence from most modal to least modal is:

```text
confirmation / review
text input
command palette
help
non-modal notification
```

Do not allow multiple modal overlays to compete for input. Opening a stronger modal replaces or suspends the weaker one according to explicit state transitions.

---

## 5. Default Global Keys

The initial global key contract is:

```text
Ctrl-C        request quit, or cancel the active cancellable input/operation context
Esc           close overlay / cancel local interaction / move toward browse mode
Tab           focus next region
Shift-Tab     focus previous region
Enter         activate the focused semantic row or default contextual action
Up/Down       move within the focused list or scrollable region
Left/Right    collapse/expand where the focused view has hierarchy semantics
Backspace     navigate back when not editing text
:             open contextual command palette
/             open find/search input
?             open help
r             refresh current semantic view when no text input owns the key
q             request quit from ordinary browse state
```

`h`, `j`, `k`, and `l` may be provided as aliases for directional navigation in ordinary browse state, but arrow keys remain supported and documented.

Keys that would conflict with text input are interpreted as text while an input field owns focus.

The keymap implementation must be data-driven enough for help and key hints to derive labels from the same bindings rather than duplicating strings across widgets.

User-configurable keymaps are not required for the first implementation, but action identifiers must be separated from key chords so configuration can be added later.

## 6. Command Palette

The command palette is the universal discoverability surface.

It combines two action classes:

### Local presentation actions

Examples:

```text
open help
switch primary view
focus inspector
go back
refresh
copy exact identifier
quit
```

### Semantic actions

These come from shared capability/operation availability for the current selection/context, for example:

```text
inspect
list children
follow relation
show history
compare
render projection
validate candidate
review migration
apply
reconcile
start session
submit agent command
cancel operation
```

Semantic palette rows must not be enabled based solely on a hard-coded TUI list. The TUI may know how to render inputs for an action identifier, but availability comes from the application/client layer.

The palette supports fuzzy or substring filtering over labels and aliases. Filtering the palette is presentation logic; determining whether an action is authorized is not.

---

## 7. Semantic Explorer

The Explorer provides progressive navigation over semantic structure.

It must support rows with at least:

```text
stable semantic reference
kind/type summary
human label or short description
expandability/navigation affordance
loading/error child state when expanded
optional trust/status marker
```

The explorer does not assume every object has filesystem-like children. Expansion may represent:

- collection members;
- typed relations;
- session branches;
- change/conflict groups;
- snapshot roots;
- projection/source links;
- domain-advertised semantic children.

The application query model determines what can be listed or followed.

Expansion state is local presentation state keyed by stable references.

---

## 8. Inspector

The Inspector shows a progressive semantic summary for the primary selection.

The compact inspector should include, when available:

```text
kind/schema
stable entity/reference identity
exact revision identity when relevant
short description
important properties
relation summaries
collection membership summary
snapshot/branch context
provenance/trust summary
available next operations
```

Deep provenance, large properties, long descriptions, and exhaustive relations are loaded or opened deliberately rather than overflowing the default inspector.

The inspector must clearly distinguish conceptual entity identity from exact revision identity.

---

## 9. Primary Views

The Primary region switches among views while preserving the current semantic location when compatible.

### 9.1 Overview

Shows a richer version of the selected object's summary, descriptions, properties, relations, and useful next actions.

### 9.2 Query and find results

Shows bounded/paginated results. Every row stores a stable result handle. The view displays scope, query summary, result count information when available, and continuation state.

### 9.3 History

Shows lineage/history returned by shared operations. Activating a historical revision creates an exact-revision semantic selection. The UI must not silently replace it with the current entity revision.

### 9.4 Diff

Shows semantic differences between two explicit references/snapshots/revisions. The left/base and right/target identities remain visible in the view header.

The TUI may render text-oriented diff blocks where returned by a projection/domain, but it must not infer semantic equality from terminal text.

### 9.5 Projection

Shows rendered projection content plus projection identity, style where relevant, source semantic reference, and synchronization state.

The initial view may be read-only. External editing or reconciliation actions are invoked through shared operations, not by writing files from the widget.

### 9.6 Changes, conflicts, and validation

Shows proposed migrations/changes, base snapshot, affected objects, conflicts, validation evidence, and approval/application actions.

This is the required review surface before canonical state-changing actions where a reviewable proposal exists.

### 9.7 Session

Shows session tree/branch structure, turns, summaries, tool invocations/results, durable promoted knowledge, and current agent-operation state where available.

Transient branches must be visibly distinct from canonical project state.

### 9.8 Operations

Shows queued/running/completed/failed/cancelled operations using shared operation identifiers and lifecycle states. Users can inspect result references and request cancellation where the capability exists.

## 10. Text and Structured Content Rendering

Terminal rendering should preserve semantic structure without becoming a full text editor.

For structured text:

- wrap at the current view width;
- preserve paragraph and heading boundaries;
- render code blocks with indentation and optional syntax styling when available;
- allow vertical scrolling independent of semantic selection;
- expose exact source/projection identity in metadata rather than embedding invisible terminal-only markers.

Do not rely on ANSI sequences embedded in application strings. Styling is applied by the TUI from structured or plain safe content.

Untrusted or externally sourced control characters must not be emitted to the terminal as executable control sequences. Normalize or visibly escape terminal control content before rendering.

## 11. Mutation and Review Workflow

Semantic actions are classified as read-only or state-changing.

Read-only actions may start immediately after required input is collected.

A state-changing action follows the logical flow:

```text
select action
    |
    v
collect explicit inputs
    |
    v
obtain/construct reviewable proposal when supported
    |
    v
show base + affected objects + conflicts + validation/trust
    |
    v
user confirms intent
    |
    v
invoke shared application command
    |
    v
observe operation/result
    |
    v
refresh affected semantic locations
```

The confirmation overlay must include the action label and affected context. Destructive or canonical actions may require a stronger explicit confirmation than reversible presentation actions.

If the base becomes stale between review and application, show the shared stale-base/conflict result. Never silently recompute and apply against a different base without renewed user intent.

---

## 12. Trust, Permission, and Validation Presentation

Trust and permission state must remain visible enough for users to understand why an action is unavailable or risky.

Use textual/symbolic labels in addition to color for states such as:

```text
trusted / authoritative
external
model-generated
derived
unvalidated
validated
validation failed
conflicted
permission denied
stale
```

The TUI may summarize evidence but must preserve links/handles needed to inspect full provenance and validation records through shared operations.

Do not expose sensitive denial reasons that the application layer intentionally redacts.

---

## 13. Sessions and Agent Input

Agent input uses an explicit text-input overlay or session composer. It must support multiline or pasted input without treating pasted control text as TUI commands.

Submitting agent input starts or extends a session through the shared session/agent application boundary. The TUI observes the resulting operation and session objects.

Streaming model text, if available, is presentation of an in-progress operation. It is not canonical project knowledge until the session/domain layer records it according to its own rules.

Users must be able to leave an agent view and inspect other knowledge while work continues, unless the application operation explicitly requires exclusive interaction.

---

## 14. Notifications and Errors

Notifications have bounded lifetime and severity but must not be the only place important failures are visible.

Recommended categories:

```text
info
success
warning
error
```

Structured semantic failures that need action, such as conflicts or validation failures, should open or link to a durable result view rather than disappearing as a toast-like notification.

Internal failures may show a short safe message plus a correlation/operation identifier where available. Avoid dumping Rust debug output, secrets, raw SQL, or untrusted terminal control sequences into the UI.

---

## 15. Clipboard and External Terminal Integration

Core functionality must not require clipboard integration.

If copy support is implemented, prefer copying stable identifiers, references, or explicitly selected plain text. Do not emit terminal escape sequences for clipboard access unless the behavior is opt-in or the security implications are clearly understood for the supported terminal environment.

Opening an external editor/browser is outside the first milestone. Later integrations must suspend/restore terminal mode correctly and return through explicit product actions.

---

## 16. Local TUI Command Surface

`design/level-2/020. repository scaffold conventions and native command surface.md` already establishes:

```text
srig tui
```

The first concrete implementation may add arguments without changing that top-level command. Recommended local option:

```text
srig tui --db <PATH>
```

with the same development database default used by other local native modes where practical.

A later remote mode may add a mutually exclusive form equivalent to:

```text
srig tui --connect <ENDPOINT>
```

The CLI crate owns parsing. The composition root owns constructing local or remote services. `scriberig-tui` owns neither database path parsing nor HTTP endpoint parsing.

---

## 17. Accessibility and Terminal Compatibility

Acceptance requirements include:

- all core workflows usable without mouse input;
- focus indicated by more than color alone;
- important state represented by text or symbols plus styling;
- usable behavior with reduced/no color;
- resize at runtime without state loss or panic;
- bounded behavior for narrow/small terminals;
- control characters sanitized before terminal rendering;
- paste handled as input data rather than key-command replay;
- Unicode decoration not required for semantic comprehension.

A future theme system may customize appearance, but theme choices must not change semantic behavior.

---

## 18. Rendering and Interaction Tests

Use Ratatui's test backend or an equivalent in-memory backend to verify representative frames.

Do not snapshot the entire application for every change. Prefer focused assertions on semantic regions and a small number of high-value full-frame fixtures.

Required size classes include at least:

```text
140x40 wide
100x30 medium
72x24 narrow
very small terminal guard case
```

Reducer/keymap tests should verify that the same action identifiers drive visible key hints/help.

Tests for pasted/untrusted text must verify that control sequences are rendered harmlessly.

---

## 19. Cross-Surface Conformance

The capability matrix must represent TUI coverage honestly.

A capability progresses through:

```text
planned -> implemented -> verified
```

only when the corresponding TUI path exists and is tested.

For semantic conformance, expose a testable adapter/model boundary so `scriberig-conformance` can compare TUI-invoked semantics against application/server/client semantics without scraping terminal cells or ANSI output.

At minimum, the first verified TUI semantic slice should cover:

```text
inspect_entity
runtime_capabilities
```

Later slices should add operation lifecycle, cancellation, event observation, history/diff, and mutation review as their underlying application capabilities become available.

---

## 20. Performance Acceptance

The TUI must remain responsive to local navigation and quit/help input while semantic work is pending.

Rendering work should be proportional to visible/bounded view models, not the total database size.

Lists use application pagination or bounded requests. The TUI must not fetch an unbounded universe merely to implement scrolling.

Redraw should be event-driven or bounded by a modest frame/tick rate. A static screen must not consume a CPU core through a busy loop.

Performance tests should prefer deterministic large synthetic view models over timing external services.

---

## 21. First-Version Non-Goals

The first TUI does not need:

- user-authored theme files;
- user-configurable keymaps;
- plugin-defined terminal widgets;
- arbitrary source-file editing;
- a terminal emulator inside the TUI;
- image rendering protocols;
- mouse-only interactions;
- a separate TUI persistence database;
- direct SQL browsing.

These may be added later only if they preserve the Level 1 TUI invariants and shared operation model.
