# Provider Continuation and Observable Model Execution

## 1. Purpose

This document translates `design/level-1/020. provider continuation state and observable model execution.md` into concrete subsystem boundaries for the current Rust implementation.

It also refines the implementation contracts in:

- `design/level-2/023. agent runtime model provider and branch orchestration.md`;
- `design/level-2/024. agent operations protocol and cross surface product contract.md`;
- task 133 shared agent-console trace controls;
- task 134 recursive TUI projection;
- task 135 recursive semantic agent execution.

The central implementation rule is:

> Scriberig persists canonical branch/session execution history and a complete safe provider-neutral effective model request. Provider-native continuation handles are opaque branch-local runtime metadata used only when they still match the canonical context lineage.

## 3. Provider-Neutral Continuation Contract

Introduce or extend one provider-neutral runtime concept equivalent to:

```rust
struct ProviderContinuationState {
    provider_profile: ProviderProfileId,
    provider_kind: ProviderKind,
    branch: EntityId,
    strategy: ProviderContinuationStrategy,
    opaque_handle: SecretSafeOpaqueId,
    context_fingerprint: ContextFingerprint,
    created_for_invocation: EntityId,
    last_used_invocation: EntityId,
    status: ProviderContinuationStatus,
    metadata: BTreeMap<String, String>,
}

enum ProviderContinuationStrategy {
    Conversation,
    PreviousResponse,
    LocalSession,
    ProviderSpecific(String),
}

enum ProviderContinuationStatus {
    Reusable,
    Stale,
    Unavailable,
    Expired,
    Unknown,
}
```

Exact Rust names may differ.

Requirements:

- opaque handle never becomes `SessionId` or `BranchId`;
- no credential values in the structure;
- no raw provider request/response bodies in the structure;
- one branch may accumulate historical continuation records across provider/profile switches;
- only the continuation matching the resolved provider/profile and context lineage is considered reusable;
- durability policy may retain enough metadata to attempt restart reuse, but correctness must never depend on successful provider-state recovery.

---

## 4. Continuation Repository Boundary

Continuation state may be persisted with session/runtime records or through another existing durable runtime repository, but ownership must remain explicit.

The owning API needs operations equivalent to:

```text
get continuation for branch + provider/profile
put continuation after successful initialization/use
mark continuation stale
mark continuation unavailable
record successor/fork relationship when useful
```

Do not expose a generic mutable map directly to TUI/web/server layers.

The application/protocol may expose safe read-only provenance such as provider kind/strategy/status, but mutation of continuation handles belongs to the runtime/provider boundary.

## 5. Canonical Effective Request Record

The existing bounded `ModelRequestProjection` is useful for normal activity rendering but is insufficient for the explicit `Full` prompt requirement.

Add a durable or durably retrievable complete safe request record concept equivalent to:

```rust
struct CanonicalModelRequest {
    invocation: EntityId,
    session: EntityId,
    branch: EntityId,
    continuation_anchor: Option<ContinuationAnchorRef>,
    context_fingerprint: ContextFingerprint,
    instructions: Vec<RequestSection>,
    messages: Vec<RequestMessage>,
    semantic_context: Vec<RequestContextItem>,
    dependency_results: Vec<SemanticRef>,
    ancestor_results: Vec<SemanticRef>,
    tools: Vec<ModelRequestTool>,
    structured_output: Option<SafeSchema>,
    model: ResolvedModelConfig,
    provider_continuation: Option<SafeContinuationRef>,
    estimated_tokens: Option<u64>,
    redactions: Vec<RedactionRecord>,
}
```

The exact representation should reuse existing provider-neutral context/message types instead of duplicating them.

The request must be constructed **after Scriberig context compilation and before provider-specific serialization**.

This record is the canonical source for prompt inspection.

## 6. Bounded Activity Projection Versus Full Detail

Keep two layers:

### Bounded ordinary projection

Suitable for activity lists/event streams:

```text
model identity
thinking level
section/message counts
bounded snippets
truncated flag
durable full-detail ref
```

### Full safe detail

Fetched on demand using stable invocation/request identity:

```text
all safe instruction sections
all safe effective messages/context sections
all safe tool definitions
all safe dependency/ancestor result projections
resolved execution config
continuation strategy/status/ref
redaction markers
```

Do not force the full request through every live event.

Do not make `Full` mean "increase a truncation limit until it is probably enough".

---

## 7. Effective Context with Provider Continuation

When the provider wire request contains only new input plus a continuation identifier, `CanonicalModelRequest` must still describe the complete effective Scriberig context.

The runtime already owns enough information to compile/fingerprint context. Preserve a request representation before handing work to the provider adapter.

Conceptual flow:

```text
ContextCompiler
   -> CompiledContext
   -> CanonicalModelRequest
   -> request fingerprint
   -> continuation reuse/reseed decision
   -> provider serialization
```

If continuation reuse allows the provider adapter to omit repeated items on the wire, that is an adapter optimization after canonical request construction.

---

## 8. Continuation Reuse Algorithm

Implement a deterministic decision equivalent to:

```text
1. resolve branch execution assignment
2. compile exact Scriberig effective context
3. compute context fingerprint / continuation lineage fingerprint
4. load continuation for branch + provider/profile
5. if none -> initialize new provider state or run stateless
6. if provider/profile mismatch -> do not reuse
7. if lineage matches expected predecessor -> reuse
8. if lineage can be safely forked by provider capability -> fork explicitly
9. otherwise mark stale and reseed from canonical request
10. invoke provider
11. record returned successor provider state/request IDs
12. bind successor state to resulting Scriberig invocation/context lineage
```

Tests must not use wall-clock coincidence to decide compatibility.

---

## 9. Context Lineage and Fingerprints

Do not assume one static request hash is enough for a multi-turn provider conversation.

Represent or derive a lineage concept that can answer:

```text
Does continuation P contain exactly the provider-visible state expected before invocation I?
```

A reasonable first implementation may use:

```text
compiled-context fingerprint
+ previous invocation identity/fingerprint
+ provider/profile/model identity
+ continuation strategy
```

The exact hash schema must remain deterministic and secret-free.

If a local-model or other-provider turn changes canonical branch history, the old OpenAI continuation must no longer be considered the automatic successor unless the current context compiler deliberately excludes that turn and the fingerprints prove equivalence.

## 10. OpenAI Adapter Strategy

The OpenAI adapter should support provider capabilities equivalent to:

```text
conversation continuation
previous-response continuation
provider-visible reasoning items/summaries
response/request IDs
```

Do not expose OpenAI types above the adapter boundary.

### Conversation strategy

When enabled for an isolated branch:

```text
branch -> OpenAI conversation
```

Initialize/seeding behavior must use the branch's compiled canonical context.

### Previous-response strategy

Reuse/fork `previous_response_id` only where the runtime can prove exact lineage.

Resend effective top-level instructions as required by provider semantics.

### Mutual exclusion

The adapter must never send both a Conversation reference and `previous_response_id` in one request when the provider forbids that combination.

Represent the strategy choice explicitly rather than relying on `Option` field accidents.

---

## 11. Provider Switching

When branch execution assignment changes provider/profile:

1. keep old continuation record as provenance/history;
2. do not pass opaque continuation state to the new provider;
3. compile current canonical Scriberig context;
4. establish new provider state if supported;
5. record the new state under the new provider/profile;
6. if later switching back, validate the old continuation against current context lineage before reuse.

Never treat "same model name" as proof that provider state is compatible.

## 12. Observable Reasoning Segment Model

Extend provider-neutral model output/activity types to represent ordered provider-visible reasoning segments.

Conceptually:

```rust
struct ObservableReasoningSegment {
    id: EntityId,
    invocation: EntityId,
    branch: EntityId,
    ordinal: u64,
    kind: ObservableReasoningKind,
    text: String,
    completeness: ReasoningCompleteness,
    provider_ref: Option<String>,
}

enum ObservableReasoningKind {
    RuntimeStatus,
    ProviderSummary,
    ProviderVisibleReasoning,
}

enum ReasoningCompleteness {
    SummaryOnly,
    FullAvailable,
}
```

Do not add a `HiddenChainOfThought` or equivalent type.

Reasoning text enters these records only when it is explicitly safe/user-visible according to provider semantics.

---

## 13. Activity Ordering

Reasoning segments must share the same deterministic invocation-local ordering system as tool/semantic calls, results, model outputs, and validation/status events.

A fake-provider sequence such as:

```text
reasoning 1
semantic operation A
result A
reasoning 2
tool B
result B
reasoning 3
assistant output
```

must be recoverable exactly from shared activity state.

Hiding reasoning in a client removes only reasoning rows. It must not reorder the remaining operations/results.

If current activity kinds are typed but content records are split across collections, introduce the minimum shared ordering/correlation representation necessary to project one causal stream.

## 15. Application Detail APIs

Extend the existing `scriberig-app::agent_console::detail` ownership rather than creating TUI/web-specific detail fetch paths.

Provide application operations equivalent to:

```text
get_model_request_summary(invocation)
get_model_request_full(invocation)
get_reasoning_segments(invocation, detail)
get_tool_result_detail(...)
```

Full model-request retrieval must:

- require stable invocation/request identity;
- return safe/redacted provider-neutral structures;
- never expose credential values;
- return a structured unavailable/retention result when complete detail was not retained;
- never re-execute a model to reconstruct detail.

---

## 16. Protocol Contract

Protocol DTOs should preserve the distinction between:

```text
activity summary
full request detail
reasoning segment summary/full-available detail
provider continuation provenance
```

Do not serialize provider-native wire types directly.

A request-detail response should be versionable and structured, not one giant prompt string.

Clients may render it as text, but the protocol keeps sections/messages/tools/config separate.

---

## 17. Server and Client

Server routes/actions should map directly to application detail operations.

Remote clients must be able to perform the same presentation changes as embedded clients without changing execution.

Required semantics:

```text
fetch full prompt detail -> read-only
fetch reasoning detail -> read-only
change local/shared presentation preference -> presentation only
continuation reuse/reseed -> runtime only
```

Do not add a server endpoint allowing clients to set arbitrary provider continuation IDs.

---

## 18. TUI and Web Rendering

TUI/web consume the same ordered activity + detail contract.

When prompt mode is `Full`, the invocation row can expand/fetch the complete safe effective request.

When reasoning is `FullAvailable`, render every provider-visible reasoning segment in its correct position around tool/semantic activity.

The two controls are independent.

Rendering must distinguish:

```text
provider-visible reasoning
runtime status
semantic operation
generic external tool/process
assistant output
```

Do not imply that provider-visible reasoning is hidden chain-of-thought.

---

## 19. Retention and Availability

Define explicit retention policy for complete safe request records and observable reasoning segments.

At minimum, settled invocation history that claims to support later `Full` inspection must retain or durably reference the full safe request.

If configurable retention is introduced later, APIs must report:

```text
available
expired/not-retained
redacted
provider-only/unavailable
```

Never silently substitute a truncated summary while labeling it `Full`.

---

## 20. Security Requirements

Before persistence/public exposure, redact or omit:

```text
credentials
authorization headers
secret environment values
provider-secret connection fields
sensitive tool parameters according to capability policy
provider-private hidden reasoning/encrypted private reasoning
```

Redaction happens before public DTO construction.

Tests should seed obvious secret sentinel values and prove they do not appear in:

```text
session records
full prompt detail
activity events
protocol JSON
TUI/web rendering snapshots
logs
```

## 21. Required Focused Tests

### Runtime continuation

- new branch creates independent continuation state;
- same branch reuses compatible continuation;
- sibling branch never reuses sibling continuation;
- provider switch invalidates automatic reuse;
- switching back reseeds when fingerprint diverged;
- unavailable provider state falls back to canonical context;
- OpenAI adapter never sends both continuation strategies together;
- `previous_response_id` path resends required instructions.

### Request observability

- full request contains all safe compiled context sections;
- bounded projection points to full detail;
- continuation wire optimization does not make full prompt incomplete;
- full detail retrieval performs no model execution;
- redacted values remain structurally marked.

### Reasoning observability

- provider-visible reasoning before/between/after tools preserves order;
- hidden reasoning projection leaves tool/result order unchanged;
- summary-only provider declares that limitation;
- provider exposing no reasoning produces no invented reasoning content;
- private/encrypted reasoning never enters visible activity.

### Cross-surface

- embedded and remote clients retrieve equivalent request detail;
- TUI/web independent prompt/reasoning toggles do not cause runtime calls;
- restart restores settled observable history without provider stream replay.

---

## 22. Completion Standard

This Level-2 design is satisfied when Scriberig can run one isolated branch through a stateful provider continuation, create an independent continuation for a child/sibling branch, safely reseed after context/provider divergence, continue correctly when provider state disappears, preserve a complete safe canonical effective request for every inspectable invocation, preserve provider-visible reasoning segments in their exact order around semantic/tool activity, and expose independent prompt/reasoning presentation controls through the same application/protocol semantics to TUI and web without rerunning model work.
