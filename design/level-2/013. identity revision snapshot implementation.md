# Identity, Revision, and Snapshot Implementation

## 1. Purpose

This document translates the Level 1 identity model into a concrete first Rust implementation.

It implements the identity substrate only:

- stable entity identity;
- immutable content-addressed revision identity;
- immutable snapshot identity;
- snapshot-scoped entity resolution;
- persistent structural sharing between snapshots;
- named mutable roots with compare-and-swap updates;
- exact snapshot diffing.

It does not implement domain schemas, migrations, projections, agents, sessions, SQLite persistence, or network APIs. Those systems must build on the contracts defined here.

The implementation must preserve the Level 1 rule:

> Stable semantic identity is local. Exact immutable state is revisioned. Global certainty is provided by snapshots.

---

The repository currently has no Rust workspace. This design creates the minimum reusable Rust foundation needed to exercise the identity model without committing the project to a database backend.

Create these files:

## 3. Crate Responsibilities

### 3.1 `sr-core`

`sr-core` contains backend-independent identity and canonical-encoding primitives.

It must not depend on `sr-store`, domain crates, agents, filesystems, servers, or UI code.

It owns:

- `EntityId`;
- `RevisionId`;
- `SnapshotId`;
- `TypeId`;
- `EncodingVersion`;
- canonical byte encoding helpers;
- hashing helpers used to construct immutable IDs.

### 3.2 `sr-store`

`sr-store` contains immutable revision storage and snapshot state.

It owns:

- canonical revision values;
- a revision-store trait;
- an in-memory revision-store implementation for conformance and tests;
- the persistent snapshot map;
- snapshot resolution and diffing;
- mutable named roots;
- compare-and-swap root updates.

`sr-store` depends on `sr-core`.

No higher product layer may be required to use either crate.

---

## 4. Identity Types

### 4.1 `EntityId`

`EntityId` represents conceptual continuity and must not be content-derived.

Use a 128-bit opaque value.

The initial implementation may generate it with UUID v4 semantics. The public type must not expose UUID-specific behavior as part of the architectural contract.

Required behavior:

```text
EntityId::new()
EntityId::from_bytes([u8; 16])
EntityId::as_bytes()
Display
FromStr
Eq
Ord
Hash
Clone
Copy
Serialize/Deserialize if serde is enabled by the crate
```

Text representation must be deterministic and round-trippable.

Changing an entity's content must never require generating another `EntityId` unless reconciliation concludes that the new object is a different conceptual entity.

### 4.2 `RevisionId`

`RevisionId` identifies one exact canonical revision value.

Use a 256-bit BLAKE3 digest represented as an opaque newtype.

A revision ID must be computed from:

```text
revision-domain tag
encoding version
type ID
canonical payload bytes
```

Do not include `EntityId` in the revision hash.

This allows identical canonical values of the same type and encoding version to deduplicate even when referenced by different entities.

### 4.3 `SnapshotId`

`SnapshotId` identifies one exact snapshot mapping.

Use a 256-bit BLAKE3 digest represented as a different opaque newtype from `RevisionId`.

A snapshot ID must be the hash of the persistent snapshot structure's root node representation, prefixed by a snapshot-domain tag and encoding version.

`RevisionId` and `SnapshotId` must not be interchangeable Rust types even though both contain 32 bytes.

### 4.4 `TypeId`

`TypeId` identifies the schema/domain type of a canonical revision.

Use a stable UTF-8 identifier wrapper in the initial implementation, for example:

```text
markdown.paragraph
rust.function
session.branch
```

The value must participate in revision hashing.

The storage layer must not hard-code a registry of every possible type.

---

## 5. Canonical Encoding

Content addressing is only correct if byte encoding is deterministic.

`sr-core::canonical` must provide a small explicit canonical writer rather than relying on general-purpose JSON serialization.

The canonical writer must support at least:

- fixed domain tags;
- unsigned integers in a defined byte order;
- byte strings prefixed by length;
- UTF-8 strings prefixed by byte length;
- booleans;
- optional values with explicit discriminants;
- ordered sequences with explicit element count;
- maps only when callers supply entries in canonical sorted-key order.

Do not encode Rust memory layout, pointer values, platform endianness, `Debug` output, or unordered `HashMap` iteration.

Expose a trait similar to:

```rust
pub trait CanonicalEncode {
    fn encode_canonical(&self, out: &mut CanonicalWriter);
}
```

The concrete method names may differ, but the contract must remain explicit and deterministic.

### 5.1 Encoding version

Every content-addressed root must include an `EncodingVersion`.

Version 1 is the initial encoding.

Changing canonical encoding rules later requires a new encoding version; old IDs must continue to mean the old bytes.

---

## 6. Canonical Revision Value

`sr-store::revision` defines the stored immutable revision value.

It must contain:

```text
encoding_version
TypeId
canonical_payload: bytes
```

The corresponding `RevisionId` is derived from exactly those canonical fields plus the fixed revision-domain tag.

The revision value does not contain:

- parent identity;
- position in a parent;
- mutable aliases;
- cache entries;
- derived summaries;
- current snapshot;
- timestamps that are not part of domain semantics;
- the `EntityId` that happens to reference it.

The revision type must provide a constructor that computes and exposes its `RevisionId`.

---

## 7. Revision Store Contract

Define a small trait for immutable revision persistence.

Required conceptual operations:

```text
put(revision) -> RevisionId
get(RevisionId) -> Option<Revision>
contains(RevisionId) -> bool
```

`put` is idempotent.

Putting the same revision twice must return the same ID and must not create two logical copies.

The initial implementation is an in-memory store using a map keyed by `RevisionId`.

The trait must not expose implementation-specific locking or database handles.

A later SQLite implementation must be able to implement the same behavioral contract.

---

## 8. Snapshot Mapping

A snapshot is conceptually:

```text
EntityId -> RevisionId
```

Do not represent the snapshot by recursively hashing semantic parents and descendants.

The snapshot structure is an independent persistent Merkle map.

### 8.1 Data structure

Implement the first version as an immutable 16-way radix trie over the 128 bits of `EntityId`.

Each level consumes one 4-bit nibble.

Maximum depth is therefore 32 branch levels.

Node kinds:

```text
Empty
Branch(children[16])
Leaf(EntityId, RevisionId)
```

An implementation may compress empty children internally, but the canonical hash of a logical node must not depend on memory layout.

Each node caches its immutable node digest.

Updating one entity creates new trie nodes only along the path from the root to that entity. Unchanged branches are shared with `Arc` or an equivalent immutable shared pointer.

This gives bounded path copying and prevents semantic containment depth from controlling snapshot update cost.

### 8.2 Trie node hashes

Use separate canonical domain tags for empty, branch, and leaf nodes.

A leaf hash includes:

```text
leaf tag
encoding version
EntityId
RevisionId
```

A branch hash includes:

```text
branch tag
encoding version
16 child hashes in nibble order
```

The empty node has one defined hash for an encoding version.

The `SnapshotId` is derived from the root node hash using a separate snapshot-root domain tag so it cannot be confused with an internal node digest.

### 8.3 Snapshot operations

The snapshot type must support:

```text
empty()
id() -> SnapshotId
resolve(EntityId) -> Option<RevisionId>
with_revision(EntityId, RevisionId) -> Snapshot
without_entity(EntityId) -> Snapshot
len() -> usize
iter() -> deterministic iteration
diff(&Snapshot) -> SnapshotDiff
```

All mutating-looking operations return a new snapshot and leave the old snapshot usable.

If `with_revision` sets an entity to the revision it already has, it should return a snapshot with the same `SnapshotId`.

If `without_entity` removes an absent entity, the ID should remain unchanged.

---

## 9. Snapshot Diff

Snapshot IDs answer whether global state differs. Snapshot diff explains which entity resolutions differ.

Represent differences using explicit cases:

```text
Added {
    entity,
    revision
}

Removed {
    entity,
    revision
}

Changed {
    entity,
    from,
    to
}
```

Diff output must be deterministic, ordered by `EntityId`.

The first implementation may compare deterministic iterators if needed. A later optimization may recursively skip identical Merkle subtrees using their node hashes.

The public behavior must not depend on which diff algorithm is used.

---

## 10. Snapshot Storage Boundary

The first implementation keeps `Snapshot` values in memory and tests structural sharing directly.

Do not yet design a durable snapshot-node database schema in code.

However, keep internal trie nodes canonically encodable and hash-addressed so a later persistence backend can store them independently by digest.

No public API should require that a snapshot exist only as one large serialized map.

---

## 11. Named Roots and Aliases

Named roots are mutable pointers to immutable snapshot IDs.

Examples:

```text
main -> SnapshotId
active-workspace -> SnapshotId
```

Define a root-store abstraction with these conceptual operations:

```text
get(name) -> Option<SnapshotId>
set(name, SnapshotId)
compare_and_swap(name, expected, new) -> result
```

`compare_and_swap` is required for safe concurrent promotion.

It succeeds only when the current value equals `expected`.

The initial implementation may use an in-memory `RwLock`-protected map.

Named roots are never included in the immutable snapshot hash.

Changing a root pointer does not mutate either the old or new snapshot.

---

## 12. Snapshot-Scoped Resolution

The lowest exact read operation is:

```text
resolve(snapshot, entity) -> RevisionId
```

The store layer must not provide an ambiguous operation that means "resolve this entity against whatever current state exists now" without naming the root or snapshot involved.

A higher application layer may define convenience operations using a named root, but it must resolve the name to a `SnapshotId` first.

This keeps reproducible reads possible under concurrent changes.

---

## 13. Error Model

Use explicit typed errors where failure is meaningful.

Examples:

- malformed textual ID;
- unsupported encoding version;
- requested revision not found;
- compare-and-swap root conflict.

Normal absence should use `Option` where appropriate rather than being an error.

Hash collisions are not handled as ordinary control flow. If storage observes the same digest with different canonical bytes, it must treat that as an integrity failure.

---

## 14. Serialization and Display

Public IDs need deterministic text forms for CLI, protocols, logs, and future APIs.

Use distinct prefixes so humans and parsers can distinguish them, for example:

```text
ent_<...>
rev_<...>
snp_<...>
```

The exact alphabet may be hexadecimal for the first implementation.

Requirements:

- parsing must reject the wrong prefix;
- round-trip must be exact;
- `RevisionId` text must never parse as `SnapshotId`;
- display formatting must not depend on locale.

Binary protocol encodings may later use raw bytes.

---

## 15. Concurrency

Immutable revisions and snapshots need no in-place mutation locks.

Synchronization is required only around mutable implementation indexes and named-root updates.

The in-memory stores may use standard Rust synchronization primitives.

Do not leak those primitives through public traits.

The externally meaningful concurrent update operation is named-root compare-and-swap.

---

## 16. Tests Required Before Higher Layers Depend on This

### 16.1 Identity tests

Verify:

- two new entities have different `EntityId` values;
- text round-trip preserves each identity type;
- prefixes prevent cross-type parsing;
- identical canonical revision values have identical `RevisionId`s;
- changing type, payload, or encoding version changes `RevisionId`.

### 16.2 Revision-store tests

Verify:

- putting a revision and reading it returns identical canonical fields;
- putting the same revision twice is idempotent;
- missing revisions return `None`;
- an integrity mismatch cannot silently overwrite an existing digest.

### 16.3 Snapshot tests

Verify:

- empty snapshots have deterministic identity;
- same logical mappings built in different insertion orders have identical `SnapshotId`s;
- changing one entity changes `SnapshotId`;
- unchanged mappings resolve to the same revisions;
- old snapshots still resolve old revisions after a successor is created;
- removing an entity changes the snapshot only when it existed;
- reapplying the same entity revision preserves the snapshot ID;
- iteration order is deterministic;
- diff reports added, removed, and changed entities correctly.

### 16.4 Structural-sharing tests

Add test-only introspection if required.

Verify that changing one key reuses trie branches that are not on the changed radix path.

Do not require callers to observe storage internals in production APIs.

### 16.5 Root tests

Verify:

- a root can point to a snapshot;
- updating the root does not mutate either snapshot;
- compare-and-swap succeeds with the expected old snapshot;
- compare-and-swap fails without changing the root when the expected snapshot is stale.

## 17. Dependency Rules

Keep dependencies minimal.

Expected external dependencies are limited to purposes such as:

- BLAKE3 hashing;
- UUID/random entity generation;
- optional serde support;
- error derivation if desired.

Do not introduce async runtime, web framework, database driver, parser framework, or agent SDK dependencies into these crates.

---

## 18. Public API Stability Rules

The exact internal trie representation is private.

The following concepts are public contracts:

```text
EntityId
RevisionId
SnapshotId
TypeId
CanonicalEncode
Revision
RevisionStore
Snapshot
SnapshotDiff
RootStore
```

Higher layers must not depend on:

- trie node shape;
- `Arc` usage;
- in-memory map implementation;
- BLAKE3 helper internals;
- UUID library types;
- lock types.

This allows persistence and performance implementations to evolve without changing semantic consumers.

---

## 19. Work Sequence

Implement in this order:

1. workspace and `sr-core` identity types;
2. canonical encoding and revision hashing;
3. revision value and in-memory revision store;
4. persistent snapshot trie and snapshot IDs;
5. snapshot resolution, iteration, and diff;
6. named roots with compare-and-swap;
7. conformance and structural-sharing tests.

Each step must compile and test before the next step begins.

---

## 20. Completion Criteria

This Level 2 design is implemented when all of the following are true:

- a caller can create a stable `EntityId`;
- a canonical revision can be hashed, deduplicated, stored, and retrieved;
- a snapshot can resolve entities to exact revision IDs;
- editing one entity produces a new snapshot without modifying the old one;
- unrelated trie branches are structurally shared;
- equivalent logical snapshots have identical `SnapshotId`s regardless of insertion order;
- snapshot diffs identify only changed entity resolutions;
- a named root can be atomically advanced using compare-and-swap;
- all identity, revision, snapshot, structural-sharing, and root tests pass;
- neither crate depends on any agent or product layer.

After these criteria are satisfied, persistence backends, migrations, domains, projections, sessions, and agents can depend on the identity substrate without redefining its semantics.
