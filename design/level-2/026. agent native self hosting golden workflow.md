# Agent-Native Self-Hosting Golden Workflow

## 1. Purpose

This document turns `design/level-1/014. agent native semantic self hosting.md` into the concrete product workflow that Scriberig must support.

The reference scenario has exactly two user instructions issued in the native TUI:

```text
Onboard the current project.
```

followed by:

```text
Add support for ingesting PHP source files.
```

The first instruction begins with a fresh SQLite database containing no project. The second instruction begins from the exact semantic project snapshot created by the first and must end in a normal reviewed, validated, accepted project-wide candidate.

This workflow extends, rather than replaces, the first useful project workflow described in `design/level-2/025. first useful project workflow vertical slice.md`.

---

## 2. Required Existing Foundations

The self-hosting slice depends on the existing public architecture for:

- project scan/import and ownership;
- active project workspaces;
- universal semantic read operations;
- durable sessions, branches, operations, and branch results;
- provider-neutral agent execution;
- progressive capability discovery;
- source projections and migration/candidate review;
- validation evidence;
- exact-base apply;
- filesystem ownership, conflict detection, and external-effect receipts;
- native TUI interaction and real PTY testing.

Relevant existing Level 3 work includes the project onboarding task and tasks `107` through `122`. New work must extend those owners rather than creating a second self-hosting-only stack.

---

## 3. Starting Product State

The user is in the Scriberig repository root and starts:

```text
srig tui --db <fresh-db>
```

The database has no project catalog rows and no project semantic snapshot.

The TUI opens agent mode successfully and visibly indicates that no project is active.

The local runtime provides bounded trusted bootstrap context:

```text
working_directory
selected database/runtime
principal/capability context
agent profile/provider configuration
```

The working directory is environmental context only. It is not silently promoted to an active semantic project.

---

## 4. Phase A — Agent-Driven Onboarding

### 4.1 Start the operation

Submitting:

```text
Onboard the current project.
```

starts the normal durable agent operation and immediately creates/reuses normal session/branch/operation identities.

No active project selection is required to start this operation.

### 4.2 Bootstrap capability catalog

The initial agent context contains a small trusted catalog sufficient to discover project onboarding.

The conceptual capabilities needed are:

```text
capabilities
project.scan
project.import
project.workspace
inspect
list
operation.observe
```

The exact provider tool names may follow existing contracts.

The model must not receive a direct database tool or an unbounded filesystem crawl tool as a substitute for project onboarding.

### 4.3 Scan the current checkout

The agent resolves "current project" from trusted local runtime context and invokes project scan for the working directory.

For the golden repository-oriented scenario, the preferred selection policy is Git-tracked files.

The scan operation remains owned by `scriberig-project` and produces a durable manifest containing deterministic project-relative paths, exact source evidence/digests, classification, selected adapter, and diagnostics.

The model does not make one tool call per source file.

### 4.4 Review the persisted manifest

The agent receives a bounded scan summary and can inspect/list the persisted manifest.

Before import it verifies at least:

- the canonical root is the intended Scriberig checkout;
- the manifest is non-empty;
- expected repository-defining files are present;
- there are no blocking scan diagnostics.

The import request identifies the exact persisted manifest. Import must not perform a hidden fresh rescan.

### 4.5 Import and promote S0

The agent invokes the normal project import operation.

Import preserves exact source artifacts, invokes registered domain adapters, records project/source ownership, constructs immutable semantic state, and atomically promotes the project-specific current root according to the existing project transaction rules.

The first successful project snapshot in the scenario is called `S0`.

### 4.6 Resolve the active workspace

The agent resolves:

```text
ProjectId P
SnapshotId S0
Root EntityId R
```

through the normal workspace operation.

The TUI activates that authoritative workspace using the same client/product state contract as human onboarding.

### 4.7 Semantic smoke check

The agent performs bounded semantic verification using normal operations such as:

```text
inspect(R@S0)
find(P@S0, Cargo.toml or another named project object)
find(P@S0, known Scriberig package/name)
render(...) where useful
```

The purpose is to prove the imported workspace is semantically useful, not merely that an import status flag changed.

### 4.8 Durable onboarding result

The branch completes with a compact result equivalent to:

```text
project = P
snapshot = S0
root = R
manifest = M0
outcome = success
important semantic references = [...]
```

Detailed model/tool traffic remains in durable session history but is not automatically replayed into every future model turn.

---

## 5. Phase Boundary — Semantic Scope Becomes Primary

After onboarding, subsequent project work starts from `P@S0`.

Paths remain useful source/projection metadata, but the agent should discover architecture through semantic `find`, `inspect`, `follow`, `query`, and `render` operations where those capabilities represent the requested knowledge.

The second instruction must not silently drop back to an unrelated raw-filesystem workspace with no exact snapshot binding.

---

## 6. Phase B — Request PHP Ingestion Support

The user submits:

```text
Add support for ingesting PHP source files.
```

The continuation records exact context:

```text
project = P
base snapshot = S0
```

No source change has happened yet.

The semantic definition of done is not simply "recognize .php". A valid implementation must make a PHP file:

- classify as a first-class PHP/code source;
- retain exact source evidence;
- parse through the PHP adapter described by `design/level-2/028. php code domain source adapter target.md`;
- produce deterministic semantic code/syntax entities;
- participate in project ownership/re-import;
- expose named PHP declarations through common semantic navigation;
- render its source through normal projection/read operations;
- fail with structured diagnostics without partially promoting a broken import.

---

## 7. Semantic Architecture Discovery Branch

The parent agent starts a read-only child branch whose purpose is to identify the minimal extension points for a new PHP code adapter.

The child branch receives explicitly:

```text
base project P
base snapshot S0
read-only semantic capabilities
expected result = architecture map
```

It does not receive change/apply capabilities.

The child discovers project guidance and implementation precedent semantically, including as appropriate:

- repository `AGENTS.md` guidance;
- code-domain design and domain adapter conventions;
- a representative Tree-sitter language adapter such as Python;
- project scan classification;
- project adapter dispatch/import mapping;
- domain conformance helpers;
- workspace/dependency metadata;
- relevant tests and capability metadata.

The child returns a compact `BranchResult` with stable semantic references and required integration points.

The parent does not automatically ingest the child's full transcript.

---

## 8. Implementation Branch

The parent starts a second child branch for implementation.

It receives:

```text
project P
exact base S0
architecture references from the discovery result
read + propose + validate capabilities
no normal change.apply capability
```

Before proposing edits it re-resolves important targets at `S0`.

The implementation is one coherent project-wide candidate and may contain:

- a new `scriberig-domain-php` crate;
- workspace/package dependency changes;
- exact parser dependency and lockfile changes;
- project scan classification change from generic text to PHP;
- project import dispatch changes;
- domain/schema/capability metadata;
- PHP domain tests;
- project import tests and fixtures;
- authoritative format documentation when applicable.

The candidate is anchored to `S0` and receives stable candidate identity `C1`.

The live project remains `P@S0` and the live checkout remains unchanged.

---

## 9. Project-Wide Candidate Contract

The self-hosting scenario requires one candidate to create and update multiple files.

The candidate must retain exact base information and expected source state per affected path.

Required effect kinds are conceptually:

```text
create(path, new content)
update(path, expected base digest/content identity, new content)
delete(path, expected base digest/content identity)
```

The candidate review model exposes aggregate and per-file semantic/source diffs.

A newly created file is still a projection/source effect owned by the candidate; it is not written early merely because it has no base file.

Detailed mechanics are defined in `design/level-2/027. project wide candidate workspaces validation and materialization.md`.

---

## 10. Validation Sequence

The implementation branch validates `C1` against isolated candidate state.

The expected profiles are conceptually:

1. `php-domain-focused`
   - parser/domain tests;
   - deterministic syntax/source-range tests;
   - malformed PHP diagnostics;
   - inline HTML coverage.
2. `project-import-focused`
   - `.php` scan classification;
   - exact source preservation;
   - ownership;
   - semantic discovery/render;
   - invalid import atomicity;
   - unchanged re-import/regression classification.
3. `rust-workspace`
   - repository formatting/check/lint/tests according to current policy.
4. `project-ingestion-e2e`
   - fresh database;
   - a small PHP project;
   - scan/import/workspace/find/inspect/render through public operations.

Validation evidence is durable and exact-input-bound.

If a parser dependency must be acquired, dependency resolution is an explicit bounded external capability and the resolved version/lock state becomes candidate content/evidence.

Validation must not modify the live Scriberig checkout.

---

## 11. Repair During Validation

A validation failure does not authorize live edits.

The implementation branch inspects structured diagnostics, renders the exact affected candidate/base source context, and creates a revised/superseding candidate through the normal change path.

A complex failure may be delegated to another nested child branch with an explicit bounded capability set.

The final successful implementation result links to the validated candidate and its validation records.

---

## 12. Agent Result and Normal Review

The root agent returns a concise terminal result containing a stable candidate reference.

The TUI offers a normal `Review candidate` action.

The review is the same migration/change review used for non-agent changes and shows at least:

```text
base snapshot S0
candidate C1
created/updated/deleted paths
important semantic contexts
source before/after or unified diffs
validation state
stale/conflict state
```

Before acceptance:

```text
P.current == S0
live working tree == base
C1 is durable
validation evidence is durable
```

---

## 13. Acceptance and Materialization

The user explicitly chooses the normal Apply action.

The shared application operation verifies:

- project current snapshot still equals `S0`;
- all affected paths remain within the project root;
- update/delete source digests still match expected base state;
- create targets do not conflict with unexpected external files;
- symlink/path-escape rules pass;
- validation/applicability policy passes.

Application then follows the repository's existing canonical-promotion/external-effect ordering and records effect status truthfully.

On the successful path, the project advances to `S1`, the accepted project-wide source effects reach disk safely, and the TUI refreshes the authoritative workspace.

No direct TUI or agent file-writing path is involved.

---

## 14. Post-Apply Proof

After apply, the scenario must be able to establish:

- `S1 != S0` and `P.current == S1`;
- history links `S0 -> C1 -> S1` according to normal migration lineage;
- changed PHP-support source is present in the checkout;
- historical `S0` remains addressable;
- provenance links the user's request, discovery/implementation branches, candidate, validations, acceptance, and materialization result.

The agent may perform bounded semantic verification against `P@S1`.

---

## 15. Restart Requirement

Exit and restart the TUI against the same database and checkout.

The product must recover enough durable state to inspect:

```text
P@S1
session and branch hierarchy
onboarding result
implementation result
C1
validation records
history/effect status
```

Replaying original provider streams is not required.

---

## 16. Critical Baseline Rule

The repository/build used at the beginning of the golden scenario must not already contain registered first-class PHP ingestion.

Test fixtures may contain the expected PHP extension source or declarative expected edits, but production scan/import dispatch in the baseline must still treat PHP as unsupported/generic according to current policy.

The agent candidate is what adds PHP support to the temporary tested checkout.

Do not satisfy the golden scenario by implementing PHP permanently first and then scripting an agent response that claims to add it.

---

## 17. Failure Scenarios

The product-level design must cover at least:

- onboarding scan failure: no fake active project;
- import failure: no project snapshot promotion to partial state;
- exact manifest mismatch/stale request: explicit failure;
- child branch lacks requested capability: tool is absent/denied, not bypassed;
- candidate validation failure: current project/tree unchanged;
- candidate becomes stale: normal stale rules apply;
- one affected file changes externally before multi-file apply: no silent overwrite of that file or unrelated partial success presented as complete success;
- materialization failure after canonical state transition: explicit effect/recovery status;
- provider/tool cancellation: durable failed/cancelled operation, no hidden source mutation;
- restart after completion: durable references recover.

---

## 18. Product Evidence

The final acceptance gate uses:

- the real built `srig` executable;
- an actual PTY;
- a fresh temporary SQLite database;
- a copied Scriberig checkout whose baseline lacks PHP ingestion;
- normal TUI key/input sequences;
- a deterministic scripted provider configured through normal provider contracts;
- public application/project/change/validation operations;
- filesystem assertions before and after Apply;
- restart assertions.

The provider must not be special-cased in production code on the literal golden prompt.

The product gate must also prove the candidate's PHP implementation by running the required PHP ingestion E2E against the candidate workspace/build, not merely by checking that files named `php` were added.

---

## 19. Implementation Sequence

The corresponding Level 3 tasks intentionally build generic capability before the test-only PHP self-extension:

```text
123 empty-database agent onboarding
124 semantic-first project context and nested discovery
125 project-wide source candidates
126 project-wide candidate validation/apply safety
127 PHP golden extension contract and fixture
128 deterministic self-hosting provider scenario
129 TUI two-command self-hosting workflow
130 real-process self-hosting product gate
```

Tasks `123` through `126` improve production capability without pre-installing PHP. Tasks `127` and `128` create test/reference material that describes and generates the PHP candidate while preserving the baseline invariant. Tasks `129` and `130` compose the complete scenario.

---

## 20. Completion Criteria

This Level 2 design is satisfied only when the final real-process gate proves the entire two-command scenario from a fresh project database and a PHP-unaware starting checkout, with no direct database mutation, no agent-only file patch path, no live-tree mutation before acceptance, no hidden partial apply, and durable restartable project/session/history evidence.
