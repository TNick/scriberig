# Canonical Encoding and Revision Identity

## Purpose

This document specifies the lower-level decisions required by the Level 1 persistence model for deterministic revision identity.

The Level 1 requirement is that a revision identifier never silently refer to different canonical content. This design chooses one concrete initial mechanism.

## Decision

Revision identity is content-addressed.

The initial implementation uses:

- BLAKE3 as the digest algorithm;
- a versioned deterministic binary canonical encoding;
- explicit object type and encoding version in the encoded value.

The exact Rust serialization library used internally may change, but the canonical byte format must be owned by Scriberig and tested independently of ordinary Rust serialization behavior.

## Canonical revision envelope

Every stored canonical revision is encoded conceptually as:

```text
RevisionEnvelope
├── encoding_version
├── object_type
└── canonical_payload
```

`RevisionId` is computed from the complete canonical envelope bytes.

Two logically identical canonical revisions encoded under the same encoding version must produce identical bytes and therefore identical `RevisionId` values.

## Rules

- Map/object fields must have deterministic ordering.
- Ordered semantic collections preserve order.
- Unordered semantic collections must be canonicalized before encoding.
- Incidental Rust memory layout must never affect bytes.
- Timestamps, insertion order, database row IDs, cache metadata, and backend-specific information must not appear in canonical revision bytes unless a domain explicitly declares them canonical.
- Parent location and reverse-index information must not be inserted merely for navigation convenience.
- Unknown encoding versions must fail explicitly rather than being interpreted as the newest version.

## Identity types

`RevisionId` should be represented internally as the BLAKE3 digest bytes plus type safety provided by `sr-core`.

External textual formatting should be deterministic and round-trippable. The human representation may use a prefix such as `rev:` plus a stable textual digest encoding.

The exact display format is not part of semantic identity.

## Encoding evolution

A newer physical encoding must use a new `EncodingVersion`.

Storage migration and semantic migration must remain separate concepts.

If the system rewrites an old revision into a newer physical representation without semantic change, the storage migration layer must preserve the ability to understand that the semantic state is equivalent even if the physical revision representation receives a different content identity under the new encoding.

The first implementation does not need automatic cross-version deduplication, but it must not pretend that an encoding rewrite is a user semantic edit.

## Files prescribed by this design

Within `sr-core`:

```text
crates/sr-core/src/
├── lib.rs
├── ids.rs
└── encoding.rs
```

Within `sr-store`:

```text
crates/sr-store/src/
├── lib.rs
└── revision.rs
```

Tests must cover stable canonical byte output and stable IDs for fixed fixtures.

## Required tests

- Same value encoded twice gives byte-for-byte identical output.
- Same value encoded through independently constructed Rust values gives the same ID.
- Changing a canonical scalar changes the ID.
- Changing ordered collection order changes the ID.
- Reordering an unordered canonical collection does not change the ID after canonicalization.
- Changing `ObjectType` changes the ID even if payload bytes are otherwise equal.
- Changing `EncodingVersion` changes the encoded envelope.
- Display/parse round-trip for `RevisionId` succeeds.

## Non-goals

This design does not define domain schemas or decide which domain fields are canonical. Domain adapters make that decision before handing a canonical revision value to the store.
