# Capability Matrix and Cross-Surface Conformance

## 1. Purpose

`design/level-1/011. runtime libraries protocol and product surfaces.md` requires user-level capabilities to evolve vertically across product surfaces and requires explicit conformance testing.

This document defines the concrete planning and test artifacts used to enforce that rule.

The central principle is:

> A capability is implemented once semantically, then exposed and verified across each relevant surface. Missing surfaces are visible and intentional.

This design prescribes a machine-readable capability matrix and a dedicated conformance-test crate.

---

## 2. Files and Package to Create

Create these repository artifacts:

```text
capabilities.toml

crates/scriberig-conformance/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    ├── inspect.rs
    ├── protocol.rs
    ├── operations.rs
    └── events.rs
```

`scriberig-conformance` is a test/support package, not a foundational runtime dependency.

It must be marked `publish = false`.

Production crates must not depend on it.

---

## 3. Capability Matrix Format

`capabilities.toml` is the project-visible source of truth for cross-surface capability coverage.

It is not a runtime authorization file and not part of canonical project knowledge.

Each capability entry must include:

```text
id
description
semantic_owner
surfaces
```

Recommended form:

```toml
[[capability]]
id = "inspect_entity"
description = "Inspect an entity under an explicit snapshot or current-state request."
semantic_owner = "scriberig-app"

[capability.surfaces]
library = "implemented"
protocol = "implemented"
server = "implemented"
client = "implemented"
cli = "implemented"
tui = "planned"
web = "planned"
agent = "implemented"
```

Allowed status vocabulary for the first version:

```text
not_applicable
planned
implemented
verified
```

Do not add arbitrary status strings.

A surface may be `not_applicable` only when the reason is clear from the capability description or a nearby comment.

---

## 4. Initial Surface Names

The matrix should use these keys consistently:

```text
library
app
protocol
server
client
cli
tui
web
agent
```

`library` means the reusable semantic/domain implementation when one exists.

`app` means the shared application-operation layer.

The remaining names refer to product or transport exposure.

The matrix may gain surfaces later, but existing keys should not be renamed casually because tooling may consume them.

---

## 5. Initial Capability Entries

Do not attempt to enumerate the final product.

Start with capabilities required to validate the runtime architecture:

```text
inspect_entity
runtime_capabilities
operation_status
operation_cancel
event_subscription
```

Only mark a surface `implemented` when code exists.

Only mark it `verified` when a conformance or dedicated surface test proves the expected semantics.

Planned work remains `planned`.

---

## 6. Conformance Crate Responsibility

`scriberig-conformance` verifies that different surfaces expose equivalent semantics.

It does not own implementations.

Its tests may depend on public APIs from:

- `scriberig-app`;
- `scriberig-protocol`;
- `scriberig-client`;
- `scriberig-server`;
- `scriberig-agent-core` when agent exposure is under test;
- test fixtures from foundational/domain crates.

Avoid depending on private module paths.

The conformance crate should exercise the same fixed test world through different adapters.

---

## 7. Fixed Test World

Create reusable test setup inside `src/lib.rs` or a later `src/fixture.rs` when complexity justifies it.

The fixture should provide:

- a deterministic in-memory or temporary store;
- one known snapshot;
- a small set of known entities/revisions;
- an application instance wired to that state;
- a server adapter or in-process transport where needed.

The fixture must not require external network access.

Do not make tests depend on user configuration, model providers, or external services.

---

## 8. `inspect.rs`

This is the first vertical acceptance test.

Given one known entity and snapshot, compare:

```text
embedded application inspect
server/client inspect
CLI-facing result model where callable without scraping terminal text
agent inspect adapter result where available
```

The test compares semantic fields, references, snapshot context, and error category.

It must not require byte-identical presentation strings.

If TUI or web exposure is not yet implemented, the matrix records `planned`; this test does not invent fake UI implementations.

---

## 9. `protocol.rs`

Protocol conformance tests verify:

- public request/response round trips;
- operation state serialization;
- structured error serialization;
- event serialization;
- protocol version metadata;
- unknown/additive field tolerance according to the chosen serializer contract;
- generated schema reproducibility when schema generation exists.

The test should catch accidental changes to public wire meaning.

Do not snapshot private Rust debug output as the protocol contract.

---

## 10. `operations.rs`

Operation tests verify that one long-running operation has the same stable identity and terminal result regardless of how it is observed.

At minimum verify:

- operation ID remains stable;
- lifecycle does not regress from terminal to non-terminal;
- cancellation uses a structured result/error;
- final result remains queryable after streaming observers disconnect;
- input snapshot/base context is retained.

Use a deterministic fake operation rather than an external model or compiler.

---

## 11. `events.rs`

Event conformance tests verify:

- an application event can be exposed through the server/client path;
- event identity/subject handles survive transport;
- consumers can resolve authoritative state after receiving an event;
- events do not contain an independently mutable copy of canonical entity state;
- reconnect/resubscribe behavior can recover current state even if a live event was missed.

The exact streaming transport can change without invalidating the semantic test.

---

## 12. Matrix Validation

The conformance crate or a small test helper should parse `capabilities.toml` and validate:

- capability IDs are unique;
- only known surface names are used;
- only known status values are used;
- every capability has a semantic owner;
- entries marked `verified` have a corresponding declared conformance test mapping once such automation is introduced.

The first implementation may keep the last rule manual if building a full mapping system would distract from the initial vertical slice.

---

## 13. Development Rule

When adding a user-visible capability:

1. add or update the semantic/application implementation;
2. add protocol representation when remote use is relevant;
3. expose it through server/client;
4. expose it through relevant product surfaces;
5. add conformance coverage;
6. update `capabilities.toml` in the same change.

A capability may intentionally remain unavailable on some surfaces, but the matrix must make that explicit.

---

## 14. Do Not Turn the Matrix Into Build Configuration

`capabilities.toml` describes product coverage.

It must not silently decide which crates compile or which server permissions are granted.

Runtime capability discovery is a separate protocol/application concern.

Authorization is a separate trust concern.

Build features are a package-management concern.

Keeping these concepts separate prevents a planning artifact from becoming hidden runtime state.

---

## 15. Completion Criteria

This design is satisfied when:

- `capabilities.toml` exists and follows the fixed vocabulary;
- `scriberig-conformance` exists as a non-published test/support crate;
- the initial capability entries are present with truthful statuses;
- one deterministic fixture can be exercised without external services;
- `inspect_entity` has an end-to-end semantic-equivalence test once its surfaces exist;
- protocol, operation, and event conformance tests use public interfaces;
- production crates do not depend on `scriberig-conformance`;
- every future user-visible capability has an obvious place in the matrix and conformance model.
