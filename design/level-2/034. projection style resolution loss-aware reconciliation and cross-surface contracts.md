# Projection Style Resolution, Loss-Aware Reconciliation, and Cross-Surface Contracts

## 1. Purpose

This document turns the durable rules in `level-1/024. projection styles personalized representations and materialization policy.md` into concrete subsystem boundaries and implementation contracts.

It refines:

- `level-2/007. projection crate boundaries and core model.md`;
- `level-2/008. filesystem projection synchronization.md`;
- `level-2/011. application operations protocol and runtime boundaries.md`;
- `level-2/012. capability matrix and cross surface conformance.md`;
- `level-2/017. web workspace packages and integrated editor.md`;
- `level-2/024. agent operations protocol and cross surface product contract.md`.

For terminal integration, `level-2/032. upstream first agent runtime and terminal product ownership correction.md` remains authoritative. This document does not reintroduce a Scriberig-owned commodity terminal framework or theme system.

The implementation target is:

```text
style sources
  -> shared style resolution
  -> exact resolved projection style
  -> domain renderer
  -> rendered projection

editable external/view representation
  + exact reconciliation baseline
  -> parse
  -> loss-aware reconcile
  -> candidate/migration/conflict
```

---

## 2. Current Implementation Baseline

The current repository already contains important generic plumbing in `sr-projection`:

```text
StyleRef
  Revision { entity, revision }
  Value(StyleValue)

ProjectionSpec.style
RenderRequest.style
RenderCacheKey.style
RenderedProjection.style
```

The generic projection tests already establish that style participates in deterministic render/cache identity.

However, current domain implementation is incomplete relative to those contracts:

- the Rust syntax renderer accepts only a `RustFile` and hard-codes four-space indentation;
- the ECMAScript domain currently focuses on parsing/ESTree-compatible structure and has no equivalent style-aware source renderer;
- generic style values are exact but opaque and there is no shared style-schema/discovery contract;
- there is no shared purpose-aware style resolution service separating personal view selection from shared materialization selection;
- `ReconciliationContext` identifies base/current semantic state, scope, specification, and opaque metadata, but does not model the exact rendered baseline/style/output relationship as a first-class typed contract;
- projection capabilities are primarily projection-kind-level, while lossiness/editability may depend on the exact resolved style.

This design keeps the useful generic primitives and fills those gaps.

## 3. Ownership Boundary

### 3.1 `sr-projection`

`sr-projection` remains domain-neutral and owns only universal contracts needed for exact rendering and reconciliation.

It may own concepts equivalent to:

```text
StyleRef
StyleValue
ResolvedStyle
StyleSchemaRef
ProjectionPurpose
ProjectionFidelity
ReconciliationBaseline
ProjectionMappingRef / adapter-owned mapping bytes
```

It must not define properties such as:

```text
indent_width
quote_style
semicolons
brace_style
comment category names for a specific language
```

### 3.2 Domain projection crates

Domain crates such as Rust, ECMAScript, and Markdown own:

```text
style schemas
style codecs/normalization
style defaults
style merge semantics
repository-convention interpretation
rendering semantics
comment/directive classification
resolved-style fidelity/editability decisions
loss-aware reconciliation rules
```

### 3.3 Shared application layer

The existing shared application owner resolves product/user/workspace selection into exact projection inputs.

It owns behavior equivalent to:

```text
list applicable style schemas/profiles
read current effective style
select user preference
set/clear view override
select workspace materialization profile
resolve purpose-aware style
request render with resolved style
report provenance/diagnostics
```

Do not create a TUI-only or web-only style resolver.

### 3.4 Product surfaces

TUI/web/CLI/server/client code presents and transports style intent. It does not implement language formatting rules.

Under the RPI migration, upstream `rpi-tui` owns generic controls, overlays, lists, settings widgets, terminal style/theme, and terminal runtime. A Scriberig component may use those widgets to select a Scriberig projection style through shared application commands.

## 4. Keep `StyleRef`, but Add an Explicit Resolved Style Input

The current `StyleRef` is useful because it can identify either an exact semantic style revision or exact inline adapter-owned bytes.

However, a renderer receiving only:

```text
StyleRef::Revision { entity, revision }
```

still needs the actual domain style value to apply unless the renderer is allowed to reach into storage. Renderers should not acquire hidden storage/global-setting dependencies.

Introduce a generic exact resolved input conceptually equivalent to:

```rust
struct ResolvedStyle {
    reference: StyleRef,
    value: StyleValue,
    schema: Option<StyleSchemaRef>,
}
```

Exact field names may differ.

Rules:

1. `reference` preserves semantic/provenance identity.
2. `value` is the exact canonical adapter-defined bytes the renderer consumes.
3. `schema` identifies the adapter/schema contract when useful for validation and discovery.
4. resolution of `StyleRef::Revision` occurs before the domain renderer is called;
5. the renderer must not fetch mutable user/project settings on its own;
6. canonical style bytes must be deterministic for semantically identical normalized style input.

For an inline `StyleRef::Value`, resolution may be trivial, but validation/normalization still belongs to the domain style adapter.

## 5. Render Contract Refinement

Refine the conceptual render request to contain an exact resolved style rather than an unresolved reference alone:

```text
RenderRequest
  specification
  semantic scope
  exact base state
  projection kind
  resolved style
  renderer version
  deterministic rendering context
```

Compatibility migration may temporarily retain the existing `style: StyleRef` field while adding exact resolved style bytes through a typed field. The final contract must not require the renderer to consult undeclared mutable state.

The render cache identity must include every output-affecting component of the resolved style. A safe conceptual key is:

```text
projection spec
semantic scope/revisions
projection kind
style reference
hash(canonical resolved style value)
renderer version
rendering context
```

If an immutable style revision cryptographically or otherwise guarantees its value identity, the implementation may avoid redundant data in a storage key, but the runtime contract must still detect mismatched reference/value pairs as an error.

## 6. Style Schema Discovery

Define an adapter-owned discovery contract separate from the universal meaning of style properties.

Conceptually:

```text
StyleSchema
  schema id/version
  projection kinds
  property descriptors
  defaults
  constraints
  documentation/labels safe for clients
```

A property descriptor may support generic presentation metadata equivalent to:

```text
stable property key
value kind
allowed enum values or numeric/string constraints
default value
human label/description
whether it may affect fidelity/editability
whether it is materialization-only/view-only/available for both
```

The schema is descriptive metadata. It must not become a second formatter implementation.

Domain code remains responsible for validating and interpreting actual style values.

A generic client should be able to render a basic settings editor from descriptors. Opinionated clients may provide richer controls keyed by stable schema/property identifiers.

---

## 7. Domain Style Adapter Contract

Use a separate domain-owned style capability rather than teaching `sr-projection` language-specific properties.

Conceptually the adapter must support behavior equivalent to:

```text
schema(projection_kind)
normalize(style_input) -> canonical StyleValue
merge(base, overlay) -> canonical StyleValue or diagnostic
resolve_defaults(context) -> canonical StyleValue
classify(resolved_style, projection_kind, purpose) -> ProjectionFidelity
```

The exact Rust trait structure is an implementation choice. It may be a separate `ProjectionStyleAdapter`, capabilities on an existing domain adapter, or another narrow domain service if that better fits current crate ownership.

Requirements:

- normalization is deterministic;
- unknown unsupported properties produce structured diagnostics unless the schema explicitly supports extension keys;
- merging is domain-defined rather than generic JSON object overlay;
- required materialization properties cannot be silently overridden;
- resolution returns canonical exact bytes for render/cache identity.

## 8. Style Sources and Provenance

Model style resolution as a composition of identified sources rather than one mutable global preference map.

Useful source classes include:

```text
DomainDefault
RepositoryConvention
ProjectPolicy
WorkspaceMaterializationPolicy
UserPreference
ViewOverride
ExplicitExportOverride
```

The resolver should retain provenance sufficient to explain the effective result.

Conceptually:

```text
ResolvedStyleProvenance
  sources in application order
  source identities/revisions
  optional per-property winning source information
```

Per-property provenance is useful but need not be stored in every render record if it can be deterministically recomputed from retained exact sources. The exact resolved value itself is mandatory for deterministic render identity.

Do not put credentials, unrelated user settings, or unstable environment data into style provenance.

## 9. Purpose-Aware Resolution

Define an explicit purpose enum/type at the shared application/projection boundary.

At minimum:

```text
InteractiveView
SharedMaterialization
ExplicitExport
```

### 9.1 Interactive view

Preferred source order:

```text
DomainDefault
RepositoryConvention / ProjectPolicy
UserPreference
ViewOverride
```

### 9.2 Shared materialization

Preferred source order:

```text
DomainDefault
RepositoryConvention / ProjectPolicy
WorkspaceMaterializationPolicy
```

Do not include `UserPreference` by default.

### 9.3 Explicit export

An export may explicitly opt into user/view overrides. The operation must record that choice and its target rather than borrowing ambient UI state implicitly.

The resolver must make source application deterministic and return structured conflicts/diagnostics when domain constraints make a combination invalid.

## 10. Repository Convention Importers

Repository convention readers belong with the applicable domain/configuration integration, not inside renderers.

Examples include adapters/readers for:

```text
.editorconfig
rustfmt.toml
Prettier configuration
Biome configuration
```

Their output is a typed/canonical domain style input or a structured unsupported/partial diagnostic.

Rules:

1. do not spawn a formatter and let it read arbitrary ambient configuration as the hidden source of render truth;
2. if an external formatter must be used, invoke it with an exact resolved configuration or in an environment whose relevant inputs are captured and declared;
3. unsupported external options must be surfaced rather than silently approximated when approximation could change output materially;
4. importing repository convention files does not automatically make them canonical project knowledge unless a configured projection/import relationship says so.

---

## 11. Projection Fidelity Must Be Evaluated After Style Resolution

Extend capability/fidelity modeling so callers can determine editability for an exact resolved projection.

Conceptually:

```text
ProjectionFidelity
  LosslessEditable
  LossAwareEditable
  ReadOnlyLossy
```

Additional detail may include adapter-owned reasons or omitted semantic categories.

Do not encode this as a single permanent flag on `ProjectionKind` because one style may be lossless and another lossy.

The adapter must calculate fidelity from at least:

```text
projection kind
resolved style
adapter version
relevant policy/purpose
```

A product surface that wants to enter edit mode queries this result. It must not infer editability from UI control values.

---

## 12. Typed Comment and Directive Policy

Code-domain style schemas should not expose only `strip_comments: bool`.

Define a domain model that can distinguish at least the categories the adapter semantically understands.

For ECMAScript/TypeScript this may include categories equivalent to:

```text
ordinary comment
documentation/JSDoc
license/header
TypeScript/compiler suppression or expectation directive
lint directive
formatter directive
source-map/tooling directive
```

Rust has related but different categories such as ordinary comments, doc comments, attributes, and tool directives. Do not force all languages into one fixed universal comment enum.

The style schema may expose generic policies only after the adapter maps domain categories safely.

Materialization policy may mark some categories `PreserveRequiredForm` even when an interactive view may hide them.

## 13. First-Class Reconciliation Baseline

Refine `ReconciliationContext` so exact baseline representation information is typed rather than hidden in an opaque metadata map.

Conceptually:

```rust
struct ReconciliationBaseline {
    base_state: SemanticStateRef,
    scope: SemanticScopeRef,
    specification: ProjectionSpecRef,
    resolved_style: ResolvedStyle,
    renderer: RendererVersion,
    adapter_version: String,
    rendered_output: ProjectionOutputRef,
    mapping: Option<ProjectionMapping>,
    fidelity: ProjectionFidelity,
}

struct ReconciliationContext {
    baseline: ReconciliationBaseline,
    current: SemanticStateRef,
    metadata: ...,
}
```

Exact names/storage differ, but the information boundary is required.

`ProjectionOutputRef` should identify the exact baseline representation strongly enough to retrieve or validate the bytes used for reconciliation. A content-addressed blob/reference is preferable to retaining only a hash when later algorithms need baseline content.

---

## 14. Baseline Content Retention

Editable projection synchronization must be able to reconstruct the exact baseline representation even after:

```text
canonical state advances
user preferences change
repository style policy changes
renderer version advances
current materialization changes
```

Therefore retain either:

1. exact baseline bytes in content-addressed projection storage; or
2. enough immutable inputs plus a guaranteed available exact renderer implementation to reproduce them.

The first option is generally safer for external synchronization because old renderer executables may no longer be available.

A hash by itself proves equality but cannot supply missing baseline structure/content for three-way reconciliation.

The filesystem synchronization record from Level-2 008 should therefore reference the exact baseline output artifact in addition to its hash when editable reconciliation needs it.

---

## 15. Projection Mapping Metadata

Some domains can reconcile safely using parsed structure plus base semantic state. Others benefit from adapter-produced mapping metadata created during render.

Allow optional adapter-owned mapping information equivalent to:

```text
rendered ranges/tokens/nodes -> semantic entity/revision handles
hidden canonical entities/categories
structural anchors
adapter-specific layout/reconciliation evidence
```

This metadata is derived projection evidence, not canonical semantic content.

It must be bound to:

```text
exact base state
exact resolved style
exact renderer/adapter version
exact rendered output
```

Do not expose unstable screen row numbers or raw parser memory identities as durable semantic identity.

---

## 16. Loss-Aware Reconciliation Algorithm Contract

For an exact `LossAwareEditable` baseline, reconciliation conceptually receives:

```text
B_semantic = semantic state at synchronization base
B_rendered = exact representation shown/materialized
B_style = exact resolved style
D = current canonical semantic state
F = current edited external/view representation
M = optional render mapping/loss metadata
```

The domain adapter must distinguish:

```text
entity absent from F because B_style never rendered it
entity represented in B_rendered and absent from F because user removed it
entity changed in D since B_semantic
new/modified visible structure in F
```

Hidden canonical entities are preserved unless the edit contains explicit evidence/operation that semantically changes or deletes them.

Do not synthesize deletions from mere non-observation of style-hidden content.

If the adapter cannot disambiguate safely, return `Ambiguous` or `Conflict`; do not guess.

---

## 17. Style Change While Editing

An edit session or managed file remains bound to the style in its synchronization baseline.

If the user changes their preferred style while an editable view contains uncommitted edits, the system must not silently reinterpret the edited bytes under the new style.

Allowed behaviors include:

```text
finish/reconcile current edit against old baseline, then rerender with new style
explicitly rebase/reproject edit with adapter support
ask user to resolve a conflict when safe automatic rebase is unavailable
```

The baseline style remains immutable evidence.

For filesystem projections, changing materialization style is itself a projection configuration change and should establish a new baseline only after successful rerender/write synchronization.

---

## 18. Shared Application Operations

Extend the existing application capability/operation layer rather than creating product-specific APIs.

The shared application surface should eventually support operations/views equivalent to:

```text
projection.style_schema(scope/kind)
projection.style_profiles(scope/kind/purpose)
projection.style_effective(scope/kind/purpose/view-context)
projection.style_set_user_preference(...)
projection.style_set_view_override(...)
projection.style_set_materialization_policy(...)
projection.render(... purpose/style selection ...)
projection.fidelity(... exact resolved style ...)
```

Exact operation names must follow current application command conventions.

Changing a user preference or view override is not a semantic code migration. Changing a project/workspace policy may be a configuration change in the appropriate configuration domain, but it still must not masquerade as source-code modification.

---

## 19. Persistence Scopes

Do not force all style-related state into the canonical project snapshot.

Use the appropriate ownership scope:

```text
domain defaults
  -> code/domain implementation/version

project style policy
  -> project semantic/configuration knowledge when user-meaningful and shared

workspace materialization policy
  -> workspace/project runtime/configuration scope as designed by the application

user preferences
  -> user/profile configuration scope

view override
  -> presentation/view state, optionally persisted as user UI state

resolved exact style
  -> immutable render input/provenance record
```

A view override should not create canonical project history merely because the UI remembers it.

---

## 20. Protocol and Client Contracts

Only style information required across a transport boundary belongs in `scriberig-protocol`.

Local and remote clients should expose the same application semantics.

Protocol models may need representations for:

```text
style schema descriptor
style profile/reference
purpose
resolved style summary/provenance
fidelity/editability
style diagnostics
style selection/update request
```

Do not serialize opaque internal Rust trait objects or domain parser structures.

Exact canonical style bytes need not be sent to every UI if the server can render and provide a safe descriptive projection, but clients that perform local deterministic rendering must receive the exact validated input contract required for that rendering mode.

## 21. TUI Integration on the RPI Redesign

The active TUI target is defined by Level-2 032: upstream owns terminal runtime/component/theme/settings infrastructure; Scriberig owns distinctive semantic projection behavior.

Therefore implement terminal style controls as:

```text
rpi-tui settings/select/editor components
        |
        v
Scriberig ProjectionStyleComponent / intent adapter
        |
        v
shared Scriberig application style operations
        |
        v
style resolver + projection adapter
```

Do not add:

```text
TUI-local TypeScript formatter settings logic
TUI-local precedence rules
TUI-owned source style persistence
parallel Scriberig terminal theme system
source projection rules inside upstream terminal theme types
```

If a generic settings control needed by this feature is missing in `rpi-tui`, follow Level-2 032's upstream-first rule and contribute/extract it upstream rather than creating a Scriberig-only commodity widget framework.

A temporary view override is TUI presentation state but its semantic interpretation is still performed by the shared style resolver.

## 22. Web Integration

The reusable web packages should consume the same protocol/client/application contracts.

The integrated editor may render semantic source locally or request rendered source depending on the existing editor architecture, but it must display the same effective style/provenance/fidelity for equivalent inputs.

MUI or another opinionated UI library may provide controls. It does not own domain style semantics.

Reusable packages should make it possible for third-party browser clients to:

```text
query schemas
query effective style
select profiles/overrides
request projections
understand read-only versus editable fidelity
```

without importing the complete integrated application.

---

## 23. CLI and Server Integration

CLI commands may expose style/profile selection and explicit materialization/export options, but they must call shared application semantics.

Examples of user intent, not prescribed command syntax:

```text
show effective TypeScript style and provenance
render this module using my view style
materialize project using workspace policy
export this scope using profile X
```

The server must not apply the server process owner's personal style as an ambient global default for remote users.

---

## 24. Agent Integration

Agents normally operate on semantic entities/operations rather than editing styled text.

When a styled source projection is supplied to an agent for inspection or interoperability:

- its exact snapshot/scope/style/renderer identity should be part of the effective context/provenance;
- the agent must not infer deletion of omitted semantic content solely from a lossy projection;
- semantic mutation still uses candidate/migration/change semantics;
- later user presentation changes do not mutate already compiled model context.

Style selection must not become a hidden source of provider-continuation divergence. If an invocation's compiled context genuinely changes because a differently styled projection is included, that change participates in the normal effective-context fingerprint.

---

## 25. Rust Domain Implementation Direction

The current Rust renderer is a small deterministic semantic renderer and hard-codes four-space indentation.

Its first style-aware slice should:

1. define a Rust source-style schema/value in the Rust domain crate;
2. normalize an indentation property at minimum;
3. pass exact resolved style into rendering;
4. replace hard-coded indentation with style-derived indentation;
5. retain deterministic output;
6. add two-style conformance tests proving different bytes from the same semantic `RustFile`;
7. keep semantic Rust structures unchanged when only style changes.

Do not generalize Rust-specific properties into `sr-projection`.

Where mature formatter behavior is eventually delegated to rustfmt or another engine, the adapter must still preserve exact declared configuration and deterministic projection identity.

---

## 26. ECMAScript/TypeScript Domain Implementation Direction

The current ECMAScript crate already parses JavaScript/TypeScript/JSX/TSX through Oxc into serializable structural records.

Add source projection support behind the domain adapter boundary rather than teaching generic projection code JavaScript formatting.

Before choosing an implementation engine, evaluate the current Oxc code-generation/formatting capabilities and other viable formatter engines against:

```text
Rust/library integration
exact configuration control
determinism
comment/directive preservation
source-map/mapping support
round-trip behavior
JS/TS/JSX/TSX coverage
ability to avoid hidden ambient config
```

The selected renderer must accept canonical/resolved Scriberig style input.

If it delegates to an external formatter, all output-affecting configuration must be explicit and captured in renderer/style identity.

## 27. Testing Matrix

### 27.1 Core projection tests

Prove:

- resolved style reference/value mismatch is rejected;
- resolved style participates in cache identity;
- style-only changes do not create semantic content revisions;
- fidelity is calculated from the exact style.

### 27.2 Domain tests

For Rust and ECMAScript as implemented:

- same semantic source + style A/style B -> expected different bytes;
- deterministic repeated render;
- invalid style property -> structured diagnostic;
- comment/directive policies preserve mandatory categories;
- lossy styles classify correctly.

### 27.3 Reconciliation tests

Prove at least:

```text
baseline contains canonical comment C
style hides C
user edits visible statement S
reconcile changes S and preserves C
```

Also prove:

- a comment visible in baseline and explicitly removed may produce a deletion candidate according to domain rules;
- concurrent canonical changes still produce correct conflict/merge behavior;
- style changes after baseline creation do not alter interpretation of old edits;
- unsupported loss-aware reconciliation produces read-only fidelity.

### 27.4 Materialization tests

Prove:

- User A and User B have different personal styles;
- shared materialization produces the same bytes for both under one workspace policy;
- changing User A's preference does not mark managed shared files dirty;
- changing workspace materialization policy deliberately rerenders and establishes a new synchronization baseline.

### 27.5 Cross-surface tests

Use deterministic fixtures to prove equivalent effective style/fidelity through:

```text
embedded application
remote client/protocol
TUI semantic component
web client/model
```

Compare semantic/effective style results rather than terminal glyphs or browser pixels.

## 28. Migration and Compatibility

Do not break all existing projections in one step.

A suitable migration order is:

```text
1. add resolved-style and fidelity contracts
2. retain compatibility constructors for current StyleRef-only render requests
3. implement shared resolver/application discovery
4. migrate one domain renderer (Rust) to prove the contract
5. add ECMA renderer/style support
6. introduce typed reconciliation baselines and baseline artifact retention
7. enable loss-aware editable styles only after tests prove preservation
8. expose shared controls through protocol/web/TUI
9. remove compatibility paths once all active adapters provide exact resolved style
```

During migration, an adapter that does not support style schema/discovery may expose one fixed exact default style and classify its capabilities conservatively.

## 30. Completion Criteria

This Level-2 design is satisfied when:

- exact style references are resolved to exact renderer-consumable canonical values before rendering;
- domain adapters advertise/validate meaningful style schemas without leaking language properties into `sr-projection`;
- personal view and shared materialization resolution are separate and deterministic;
- Rust and ECMAScript can render at least meaningful style differences from one canonical semantic source;
- exact resolved style affects render/cache identity but not semantic source identity;
- exact editable projection baselines include style/renderer/output evidence;
- lossy editable styles preserve hidden canonical content through loss-aware reconciliation or are read-only;
- shared application/protocol/client contracts expose effective style and fidelity;
- TUI and web consume those shared contracts;
- `rpi-tui` remains the terminal framework/theme owner while Scriberig remains the semantic projection/style owner.
