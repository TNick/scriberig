# Snapshots, Roots, and Persistent Collections

## Purpose

This document specifies how the Level 1 snapshot model is represented without tying semantic containment to storage identity.

## Snapshot model

A snapshot is an immutable mapping:

```text
EntityId -> RevisionId
```

The mapping is independent from domain containment.

Changing a paragraph revision must not automatically change the revision of its containing section unless the section's own canonical structure changed.

## Persistent snapshot map

The initial implementation must use a persistent structurally shared map abstraction.

The logical API must support:

```text
lookup(snapshot, entity)
apply_changes(base_snapshot, changes) -> new_snapshot
iterate(snapshot)
diff(snapshot_a, snapshot_b)
```

A new snapshot may share all unchanged internal map nodes with its base snapshot.

The public API must not expose the concrete persistent-map implementation.

The first implementation may use a simple copy-on-write persistent tree suitable for correctness before later optimizing to a HAMT, radix trie, Merkle B-tree, or another structure.

The design requirement is behavioral:

- creating a snapshot from a small change must not require copying every entity mapping;
- snapshot identity must be deterministic for exact map content;
- equal complete maps must converge to the same snapshot identity when encoded under the same format version.

## Snapshot changes

A snapshot builder accepts changes such as:

```text
Set(EntityId, RevisionId)
Remove(EntityId)
```

The builder is not itself a semantic migration system. It only creates the resulting exact mapping.

Higher layers explain why those changes happened.

## Named roots

Named roots provide mutable names for immutable snapshots.

Examples:

```text
main
workspace/123
session/current
```

The storage API must support:

```text
read_root(name) -> SnapshotId?
compare_and_set_root(name, expected, new) -> result
```

Promotion must be atomic.

A compare-and-set failure means another writer advanced the root; it must never silently overwrite the newer value.

## Persistent semantic collections

Entity revisions may contain canonical ordered collections such as section children or function parameters.

Large collections should not require copying every element when one item is inserted, removed, or moved.

The storage-facing collection representation should therefore support structural sharing.

The first implementation may use a simple immutable chunked sequence. It must hide the physical representation behind a collection API so a later implementation can replace it.

Child revisions do not include their index merely because they appear in an ordered collection.

## Files prescribed by this design

Within `sr-store`:

```text
crates/sr-store/src/
├── snapshot.rs
├── roots.rs
└── collection.rs
```

Within `sr-store-memory`:

```text
crates/sr-store-memory/src/
├── lib.rs
├── snapshot.rs
└── roots.rs
```

The SQLite backend will implement the same behavior in its own backend modules.

## Required tests

- Build `S2` from `S1` with one changed entity and confirm all other mappings resolve identically.
- Reconstruct the same complete mapping through a different update order and confirm identical `SnapshotId`.
- Remove an entity and confirm the prior snapshot still resolves it.
- Branch two snapshots from one base without altering the base.
- Compare-and-set root succeeds with the expected value.
- Compare-and-set root fails when the expected value is stale.
- Reordering a semantic collection changes the container revision while leaving child revision IDs unchanged.

## Non-goals

This design does not define merge semantics, migration provenance, or domain-specific collection meaning.
