# SQLite Backend, Transactions, and Recovery

## Purpose

This document defines the first durable backend implementation for the persistence model.

The Level 1 design allows any backend that preserves the required semantics. This Level 2 design selects SQLite for the first durable implementation because it provides an embedded transactional store while keeping the public storage API backend-independent.

## Backend boundary

`sr-store-sqlite` implements `sr-store` traits. No higher crate should issue SQL against its internal tables.

SQLite-specific schema and migration code stays inside this crate.

## Required persisted categories

The backend must persist enough information to reconstruct:

- immutable revision records;
- persistent snapshot-map nodes;
- snapshot roots;
- named roots;
- storage format/schema version;
- required backend indexes;
- integrity/recovery metadata.

Derived caches may later use the same database, but they must remain distinguishable and removable.

## Transaction model

Canonical promotion is atomic.

A write flow is conceptually:

```text
begin transaction
  insert missing immutable revisions
  insert missing persistent map/collection nodes
  insert new snapshot record
  update required indexes
  compare expected named root
  move named root to new snapshot
commit
```

If the expected root is stale, the transaction must fail without promoting the root.

Already-created immutable content may be safely reused if a retry later produces the same content.

## Crash safety

After process or machine interruption, one of two states is visible:

- the previous committed root;
- the complete newly committed root.

A partially published canonical snapshot is never visible.

Unreachable immutable records left by aborted or interrupted preparation are acceptable and can be reclaimed later.

## SQLite schema evolution

The backend owns a storage schema version separate from semantic schema versions and canonical encoding versions.

Backend schema upgrades must be transactional where SQLite permits it and must not invent semantic migrations.

An upgrade that reorganizes tables or indexes but preserves semantic state is a storage migration only.

## Connection behavior

The first implementation may use a single writer model. Reads may use additional connections if the chosen SQLite wrapper supports safe concurrency.

The public storage API must not promise SQLite-specific locking behavior.

Use explicit transactions for root promotion and integrity-sensitive multi-step writes.

## Files prescribed by this design

```text
crates/sr-store-sqlite/src/
├── lib.rs
├── connection.rs
├── schema.rs
├── revision.rs
├── snapshot.rs
├── roots.rs
└── recovery.rs
```

Schema SQL may be embedded in Rust or stored under a crate-local migrations directory. If migration files are used, create:

```text
crates/sr-store-sqlite/migrations/
```

with monotonically ordered migration files.

## Required tests

- Open a fresh database and initialize schema.
- Reopen it and read previously stored revisions and roots.
- Inserting the same revision twice does not create divergent logical copies.
- Failed compare-and-set root does not publish the attempted snapshot as the named root.
- Transaction rollback preserves the previous root.
- Reopening after a committed write returns the new root.
- Simulated failure before root promotion leaves the previous root visible.
- Backend schema version is detectable and unsupported newer versions fail explicitly.

## Non-goals

This design does not implement semantic merging, projection reconciliation, or distributed multi-writer consensus.
