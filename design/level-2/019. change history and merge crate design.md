# Change History and Merge Crate Design

## Purpose

This document turns `design/level-1/005. changes migrations branches and merge.md` into a concrete Rust library boundary and file plan.

It depends on the persistence boundaries already defined in `design/level-2/001. persistence crate boundaries.md`.

This design does not change the Level 1 model. It chooses where the change model lives in code, which public concepts it exposes, and which implementation files must exist.

## Required crate

Create one backend-independent crate:

```text
crates/sr-change/
```

Dependency direction:

```text
sr-core
   ↑
sr-store
   ↑
sr-change
```

`sr-change` may depend on `sr-core` and the public storage interfaces from `sr-store`.

`sr-change` must not depend on:

- SQLite;
- a concrete storage backend;
- agents;
- sessions;
- Markdown;
- a programming-language adapter;
- CLI, HTTP, TUI, or web UI code.

Domain adapters and product surfaces depend on `sr-change`, not the reverse.

## Responsibilities

`sr-change` owns the domain-independent model and algorithms for:

- migrations;
- generic change operations;
- provenance of changes;
- explicit history topology;
- branches and isolated workspaces;
- optimistic promotion of named roots;
- semantic snapshot diffs;
- structured conflicts;
- three-way merge;
- semantic replay and rebase;
- change-history and lineage queries;
- progressively disclosed change summaries.

It does not own revision persistence, snapshot persistence, or named-root storage. Those remain storage capabilities supplied through `sr-store`.

## Migration model

A committed migration identifies one exact transition:

```text
base SnapshotId
result SnapshotId
```

The migration must contain enough universal information to describe the exact changed set even when no domain adapter is installed.

The minimum universal entity delta is:

```text
EntityDelta {
    entity: EntityId,
    before: Option<RevisionId>,
    after: Option<RevisionId>,
}
```

Interpretation:

- `None -> Some` means creation or introduction into the relevant canonical state;
- `Some -> None` means semantic removal from that state;
- `Some(old) -> Some(new)` means the visible revision changed;
- equal before and after values must not be stored as a change.

A migration may additionally record generic semantic operations and domain-specific semantic operation references.

## Generic operations

The initial generic operation vocabulary must support at least:

```text
CreateEntity
ReplaceRevision
RemoveEntity
AddRelation
RemoveRelation
InsertCollectionMember
RemoveCollectionMember
MoveCollectionMember
ReplaceCollectionStructure
```

These operations describe intent where known. They do not replace the authoritative base/result snapshots and entity deltas.

Do not require every migration to contain a perfect semantic operation list. Exact before/after state remains sufficient for correctness.

## Domain-specific operations

`sr-change` must allow richer operations without knowing their domain schemas.

The generic crate should represent a domain operation as a typed reference or opaque domain payload with explicit domain/type identity.

Do not add Rust-specific, Markdown-specific, PDF-specific, or session-specific variants to the universal operation enum.

Domain adapters may provide interpretation and replay support through extension traits.

## Provenance

A migration must support provenance describing where the change came from.

The universal source categories should cover at least:

```text
User
ExternalProjection
Agent
Cli
Api
WebEditor
Tui
Importer
Refactoring
Merge
Synchronization
System
Other
```

The model must allow additional structured references such as:

- actor or tool identity;
- workspace or branch identity;
- external projection identity;
- parent migration identities;
- validation-result references;
- free-form or typed metadata owned by higher layers.

Provenance does not bypass validation or promotion rules.

## History topology

History is a DAG, not a list.

The crate must expose structures and queries that preserve:

- base and result snapshot for each migration;
- linear parentage where applicable;
- multiple merge parents where applicable;
- lookup of migrations that introduced a revision or touched an entity;
- common-ancestor discovery through snapshot ancestry supplied by storage.

Physical write order and timestamps must never be used as the authoritative history topology.

## Branches

A branch is a named or semantic line of work whose current head is a snapshot.

The crate should model branch state independently from snapshot state.

At minimum, branch-facing code must be able to represent:

```text
branch entity/reference
base snapshot
current snapshot
status
optional title
optional purpose
optional short description
optional outcome
optional resulting migration
```

The stable semantic representation of branch metadata may later live in the universal graph, but `sr-change` owns the branch/workspace operations that use snapshots and named roots.

## Workspaces

A workspace is an isolated branch used for speculative work.

It must always have an exact base snapshot and a current snapshot.

Failed validation or abandoned work must not modify the base snapshot or target named root.

Workspace APIs must make it possible to:

- create from a base snapshot;
- advance through descendant snapshots;
- inspect base/current state;
- abandon without promotion;
- promote or merge completed work later.

## Promotion

Promotion advances a named root from an expected snapshot to a result snapshot.

The operation must use optimistic concurrency.

Conceptually:

```text
promote(root, expected = S1, result = S2)
```

If the current root no longer resolves to `S1`, promotion must fail with a conflict result containing the actual current snapshot.

It must never silently overwrite concurrent work.

The storage backend performs the atomic compare-and-promote. `sr-change` provides the higher-level operation and error semantics.

## Semantic diff

A diff compares any two snapshots. It does not require direct ancestry.

The universal diff must report at least:

- entities introduced;
- entities removed from the compared state;
- entities whose revision changed.

Where canonical relation/collection information is available through generic graph interfaces, the diff may additionally expose relation and collection changes.

Domain adapters may enrich the same diff with domain meaning.

The diff API must not imply that every entity changed merely because the global `SnapshotId` changed.

## Merge

The universal merge entry point is three-way:

```text
base
left
right
```

The engine first compares entity-resolution changes against the base.

Rules:

1. Changes made by only one side are adopted.
2. Equal resulting revisions on both sides converge without conflict.
3. Independent entities merge without conflict.
4. Same-entity changes are passed to progressively deeper merge logic.
5. The generic engine may resolve generic relation/collection changes when intent is unambiguous.
6. Domain-specific strategies may resolve conflicts more deeply.
7. Ambiguity must remain a structured conflict; the engine must not choose silently.

Merge creates a new result state. It never mutates base, left, or right.

## Structured conflicts

The universal conflict model must carry enough information to inspect the disagreement without rendering textual conflict markers.

At minimum:

```text
Conflict {
    entity: EntityId,
    base: Option<RevisionId>,
    left: Option<RevisionId>,
    right: Option<RevisionId>,
    kind: ConflictKind,
}
```

Initial conflict kinds should distinguish at least:

```text
BothModified
DeleteModify
CompetingCreate
RelationConflict
CollectionConflict
DomainConflict
```

Conflicts may carry a minimal affected field/relation/collection path and domain-specific detail.

A merge result may contain resolved deltas plus unresolved conflicts. Promotion policy decides whether unresolved results may become current; the default project workflow should require resolution first.

## Rebase and replay

Rebase creates new history from an existing line of work and a new base.

It must never rewrite retained historical snapshots or migrations.

Replay should prefer recorded semantic operations when they are available and still valid.

If only exact state deltas are available, the rebase engine may use generic replay rules or surface a conflict rather than inventing intent.

Domain-specific replay must be supplied through extension traits.

## Change queries

The crate must expose a service layer capable of answering Level 1 queries such as:

```text
what changed between snapshots A and B?
what migration introduced revision R?
what is the history of entity E?
which migrations touched entity E?
what branches descend from snapshot S?
what is the common ancestor of A and B?
what conflicts prevent merging A and B?
```

Queries must use explicit history and storage ancestry, never physical insertion order.

## Summaries and progressive disclosure

Migration, diff, branch, and merge-result objects must support compact inspection before full detail.

The crate should expose deterministic structural summaries such as:

```text
changed entity count
created entity count
removed entity count
conflict count
base/result snapshots
source category
validation status reference count
```

Human-authored or model-generated descriptions belong to higher layers but can reference these objects.

## Public extension traits

The crate should provide narrow extension points for domain adapters.

At minimum, design for traits equivalent in responsibility to:

```text
DomainDiffInterpreter
DomainMergeStrategy
DomainReplayStrategy
```

Exact trait names and method signatures may be adjusted during implementation, but the dependency direction is mandatory: `sr-change` defines extension points; domain crates implement them.

## Required dependency behavior

The crate should rely on public storage capabilities for:

- resolving an entity in a snapshot;
- enumerating changes between snapshot mappings efficiently where available;
- snapshot ancestry traversal;
- constructing a descendant snapshot from entity-resolution changes;
- named-root compare-and-promote.

If a required storage capability is not yet present in `sr-store`, the implementation must extend the backend-independent `sr-store` trait first and add conformance coverage for both memory and SQLite backends. It must not reach around `sr-store` into a backend implementation.

## Testing strategy

The conformance suite must cover at least:

- direct migration with one revision replacement;
- create and remove entity deltas;
- branch creation without copying state;
- failed optimistic promotion when the expected root is stale;
- diff of unrelated sibling snapshots;
- automatic merge of disjoint changes;
- automatic convergence when both sides produce the same revision;
- structured conflict for competing same-entity edits;
- delete/modify conflict;
- rebase that creates new history while preserving the original line;
- history query using explicit topology rather than insertion order;
- cross-domain migration represented only through universal entity deltas;
- no semantic migration for representation-only changes.

Tests should use the in-memory store whenever possible. Durable backend behavior belongs to shared store conformance tests rather than being duplicated here.

## Completion criteria

This design is satisfied when:

- `sr-change` builds without a concrete backend dependency;
- all prescribed modules exist with focused responsibilities;
- migrations preserve exact base/result snapshots and universal entity deltas;
- branches and workspaces operate on snapshot references rather than copied state;
- named-root promotion uses optimistic concurrency;
- diff works between arbitrary snapshots;
- disjoint three-way changes merge automatically;
- unresolved ambiguity is represented as structured conflicts;
- rebase produces new history;
- generic history remains useful without any domain adapter;
- the conformance suite passes against the in-memory persistence backend.
