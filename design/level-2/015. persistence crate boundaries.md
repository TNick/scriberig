# Persistence Crate Boundaries

## Purpose

This document turns the persistence guarantees in `design/level-1/004. persistence and storage model.md` into Rust crate boundaries.

This level chooses implementation structure. It does not change the Level 1 model.

## Required crates

The initial persistence slice must create these workspace crates:

```text
crates/
├── sr-core/
├── sr-store/
├── sr-store-memory/
└── sr-store-sqlite/
```

The dependency direction is:

```text
sr-core
   ↑
sr-store
   ↑        ↑
sr-store-memory  sr-store-sqlite
```

No crate in this slice may depend on agents, sessions, Markdown, source-code adapters, the CLI, the API server, or web code.

## `sr-core`

`sr-core` owns universal identifiers and value types that must not depend on a backend.

Initial public concepts:

- `EntityId`
- `RevisionId`
- `SnapshotId`
- `RootName`
- `ObjectType`
- `EncodingVersion`

Identifiers must be strongly typed. Do not use raw `String` or byte arrays throughout the public API when a specific identifier type exists.

The crate may contain deterministic encoding support shared by persistence crates, but it must not contain SQLite code or storage traits.

## `sr-store`

`sr-store` owns the backend-independent persistence API and logical storage types.

It must define traits or equivalent interfaces for:

- immutable revision insertion and retrieval;
- snapshot lookup;
- snapshot construction from a base snapshot plus changes;
- named-root lookup and atomic promotion;
- ancestry/history traversal needed by higher layers;
- integrity verification hooks;
- reachability enumeration;
- index rebuild hooks where the backend owns physical indexes.

It also owns storage-level error types.

The public API must describe semantic persistence operations, not SQL statements, paths, pages, or table layouts.

## `sr-store-memory`

`sr-store-memory` implements the `sr-store` interfaces entirely in memory.

Its purposes are:

- executable specification of store behavior;
- fast unit and conformance tests;
- deterministic testing of concurrency and root promotion;
- a backend usable by embedding applications that do not need persistence.

It must implement the same externally visible behavior as the SQLite backend.

## `sr-store-sqlite`

`sr-store-sqlite` provides the first durable embedded backend.

It must hide SQLite-specific details behind `sr-store` interfaces.

It owns:

- schema creation and upgrades for storage-internal tables;
- transactions;
- durable immutable revision storage;
- persistent snapshot structures;
- named roots;
- backend indexes;
- integrity metadata needed for recovery.

No consumer outside this crate should issue SQL against Scriberig's internal tables.

## Workspace files prescribed by this design

The first implementation agent must create at least:

```text
Cargo.toml
crates/sr-core/Cargo.toml
crates/sr-core/src/lib.rs
crates/sr-store/Cargo.toml
crates/sr-store/src/lib.rs
crates/sr-store-memory/Cargo.toml
crates/sr-store-memory/src/lib.rs
crates/sr-store-sqlite/Cargo.toml
crates/sr-store-sqlite/src/lib.rs
```

Additional modules should be introduced only when their responsibility is clear from the other Level 2 storage designs.

## Architectural rules

- `sr-core` must remain backend-independent.
- `sr-store` must remain backend-independent.
- Backend crates depend on `sr-store`; `sr-store` never depends on a backend crate.
- The memory and SQLite implementations must pass the same conformance tests.
- Named roots are mutable references to immutable snapshots. Snapshots themselves are never updated in place.
- Public persistence APIs must not assume an agent exists.

## Completion criteria

This design is satisfied when the workspace builds with the four crates, the dependency direction is enforced, and both backend crates can implement one shared storage conformance suite without exposing backend-specific operations.
