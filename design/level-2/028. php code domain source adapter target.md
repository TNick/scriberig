# PHP Code Domain Source Adapter Target

## 1. Purpose

This document defines the exact source-domain capability that the golden self-hosting agent is expected to add when the user asks:

```text
Add support for ingesting PHP source files.
```

It is a target contract, not permission to pre-install PHP support before the self-hosting product gate.

The golden baseline must still lack registered first-class PHP ingestion. Test/reference fixtures may contain the expected candidate implementation described here, but the agent-produced candidate is what introduces PHP support into the temporary tested checkout.

---

## 2. Architectural Placement

PHP is a language-specific specialization of Scriberig's shared source/code domain.

The expected dependency direction is:

```text
PHP source bytes
    -> PHP parser/adapter
    -> PHP document + deterministic syntax/code facts
    -> shared code-domain concepts
    -> universal graph/project ownership
```

The PHP adapter must not introduce a private database, private query engine, or PHP-specific project catalog.

The expected production crate shape produced by the golden candidate is equivalent to:

```text
crates/domains/scriberig-domain-php/
```

and should follow the conventions used by existing language domain crates, especially a Tree-sitter-based source adapter such as Python where appropriate.

---

## 3. File Classification

The minimum required project extension is:

```text
.php
```

A scanned `.php` file must be classified as a first-class PHP/code source and assigned the PHP adapter in the persisted project manifest.

Classification is decided during scan and retained in the manifest. Import must consume that decision rather than independently re-guessing the format from a fresh filesystem read.

The golden candidate must include regression coverage proving that unrelated source extensions keep their existing adapter choices.

Do not silently broaden the milestone to every PHP-adjacent extension unless repository policy explicitly adds them.

---

## 4. Exact Source Evidence

Before or alongside semantic parsing, project import retains the exact source artifact according to existing project ingestion conventions.

For every PHP source this includes at least:

```text
project ownership
project-relative path
exact bytes
content digest
classification/media metadata
PHP adapter identity/version
```

Semantic PHP structure is additional knowledge. It does not replace exact source evidence.

All imported semantic PHP entities retain provenance to the exact source artifact/import that produced them.

---

## 5. Parser Strategy

The golden target should use a mature inert PHP parser compatible with the repository's deterministic syntax-domain architecture.

A Tree-sitter PHP grammar is the preferred target because it aligns with existing complete-syntax-tree adapters and supports PHP mixed with inline HTML.

The exact dependency version must be pinned/resolved through normal Cargo metadata and lockfile policy.

The parser is an implementation dependency, not a semantic identity exposed to clients beyond normal adapter/version provenance.

---

## 6. Inert Parsing

Importing PHP is parsing, not executing PHP.

The adapter must never, as part of ingestion:

- execute the PHP program;
- evaluate expressions for side effects;
- follow `include`/`require` by executing them;
- load Composer autoloaders;
- run project scripts;
- make network requests because source code asks it to;
- contact application endpoints embedded in code;
- resolve remote resources as an execution side effect.

Any later derived analyzer that intentionally resolves dependencies is a separate capability with separate trust/provenance rules.

---

## 7. PHP Document Model

The language adapter exposes a versioned root document concept equivalent to:

```text
PhpDocument {
    adapter/schema metadata
    serialized complete syntax tree
    deterministic ordered syntax-node records
    source metadata
}
```

Use repository domain schema/version conventions instead of inventing ad-hoc unversioned property names.

The document should participate in the shared code-domain/source-document concepts where applicable.

---

## 8. Complete Syntax Preservation

The adapter must preserve complete deterministic syntax structure, not merely extract top-level symbol names.

For every syntax node where the existing source-domain pattern represents node entities, retain information equivalent to:

```text
deterministic structural/node path
node kind
named flag
missing/error state
byte start/end
line/column start/end
parent/child ordering
field relationship when available
leaf/source text when appropriate
comment information
```

Unnamed nodes may be required to preserve faithful syntax and must not be discarded merely because they are not useful navigation labels.

Repeated parsing of identical source bytes must produce semantically equivalent serialized tree structure and deterministic traversal ordering.

---

## 9. Stable Node and Entity Identity

Imported PHP children use the repository's deterministic domain/project identity conventions.

Identity must not depend on:

- random UUID generation for each parse;
- nondeterministic filesystem enumeration order;
- hash-map iteration order;
- absolute machine-specific paths where project-relative ownership suffices.

Unchanged re-import should preserve semantic equivalence and stable identities wherever the domain identity policy promises continuity.

---

## 10. Source Ranges

Syntax/code records expose exact ranges needed for inspection and source projection:

```text
byte start/end
start row/column
end row/column
```

Range conventions must be consistent with existing code-domain adapters.

These mappings must be sufficient for a common source renderer/client to identify where a named PHP declaration came from without parsing PHP privately in the frontend.

---

## 11. Comments

PHP comments are source knowledge and should remain represented through syntax and/or shared code-domain comment metadata according to existing adapter conventions.

Coverage should include the comment forms supported by the chosen grammar, including representative line and block comments.

Do not strip comments before constructing the canonical PHP syntax representation.

---

## 12. Named Declaration Metadata

In addition to complete syntax, the adapter should expose human-meaningful metadata for important named PHP declarations through the shared code navigation model where practical.

The golden target includes at least:

```text
namespace
class
interface
trait
enum when supported by the grammar/version
function
method
```

For these concepts, clients should be able to obtain a display name/kind/source path/range/containment context through public semantic data rather than reparsing the serialized PHP tree.

Lower-level syntax remains available for raw knowledge inspection.

---

## 13. Inline HTML

A normal PHP source file may contain text/HTML around PHP code blocks.

Representative valid input:

```php
<html>
<body>
<?php
function title(): string {
    return "Scriberig";
}
?>
</body>
</html>
```

The chosen grammar/adapter must treat this as legitimate PHP source according to parser semantics and retain the complete parse structure, including surrounding inline content represented by the grammar.

Do not assume every `.php` file begins with `<?php` and contains only PHP syntax until EOF.

---

## 14. UTF-8 and Decode Failures

Follow existing code adapter policy for source decoding.

If the PHP adapter requires UTF-8 input and exact bytes cannot be decoded as required, return the normal structured adapter diagnostic at the decode stage rather than lossy silent substitution.

Exact source bytes remain captured according to project import/error evidence policy.

---

## 15. Parse Error Semantics

Malformed PHP must not be presented as a successfully trusted `PhpDocument` merely because the parser could construct a partial error tree.

The adapter returns a structured diagnostic equivalent to:

```text
path
adapter = php
stage = parse
code/category
message
source range/position when available
retryability
```

The project importer associates that diagnostic with the exact source artifact.

When PHP semantic parsing is required for the manifest-selected adapter, the project import does not silently promote a partial successor that omits/buries the PHP failure.

The previous valid project snapshot remains authoritative.

---

## 16. Project Import Mapping

For a valid PHP source artifact, project import creates ordinary universal/domain records equivalent to:

```text
project source artifact
    -> PHP document entity/revision
        -> deterministic PHP syntax/code entities
```

Every imported entity that belongs to the file participates in normal source-relative project ownership so later re-import/deletion reconciliation can identify what the source contributed.

Do not create a PHP-only ownership table that project cleanup cannot understand.

---

## 17. Common Semantic Discovery

After importing a PHP fixture containing `Greeter::greet`, public semantic operations must be able to discover and inspect those named declarations through the same shared navigation/query model used for other code domains.

Conceptually:

```text
find(project@S, name="Greeter", kind=class)
find(project@S, name="greet", kind=method)
inspect(Greeter@S)
inspect(greet@S)
render(source for relevant document/selection)
follow(source provenance)
```

The test must not pass solely because raw text search can find the token `Greeter`.

PHP must not require a private PHP-specific query universe for basic named navigation.

---

## 18. Source Projection

At minimum, imported PHP source supports a truthful read/source projection that returns:

```text
project/snapshot identity
source-relative path
exact or faithful source text
semantic/source mapping for supported selected entities
read/write capability metadata
```

Bidirectional PHP editing is not required by this self-hosting milestone.

If the projection is read-only, advertise it as read-only rather than pretending reconciliation/apply support exists.

---

## 19. Domain Capability Metadata

Inspecting PHP domain objects should reveal relevant shared capabilities through the domain/capability registry.

Examples include:

```text
inspect
list/follow syntax or containment
find named declarations
render source
follow provenance
```

The PHP adapter/schema version must participate in the repository's normal domain version metadata so imported results can explain which adapter version produced them.

---

## 20. Workspace and Dependency Integration

The golden candidate is expected to update normal Rust workspace metadata so the new domain crate compiles and `scriberig-project` can call it.

Likely candidate areas include:

```text
Cargo.toml
Cargo.lock
crates/domains/scriberig-domain-php/**
crates/scriberig-project/**
capabilities.toml or domain/format registry metadata where authoritative
relevant test fixtures/documentation
```

Follow actual repository ownership rather than duplicating extension lists across every product surface.

TUI/web/CLI should consume the project service result; they do not each implement `.php` classification independently.

---

## 21. Required Domain Tests

The candidate must include focused tests equivalent to:

### PHP-DOMAIN-01 — declarations

Parse a fixture containing namespace, class, method, and free function. Assert root/document, named declaration metadata, ranges, and deterministic node order.

### PHP-DOMAIN-02 — comments

Assert representative PHP comments survive syntax/semantic import.

### PHP-DOMAIN-03 — nested syntax

Use nested control flow/expressions and prove the adapter retains complete structure rather than only top-level declarations.

### PHP-DOMAIN-04 — inline HTML

Parse mixed HTML/PHP input and verify complete successful structure plus discoverable PHP function/declaration.

### PHP-DOMAIN-05 — malformed input

Use deterministic invalid PHP and assert structured parse failure/position with no trusted successful document result.

### PHP-DOMAIN-06 — deterministic output

Parse identical bytes repeatedly and compare normalized serialized tree/node ordering and deterministic identity inputs.

---

## 22. Required Project Integration Tests

### PHP-IMPORT-01 — classification

Scan a project containing `src/example.php`. Persisted manifest selects the PHP adapter.

### PHP-IMPORT-02 — exact source preservation

Import valid PHP. Exact bytes/digest on the source artifact match input.

### PHP-IMPORT-03 — ownership

PHP document and syntax/code entities are owned by the correct project and relative source path.

### PHP-IMPORT-04 — semantic discovery

Use public semantic operations to find a known class and method. Do not use private database queries or raw grep as the proof.

### PHP-IMPORT-05 — source projection

Render the imported PHP source at the exact project snapshot and verify correct path/text/mapping.

### PHP-IMPORT-06 — malformed file blocks clean promotion

Starting from a valid imported project snapshot, scan/import malformed PHP and assert structured diagnostic plus unchanged authoritative prior snapshot.

### PHP-IMPORT-07 — unchanged re-import

Rescan/reimport unchanged valid PHP and verify idempotent semantic equivalence/stable ownership according to project invariants.

### PHP-IMPORT-08 — deletion reconciliation

Remove the PHP source, rescan/import, and assert only entities owned by that source/project are reconciled away.

---

## 23. Classification Regression Matrix

Adding PHP must not steal unrelated files from existing adapters.

At minimum retain coverage equivalent to:

```text
.rs -> Rust
.py/.pyi/.pyw -> Python
.ts/.tsx -> TypeScript
.js/... -> JavaScript
.c/.h/... -> current C/C++ policy
.md -> Markdown
.toml/json/yaml -> structured-data policy
unknown UTF-8 -> generic text policy
binary/non-UTF-8 -> binary policy as applicable
.php -> PHP after candidate
```

The baseline before the agent candidate intentionally does not make the final `.php -> PHP` assertion true.

---

## 24. Fresh-Database PHP E2E

The most important candidate validation creates a fresh database and a small standalone project such as:

```text
php-golden/
  README.md
  src/Greeter.php
```

Then, using public project/semantic operations:

```text
scan
review persisted manifest
import
workspace resolve
find Greeter
find greet
inspect/render
```

Expected result:

- `.php` classified by the candidate's PHP adapter;
- exact source retained;
- semantic PHP structure created;
- class/method discoverable;
- source projection renders;
- no blocking diagnostics.

This test must execute against the candidate workspace/build so it proves the proposed PHP feature actually composes before user acceptance.

---

## 25. Golden Baseline Fixture Rule

Repository test data may include:

- expected PHP source fixtures;
- declarative expected candidate file list;
- scripted-provider instructions;
- expected source snippets or complete test-only files needed to construct the candidate;
- validation assertions.

It must not register the PHP adapter in the normal baseline runtime before the scenario begins.

If a future unrelated change adds first-class PHP support permanently, this golden scenario must deliberately choose another absent format or preserve an explicit historical/baseline fixture. For the present milestone, PHP is the required absent format.

---

## 26. Non-Goals

The PHP target does not require:

- executing PHP;
- Composer dependency resolution during import;
- PHP type inference;
- cross-file symbol resolution;
- a PHP compiler/interpreter integration;
- bidirectional PHP source reconciliation/editing;
- LSP functionality;
- formatting PHP;
- interpreting templates beyond syntax represented by the chosen grammar.

Those may be later derived/domain capabilities.

---

## 27. Completion Criteria

The PHP extension target is satisfied when the agent-produced project-wide candidate can add a versioned inert PHP code adapter that preserves complete deterministic syntax and source evidence, integrates `.php` into normal scan/import/ownership/navigation/rendering, rejects malformed PHP with structured non-promoting diagnostics, passes focused and fresh-database integration tests, and remains an ordinary Scriberig domain extension rather than a PHP-specific product path.
