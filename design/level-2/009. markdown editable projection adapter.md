# Markdown Editable Projection Adapter

## Purpose

This document defines the first concrete editable file projection required by `design/level-1/006. projections and bidirectional editing.md`.

Markdown is chosen because it exercises the full projection cycle—render, external edit, parse, identity reconciliation, migration, and rerender—without requiring compiler semantics.

The implementation belongs in `crates/sr-markdown` and plugs into `sr-projection` and `sr-projection-fs`.

## Scope

The first adapter must support semantic objects corresponding to at least:

```text
MarkdownDocument
Section
Heading
Paragraph
List
ListItem
Table
TableRow
TableCell
CodeBlock
QuoteBlock
Link
```

Inline formatting may be represented through a smaller inline model initially, but it must preserve authored text structure sufficiently for deterministic round-trip rendering.

The adapter must not require hidden Scriberig IDs in ordinary Markdown files.

## Domain boundary

The adapter owns the boundary between canonical document meaning and Markdown presentation.

Canonical domain structure includes:

- document/section hierarchy;
- block identity and order;
- paragraph textual content;
- list/list-item structure;
- table/row/cell structure;
- code block language/fence semantic data where represented;
- links and quotations;
- author-significant inline structure selected by the domain model.

Projection style may control:

- blank-line policy;
- list marker preference where semantically equivalent;
- table spacing/alignment formatting;
- wrapping where supported safely;
- code-fence choice where equivalent;
- final newline policy.

Style must not silently restructure sections, merge/split semantic paragraphs, or change link targets/code contents.

## Parser output

The Markdown parser must produce a candidate document representation distinct from stable canonical identity.

Candidate nodes should have local candidate IDs/paths sufficient for reconciliation diagnostics, but they must not invent `EntityId` values for existing canonical entities.

Parser output must preserve:

- semantic node kind;
- ordered child structure;
- text/content needed for canonical construction;
- source spans only as diagnostic/projection coordinates;
- parse diagnostics.

Source offsets and line numbers must not become canonical identity.

## Renderer

Rendering must be deterministic for the same:

```text
canonical document state
Markdown style revision
renderer version
relevant rendering context
```

The renderer should construct output from semantic blocks, not from a stored original Markdown blob.

Round-trip tests compare semantic structure, not byte equality across arbitrary input styles.

## Style

Define a `MarkdownStyle` domain value. The initial style should include only options the adapter can implement deterministically and safely.

Suggested initial properties:

```text
list_marker
ordered_list_delimiter
blank_lines_between_blocks
final_newline
code_fence_preference
table_spacing
```

Do not add style options that imply semantic transformations.

## Reconciliation strategy

Reconciliation compares:

```text
B = semantic state corresponding to the last synchronized Markdown projection
D = current canonical semantic state
C = parsed candidate semantic structure from the edited file
```

For the simple case where `D == B`, match candidate nodes against `B` and produce a migration proposal.

Matching evidence should be deterministic and ordered from strongest to weakest. Initial evidence should include:

1. exact unchanged subtree/content;
2. node type and exact content;
3. parent/section correspondence;
4. sibling sequence alignment;
5. nearby unchanged anchors;
6. heading/title or other domain-significant names;
7. conservative text similarity for same-kind nodes.

Do not use text similarity to force continuity when multiple matches are equally plausible.

## Content versus structure

The reconciler must emit different semantic intent for content and collection changes.

Example:

```text
before:
Section S -> [P1, P2]

candidate:
Section S -> [P1 changed, P3 inserted, P2]
```

Preferred result:

```text
P1: new revision of same entity
P3: new entity
P2: reused unchanged entity
S: new structural revision because child collection changed
```

A changed paragraph must not force unrelated siblings to receive new identities.

## Formatting-only edits

If parsed candidate semantics are equivalent to the synchronization base/current semantic state, return `NoSemanticChange`.

The filesystem layer may rerender according to configured style and update synchronization state, but no semantic migration is created.

## Ambiguity

If continuity is uncertain, return structured ambiguity/conflict details containing candidate node, possible canonical matches, evidence, and affected parent/collection.

Do not silently select one identical paragraph over another when evidence is insufficient.

A conservative new entity is preferable to unsupported lineage, subject to collection reconciliation rules.

## Unrepresented knowledge

Markdown does not represent all relationships attached to document entities.

Editing a paragraph through Markdown must preserve unrelated canonical relations such as:

- provenance;
- decisions referring to it;
- summaries;
- citations represented elsewhere;
- agent/session references.

The adapter therefore proposes changes only to semantic dimensions owned by the Markdown projection.

It must never rebuild the entire database state from the parsed file.

## Three-way reconciliation

When `D != B`, first derive semantic changes from `B -> D` and `B -> C`, then combine them through `sr-change`/domain-aware merge rules.

Disjoint block/entity changes should merge automatically.

Competing changes to the same paragraph/structure must produce structured conflict data rather than textual conflict markers as the canonical conflict representation.

A textual conflict view may be rendered later.

## Validation

Before promotion, validate at least:

- candidate document schema/structure;
- renderer can render the proposed resulting document;
- render-parse semantic equivalence of the resulting synchronized projection for supported constructs.

Invalid transient Markdown edits must not destroy the last valid canonical snapshot.

## Required acceptance scenarios

### Edit a paragraph

Input semantic state contains `P1 = "Objects are immutable."`.

External Markdown changes only that paragraph to `"Objects are immutable and content addressed."`.

Expected: same paragraph entity, new revision, no unrelated structural churn.

### Insert a paragraph

External Markdown inserts a new paragraph between two unchanged paragraphs.

Expected: new entity for inserted paragraph; both unchanged neighbors retain identity; parent child collection gets a structural revision.

### Reformat only

Change list markers/spacing in a way defined as presentation-equivalent.

Expected: no semantic migration.

### Ambiguous duplicate paragraphs

Two equal paragraphs exist and an edit cannot be mapped confidently.

Expected: structured ambiguity instead of fabricated lineage.

### Concurrent edit

Database changes paragraph `P1` while external file independently inserts `P3` elsewhere.

Expected: automatic three-way merge when changes are disjoint.

### Invalid transient file

Parser cannot produce a valid supported candidate.

Expected: old canonical snapshot and synchronization base remain intact; diagnostics/retry state are retained.

## Completion criteria

This design is satisfied when an ordinary Markdown file can be rendered from canonical document knowledge, edited with an external editor, parsed back into a candidate graph, reconciled without hidden IDs, converted into a semantic migration when meaning changed, treated as a no-op when only formatting changed, and rerendered as the new synchronization baseline.
