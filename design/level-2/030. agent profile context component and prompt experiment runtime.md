# Agent Profile, Context Component, and Prompt Experiment Runtime

## 1. Purpose

This document turns `design/level-1/021. agent profiles context composition and evidence driven optimization.md` into concrete subsystem boundaries and data-flow requirements.

It also refines the model/context portions of:

- `design/level-2/023. agent runtime model provider and branch orchestration.md`;
- `design/level-2/025. provider continuation and observable model execution.md`;
- `design/level-1/017. recursive agent decomposition and context isolation.md`;
- `design/level-1/018. durable plans dependency scheduling and multi-model execution.md`.

The controlling rule is:

> Scriberig resolves a versioned agent profile into typed context components, activates only the components relevant to the exact branch invocation, compiles them with semantic/session state into the provider-neutral effective request, and records enough provenance to reproduce and evaluate that behavior.

The first implementation must improve ordinary branch behavior before attempting autonomous prompt optimization.

---

## 2. Current Implementation Baseline

As of this design revision, the current implementation already provides important pieces that must be reused rather than replaced.

### `scriberig-session`

`Branch` owns durable branch activity and has `parent`, `purpose`, `turns`, model/tool evidence, status, and optional `BranchResult`.

`BranchResult` already contains:

```text
status
summary
result_kind
references
result_handles
touched
produced_changes
validations
unresolved_questions
```

### `scriberig-app`

The local child completion path stores the child executor's final output as:

```text
AgentOutput.text
BranchResult.summary
AgentResult.final_output
```

It then marks the child branch completed.

There is no separate branch-summarization model call in this path.

### native child runtime

The integrated `delegate` capability creates a durable child branch, runs the model/tool loop, completes the branch, and returns a compact `ChildResult` containing the completed output plus stable handles.

The current code calls this subsystem a child-agent runtime in some identifiers. New code should avoid deriving semantic agent identity from those historical names.

### `scriberig-agent-runtime`

The current context compiler already produces a deterministic provider-neutral `CompiledContext` from `BranchExecutionContext` and records canonical context text plus exact dependencies/omitted handles.

The existing system instruction is intentionally small but currently too weak to carry the Scriberig behavior invariants and non-root handoff contract defined by Level 1.

These existing owners remain authoritative. Do not add a second branch store, prompt compiler, child completion mechanism, or model loop.

---

## 3. Ownership Boundaries

Keep the current dependency direction.

### `scriberig-agent-core`

Own provider-neutral reusable descriptors/value types for concepts such as:

```text
AgentProfileDescriptor
AgentProfileRevisionRef
ContextComponentDescriptor
ContextComponentRevisionRef
ContextComponentKind
ContextActivationRule
ResolvedContextComponent
```

Only place types here when they are reusable independently of concrete HTTP/provider execution.

This crate must not own network execution or product UI policy.

### `scriberig-agent-runtime`

Own:

```text
profile resolution for one invocation
context-component activation
ordering/composition into effective context
branch-role behavior selection
request/profile/component fingerprint contribution
provider-neutral execution-time prompt provenance
experiment probe execution support where runtime-specific
```

It must not become the canonical semantic store for profiles/lessons/experiments.

### `scriberig-session`

Continue to own durable session/branch/model/tool/result execution history.

Add session references to exact effective profile/component identities when that provenance belongs to a model invocation, but do not make reusable global profiles children of a session merely for convenience.

### shared semantic/application layer

Canonical reusable profile/component/lesson/experiment state is structured semantic knowledge exposed through shared application operations.

The exact storage adapter may evolve, but the API must preserve stable identities and immutable revisions rather than treating TOML/Markdown prompt files as canonical.

### product surfaces

TUI/web/CLI/server may select, inspect, compare, or request authorized changes to profiles. They do not assemble prompt strings or independently decide component activation.

---

## 4. Terminology and Runtime Identity

Introduce or document these concepts without inventing duplicate global identity systems:

```text
BranchRef
  canonical session-tree context scope

ExecutorAssignment
  resolved owner/model/profile configuration for a branch or invocation

AgentProfileRef
  stable profile identity + exact revision

ContextComponentRef
  stable component identity + exact revision

ModelInvocation
  one request/response step
```

A child branch with the same resolved executor/profile remains the same logical executor operating under another context frame.

A branch with a different explicit assignment is still the same kind of branch; only its `ExecutorAssignment` differs.

Do not add `AgentId` merely to rename `BranchId`.

---

## 5. Branch Role Must Be Explicit in Context Compilation

The context compiler needs enough information to distinguish root user-facing execution from non-root parent-handoff execution.

Prefer an explicit provider-neutral value rather than heuristics based on prompt text.

A minimal shape is conceptually:

```text
BranchRole
  Root
  NonRoot { parent_branch }
```

or an equivalent parent-aware representation already available in session context.

`BranchExecutionContext` or its replacement must expose the branch role to component activation.

Do not infer non-root status from:

- title strings such as `delegated agent branch`;
- operation names;
- provider continuation presence;
- model/profile differences;
- TUI indentation.

---

## 6. Agent Profile Shape

Define a provider-neutral profile descriptor conceptually equivalent to:

```text
AgentProfileDescriptor
  identity
  revision
  name
  description
  components: ordered component refs
  context_policy
  optional execution-policy refs
  status
```

The first implementation may ship a built-in default profile whose identity/revision is deterministic.

That built-in profile is a bootstrap source, not an excuse to make literal source-code strings the permanent canonical architecture.

When durable semantic profile CRUD arrives, the built-in profile may be imported/materialized as normal semantic state while preserving behavior and revision identity.

---

## 7. Context Component Shape

Define components conceptually equivalent to:

```text
ContextComponentDescriptor
  identity
  revision
  kind
  content
  activation
  scope
  priority
  provenance
  status
```

Initial `kind` values should cover:

```text
CoreInvariant
BehaviorPolicy
DomainGuidance
ToolGuidance
SkillTrigger
ExecutionLesson
```

Do not require every kind to be fully persisted/authorable in the first code change. The enum/data model should leave room for the complete architecture without forcing speculative UI.

`content` is provider-neutral instructional content. It is not assumed to be one provider's `system` wire field.

---

## 8. Activation Rules

Activation must be deterministic and testable.

Initial rules may include concepts equivalent to:

```text
Always
RootOnly
NonRootOnly
Domain(domain_id/kind)
Capability(capability_id)
Tool(tool_id)
BranchPolicy(policy_id)
Explicit
```

Do not introduce a general scripting language for activation in the first implementation.

A component activates only from explicit, inspectable invocation state.

Activation evaluation must not read arbitrary wall-clock mutable globals after the effective invocation configuration is snapshotted.

---

## 9. Default Profile Components

The bootstrap/default profile should be composed from at least two separate components.

### Core Scriberig invariant component

Meaning equivalent to:

```text
Operate inside the current Scriberig branch/context frame.
Prefer semantic/domain operations over raw file mutation for understood domains.
Treat files as projections where the domain is understood.
Use the shared candidate/migration/validation/promotion path for canonical change.
Use stable semantic handles and exact revisions/snapshots when exact state matters.
Use child branches for focused isolation when useful; branch creation alone does not imply a new agent.
Parents/dependencies consume compact durable results rather than child transcripts.
Use capabilities progressively.
```

Activation: `Always`.

### Non-root branch handoff component

Meaning equivalent to:

```text
When you are about to finish this non-root branch, make the final response a compact one-paragraph summary for the parent. Include the important outcome, decisions/discoveries, remaining issues, and durable semantic/result handles the parent may need. Do not reproduce the branch transcript or hidden reasoning.
```

Activation: `NonRootOnly`.

Do not put the non-root instruction into root requests.

---

## 10. Context Compilation Order

The compiler should expose stable typed sections even if a provider later flattens them.

Use an ordering equivalent to:

```text
1. activated core invariants
2. activated behavior policies
3. branch role/purpose and branch-specific contract
4. accepted ancestor/dependency BranchResults and decisions
5. exact semantic/project scope
6. current user/delegation instruction
7. bounded branch-local activity/history
8. activated domain/tool/skill guidance where appropriate
9. capability/tool definitions
```

The exact provider message roles may differ. The provider-neutral order and identities must be deterministic.

Avoid duplicated prose when a tool descriptor or deterministic runtime rule already communicates the behavior.

---

## 11. Parent/Child Context Frame Semantics

The runtime should make this invariant testable:

```text
parent effective context = X
enter child B
child effective context = compile(X-compatible selected inheritance + B-local frame)
finish child -> BranchResult BR
resume parent = compile(parent state + selected BR)
```

This does not require byte-identical replay of `X` in the child.

The child compiler selects from canonical state. Unrelated parent turns and sibling histories remain omitted unless explicitly selected by policy.

The parent must not gain child model/tool history simply because the child completed.

If the parent needs more detail, it uses the stable child/result reference to inspect it.

---

## 12. Branch Completion Contract

Keep the current completion flow: final executor output becomes the source of the child `BranchResult.summary`.

Do not add an automatic second summarization invocation.

The runtime/application boundary should validate only mechanical requirements that can be checked without pretending to understand prose, for example:

```text
non-empty final output for successful child branch
result handles remain separately preserved
branch result status matches terminal branch status
```

Do not reject a useful result solely because it is two paragraphs instead of one. The paragraph rule is model behavior guidance, while structured result integrity is runtime policy.

Future optional quality policy may flag poor summaries without corrupting branch completion.

---

## 13. Exact Profile/Component Provenance in Model Invocation

Each model invocation must be attributable to the effective profile revision and activated component revisions.

Extend existing invocation/request provenance rather than adding a separate trace store.

Conceptually retain:

```text
agent_profile: AgentProfileRevisionRef
activated_context_components: [ContextComponentRevisionRef]
context_fingerprint
canonical effective request reference/projection
```

If the complete-request work from task 136 introduces a canonical request record first, attach these fields there and reference them from `ModelInvocation` rather than duplicating payloads.

The request fingerprint must change when output-relevant profile/component revisions or activation differ.

---

## 14. Compatibility with Provider Continuation

Task 136 / Level-2 provider-continuation design remains authoritative for provider state.

Profile/component activation contributes to context lineage.

Consequences:

- changing an active behavior component may stale a provider continuation;
- child continuation remains branch-local even when the same executor/profile enters the child;
- returning from a child uses compatible parent continuation if it still represents parent lineage, otherwise reseeds from canonical parent context;
- no provider conversation rewind is assumed;
- full prompt inspection reports the effective profile/component revisions independently from provider wire optimization.

---

## 15. Learned Execution Lessons

Represent learned guidance as derived semantic knowledge, not as an append-only text memory.

A durable lesson contract should contain or reference:

```text
identity + immutable revision
cue
lesson/guidance
applicability scope
source experiment
supporting evidence refs
confidence
producer provenance
status: candidate/accepted/superseded/rejected or equivalent
```

Lesson activation uses the same deterministic component pipeline after a lesson is accepted for use.

Candidate lessons are not automatically injected merely because one model proposed them.

Exact task/project facts remain bound to their original semantic revisions/snapshots and are not generalized into lessons without explicit evidence/derivation.

---

## 16. Prompt Experiment Model

Add a durable structured representation conceptually equivalent to:

```text
PromptExperiment
  identity
  base_profile_revision
  evaluation_case/task/branch refs
  candidate_profile_revisions
  probe branch refs
  probe BranchResult refs
  validation refs
  behavioral contrast records
  composition decision
  attribution records
  status
```

and:

```text
PromptAttribution
  component/candidate ref
  assessment: Helped | Hurt | NoObservedEffect | Confounded
  evidence refs
  note/summary
```

Do not encode the experiment only as a coordinator transcript.

These entities may initially be internal/application types if the universal semantic schema integration needs a separate migration, but the public contract must be stable enough to move into canonical semantic storage without reparsing prose.

---

## 17. Propose-Probe-Compose Execution

Implement optimization through normal plan/branch machinery when automatic experiments are enabled.

A minimal experiment plan is:

```text
Experiment coordinator
  |
  +-- baseline probe
  |     profile = base revision
  |
  +-- candidate proposal A
  |     -> candidate profile revision A
  |     -> probe A
  |
  +-- candidate proposal B (optional)
  |     -> candidate profile revision B
  |     -> probe B
  |
  +-- compose/evaluate
        depends_on baseline + candidate probes
        consumes compact BranchResults + validations
        emits keep-base or selected candidate + attribution
```

Candidate probes should use equivalent task/base semantic state wherever meaningful.

Do not let the candidate proposer modify the live profile before probing.

The composer receives identities/results/evidence, not full hidden candidate transcripts by default.

---

## 18. Evidence Rules

Automated candidate creation should point to an observed execution moment or explicit evaluation case.

Prefer evidence in roughly this order when applicable:

```text
repeated deterministic validation failure/success
repeated base behavioral failure with candidate correction
clear behavioral divergence tied to the changed component
single-run behavioral improvement
visible plausible risk without observed failure
```

A candidate may choose `KEEP_BASE`/no change.

Do not treat model agreement as independent proof when the models share the same evidence or prompt lineage.

When causality is not isolated, attribution is `Confounded` rather than forced positive/negative credit.

---

## 19. Profile Mutation and Promotion

Profile/context-component changes must use shared semantic change semantics.

The lower-level operation shape should be equivalent to:

```text
inspect current profile revision
create candidate component/profile revision
validate structural invariants
run configured probes/validators
review evidence/policy
promote selected candidate
retain rejected alternatives/history
```

Raw edits to a prompt Markdown/TOML/source file may exist only as bootstrap/interoperability mechanisms until the semantic profile domain is available.

Do not make filesystem text the source of truth for automated optimization.

---

## 20. Public Application Operations

As the semantic profile domain becomes durable, expose shared operations rather than UI-specific mutation.

Likely operations include concepts equivalent to:

```text
agent_profile.inspect
agent_profile.list
agent_profile.resolve
agent_profile.propose_change
agent_profile.validate_candidate
agent_profile.promote
prompt_experiment.inspect
prompt_experiment.start
prompt_experiment.status
execution_lesson.inspect/list
```

Names may follow existing application naming conventions discovered during implementation.

Do not add all operations speculatively if the first Level-3 slice only needs resolution and inspection.

---

## 21. Cross-Surface Behavior

All product surfaces consume the same resolved effective profile/context semantics.

The TUI or web may display something like:

```text
Profile: default@R7
Activated guidance:
  core-invariants@R3
  non-root-handoff@R2
  rust-domain-guidance@R9
```

but that is a presentation over shared provenance.

Changing prompt visibility or expanding component detail must not rerun the model or change activation.

Profile selection changes future execution configuration according to existing branch/session/plan assignment rules; it does not retroactively mutate historical invocations.

---

## 22. Caching and Fingerprints

Existing request/context fingerprint machinery should include behaviorally relevant profile/component inputs.

At minimum, cache identity must distinguish:

```text
same text + different profile revision
same profile + different activated component revision
root vs non-root when activation differs
same branch task + changed accepted ExecutionLesson
changed tool/domain guidance that is provider-visible
```

Do not hash credential values.

Do not use a profile display name alone as cache identity.

---

## 23. Tests

The implementation needs focused tests at the owning layers.

### Context compiler tests

Prove:

- default core invariant component is present;
- non-root handoff component is present for child context;
- non-root handoff component is absent for root context;
- component ordering is deterministic;
- unrelated inactive components are absent;
- component revision change changes context/request identity;
- same exact inputs compile identically;
- child context does not contain unrelated parent/sibling transcript material.

### Child execution tests

Prove:

- child final output becomes `BranchResult.summary`;
- returned `ChildResult.summary` matches durable child result;
- result handles remain preserved independently of prose summary;
- ordinary child completion does not cause an extra summarization provider invocation;
- parent activity contains the child result/handle without copying child model/tool history into parent-local activity.

### Root execution tests

Prove:

- root request does not receive the non-root handoff instruction;
- root output remains unrestricted by child-summary mechanics.

### Experiment tests

When the experiment layer is implemented, prove:

- candidates do not mutate the base profile;
- probes bind exact candidate revisions;
- compose node waits for required durable results;
- validation evidence is retained;
- `KeepBase` is representable;
- attribution supports `Confounded`;
- promotion creates a new revision and preserves old/rejected revisions.

---

## 24. Migration Strategy

Implement in layers.

### Stage 1 — behavior correctness

Add branch-role-aware bootstrap profile components and final-handoff guidance using existing runtime/context structures.

### Stage 2 — explicit versioned resolution

Make `AgentProfile` and `ContextComponent` descriptors/revisions first-class provider-neutral types and record exact resolution in invocation/effective-request provenance.

### Stage 3 — semantic persistence

Move reusable profiles/components into canonical semantic/application storage if they are still bootstrap literals. Provide projection/import/export as needed.

### Stage 4 — evidence model

Add `ExecutionLesson`, `PromptExperiment`, attribution, evidence references, and application inspection operations.

### Stage 5 — automated optimization

Use durable plans/branches to run propose-probe-compose experiments, validators, candidate promotion, and lesson extraction.

Each stage must leave the system architecturally valid if later stages are not yet implemented.

---

## 25. Architectural Prohibitions

Do not:

- equate child branch identity with new agent identity;
- add a second model call solely to summarize every child branch;
- force root user output into a one-paragraph branch-handoff format;
- copy full parent transcripts to children;
- copy full child transcripts to parents;
- implement prompt concatenation independently in TUI/web/server;
- make mutable Markdown/TOML prompt files canonical learned state;
- inject every lesson permanently into always-on prose;
- let an experiment mutate the live base profile before validation/promotion;
- satisfy experiment dependencies through transcript sharing;
- use provider conversation identity as profile/branch identity;
- exclude profile/component revisions from effective prompt observability;
- expose hidden chain-of-thought as optimization evidence;
- bypass semantic candidate/validation/promotion because the mutated object is "only a prompt".

---

## 26. Definition of Done for the Subsystem

The subsystem is conformant when:

1. every invocation resolves an exact profile revision;
2. context components activate deterministically from exact branch/invocation state;
3. root and non-root behavior contracts are distinct where required;
4. non-root final output is instructed to be a compact durable handoff and existing completion stores it as `BranchResult.summary`;
5. no default second summarizer call exists;
6. profile/component provenance is visible in the complete safe effective request and affects request identity;
7. branch creation alone does not imply another executor;
8. parent context after child completion uses selected durable results, not child transcripts;
9. profiles/components can evolve into canonical semantic revisions rather than remaining opaque prompt blobs;
10. prompt experiments and lessons, when enabled, are durable evidence-backed structures using normal branch/plan/change semantics.
