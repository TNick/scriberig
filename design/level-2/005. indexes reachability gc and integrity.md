# Indexes, Reachability, Garbage Collection, and Integrity

## Purpose

This document defines the lower-level maintenance model required by the Level 1 persistence design.

Canonical data must remain authoritative. Indexes and caches accelerate access but must be rebuildable. Immutable history requires explicit reachability and integrity rules.

## Derived indexes

The initial persistence layer should support backend-maintained indexes for operations that are expensive to derive repeatedly.

At minimum, design for indexes such as:

```text
RevisionId -> stored revision location
SnapshotId -> snapshot map root
RootName -> SnapshotId
RevisionId -> references to other stored immutable nodes, when needed for traversal
```

Graph/domain indexes such as reverse semantic relations, symbol references, full-text search, or projection paths belong to higher layers unless a backend-neutral storage primitive is required.

Every derived index must have a rebuild path from authoritative data.

## Reachability

Reachability starts from protected roots.

The storage API must support enumerating or supplying protected snapshot roots and traversing all canonical immutable storage required to read them completely.

A protected snapshot must retain:

- its snapshot-map structure;
- every referenced canonical revision;
- every persistent canonical collection node needed by those revisions;
- required ancestry/history objects when retention policy marks them protected.

Derived caches do not automatically gain canonical retention merely because they reference a protected object.

## Garbage collection phases

The initial GC design should use a conservative mark-and-sweep model:

```text
1. capture protected roots
2. mark reachable canonical storage
3. optionally mark policy-retained historical objects
4. identify unreachable candidates
5. sweep candidates in a transactionally safe way
```

The first implementation should support dry-run reporting before destructive sweep.

GC must never run against a moving root set without either a stable captured view or backend coordination that guarantees safety.

## Integrity verification

Integrity checking should be callable independently of the agent runtime and UI.

Checks include:

- recompute revision identity from stored canonical bytes;
- verify all referenced persistent nodes exist;
- verify snapshot-map root integrity;
- verify named roots resolve to valid snapshots;
- verify protected snapshots are completely readable;
- verify collection structure invariants;
- verify backend index entries reference existing authoritative records;
- report orphan/unreachable immutable records separately from corruption.

An unreachable object is not automatically corrupt.

## Repair policy

Canonical content must not be silently rewritten by an integrity checker.

Safe automatic repairs may include rebuilding derived indexes.

Missing or mismatched canonical content must be reported as corruption and require explicit recovery policy.

## Files prescribed by this design

Within `sr-store`:

```text
crates/sr-store/src/
├── reachability.rs
└── integrity.rs
```

Within `sr-store-sqlite`:

```text
crates/sr-store-sqlite/src/
├── indexes.rs
├── reachability.rs
├── gc.rs
└── integrity.rs
```

The memory backend should implement enough reachability and integrity behavior to participate in shared conformance tests.

## Required tests

- Rebuild a deleted derived index from authoritative data.
- Mark all records reachable from one protected snapshot.
- Confirm an abandoned branch is collectible only when no protected root reaches it.
- Dry-run GC reports candidates without deleting them.
- Sweep never deletes records required by a protected snapshot.
- Corrupt canonical revision bytes are detected by identity verification.
- Missing persistent snapshot-map node is reported as corruption.
- Unreachable but valid immutable content is reported as unreachable, not corrupt.

## Non-goals

The first implementation does not need online incremental GC, compaction across distributed stores, or sophisticated retention-policy configuration.
