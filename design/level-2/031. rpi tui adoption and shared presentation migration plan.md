# RPI TUI Adoption and Shared Presentation Migration Plan

> **Superseded ownership target:** Level-2 plan 032 is the current authority
> for final runtime and terminal ownership. This document and tasks 138–143
> preserve historical research and implementation evidence only. In particular,
> the `scriberig-tui-kit` boundary and Ratatui-based acceptance language below
> do not authorize retaining a ScribeRig-owned commodity widget layer. The
> corrective migration must delegate reusable terminal machinery directly to
> upstream `rpi-tui`, remove local duplicates, and keep only ScribeRig semantic
> projections and adapters. Final acceptance is tracked by tasks 144–149.

## 1. Purpose

This document converts the research and recommendations in `design/level-1/022. Adopt TUI.md` into an implementation-oriented Level-2 plan for the current Scriberig repository.

It is constrained by the existing Scriberig architecture and by work that landed after the research snapshot. In particular, the repository now already has:

- `crates/scriberig-tui`;
- a Ratatui/Crossterm terminal stack;
- an event -> action -> reducer -> effect architecture;
- shared application/protocol/client boundaries;
- recursive session/plan conversation behavior from tasks 134 and 135;
- shared agent-console presentation/configuration models;
- remote-client and web packages.

Therefore this is **not** a greenfield TUI design and it is **not** permission to replace Scriberig with the architecture of another coding agent.

The controlling rule is:

> Adopt `rpi-tui` as reusable terminal presentation infrastructure while preserving Scriberig-owned semantic state, recursive sessions, plans, application operations, protocol, change model, and cross-surface behavior.

The plan must reduce locally maintained commodity terminal/editor/rendering code without changing which layer owns meaning.

This document therefore changes the **terminal implementation strategy**, not the semantic ownership rules in `021` or the product behavior in `022`.

### 2.2 What this document does not change

This plan does not replace:

- Scriberig session/branch identity with an upstream transcript/session type;
- `BranchResult` with an upstream message summary type;

- semantic operations with upstream file/shell tools;
- candidate/migration/validation/promotion with upstream write-file behavior;
- current application/client/protocol contracts with a new UI-only backend;
- current web packages with a second browser application.

## 3. Current Baseline and Research Drift

The Level-1 study was written against an earlier repository snapshot and explicitly reported no current `scriberig-tui` crate. That statement is no longer true and must not guide implementation.

Current `main` has `crates/scriberig-tui` with direct dependencies on Ratatui and Crossterm plus shared Scriberig crates. It already contains action/effect/event/state/keymap/layout/rendering and conversation-oriented code.

Tasks 134 and 135 additionally establish that the default TUI is a recursive conversation/tree projection, not the earlier three-pane semantic browser as the ordinary home surface.

The migration must therefore preserve current behavior first and replace implementation pieces underneath it.

A migration agent must begin each task by verifying current repository owners rather than assuming the filenames in this plan remain exact.

## 4. Adoption Decision

The preferred terminal foundation is `rpi-tui` from `bigfish1913/pi-rust`.

Adopt the following categories from it where the current pinned revision proves suitable:

- terminal lifecycle and normalized terminal input;
- generic component/text primitives;
- editor/composer behavior;
- Markdown rendering;
- selection/search/fuzzy interaction;
- theme/style primitives;
- width/wrapping/Unicode helpers;
- clipboard support behind Scriberig policy;
- streaming-friendly rendering patterns.

Use `tape_tui` only as a design/reference fallback when a specific `rpi-tui` behavior is insufficient. Do not combine two terminal runtimes casually.

The following remain Scriberig implementations:

- recursive session/tree projection;
- reply anchors and continuation semantics;
- durable plans and dependency DAG rendering;
- model invocation and reasoning visibility;
- semantic selection;
- semantic diff/change review;
- candidate validation/promotion;
- capability discovery;
- application commands and operation lifecycle;
- local/remote synchronization;
- provider execution;
- project/domain semantics.

No production dependency on `rpi-agent`, `rpi-harness`, `rpi-tools`, `rpi-extensions`, or another upstream coding-agent runtime is introduced by this plan.

## 5. Upstream Intake and Provenance

Scriberig must pin an exact upstream revision before copying or adapting code.

The default intake layout is:

```text
third_party/
  rpi-tui/
    UPSTREAM.md
    LICENSE
    PATCHES.md
    ... pinned upstream crate source ...

crates/
  scriberig-tui-kit/
    Cargo.toml
    src/
      ... Scriberig-owned adapter/facade ...
```

If repository/Cargo constraints discovered during task 138 require a materially different vendor location, record that decision in the task before implementation and preserve the same provenance boundary.

`UPSTREAM.md` must record at least:

```text
upstream repository
exact commit SHA
intake date
upstream crate/path
upstream license at that revision
source acquisition method
local files intentionally omitted, if any
```

`PATCHES.md` must describe intentional divergence from the pinned source. It is not a substitute for version control history.

Do not strip upstream copyright/license notices. Follow `design/level-2/014. licensing artifacts package metadata and notices.md` for repository notices and package metadata.

The vendored source is an implementation dependency, not architectural authority.

## 6. `scriberig-tui-kit` Boundary

Introduce a narrow terminal-presentation adapter crate named `scriberig-tui-kit` unless the implementation audit finds an already existing crate with exactly this responsibility.

Its purpose is to isolate upstream API churn and present Scriberig-owned generic terminal primitives.

It may own concepts equivalent to:

```text
TerminalSession / TerminalGuard
normalized input events
text lines and styled segments
editor state and editor events
selection/list helpers
Markdown-to-safe-terminal-text rendering
theme/style mapping
clipboard facade and policy
terminal capability flags
```

It must not depend on:

```text
scriberig-session
scriberig-app
scriberig-protocol
scriberig-agent-runtime
scriberig-project
semantic query/change/domain crates
```

The expected dependency direction is:

```text
pinned rpi-tui source
        |
        v
scriberig-tui-kit
        |
        v
scriberig-tui
        |
        v
apps/scriberig
```

Shared Scriberig application/domain contracts remain a separate input to `scriberig-tui`:

```text
scriberig-session / scriberig-app / scriberig-client / scriberig-protocol
                               |
                               v
                        scriberig-tui
```

Neither `scriberig-tui-kit` nor the upstream crate may become an owner of Scriberig semantic state.

## 7. Do Not Create a Parallel `scriberig-ui` Architecture by Default

The Level-1 study sketched a new `scriberig-ui` crate, `ScriberigUiPort`, new presentation snapshots, and HTTP/SSE command/event envelopes. Those sketches express useful separation principles, but the current repository already has shared application, protocol, client, agent-console, and web layers.

The implementation rule is therefore:

> Reuse and extend the current shared owner before introducing a second presentation/application contract.

When both TUI and web need a new terminal-independent model, event, preference, or command:

1. inspect `scriberig-app`, `scriberig-protocol`, `scriberig-client`, `scriberig-session`, and existing reusable web models;
2. extend the existing public contract when responsibility fits there;
3. add protocol serialization only for information that must cross the transport boundary;
4. create a new shared presentation crate only if the audit demonstrates that existing ownership would otherwise create a dependency cycle or inappropriate product coupling.

A Level-3 task must not create a `UiSnapshot`, `UiCommand`, or event stream merely because those names appeared in the research report.

## 8. Preserve the Existing TUI State Machine

The current event -> action -> reducer -> effect model remains the controlling TUI architecture unless a separately approved design replaces it.

Adopting `rpi-tui` does not mean moving semantic effects into widgets.

The logical flow remains:

```text
terminal/upstream input
      -> normalized Scriberig TUI event/action
      -> deterministic reducer
      -> TUI-local next state + typed effects
      -> shared application/client operation
      -> result/event action
      -> reducer
      -> render
```

Commodity upstream components may own their local editor cursor, selection, wrapping, theme, or terminal lifecycle state.

They may not directly:

- start semantic operations;
- mutate sessions/plans;
- call model providers;
- update project snapshots;
- apply migrations;
- bypass capability checks.

Widgets/components emit local actions or Scriberig intents; the existing effect/application boundary performs work.

---

## 9. Crossterm and Runtime Coherence

Terminal state is process-global enough that duplicate incompatible Crossterm lines are a correctness risk.

At intake time, audit the pinned `rpi-tui` dependency graph and Scriberig's current terminal dependencies.

The migration must converge on one compatible Crossterm version for the active TUI path. If the vendored upstream manifest uses an older compatible Crossterm line, adapt the vendored manifest/API calls as an explicit recorded patch rather than shipping two independently active terminal stacks.

Do not run the Ratatui terminal runtime and the `rpi-tui` terminal runtime simultaneously in one process/terminal session.

During migration, a feature-gated or separately selected legacy renderer is acceptable for rollback, but each actual terminal session has exactly one lifecycle owner.

## 10. Default Recursive Conversation Surface

Task 134's product behavior remains authoritative.

The adopted terminal foundation must support the existing default home surface:

- composer focused on launch;
- recursive structural placement of activity;
- stable reply anchors;
- nested branch rails;
- compact completed child results with optional expansion;
- plan/dependency state;
- per-node model/thinking/profile information;
- streaming model-visible output;
- independent prompt/reasoning/tool visibility preferences;
- slash-command access to auxiliary views.

Upstream transcript/message widgets may be reused only as rendering primitives. They must not define the session shape.

The renderer consumes Scriberig's existing recursive projection rows or their current replacement, keyed by stable semantic/session identities.

---

## 11. Auxiliary Semantic Views

The TUI must retain auxiliary inspection and control surfaces after the terminal foundation migration.

At minimum preserve access to behaviors equivalent to:

```text
/session
/explorer
/inspect
/history
/diff
/projection
/changes or review
/operations
/models
/help
```

Exact slash-command names follow current task-134/current-main behavior, not this illustrative list.

These views may use adopted generic selection, Markdown, wrapping, editor, list, and theme primitives, but their data comes from shared Scriberig application/protocol contracts.

Semantic diff generation, validation interpretation, project navigation, branch structure, and capability availability are never delegated to the upstream TUI library.

---

## 12. Terminal Safety Policy

All model, tool, compiler, source, document, and external strings are untrusted terminal input.

The adopted rendering path must:

- prevent untrusted content from becoming executable ANSI/OSC control sequences;
- distinguish trusted style metadata from external text;
- normalize or visibly escape unsafe control characters;
- bound pathological width/wrapping cases;
- restore terminal modes on normal exit, error, cancellation, and panic paths as far as the platform permits.

Clipboard access is explicit user action and must be disableable by policy/configuration.

Image-terminal protocol support is out of scope for the initial adoption and remains disabled unless a later task explicitly enables and threat-models it.

Do not add native upstream plugin loading as part of this migration.

---

## 13. Local and Remote Behavior

The same `scriberig-tui` state machine must continue to support embedded/local application access and the remote client path where currently implemented.

Do not let the upstream terminal library know whether data came from:

- in-process application services;
- `scriberig-client`;
- server events;
- deterministic fixtures.

Reconnect/resume correctness is Scriberig behavior.

Where current protocol already has sequence/cursor/idempotency semantics, reuse them. Where it lacks a behavior required to prevent duplicate side effects or reconstruct presentation state, extend the shared protocol/application design rather than building a TUI-only workaround.

No state-changing command is replayed merely because the terminal reconnected.

---

## 14. Web and Cross-Surface Conformance

The Level-1 report correctly requires TUI and browser to consume the same application semantics.

Current web packages remain the browser implementation. This plan does not create another React app.

The migration must strengthen shared conformance by using common deterministic fixtures for concepts such as:

```text
recursive session/branch ordering
plan node status and dependencies
model invocation lifecycle
reasoning/tool visibility preferences
candidate/change status
validation result status
operation lifecycle
stable semantic labels/handles
```

A terminal-specific renderer may choose different layout and glyphs. It may not invent different semantic state transitions.

When a shared model is missing, add it to the appropriate existing shared owner before teaching each surface to reconstruct it independently.

## 15. Testing Strategy

The adoption is accepted through layers.

### 15.1 Vendor/adapter tests

Prove:

- pinned upstream provenance is recorded;
- the wrapper compiles independently of semantic Scriberig crates;
- editor, text, Markdown, selection, and theme primitives behave deterministically for fixtures;
- unsafe control text is escaped/sanitized;
- no duplicate active Crossterm line exists.

### 15.2 TUI reducer tests

Existing reducer/action/effect tests remain valuable and should require minimal semantic change.

Prove that changing the terminal foundation does not change:

- semantic selection identity;
- navigation anchors;
- reply anchors;
- plan coordinator cursor;
- capability-driven operation dispatch;
- candidate/review actions.

### 15.3 Rendering/golden tests

Use deterministic fixtures for:

- recursive rails;
- narrow widths;
- Unicode and combining characters;
- multiline editor behavior;
- long Markdown;
- malformed Markdown;
- control characters;
- resize sequences;
- streaming updates;
- completed/collapsed branches;
- plan/dependency state.

### 15.4 Cross-surface fixtures

Replay the same durable/shared event or state fixture through TUI and web/client reducers/models where corresponding reducers exist, and compare semantic outcomes rather than pixel/glyph output.

### 15.5 Terminal lifecycle E2E

Exercise normal exit, Ctrl-C/cancellation, panic/error recovery harnesses, resize, and remote disconnect/reconnect without leaving the terminal unusable or replaying canonical mutations.

## 17. Rollback Strategy

The migration must remain reversible until final acceptance.

Keep these boundaries intact:

```text
shared Scriberig application/session/protocol semantics
                  |
                  v
          scriberig-tui state machine
                  |
                  v
        terminal presentation adapter
                  |
                  v
            rpi-tui foundation
```

If the pinned upstream foundation proves unsuitable:

- remove/replace `scriberig-tui-kit` and the vendor tree;
- keep shared session/application/protocol work;
- keep Scriberig TUI actions/reducer/effects;
- retain CLI/server/web behavior;
- use `tape_tui` or another foundation only through the same adapter boundary.

Do not make a semantic schema or protocol depend on an `rpi-tui` type.

---

## 18. Final Acceptance

The migration is complete only when all of the following are true:

1. `rpi-tui` is pinned to an exact reviewed upstream revision with preserved licensing/provenance.
2. Upstream-specific types are contained behind the terminal-kit boundary except for narrowly documented unavoidable cases.
3. The active TUI has one terminal lifecycle owner and one compatible Crossterm dependency line.
4. Current recursive session/plan/reply-anchor behavior remains Scriberig-owned and passes focused tests.
5. Semantic actions still flow through shared application/client capability and change semantics.
6. Untrusted content cannot inject arbitrary terminal control sequences through normal rendering APIs.
7. Clipboard/image/plugin behavior does not silently expand authority.
8. Local and remote TUI modes preserve the same semantic command meaning.
9. Web and TUI derive shared states from common application/protocol semantics rather than duplicated backend logic.
10. Terminal recovery, resize, streaming, Unicode, and reconnect fixtures pass.
11. Temporary migration compatibility code is removed or explicitly documented with an owner and follow-up.
12. The repository-wide final quality gate passes after all Level-3 sheets are complete.
