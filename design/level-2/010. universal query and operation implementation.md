# Universal Query and Operation Implementation

## 1. Purpose

This document translates `design/level-1/010. universal query and operation model.md` into concrete Rust library boundaries and implementation contracts.

The Level 1 design defines one universal interaction grammar:

```text
inspect
list
follow
find
query
diff
history
render
branch
apply
commit
```

This Level 2 design specifies where that grammar lives in the Rust workspace, the files required to implement it, the dependency boundaries between read-side queries and application operations, and the data structures that allow all later surfaces to share the same semantics.

This design intentionally does **not** define HTTP routes, CLI syntax, TypeScript packages, React hooks, TUI bindings, concrete agent tool schemas, authorization policy, or one database backend's indexes. Those are separate surface and persistence concerns.

The central implementation rule is:

> `scriberig-query` owns reusable semantic read/query vocabulary; `scriberig-app` composes that vocabulary with history, projection, migration, validation, and branch services into the universal application-operation boundary.

- the Level 2 universal knowledge-model library design;
- the Level 2 change/history design;
- the Level 2 projection design.

The implementation must reuse the established equivalents of:

```text
EntityId
RevisionId
SnapshotId
TypeId / EntityTypeId
RelationTypeId
CollectionTypeId
MigrationId
ProjectionId
StyleId
```

Do not redefine those identifiers inside the query or application crates.

The implementation must also reuse the established graph, change/history, and projection abstractions rather than introducing alternate persistence, branch, migration, diff, history, or render systems.

If a prerequisite crate has not been implemented yet, create only the files owned by this design that can compile against the agreed public contracts. Do not invent a duplicate substitute crate merely to make this lineage self-contained.

## 4. Dependency Direction

The intended dependency direction is:

```text
scriberig-core
     |
     +--> scriberig-schema
     |
     +--> scriberig-store
              |
              v
        scriberig-graph
              |
              v
        scriberig-query
              |
              +-------------------+
                                  v
scriberig-migration ----------> scriberig-app
scriberig-projection ---------> scriberig-app
other domain/application -----> scriberig-app
```

`s criberig-query` must remain useful without:

- an agent runtime;
- an HTTP server;
- CLI/TUI code;
- React or TypeScript;
- a concrete SQLite connection;
- a specific domain adapter.

`scriberig-app` is allowed to depend on reusable domain-independent subsystems and later selected domain adapters, but no foundation crate may depend on `scriberig-app`.

## 5. Handle Types

`src/handle.rs` defines semantic references used by read operations.

The implementation should provide lightweight wrappers or enums for the Level 1 concepts:

```text
EntityRef
RevisionRef
SnapshotRef
RelationRef
CollectionRef
ProjectionRef
OperationRef
```

Where an existing crate already owns the underlying identifier, the handle should wrap or reuse that type rather than duplicate identity semantics.

A useful exact object target is conceptually:

```text
EntityAtRevision {
    entity: EntityId,
    revision: RevisionId,
}
```

A snapshot-resolved entity target is conceptually:

```text
EntityInSnapshot {
    entity: EntityId,
    snapshot: SnapshotId,
}
```

The public API may choose a smaller unified enum if that produces clearer call sites.

The important invariant is that the caller can distinguish:

- conceptual entity identity;
- exact immutable revision identity;
- snapshot-relative entity resolution.

---

## 6. Selection and Projection Anchors

The query crate should define a transport-neutral semantic selection model.

Conceptually:

```text
Selection {
    snapshot: SnapshotId,
    entity: EntityId,
    revision: Option<RevisionId>,
    relation_path: Vec<RelationStep>,
    projection_anchor: Option<ProjectionAnchor>,
}
```

`ProjectionAnchor` must be extensible enough to represent opaque domain/projection-specific anchors without making line numbers, byte ranges, DOM nodes, or page rectangles canonical identity.

This type exists so later UI, editor, TUI, and agent layers can refer to one semantic selection.

Do not add UI toolkit types to the query crate.

---

## 7. Query Scope

`src/scope.rs` defines explicit search/query scope.

The model must support at least:

```text
Snapshot
EntitySubtree / Entity
ExplicitEntitySet
```

Domain adapters may later expose named semantic scopes such as project, module, document, section, session, or branch as typed wrappers or expansions.

Every `find` and `query` request must carry a resolved `SnapshotId`, either supplied by the caller or resolved by `scriberig-app` before execution.

The query layer must never silently switch snapshots during one operation.

---

## 8. Pagination

`src/pagination.rs` defines bounded traversal without exposing storage-specific cursors.

Provide concepts equivalent to:

```text
PageRequest {
    limit,
    continuation
}

Page<T> {
    items,
    next
}
```

The continuation token should be opaque at this layer.

The public contract must not expose SQL offsets, row IDs, B-tree keys, or backend-specific cursor structure.

The implementation may initially use a simple internal representation, but callers must treat it as opaque.

All potentially large `list`, `follow`, `find`, and `query` results should be representable as pages.

---

## 9. Progressive Detail

`src/detail.rs` defines a small transport-neutral vocabulary for progressive disclosure.

At minimum support concepts equivalent to:

```text
Identity
Compact
Structure
Full
```

Do not hard-code domain-specific levels such as `FunctionGroups` or `PdfLayout` into the universal enum.

Domain-specific views are advertised separately.

The query result may also expose an optional `InformationCost` estimate, for example bytes, approximate tokens, item counts, or another coarse measure. Cost is advisory, not a correctness requirement.

---

## 10. Inspection Model

`src/inspect.rs` defines the universal orientation result.

An inspection result should be capable of carrying:

```text
subject handle
resolved snapshot
resolved revision
entity type
short description
selected important properties
counts
available relations
available collections
available views
available operations
provenance summary
information-cost hints
```

The result must not require every field to be present for every domain.

Unknown or partially adapted resources must still be inspectable with whatever metadata is available.

Inspection is intended to be compact by default.

Do not make `inspect` return an unrestricted full graph dump.

---

## 11. Traversal Model

`src/traverse.rs` defines universal `list` and `follow` requests/results.

`list` is for a declared collection owned by or associated with an entity.

`follow` is for a typed relation.

Both must:

- operate against one exact snapshot;
- return semantic handles;
- preserve relation/collection type information;
- support bounded pagination;
- return compact navigation entries by default;
- distinguish canonical relations from derived relations when that information is available.

A navigation entry should support at least:

```text
handle
type
short label/description
optional count/summary metadata
```

Do not force domain adapters to serialize full entity bodies merely to list children.

---

## 12. Discovery Model

`src/find.rs` defines `find` as a discovery operation.

The request must include:

```text
scope
snapshot
search text or search expression
strategy
limit/page
```

Supported strategies should be extensible rather than a closed promise that every backend implements every strategy.

Initial universal strategy identifiers may include equivalents of:

```text
ExactText
Token
StructuredName
Semantic
DomainSpecific(String)
```

A result hit must resolve to a semantic handle whenever possible and may additionally contain:

```text
score/rank
preview
projection anchor
provenance / derivation metadata
```

The query layer should permit backends/domain indexes to declare unsupported strategies cleanly.

---

## 13. Structured Query AST

`src/query.rs` defines a declarative serializable query AST.

The AST must represent the Level 1 concepts without exposing SQL:

```text
scope
type constraints
property predicates
relation traversal
collection membership
revision/snapshot constraints
ordering
limits
```

A reasonable initial shape is a small expression tree containing operations equivalent to:

```text
All
TypeIs
PropertyEq
PropertyExists
Related
ContainedIn / MemberOf
And
Or
Not
```

plus explicit ordering and page/limit metadata outside the boolean expression.

Do not attempt to design a complete general-purpose query language in the first version.

The query AST should be:

- clonable/debuggable;
- serializable later without semantic redesign;
- independent of one storage backend;
- extensible by versioned domain predicates or query expansion rather than arbitrary SQL fragments.

The initial executor may support only a useful subset as long as unsupported nodes fail structurally and explicitly.

---

## 14. Result Types

`src/result.rs` defines common read-side result metadata.

Every result should be capable of reporting:

```text
resolved snapshot
subject/scope
returned semantic handles
provenance where relevant
continuation where relevant
warnings/diagnostics where relevant
```

Results must be directly composable: handles returned by one operation should be valid inputs to later universal operations without reparsing display labels.

The result vocabulary should remain semantic rather than terminal/UI-specific.

---

## 15. Read-Side Errors

`src/error.rs` defines structured query/read failures.

The initial taxonomy should distinguish at least:

```text
NotFound
WrongType / InvalidTarget
UnsupportedCapability
InvalidScope
InvalidQuery
InvalidContinuation
Ambiguous
SnapshotUnavailable
DerivedDataUnavailable
Internal
```

Every error should preserve operation context and relevant semantic handles where available.

Do not use unstructured strings as the only public failure representation.

Storage/driver errors may be retained as sources internally while being mapped to this semantic boundary.

---

## 16. Query Service Boundary

`scriberig-query` should expose a service trait or small set of traits that application code can implement over the established graph/store/index layers.

The read-side contract should cover equivalents of:

```text
inspect
list
follow
find
query
```

`diff`, `history`, and `render` should **not** be reimplemented in `scriberig-query` if their canonical engines already belong to change/history and projection crates.

The query service should therefore be narrow enough that `scriberig-app` can compose it with those other systems.

---

## 17. Application Request Model

`crates/scriberig-app/src/request.rs` defines the transport-independent application request vocabulary.

Provide one enum or equivalent typed command model covering the universal grammar:

```text
Inspect
List
Follow
Find
Query
Diff
History
Render
Branch
Apply
Commit
```

Each request must contain or resolve enough context to identify:

- target/scope;
- exact snapshot or branch base where required;
- operation-specific options;
- detail/profile request;
- page request where relevant.

Do not add HTTP headers, command-line flags, terminal formatting, React state, or model-provider concepts.

---

## 18. Application Result Model

`src/result.rs` defines one corresponding application result vocabulary.

It should wrap the canonical result types produced by each subsystem rather than flattening them into strings.

Conceptually:

```text
Inspect(...)
List(...)
Follow(...)
Find(...)
Query(...)
Diff(...)
History(...)
Render(...)
Branch(...)
Apply(...)
Commit(...)
OperationStarted(OperationRef)
```

All variants that describe canonical state must report the exact snapshot/revision/branch context used.

Later transports can serialize this model or map it to an equivalent wire model.

---

## 19. Capability Discovery

`src/capability.rs` defines descriptors advertised by `inspect` and other orientation results.

Provide transport-neutral descriptors equivalent to:

```text
RelationCapability
CollectionCapability
ViewCapability
OperationCapability
```

Each descriptor should carry:

- stable capability identifier/name;
- short human-readable label/description;
- applicability/target type information where practical;
- whether the capability is canonical or derived where relevant;
- optional cost/availability metadata;
- enough metadata for later clients to formulate the next request without hard-coding every domain.

Domain adapters may register additional views and high-level operations.

High-level operations must still execute through the application/change boundary rather than bypassing branch/migration history.

---

## 20. Application Service

`src/service.rs` defines the shared application-operation boundary used later by CLI, server, TUI, web integration, agents, and third-party embedded callers.

The service composes existing engines:

```text
inspect/list/follow/find/query -> scriberig-query

diff/history                 -> change/history subsystem

render                       -> scriberig-projection

branch/apply/commit          -> migration/change subsystem
```

The application service must not duplicate the algorithms owned by those subsystems.

It is responsible for cross-cutting behavior such as:

- resolving an omitted current snapshot to one exact snapshot before execution;
- preserving exact operation context;
- normalizing structured application errors;
- advertising applicable capabilities;
- returning typed application results;
- producing operation handles for work that is delegated as long-running.

---

## 21. Branch, Apply, and Commit Integration

The application crate does not own a second branch implementation.

Its `Branch`, `Apply`, and `Commit` request variants must adapt to the canonical change/migration subsystem defined elsewhere.

The application layer must preserve:

```text
base snapshot
candidate snapshot/root
migration proposal
validation/conflict result
commit provenance
```

`Apply` does not advance the canonical named root.

`Commit` is the explicit promotion boundary.

If the change subsystem uses a workspace identifier rather than the word `Branch`, the application layer may adapt terminology without duplicating semantics.

---

## 22. Diff, History, and Render Integration

`Diff` and `History` must delegate to canonical history/change APIs.

`Render` must delegate to projection APIs.

The application result should preserve the domain-specific semantic result when available rather than converting everything to text.

For example, a semantic diff object should remain inspectable/renderable as structured data.

A raw textual diff is an optional rendering, not the core diff contract.

---

## 23. Structured Application Errors

`crates/scriberig-app/src/error.rs` maps lower subsystem failures into a transport-neutral application error taxonomy.

It must preserve at least these categories:

```text
NotFound
InvalidRequest
UnsupportedCapability
Conflict
ValidationFailed
Ambiguous
PermissionDenied        # category only; policy is owned elsewhere
SnapshotUnavailable
OperationFailed
Internal
```

A structured error should carry relevant context such as:

```text
operation kind
snapshot/branch
subject handles
candidate/conflicting handles
diagnostics
possible next capabilities where useful
```

Do not implement authorization policy here merely because the taxonomy includes `PermissionDenied`.

---

## 24. Long-Running Operation Handles

`src/operation.rs` defines the application-level representation of work that may outlive one immediate call.

The minimal lifecycle is:

```text
Queued
Running
Completed
Failed
Cancelled
```

An operation record/handle should support:

```text
OperationRef
kind
base snapshot/branch context
state
progress summary
produced result handles
diagnostics
```

This design defines the semantics, not an async scheduler or background worker implementation.

The application layer may return an immediate result for fast work or an `OperationRef` for delegated work without changing the meaning of the underlying operation.

---

## 25. Domain Extension Registration

The application/query boundary must allow domains to contribute:

- relation descriptors;
- collection descriptors;
- specialized views;
- find strategies;
- query expansions/predicates;
- high-level operations.

Do not implement domain behavior through a central `match` statement that must be edited for every future domain.

Use a registry/provider trait or another extensible mechanism.

Domain extensions may add convenience APIs but must ultimately consume universal handles and produce universal application/change results.

---

## 26. Conformance Tests

`tests/universal_read_model.rs` should verify at least:

1. an entity-only reference is resolved against one exact snapshot;
2. exact revision references remain stable across newer snapshots;
3. `inspect` returns orientation metadata without requiring full content;
4. `list` is bounded and returns a continuation when appropriate;
5. `follow` preserves relation identity;
6. `find` returns semantic handles;
7. `query` can combine type and relation/property predicates;
8. results from one operation can feed another directly;
9. invalid continuation/scope/query errors are structured;
10. unsupported capabilities fail explicitly rather than silently degrading.

`tests/universal_operation_model.rs` should verify at least:

1. all eleven universal operations have application request/result representations;
2. omitted current snapshot is resolved before execution and reported in the result;
3. diff/history/render delegate to their owning subsystem interfaces;
4. branch/apply/commit preserve explicit change semantics;
5. `apply` does not promote a canonical root;
6. `commit` is the only universal operation in this flow that may promote according to policy;
7. inspection advertises available relations/views/operations;
8. structured conflicts survive the application boundary;
9. a long-running operation can be represented by `OperationRef`;
10. no application result requires terminal/UI formatting to be useful.

Use memory/test doubles for graph, history, projection, and change services where possible. Do not make these conformance tests depend on SQLite.

## 28. Completion Criteria

This Level 2 design is implemented when:

- the universal handle, selection, scope, pagination, detail, and read-result vocabulary exists in `scriberig-query`;
- `inspect`, `list`, `follow`, `find`, and structured `query` have reusable Rust contracts;
- the query AST is semantic and storage-independent;
- all canonical reads are bound to a resolved exact snapshot;
- navigation results return reusable semantic handles;
- progressive disclosure and capability discovery are represented in the public model;
- `scriberig-app` exposes all eleven universal operations through one transport-independent application boundary;
- diff/history/render and branch/apply/commit delegate to their canonical subsystems rather than being reimplemented;
- conflicts and errors remain structured and referential;
- long-running work has a universal operation-handle representation;
- conformance tests prove composability and exact-state semantics;
- no agent, CLI, server, TUI, or web-specific dependency is required to use these libraries.
