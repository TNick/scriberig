# Repository Scaffold, Conventions, and Native Command Surface

## 1. Purpose

This document reconciles the implemented repository scaffold with the Level 1 architecture and the earlier Level 2 package designs. It records repository-wide implementation conventions that apply across Rust, TypeScript, tooling, tests, and product composition.

It complements:

1. `design/level-2/011. application operations protocol and runtime boundaries.md`;
2. `design/level-2/017. web workspace packages and integrated editor.md`;
3. `design/level-2/018. workspace and package layout.md`.

The controlling rule is:

> The scaffold defines dependency and ownership boundaries, not proof that runtime behavior exists.

A crate, package, command, view, or application may exist as a documented stub while its semantic implementation remains pending in a focused Level 3 task.

---

## 2. Native Product Identity

The native product composition root remains:

```text
apps/scriberig/
```

Its Cargo package name remains:

```text
scriberig
```

The executable produced by that package is named:

```text
srig
```

Package identity and executable spelling are intentionally distinct. Documentation, examples, shell commands, installers, and help output must use `srig` when referring to the executable.

`apps/scriberig` remains composition-only. Reusable command parsing belongs in `scriberig-cli`; runtime behavior belongs in the server, TUI, agent runtime, application, storage, and domain crates that own it.

---

## 3. Native Command Surface

The stable top-level command names are:

```text
srig tui
srig serve
srig run <PROMPT>
srig agent <PROMPT>
srig maintenance
```

The executable must also provide conventional:

```text
srig --help
srig --version
```

The initial `serve` command accepts endpoint-selection arguments equivalent to:

```text
--host <HOST>
--port <PORT>
```

These commands may initially be stubs. A stub must:

- parse successfully;
- appear in generated help;
- reject malformed arguments through the CLI parser;
- state clearly that its runtime behavior is not implemented;
- avoid direct persistence, server, TUI, or agent behavior in the CLI crate.

Later tasks replace individual stubs by delegating to the owning runtime APIs without changing the top-level command grammar unnecessarily.

## 5. Implemented Web Scaffold

The current web workspace is rooted at `web/` and uses pnpm.

Reusable packages are:

```text
@scriberig/protocol
@scriberig/client
@scriberig/model
@scriberig/editor-core
@scriberig/react
@scriberig/components
@scriberig/components-mui
@scriberig/agent-ui
```

The integrated reference browser application is:

```text
web/apps/scriberig/
```

with private package identity:

```text
@scriberig/app
```

`agent-ui` is a first-class reusable package. It must use the same protocol/model/editor abstractions as the rest of the web platform and must not become a product-only shortcut into agent or server internals.

The integrated application consumes public packages. Reusable packages must never depend on `web/apps/scriberig`.

## 6. Repository Guidance Files

Important architectural directories contain `AGENTS.md` files.

An `AGENTS.md` file explains:

- the purpose of its directory;
- ownership boundaries;
- allowed dependency directions;
- relationships with sibling/lower/higher layers;
- local exceptions or refinements to repository-wide implementation rules.

Agents must read the repository root `AGENTS.md` and the nearest applicable nested `AGENTS.md` before editing a subsystem.

A nested file may refine a repository rule but must not silently reverse architectural invariants defined by Level 1 or Level 2 design.

---

## 7. Source File Size

Source-code files are limited to 400 lines after excluding the leading preamble.

The preamble may contain:

- file/module documentation;
- license headers;
- attributes/directives;
- imports and Rust `use` declarations.

Markdown and other prose/text files are exempt.

When a source file grows beyond the limit, split by responsibility rather than compressing unrelated logic. A preferred strategy is to replace an oversized file by a directory with the same stem and focused child modules while preserving the public re-export boundary.

---

## 8. Documentation and Logical Blocks

Every source file has a file-level description.

Every public or private function and method has documentation containing:

- a one-line brief description;
- optional extended explanation;
- parameter documentation;
- return-value documentation when meaningful;
- thrown/returned error documentation when applicable.

Class-like constructs document their purpose and members. Class documentation separates public and private members where the language supports that distinction.

Each logical code block has a one- or two-line plain intent comment. For a
documented declaration, place the comment after its documentation. In Rust,
put the intent comment immediately after the `///` lines without a blank line,
so Clippy does not report `empty_line_after_doc_comments`. Do not add a special
prefix to explanatory comments.

These rules apply to implementation work, not only public APIs.

---

## 9. Formatting Policy

Formatting policy is intentionally language-specific:

```text
TypeScript / JavaScript: 2 spaces
Rust:                    4 spaces
```

Prettier is authoritative for supported web source files. `rustfmt` is authoritative for Rust formatting.

CI verifies formatting without modifying the tree.

Pre-commit automation may modify staged files when the modification is deterministic and safe.

---

## 10. Repository Lint and Auto-Fix

Repository-specific conventions are enforced by `tools/lint_repo.py` and its `tools/repo_lint/` implementation package.

The linter should prefer deterministic safe fixes when possible. Rules that require semantic judgment may reject a file with a precise diagnostic rather than applying a risky rewrite.

The linter itself follows the same source-size and documentation rules. If it grows, split it into focused modules rather than exempting it merely because it is tooling.

`tools/fix.sh` is the repository-wide safe-fix entry point. `tools/check.sh` is the non-mutating verification entry point.

---

## 11. Pre-Commit Behavior

The repository uses pre-commit hooks to prevent malformed source files from entering Git history.

The intended separation is:

```text
pre-commit: fix safe deterministic issues, then verify
CI:         verify only
```

For staged TypeScript/JavaScript files, the pre-commit formatter runs Prettier with `--write` and re-stages the exact files it formatted. This lets a normal add-and-commit operation succeed with formatter corrections included in the same commit attempt.

Hooks must not silently stage unrelated files.

Developers and agents must not bypass the hook to land known malformed source.

## 12. Tests and Cross-Surface Verification

Repository-level test structure includes dedicated locations for:

```text
tests/conformance/
tests/protocol/
tests/end-to-end/
tests/fixtures/
```

These directories provide shared homes for tests that do not belong exclusively to one crate/package.

The presence of these directories is scaffolding. Concrete conformance behavior is completed only when the corresponding Level 3 test task and its assertions exist.

## 13. Scaffold Task Status Rules

Level 3 task bookkeeping must distinguish these states:

- **Complete**: every completion criterion that remains applicable is implemented and verified.
- **Partial**: structural work exists, but one or more applicable completion checks remain outstanding.
- **Superseded**: a later task/design replaced the instructions before completion; the old task remains for history but is no longer implementation authority.
- **Pending**: implementation has not materially started.

A task must not be marked Complete merely because its directories exist.

When a later design intentionally changes a path, package name, executable name, framework choice, or dependency boundary, reconciliation should mark the older conflicting task Superseded rather than forcing the repository backward to satisfy obsolete instructions.

## 14. Renumbering References

Level 2 and Level 3 filename prefixes are unique identifiers in the current design tree, but earlier documents were authored before the numbering was normalized.

All new or edited design references must use the current filename.

Important current mappings include:

```text

design/level-2/018. workspace and package layout.md
design/level-3/028. initialize rust foundation workspace.md
design/level-3/048. initialize web workspace and headless packages.md
design/level-3/088. scaffold runtime application and product crates.md
```

When touching an older task, repair stale numbered references in that task as part of the change.

---

## 15. Reconciliation Principle

The repository tree, Level 1 invariants, and the newest non-superseded Level 2 design together determine the intended scaffold.

Reconciliation must not mark semantic work complete simply because a placeholder file exists.

Conversely, once a later decision is explicit—such as the `srig` executable name, the `web/apps/scriberig` application path, the reusable `agent-ui` package, or repository-wide quality automation—older scaffold instructions should be updated or marked superseded instead of remaining as contradictory implementation guidance.
