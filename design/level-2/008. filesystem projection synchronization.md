# Filesystem Projection Synchronization

## Purpose

This document specifies the concrete file-synchronization layer required by `design/level-1/006. projections and bidirectional editing.md`.

It applies only to projections whose external representation is a filesystem artifact. It does not define Markdown semantics or source-language AST semantics.

The implementation belongs primarily in `crates/sr-projection-fs` and uses the generic contracts from `sr-projection`.

## Core responsibilities

`sr-projection-fs` must own:

- explicit file-projection ownership;
- path/location mapping;
- deterministic file rendering/write-out;
- file-content hashing;
- persistent/runtime synchronization metadata;
- observation of external file changes;
- dirty-state detection;
- feedback-loop suppression;
- import scheduling boundary;
- failed-import retention/retry state;
- rename/move observation;
- delete/create observation;
- establishing a new synchronization base after successful reconciliation.

It must not own domain parsing or semantic matching.

## Ownership classes

Every observed path must be classified explicitly enough to prevent accidental capture.

Support at least:

```text
ManagedEditable
ManagedReadOnly
Unmanaged
ImportedExternal
```

Meaning:

- `ManagedEditable`: Scriberig renders the file and supported external edits may be reconciled.
- `ManagedReadOnly`: Scriberig renders the file; external changes are not imported as canonical edits.
- `Unmanaged`: Scriberig does not own or rewrite the file.
- `ImportedExternal`: the file is an external artifact used as input/knowledge but is not a Scriberig-owned projection.

A directory scan must never implicitly convert `Unmanaged` files into managed projections.

## External location

The filesystem layer owns a normalized external-location type for file paths.

Semantic entity identity must not derive from a path.

A projection specification may map one semantic scope to one path, and changing that mapping may represent a projection/configuration change rather than a semantic-content change.

Domain rules may declare path placement semantically meaningful, but that fact must come from the domain adapter rather than from the filesystem layer.

## Synchronization state

For each managed filesystem projection, runtime synchronization state must retain enough information for three-way reconciliation.

At minimum it must identify:

```text
projection/spec reference
external path
last synchronization base snapshot
last synchronized semantic scope/revisions
last rendered content hash
last observed content hash when useful
adapter/renderer version used for the base
style revision used for the base
state/status
```

The exact storage representation is deferred, but the API must not require this state to be canonical semantic knowledge.

Suggested synchronization states include:

```text
Synchronized
ExternallyModified
Rendering
ImportPending
ImportFailed
Conflict
Missing
```

## Hashing and dirty detection

The filesystem layer must compute a deterministic hash of exact file bytes or normalized bytes according to an explicit policy.

For the initial implementation, prefer hashing exact bytes written/read.

If the observed hash equals the last rendered synchronized hash, the file is not an independent external semantic edit.

If it differs, the path becomes externally modified and must enter the adapter import/reconciliation lifecycle.

A hash difference alone must not be interpreted as semantic difference.

## Rendering and atomic replacement

Writing a managed projection must avoid exposing partially written output where practical.

The file-writing boundary should support a write-temporary-then-replace strategy or an equivalent atomic mechanism appropriate to the platform.

After a successful write:

1. compute/confirm the exact written hash;
2. update synchronization metadata;
3. mark the projection synchronized;
4. make subsequent watcher notifications attributable to the render rather than to an independent user edit.

Do not update synchronization state before a failed write is known to have succeeded.

## Feedback-loop suppression

Filesystem watchers may report Scriberig's own writes.

The implementation must not re-import those writes.

The initial suppression strategy should use exact rendered hashes as the authoritative check. An operation token or short-lived write registry may be added as an optimization, but correctness must not depend only on timing/debounce.

The system must converge even if watcher events are duplicated, reordered, or coalesced.

## Observation abstraction

Filesystem event delivery must sit behind a small interface so tests can supply deterministic synthetic events.

Model at least:

```text
Created(path)
Modified(path)
Removed(path)
Renamed { from, to }
RescanRequired(scope)
```

Do not expose a specific watcher library's event enum through the public crate API.

Watcher events are hints that cause state inspection. The current filesystem contents and synchronization records determine the actual state.

## External modification lifecycle

For `ManagedEditable`:

```text
observe change
    -> read exact external content
    -> compare to synchronized hash
    -> if different, mark externally modified
    -> call domain adapter parse
    -> call reconcile against synchronization base/current canonical state
    -> validate proposed migration
    -> commit/promote when allowed
    -> render canonical result
    -> write file
    -> establish new synchronization base
```

For `ManagedReadOnly`, an external modification must not silently become canonical state. Policy may restore the generated file or surface drift; exact UX belongs elsewhere.

## Failed imports

If parsing, reconciliation, validation, or commit fails, retain:

- previous valid synchronization base;
- current external path;
- exact observed content hash;
- diagnostics;
- enough access to the external content to retry while it remains available.

Do not advance the synchronization base on failure.

A later file event must be able to retry from the same known base or detect that the external file changed again.

## Three-way state

The synchronization layer must make the three required states available to reconciliation:

```text
B = last synchronized semantic base / projection
D = current canonical state
F = current external file
```

The filesystem layer does not perform domain semantic merge itself. It supplies exact bases and current external bytes to the adapter/reconciliation layer.

## Renames and moves

A rename/move should first be interpreted as an external-location change for the projection.

It must not manufacture new semantic entities merely because the path changed.

If reliable rename information is unavailable from the platform, the system may conservatively observe remove/create and use projection/content matching to recover the move when possible.

## Deletes

Deleting a managed file is not automatically equivalent to deleting its semantic scope.

The projection specification/adapter policy must decide whether external deletion means:

- projection drift requiring regeneration;
- a candidate semantic deletion;
- projection removal/configuration change;
- unresolved user action.

The filesystem layer must surface the deletion without inventing semantic meaning.

## Testing requirements

Tests must cover at least:

- rendered file becomes synchronized;
- watcher notification for the exact rendered bytes is ignored as self-generated;
- external byte change becomes `ExternallyModified`;
- formatting-only semantic no-op can return to synchronized state without a canonical migration;
- failed parse preserves previous base;
- repeated watcher events are idempotent;
- unmanaged files are never rewritten;
- read-only projections do not import external edits;
- rename preserves projection/semantic identity where domain semantics allow it;
- canonical state changing while an external edit exists exposes the correct three-way base/current/external inputs.

Use temporary directories and a fake observation source for deterministic tests. Real watcher-library integration can have a smaller platform integration test set.

## Completion criteria

This design is satisfied when managed files can be rendered, observed, classified as synchronized or externally modified, routed into a domain adapter without direct semantic mutation, recovered after failed imports, and resynchronized without feedback loops.
