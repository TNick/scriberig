# Agent-Native Semantic Self-Hosting

## 1. Purpose

Scriberig must be able to use its own project knowledge, agent runtime, change model, validation system, and product surfaces to evolve Scriberig itself.

Self-hosting is not a special privileged mode. It is the composition of ordinary Scriberig capabilities into a complete loop:

```text
trusted local runtime context
    -> project scan
    -> reviewed persisted manifest
    -> semantic import
    -> active project P@S0
    -> semantic discovery
    -> agent candidate C
    -> isolated validation
    -> explicit acceptance
    -> safe materialization
    -> active project P@S1
```

The reference proof begins in the native TUI with an empty database, asks an agent to onboard the current Scriberig checkout, then asks the agent to add support for ingesting PHP source files.

This document defines the durable invariants behind that proof. Concrete operation shapes belong in Level 2, and focused implementation work belongs in Level 3.

---

## 2. Bootstrap Context Is Not Project Knowledge

An agent may start when there is no active project and no project snapshot in the database.

The local product composition may provide bounded trusted environmental context such as:

- current working directory;
- database/runtime identity;
- authenticated principal;
- provider configuration;
- capabilities authorized for the local process.

That context is enough to bootstrap project onboarding, but it is not itself a semantic project.

A filesystem path must not be treated as an `EntityId`, project root, or current semantic snapshot merely because the TUI was launched from that directory.

The transition from external environment to semantic project state is explicit:

```text
filesystem path
    -> project.scan
    -> persisted manifest
    -> project.import
    -> ProjectId + SnapshotId + semantic root
```

---

## 3. Onboarding Is an Agent-Usable Application Capability

Project onboarding must be available to an authorized agent through the same application boundary used by other clients.

The agent does not implement onboarding by:

- recursively reading one file at a time through model-visible filesystem calls;
- opening SQLite;
- writing project catalog tables;
- inventing source ownership records;
- constructing project snapshots directly.

The project subsystem owns deterministic scan, manifest persistence, adapter classification, import, ownership reconciliation, and atomic project promotion.

The agent's responsibility is orchestration: discover the capability, select the intended project context, review bounded results, invoke import for the exact reviewed manifest, and verify that the resulting semantic workspace is useful.

---

## 4. Progressive Semantic Transition

Before onboarding, filesystem/environment references are unavoidable bootstrap evidence.

After onboarding, project work should preferentially use stable semantic scope:

```text
ProjectId
SnapshotId
root EntityId
selected EntityId when applicable
projection identity when applicable
```

The agent should not continue to treat arbitrary paths and raw grep output as its primary project model once equivalent semantic objects are available.

Filesystem/source paths remain important provenance and projection metadata. They do not replace semantic identity.

This transition is central to Scriberig's purpose: the tool should become more useful to an agent after it has ingested a project than before.

---

## 5. Capability Discovery Remains Progressive

Self-hosting does not justify giving every tool to every model turn.

The bootstrap catalog should contain only the capabilities needed to orient and make progress, with additional capabilities disclosed from trusted registries as scope becomes more specific.

For the reference flow, the agent can progress conceptually from:

```text
capabilities
project.scan
project.import
project.workspace
```

to project-scoped semantic reads such as:

```text
inspect
list
follow
find
query
render
history
```

and only then, for authorized change work, to:

```text
branch.start
change.propose
change.inspect
validate
```

`change.apply` remains governed by the product's acceptance policy and must not be implicitly granted merely because the change was produced by an agent.

---

## 6. Nested Branches Are Context Boundaries

Substantial self-hosting work should be decomposable into nested agent branches.

A child branch receives an explicit subset of parent context, including as appropriate:

- purpose;
- exact project and snapshot;
- semantic selection;
- authorized capabilities;
- expected result shape.

A child must not inherit ambient mutable state accidentally.

When a child completes, its durable `BranchResult` is the normal input returned to the parent. The entire child transcript is not automatically injected into the parent's active model context.

The detailed child conversation remains inspectable through session/history tools when needed.

This property makes branches a real context-scaling mechanism rather than only a visual grouping feature.

---

## 7. Agents Use the Same Change Model as Humans

An agent has no privileged canonical mutation path.

A source change produced by an agent must become the same normal candidate/migration consumed by review, diff, validation, apply, history, and materialization operations for human-produced changes.

The canonical provenance may distinguish:

```text
initiator = agent
session
branch
operation
```

but provenance must not select a weaker mutation path.

In particular, the agent must not:

- write live project files as the canonical edit mechanism;
- create an agent-only patch type that bypasses migration semantics;
- advance a project root directly;
- write semantic records directly to storage;
- silently auto-apply its own candidate unless an explicit future policy authorizes that behavior.

---

## 8. Project-Wide Changes Are Coherent Candidates

Self-hosting commonly requires more than changing one existing source range.

A normal candidate must therefore be able to represent a coherent project-wide source change containing, as needed:

- creation of new source files;
- updates to existing source files;
- deletion of owned source files;
- package/workspace metadata changes;
- lockfile changes;
- tests and fixtures;
- documentation or registry changes.

All file effects belong to one exact-base candidate when they jointly implement one semantic capability.

The candidate must remain inspectable and renderable without making it current project state.

The live project snapshot and live working tree remain at the base until normal acceptance.

---

## 9. Validation Binds to Exact Candidate State

Validation evidence is meaningful only when bound to the exact candidate content it validated.

Self-hosting validation may include:

- semantic/reconciliation checks;
- focused crate/unit tests;
- workspace compile/lint/test profiles;
- end-to-end project ingestion tests;
- product tests in real processes.

Validation that needs filesystem/process execution uses isolated candidate materialization or an equivalent safe workspace. It must not validate by overwriting the user's live project before acceptance.

External dependency acquisition, if required, is an explicit bounded capability. It is not implicit unrestricted network access for the agent.

---

## 10. Acceptance Separates Proposal From Authority

A validated agent candidate is still a proposal.

Before normal acceptance:

```text
project current snapshot == candidate base snapshot
live project files == expected base projections
candidate is durable and inspectable
validation evidence is durable and inspectable
```

Acceptance uses exact-base compare-and-swap semantics and the shared external-effect/materialization design.

The database and filesystem are not falsely described as one atomic transaction. Effect status and recovery remain explicit.

After successful apply/materialization, clients refresh the authoritative project workspace instead of locally inventing the successor snapshot.

---

## 11. Extending Domains Must Extend the Shared Model

A self-hosted request such as "add support for ingesting PHP source files" must extend Scriberig's existing domain architecture, not create a private format-specific storage system.

A new source-code adapter is expected to:

- preserve exact source evidence;
- use versioned adapter/schema metadata;
- normalize parser output into the universal/code domain model;
- preserve deterministic syntax/source mappings appropriate to the language;
- expose named declarations through common semantic discovery when available;
- produce structured adapter diagnostics;
- participate in normal project ownership and re-import reconciliation;
- remain inert with respect to executing imported user code.

Language-specific richness is encouraged. Language-specific isolation from universal operations is not.

---

## 12. Self-Hosting Must Be Proven From a Baseline That Lacks the New Capability

A golden self-extension test is invalid if the requested feature already exists in the starting product and the agent merely reports success.

For the PHP reference scenario, the starting Scriberig checkout used by the product gate must not already have first-class PHP semantic ingestion registered.

The agent-produced candidate must be what introduces the PHP domain adapter and its integration into the tested checkout.

Test-only fixtures may describe the required PHP extension and deterministic provider behavior, but they must not make PHP a production adapter before the scenario begins.

This invariant preserves the meaning of self-hosting.

---

## 13. Durable Session and Provenance Requirements

The complete loop must remain inspectable after model streaming ends and after the product restarts.

Durable state must be sufficient to answer questions such as:

- Which user request started the work?
- Which session and branch performed architecture discovery?
- Which exact project snapshot did the implementation branch use?
- Which tool operations were executed?
- Which candidate did the agent produce?
- Which validations evaluated it?
- Who accepted it?
- Which successor snapshot became current?
- Which external file effects succeeded or require recovery?

The original provider stream is not the canonical historical record.

---

## 14. Cross-Surface Invariant

The reference scenario is intentionally TUI-first, but none of its semantic state is TUI-owned.

Stable project, snapshot, entity, session, branch, operation, candidate, validation, history, and effect references must remain meaningful through the shared embedded application and supported protocol/client surfaces.

The TUI is a client of application semantics, not an alternate implementation of them.

---

## 15. Non-Goals

This principle does not require:

- autonomous unreviewed repository rewrites;
- unrestricted shell or network access for models;
- a full IDE implementation for every source language;
- compiler/type analysis for every newly ingested language;
- replaying full historical transcripts into every continuation;
- making every imported language bidirectionally editable;
- treating every self-hosted task as a special product mode.

The objective is stronger shared semantics and safe composition, not maximal agent privilege.

---

## 16. Completion Standard

Scriberig satisfies this principle when a real product test can begin with an empty project database, use the TUI agent to onboard the current Scriberig checkout, continue from the resulting exact semantic workspace, produce a validated multi-file candidate that adds a previously absent source format, review and accept that candidate through the normal change path, observe the authoritative successor snapshot and safe filesystem effects, restart, and recover the resulting project/session/history state without relying on hidden test mutation paths.
