# Runtime Libraries, Protocol, and Product Surfaces

## 1. Purpose

Scriberig is not one application with several wrappers around it.

It is a reusable knowledge platform with multiple consumers.

The same underlying capabilities must be usable by:

- Rust applications embedding the libraries directly;
- the command-line interface;
- the TUI;
- the HTTP/API server;
- browser and desktop applications;
- third-party clients;
- the agent runtime;
- the full Scriberig editor.

These consumers should not each develop their own version of project inspection, semantic editing, querying, migration handling, validation, or session control.

The central architectural rule is:

> Product surfaces consume shared application operations. Lower-level storage and domain libraries never depend on product surfaces or on the agent runtime.

This document defines the separation between reusable runtime libraries, application operations, protocol types, transport adapters, command-line and interactive products, and the agent runtime.

It also defines how capabilities must evolve across those surfaces so that Scriberig does not become a powerful backend with incomplete or incompatible frontends.

Concrete crate names, Cargo features, endpoint paths, serialization formats, framework choices, process topology, command names, and UI component APIs belong in lower-level designs.

---

## 2. One System, Multiple Consumers

Scriberig has one semantic system and many ways to use it.

Conceptually:

```text
               Knowledge and Domain Libraries
                         |
                         v
                 Application Operations
                         |
                 Stable Protocol Model
             /-----------+------------\
            /            |             \
           v             v              v
        Embedded        Server          Agent
        Clients         Runtime         Runtime
           |             |              |
      +----+----+    +---+---+      +---+---+
      |         |    |       |      |       |
     CLI       TUI  Web     API   Tools   Sessions
                     Apps   Clients
```

The exact deployment may vary.

For example:

- a small utility may link directly to the storage and graph libraries;
- the CLI may call application operations in-process;
- a web application may call the same operations through the server protocol;
- an external IDE may use a generated client library;
- an agent may use a constrained tool adapter over the same operation model.

The capability should remain conceptually the same in every case.

For example, "inspect this entity" should not mean one thing to the CLI, another thing to the server, and a third thing to an agent.

---

## 3. The Lower Layers Must Be Useful Without Agents

The storage and semantic platform must not depend on the existence of an agent runtime.

A user may want Scriberig only as:

- a versioned semantic database;
- an immutable object and snapshot store;
- a structured knowledge graph;
- a query library;
- a Markdown or code model;
- a semantic diff engine;
- a projection and reconciliation engine;
- an API server for another application.

All of those must remain valid uses.

This gives a strict dependency rule:

```text
storage
   ^
knowledge model
   ^
domain adapters
   ^
application operations
   ^
agent integration
```

The arrows represent dependency direction.

The storage layer must not import agent concepts.

A Rust AST adapter must not know how prompts work.

A Markdown reconciler must not know that a chat UI exists.

The agent runtime is a consumer of the platform, not the platform's owner.

---

## 4. Logical Runtime Layers

The architecture is divided into logical layers.

The exact number of crates may change, but the responsibilities must remain separated.

### 4.1 Core identity and value model

The bottom layer defines universal values and identities used throughout Scriberig.

Examples include concepts equivalent to:

- entity identity;
- revision identity;
- snapshot identity;
- relation and collection identity;
- migration identity;
- operation identity;
- style identity;
- type and schema identity.

This layer should have very few dependencies and should be stable.

It must not know about:

- SQLite;
- HTTP;
- Markdown;
- Rust source code;
- sessions;
- agents;
- React;
- command-line parsing.

### 4.2 Persistence implementations

The persistence layer implements storage contracts.

It is responsible for concerns such as:

- immutable revision storage;
- snapshot storage;
- entity-to-revision mappings;
- transactions;
- deduplication;
- retained roots;
- storage-level indexes;
- garbage-collection primitives.

The logical persistence API must not require consumers to know the backend representation.

A first implementation may use SQLite, but SQLite must not become the public semantic API.

Alternative implementations should remain possible.

### 4.3 Universal graph and schema model

This layer exposes domain-independent semantic operations over:

- entities;
- revisions;
- properties;
- typed relations;
- collections;
- provenance;
- descriptions;
- schemas.

It turns raw immutable storage into a knowledge system.

### 4.4 Query and change infrastructure

Shared query and change mechanisms belong above the universal graph.

These include:

- traversal;
- filtering;
- search;
- semantic diff;
- migration construction;
- migration application;
- history inspection;
- common-ancestor lookup;
- merge support.

They remain domain-independent where possible.

### 4.5 Domain adapters

Domain libraries specialize the knowledge store.

Examples include:

- Markdown and structured documents;
- programming-language-independent code concepts;
- Rust;
- PDFs;
- sessions;
- future languages and document formats.

A domain adapter defines its own schemas, parsers, renderers, validators, relations, derived analyses, and specialized operations.

It does not replace the shared persistence, query, history, or operation models.

### 4.6 Projection infrastructure

Projection infrastructure handles the relationship between semantic state and external representations.

It owns common concerns such as:

- projection identity;
- rendering lifecycle;
- style selection;
- external modification detection;
- reconciliation lifecycle;
- projection state;
- dirty-state tracking;
- synchronization events.

Domain adapters supply the domain-specific parse, render, and reconciliation behavior.

### 4.7 Application operations

Above the libraries sits an application-operation layer.

This layer expresses user-visible capabilities rather than low-level storage calls.

Examples include concepts equivalent to:

```text
inspect an entity
list semantic children
follow a relation
run a query
show history
compare two revisions
create a branch
apply a migration
render a projection
reconcile an edited projection
validate a candidate change
open a session
submit an agent command
```

The CLI, server, TUI, web application, and agent adapters should reuse these operations.

This layer is the main boundary between reusable internal libraries and product surfaces.

---

## 5. Application Operations Are the Shared Product Core

The application layer must prevent product-specific business logic from spreading into each frontend.

A bad architecture would look like:

```text
CLI implements semantic diff
server implements another semantic diff
web app implements its own reconciliation logic
agent runtime reaches directly into database tables
```

Scriberig instead requires:

```text
                    semantic_diff operation
                           |
        +------------------+------------------+
        |                  |                  |
        v                  v                  v
       CLI                API               agent
```

The same principle applies to mutations.

A web edit, agent edit, CLI edit, or external-file edit should not have unrelated write paths.

They should converge on the same migration and validation machinery.

Conceptually:

```text
external file edit ---\
web editor ------------\
CLI operation ----------+--> migration --> validation --> snapshot
agent operation --------/
third-party client ----/
```

The source of an operation is recorded as provenance, but the semantic change model remains shared.

---

## 6. The Protocol Is a First-Class Architectural Boundary

The server protocol must not be treated as an accidental serialization of internal Rust structures.

It is a public architectural contract.

The protocol should represent stable concepts such as:

- entity references;
- revision references;
- snapshot references;
- typed object summaries;
- relation and collection summaries;
- descriptions;
- query expressions;
- semantic diffs;
- migrations;
- validation results;
- sessions and branches;
- operations and events;
- projection state.

The protocol should expose semantic concepts rather than backend implementation details.

For example, clients should receive:

```text
EntityReference
RevisionReference
ObjectSummary
```

rather than:

```text
SQLite row id
page number inside a database file
internal table name
```

This allows the persistence implementation to change without redesigning every client.

---

## 7. One Wire Model

Protocol types must have one authoritative definition or one authoritative generation path.

Rust server types and TypeScript client types must not evolve independently by hand.

The architecture should support one of the following patterns:

```text
Rust protocol model
    -> machine-readable schema
    -> generated clients/types
```

or:

```text
language-neutral schema
    -> Rust protocol types
    -> TypeScript protocol types
    -> other clients
```

The exact mechanism belongs in a lower-level design.

The invariant is:

> A protocol concept has one canonical contract, even when represented in multiple programming languages.

This applies especially to:

- IDs and references;
- operation states;
- error forms;
- event types;
- query forms;
- migration forms;
- compatibility metadata.

---

## 8. Embedded Use and Server Use Must Share Semantics

Scriberig should support both embedded and service-oriented use.

An embedded Rust application may call application operations directly:

```text
application.inspect(...)
application.query(...)
application.apply(...)
```

A remote client may perform conceptually the same actions through a transport:

```text
client.inspect(...)
client.query(...)
client.apply(...)
```

The transport may add concerns such as:

- authentication;
- authorization;
- serialization;
- request IDs;
- network retries;
- streaming;
- remote cancellation.

It must not redefine the meaning of the operation.

This makes it possible to test product behavior once at the application layer and then test each transport for faithful exposure.

---

## 9. Product Surfaces

Scriberig has several product surfaces.

They serve different users but should expose the same conceptual platform.

### 9.1 CLI

The CLI is both a product and a diagnostic surface.

It should support low-level and high-level operations.

Low-level examples include:

- inspect an entity;
- inspect a revision;
- inspect a snapshot;
- list relations;
- query the graph;
- inspect migrations.

High-level examples include:

- render a project;
- reconcile projections;
- validate a branch;
- start a session;
- issue an agent command;
- run a one-shot task;
- start the server;
- start the TUI.

The CLI should contain minimal business logic.

Its purpose is to bind command-line input and output to shared application operations.

### 9.2 API server

The server exposes the application layer to remote clients.

Its responsibilities include:

- transport;
- authentication and authorization where configured;
- request lifecycle;
- protocol compatibility;
- event delivery;
- long-running operation management;
- remote cancellation;
- connection and subscription handling.

The server must not become a second implementation of the domain model.

### 9.3 TUI

The TUI is an interactive client of the same operations.

It may combine:

- graph navigation;
- session navigation;
- agent interaction;
- migration review;
- validation output;
- projection inspection.

It should not receive privileged access unavailable to other clients unless a capability explicitly requires local process access.

### 9.4 Web and desktop applications

Browser and desktop applications should use public protocol and client libraries.

They may provide richer interaction and visualization, but must not depend on private server internals.

The full web/editor architecture is defined separately.

### 9.5 Agent runtime

The agent runtime consumes the same platform through a deliberately constrained tool layer.

It may combine several application operations into agent-oriented tools, but it must not bypass the public semantic model.

An agent tool such as:

```text
inspect function
```

should ultimately use the same semantic inspection facilities available to ordinary clients.

An agent tool such as:

```text
edit paragraph
```

should produce the same migration forms used by non-agent clients.

---

## 10. The Agent Runtime Is an Adapter, Not a Privileged Backend

The agent runtime has special requirements:

- progressive disclosure;
- context budgeting;
- session state;
- tool schemas;
- branch management;
- model interaction;
- summarization;
- capability restriction.

Those requirements justify an agent-specific layer.

They do not justify direct access to private storage details.

The correct relationship is:

```text
Agent
  |
  v
Agent Tools
  |
  v
Application Operations
  |
  v
Knowledge Platform
```

Not:

```text
Agent
  |
  v
SQLite tables
```

This boundary matters for:

- safety;
- testing;
- compatibility;
- third-party agent implementations;
- alternative storage backends;
- non-agent use of the same platform.

---

## 11. Agent Tools May Be Coarser Than Application Operations

The agent tool surface should remain simple even if the application layer is rich.

For example, application operations may distinguish several query and inspection forms.

An agent-facing tool may present a higher-level operation such as:

```text
inspect(object, detail_level)
```

and map that internally onto multiple application operations.

Likewise:

```text
edit_function(...)
```

may construct and validate several semantic operations before producing one migration.

The important rule is that the agent adapter composes platform capabilities.

It does not invent a separate persistence model or mutation path.

---

## 12. Universal Operation Identity

Long-running and externally visible work should have stable operation identity.

Examples include:

- an agent command;
- a validation run;
- a large query;
- an import;
- a projection reconciliation;
- a render;
- a compiler analysis;
- a migration application;
- a test run.

Conceptually:

```text
Operation
  id
  kind
  requested_by
  input_snapshot
  status
  progress
  result
  diagnostics
```

Possible lifecycle states include concepts equivalent to:

```text
queued
running
completed
failed
cancelled
```

The exact states belong in lower-level protocol design.

The important architectural property is that every surface can observe the same operation.

For example:

- the CLI can print progress;
- the TUI can display it;
- a web application can subscribe to it;
- an API client can poll or stream it;
- an agent session can reference its result.

---

## 13. Events Are Part of the Shared Runtime Model

Snapshot-based state benefits from an explicit event stream.

Useful event categories include:

```text
snapshot changed
entity changed
projection changed
branch changed
migration created
operation started
operation progressed
operation completed
validation completed
agent output produced
```

Events inform clients that something happened.

They are not themselves the authoritative semantic state.

A client receiving:

```text
EntityChanged(E)
```

should be able to resolve the new state through the normal application or protocol model.

This avoids turning event payloads into a second database representation.

---

## 14. Commands and Queries Must Be Distinguishable

The runtime should distinguish operations that inspect state from operations that may create new canonical state.

Conceptually:

```text
Queries
  inspect
  list
  follow
  find
  diff
  history

Commands
  branch
  apply migration
  reconcile
  commit
  merge
  update projection configuration
```

Some expensive queries may create derived cache entries, but they must not advance canonical snapshots merely because they ran.

This distinction makes it easier to reason about:

- permissions;
- retries;
- idempotency;
- audit history;
- agent capabilities;
- UI behavior.

---

## 15. Product Surfaces Must Not Own Canonical State

A UI, CLI process, agent runtime, or server connection may maintain local view state.

Examples include:

- current selection;
- expanded tree nodes;
- scroll position;
- command history;
- temporary form state;
- unsent text;
- cached remote responses.

Those are product concerns.

Canonical project and session knowledge remains in the shared semantic system.

A frontend must not silently become authoritative for data that the rest of the system cannot see.

When product state becomes durable project knowledge, it must be committed through the normal semantic change model.

---

## 16. One Capability, Multiple Presentations

The same capability may look different in different surfaces.

For example, inspecting an entity may appear as:

```text
CLI
  scriberig inspect <id>

TUI
  selected object panel

Web
  object inspector

Agent
  inspect tool result

API client
  inspect(entity)
```

These are different presentations of one capability.

Likewise, semantic diff may appear as:

- machine-readable protocol data;
- a colored terminal diff;
- a structured web visualization;
- a compact agent summary.

The presentation may differ greatly.

The underlying semantic result must remain consistent.

---

## 17. Vertical Capability Development

Scriberig must avoid developing one subsystem far ahead of all product surfaces.

A common failure mode would be:

```text
core libraries: 80 capabilities
CLI:            55 capabilities
server API:     30 capabilities
web client:     12 capabilities
agent tools:     8 capabilities
```

That produces several incompatible products sharing only a repository.

Instead, user-level features should normally be developed vertically.

A capability is not considered broadly available until the relevant surfaces expose it.

For example, a new "semantic diff" capability may require:

```text
knowledge/application operation
protocol representation
server transport
client-library method
CLI command or view
web/TUI presentation where relevant
agent tool exposure where useful
conformance tests
```

Not every internal primitive needs a button in every UI.

The rule applies to meaningful user-facing capabilities.

---

## 18. Capability Matrices

The project should maintain an explicit capability matrix.

Conceptually:

```text
Capability            Library  App  Protocol  CLI  Server  Web  TUI  Agent
inspect entity           yes    yes    yes     yes    yes   yes  yes   yes
semantic diff            yes    yes    yes     yes    yes   yes  yes   yes
raw storage GC           yes    yes    maybe   yes    local maybe no    no
agent command            n/a    yes    yes     yes    yes   yes  yes   yes
```

The exact matrix belongs in project planning rather than this design.

The architectural rule is that gaps are visible and intentional.

A feature should not accidentally exist only because one frontend reached into an internal library.

---

## 19. Third-Party Applications Are First-Class Consumers

The protocol and reusable libraries must be designed for consumers other than the reference Scriberig applications.

A third party may want to build:

- a custom IDE;
- a CAD or GIS application using the knowledge store;
- a documentation editor;
- a code-analysis service;
- a CI integration;
- an alternate agent runtime;
- a specialized browser for one domain;
- a proprietary application embedding only the storage layer.

This implies:

- stable public boundaries;
- transport-independent semantic models;
- documented compatibility expectations;
- client libraries that do not require the full editor;
- no dependency from foundational crates to agent-specific code;
- no requirement to adopt the reference UI style.

The reference products should prove these public boundaries rather than bypass them.

---

## 20. Client Libraries

Remote use should be supported through reusable clients rather than requiring every application to manually construct transport requests.

A client library should expose semantic operations in the host language.

Conceptually:

```text
client.inspect(entity)
client.query(query)
client.diff(a, b)
client.apply(migration)
client.subscribe(...)
```

The client may provide:

- request construction;
- protocol version negotiation;
- typed decoding;
- operation tracking;
- event subscriptions;
- retry helpers where safe;
- cancellation;
- common error handling.

It must not implement a separate semantic model.

The server remains one transport realization of the application operations.

---

## 21. The Reference Products Must Use Public Boundaries

The full Scriberig products should behave like demanding external consumers.

The reference web editor should use the public client and UI libraries.

The CLI should use the shared application layer rather than private shortcuts.

The TUI should use the same semantic operations.

The agent runtime should use the same public platform interfaces expected of alternate agents.

This gives a strong architectural test:

> If the reference product needs a private path to implement an important capability, the reusable boundary is probably incomplete.

There may be carefully justified local-only capabilities, but they must be explicit exceptions.

---

## 22. Local Runtime and Server Runtime

Scriberig should support several deployment shapes without changing its semantic architecture.

Examples include:

### 22.1 In-process use

```text
application
  -> libraries
  -> local store
```

Suitable for:

- tests;
- command-line tools;
- embedded applications;
- single-process utilities.

### 22.2 Local server use

```text
CLI / TUI / browser
        |
        v
local Scriberig server
        |
        v
local store
```

Suitable for a desktop development environment.

### 22.3 Remote service use

```text
client applications
        |
        v
remote Scriberig service
        |
        v
managed store
```

Suitable for shared or hosted environments.

The protocol and application semantics should remain recognizably the same across all three.

---

## 23. One Executable May Host Several Surfaces

A convenient distribution may expose several modes from one executable.

Examples include concepts such as:

```text
serve
TUI
one-shot command
agent command
maintenance operation
```

This is a packaging choice, not an architectural requirement.

The important property is that these modes are thin hosts over reusable libraries.

A future deployment may split them into separate processes without redesigning the knowledge model.

---

## 24. Error Semantics Must Be Shared

Errors are part of the protocol contract.

The system should distinguish meaningful categories such as:

- entity not found;
- revision not found;
- snapshot not found;
- schema violation;
- stale base snapshot;
- semantic conflict;
- validation failure;
- permission denied;
- unsupported domain operation;
- projection out of sync;
- operation cancelled;
- transport failure.

A frontend may render these differently.

It must not infer semantic error meaning by parsing arbitrary text messages.

Machine-readable error categories should survive across embedded APIs, the server protocol, clients, and agent tool results.

---

## 25. Snapshot Awareness Is a Cross-Surface Concern

Clients must know which semantic state they are viewing or modifying.

Important results should therefore carry enough snapshot or revision context to prevent accidental ambiguity.

For example, a client may inspect an entity under:

```text
Snapshot S10
```

while the current project later advances to:

```text
Snapshot S11
```

The client should be able to distinguish:

```text
show me exactly what I previously viewed
```

from:

```text
show me the current revision of this entity
```

Mutation operations should make their base state explicit when conflicts matter.

This is necessary for:

- agents;
- multiple web clients;
- concurrent CLI operations;
- long-running editor sessions;
- remote API clients.

---

## 26. Offline and Cached Clients Must Not Invent Canonical Truth

Client libraries and applications may cache data aggressively.

A cached object should remain associated with the revision or snapshot from which it came.

If connectivity is lost, a client may continue to display known historical data.

It must not silently present stale data as current.

If offline editing is eventually supported, the result should be represented as a branch or migration against an explicit base snapshot and reconciled on reconnect.

This follows the same branch and merge model used elsewhere in Scriberig.

---

## 27. Transport Concerns Must Stay Above Semantic Concerns

HTTP, WebSocket, local IPC, or another transport may be used.

Those choices should remain replaceable.

Transport-specific concepts include:

- URLs;
- headers;
- connection lifecycle;
- serialization framing;
- streaming channels;
- request deadlines.

Semantic concepts include:

- entities;
- revisions;
- snapshots;
- migrations;
- branches;
- queries;
- operations.

The protocol model may be serialized through a transport, but semantic behavior must not depend unnecessarily on one transport technology.

---

## 28. Streaming Is a Delivery Mechanism, Not a Separate Semantic API

Some operations produce incremental output.

Examples include:

- agent responses;
- large queries;
- validation logs;
- test runs;
- import progress;
- long reconciliations.

Streaming may improve responsiveness.

It must not create an alternative final-result model.

Conceptually:

```text
Operation O
  -> progress events
  -> partial output events
  -> final OperationResult
```

The final operation result remains addressable independently of whether a client observed the stream live.

This is important for sessions and auditability.

---

## 29. Protocol Versioning

The protocol will evolve.

Compatibility must therefore be explicit.

The architecture should support:

- protocol version identification;
- additive evolution where practical;
- capability discovery or negotiation where useful;
- explicit handling of unsupported operations;
- migration strategy for breaking changes.

Internal Rust APIs may evolve faster than the remote protocol.

The public protocol should be treated as a compatibility boundary with a larger cost of change.

The exact versioning policy belongs in lower-level design.

---

## 30. Domain Extensibility Must Reach Product Surfaces

Adding a new domain should not require rewriting every product.

A domain adapter should be able to contribute semantic capabilities such as:

- type descriptions;
- child relations;
- renderers;
- specialized commands;
- validators;
- query fields;
- summaries;
- diff interpretation.

Generic products should still be able to browse unknown domains at a lower level using universal operations.

For example, even if the web editor has no specialized visualization for a new domain, it should still be able to:

```text
inspect entity
list relations
list collections
show description
show history
show revisions
```

Specialized UI can then improve the experience without making the domain inaccessible beforehand.

---

## 31. Raw and High-Level Operations Must Coexist

Advanced users need access to the underlying knowledge model.

Other users need task-oriented operations.

Both should be supported.

Examples of low-level operations:

```text
inspect revision
list outgoing relations
list incoming relations
inspect snapshot mapping
show migration operations
```

Examples of high-level operations:

```text
rename symbol
move section
reconcile Markdown file
resume session branch
ask agent to refactor function
```

High-level operations should reduce to shared semantic mechanisms rather than mutate hidden state.

This duality is important for:

- debugging;
- extensibility;
- power users;
- automated agents;
- building the integrated editor.

---

## 32. Conformance Tests Across Surfaces

A shared architecture requires shared tests.

Important capabilities should have conformance tests that verify equivalent behavior across relevant surfaces.

For example, given a fixed snapshot:

```text
application.inspect(E)
server/client inspect(E)
CLI inspect E
agent inspect(E)
```

should describe the same semantic object even if formatting differs.

Mutation tests should verify that equivalent edits create equivalent semantic results.

Event tests should verify that clients observe operations consistently.

Protocol tests should verify that client and server types remain compatible.

The goal is not byte-for-byte identical presentation.

The goal is semantic equivalence.

---

## 33. Vertical Acceptance Tests

Each important feature should eventually have an end-to-end test path.

For example, a semantic diff feature may be considered complete when a test can:

```text
create two snapshots
compute semantic diff through application layer
retrieve it through server protocol
decode it with client library
render it in CLI or reference UI
make it available to an agent where appropriate
```

This catches architectural drift earlier than isolated unit tests.

It also ensures the reference products exercise public interfaces.

---

## 34. Observability Belongs to the Runtime, Not the Domain Model

The runtime should expose operational information needed to diagnose the system.

Examples include:

- operation duration;
- cache hits and misses;
- query cost;
- validation duration;
- projection synchronization state;
- server request tracing;
- agent-tool timing;
- event backlog.

These are operational concerns.

They should not become canonical domain knowledge unless explicitly imported for a reason.

This preserves the distinction between:

```text
what the project means
```

and:

```text
how the runtime behaved while serving it
```

---

## 35. Security and Capabilities Must Be Enforceable Below the UI

A product surface may hide unavailable actions, but security must not rely on hiding buttons or tool descriptions.

The server and application layers must be able to enforce capabilities such as:

- read a scope;
- query a scope;
- create a branch;
- propose changes;
- commit changes;
- run validation;
- execute an agent;
- access external resources.

The detailed trust and capability model is defined separately.

This document establishes the runtime boundary:

> Authorization decisions must be enforced at shared operation boundaries, not only in individual frontends.

---

## 36. Dependency Direction

The architecture must keep dependencies flowing upward.

Conceptually:

```text
                Core Values
                    |
                    v
                 Storage
                    |
                    v
             Graph and Schema
                    |
            +-------+-------+
            |               |
            v               v
          Query         Migration
            \               /
             \             /
              v           v
              Domain Adapters
                    |
                    v
               Projections
                    |
                    v
           Application Operations
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
      Server       CLI/TUI     Agent
        |
        v
     Clients
        |
        v
    Web/Desktop
```

This diagram is conceptual rather than a required crate graph.

The important rules are:

- lower layers do not depend on product layers;
- domain adapters do not depend on agents;
- application operations depend on reusable semantic libraries;
- transports depend on application operations;
- clients depend on protocol contracts;
- reference products depend on public interfaces wherever practical.

---

## 37. Dependency Cycles Are Architectural Smells

Some features will create pressure for upward layers to leak downward.

Examples include:

- storage wanting to know about sessions;
- a parser wanting to call the agent runtime directly;
- a domain library wanting to emit web-specific models;
- the server wanting to own semantic business logic;
- the web app wanting a private mutation endpoint.

These pressures should normally be resolved with:

- traits or interfaces;
- callbacks;
- domain events;
- application orchestration;
- derived-data providers;
- explicit adapters.

A dependency cycle should be treated as evidence that responsibilities are mixed.

---

## 38. Library Boundaries Must Reflect Independent Use

A practical test for a library boundary is:

> Can a user reasonably want this capability without the layers above it?

Examples:

A user may want storage without agents.

A user may want the graph and query engine without Markdown.

A user may want Markdown projection without source-code support.

A user may want source-code analysis without the agent runtime.

A user may want the server without the reference web application.

A user may want the protocol client without any Scriberig UI components.

These are strong candidates for reusable package boundaries.

Exact crate and package splits should be decided in Level 2 designs based on compile-time coupling, API stability, and implementation cost.

---

## 39. Avoid a Monolithic Feature-Flagged Core

It may be tempting to place everything in one large crate with feature flags such as:

```text
markdown
rust
pdf
server
agent
web
```

This would make dependency direction harder to enforce and independent use harder to understand.

Some feature flags are reasonable for optional backend integrations.

They should not replace meaningful architectural boundaries.

The lower-level design should prefer explicit libraries when capabilities have independent users or stability needs.

---

## 40. Product Bundles May Be Opinionated

Reusable libraries should remain composable.

Products may be opinionated.

For example, the full Scriberig application may choose:

- one default database backend;
- one server transport;
- one web framework;
- one component library;
- one default agent runtime;
- one default rendering style.

Those choices simplify the product.

They must not unnecessarily constrain the underlying libraries.

This distinction allows Scriberig to provide a coherent default experience while remaining a reusable platform.

---

## 41. The Server Is Not the Architecture

The server is an important product surface, but it must not become the place where all architectural concepts live.

The server should primarily:

```text
receive request
  -> authorize
  -> invoke application operation
  -> expose progress/events
  -> serialize result
```

If an operation is only possible through the server because its logic exists in a handler, embedded applications and tests become second-class.

Business behavior should remain callable independently of network transport.

---

## 42. The CLI Is Not the Architecture

The CLI is valuable because it makes nearly every capability scriptable and inspectable.

It must not define the semantic model through command syntax.

Commands are mappings onto application operations.

This allows command names and flags to evolve without redefining the knowledge system.

It also makes it possible for automation to use a structured client API instead of scraping terminal output.

---

## 43. The Agent Is Not the Architecture

The full Scriberig vision includes agents deeply, but agent convenience must not distort the lower layers into a private agent backend.

The system should remain understandable as:

```text
knowledge platform
+
product surfaces
+
agent consumer
```

rather than:

```text
agent harness
with some database helpers
```

This distinction preserves the possibility that the storage, graph, projection, query, and UI libraries become useful infrastructure beyond the reference agent product.

---

## 44. Product-Specific State May Still Use the Universal Store

A product may choose to persist some of its own durable state inside Scriberig.

Examples include:

- saved workspace layouts;
- named views;
- user-created bookmarks;
- persistent selections;
- saved queries.

If stored in the universal knowledge model, these should be represented as explicit domain entities rather than hidden implementation tables masquerading as project knowledge.

Whether a given piece of UI state belongs in the universal store is a domain decision.

Ephemeral interaction state should normally remain outside canonical snapshots.

---

## 45. Capability Discovery

Clients and agents should be able to discover what can be done with an object or runtime.

This may include:

- supported relation types;
- available renderers;
- available domain operations;
- available validators;
- protocol capabilities;
- runtime features;
- permission-constrained operations.

Capability discovery helps generic clients support future domains without hard-coding every possibility.

It also allows a simpler agent to navigate the system using one interaction grammar.

The exact discovery representation belongs in lower-level protocol design.

---

## 46. Example: Inspecting a Function

The following surfaces may all inspect the same function.

### Embedded library consumer

```text
application.inspect(Function F, Snapshot S)
```

### CLI

```text
inspect F
```

### Server client

```text
client.inspect(F, S)
```

### Web editor

The user selects `F` and opens the object inspector.

### Agent

The model requests an inspect tool for `F`.

All should resolve to the same semantic revision under the same snapshot.

Presentation can differ.

The function summary exposed to the agent may be more compact than the full web inspector.

That is projection and presentation, not a different semantic truth.

---

## 47. Example: Editing a Paragraph

Assume paragraph `P` exists under snapshot `S1`.

A user edits it through the web application.

Conceptually:

```text
Web Editor
    |
    v
Client Library
    |
    v
Protocol
    |
    v
Application Operation
    |
    v
Migration M
    |
    v
Validation
    |
    v
Snapshot S2
```

An agent editing the same paragraph should enter at a different surface:

```text
Agent
  |
  v
Agent Tool
  |
  v
Application Operation
  |
  v
Migration
```

The lower half of the flow is shared.

That is a core architectural invariant.

## 48. Example: Browsing Raw Knowledge

A third-party database browser may not know anything about Rust functions or Markdown sections.

It can still use universal operations:

```text
inspect entity
show revision
list properties
list relations
list collections
show provenance
show history
```

A specialized code client can recognize the same entity as a `Function` and add:

```text
show parameters
show code groups
find callers
render source
```

This demonstrates the relationship between the universal platform and domain specialization.

---

## 49. Example: Starting an Agent Command

An agent command should itself be represented as an operation with explicit context.

Conceptually:

```text
request:
  session: Session S
  snapshot: Project Snapshot P
  scope: Function F
  instruction: "Refactor validation"
```

The agent runtime may then create:

- a session branch;
- one or more tool invocations;
- a candidate project branch;
- validation operations;
- a resulting migration.

The CLI, web editor, TUI, or external API client can all start the same class of operation.

The agent runtime remains independent of which product initiated it.

---

## 50. Public and Internal APIs

Not every internal helper must become a compatibility-guaranteed public API.

The project should distinguish:

```text
internal implementation interfaces
reusable library interfaces
application-operation interfaces
public remote protocol
```

These layers have different stability requirements.

Internal helpers may change freely.

Reusable library interfaces should evolve carefully.

The public remote protocol should have the strongest compatibility discipline.

This allows implementation progress without freezing every Rust type prematurely.

---

## 51. Level Boundaries

This document defines architecture, not package manifests.

Lower-level designs must decide details such as:

- exact Rust crate names;
- crate dependency graph;
- trait definitions;
- sync versus async boundaries;
- SQLite adapter design;
- API framework;
- HTTP endpoint structure;
- streaming transport;
- serialization format;
- generated-client tooling;
- CLI command hierarchy;
- TUI framework;
- process lifecycle;
- exact operation and event enums;
- protocol version negotiation;
- feature flags.

Those decisions must preserve the invariants defined here.

---

## 52. Required Invariants

Lower-level designs and implementations must preserve the following rules.

1. Foundational storage and graph libraries are useful without an agent runtime.
2. Lower layers do not depend on product surfaces.
3. Domain adapters do not depend on the agent runtime.
4. The agent runtime consumes public semantic operations rather than private storage details.
5. CLI, TUI, server, web clients, and agents share application-level semantics.
6. User-visible mutations converge on the shared migration and validation model.
7. The server protocol represents semantic concepts rather than backend tables.
8. Protocol types have one authoritative contract or generation path.
9. Embedded and remote use expose equivalent semantic behavior where applicable.
10. Long-running work has stable operation identity.
11. Events report changes but do not replace authoritative state.
12. Canonical state remains snapshot-aware across all surfaces.
13. Client caches retain revision and snapshot identity.
14. The reference products use public or reusable boundaries wherever practical.
15. Third-party applications are first-class consumers.
16. Domain extensions remain generically browsable before specialized UI exists.
17. User-level capabilities evolve vertically across relevant product surfaces.
18. Conformance tests verify semantic equivalence across surfaces.
19. Transport concerns remain separate from domain semantics.
20. Product-specific convenience must not collapse the reusable platform into one monolithic application.

---

## 53. Architectural Summary

Scriberig should be built as a stack of reusable semantic capabilities with several product surfaces above them.

The foundation is not the server, the CLI, the web editor, or the agent runtime.

The foundation is the knowledge platform.

Application operations turn that platform into reusable user-facing capabilities.

The protocol makes those capabilities available across process and language boundaries.

The CLI, TUI, API server, web applications, external clients, and agent runtime are different consumers and presentations of the same system.

The full architecture can therefore be summarized as:

```text
Reusable Knowledge Libraries
          |
          v
Application Operations
          |
          v
Protocol and Events
          |
    +-----+------+-----------+-----------+
    |            |           |           |
    v            v           v           v
   CLI          TUI        Server       Agent
                            |
                            v
                         Clients
                            |
                            v
                      Web/Desktop Apps
```

The main product-development rule follows directly:

> Build capabilities once in the shared semantic and application layers, then expose them coherently across the relevant product surfaces.

This keeps Scriberig usable as infrastructure, prevents the agent runtime from owning the architecture, and allows CLI, API, TUI, web, and third-party applications to evolve together instead of becoming incompatible implementations of the same ideas.
