# Agent Interaction and Sessions

## 1. Purpose

Scriberig treats agents as clients of the same universal knowledge system used by humans, applications, domain adapters, and external tools.

An agent session is therefore not fundamentally a transcript stored beside the project. It is another structured knowledge graph in the same database.

A session may contain goals, questions, observations, decisions, tool invocations, tool results, branches, summaries, proposed migrations, validation results, artifact references, and user or agent messages. Those objects use the same identity, revision, snapshot, provenance, history, query, and relation concepts as the rest of Scriberig.

The central rule is:

> An agent does not receive a privileged view of the project. It navigates and changes the same typed knowledge system as every other consumer, while its own session is stored in that same system and exposed through the same progressive interaction model.

This document defines the architectural model for sessions and agent interaction.

It covers:

- sessions as structured knowledge rather than flat transcripts;
- session branches and nested investigations;
- short branch descriptions and progressive disclosure;
- agent context as a projection of session and project knowledge;
- universal object handles and semantic navigation;
- tool invocations and results as first-class knowledge;
- capability-scoped access rather than unrestricted file access;
- speculative agent work and promotion through migrations;
- durable decisions and project knowledge derived from sessions;
- multi-agent and concurrent work;
- provenance, auditability, summaries, and retention.

It intentionally does not define model-provider APIs, prompt templates, Rust traits, wire formats, HTTP endpoints, concrete tool schemas, or UI components. Those belong in lower-level designs and in the universal query and operation design.

---

## 2. Design Goals

Agent interaction and session storage must satisfy the following goals.

### 2.1 Use one knowledge substrate

Sessions must not require a second persistence architecture.

The same underlying system should represent:

- a Rust function;
- a Markdown paragraph;
- a PDF page;
- a project decision;
- an agent branch;
- a tool result;
- a migration proposal;
- a session summary.

The domain vocabulary differs, but the underlying concepts remain:

```text
entity
revision
snapshot
relation
collection
migration
provenance
description
derived knowledge
```

This allows an agent to follow relations naturally across domains.

A branch may refer directly to the function it is changing, the document section that motivated the change, the migration it produced, the validation result that accepted it, and the decision that was promoted from the discussion.

### 2.2 Make sessions structured rather than transcript-shaped

Chronological messages are useful for humans, but they are not sufficient as the canonical session model.

A transcript hides important distinctions inside text:

- what the current goal is;
- which question is unresolved;
- what decision was accepted;
- which tool call produced an observation;
- what branch performed an edit;
- which project objects were examined;
- what migration was produced;
- what result was validated;
- what prior conclusion was superseded.

Scriberig should preserve those concepts explicitly when they are known.

### 2.3 Support progressive disclosure

An agent should not need the entire session or project in context in order to make one decision.

It should be able to move from coarse structure to detail:

```text
Session
  -> branch
     -> episode or turn
        -> observation or tool result
```

and:

```text
Project
  -> subsystem
     -> module
        -> function
           -> code group
              -> statement
```

The same pattern should apply to documents, PDFs, sessions, code, migrations, and future domains.

### 2.4 Make branching a normal unit of agent work

Exploration, editing, validation, retries, and focused subproblems should be able to occur in branches without forcing all intermediate activity into the main session path.

A completed branch should be representable compactly by its purpose, outcome, touched knowledge, and result references while remaining fully inspectable when needed.

### 2.5 Keep agent work transactional

Agents should not silently mutate canonical project state while exploring.

A branch or workspace should be able to produce a proposed migration, validate it, compare it with its base, and only then promote the result.

Failed attempts should not corrupt the accepted state.

### 2.6 Preserve exact provenance

An agent observation must be traceable to what the agent actually saw.

If an agent inspected a particular function revision, later edits must not make the historical observation appear to have been based on the new revision.

The session should therefore distinguish stable conceptual entities from exact revisions and snapshots where historical precision matters.

### 2.7 Avoid privileged raw access

An agent should not normally receive unrestricted byte-oriented file read and write capabilities merely because files exist as projections.

It should use semantic navigation and editing capabilities appropriate to the knowledge it is working with.

Raw or projection-level access may still exist when required, but it is an explicit capability rather than the universal default.

### 2.8 Remain useful without an agent runtime

Session data, branch history, tool provenance, decisions, migrations, summaries, and project knowledge should remain ordinary database content that can be inspected through the CLI, API, TUI, web editor, or third-party applications.

The knowledge system must not depend on one model provider or even on the presence of an LLM.

## 3. Sessions Are a Domain over the Universal Knowledge Model

The session domain specializes the universal knowledge model in the same way that Markdown, source code, and PDFs do.

Conceptually:

```text
Universal Knowledge Model
        |
        +-- Markdown Domain
        +-- Source Code Domain
        +-- PDF Domain
        +-- Session Domain
```

The universal store does not need hard-coded understanding of a session turn, branch, goal, or tool result.

The session domain defines those meanings through schemas, relations, validation rules, descriptions, queries, projections, and operations.

This is important because session objects should be able to participate in universal operations such as:

```text
inspect
list
follow relations
find
query
diff
history
render
branch
```

A session should not be an opaque serialized conversation blob.

---

## 4. A Session Is a Graph, Not a Log

A chronological log is one useful projection of a session, but it is not the complete session model.

A session may conceptually contain:

```text
Session S
├── Goal G
├── HumanInput H1
├── AgentTurn T1
│   ├── ToolInvocation I1
│   ├── ToolResult R1
│   └── Observation O1
├── Branch B1
│   ├── purpose
│   ├── investigation
│   └── BranchResult BR1
├── Decision D1
└── OpenTask Q1
```

Some relationships are chronological.

Others are semantic:

```text
Observation O1
    derived_from -> ToolResult R1

Decision D1
    derived_from -> Branch B1
    concerns -> ProjectEntity P

Branch B1
    touched -> Function F
    produced -> Migration M
```

Flattening all of this into messages loses useful structure.

The session model should therefore preserve both:

```text
event order
+
semantic relationships
```

A familiar chat transcript can be rendered from that structure when needed.

---

## 5. Session Identity and Revision

Sessions follow the same identity rules as other domains.

A conceptual session may have stable identity while its exact state evolves through immutable revisions.

Conceptually:

```text
Session S
    revision SR1
    revision SR2
    revision SR3
```

Appending a turn, adding a branch, resolving a task, or promoting a decision produces new session state rather than rewriting historical state.

The exact representation of session membership belongs in lower-level design, but the architectural requirements are:

- historical session states remain addressable;
- session objects can refer to exact project revisions or snapshots;
- current views can resolve stable entity references to current revisions;
- historical views can remain pinned to the revisions that were actually observed;
- session evolution uses the same immutable change model as other knowledge.

Recording session activity may change a global snapshot even when project code does not change.

That is acceptable.

Consumers that care about project changes should compare the relevant entities, project roots, dependencies, or scoped state rather than interpreting every global snapshot change as a source-code change.

---

## 6. Core Session Concepts

The session domain should support a small set of durable concepts without requiring every implementation to store every model interaction at the same granularity.

Useful conceptual types include:

```text
Session
Goal
HumanInput
AgentOutput
Question
Observation
Decision
Task
ToolInvocation
ToolResult
ArtifactReference
Branch
BranchResult
MigrationProposal
ValidationResult
Summary
```

These names describe semantics, not mandatory table names or Rust types.

A domain extension may add more specialized objects where useful.

The important rule is that known structure should not be unnecessarily collapsed into untyped text.

---

## 7. Turns Are Presentation Boundaries, Not the Only Semantic Boundaries

A conversational interface naturally groups activity into turns.

For example:

```text
user message
agent reasoning and actions
agent response
```

That grouping is useful for chronological display, but many important objects inside the turn deserve their own identities and relationships.

A turn may include:

```text
AgentTurn T
├── ToolInvocation I1
├── ToolResult R1
├── Observation O1
├── ToolInvocation I2
├── ToolResult R2
├── MigrationProposal M1
└── AgentOutput A1
```

Another consumer may care about `M1` without needing the rest of the turn.

A branch summary may refer to `O1` and `M1` directly.

A validation result may refer to `M1` without referring to the human-facing response.

This makes the session graph useful for machines as well as for transcript rendering.

---

## 8. The Model Does Not Require Private Reasoning Traces

Scriberig correctness must not depend on storing hidden model reasoning or an implementation-specific chain of thought.

The durable session model should be built from externally meaningful artifacts such as:

- user inputs;
- agent outputs;
- explicit goals;
- observations;
- questions;
- decisions;
- tool invocations;
- tool results;
- migration proposals;
- validation evidence;
- summaries;
- project references.

A model integration may provide additional reasoning artifacts when permitted and useful, but those artifacts are optional domain data rather than a prerequisite for replay, history, or auditability.

This keeps the session model independent of provider-specific hidden state.

---

## 9. Branches Are First-Class Session Objects

A branch represents focused work derived from a parent context.

Examples include:

- investigating one design question;
- editing one function;
- exploring an alternative implementation;
- resolving a merge conflict;
- checking one external source;
- running a validation loop;
- asking a specialized sub-agent to perform a bounded task.

A branch is not merely a UI indentation level.

It is a first-class knowledge object with its own history, description, relationships, and result.

Conceptually:

```text
Main Session
    |
    +-- Branch B1
    |     "Investigate cache invalidation"
    |
    +-- Branch B2
          "Refactor parser error handling"
```

Branches may themselves contain nested branches.

---

## 10. Branch Descriptors

Every significant branch should have a compact descriptor suitable for navigation.

A descriptor may communicate concepts such as:

```text
title
purpose
status
outcome
touched knowledge
result references
size or activity counts
```

For example:

```text
Branch B42

Title:
  Render cache invalidation

Purpose:
  Determine which identities must participate in render caching.

Status:
  completed

Outcome:
  Cache by immutable content revision, immutable style revision,
  and renderer version.

Touches:
  RenderCache
  StyleModel
  RevisionIdentity

Result:
  Decision D19
```

The descriptor is intentionally small.

It allows an agent or human to decide whether the branch is relevant without loading its full history.

Descriptions may be authored by users, produced by the agent, generated from branch state, or derived later. Their provenance should remain available.

---

## 11. Branch Progressive Disclosure

Branches should expose multiple levels of detail.

A session overview may show only:

```text
B17  Immutable node identities
B18  External file reconciliation
B19  Session graph model
```

Inspecting one branch may reveal:

```text
purpose
status
outcome
touched entities
produced migrations
produced decisions
open questions
turn count
tool-call count
```

Opening the branch may reveal:

```text
episodes
turns
tool interactions
observations
full outputs
```

This pattern is the same one used elsewhere in Scriberig.

A project may expose modules before functions. A PDF may expose pages before regions. A session exposes branches before individual interactions.

---

## 12. Branches May Be Transient in Context without Being Lost

A completed branch does not need to remain expanded in the parent agent context.

The parent may retain only a compact reference such as:

```text
BranchResult BR1

summary:
  "Use immutable revision identity for local caches and a snapshot
   identity for global state detection."

produced:
  Decision D19

related:
  Branch B42
```

The full branch remains addressable through `B42`.

This distinction is central to long-running sessions.

Without it, every investigation permanently increases the amount of context required by future agent turns.

With it, old work can collapse to a small semantic handle while preserving exact provenance.

---

## 13. Branch Lifecycle

A typical focused agent branch has a lifecycle conceptually similar to:

```text
create branch
    |
    v
establish purpose and scope
    |
    v
inspect relevant knowledge
    |
    v
perform actions or propose changes
    |
    v
validate results
    |
    +-- failure -> revise, retry, or abandon
    |
    v
produce BranchResult
    |
    v
promote selected outcomes to parent
```

Not every branch must produce a project change.

A branch may instead produce:

- a decision;
- an answer;
- a summary;
- an observation;
- a rejected hypothesis;
- an unresolved question;
- a migration;
- a validation result;
- no useful result at all.

The branch remains a record of focused work even when nothing is promoted.

---

## 14. Nested Branches

Branches may create child branches for narrower tasks.

For example:

```text
Branch B1
"Design Rust reconciliation"
    |
    +-- B1.1
    |   "Investigate macro representation"
    |
    +-- B1.2
        "Compare parser strategies"
```

When the child branches complete, `B1` need not absorb their complete histories.

It may retain their descriptors and results.

This allows arbitrary depth without forcing arbitrary depth into model context.

Nested branches should therefore preserve two distinct relationships:

```text
structural parentage
```

and:

```text
semantic references between results
```

A decision produced in a deep branch may later become project-level knowledge without requiring consumers to traverse every parent turn.

---

## 15. Branch Result

A completed branch should be able to produce an explicit result object.

Conceptually it may include or reference:

```text
summary
status
resulting migration or snapshot
validated artifacts
decisions
observations
open questions
touched entities
child-branch results
```

For an editing branch:

```text
BranchResult
    summary -> "Add timeout handling to payment provider calls"
    produced -> Migration M12
    validated_by -> ValidationResult V8
    touched -> Function process_payment
```

For a research branch:

```text
BranchResult
    summary -> "Existing parser cannot preserve required token structure"
    produced -> Decision D7
    references -> SourceArtifact A3
```

The parent session can consume the result without replaying the branch.

---

## 16. Session Context Is a Projection

The context sent to an agent is not the session itself.

It is one projection of session and project knowledge chosen for a particular model invocation.

Conceptually:

```text
Session Graph
Project Knowledge
Current Selection
Capabilities
Context Policy
        |
        v
   Context Renderer
        |
        v
    Model Context
```

This is analogous to other Scriberig projections:

```text
semantic document + Markdown style -> Markdown text
semantic code + source style       -> source file
session graph + context policy     -> model context
```

The canonical session must not be distorted merely to match one model's context window or prompt format.

---

## 17. Context Policies

A context policy determines which information is useful for one agent invocation.

It may prefer:

```text
current goal
current branch purpose
recent interactions
open tasks
accepted decisions
relevant object descriptions
current project selection
relevant completed branch results
```

while omitting or summarizing:

```text
completed exploratory branches
redundant tool outputs
superseded decisions
unrelated history
large raw artifacts
failed attempts that no longer matter
```

Different agents or tasks may use different context policies over the same session.

A debugging agent may want recent diagnostics and exact code revisions.

A design agent may want current decisions and branch summaries.

A human transcript view may prefer chronological completeness.

The underlying session graph remains the same.

---

## 18. Context Must Preserve Referential Integrity

Compact context is only useful if it contains handles that allow the agent to obtain more information.

A summary should therefore prefer:

```text
Function F — "Parses incoming requests"
Branch B42 — "Investigated render caching"
Decision D19 — "Cache by immutable revision and style identity"
```

over unreferenced prose that cannot be followed.

If an agent decides that `B42` is relevant, it should be able to inspect `B42` directly.

If it needs the exact historical function state discussed by the branch, that relationship should be available.

This makes compressed context navigable rather than lossy.

---

## 19. Current References and Historical References

The system should distinguish two common meanings of an entity reference.

A current reference asks:

> What is the current revision of this conceptual entity in my current scope?

A pinned historical reference asks:

> What exact revision did this observation, tool result, or decision refer to at that time?

Both are useful.

For example:

```text
Observation O7
    inspected -> Function F @ Revision FR12
```

Later the current project may resolve `F` to `FR19`.

Historical inspection of `O7` must still point to `FR12`.

A current agent may then ask for the lineage or semantic diff from `FR12` to `FR19` rather than rereading unrelated history.

---

## 20. Tool Invocations Are First-Class Knowledge

A tool invocation should not exist only as text embedded in a transcript.

It should be possible to represent concepts such as:

```text
ToolInvocation I
    operation -> inspect
    target -> Function F
    pinned_revision -> FR12
    initiated_by -> Branch B3
```

The exact low-level arguments belong to the operation protocol, but the semantic relationships should remain queryable.

This allows the system to answer questions such as:

- which branch inspected this entity;
- which tool result supported this decision;
- which migration caused a validation run;
- whether an observation came from current or historical project state.

---

## 21. Tool Results Are Reusable Knowledge

A tool result should be able to reference structured knowledge rather than always storing another independent text blob.

For example:

```text
ToolInvocation I1
    inspect -> Function F @ FR12

ToolResult R1
    produced -> FunctionSummary S9
```

If the same immutable function revision and summary profile are requested elsewhere, the derived result may be reusable.

This connects session architecture to Scriberig's broader caching and derived-knowledge model.

The session records that `R1` was observed in this branch, while the summary itself can remain a reusable derived object.

Large results should also support progressive disclosure.

An agent may initially receive counts, descriptions, or result handles rather than complete raw output.

---

## 22. One Navigation Grammar across Domains

Agents should not need fundamentally different navigation concepts for sessions, code, PDFs, and documents.

The universal interaction model should allow patterns such as:

```text
inspect(object)
list(object, relation)
follow(object, relation)
find(scope, query)
diff(a, b)
history(object)
render(object, projection)
```

The domain determines what relations and specialized capabilities exist.

For example:

```text
Function F
relations:
  parameters
  body
  calls
  references
  comments
```

```text
PDF Document P
relations:
  pages
  headings
  tables
  figures
```

```text
Session S
relations:
  goals
  branches
  decisions
  tasks
  recent activity
```

This gives agents one mental model for discovering all knowledge in Scriberig.

Domain-specific semantic operations may still exist, but they extend the shared interaction grammar rather than replacing it.

---

## 23. Progressive Disclosure Is an Agent Safety and Efficiency Mechanism

Progressive disclosure is not merely a user-interface preference.

It reduces several failure modes:

- context windows filled with irrelevant data;
- agents overlooking important structure inside large blobs;
- repeated rereading of unchanged source;
- excessive tool output;
- accidental access to unrelated project areas;
- unnecessary model cost;
- increased decision complexity from hundreds of possible objects at once.

A container should therefore be able to describe its shape before revealing all content.

Examples:

```text
Section
  subsections: 4
  paragraphs: 9
  tables: 2
```

```text
Function
  code groups: 6
  statements: 34
  external calls: 4
```

```text
Branch
  turns: 12
  tool calls: 7
  decisions: 2
  resulting migrations: 1
```

The agent can then choose where to spend attention.

---

## 24. Agents Should Receive Semantic Objects before Raw Projections

When a semantic representation exists, it should normally be the agent's first interface.

For a Markdown document, the agent should be able to inspect sections, paragraphs, tables, and rows rather than reading the entire `.md` file.

For source code, it should be able to inspect modules, functions, code groups, statements, symbols, and references rather than receiving an unrestricted source blob by default.

For a session, it should inspect goals, branches, results, and decisions rather than replaying every message.

For a PDF, it should be able to navigate pages, regions, tables, figures, and extracted semantic content.

Raw text and rendered projections remain valuable when exact presentation matters, but they are not the universal access primitive.

---

## 25. Capability-Scoped Access

Agent access should be expressible as capabilities over knowledge rather than as blanket filesystem permissions.

A branch may receive scope such as:

```text
project P
module M
function F
document section S
session branch B
```

and operations such as:

```text
inspect
query
propose change
validate
render
```

A focused sub-agent working on one function should not require automatic access to every unrelated document and session in the database.

Likewise, a research branch that only needs read access should not automatically receive mutation capabilities.

The detailed authorization model belongs in the trust and capabilities design, but agent interaction must be compatible with narrow scopes from the beginning.

---

## 26. Agent Edits Produce Semantic Change

An agent should not be modeled as a process that writes bytes directly into canonical storage.

Its edits should produce semantic operations or a migration proposal against a known base state.

Conceptually:

```text
Base Snapshot S1
        |
        v
 Agent Branch
        |
        v
Migration Proposal M
        |
        v
 Validation
        |
        +-- rejected -> branch continues or is abandoned
        |
        v
Promotion
        |
        v
Result Snapshot S2
```

This is the same change model used for human operations, API clients, web editing, CLI commands, and external projection reconciliation.

The agent is not a special mutation path.

---

## 27. Agent Workspaces and Session Branches Are Related but Distinct

A session branch represents conversational and semantic work.

A project workspace represents speculative project state derived from a base.

They are often linked, but they should not be conflated.

For example:

```text
Branch B7
    purpose -> "Refactor parser error handling"
    workspace -> W3
    produced -> Migration M18
```

The branch may continue discussing a failed workspace, create another candidate, compare alternatives, and eventually promote one result.

This separation allows one branch to reason about multiple candidate states without pretending every attempt became canonical project history.

---

## 28. Validation Is Part of Agent Work, Not an Afterthought

A branch that proposes canonical changes should be able to attach evidence that the result was checked.

Depending on domain, validation may include:

```text
schema validation
parse validation
type checking
linting
tests
projection round-trip checks
domain invariants
human approval
```

Validation results are ordinary structured objects that can be linked to the migration, branch, and resulting state.

The agent may use failed validation as new observations and continue working within the branch.

Only accepted results are promoted according to policy.

---

## 29. Failures and Abandoned Attempts Remain Distinguishable

Not every agent action succeeds.

The session model should represent failure explicitly rather than forcing consumers to infer it from prose.

Useful states may include concepts such as:

```text
active
completed
abandoned
failed
superseded
```

A failed migration proposal should not be confused with a committed migration.

An abandoned branch should not be presented as current project knowledge.

A superseded decision should remain historical but should not normally appear as the current answer to a project query.

The precise state vocabulary belongs in domain schemas, but the distinction is architectural.

---

## 30. Decisions and Durable Project Knowledge

Sessions often produce information that remains useful after the conversation ends.

Examples include:

- accepted architectural decisions;
- facts discovered from project artifacts;
- open questions;
- rejected alternatives;
- tasks;
- constraints;
- validated hypotheses.

These should be promotable to durable project knowledge while retaining provenance back to the session branch that produced them.

Conceptually:

```text
Decision D19
    text -> "Canonical source nodes preserve chosen syntax"
    status -> accepted
    derived_from -> Branch B81
    concerns -> SourceModel
```

Later sessions should be able to query `D19` directly rather than searching old transcripts.

The original branch remains available when the reasoning history or evidence matters.

---

## 31. Promotion Is Explicit

A conversational statement should not automatically become an authoritative project fact merely because an agent said it.

Promotion from session activity to durable knowledge should be explicit or governed by a clear policy.

For example:

```text
AgentOutput
    -> proposes Decision D

Decision D
    status -> proposed

later

Decision D
    status -> accepted
```

The exact workflow may vary, but the system must preserve the distinction between:

```text
conversation
interpretation
proposal
accepted knowledge
```

This avoids turning every speculative agent sentence into canonical truth.

---

## 32. Summaries Are Derived Knowledge

A branch summary, session summary, function summary, or tool-result summary is normally derived from other objects.

It should therefore follow the same derived-knowledge principles as compiler analysis, render intermediates, and cached descriptions.

A summary should identify:

- what object or state it summarizes;
- what summary profile or policy was used where relevant;
- its provenance;
- whether it is authoritative or model-generated.

Because source revisions are immutable, a summary of an exact immutable source can be cached safely.

If a branch changes, its new revision may require a new summary while the old summary remains valid for the old branch state.

---

## 33. Session Summaries Should Preserve Structure

A useful session summary is not merely a shorter transcript.

It should preferentially preserve semantic structure such as:

```text
current goal
accepted decisions
open questions
active branches
completed branch outcomes
important touched entities
pending migrations
validation status
```

This makes the summary useful as input to later agents and other applications.

A chronological narrative may also exist as another projection.

---

## 34. Multi-Agent Work Uses the Same Branch Model

Multiple agents should not require a separate collaboration architecture.

They can operate on independent branches or workspaces derived from known bases.

For example:

```text
                  Base S1
                 /       \
                /         \
       Agent Branch A   Agent Branch B
              |               |
              v               v
             S2              S3
                \            /
                 \          /
                    merge
                      |
                      v
                     S4
```

The agents may work on unrelated entities and merge automatically, or they may produce semantic conflicts requiring resolution.

Session branches record who or what performed the work and how the results were derived.

The underlying merge model remains the universal migration and snapshot model.

---

## 35. Agents May Delegate through Nested Branches

A parent agent may delegate a focused task to another agent or agent configuration.

The child receives:

- a purpose;
- a base state;
- selected knowledge handles;
- a capability scope;
- an expected result shape.

The parent receives a `BranchResult` rather than an uncontrolled stream of the child's entire interaction history.

This allows specialization without permanently inflating parent context.

The full child branch remains inspectable for provenance and debugging.

---

## 36. Agent Configuration Is Not Session Identity

A session may involve different models, providers, tools, context policies, or agent profiles over time.

The session is the persistent knowledge structure.

The agent configuration is execution metadata associated with particular work.

This distinction allows:

- resuming a session with a different model;
- assigning a specialized agent to one branch;
- replaying or inspecting historical activity without requiring the original provider;
- comparing outcomes from different agent configurations.

Relevant execution metadata may be stored for provenance, but session semantics must not depend on one specific model implementation.

---

## 37. Replay and Reproducibility

Scriberig should preserve enough structured provenance to reconstruct what information and operations participated in important work.

That does not imply deterministic replay of model behavior.

Models and external services may be nondeterministic or unavailable later.

The stronger guarantee is:

> Historical inputs, referenced knowledge revisions, tool invocations, tool results, migrations, validations, and accepted outcomes should remain inspectable even when the original agent cannot be reproduced exactly.

Where exact replay is possible, the stored structure should support it.

Where it is not, auditability remains valuable.

---

## 38. Human and Agent Views Share the Same Session

A human-facing application may render a session as a familiar conversation.

An agent-facing context renderer may show goals, current decisions, branch summaries, and relevant project objects.

An audit view may show every tool invocation and result.

A database browser may show the raw entity and relation graph.

These are projections over the same underlying session knowledge.

Conceptually:

```text
                 Session Graph
                /      |      \
               /       |       \
     Human Transcript  |   Audit View
                       |
                 Agent Context
```

No projection should become a second source of truth.

---

## 39. Selection and Scope Can Cross Interface Boundaries

The same object handle should be usable across CLI, API, web UI, TUI, and agent interaction.

For example, a user may select a function in the integrated editor and issue an agent command.

The command should conceptually scope the agent to:

```text
Function F
at Snapshot S
```

rather than converting the selection into an informal instruction such as:

```text
"look at lines 120-180 of src/foo.rs"
```

The same function reference can then be used by:

- the object inspector;
- history view;
- semantic diff view;
- agent branch;
- validation system;
- CLI;
- third-party API clients.

This is one of the main benefits of storing sessions and project content in the same knowledge system.

---

## 40. Search across Sessions Should Be Semantic

A session search should not be limited to text matching over transcripts.

Useful queries include:

```text
find branches touching Function F
find decisions about snapshot identity
find migrations produced by Agent A
find failed validations for Module M
find observations derived from ToolResult R
find branches that superseded Decision D
```

Text search remains useful, but it should return semantic handles such as branches, decisions, tool results, and messages rather than only byte offsets.

---

## 41. Descriptions Are Attention Metadata

Short descriptions are important across the entire knowledge system, but they are especially important for agents.

A description helps an agent decide what to inspect next without consuming the full object.

Examples:

```text
Function F
"Reconciles an externally edited Markdown projection."
```

```text
Branch B
"Investigates whether entity identity should change on edits."
```

```text
Migration M
"Adds session branches and branch-result promotion."
```

Descriptions should be cheap to retrieve and should include provenance when generated rather than authored.

They are a navigation layer over canonical knowledge, not a replacement for it.

---

## 42. Information Cost May Be Exposed

An agent can make better navigation decisions when it knows approximately how much information an operation will reveal.

An implementation may expose estimates such as:

```text
branch descriptor     small
branch summary        medium
full branch history   large
```

or:

```text
function description  small
code-group map         medium
full syntax tree       large
```

The exact cost metric belongs in lower-level designs, but the architectural principle is useful:

> Consumers should be able to choose an appropriate level of detail before paying the full context cost.

---

## 43. Capability Results Should Advertise Next Handles

Agent-facing results should be referential.

Instead of returning only:

```text
"The cache decision was made in an earlier branch."
```

prefer information equivalent to:

```text
Branch B42
  description: "Investigated render caching"

Decision D19
  description: "Cache by immutable revision and style identity"
```

The agent can then inspect either object directly.

This pattern reduces repeated searching and makes progressive disclosure practical.

---

## 44. Context Changes Need Not Invalidate Unrelated Understanding

A session's global snapshot may change frequently because new turns, branches, and results are added.

That should not force the agent system to discard every cached description or analysis.

Derived knowledge should depend on the exact immutable objects it actually used.

For example:

```text
FunctionSummary FS
    depends_on -> Function F @ FR12
```

A new session message does not invalidate `FS`.

A different unrelated function changing does not invalidate `FS`.

Only a dependency change requires recomputation.

This follows the same local-versus-global identity model used elsewhere in Scriberig.

---

## 45. Tool Output Should Not Pollute Context by Default

Tool results may be large.

A compiler can produce thousands of diagnostics. A search can return hundreds of objects. A PDF extraction can contain many pages. A test run can emit large logs.

Storing these results does not imply injecting them into every future model context.

The session should retain handles and summaries while allowing full results to be inspected on demand.

This is another application of the distinction between:

```text
persistent knowledge
```

and:

```text
current context projection
```

---

## 46. Sensitive and External Data Remain Scoped Knowledge

Sessions may reference external services, private repositories, local files, credentials-adjacent configuration, or other sensitive resources.

The fact that all knowledge uses one substrate does not imply that all knowledge is globally visible to every agent.

Authorization, provenance, retention, and capability scopes must continue to apply to session-derived objects and references.

An agent context renderer must respect those boundaries when following session relations.

The detailed security policy belongs in the trust and capability design.

---

## 47. Retention and Garbage Collection

Some session data may need long-term retention while other data may eventually be collectible.

Examples of likely retained roots include:

- active sessions;
- named or pinned branches;
- accepted decisions;
- migrations retained as project history;
- branch results referenced by current knowledge;
- audit records required by policy.

Transient failed work may become collectable when no retained root references it and policy permits deletion.

Garbage collection must follow the same reachability and retention model as the rest of the immutable object store.

The session domain should not require its own separate cleanup mechanism.

---

## 48. Session Projections

Useful session projections include at least the following conceptual views.

### 48.1 Human chat projection

A chronological conversational representation suitable for a familiar chat interface.

### 48.2 Agent context projection

A compact representation optimized for one model invocation.

### 48.3 Audit projection

A detailed view emphasizing tool actions, exact referenced revisions, migrations, validation, and provenance.

### 48.4 Decision projection

A view emphasizing accepted decisions, superseded decisions, open questions, and their provenance.

### 48.5 Branch tree projection

A hierarchical representation of investigations and delegated work.

These projections may differ greatly while referring to the same underlying session graph.

---

## 49. Session Structure Should Be Useful to Non-Agent Applications

A project-management UI may use session tasks without running an agent.

A code-review tool may inspect migrations and validation evidence from an agent branch.

A web editor may show branch history and decisions.

A CI system may attach validation results to a migration.

A database browser may inspect the raw relation graph.

A third-party application may create its own structured session objects through the public API.

Therefore session schemas and navigation must remain reusable infrastructure rather than private implementation details of the built-in agent runtime.

---

## 50. Relationship to Migrations and Project History

A session branch may produce a migration, but the session branch and migration are different objects.

The branch explains the work process and context.

The migration explains the canonical state transition.

Conceptually:

```text
Branch B
    produced -> Migration M

Migration M
    base -> Snapshot S1
    result -> Snapshot S2
```

A project history view can inspect `M` without reading `B`.

An audit view can follow `M` back to `B` when it needs the provenance of the change.

This separation prevents conversation history from becoming mandatory for understanding canonical state.

---

## 51. Relationship to External Projection Edits

An externally edited source file and an agent edit should ultimately enter the same change model.

For example:

```text
external editor
    -> parse
    -> reconcile
    -> migration
```

and:

```text
agent branch
    -> semantic operations
    -> migration proposal
    -> validation
    -> migration
```

The provenance differs.

The canonical state transition model does not.

This is important because history, merge, validation, and UI should not need separate implementations for human file edits and agent edits.

---

## 52. Relationship to the Universal Query and Operation Model

This document defines why agents need one shared navigation and action model.

The precise operation vocabulary belongs in the universal query and operation design.

The session architecture assumes that agents can work through domain-independent concepts such as:

```text
inspect
list
follow
find
query
diff
history
render
branch
apply
commit
```

and that domains can extend those concepts with semantic operations.

Session-specific operations should therefore be thin specializations of the common model rather than a separate agent-only protocol.

---

## 53. Relationship to Domain Adapters

The session domain should be implemented like any other domain specialization.

It defines:

- entity types;
- relations;
- branch semantics;
- projection types;
- summary profiles;
- domain validation;
- domain-specific queries;
- domain-specific operations.

Agent tools that inspect source code, PDFs, or documents use those domains' adapters.

The session layer coordinates and records the work but should not duplicate domain logic.

For example, session code should not implement its own Rust parser or PDF extractor.

---

## 54. Relationship to Derived Knowledge

Descriptions, branch summaries, session summaries, model-generated interpretations, and cached tool views are derived knowledge unless explicitly promoted or authored as canonical facts.

They should preserve:

```text
source objects
source revisions
profile or policy
provenance
```

This makes them safely cacheable and prevents generated interpretation from being confused with authoritative source knowledge.

---

## 55. Relationship to Trust and Provenance

The session model records where observations and changes came from, but it does not by itself decide what should be trusted or permitted.

The trust and capability design defines policies such as:

- who may inspect an object;
- who may propose a migration;
- who may promote a migration;
- which validations are required;
- which external sources are trusted;
- which generated descriptions may be presented as authoritative;
- what sensitive session data may be retained.

The session architecture must preserve enough provenance for those policies to be enforceable.

---

## 56. Architectural Invariants

Implementations of agent interaction and sessions must preserve the following invariants.

1. **Sessions use the universal knowledge store.**

   They are not a separate transcript database.

2. **A transcript is a projection.**

   Chronological chat is one representation of richer session structure.

3. **Branches are first-class knowledge objects.**

   They may be described, queried, nested, summarized, retained, or collected like other knowledge.

4. **Completed branches may collapse in context without disappearing from storage.**

   A branch result and descriptor can stand in for full history until deeper inspection is needed.

5. **Session history does not require private model reasoning.**

   Durable semantics are built from observable actions, outputs, decisions, tool interactions, and explicit structured knowledge.

6. **Agent context is derived from the session; it is not the session itself.**

   Different context policies may render the same session differently.

7. **Historical observations remain pinned to what was actually observed.**

   Later entity revisions do not rewrite the meaning of old tool results or decisions.

8. **Agents use semantic handles.**

   Filenames, line numbers, and raw byte offsets are projection details when more stable semantic identities exist.

9. **Agents do not require unrestricted file access.**

   Access can be scoped to objects, relations, domains, and operations.

10. **Agent edits use the universal change model.**

    They produce semantic proposals and migrations rather than a separate mutation path.

11. **Speculative work is isolated.**

    Failed or exploratory branches do not silently become canonical project state.

12. **Validation evidence is first-class.**

    Successful promotion may reference structured validation results.

13. **Session-derived knowledge has provenance.**

    Decisions and summaries retain links to the branches and evidence that produced them.

14. **Generated summaries are not automatically canonical truth.**

    Derived interpretation remains distinguishable from accepted knowledge.

15. **Tool results may be persistent without being permanent context.**

    Large outputs can be summarized and reopened on demand.

16. **One interaction grammar spans domains.**

    Sessions, code, PDFs, documents, and future domains share universal navigation concepts.

17. **The agent runtime is a consumer, not a dependency of the knowledge system.**

    Session and project data remain useful through ordinary libraries and applications.

18. **Multi-agent work uses the same branch, snapshot, migration, and merge concepts as other concurrent work.**

19. **Project knowledge can outlive the session that produced it.**

    Durable facts, decisions, and tasks are promoted explicitly with provenance.

20. **All projections remain subordinate to canonical structured knowledge.**

    Human chat, agent context, audit logs, and branch trees do not become independent sources of truth.

---

## 57. Non-Goals

This Level 1 design does not require:

- storing every model token;
- storing hidden chain-of-thought reasoning;
- deterministic replay of nondeterministic models;
- one fixed prompt format;
- one model provider;
- one fixed branch-depth limit;
- one universal summary algorithm;
- injecting every stored tool result into context;
- replacing domain-specific semantic tools with only generic graph traversal;
- giving agents unrestricted database access;
- giving agents unrestricted filesystem access;
- making every conversational statement project truth;
- keeping every abandoned branch forever;
- defining the precise Rust crate boundaries or API endpoints.

Those choices may be made in lower-level designs where appropriate.

## 58. Example: Focused Code Edit

Consider a user asking an agent to change retry behavior in a function.

The user or UI identifies:

```text
Function F
```

The session creates:

```text
Branch B
purpose:
  "Change retry behavior in Function F"
```

The branch receives access to relevant semantic knowledge.

It inspects:

```text
Function F @ Revision FR12
```

and possibly relevant callers, configuration, tests, and decisions.

The branch proposes:

```text
Migration M
```

Validation produces:

```text
ValidationResult V
```

If accepted, the branch result records:

```text
BranchResult BR
    produced -> Migration M
    validated_by -> V
    touched -> Function F
```

The parent session may retain only:

```text
B — "Updated retry policy; validation passed"
```

while the full branch remains inspectable.

No stage requires the parent context to contain the full source file or every intermediate turn.

---

## 59. Example: Research Branch without Project Mutation

A design session asks whether content-addressed revisions should include parent identity.

A branch is created:

```text
Branch B
purpose:
  "Evaluate parent identity in revision hashes"
```

The branch inspects the identity design and related examples.

It concludes:

```text
Decision D
"Parent identity is not part of a child revision's local identity."
```

No source migration is produced.

The branch result contains:

```text
summary
Decision D
references to the relevant design entities
```

The parent session uses `D` and the compact branch result.

Later agents can query `D` directly without replaying the branch.

---

## 60. Example: Nested Delegation

A parent branch is implementing a Rust adapter.

It creates two child branches:

```text
B1
"Implement Rust adapter"
    |
    +-- B1.1
    |   "Investigate macro token preservation"
    |
    +-- B1.2
        "Investigate formatting strategy"
```

Each child has its own capabilities, context policy, tool interactions, and result.

The parent receives:

```text
B1.1 result:
  preserve invocation token trees canonically

B1.2 result:
  render through style-dependent pretty-print IR
```

The parent need not include the complete child transcripts in its next invocation.

If a later implementation problem appears in macro handling, the agent can reopen `B1.1` directly.

---

## 61. Example: Session as a Navigable Knowledge Tree

A long-running project session may initially be presented as:

```text
Session S
Goal:
  Build the Scriberig universal knowledge platform

Active branches:
  B71  "Agent interaction and sessions"

Completed branches:
  B12  "Identity and snapshots"
  B29  "Bidirectional projections"
  B44  "Domain adapters"

Current decisions:
  D8   "Entities have stable conceptual identity"
  D15  "Revisions identify exact immutable state"
  D22  "Files are editable projections"
```

This representation may be only a few hundred tokens even if the full session contains thousands of interactions.

The agent then opens only the relevant branch or decision.

That is the intended scaling model.

---

## 62. Definition of a Session

A Scriberig session is a structured, versioned knowledge graph describing an interaction process around goals, observations, decisions, actions, branches, and results.

It is stored in the same universal knowledge system as the artifacts the agent works on.

A session can be rendered as a human transcript, an agent context, an audit history, a branch tree, or a decision view without changing its canonical meaning.

Branches allow focused and nested work to proceed without permanently expanding parent context. Short descriptions and branch results make completed work cheap to navigate while retaining exact provenance.

Agents interact with project and session knowledge through stable semantic handles, progressive disclosure, shared query operations, and capability-scoped actions. Their edits become semantic migrations subject to the same branching, validation, history, and merge rules as changes produced by humans and other clients.

The result is a session model in which conversation is not an append-only wall of text. It is a navigable part of the project's knowledge graph, capable of scaling with long-running work while preserving history, exact references, and durable outcomes.
