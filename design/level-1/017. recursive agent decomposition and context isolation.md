# Recursive Agent Decomposition and Context Isolation

## 1. Purpose

Scriberig sessions are trees because agent work is recursively decomposed into focused units whose internal work should not automatically pollute the context of their parents or siblings.

This document makes that principle explicit and easy to reference. It refines, but does not replace:

1. `009. agent interaction and sessions.md`;
2. `015. terminal user interface principles.md`;
3. `016. model driven agent execution and branch isolation.md`;
4. `design/level-2/023. agent runtime model provider and branch orchestration.md`.

The controlling rule is:

> A branch is a context-isolation boundary for one focused goal. The branch may perform arbitrary model/tool back-and-forth and may recursively create children. Its parent normally receives only a compact result, durable handles, and the small amount of information needed to continue.

A branch is not primarily a visual indentation feature and it is not primarily a user-created chat fork. User continuations, agent delegation, retries, focused edits, investigation, validation, and conflict resolution all use the same branch model.

---

## 2. Why the Session Is a Tree

A linear transcript forces every later model step to inherit noise from all earlier work. That is acceptable for short chats but scales poorly for implementation work.

Consider a root task:

```text
Implement feature X
```

The agent may decompose it into work such as:

```text
Root: Implement feature X
|
+-- Understand architecture
|
+-- Create new source file
|   |
|   +-- Determine exact structure
|   +-- Write the file
|   +-- Repair syntax/type errors
|   +-- Validate the file
|
+-- Add tests for the completed source file
|
+-- Integrate feature
|
+-- Validate feature
```

Creating the source file may require many model calls, write operations, inspections, compiler errors, corrections, and local validation. The later test-writing task usually does not need that conversational history. It needs the completed file, its public behavior, relevant semantic handles, and possibly validation evidence.

The root task also does not need the full implementation dialogue. It needs a compact statement equivalent to:

```text
File created successfully.
Purpose: implements X.
Important interfaces: A, B, C.
Source/entity handles: ...
Validation: passed.
```

The tree exists so detailed work can remain fully inspectable without becoming permanent context for unrelated later work.

---

## 3. Branches May Be Created by Humans, Agents, or Runtime Policy

Do not treat human-created forks as a special branch architecture.

A branch may begin because:

- the user chooses to continue from an earlier session location;
- the current agent delegates a focused subtask;
- a branch-producing tool contract starts isolated work;
- the runtime isolates a speculative mutation or retry;
- validation failure triggers a repair branch;
- the agent compares alternatives in independent branches;
- conflict resolution requires a focused branch;
- a child agent recursively decomposes its own task.

The same canonical branch semantics apply in every case.

Origin may be useful provenance, but origin must not create incompatible kinds of session trees.

---

## 4. Recursive Decomposition Is Expected Behavior

A model-driven agent is expected to decompose work when doing so improves context quality, isolation, validation, or recoverability.

A child branch may create another child branch using the same rules. There is no architectural distinction between the first delegation level and deeper delegation levels.

Conceptually:

```text
Root task
|
+-- Child A
|   |
|   +-- Grandchild A1
|   |   |
|   |   +-- Great-grandchild A1a
|   |
|   +-- Grandchild A2
|
+-- Child B
```

Runtime budgets may limit depth, child count, token use, cost, or elapsed time. Those limits are execution policy. They do not change the semantic fact that branches may nest recursively.

---

## 5. Atomic Tool Calls and Branch-Producing Work Are Different

Do not create a branch for every small tool invocation.

An atomic operation can remain inside the current branch when it does not need an independent reasoning loop. Examples include:

```text
inspect one entity
read one bounded relation page
query operation status
fetch one compact semantic result
```

Create or delegate to a child branch when the work can require its own model/tool loop, speculative state, retries, validation, or further decomposition. Examples include:

```text
implement one file
edit one function
investigate a failing test
reconcile a projection
research one architectural question
compare an alternative implementation
resolve a conflict
validate and repair a candidate
```

This distinction prevents branch explosion while preserving context isolation where it matters.

---

## 6. Child Context Is Selected, Not Copied

Creating a child branch does not copy the complete parent transcript.

The child receives an explicit inheritance plan containing only the information required for its goal. Depending on the task, that may include:

```text
child purpose and expected result
parent branch descriptor
selected parent result handles
accepted decisions or constraints
semantic selection and exact snapshot/workspace
specific source/entity handles
capability subset
explicit delegation instruction
small bounded parent excerpt when policy deliberately allows it
```

Unrelated parent activity is omitted.

This is important in both directions:

- the child does not automatically inherit all parent history;
- the parent does not automatically inherit all child history.

Context construction is a projection over the session graph and project knowledge, not transcript concatenation.

---

## 7. Branch Completion Produces a Compact Contract

A completed branch produces a durable `BranchResult` or an explicit no-result/failure outcome.

A useful result contains concepts equivalent to:

```text
branch identity
status
short outcome summary
result kind
important semantic handles
produced candidate/migration/workspace handles
important touched entities
validation handles
unresolved questions
failure summary when unsuccessful
```

The result is the normal information boundary between parent and child.

The full child history remains stored and inspectable by stable reference. It can be reopened if the result is insufficient, but it is not implicitly inserted into the parent's next model request.

---

## 8. Parent Context Uses Results, Not Child Transcripts

After a child finishes, the parent normally continues with context equivalent to:

```text
current parent goal
recent parent activity
child descriptor
child BranchResult
relevant project state/result handles
other selected completed child results
```

It does not normally receive:

```text
every child model response
every child tool call
every failed edit attempt
every compiler diagnostic already resolved
every correction step
every grandchild transcript
```

The omitted history remains available for audit and inspection.

This is the principal mechanism that prevents a long implementation session from degrading into an ever-growing prompt.

---

## 9. Sibling Branches Should Communicate through Results

Sibling tasks should not depend on one another's internal conversational history.

For example:

```text
Root: implement feature
|
+-- Child A: create parser.rs
|     -> BranchResult: parser implementation + handles + validation
|
+-- Child B: write parser tests
```

Child B may receive the result of Child A, the exact created semantic/source state, and relevant design constraints. It does not need the back-and-forth that Child A used to arrive there.

If Child B discovers a defect, it may create or request another focused repair branch. That repair branch returns a new result rather than causing all previous implementation history to be copied into Child B's permanent context.

---

## 10. User Continuations Use the Same Tree

A user may navigate to a historical replyable node and continue from that semantic location.

That continuation is another branch operation over the same session graph. It is not a separate chat-fork mechanism.

The context compiler resolves the exact continuation location and constructs context from the path and results relevant to that point. Later sibling work is not silently injected merely because it occurred later in wall-clock time.

The default user behavior may continue from the current root/head so ordinary use feels linear, but the canonical session remains tree-shaped.

---

## 11. Branch Tree and Execution Activity Are Distinct

Two structures coexist:

### Session branch tree

Represents focused work decomposition:

```text
root task
  child task
    grandchild task
```

### Local execution/activity structure

Represents causal activity inside one branch:

```text
model invocation
  tool invocation
    tool result
  model invocation
  final output
```

Do not collapse these into one canonical relation.

A UI may combine them into one visual tree, but it must preserve which depth comes from branch ancestry and which depth comes from local activity causality.

---

## 12. TUI Conversation Is a Projection of This Recursive Tree

The default TUI should feel like a conventional coding-agent conversation while faithfully representing recursive decomposition.

Normal root interaction may look nearly linear:

```text
You
Implement X.

Assistant
Working on it...
```

When the agent creates focused children, the TUI inserts them structurally at the location where they belong rather than appending them only by timestamp.

A compact completed child may render like:

```text
▏ Create parser.rs
▏ ✓ completed — parser implementation created and validated
```

An active or expanded child may reveal its internal activity:

```text
▏ Create parser.rs
▏
▏ ▏ inspect existing parser conventions
▏ ▏ ✓ ...
▏
▏ ▏ Write parser.rs
▏ ▏ ...
▏
▏ ▏ Fix compile error
▏ ▏ ...
▏
▏ ✓ completed — parser implementation created and validated
```

If that child itself delegates validation, another rail depth appears beneath it.

The fact that the UI can expand the child does not mean the parent model received the expanded history.

---

## 13. Depth Rails Encode Structural Nesting

Terminal presentation should encode nesting with one visible vertical rail per ancestor depth.

Conceptually:

```text
▏ depth 1
▏ ▏ depth 2
▏ ▏ ▏ depth 3
```

Each depth uses a stable theme color from a finite palette. The palette may cycle at deep levels.

Color is supplemental. Nesting must remain understandable through rail count/position when color is unavailable.

For narrow terminals, older ancestor rails may be compacted with an explicit marker such as:

```text
… ▏ ▏ deeply nested activity
```

Do not persist depth color or indentation as semantic state. Derive them from branch/activity ancestry.

---

## 14. Completed Children Are Compact by Default, Expandable on Demand

The ordinary conversation projection should prefer attention-efficient presentation.

Recommended behavior:

- active branch: show enough live activity to understand progress;
- completed child branch: collapse to descriptor + result by default;
- failed child branch: show compact failure result and status;
- selected/expanded child: render retained detail on demand;
- parent branch: continue after the compact child result without reproducing child history.

Expansion is presentation state only.

Collapsing or expanding a branch must not change model context, branch semantics, or durable records.

---

## 15. Per-Activity Presentation Is Independent from Context

Each visible activity/message kind may have its own client presentation policy.

Examples include:

```text
tool invocation:
  hidden
  command truncated
  command full
  parameters one per line

tool result:
  hidden
  summary
  preview
  full bounded detail

reasoning summary:
  hidden
  shown

model request/prompt:
  hidden
  summary
  structured full

branch:
  compact result
  expanded activity
```

These settings affect rendering only.

They must not change:

- what was captured;
- branch ancestry;
- continuation identity;
- context compilation;
- tool execution;
- provider execution.

Changing a presentation mode never reruns work.

---

## 16. Navigation and Reply Anchors Use Stable Session Identity

A user-facing row number, terminal cursor position, scroll offset, indentation level, or current rendering mode is never a continuation identity.

When the user chooses a historical reply point, the TUI resolves that row to a stable semantic session object/continuation anchor.

Changing presentation detail may add or remove visual rows without changing the selected continuation target.

The application/session layer, not the TUI, decides how context is compiled for that continuation anchor.

---

## 17. New Activity Is Placed Structurally, Not Appended by Time

The UI must not treat the conversation as an append-only list.

When a child branch or historical continuation produces new activity, the view recomputes a deterministic tree projection and places that activity beneath its semantic parent.

Creation time and event sequence remain useful for ordering siblings and activity where the session model defines them, but wall-clock append position is not the canonical layout rule.

This applies equally to:

- user-created continuations;
- agent-created children;
- recursively delegated grandchildren;
- repair branches;
- validation branches;
- alternative implementations.

---

## 18. Guiding Example

A useful complete mental model is:

```text
Root: Add PHP ingestion
|
+-- Discover architecture
|   +-- inspect code-domain conventions
|   +-- inspect project import dispatch
|   `-- Result: required extension points
|
+-- Implement PHP adapter
|   |
|   +-- Create parser module
|   |   +-- draft implementation
|   |   +-- repair syntax/API mismatch
|   |   `-- Result: parser module validated
|   |
|   +-- Add adapter registration
|   |   `-- Result: scanner/import dispatch updated
|   |
|   +-- Write focused tests
|   |   `-- Result: domain tests pass
|   |
|   `-- Result: validated implementation candidate
|
+-- End-to-end validation
|   `-- Result: PHP onboarding fixture passes
|
`-- Root result: PHP ingestion candidate ready for review
```

The root model does not need every operation under every descendant.

The implementation child does not need the architecture child's raw tool transcript once it has the architecture result.

The test-writing child does not need the parser-writing child's syntax-correction dialogue once it has the validated parser source and result handles.

The complete histories remain durable and inspectable for provenance, debugging, audit, and later reopening.

---

## 19. Product-Surface Invariant

CLI, TUI, web, server clients, and future agents must agree on the same branch topology and compact-result semantics.

The TUI may offer the richest immediate visualization, but it does not own recursive decomposition.

The runtime may create branches autonomously, but it does not own their canonical meaning.

The session domain stores the tree, the runtime orchestrates work within it, the context compiler selects what each branch sees, and product surfaces render and navigate the resulting shared semantics.

---

## 20. Non-Negotiable Summary

Future design and implementation work should preserve these rules:

1. A session is a graph/tree, not a transcript log.
2. Branches are context-isolation boundaries for focused work.
3. Agents are expected to create branches recursively when useful.
4. Users and agents use the same branch model.
5. Atomic tool calls may remain inside a branch; independent reasoning loops belong in child branches.
6. A child receives selected parent context, not the complete parent transcript.
7. A parent normally receives `BranchResult`, not the complete child transcript.
8. Siblings communicate through semantic state/results, not inherited conversational noise.
9. Full child history remains durable and inspectable by reference.
10. Context compilation is independent from UI expansion and verbosity.
11. The default TUI renders the same recursive tree, with completed children compact by default and expandable on demand.
12. New activity is inserted at its structural location, not blindly appended by wall-clock time.
13. Vertical depth rails are derived presentation of ancestry, not canonical data.
14. User reply anchors are stable session identities and use the same tree as autonomous agent delegation.
15. No product surface may rebuild these semantics independently.
