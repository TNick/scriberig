# Recursive Agent Decomposition and Context Isolation

## 1. Purpose

Scriberig sessions are trees because agent work is recursively decomposed into focused units whose internal reasoning/tool activity should not automatically pollute the context of parents, siblings, later workers, or the long-running coordinator.

This document makes that principle explicit and easy to reference. It refines, but does not replace:

1. `009. agent interaction and sessions.md`;
2. `014. agent native semantic self hosting.md`;
3. `015. terminal user interface principles.md`;
4. `016. model driven agent execution and branch isolation.md`;
5. `018. durable plans dependency scheduling and multi-model execution.md`;
6. `019. semantic agent operations and projection-first editing.md`;
7. `design/level-2/023. agent runtime model provider and branch orchestration.md`.

The controlling rule is:

> A branch is a context-isolation boundary for one focused goal. It may perform arbitrary model/semantic-operation/tool back-and-forth and may recursively create children. Its parent normally receives only a compact result, exact semantic handles, validation/candidate references, and the small amount of information needed to continue.

A branch is not primarily a visual indentation feature and it is not primarily a user-created chat fork. User continuations, agent delegation, planned work, retries, focused semantic edits, research, validation, conflict resolution, and alternative attempts all use the same branch model.

---

## 2. Why the Session Is a Tree

A linear transcript forces every later model step to inherit noise from all earlier work. That is acceptable for short chats but scales poorly for implementation work.

Consider a root goal:

```text
Implement feature X
```

A semantic agent may decompose it into work such as:

```text
Root: Implement feature X
|
+-- Understand architecture
|
+-- Implement parser capability
|   |
|   +-- Decide semantic structure
|   +-- Create/update module/function entities
|   +-- Repair semantic/API incompatibilities
|   +-- Validate candidate projection
|
+-- Add tests against the completed semantic result
|
+-- Integrate sibling candidates
|
+-- Validate feature
```

The parser branch may require many model invocations, semantic reads, semantic edits, child branches, compiler diagnostics, corrections, and local validation. The later test-writing task does not need that conversational history. It needs the completed semantic result, exact handles/revisions, candidate/workspace state, public behavior, relevant decisions, and validation evidence.

The root also does not need the full implementation dialogue. It needs a compact result equivalent to:

```text
Parser capability implemented.
Touched semantic entities: Module M, Function F1, Function F2.
Candidate: C18.
Validation: passed.
Relevant source projection: src/php/parser.rs.
```

The tree exists so detailed work can remain durable and inspectable without becoming permanent context for unrelated later work.

---

## 3. Branches May Be Created by Humans, Agents, Plans, or Runtime Policy

Do not treat human-created forks as a special branch architecture.

A branch may begin because:

- the user chooses to continue from an earlier replyable session location;
- the current agent delegates a focused subtask;
- `/plan` materializes or starts a planned node;
- a branch-producing semantic tool contract starts isolated work;
- the runtime isolates a speculative mutation or retry;
- validation failure triggers a repair branch;
- the agent compares alternatives in sibling branches;
- two different model profiles are asked to attempt the same goal independently;
- conflict resolution requires focused work;
- a child agent recursively decomposes its own task.

The same canonical branch semantics apply in every case.

Origin, assignment, model/provider, plan membership, and coordinator/worker role are useful provenance. They must not create incompatible kinds of session trees.

---

## 4. Recursive Decomposition Is Expected Behavior

A model-driven agent is expected to decompose work when doing so improves context quality, isolation, validation, recoverability, scheduling, parallelism, or semantic scope.

A child branch may create another child branch using the same rules. There is no architectural distinction between the first delegation level and deeper delegation levels.

Conceptually:

```text
Root task
|
+-- Child A
|   |
|   +-- Grandchild A1
|   |   |
|   |   +-- Great-grandchild A1a
|   |
|   +-- Grandchild A2
|
+-- Child B
```

Runtime budgets may limit depth, child count, token use, cost, operation count, or elapsed time. Those limits are execution policy. They do not change the semantic fact that branches may nest recursively.

---

## 5. Atomic Operations and Branch-Producing Work Are Different

Do not create a branch for every small operation.

An atomic operation can remain inside the current branch when it does not need an independent reasoning loop. Examples include:

```text
inspect one semantic entity
list one bounded child collection
follow one relation page
query one bounded semantic fact
render one selected source/document fragment
read one operation status
apply one small capability-scoped semantic operation whose result is immediately known
```

Create or delegate to a child branch when the work can require its own model/operation loop, speculative state, retries, validation, reconciliation, merge, or further decomposition. Examples include:

```text
implement one semantic module/capability
edit one complex function
investigate a failing validation
reconcile an ambiguous projection
research one architectural question
compare alternative implementations
resolve a semantic merge conflict
validate and repair a candidate
```

This distinction prevents branch explosion while preserving context isolation where it matters.

---

## 6. Semantic Operations Are the Normal Work Primitive

For understood domains, branch activity should primarily use semantic knowledge and domain operations rather than generic raw file manipulation.

A branch working on source code may operate on:

```text
Module
Type
Function
Parameter
CodeGroup
Statement
Expression
Comment
```

A branch working on Markdown may operate on:

```text
Document
Section
Paragraph
List
Table
TableRow
TableCell
```

Typical operations are semantic/capability driven:

```text
inspect
list
follow
find
query
render
code.add_function
code.insert_statement
code.replace_expression
document.insert_paragraph
validate
```

Source files and documents are projections of canonical semantic state. Raw write and shell capabilities remain fallback/bootstrap/interoperability/validation mechanisms as defined by `019. semantic agent operations and projection-first editing.md`.

Do not describe branch isolation as though its ordinary purpose were to hide a sequence of `write_file` and `bash` calls. Its ordinary purpose is to hide local semantic implementation detail while returning exact semantic results.

---

## 7. Child Context Is Selected, Not Copied

Creating a child branch does not copy the complete parent transcript.

The child receives an explicit inheritance plan containing only the information required for its goal. Depending on the task, that may include:

```text
child purpose and expected result
parent branch descriptor
selected parent result handles
fulfilled plan dependency results
accepted decisions or constraints
semantic selection and exact snapshot/workspace
specific entity/revision handles
candidate/workspace handles
capability subset
agent/model profile and branch policy
explicit delegation instruction
small bounded parent excerpt when policy deliberately allows it
```

Unrelated parent activity is omitted.

This is important in both directions:

- the child does not automatically inherit all parent history;
- the parent does not automatically inherit all child history.

Context construction is a projection over session knowledge, plan/dependency results, and project semantic knowledge—not transcript concatenation.

---

## 8. Branch Completion Produces a Compact Contract

A completed branch produces a durable `BranchResult` or an explicit no-result/failure outcome.

A useful result contains concepts equivalent to:

```text
branch identity
status
short outcome summary
result kind
important semantic handles and exact revisions
produced candidate/migration/workspace handles
important touched entities
projection/materialization references when relevant
validation handles
unresolved questions
failure summary when unsuccessful
```

The result is the normal information boundary between parent and child and the normal fulfillment artifact for plan dependencies.

The full child history remains stored and inspectable by stable reference. It can be reopened if the result is insufficient, but it is not implicitly inserted into the parent's next model request.

---

## 9. Parent Context Uses Results, Not Child Transcripts

After a child finishes, the parent normally continues with context equivalent to:

```text
current parent goal
recent parent-local activity
child descriptor
child BranchResult
relevant semantic project/candidate state
selected completed child/dependency results
```

It does not normally receive:

```text
every child model response
every child tool/semantic-operation invocation
every failed semantic edit attempt
every compiler diagnostic already resolved
every correction step
every grandchild transcript
raw provider streams
```

The omitted history remains available for audit and inspection.

This is the principal mechanism that prevents a long implementation session from degrading into an ever-growing prompt.

---

## 10. Sibling Branches Communicate through Results and Semantic State

Sibling tasks should not depend on one another's internal conversational history.

For example:

```text
Root: implement feature
|
+-- Child A: implement parser capability
|     -> BranchResult: semantic handles + candidate + validation
|
+-- Child B: write parser tests
```

Child B may receive the result of Child A, exact created/updated semantic state, relevant dependency handles, and design constraints. It does not need the back-and-forth that Child A used to arrive there.

If Child B discovers a defect, it may create/request another focused repair branch. That repair branch returns a new result rather than causing all previous implementation history to be copied into Child B's permanent context.

---

## 11. User Continuations Use the Same Tree

A user may navigate to a historical replyable node and continue from that semantic location.

That continuation is another branch operation over the same session graph. It is not a separate chat-fork mechanism.

The context compiler resolves the exact continuation location and constructs context from the branch path, semantic state, decisions, and results relevant to that point. Later sibling work is not silently injected merely because it occurred later in wall-clock time.

The default user behavior may continue from the current root/coordinator position so ordinary use feels fluid, but the canonical session remains tree-shaped.

---

## 12. Plans Reuse the Branch Tree but Add Dependency Edges

`/plan` creates durable planned work that is shown in the same tree used by executed branches.

Structural parent/child relations still mean context ownership and decomposition.

Plan dependencies are separate edges that mean execution ordering/readiness.

Conceptually:

```text
Root
  Parser
  Importer
  Integration

Dependencies:
  Integration depends_on Parser
  Integration depends_on Importer
```

Do not fake dependencies by nesting siblings under one another.

A planned node can be visible before its branch executes. When execution begins, it becomes or binds to the branch that owns the work.

The complete scheduling model is defined by `018. durable plans dependency scheduling and multi-model execution.md`.

---

## 13. Multiple Models Share the Same Tree

Different branches may be assigned to different model/provider profiles.

For example:

```text
Discover architecture   -> local model
Implement parser        -> OpenAI/Codex profile
Research edge cases     -> OpenRouter profile
Documentation           -> local inexpensive profile
```

This does not create separate sessions.

One plan has at most one auto-advancing coordinator, but many workers may execute ready branches concurrently.

One branch normally has one active executing owner. If two models should independently attempt the same goal, create sibling attempt branches and compare their results explicitly.

---

## 14. Plan Dependencies Carry Compact Results, Not Transcripts

A dependent node should become ready because required result contracts were fulfilled, not because predecessor output happened earlier in a transcript.

For example:

```text
ParserImplementationResult
  Function parse_type @ R22
  Function parse_union_type @ R1
  Candidate C18
  Validation V7
```

may satisfy the dependency of a test branch.

That test branch does not inherit the parser worker's model/tool history.

This makes dependency edges useful context declarations as well as scheduling constraints.

---

## 15. Branch Tree, Plan Dependency Graph, Knowledge Graph, and Activity Causality Are Distinct

Four different structures coexist:

### Session branch tree

```text
root task
  child task
    grandchild task
```

### Plan dependency graph

```text
A ----\
       -> C
B ----/
```

### Semantic knowledge graph

```text
Project -> Module -> Function -> Statement -> Expression
```

### Local execution/activity causality

```text
model invocation
  semantic operation/tool invocation
    operation/tool result
  model invocation
  branch result
```

Do not collapse these into one canonical relation.

A UI may combine them into one visual tree, but it must preserve the underlying meanings.

---

## 16. The Default TUI Is a Tree-Aware Conversation Projection

The default TUI should feel like a conventional coding-agent conversation while faithfully representing recursive agent decomposition, planned work, dependencies, assignments, and user continuations.

Normal root interaction may look nearly linear when no branching is visible.

When the agent or plan creates focused children, the TUI inserts them structurally at the location where they belong rather than appending them only by timestamp.

A compact completed child may render like:

```text
▏ Implement parser capability
▏ ✓ parser entities created and validated
```

An active/expanded child may reveal its internal activity:

```text
▏ Implement parser capability
▏
▏ ▏ inspect Function parse_type
▏ ▏ ✓ 4 code groups
▏
▏ ▏ replace expression in nullable-suffix group
▏ ▏ ✓ Expression E17 -> Revision R9
▏
▏ ▏ Validate parser candidate
▏ ▏ ▏ cargo test -p scriberig-domain-php ...
▏ ▏ ▏ ✓ 12 tests passed
▏
▏ ✓ parser capability implemented
```

The external `cargo test` is displayed as a shell-like process because it actually is one. Semantic edits are displayed as semantic operations.

The fact that the UI can expand the child does not mean the parent model received the expanded history.

---

## 17. Depth Rails Encode Structural Nesting

Terminal presentation should encode branch/activity nesting with visible vertical rails.

Conceptually:

```text
▏ depth 1
▏ ▏ depth 2
▏ ▏ ▏ depth 3
```

Each depth uses a stable theme color from a finite palette. The palette may cycle at deep levels.

Color is supplemental. Nesting must remain understandable through rail count/position when color is unavailable.

For narrow terminals, older ancestor rails may be compacted with an explicit marker such as:

```text
… ▏ ▏ deeply nested activity
```

Do not persist depth color or indentation as semantic state. Derive them from branch/activity ancestry.

---

## 18. Completed Children Are Compact by Default, Expandable on Demand

The ordinary conversation projection should prefer attention-efficient presentation.

Recommended behavior:

- planned node: compact state/assignment/dependency indicator;
- active branch: show enough live activity to understand progress;
- completed child branch: collapse to descriptor + result by default;
- failed child branch: show compact failure result and status;
- selected/expanded child: render retained detail on demand;
- parent branch: continue after the compact child result without reproducing child history.

Expansion is presentation state only.

Collapsing or expanding a branch must not change model context, branch semantics, durable plan state, or result dependencies.

---

## 19. Per-Activity Presentation Is Independent from Context

Each visible activity/message kind may have its own client presentation policy.

Examples include:

```text
semantic/tool invocation:
  hidden
  compact/truncated
  full one-line/wrapped
  structured parameters one per line

tool/operation result:
  hidden
  summary
  preview
  full bounded detail

reasoning summary:
  hidden
  shown

model request/prompt:
  hidden
  summary
  structured full

branch:
  compact result
  expanded activity

plan node:
  compact
  dependencies/assignment detail
```

A compact semantic invocation may look like:

```text
▏ add function parse_union_type to php::parser
```

A structured version may look like:

```text
▏ code.add_function
▏   module: php::parser
▏   after: parse_named_type
▏   name: parse_union_type
```

An actual process invocation may use shell-command formatting.

These settings affect rendering only. They must not change captured activity, ancestry, continuation identity, context compilation, tool execution, provider execution, or scheduling.

---

## 20. Navigation Cursor, Reply Anchor, and Coordinator Cursor Are Distinct

A user-facing row number, terminal cursor position, scroll offset, indentation level, or current rendering mode is never a continuation identity.

The TUI needs three distinct concepts:

```text
navigation cursor
  where the user is browsing

reply anchor
  where the next human message will attach

coordinator cursor
  where the single auto-advancing plan coordinator is currently operating/evaluating
```

Normally the reply anchor may auto-follow the coordinator cursor while the user is idle.

When the user deliberately selects a historical/sibling node or starts typing against it, the reply anchor becomes pinned. Coordinator progress must not move it underneath an in-progress draft.

All anchors resolve to stable session/plan identities, never terminal row numbers.

---

## 21. The Reply Anchor Is Visually Distinct

The current reply anchor should use a background highlight or equivalent strong focus treatment.

Depth rail color must not double as reply-anchor state.

The background answers:

```text
Where will my next message attach?
```

The rails answer:

```text
What structural ancestry does this content have?
```

The composer may show a compact `Replying to ...` label when the anchor is not the ordinary current/coordinator head.

Important state must not depend on color alone.

---

## 22. New Activity Is Placed Structurally, Not Appended by Time

The UI must not treat the conversation as an append-only list.

When a planned branch, autonomous child, historical user continuation, worker result, or nested repair branch produces new activity, the view recomputes a deterministic tree projection and places that activity beneath its semantic parent.

Creation time and event sequence remain useful for ordering siblings/activity where the session model defines them, but wall-clock append position is not the canonical layout rule.

This applies equally to:

- user-created continuations;
- agent-created children;
- planned nodes and their later execution;
- recursively delegated grandchildren;
- repair branches;
- validation branches;
- alternative model attempts;
- concurrent worker results.

---

## 23. Auto-Follow Is Presentation State

When a long-running plan is active, the TUI may automatically keep the viewport near the coordinator cursor.

Recommended behavior:

```text
user idle -> follow coordinator
user scrolls/selects -> pause follow
user explicitly resumes follow -> follow coordinator again
```

This is presentation state only. It has no effect on scheduling or context.

## 24. Guiding Example

A synchronized mental model is:

```text
Root: Add PHP ingestion
|
+-- Discover architecture                     [local-fast]
|   +-- inspect code-domain conventions
|   +-- inspect project import registry
|   `-- Result: required semantic extension points
|
+-- Implement PHP adapter                     [OpenAI profile]
|   |
|   +-- Add PHP syntax/domain entities
|   |   +-- create/update semantic schema nodes
|   |   +-- create parser functions/code groups
|   |   `-- Result: parser semantic candidate
|   |
|   +-- Register adapter
|   |   `-- Result: source-domain registry candidate
|   |
|   +-- Validate parser
|   |   +-- materialize candidate projection
|   |   +-- external compiler/test validation
|   |   `-- Result: validation evidence
|   |
|   `-- Result: validated adapter candidate
|
+-- Research PHP edge cases                   [OpenRouter profile]
|   `-- Result: accepted edge-case constraints
|
+-- Add tests                                 [local/other profile]
|   depends_on: adapter result, research result
|   `-- Result: semantic test entities + validation
|
+-- Integration
|   depends_on: adapter, tests
|   `-- Result: merged candidate
|
`-- Root result: PHP ingestion candidate ready for review
```

The root model does not need every operation under every descendant.

The test branch receives exact adapter/research results, not their transcripts.

The complete histories remain durable and inspectable for provenance, debugging, audit, and later reopening.

---

## 25. Product-Surface Invariant

CLI, TUI, web, server clients, and future agents must agree on the same branch topology, plan-node identities, dependency results, semantic handles, compact-result semantics, and execution assignments.

The TUI may offer the richest immediate visualization, but it does not own recursive decomposition, plan scheduling, semantic editing, or model assignment.

The session domain stores the tree; the plan subsystem records intended work/dependencies; the runtime orchestrates branch execution; the semantic application/domain layers own reads and mutations; the context compiler selects what each branch sees; product surfaces render and navigate the resulting shared semantics.

---

## 26. Non-Negotiable Summary

Future design and implementation work must preserve these rules:

1. A session is a graph/tree, not a transcript log.
2. Branches are context-isolation boundaries for focused work.
3. Agents are expected to create branches recursively when useful.
4. Users, plans, agents, and runtime policy use the same branch model.
5. Atomic semantic operations may remain inside a branch; independent reasoning loops belong in child branches.
6. Known source/document work is semantic-first; raw file/shell primitives are fallback/runtime mechanisms.
7. A child receives selected parent/dependency context, not the complete parent transcript.
8. A parent normally receives `BranchResult`, not the complete child transcript.
9. Siblings communicate through semantic state/results, not inherited conversational noise.
10. Plan dependencies are separate from branch parentage and are satisfied by durable results.
11. Many model profiles may execute different branches; one plan has one auto-advancing coordinator.
12. Full child history remains durable and inspectable by reference.
13. Context compilation is independent from UI expansion and verbosity.
14. The default TUI renders the same recursive/planned tree, with completed children compact by default and expandable on demand.
15. New activity is inserted at its structural location, not blindly appended by wall-clock time.
16. Vertical depth rails are derived presentation of ancestry, not canonical data.
17. Navigation cursor, reply anchor, and coordinator cursor are distinct stable concepts.
18. The current reply anchor uses a strong visual highlight separate from rail colors.
19. Per-activity detail modes are presentation only and include semantic-operation-specific forms.
20. No product surface may rebuild these semantics independently.
