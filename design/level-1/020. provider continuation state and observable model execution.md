# Provider Continuation State and Observable Model Execution

## 1. Purpose

Scriberig owns canonical session identity, branch topology, context isolation, semantic state, plans, dependencies, model assignments, migrations, and durable history.

Model providers may additionally offer their own server-side continuation mechanisms. Examples include durable conversation objects, previous-response chains, cached reasoning state, or local-runtime session handles.

Scriberig should use those mechanisms when they improve continuity, latency, or provider reasoning quality, but it must never confuse provider state with Scriberig state.

The controlling rules are:

> Provider continuation is branch-local execution state. It is an optimization and continuity mechanism attached to a Scriberig branch, never the canonical identity of the session or branch.

and:

> The user may independently inspect the complete safe effective request Scriberig provided to a model and the provider-visible reasoning content produced around tool/semantic operations, without rerunning the model and without exposing hidden chain-of-thought.

## 2. Scriberig Identity Is Canonical

The canonical identities remain Scriberig-owned concepts such as:

```text
SessionId
BranchId
ContinuationAnchor
PlanId
PlanNodeId
OperationId
ModelInvocationId
BranchResultId
SnapshotId
EntityId
```

A provider conversation identifier such as an OpenAI conversation ID is not interchangeable with any of these.

Provider identity cannot be canonical because:

- one Scriberig session may use several providers;
- sibling branches may use different providers simultaneously;
- one branch may switch providers over time;
- a local model may expose no remote session identifier;
- provider state may expire, be deleted, become unavailable, or be administratively inaccessible;
- Scriberig must reconstruct context after restart independently of one provider;
- plans, dependencies, migrations, semantic handles, and branch results are not provider-owned state.

The loss of provider continuation state may reduce efficiency or continuity quality, but it must not make a Scriberig session unrecoverable.

---

## 3. Provider Continuation Is Branch-Local

Provider continuation state belongs to one isolated execution lineage.

The normal mapping is conceptually:

```text
Scriberig Session
|
+-- Root Branch
|     provider continuation A
|
+-- Child Branch: implement parser
|     provider continuation B
|     |
|     +-- Grandchild: validate parser
|           provider continuation C
|
+-- Child Branch: research edge cases
      provider continuation D or none
```

Do not normally attach one provider conversation to the whole Scriberig session tree.

Doing so would reintroduce exactly the context pollution that recursive branch isolation is intended to prevent: detailed work from one child would become implicit provider context for unrelated siblings and their parent.

A new child branch therefore normally receives a newly established provider continuation seeded from the child's compiled Scriberig context rather than inheriting the parent provider conversation wholesale.

---

## 4. Provider-Neutral Continuation State

Scriberig should represent provider continuation through a provider-neutral contract conceptually equivalent to:

```text
ProviderContinuationState
  provider profile
  provider kind
  opaque continuation handle
  branch
  context fingerprint
  state revision/version when available
  created-at provenance
  last-used invocation
  validity/status
  provider-specific non-secret metadata
```

The exact provider handle remains opaque outside the provider/runtime boundary.

Examples may include:

```text
OpenAI Conversation ID
OpenAI previous response ID
OpenRouter/provider-specific continuation token
local model runtime session ID
none
```

Credentials, authorization headers, secret connection values, and provider-private hidden reasoning must never be stored in this state.

---

## 5. Context Fingerprint Guards Reuse

A provider continuation may only be reused when it still represents the exact Scriberig context lineage expected by the branch.

Scriberig therefore binds continuation state to a context fingerprint or equivalent immutable context identity.

Conceptually:

```text
compiled branch context C1
    -> fingerprint H1
    -> provider continuation P1
```

Before reusing `P1`, the runtime compares the expected continuation context against `H1` or a derived successor relationship.

If branch history changes outside that provider continuation, for example:

```text
OpenAI invocation
local-model invocation
user historical continuation
manual semantic change
branch rebase
accepted dependency result changes
```

then blindly resuming the old provider continuation may produce incorrect context.

The runtime must detect the divergence and either:

- seed a new provider continuation from the current canonical Scriberig context;
- use an explicit provider fork when semantically equivalent and supported;
- fall back to stateless request construction.

Provider continuation is therefore a cache-like stateful acceleration layer, not an authority.

---

## 6. New Child Branches Start from Selected Context

When Scriberig creates an isolated child branch, it first compiles child context using normal context-isolation rules:

```text
child purpose
expected result
selected ancestor BranchResults
fulfilled dependency results
accepted decisions and constraints
semantic scope and exact snapshot/workspace
relevant semantic handles
bounded explicit parent excerpts when policy allows
capability/tool catalog
resolved execution assignment
```

Only after this context exists does the provider adapter establish provider continuation state.

The direction of authority is:

```text
Scriberig branch/context compiler
        |
        v
canonical effective request/context
        |
        v
provider continuation initialization
```

Never reverse that relationship by asking the provider conversation to define the branch's canonical context.

---

## 7. Same-Branch Continuation May Reuse Provider State

Within one branch, later invocations may reuse compatible provider continuation state instead of retransmitting every previous provider-visible item.

This is especially useful for providers that preserve tool/reasoning state internally.

The runtime still records each Scriberig `ModelInvocation` separately with:

- exact branch identity;
- model/provider/profile/thinking configuration;
- canonical effective request identity;
- continuation state used;
- provider request/response IDs when safe;
- observable activity sequence;
- result/output identity.

Provider continuation does not collapse several model invocations into one Scriberig historical object.

## 8. OpenAI Continuation Strategy

As of October 2026, OpenAI's Responses ecosystem exposes two relevant continuation mechanisms.

### 8.1 Conversations API

A Conversation is a durable server-side object with its own identifier and persistent items. It can be reused across sessions, devices, or jobs.

For Scriberig, a Conversation is well suited to long-lived continuation within one isolated branch.

Recommended default mapping when supported:

```text
one isolated Scriberig branch execution lineage
    -> one OpenAI Conversation
```

A child branch normally receives another Conversation initialized from the child's selected Scriberig context.

### 8.2 `previous_response_id`

Responses may also continue or fork from a previous response ID.

This is useful for shorter response chains or provider-side forks where Scriberig can prove that the response lineage corresponds exactly to the intended branch/continuation context.

The runtime must remember that provider top-level instructions are not implicitly carried forward by `previous_response_id`; Scriberig still owns and supplies the effective instruction/context contract required for each invocation.

### 8.3 Do not mix mechanisms accidentally

OpenAI currently does not allow `conversation` and `previous_response_id` on the same response request.

The OpenAI adapter therefore chooses one continuation strategy deliberately for a given invocation and records that choice in safe provenance.

### 8.4 OpenAI retention is not Scriberig durability

OpenAI Conversation items may be persisted beyond the ordinary stored-response lifetime. Scriberig must still retain enough canonical state to reconstruct the branch without depending on that provider retention policy.

Provider retention policy is external behavior, not a Scriberig persistence guarantee.

## 9. Multi-Provider and Provider-Switching Branches

A session tree may contain concurrent branches such as:

```text
Architecture       -> local model
Parser             -> OpenAI
Research           -> OpenRouter model
Integration        -> OpenAI with another profile
Documentation      -> local model
```

Each branch resolves its own provider continuation independently.

If a branch switches providers, the new provider receives a newly compiled canonical Scriberig context unless an explicitly supported cross-provider representation can prove equivalence.

A provider continuation from provider A is never passed as opaque state to provider B.

The canonical bridge between providers is Scriberig state:

```text
semantic state
branch-local history
BranchResults
dependency results
accepted decisions
canonical effective request projection
```

## 10. Complete Effective Model Request Is Observable

The user may choose to inspect the complete safe effective request that Scriberig supplied to a model invocation.

This requirement is stronger than retaining a bounded activity summary and stronger than displaying the literal HTTP request body.

The canonical observable request is the provider-neutral Scriberig request immediately before provider-specific serialization.

Conceptually:

```text
CanonicalModelRequest
  invocation identity
  branch/continuation anchor
  instructions
  ordered conversation/context sections
  selected ancestor results
  dependency results
  semantic/context projections
  tool/semantic capability definitions
  structured-output schema when present
  resolved model/provider/profile
  thinking level
  safe generation configuration
  continuation-state reference and strategy
  optional token/cost estimates
```

The exact structure may use typed sections/messages rather than these literal fields.

Secrets and sensitive values are redacted before this representation reaches public/session/protocol layers.

---

## 11. Full Prompt Means Effective Context, Not Wire JSON

When provider continuation is used, the literal network request may contain only new input plus a provider continuation ID.

That does not mean the model effectively saw only the new input.

Therefore `PromptPresentation::Full` means:

> Show the complete safe effective Scriberig model request/context for this invocation, including the prior context represented by provider continuation state.

It does not mean:

> Dump the raw outbound provider HTTP payload.

A debug/audit artifact may optionally expose sanitized provider-wire information separately, but it is not the canonical prompt view.

This distinction is required for:

- auditing;
- provider portability;
- deterministic context tests;
- debugging context isolation;
- reconstructing history after provider state disappears;
- comparing two providers on equivalent input.

---

## 12. Prompt Capture and Prompt Presentation Are Separate

The runtime should capture or durably reference the complete safe canonical request once per invocation.

Clients then choose independently how to render it.

Recommended presentation modes are conceptually:

```text
PromptPresentation
  Hidden
  Summary
  Full
```

`Summary` may show counts, major context sections, model identity, and token estimate.

`Full` resolves the complete safe canonical request without rerunning the model.

Changing prompt presentation never:

- changes model execution;
- changes context compilation;
- creates a model invocation;
- changes provider continuation;
- mutates semantic session history.

---

## 13. Provider-Visible Reasoning Is Ordered Activity

Some models/providers expose user-visible reasoning summaries or reasoning content. Other models keep reasoning hidden.

Scriberig may capture only reasoning content that the provider explicitly exposes for user/application consumption.

Reasoning must be represented as ordered activity because it may appear:

```text
before a tool call
between tool calls
after a tool result
before final output
interleaved repeatedly throughout one invocation
```

For example:

```text
ModelInvocation
  ReasoningSegment 1
  SemanticOperation A
    OperationResult A
  ReasoningSegment 2
  ToolInvocation B
    ToolResult B
  ReasoningSegment 3
  AssistantOutput
```

Do not collapse all reasoning into one branch-level blob when the provider exposes meaningful ordered segments.

---

## 14. Hidden Chain-of-Thought Is Never Requested or Exposed

`Show thinking` must not be interpreted as a request to obtain private hidden chain-of-thought.

Allowed observable reasoning includes:

- Scriberig runtime phases/status;
- provider-provided reasoning summaries intended for display;
- provider-provided reasoning content explicitly surfaced through the API as user/application-visible output;
- structured plan/status information generated as normal visible output.

Disallowed behavior includes:

- requesting hidden chain-of-thought merely so it can be shown;
- inferring private reasoning from provider internals;
- persisting encrypted/private reasoning blobs as user-readable trace;
- claiming hidden reasoning is available when the provider exposes only a summary.

A provider may internally preserve hidden reasoning across continuation calls. That internal state is provider execution state, not Scriberig-visible reasoning.

---

## 15. Reasoning Capture and Presentation Are Independent

When provider-visible reasoning exists, Scriberig preserves its ordering and stable invocation association independently from whether the current client shows it.

Recommended presentation modes are conceptually:

```text
ReasoningPresentation
  Hidden
  Summary
  FullAvailable
```

`FullAvailable` means the complete reasoning content that the provider explicitly made available for display. It does not imply hidden chain-of-thought exists or can be retrieved.

A provider that exposes only summaries may map both `Summary` and `FullAvailable` to the best safe available representation while declaring the limitation explicitly.

Changing reasoning presentation does not rerun work.

---

## 16. Prompt and Reasoning Controls Are Independent

Prompt visibility and reasoning visibility are orthogonal.

These are all valid client configurations:

```text
prompt: Full
reasoning: Hidden
operations: Compact
results: Summary
```

```text
prompt: Hidden
reasoning: FullAvailable
operations: StructuredParameters
results: FullBounded
```

```text
prompt: Summary
reasoning: Summary
operations: Hidden
results: Hidden
```

No global `trace_level` may replace the independent controls.

Presets may set several controls at once, but the underlying values remain independent and individually editable.

---

## 17. Capture Once, Render Many Ways

The architecture should be:

```text
model/provider execution
        |
        +-- canonical safe effective request
        +-- provider-visible reasoning segments
        +-- semantic/tool invocations
        +-- operation/tool results
        +-- assistant output
        |
        v
ordered durable/observable activity
        |
        +-- prompt presentation
        +-- reasoning presentation
        +-- invocation presentation
        +-- result presentation
        +-- branch/plan presentation
        |
        v
TUI / web / API clients
```

Presentation is disposable and client-local or user-preference state.

Execution provenance and safely observable model activity remain durable or durably retrievable according to retention policy.

---

## 18. Activity Ordering and Causality

Reasoning segments, tool/semantic operations, results, and final output must share deterministic invocation-local order.

Store or derive concepts equivalent to:

```text
activity id
invocation id
branch id
sequence/ordinal
parent/correlation id when causal nesting exists
activity kind
lifecycle state
safe content/ref
```

Do not derive interleaving solely from wall-clock timestamps.

The branch tree and activity causality remain separate structures. A UI may combine them visually, but one does not replace the other.

---

## 19. Provider Continuation and Context Isolation

Provider continuation must preserve the same isolation rules as the Scriberig context compiler.

A provider must not accidentally see:

- sibling branch transcripts;
- unrelated completed child transcripts;
- later historical continuations;
- other plan-node activity merely because it shares one user session;
- model activity from a different provider assignment unless Scriberig explicitly includes its compact result/context.

Tests must prove this for provider-state reuse as well as stateless requests.

A continuation mechanism that cannot preserve branch isolation must be disabled for that execution path.

---

## 20. Reconnect and Restart

On restart, Scriberig restores canonical branch/session/plan state first.

Provider continuation state may then be classified as:

```text
reusable
stale
disconnected/unavailable
expired/deleted
unknown
```

If reusable, the runtime may resume it.

Otherwise the next invocation recompiles canonical Scriberig context and establishes new provider state.

The UI must not need provider stream replay to reconstruct settled conversation/activity history.

---

## 21. Security and Privacy

Never store or expose in canonical prompt/activity records:

```text
API keys
Authorization headers
resolved credential values
secret environment variables
provider-private hidden reasoning
sensitive tool parameters that policy requires redacting
raw provider payloads containing secrets
```

Full prompt views are full **safe** effective requests.

Where redaction occurs, the view should preserve structure and mark redaction rather than pretending the value never existed.

Provider continuation handles themselves may be sensitive operational identifiers. Expose them in normal UI only when useful; protocols should treat them as opaque runtime metadata rather than user-authored semantic content.

---

## 22. Cross-Surface Contract

Embedded Rust callers, CLI, HTTP/server clients, TUI, web, and future external clients must agree on:

- Scriberig canonical session/branch identity;
- provider continuation state as secondary runtime metadata;
- effective request identity and safe retrieval;
- independent prompt/reasoning presentation controls;
- ordered provider-visible reasoning segments;
- provider/model invocation provenance;
- branch isolation semantics.

No product surface may reconstruct provider continuation semantics independently.

---

## 23. Required Conformance Scenarios

Implementations must eventually prove at least these scenarios.

### Same-branch OpenAI continuation

Two successive invocations in one branch reuse one compatible OpenAI Conversation or supported response chain while preserving two distinct Scriberig invocation records.

### Child branch isolation

Creating a child compiles selected child context and creates independent provider continuation. Child-private tool/reasoning history does not appear in the parent provider context.

### Sibling isolation

Two sibling branches using OpenAI receive independent provider state and cannot observe one another's transcripts except through explicitly supplied `BranchResult`s/dependency results.

### Provider switch

A branch runs first on OpenAI and then on a local model. Switching back to OpenAI detects that the old continuation no longer represents current branch context and reseeds or forks safely.

### Lost provider state

Provider continuation is unavailable after restart. Scriberig recompiles canonical context and continues correctly without losing session history.

### Full prompt with continuation

A provider request uses only a continuation ID plus new input on the wire. The user selects full prompt display and still sees the complete safe effective Scriberig context that invocation used.

### Independent prompt/reasoning controls

Prompt is shown full while reasoning is hidden; then reasoning is shown while prompt is hidden. Neither change reruns the invocation.

### Interleaved reasoning

A fake provider emits visible reasoning, semantic operation, result, more reasoning, another tool call, and final output. The shared activity projection preserves exact order when reasoning is shown and preserves operation order when reasoning is hidden.

### Hidden reasoning provider

A provider exposes no user-visible reasoning. `FullAvailable` clearly shows that no fuller provider-visible reasoning exists rather than exposing or inventing hidden chain-of-thought.

---

## 24. Non-Negotiable Summary

Future design and implementation work must preserve these rules:

1. Scriberig owns canonical session and branch identity.
2. Provider continuation state is secondary branch-local runtime state.
3. One provider conversation must not normally span unrelated Scriberig branches.
4. Child provider state is seeded from selected compiled child context.
5. Continuation reuse is guarded by exact context lineage/fingerprints.
6. Provider switching never transfers opaque provider state across providers.
7. Loss of provider continuation must not make Scriberig history unrecoverable.
8. OpenAI Conversations and `previous_response_id` are adapter strategies, not Scriberig domain concepts.
9. The canonical full prompt is the complete safe effective Scriberig request, not raw provider JSON.
10. Full prompt remains reconstructable/inspectable even when the provider manages prior state server-side.
11. Provider-visible reasoning may be interleaved with tool/semantic operations and must preserve ordering.
12. Hidden/private chain-of-thought is never requested or exposed.
13. Prompt and reasoning presentation controls are independent.
14. Changing presentation never reruns model/tool work.
15. Branch isolation must hold equally for stateless requests and provider-stateful continuation.
16. All product surfaces consume one shared continuation/observability contract.
