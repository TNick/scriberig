# Terminal User Interface Principles

## 1. Purpose

The Scriberig terminal user interface is a first-class product surface over the same semantic platform used by the CLI, API server, web editor, third-party clients, and agents.

It is not a second backend, a direct database browser that bypasses application rules, or a terminal-only implementation of semantic behavior.

This document specializes the product-surface principles from `design/level-1/011. runtime libraries protocol and product surfaces.md` for interactive terminal use. It defines durable interaction and architectural invariants. Concrete Rust modules, terminal libraries, key bindings, layout thresholds, command-line flags, and implementation tasks belong in Level 2 and Level 3.

The controlling rule is:

> The TUI makes Scriberig's semantic operations visible, navigable, and composable in a keyboard-first environment without creating a parallel semantic system.

---

## 2. Role of the TUI

The TUI is the native interactive workbench for users who want more continuity than one-shot CLI commands but do not need or cannot use the browser editor.

It should support the same broad classes of work as other product surfaces:

- inspect semantic entities and exact revisions;
- navigate relations, collections, and snapshots;
- search and query knowledge;
- inspect history and semantic diffs;
- inspect rendered projections and synchronization state;
- review branches, migrations, conflicts, validation, and trust evidence;
- navigate sessions and their nested branches;
- issue agent commands and observe operation progress;
- discover which operations are available for the current context.

The terminal presentation may be compact and keyboard-oriented, but the meaning of an operation must remain shared with the application layer.

---

## 3. TUI Invariants

Every lower-level TUI design and implementation must preserve these invariants.

### 3.1 Shared semantic operations

The TUI invokes application operations or a public client that exposes those operations. It must not implement storage queries, migration semantics, projection reconciliation, validation rules, session semantics, or agent mutation semantics itself.

### 3.2 Explicit semantic context

The interface must make important context visible rather than hiding it in process-global state. At minimum, users must be able to determine the active project or database context, branch or snapshot context, current selection, trust or validation state when relevant, and whether an operation is pending.

### 3.3 Stable semantic handles

Navigation is based on stable Scriberig handles and references, not terminal row numbers or backend record identifiers. A row may move after refresh without changing what it means.

### 3.4 Capability-driven actions

The TUI must not advertise mutations or privileged operations merely because a widget knows their names. Available actions are derived from application capability discovery and the current semantic context. A denied or unavailable action must remain denied or unavailable in the TUI.

### 3.5 No alternate mutation path

A TUI edit, branch action, migration application, projection reconciliation, session command, or agent action must pass through the same proposal, validation, conflict, trust, and snapshot-transition machinery used by other surfaces.

### 3.6 Presentation state is disposable

Pane focus, scroll offsets, expanded rows, filters, open overlays, and cached view models are TUI state. Canonical knowledge is not. Losing the terminal process may lose presentation state, but must not silently lose or corrupt committed semantic state.

### 3.7 Rendering is observational

Drawing the screen must not change canonical state, invoke hidden mutations, or perform semantic work whose result changes merely because a frame was rendered.

---

## 4. Semantic Navigation Before File Navigation

Scriberig is not fundamentally file-oriented, so the TUI must not reduce the product to a filesystem tree with an inspector attached.

A user should be able to move among semantic objects such as:

```text
project -> collection -> entity -> revision
entity -> relation -> related entity
entity -> history -> earlier revision
snapshot -> diff -> changed entity
session -> branch -> turn -> tool result
projection -> source entity -> synchronization state
operation -> result -> affected semantic object
```

Filesystem paths remain useful projection metadata and may be exposed when a domain uses them. They are not the universal navigation model.

The primary selection is therefore a semantic reference plus enough snapshot or branch context to interpret it.

---

## 5. Progressive Disclosure

The TUI must support progressive disclosure rather than showing every property, relation, provenance record, operation, and diagnostic at once.

The default flow is:

```text
summary -> inspect -> related knowledge -> history/diff -> provenance/trust -> operation
```

A compact summary should be cheap to render and should advertise useful next operations. Deeper inspection may request additional detail only when the user asks for it.

This principle is shared with agent interaction: both humans and agents should be able to begin with a small semantic handle and deliberately ask for more context.

---

## 6. One Selection, Several Views

The TUI may show the same selection through several views without inventing separate identities for each presentation.

For example, one selected entity may drive:

- a semantic inspector;
- relation and collection navigation;
- history;
- a diff against another revision;
- a rendered Markdown or source-code projection;
- provenance and trust evidence;
- contextual commands.

Changing the active view changes presentation, not the identity of the selected knowledge.

When a view introduces a comparison target, base snapshot, branch, or projection, that extra context must be explicit and visible.

---

## 7. Keyboard First, Discoverable, and Composable

The terminal interface is keyboard-first. Every core workflow must be usable without a mouse.

Keyboard-first must not mean mnemonic-only or undiscoverable. The interface must provide:

- contextual key hints for common actions;
- a searchable command or action palette;
- an always-available help surface;
- visible focus;
- clear indication when keys are captured by a text input or modal review.

Navigation commands and semantic operations should compose predictably. The same conceptual action should not use unrelated interaction patterns in different views without a strong reason.

Optional mouse support may improve convenience, but it must not be required to reach product functionality.

---

## 8. Review Before Canonical Change

Read operations may execute immediately. Canonical changes require explicit intent.

The TUI should make the transition from exploration to mutation visible. When an action can advance canonical state, the user should be able to inspect the proposed change, base context, conflicts, validation result, and important trust evidence before confirmation when those concepts apply.

Confirmation is not permission. Permission and capability checks belong to the application layer and remain authoritative even after a user confirms in the TUI.

A terminal prompt must never be used as a substitute for semantic validation or conflict detection.

---

## 9. Sessions and Agents Are Peers of Other Knowledge

Agent interaction is integrated into the TUI but does not own the TUI.

Sessions, branches, turns, tool invocations, results, summaries, and promoted knowledge are semantic objects that can be navigated like other Scriberig knowledge. An agent panel may provide a convenient conversational flow, but durable results still resolve to the same entities, revisions, snapshots, branches, migrations, and operations visible elsewhere.

Transient exploratory branches should remain visibly distinct from canonical project state until promoted through normal change machinery.

---

## 10. Live Work Without Hidden State Divergence

The TUI may observe long-running operations, application events, server events, filesystem reconciliation, or agent output.

Live updates are observations, not a second source of truth. When an event says that something changed, the interface resolves authoritative state through normal operations before treating the new state as canonical.

Cached summaries and rows may be invalidated or refreshed incrementally, but stale cache entries must not become silent substitutes for current semantic state.

The interface must distinguish at least:

```text
loading
current
stale or refresh-needed
failed
cancelled
```

where those states are meaningful.

---

## 11. Local and Remote Use Share Interaction Semantics

A TUI may run embedded in the `srig` process against local application operations or may later use the public client/server boundary.

The interaction model must not depend on privileged local access. If an operation is available only in local mode, that fact must be represented as a capability or product limitation rather than as an invisible bypass.

Local and remote modes may differ in latency, authentication, event delivery, and cancellation mechanics, but an operation such as `inspect`, `history`, `diff`, or `apply` must preserve the same semantic meaning.

---

## 12. Terminal Robustness Is a Product Requirement

A terminal interface temporarily changes terminal state, so failure recovery is part of correctness.

The TUI must be designed so that normal exit, application errors, user cancellation, resize events, and unexpected panics do not intentionally leave the user's terminal in an unusable raw or alternate-screen state.

Rendering must tolerate terminals of different sizes and capabilities. A smaller terminal may collapse panes or reduce decoration, but it should preserve access to the same semantic workflows whenever practical.

Important state must not be communicated only through color. Focus, trust, validation, conflicts, errors, and operation status need textual or symbolic cues that remain understandable with limited color support.

Unicode may improve presentation, but the essential interface must not depend on a specific font or glyph repertoire.

---

## 13. Performance and Responsiveness

The terminal event loop must remain responsive while semantic work is in progress.

Potentially expensive queries, rendering, validation, agent work, and remote requests must not be performed inside frame rendering. Long-running work should expose progress or an operation identity where the application layer supports it, and users should be able to continue inspecting unrelated state when that is semantically safe.

Large collections should be navigable without materializing or drawing the entire universe at once. Pagination, bounded result sets, and incremental loading should reuse shared query semantics rather than inventing TUI-only truncation rules.

---

## 14. Non-Goals

The initial TUI is not required to be:

- a full terminal IDE;
- a replacement for the richer web editor;
- a general-purpose text editor;
- a direct SQL/database administration console;
- a second implementation of Markdown, code, PDF, or session domain semantics;
- a privileged shell around internal Rust objects;
- dependent on an agent or model provider in order to browse ordinary knowledge.

A later terminal editor may support editing projections or structured semantic forms, but such editing must still produce normal Scriberig changes and preserve the invariants in this document.

---

## 15. Lower-Level Design Direction

Level 2 must define the concrete TUI package boundary, terminal runtime, state/effect loop, selection and navigation model, responsive shell, view contracts, command palette, application/client adapters, and conformance strategy.

Level 3 must break that design into implementation slices that can be completed and verified independently.

No Level 2 or Level 3 convenience may override the central rule: the TUI is an interactive semantic client of shared Scriberig capabilities.
