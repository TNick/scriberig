# Vertical Product Completion and End-to-End Usability

## 1. Purpose

Scriberig is built from reusable semantic libraries, application operations, protocol types, adapters, CLI/TUI/web surfaces, projections, and an agent runtime. Those layers are necessary, but the existence of those layers is not itself a useful product.

This document adds a durable architectural rule that applies to all future implementation work:

> A user-facing capability is not complete because its storage model, library API, protocol endpoint, UI component, adapter, or isolated test exists. It is complete only when a real user workflow reaches a meaningful outcome through the intended product surface and that workflow is protected by end-to-end acceptance tests.

This rule extends the vertical capability requirements in `011. runtime libraries protocol and product surfaces.md` and the integrated-editor requirements in `012. web platform and integrated editor.md`.

It exists because horizontal subsystem completion can otherwise produce a repository with substantial infrastructure but no continuous workflow that a user can depend on.

---

## 2. Three Different Meanings of Completion

Scriberig must distinguish three kinds of completion.

### 2.1 Subsystem implemented

A subsystem is implemented when its own public contract exists and its focused tests pass.

Examples include:

- an immutable snapshot store exists;
- a Rust parser emits semantic entities;
- an HTTP endpoint exposes an application operation;
- a reusable React component renders a semantic object;
- a TUI reducer handles a command;
- an agent provider adapter can execute a model request.

Subsystem implementation is valuable engineering progress, but it is not product completion.

### 2.2 Surface integrated

A capability is surface-integrated when a real product surface invokes the shared capability through its public boundary and presents the result correctly.

Examples include:

- the web application can invoke project import;
- the TUI can inspect a selected entity;
- the CLI can request history;
- the agent adapter can call semantic inspection.

Surface integration still does not prove that the result composes into a useful workflow.

### 2.3 Product verified

A capability or milestone is product-verified only when an end-to-end workflow starts from a realistic user entry point, traverses the real boundaries that matter, and reaches a useful observable outcome.

For interactive products, this normally means launching the actual executable or browser application against an actual local server/runtime and interacting through the same controls a user sees.

A mock-only component test cannot establish product verification.

A protocol-only test cannot establish product verification.

A test that asserts only HTTP status codes cannot establish product verification when the user outcome is navigation, editing, review, or filesystem change.

---

## 3. Product Verification Is a Release Gate

For milestones explicitly designated as product milestones, product verification is mandatory.

A milestone must not be described as complete, usable, finished, supported, or verified unless all required product-verification scenarios pass from a clean checkout.

Historical task checklists may continue to record that a subsystem was implemented. They do not override this rule.

In particular, a previously checked Level-3 task does not prove a current product workflow. If later integration shows that its output cannot be reached or composed through a product surface, the subsystem may remain implemented while the product capability remains unverified.

Documentation, capability matrices, release notes, and agent reports must use these distinctions truthfully.

---

## 4. The First Useful Software-Project Workflow

The first mandatory product milestone for Scriberig is a continuous workflow over a small real Git-backed source project.

A user must be able to perform the following sequence without leaving Scriberig or using an undocumented internal API:

```text
open or import project
        |
        v
project becomes active workspace
        |
        v
browse recognizable semantic structure
        |
        v
select a named code object
        |
        v
view its real source projection
        |
        v
ask an agent about it and/or edit it
        |
        v
produce a candidate semantic migration
        |
        v
review semantic and source differences
        |
        v
validate candidate
        |
        v
accept/apply migration
        |
        v
write the resulting projection to the working tree
        |
        v
observe the successor snapshot/history and continue
```

This is called the **first useful project workflow** or **golden path** in lower-level designs.

The first implementation may intentionally limit the editable golden path to one well-supported source language, initially Rust. The architecture must remain domain-extensible.

---

## 5. Active Workspace Is Explicit Product State

Importing a project and working on a project are different operations.

After a project is imported, a product surface must be able to make that project's semantic root and current snapshot its active workspace.

The active workspace includes at least:

- stable project identity;
- canonical filesystem location when local filesystem access is relevant;
- current project snapshot;
- semantic root for that snapshot;
- current selection/navigation state.

Active-workspace state is per client/session/product instance. It must not be implemented as one mutable global "current project" in a shared server or database.

Selecting a project in one browser or TUI must not silently change another client's active project.

---

## 6. Imported Knowledge Must Be Human-Navigable

A semantic store containing entities is not enough.

For supported domains, users must be able to recognize what they are browsing without decoding entity IDs, revision IDs, array positions, or labels such as `path :: kind #N`.

Supported domain adapters must expose stable display information and meaningful containment/navigation relationships.

For code, useful navigation includes recognizable concepts such as:

```text
project
  source path / module
    type / trait / function
      method / nested semantic object
```

Exact hierarchy varies by language, but symbol names and semantic kinds must be available through public semantic data, not reconstructed privately in each frontend.

Raw IDs remain available for diagnostics. They are not the primary product label when a semantic name exists.

---

## 7. Projection Is the Human Representation, Not Another Inspector

A projection view must show the domain's human-oriented representation.

For source code this means source text associated with the selected semantic object or source artifact, together with mapping back to semantic identity.

For the editable golden path, the product must expose a real editable projection or a structured edit interaction that results in the same shared change machinery.

A generic property/object inspector does not satisfy the source-projection requirement.

A browser-local edited buffer is never canonical state by itself.

---

## 8. Every Mutation Uses the Shared Change Path

Human web edits, TUI edits, CLI changes, agent proposals, external-file reconciliation, and third-party client edits must converge on the shared migration/change model.

The required conceptual path is:

```text
intent or edited projection
        -> candidate semantic change
        -> migration with exact base snapshot
        -> validation
        -> reviewable semantic/source diff
        -> compare-and-swap application
        -> successor canonical snapshot
        -> projection materialization / external effect
```

A product surface must not write canonical database rows directly.

An agent must not write the working tree directly as a privileged shortcut when the same change is expected to be reviewable through migration semantics.

A web editor must not invent a private mutation endpoint.

---

## 9. Filesystem Write-Back Is Part of the Software-Project Product

For a software project backed by ordinary source files, accepting a change is not useful if the resulting source never reaches the working tree.

The first useful project workflow therefore includes controlled projection materialization back to the project filesystem.

Write-back must:

- remain inside the project's configured/canonical root;
- use the projection ownership and atomic-I/O rules;
- reject stale or conflicting external changes rather than silently overwrite them;
- retain enough effect/recovery information to explain partial external-effect failures;
- never escape through symlinks or path traversal;
- update only files owned/targeted by the accepted projection operation.

The canonical semantic snapshot and filesystem projection may have different failure domains. Lower-level design must make recovery explicit rather than pretending both writes form one filesystem/database transaction.

---

## 10. Agent Use Must Be Semantically Scoped

The agent is a peer consumer of the same platform.

When a user asks an agent about a selected code object, the request must contain the semantic selection and exact/current snapshot context, not only a copied line range or an unstructured full repository dump.

When an agent proposes a code change for the golden path, that proposal must become the same reviewable migration that a human-generated edit would produce.

End-to-end tests for this behavior must not depend on an external commercial model service. A deterministic test provider may emulate the required provider/tool interaction while still exercising the real Scriberig agent/application/protocol/product boundaries.

---

## 11. Surface Parity for the Golden Path

The web application and native TUI are both first-class interactive products.

The first useful project milestone is not complete if one surface can perform useful work and the other remains only a database inspector, unless a Level-1 design explicitly marks a step not applicable to that surface.

Presentation may differ, but both interactive surfaces must support the core semantic sequence:

- choose/open an imported project;
- browse named semantic objects;
- inspect source projection;
- create or receive a candidate change;
- review/validate/apply it;
- observe the resulting current state.

The web surface is expected to support direct editable projection interaction in the first golden path.

The TUI may use a command/editor-buffer interaction appropriate to a terminal, but it must still use the same public operations and migration model.

CLI remains a diagnostic/automation peer and should expose the same underlying operations where command-line use is meaningful.

---

## 12. End-to-End Tests Must Observe User Outcomes

Product E2E tests must assert outcomes at the layer where the user experiences them.

Examples of valid assertions include:

- after import and project activation, the explorer visibly contains the known fixture symbol `Calculator`;
- selecting `add` shows the source containing `left + right`;
- after editing, a migration review visibly contains the changed expression;
- before acceptance, the fixture file on disk is unchanged;
- after acceptance and write-back, the fixture file on disk contains the accepted expression;
- the current snapshot ID changes;
- history shows a successor state or migration entry;
- reloading the web application or restarting the TUI still observes the accepted state;
- an agent request receives the selected entity/snapshot and its candidate follows the same review/apply path.

Examples that are insufficient by themselves include:

- endpoint returned HTTP 200;
- a React component mounted;
- a reducer action was dispatched;
- a database row count increased;
- an import operation ended with `status=imported`;
- an object inspector displayed some entity ID.

Those may remain useful lower-level tests but cannot replace product E2E acceptance.

---

## 13. Deterministic Product Fixtures

Golden-path tests must use repository-controlled deterministic fixtures copied into a temporary working directory.

Fixtures must:

- be small enough to understand completely;
- contain no network dependencies;
- be initialized or copied as a real Git project when Git behavior is under test;
- contain stable symbol names used by assertions;
- permit source mutation without modifying the Scriberig checkout itself;
- support deterministic validation such as parsing and, where applicable, `cargo check` with no dependency downloads.

Tests must not edit this repository's own tracked source as their golden-path workspace.

---

## 14. No Placeholder Completion

The following do not satisfy a required workflow step:

- a route that displays `unsupported` when that capability is required by the current milestone;
- a button wired to a stub operation;
- a projection panel that displays generic semantic metadata instead of source;
- a fake symbol label generated only in the UI while public semantic data remains unnamed;
- a migration preview that cannot be applied;
- an apply operation that changes the semantic store but not the required filesystem projection;
- an agent UI that can chat but cannot preserve semantic scope;
- a test that mocks away the boundary whose integration is being claimed.

Unsupported states remain correct behavior for optional capabilities and older servers. They are not evidence that a milestone requiring that capability is complete.

---

## 15. Product-First Development Order

Until the first useful project workflow is product-verified, work should preferentially close gaps in that workflow rather than expand unrelated horizontal breadth.

New adapters, formats, storage features, generic UI components, or agent features are justified during this period when they:

- directly unblock a golden-path step;
- fix correctness/security required by that step; or
- are necessary to keep shared abstractions honest across the required surfaces.

This is a prioritization rule, not a permanent ban on platform development.

Once the golden path is verified, additional capabilities should be developed as new vertical slices with their own user outcomes.

---

## 16. Capability Matrix Semantics

The capability matrix remains useful, but surface statuses must not be interpreted as product usability by themselves.

`implemented` means code for that capability exists on the surface.

`verified` means the capability's surface semantics have dedicated verification.

Product milestones must additionally identify their required workflow-level E2E scenarios.

A future matrix extension may add workflow/milestone references, but no status vocabulary change is required to adopt this design.

---

## 17. Definition of Done for the First Useful Project Milestone

The milestone is complete only when all of the following are true:

1. a clean build can launch the real local server/runtime, web app, and native TUI;
2. a deterministic Git/Rust fixture can be copied to a temporary directory and onboarded;
3. both web and TUI can make that project their active workspace without changing global server state;
4. both surfaces expose recognizable semantic names including a known type and method/function from the fixture;
5. source projection for the known selected symbol displays exact fixture source;
6. the web surface can create a candidate source edit through the shared change path;
7. the candidate has an exact base snapshot, semantic/source diff, and validation result;
8. accepting the candidate creates a successor snapshot and writes the accepted source to the fixture working tree through controlled projection materialization;
9. the refreshed product state and history show the successor state;
10. a deterministic agent-provider scenario receives the same semantic selection and can produce a candidate that enters the same review path;
11. stale/conflicting filesystem content is not silently overwritten;
12. browser E2E, native TUI E2E, cross-surface conformance, and repository quality gates pass from a clean checkout.

No individual subsystem checklist can waive these requirements.

---

## 18. Relationship to Earlier Designs

This document does not invalidate the architecture in Levels 1-3.

It changes how completion is judged.

Earlier documents that mark project onboarding, the integrated editor, TUI views, projections, or agent surfaces as implemented remain useful records of subsystem work. Their checked boxes must not be read as proof that the first useful project workflow is product-verified.

Lower-level designs created under this Level-1 rule must specify the exact active-workspace contract, golden fixture, product interactions, mutation/write-back sequence, and E2E tests required to close the workflow.
