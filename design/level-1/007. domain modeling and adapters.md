# Domain Modeling and Adapters

## 1. Purpose

Scriberig uses one universal knowledge model, but useful systems are built from domains with their own semantics.

Markdown has sections, paragraphs, lists, tables, links, and code blocks. Source code has modules, functions, parameters, statements, expressions, comments, attributes, and language-specific syntax. PDFs have pages, text regions, tables, figures, annotations, and layout. Sessions have branches, turns, goals, decisions, tool invocations, and results.

These domains must not become independent storage systems.

They specialize the universal knowledge model through schemas, adapters, projections, validation, semantic operations, descriptions, and derived analysis.

The central rule is:

> A domain defines meaning and behavior over the universal knowledge model. An adapter translates between that meaning and external representations or tools without creating a second source of truth.

This document defines the architectural role of domains and adapters, the boundary between canonical and derived information, and the rules that domain implementations must preserve.

It intentionally does not prescribe Rust traits, parser libraries, compiler APIs, SQL layouts, HTTP endpoints, or concrete UI components. Those belong in lower-level designs.

---

## 2. Design Goals

Domain modeling must satisfy the following goals.

### 2.1 Preserve one universal substrate

A new domain must not require a new persistence architecture.

Markdown, Rust, PDFs, sessions, and future domains should all use the same concepts for:

- entities;
- revisions;
- snapshots;
- typed properties;
- relations;
- collections;
- migrations;
- provenance;
- descriptions;
- derived knowledge;
- querying;
- history;
- branching;
- merging.

The domain defines vocabulary and constraints. It does not replace the substrate.

### 2.2 Preserve domain meaning

Universality must not flatten important distinctions.

A Rust expression is not merely text. A Markdown table row is not merely a list of strings. A PDF table cell may have extraction uncertainty and page geometry. A session branch has purpose, outcome, and provenance that differ from document containment.

Each domain must be able to preserve the choices that matter to its users and tools.

### 2.3 Support progressive disclosure

Domains must expose useful semantic boundaries that let consumers move from coarse structure to fine detail.

A consumer should be able to inspect a document before paragraphs, a function before expressions, a PDF before regions, and a session before turns.

The canonical model should therefore preserve or derive meaningful navigation units rather than forcing every consumer to traverse raw low-level syntax.

### 2.4 Separate canonical knowledge from derived analysis

A parser, compiler, OCR system, static analyzer, model, renderer, or external service may produce valuable information.

That information should be storable and queryable, but it must not silently become canonical knowledge merely because it exists in the same database.

### 2.5 Support ordinary external tools

A domain adapter should make Scriberig interoperable with the existing tools of that domain whenever practical.

Examples include:

- normal Markdown editors;
- source-code editors and formatters;
- compilers and language servers;
- PDF viewers and extraction tools;
- browser applications;
- third-party API clients.

### 2.6 Remain useful without agents

Domain schemas, parsing, rendering, querying, reconciliation, and analysis must not depend on an agent runtime.

Agents are consumers of domain capabilities, not a prerequisite for them.

## 3. Domain Specialization

A domain specializes the universal model by defining a coherent vocabulary and rules over it.

Conceptually:

```text
Universal Knowledge Model
        |
        +-- Markdown Domain
        |
        +-- Source Code Domain
        |       |
        |       +-- Rust Specialization
        |       +-- TypeScript Specialization
        |       +-- future languages
        |
        +-- PDF Domain
        |
        +-- Session Domain
        |
        +-- future domains
```

A domain may define:

- entity types;
- property types;
- relation types;
- collection semantics;
- canonical structure;
- validation rules;
- semantic operations;
- navigation summaries;
- descriptions;
- projection kinds;
- reconciliation rules;
- derived analyses;
- domain-specific queries;
- domain-specific commands;
- domain-specific UI views.

The universal store does not need hard-coded knowledge of these concepts.

For example, the store does not need to understand that a Rust `match` expression has arms or that a Markdown table contains rows. Those meanings belong to domain schemas and adapters.

---

## 4. Domain Schemas and Adapters Are Different

A schema and an adapter have related but distinct responsibilities.

A schema defines what knowledge means once it is inside Scriberig.

An adapter connects that knowledge to some external representation, tool, parser, compiler, or environment.

Conceptually:

```text
external representation
        |
        v
      adapter
        |
        v
    domain schema
        |
        v
universal knowledge model
```

A schema may exist without a file format.

For example, session branches and project decisions may be created directly in the database and never imported from files.

An adapter may also serve only one aspect of a domain.

For a programming language, separate adapters may eventually connect to:

- source syntax;
- formatting;
- compiler analysis;
- language-server analysis;
- test execution;
- package metadata.

The architecture should not assume one monolithic adapter must do everything.

---

## 5. Canonical Domain Knowledge

Each domain must define which information participates in canonical semantic state.

Canonical knowledge is what the domain intends to preserve through snapshots, history, branching, merging, and semantic editing.

The correct boundary differs by domain.

### 5.1 Canonical does not mean minimal

Canonical state should not be reduced to the smallest representation that happens to preserve execution or rendering today.

If an author made a meaningful syntactic or structural choice, the domain should normally preserve it.

For example, two source constructs that currently compile to equivalent behavior may still represent different chosen syntax and should not automatically collapse to the same canonical state.

### 5.2 Canonical does not mean exact bytes

Conversely, presentation details that do not carry domain meaning should not automatically become canonical.

Formatting, line wrapping, indentation width, table alignment spacing, and similar choices may belong to projection style rather than semantic identity.

The domain owns this distinction.

### 5.3 Canonical boundaries must be explicit

For each important field or relation, the domain should be able to say whether it is:

```text
canonical
```

or:

```text
derived
```

or:

```text
projection-only
```

or:

```text
external evidence
```

This classification is necessary for correct history, caching, trust, and reconciliation.

---

## 6. Derived Domain Knowledge

Derived knowledge is computed from canonical state, external evidence, or both.

Examples include:

```text
source code:
  symbol resolution
  inferred types
  call graph
  control-flow graph
  data-flow graph
  compiler diagnostics
  lint results
  macro expansion

Markdown/documents:
  summaries
  topic labels
  link indexes
  generated outlines

PDFs:
  extracted text
  layout regions
  table detection
  figure classification
  OCR results
  reading order
  semantic summaries

sessions:
  branch summaries
  topic groupings
  inferred decisions
  relevance indexes
```

Derived knowledge must identify exact dependencies and provenance whenever practical.

Conceptually:

```text
DerivedAnalysis
  domain: rust
  input: Function F at Revision R17
  producer: analyzer A
  configuration: C
  output: ...
```

If the inputs and producer configuration remain identical, the result may be reused.

If they change, the derived result may need recomputation even though the underlying entity identity remains stable.

---

## 7. Domain Adapters

A domain adapter is the boundary between domain-specific external systems and Scriberig's semantic model.

An adapter may provide some or all of the following capabilities:

```text
parse
import
canonicalize
render
reconcile
validate
analyze
query
execute domain operations
produce descriptions
map external coordinates
```

Not every adapter needs every capability.

Examples:

```text
Markdown adapter
  parse
  render
  reconcile

Rust syntax adapter
  parse
  render
  reconcile

Rust compiler adapter
  validate
  analyze

PDF import adapter
  import
  extract structure
  map page coordinates

Session adapter
  create and navigate session structure
  render transcripts and agent context
```

Adapters must operate through public knowledge-model operations rather than bypassing the model with domain-specific persistence tables that become independent sources of truth.

Domain-specific indexes are allowed, but they must be rebuildable or clearly classified as canonical domain state.

---

## 8. Adapter Boundaries

Adapters should have narrow, explicit boundaries.

The universal store should not depend on Markdown parsing, Rust compiler libraries, PDF extraction, or session rendering.

The dependency direction is:

```text
universal store
      ^
      |
knowledge model
      ^
      |
domain schema
      ^
      |
   adapter
      ^
      |
external format/tool
```

Higher layers depend on lower layers.

Lower layers do not call back into specific domains.

This keeps the universal store reusable for applications that never install a particular adapter.

---

## 9. Multiple Adapters May Serve One Domain

A domain should not be permanently coupled to one implementation.

For example, the Rust domain may eventually have:

```text
syntax adapter A
compiler adapter B
formatter adapter C
language-server adapter D
```

Likewise, PDF ingestion may have different extractors with different quality, performance, licensing, or platform requirements.

Derived results must therefore identify which adapter or producer created them.

Consumers may choose among several implementations while still reading and writing the same domain schema.

This separation is important for extensibility and testing.

---

## 10. Domain Composition

Real knowledge frequently crosses domain boundaries.

A Markdown document may contain a code block. A PDF may contain source-code excerpts. A session branch may reference a function, paragraph, PDF page, migration, or test result. A source-code comment may link to a design decision.

Scriberig should support these relationships directly rather than forcing domains into isolated silos.

For example:

```text
SessionBranch --touches--> Function
Decision --supported_by--> PDFPage
MarkdownCodeBlock --represents--> FunctionRevision
Comment --references--> Decision
Migration --changes--> Paragraph
Migration --changes--> Function
```

Cross-domain relations use the same universal graph machinery as relations inside one domain.

The existence of cross-domain links must not require either domain to own or copy the other domain's content.

---

## 11. Domain Ownership and References

A domain must distinguish ownership from reference.

For example:

```text
MarkdownDocument --contains--> CodeBlock
```

may represent ownership of the code block as part of the document.

But:

```text
CodeBlock --references--> Function
```

should not imply that the document owns the function.

Similarly, a session branch may reference a function without copying or owning that function.

This prevents accidental duplication and unnecessary revision coupling across domains.

Containment should express structural ownership. Other relations should express semantic association.

---

## 12. Markdown and Structured Documents

Markdown is the first recommended document-domain specialization because it has meaningful structure while remaining easy to inspect and edit with ordinary tools.

A Markdown model should support semantic entities such as:

```text
MarkdownDocument
Section
Heading
Paragraph
List
ListItem
Table
TableRow
TableCell
CodeBlock
QuoteBlock
Link
ImageReference
InlineContent
```

The exact list may evolve, but the following principles should hold.

### 12.1 Sections are semantic navigation units

A document should expose top-level sections before paragraphs.

Nested sections provide natural progressive disclosure.

### 12.2 Paragraphs are independently addressable

Paragraphs should be entities that can be inspected, described, referenced, changed, and searched without requiring a consumer to load the full file.

### 12.3 Tables expose rows and cells

Search and editing should be able to return or modify a row or cell semantically rather than only by byte coordinates.

### 12.4 Formatting is not automatically canonical

Whitespace, table alignment, wrapping, and similar choices normally belong to projection style unless the domain explicitly decides otherwise.

### 12.5 External editing remains supported

A `.md` file is an editable projection.

The Markdown adapter parses an external edit, matches semantic entities where possible, and produces semantic changes rather than treating the file as an opaque replacement blob.

---

## 13. Source Code as a Domain Family

Source code should be modeled as a family of related domains rather than one universal AST that pretends all programming languages are identical.

A language-independent code layer may define useful broad concepts such as:

```text
Module
Type
Function
Parameter
CodeGroup
Statement
Expression
Comment
Symbol
Reference
```

Language-specific schemas then specialize those concepts.

For example:

```text
Code Domain
   |
   +-- Rust Domain
   |     +-- Rust-specific expressions
   |     +-- patterns
   |     +-- attributes
   |     +-- macros
   |     +-- token trees
   |
   +-- TypeScript Domain
   |     +-- TypeScript-specific syntax
   |
   +-- future language domains
```

The common layer exists to enable shared operations where semantics genuinely overlap.

It must not erase language-specific constructs to force uniformity.

---

## 14. Canonical Source Syntax

For source code, the canonical representation should preserve the syntax the programmer chose at a meaningful structural level.

The canonical code model should normally include:

- declarations;
- parameters;
- statements;
- expressions;
- patterns;
- type syntax;
- attributes or annotations;
- macro invocations or equivalent language constructs;
- comments that are intentionally preserved;
- meaningful ordering;
- other syntax that affects author intent or round-trip fidelity.

The system should not use compiler intermediate representation as the primary canonical program representation.

Compiler IR may be extremely valuable derived knowledge, but it may erase syntax choices, comments, macros, and source-level structure that humans and agents need.

---

## 15. AST Nodes and Semantic Identity

AST nodes may be represented as normal domain entities when independent identity is useful.

This enables operations such as:

```text
inspect function
inspect code group
inspect statement
inspect expression
replace expression
move statement
find references
compare revisions
```

However, storage granularity and semantic granularity do not have to be identical.

A lower-level design may optimize the physical representation while preserving the logical ability to address meaningful syntax entities.

The Level 1 invariant is that agents and applications should not be forced to recover structure from source text when the domain already knows that structure.

---

## 16. Comments Are First-Class Domain Knowledge

Source-code comments should not automatically be discarded as parser trivia.

Comments may encode:

- documentation;
- explanations;
- invariants;
- safety arguments;
- TODOs;
- warnings;
- directives;
- user intent.

A code domain should allow comments to have identity, provenance, attachment, and history where appropriate.

Possible comment classifications include:

```text
ordinary
documentation
explanation
invariant
safety
todo
directive
generated
```

The exact classification may differ by language.

Comments remain distinct from model-generated descriptions. A source comment is authored source content; a generated description is derived knowledge unless explicitly promoted.

---

## 17. Human-Oriented Code Groups

Raw AST depth is often too fine-grained for navigation by humans and agents.

A function should be able to expose conceptual groups such as:

```text
Function process_payment

1. validate order
2. calculate amount
3. prepare provider request
4. charge provider
5. persist transaction
6. emit event
7. construct receipt
```

A `CodeGroup` is a semantic navigation layer above individual statements and expressions.

It may be determined by:

- intentional comments;
- preserved source grouping;
- blocks;
- blank-line boundaries;
- explicit editor operations;
- static analysis;
- generated descriptions.

The adapter must distinguish which parts of a code group are canonical and which are inferred.

For example, preserved grouping intentionally authored by the user may be canonical, while a generated one-line purpose may be derived.

Code groups exist to reduce the information cost of understanding a function without sacrificing access to the underlying syntax.

---

## 18. Concrete Syntax and Token Preservation

Some languages contain constructs that cannot safely round-trip through a simplified AST alone.

Rust macros are a representative example.

A domain may need several structural layers:

```text
human-oriented semantic structure
        |
        v
source-level AST
        |
        v
concrete syntax or token structures when required
        |
        v
derived compiler semantics
```

The canonical representation may therefore preserve token trees or other concrete syntax for constructs whose meaning or author intent cannot be reconstructed from a normalized AST.

This does not imply that all whitespace and every source byte must become semantic identity.

The domain should preserve only the concrete structure required for faithful meaning and round-trip behavior.

---

## 19. Compiler and Static Analysis Integration

Compiler-derived information is generally derived knowledge rather than canonical syntax.

Examples include:

```text
symbol resolution
type inference
trait or interface resolution
call graph
control-flow graph
data-flow graph
macro expansion
compiler diagnostics
lint diagnostics
```

These results may depend on more than one source entity.

They may also depend on:

- compiler version;
- dependency graph;
- enabled features;
- build target;
- environment;
- configuration.

The producer and dependency set must therefore be explicit enough to support correct invalidation and reproducibility.

Compiler facts should be queryable through the same universal graph even though they are not canonical program syntax.

---

## 20. PDFs and Imported Documents

PDFs differ from Markdown and source code because they are often imported artifacts rather than editable semantic projections.

The original PDF should be preservable as an exact source artifact.

An adapter may then derive structured entities such as:

```text
PDFDocument
PDFPage
TextRegion
Paragraph
Table
TableRow
TableCell
Figure
Annotation
```

Some of this structure may be certain; some may be inferred.

The domain must preserve provenance and confidence where extraction is uncertain.

For example:

```text
Table T
source: PDFPage 12
producer: extractor X
confidence: 0.93
```

A consumer must be able to distinguish:

```text
exact imported PDF bytes
```

from:

```text
parser/extractor interpretation
```

from:

```text
model-generated summary
```

These may coexist in the same database without having equal authority.

---

## 21. PDF Geometry and Semantic Structure

Page coordinates are important for PDFs but should not replace semantic identity.

A paragraph may have:

```text
semantic entity: Paragraph P
page: 12
bounding region: ...
```

The coordinates help a viewer highlight the source region.

The paragraph entity allows agents and applications to search, reference, summarize, relate, and navigate the extracted content semantically.

If a later extractor produces improved structure, the system should be able to preserve lineage and provenance rather than pretending the earlier extraction never existed.

---

## 22. Sessions as a Domain

Sessions use the same universal model as documents and code.

A session-domain schema may define:

```text
Session
Branch
Goal
HumanInput
AgentOutput
Observation
Question
Decision
ToolInvocation
ToolResult
BranchResult
Summary
Task
```

Typical relations include:

```text
Session --contains--> Branch
Branch --contains--> Turn
Branch --touches--> Entity
Decision --derived_from--> Branch
ToolResult --produced_by--> ToolInvocation
BranchResult --produced_by--> Branch
```

A branch may have a short description, purpose, outcome, state, and touched entities so that it can be navigated without loading all contained turns.

The session adapter may render several projections from the same underlying session knowledge:

```text
human transcript
agent context
branch tree
audit history
decision log
```

The session domain must not be tied to one model provider or one chat UI.

---

## 23. Domain-Level Progressive Disclosure

Each domain should define natural levels of inspection.

Examples:

```text
Markdown:
Document
  -> Section
     -> Block
        -> Paragraph/Table/List
           -> Cell/Item/InlineContent

Code:
Project
  -> Module
     -> Function/Type
        -> CodeGroup
           -> Statement
              -> Expression

PDF:
Document
  -> Page
     -> Region
        -> Paragraph/Table/Figure
           -> Row/Cell

Session:
Session
  -> Branch
     -> Episode/Turn
        -> Message/ToolInteraction
```

These hierarchies are views over the graph, not a requirement that the entire universal model be stored as one tree.

Domain adapters should expose child counts, descriptions, and useful handles before requiring consumers to load full content.

---

## 24. Domain Descriptions

Important domain entities should expose concise descriptions suitable for navigation.

Examples:

```text
Function
"Validates the request and persists the resulting payment."

Section
"Defines snapshot and revision identity."

PDFPage
"Contains methodology and the first results table."

Branch
"Investigates render-cache invalidation."
```

Descriptions may come from different sources.

A domain should declare whether a description is:

- authored;
- parsed;
- compiler-derived;
- statically inferred;
- model-generated;
- imported.

Generated descriptions should normally remain derived knowledge and should not alter the canonical revision of the described entity.

---

## 25. Domain Search Results

Search should return semantic domain objects whenever possible.

Examples:

```text
Markdown search result
  Paragraph P
  containing Section S

Table search result
  TableRow R
  containing Table T

Code search result
  Function F
  CodeGroup G
  Statement S

PDF search result
  Paragraph P
  Page 12
  source region ...

Session search result
  Branch B
  Decision D
```

External coordinates such as filenames, line numbers, page numbers, and byte ranges remain useful metadata, but semantic handles should be preferred for continued interaction.

---

## 26. Domain Semantic Operations

Domains may define semantic operations that are more meaningful than generic graph edits.

Examples include:

```text
Markdown:
  rename heading
  insert paragraph
  move section
  add table row

Code:
  rename symbol
  replace expression
  add parameter
  move statement
  extract function

Session:
  start branch
  complete branch
  promote decision
  reopen task
```

These operations should ultimately produce the same universal migrations and new revisions as lower-level edits.

A domain-specific command is therefore an ergonomic and validation layer, not an alternate history mechanism.

Generic graph operations remain available where appropriate, especially for infrastructure and debugging, but normal domain users should not need to express every change as raw relation manipulation.

---

## 27. Validation Belongs to the Domain Boundary

The universal store can validate universal invariants, but domain correctness requires domain knowledge.

Examples:

```text
Markdown:
  structural validity

Rust:
  parse validity
  language constraints
  compiler validation

PDF:
  source-region consistency
  extractor output shape

Session:
  valid branch state transitions
  valid result references
```

Adapters and domain services should provide validation before changes are promoted when correctness matters.

Validation results should be stored as derived knowledge with explicit provenance rather than silently mutating canonical state.

---

## 28. Reconciliation Is Domain-Specific

Bidirectional editing requires domain knowledge.

The universal projection system can provide common orchestration for:

- detecting external changes;
- tracking base projections;
- maintaining snapshot references;
- invoking reconciliation;
- representing conflicts;
- committing migrations.

But only the domain adapter knows what an external edit means.

For Markdown, reconciliation may match sections and paragraphs.

For source code, it may match declarations and syntax subtrees.

For another structured format, it may match rows, records, or semantic keys.

The adapter should produce semantic changes rather than directly updating persistence internals.

---

## 29. Domain Identity During Reconciliation

External representations often do not carry Scriberig entity IDs.

Adapters must therefore match old and newly parsed semantic objects using domain-appropriate evidence.

Possible signals include:

```text
exact content equality
structural role
parent context
sibling order
names or signatures
text similarity
syntax similarity
stable external identifiers
```

When a match is reliable, the existing conceptual entity can receive a new revision.

When it is not reliable, the adapter should prefer creating new entities or reporting ambiguity rather than inventing false continuity.

The exact matching algorithms belong in lower-level designs.

The Level 1 requirement is that identity reconciliation be explicit and domain-aware.

---

## 30. Adapter Versioning

Adapters evolve.

A parser may improve. A PDF extractor may identify tables more accurately. A compiler integration may change. A reconciliation algorithm may gain new behavior.

Derived results must therefore identify the adapter version or producer profile that created them when that version affects interpretation.

Canonical imported knowledge may also require migration when a domain schema evolves.

Schema evolution and adapter evolution are related but not identical:

```text
schema version
  defines what stored domain knowledge means

adapter version
  defines how an external representation or tool maps to that schema
```

The system must not conflate them.

---

## 31. Schema Evolution

Domain schemas will change as Scriberig learns to represent more meaning.

A schema evolution may:

- add entity types;
- add relations;
- add optional properties;
- refine validation rules;
- split one concept into several;
- introduce richer canonical structure;
- deprecate old structures.

Existing history must remain interpretable.

A domain should therefore make schema versions explicit and provide migrations when a new schema changes the meaning or shape of canonical knowledge.

Schema migrations are different from ordinary user-content migrations.

Both should remain inspectable and reproducible.

---

## 32. Generic Operations and Domain Extensions

All domains should remain reachable through the universal interaction grammar.

Conceptually:

```text
inspect
list
follow
find
query
diff
history
render
branch
apply
commit
```

Domain-specific operations extend this grammar.

For example:

```text
inspect(Function F)
```

may advertise:

```text
parameters
code_groups
references
callers
history
render source
```

while:

```text
inspect(PDFPage P)
```

may advertise:

```text
paragraphs
tables
figures
source image
reading order
```

The agent, CLI, API server, browser, and third-party libraries should all consume the same underlying domain capabilities.

---

## 33. Adapters Must Not Be Agent-Specific

An adapter is part of the knowledge platform, not part of the agent runtime.

This means:

```text
Markdown parsing works without an agent.
Rust analysis works without an agent.
PDF extraction works without an agent.
Session storage works without an agent model provider.
```

An agent may use these capabilities through tools, but ordinary applications may use the same APIs directly.

This separation allows third-party products to use Scriberig as a semantic database, document platform, source-code analysis system, or editor foundation without adopting the agent runtime.

---

## 34. Domain UI Views

Domains may provide reusable UI views, but UI code is not the canonical domain model.

Examples include:

```text
Markdown section browser
source-code function inspector
PDF page viewer
session branch tree
```

These views should consume the same public domain APIs available to other clients.

A full Scriberig application may compose low-level graph browsing with high-level domain views, but neither should require privileged access to private storage internals.

The UI should be able to move between:

```text
raw universal graph view
```

and:

```text
domain-specific semantic view
```

without changing the underlying object being inspected.

---

## 35. Future Domains

The architecture must support domains that were not anticipated when the core system was written.

Possible future domains include:

- spreadsheets;
- notebooks;
- CAD or geospatial structures;
- database schemas;
- API specifications;
- diagrams;
- issue trackers;
- email;
- calendars;
- media transcripts;
- scientific datasets;
- build graphs.

A new domain should ideally require:

```text
schema
adapter(s)
projection(s)
validation
optional derived analysis
optional UI views
```

It should not require modification of the fundamental entity/revision/snapshot architecture.

If adding a reasonable new domain requires changing the universal storage model, that is evidence that an architectural assumption should be re-examined.

---

## 36. Domain Capability Discovery

Consumers should be able to discover what a domain entity supports without knowing every domain in advance.

An inspected object may advertise concepts such as:

```text
available relations
available summaries
available projections
available semantic commands
available analyses
validation capabilities
```

This is important for generic clients and agents.

A database browser can remain universal while still allowing rich domain-specific behavior when adapters are installed.

Capability discovery also allows smaller deployments to install only the domains they need.

---

## 37. Minimal Installations

The domain architecture should allow different users to stop at different layers.

Examples:

```text
storage-only deployment
  universal store

knowledge-graph deployment
  store + schemas + queries

Markdown deployment
  knowledge graph + Markdown domain

code-analysis deployment
  knowledge graph + code domain + language adapter

full Scriberig deployment
  many domains + sessions + agents + web editor
```

No domain should make unrelated domains mandatory dependencies.

This modularity is a product requirement, not only a build optimization.

---

## 38. Domain Testing Principles

Every domain should be testable against common architectural invariants.

At Level 1, important invariants include:

- canonical data round-trips without semantic loss;
- derived data can be rebuilt;
- provenance remains visible;
- semantic identities survive irrelevant projection changes;
- external edits produce migrations rather than direct mutation;
- domain validation is applied at the domain boundary;
- unchanged entities and revisions can be reused;
- generic graph inspection continues to work;
- domain-specific inspection exposes richer meaning;
- no agent runtime is required for domain functionality.

Detailed conformance suites belong in lower-level design.

---

## 39. Architectural Invariants

The following rules apply to every domain.

1. A domain specializes the universal model; it does not create a separate persistence architecture.
2. Domain schemas define meaning, constraints, and canonical structure.
3. Adapters connect external representations and tools to domain schemas.
4. Canonical and derived knowledge must remain distinguishable.
5. Derived knowledge records provenance and exact dependencies when practical.
6. Projection formatting does not become semantic identity unless the domain explicitly requires it.
7. Containment and reference are different relationships.
8. Cross-domain relations may connect entities without copying or owning them.
9. Domain-specific operations produce ordinary revisions and migrations.
10. Reconciliation is explicit and domain-aware.
11. Ambiguous external identity matching must not invent false continuity silently.
12. Compiler, analyzer, OCR, and model output are not automatically canonical.
13. Domain entities expose semantic handles suitable for continued interaction.
14. Domains should provide progressive disclosure from coarse structure to fine detail.
15. Important entities may expose concise descriptions with provenance.
16. Domain functionality remains usable without agents.
17. Adapters and schemas are versioned independently when necessary.
18. New domains should be addable without changing the fundamental store.

## 40. Resulting Model

The architecture can be summarized as:

```text
                         Universal Knowledge Store
                                   |
                    entities / revisions / snapshots
                                   |
                                   v
                         Universal Graph Model
                                   |
                    schemas / relations / queries
                                   |
             +---------------------+---------------------+
             |                     |                     |
             v                     v                     v
        Markdown Domain       Code Domain           Session Domain
             |                     |                     |
             |                +----+----+                |
             |                |         |                |
             v                v         v                v
      Markdown Adapter       Rust     Future         Session Views
                              |      Languages
                              |
                              v
                      Compiler Analysis

             +------------------------------------------+
             |
             v
          PDF Domain
             |
             v
       PDF Import/Extraction
```

Across every domain, the same questions remain valid:

```text
What entity is this?
What revision is visible in this snapshot?
What relations does it have?
What is canonical?
What is derived?
Where did this knowledge come from?
What projections are available?
What semantic operations are valid?
What changed between two states?
```

That consistency is the purpose of the domain architecture.

Scriberig should be able to become richer in each specialized domain without fragmenting into unrelated subsystems. Markdown, source code, PDFs, sessions, and future domains should feel different where their semantics are different and identical where they rely on the same knowledge, history, query, projection, and migration foundations.
