# Projection Styles, Personalized Representations, and Materialization Policy

## 1. Purpose

Scriberig treats source files and other familiar representations as projections of canonical semantic knowledge. `006. projections and bidirectional editing.md` already establishes that style is an explicit projection input and that the same semantic object may be rendered in several styles without becoming several semantic objects.

This document refines that principle for personalized source-code presentation, shared filesystem materialization, style discovery, comments and other selectively visible content, and editable projections whose chosen style intentionally omits canonical information.

The central rule is:

> A user's preferred representation of canonical knowledge is not itself a mutation of that knowledge, and a user's private presentation preferences must not silently become the shared materialization policy of a project.

A second rule is:

> Style is allowed to change representation, including intentional omission of safely omittable presentation content, but it must not silently perform semantic program transformations or erase canonical knowledge.

This document refines rather than replaces:

- `level-1/002. universal knowledge model.md`;
- `level-1/003. identity revisions and snapshots.md`;
- `level-1/005. changes migrations branches and merge.md`;
- `level-1/006. projections and bidirectional editing.md`;
- `level-1/007. domain modeling and adapters.md`;
- `level-1/011. runtime libraries protocol and product surfaces.md`;
- `level-1/019. semantic agent operations and projection-first editing.md`.

For terminal-product integration this document is additionally constrained by the active RPI adoption work, especially `level-2/032. upstream first agent runtime and terminal product ownership correction.md`.

## 2. Canonical Knowledge and Representation Preferences Are Separate

Consider one exact semantic TypeScript module `M` in snapshot `S`.

Two users may legitimately prefer:

```text
User A
  indentation: 2 spaces
  line width: 100
  ordinary comments: visible

User B
  indentation: 4 spaces
  line width: 120
  ordinary comments: hidden
```

Both users may view the same module at the same time:

```text
M@S + Style A -> projection A
M@S + Style B -> projection B
```

The semantic identity and semantic revision of `M` do not change merely because the rendered bytes differ.

Style changes may invalidate derived projection caches. They do not, by themselves, create program migrations.

The architecture must therefore avoid any hidden equation of:

```text
current user style == current project source state
```

or:

```text
rendered bytes changed == semantic code changed
```

## 3. Style Is Exact Semantic Configuration

A style that affects deterministic output must resolve to an exact immutable input before rendering.

Conceptually:

```text
StyleProfile
  stable conceptual identity
  immutable revisions
  domain/projection applicability
  domain-defined properties
```

Examples of code-style properties may include:

```text
indentation kind
indentation width
maximum line width
quote preference
semicolon policy
trailing-comma policy
brace/layout policy
comment visibility/presentation policy
```

The universal projection layer must not define the meaning of these properties. A Rust adapter, ECMAScript adapter, Markdown adapter, or another domain owns the properties that are meaningful for that domain and projection kind.

Before rendering, the selected style must become an exact resolved value or immutable style revision so that rendering, caching, synchronization, and later reconciliation can identify precisely what produced the representation.

---

## 4. Generic Style Identity and Domain Style Semantics Are Different Responsibilities

Keep the following responsibilities separate.

The universal projection layer owns:

```text
exact style identity/reference
exact resolved style input boundary
render/cache identity participation
style provenance sufficient for reproduction
projection synchronization association
```

A domain adapter owns:

```text
style property schema
allowed values
default values
normalization
property merging where supported
rendering semantics
whether a property is safe for editable projections
whether a style is lossless or lossy for a projection kind
```

Application/product layers may own:

```text
which profile is selected for a user/view/workspace
precedence between applicable style sources
persistence of user preferences
repository/workspace materialization policy
cross-surface commands and discovery
```

The TUI, web application, CLI, and server do not independently implement source-language formatting rules.

---

## 5. Style Schemas Must Be Discoverable

A client should not need hard-coded knowledge that TypeScript supports two-space indentation while another projection supports unrelated settings.

Projection/domain capabilities should make style options discoverable enough that shared application surfaces can answer questions equivalent to:

```text
what style schema applies to this projection?
what properties are supported?
what are their allowed values/defaults?
which properties affect editability or fidelity?
what style is currently resolved?
where did each resolved choice come from?
```

The exact lower-level schema is defined by Level 2.

A client may present a specialized opinionated editor for a known schema, but generic clients must still be able to inspect and select style configuration without becoming the owner of domain semantics.

---

## 6. Style Resolution Has Purpose

A style is not selected in a vacuum. Resolution must know why a projection is being produced.

At minimum distinguish:

```text
InteractiveView
SharedMaterialization
ExplicitExport
```

Additional purposes such as agent context or diagnostic rendering may be added when their semantics require them.

The distinction matters because a user's private display preference must not automatically affect shared external artifacts.

---

## 7. Interactive View Resolution

For an ordinary personal view, the preferred conceptual precedence is:

```text
domain defaults
    < repository/project conventions
    < user preferences
    < explicit view override
    -> ResolvedViewStyle
```

A domain may reject or diagnose incompatible combinations instead of blindly merging arbitrary properties.

This ordering permits Alice and Bob to inspect the same exact semantic snapshot through different source representations without either user's preference mutating the project.

View-local changes such as choosing two spaces instead of four should normally be presentation state. They must not move a session reply anchor, change a branch, rerun a model invocation, alter a plan, or create a code migration.

---

## 8. Shared Filesystem Materialization Resolution

Shared checked-out files have a different purpose.

The preferred conceptual precedence is:

```text
domain defaults
    < repository/project conventions
    < workspace/materialization policy
    -> ResolvedMaterializationStyle
```

Personal user view preferences are deliberately absent from the default path.

Therefore opening a project as User A must not rewrite shared `.ts`, `.rs`, or `.md` files into User A's preferred layout, followed by User B rewriting the same files into User B's layout.

A user may explicitly request an export using a personal style, but that is an explicit export/materialization action with an explicit target and policy. It is not an incidental consequence of looking at the project.

---

## 9. Repository Conventions Are Inputs, Not Accidental Canonical Truth

Existing ecosystems contain style/configuration sources such as:

```text
.editorconfig
rustfmt.toml
Prettier configuration
Biome configuration
language/tool-specific formatter settings
```

Scriberig should be able to interpret applicable conventions through domain/configuration adapters.

When Scriberig understands such configuration, the architectural direction is:

```text
external convention source
  -> parse/interpret
  -> domain style candidate or policy input
  -> resolve to exact Scriberig projection style
```

The raw external file does not automatically become a privileged global variable read by renderers.

All output-affecting settings must still become declared exact render inputs.

If a project intentionally treats an external configuration artifact as authoritative input, that relationship must be explicit and synchronized under the normal projection/import rules rather than hidden inside renderer process state.

---

## 10. Style and Semantic Transformation Must Remain Distinct

Ordinary representational differences include things such as:

```text
2 versus 4 spaces
line wrapping
spacing
brace layout
quote spelling where the language semantics are unchanged
presentation of safely representable comments
```

Style must not silently choose a different semantic or author-significant program construct merely because two constructs currently behave similarly.

For example, a formatter/style must not silently turn one control-flow form into another semantic syntax choice when that choice belongs to canonical authoring structure.

If a transformation should change canonical semantic/syntactic structure, represent it as an explicit semantic operation and migration, not as a style side effect.

---

## 11. Comment Policy Is Typed, Not a Single Boolean

`strip_comments: true` is too coarse for a semantic projection system.

Comments and comment-like source elements may include materially different categories:

```text
ordinary explanatory comments
documentation comments
license/header comments
lint directives
compiler/type-check directives
formatter directives
source-map/tooling directives
generated-code markers
other domain-specific directives
```

A domain adapter must classify the categories it understands and define which projection treatments are safe.

A style may request policies such as:

```text
Show
HideInProjection
RenderAsLineComment
RenderAsBlockComment
PreserveRequiredForm
```

but the adapter may reject a requested treatment when it would change program/tool behavior, violate policy, or lose author-significant structure.

For example, a TypeScript suppression directive is not equivalent to an ordinary explanatory comment merely because both use comment syntax.

A license header may be semantically irrelevant to program execution while still being mandatory for legal/materialization policy.

The style system must preserve these distinctions.

---

## 12. Lossy Projection Is Different from Semantic Deletion

A projection is lossy when canonical knowledge intentionally exists but is not represented in that projection.

For example:

```text
canonical module
  Comment C
  Statement S

style hides ordinary comments

rendered projection
  Statement S
```

The absence of `C` from the rendered representation is not evidence that `C` was deleted from canonical knowledge.

This becomes critical when the projection is editable.

If the user edits the visible statement, reconciliation must not interpret all style-hidden entities as deletions.

Therefore:

> An editable lossy projection requires a loss-aware reconciliation contract. If the adapter cannot provide one, the lossy projection must be read-only.

This is a capability/fidelity decision for the exact resolved style, not merely for the projection kind in the abstract.

---

## 13. Editable Reconciliation Is Bound to the Exact Baseline Projection

For editable projections, Scriberig must retain enough information to know exactly what the user was shown when editing began or when the external file was last synchronized.

Conceptually a reconciliation baseline includes:

```text
semantic base snapshot
semantic scope
projection specification
exact resolved style
renderer version
exact rendered output identity/content reference
adapter version
projection-to-semantic mapping metadata when required
visibility/loss metadata when required
```

The purpose is to distinguish at least:

```text
not present because the style omitted it
```

from:

```text
was represented in the baseline and the user removed it
```

and from:

```text
was concurrently changed in canonical state
```

A mere current parser result is insufficient for this distinction.

The existing base/current/external three-way model remains controlling; this document makes the exact baseline representation and its style part of the evidence supplied to reconciliation.

---

## 14. Fidelity and Editability Are Properties of the Resolved Projection

Do not assume that all styles for one projection kind have equal round-trip behavior.

For example:

```text
TypeScript + full source style
  -> potentially lossless editable projection

TypeScript + hide ordinary comments
  -> lossy but potentially loss-aware editable projection

TypeScript + summary-only style
  -> likely read-only projection
```

A projection adapter should be able to describe a resolved projection as something equivalent to:

```text
LosslessEditable
LossAwareEditable
ReadOnlyLossy
```

Exact names belong to Level 2.

Product surfaces should use this capability information rather than guessing from the selected style controls.

---

## 15. Materialization May Be Stricter Than Personal Viewing

A style can be acceptable for a private interactive projection while unacceptable for a shared source file.

Examples include:

- hiding ordinary comments from a personal view while preserving them in checked-out source;
- suppressing documentation in a compact personal view while materialization keeps documentation;
- displaying semantic source using a preferred indentation width while repository files follow project policy.

Materialization policy may impose mandatory properties or categories that a personal view can override only locally.

This separation prevents personal presentation preferences from becoming repository churn or from violating repository/tool/legal requirements.

---

## 16. Style Resolution and Caching Must Be Reproducible

Rendering caches must include the exact resolved style and every other output-affecting input.

Changing user style should invalidate only projections whose output depends on that style. It must not invalidate semantic program identity or unrelated derived knowledge.

Where a style is composed from several sources, the renderer must receive an exact immutable resolved result rather than consult those mutable sources independently during rendering.

Provenance should remain inspectable so a user can understand why a style property has its current value.

Conceptually:

```text
indent_width = 2
  from user profile "compact-typescript" revision R7

line_width = 100
  from repository policy revision R3
```

The exact provenance representation belongs to Level 2.

---

## 17. Source Projection Style Is Not Terminal Theme

The active terminal redesign delegates commodity terminal presentation to upstream `rpi`/`rpi-tui` according to Level-2 plan 032.

Keep these concepts distinct:

```text
rpi-tui terminal theme/style
  -> colors, emphasis, layout primitives, terminal chrome

Scriberig projection style
  -> how canonical semantic code/document knowledge is represented
```

Upstream terminal theme machinery may render a source projection attractively. It must not become the authority for source indentation, comment visibility, repository materialization policy, or source projection reconciliation.

Conversely, Scriberig must not recreate a parallel terminal theme/widget system merely to expose projection-style selection.

A custom Scriberig source/projection component running on `rpi-tui` consumes projection results and shared style-selection/application contracts.

---

## 18. TUI, Web, CLI, Server, and Agents Share One Style Semantics

Product surfaces may offer different controls, layouts, and affordances, but they consume the same style-resolution and projection capabilities.

Do not implement separate rules such as:

```text
TUI says user preference overrides repository
web says repository always wins
CLI reads formatter config directly
server ignores style provenance
```

Instead:

```text
surface intent
  -> shared application style-selection/resolution operation
  -> exact resolved style
  -> projection adapter render/reconcile
```

Local/remote use must produce equivalent resolved style semantics from equivalent inputs.

Only state that genuinely belongs to one presentation instance, such as a temporary view override, remains presentation-local.

---

## 19. User Preference State Must Not Affect Execution Semantics Accidentally

Changing a personal projection style is presentation configuration unless the user explicitly requests a materialization/export policy change.

It must not by itself:

- change canonical source entities;
- create a code migration;
- move a session navigation/reply/coordinator cursor;
- change plan dependencies;
- alter a model/provider assignment;
- invalidate provider continuation;
- rerun an agent/model operation;
- rewrite shared files.

If an agent is explicitly supplied a styled projection as context, that exact projection becomes part of that invocation's declared context. Later UI style changes still do not retroactively alter the invocation.

---

## 20. Security, Policy, and Required Content

A projection style is not permission to bypass required content or trust policy.

Domains and materialization policies may mark some source elements as mandatory for a purpose.

Examples may include:

```text
license notices
security annotations
generated-file warnings
compiler/lint directives required for the represented program
integrity markers required by an external format
```

A style resolver must surface an incompatibility when a requested style would violate such requirements instead of silently dropping them.

---

## 21. Conformance Requirements

The architecture should eventually prove at least the following cross-layer behaviors:

1. The same semantic snapshot can be rendered under two different styles into different bytes while retaining the same semantic program identity.
2. Changing style changes the render/cache identity but does not create a semantic content revision.
3. Two users can concurrently view one semantic source scope using different styles.
4. A user's private view style does not rewrite shared materialized files.
5. Repository/materialization style remains deterministic and reproducible independently of the currently logged-in viewer.
6. Style schemas and current resolved values are discoverable through shared application semantics.
7. Domain adapters reject style settings they cannot safely support.
8. Hiding safely omittable comments from a projection does not delete those comments from canonical state.
9. A lossy editable projection reconciles against its exact baseline representation and exact style.
10. A lossy style without loss-aware reconciliation is exposed as read-only.
11. Local TUI and remote/web clients resolve equivalent style semantics through shared contracts.
12. Terminal theme changes and source projection style changes remain independent.

---

## 22. Non-Goals

This document does not choose:

- one universal formatter library;
- a single style schema shared by all languages;
- one UI layout for editing style properties;
- whether TypeScript ultimately renders through Oxc, Biome, dprint, Prettier, or another implementation;
- a database schema for user settings;
- a filesystem watcher strategy;
- exact Rust type names.

Those decisions belong in Level 2/3 or domain-specific implementation work.

---

## 23. Summary of Durable Invariants

The durable rules are:

```text
canonical semantic content != rendered source bytes

style is an exact declared projection input

domain adapters own style meaning

personal view style != shared materialization style

renderer reads resolved style, not undeclared mutable globals

style may omit only content the domain/policy says is safe to omit

lossy editable projection -> loss-aware reconciliation
otherwise -> read-only

reconciliation is bound to exact baseline snapshot + style + renderer + output

source projection style != terminal theme

TUI/web/CLI/server share style semantics through application/projection contracts
```

These rules preserve the central Scriberig architecture: one canonical semantic knowledge world can support many simultaneous, purpose-specific representations without confusing representation preferences with semantic change.
