# Changes, Migrations, Branches, and Merge

## 1. Purpose

Scriberig represents canonical knowledge as immutable revisions resolved through immutable snapshots.

That model makes state exact, but a usable system also needs an equally clear model for change.

The system must be able to answer:

- what changed between two states;
- why it changed;
- which entity revisions were replaced or introduced;
- whether a change came from a human, an agent, an importer, a merge, or another source;
- what work was performed speculatively rather than promoted;
- how two concurrent lines of work relate;
- whether they can be combined automatically;
- where a conflict exists when they cannot;
- how historical lineage can be inspected without reconstructing it from physical write order.

The central rule is:

> Canonical change is an explicit transition between immutable snapshots, not mutation of an existing snapshot.

This document defines the architectural model for those transitions.

It covers migrations, change lineage, semantic diffs, branches, workspaces, concurrency, common ancestors, merge, conflict representation, and promotion of completed work.

It intentionally does not define Rust types, SQL tables, wire formats, one diff algorithm, or one merge implementation. Those belong in lower-level designs.

---

## 2. Relationship to Entities, Revisions, and Snapshots

The identity model distinguishes:

```text
EntityId   -> What conceptual thing is this?
RevisionId -> What exact state is this entity in?
SnapshotId -> What exact state is the whole canonical world in?
```

A change operates across those layers.

For example:

```text
Snapshot S1
Paragraph P -> Revision PR1

change paragraph P

Snapshot S2
Paragraph P -> Revision PR2
```

The entity `P` remains the same conceptual paragraph.

`PR1` and `PR2` are different immutable states.

`S1` and `S2` are different immutable global states.

The transition from `S1` to `S2` is represented by a migration or equivalent change object.

Conceptually:

```text
S1 --Migration M1--> S2
```

The state and the explanation of the state transition are distinct objects.

---

## 3. State Does Not Explain History by Itself

Two snapshots can be compared to discover that they differ, but snapshot contents alone do not explain why one state followed another.

For example, the same final state may be reached by:

```text
human edit
agent edit
import
refactoring
merge
reconciliation of an external projection
```

The resulting snapshot may be identical in every case.

Therefore Scriberig must not infer history solely from:

- physical write order;
- timestamps;
- current entity revisions;
- file modification times;
- database transaction order.

History is explicit semantic data.

The system stores or derives explicit relationships such as:

```text
base snapshot
result snapshot
change source
semantic operations
provenance
validation evidence
parent changes
merge parents
```

This makes historical topology queryable and reproducible.

---

## 4. Migration

A migration describes a canonical transition from one snapshot to another.

Conceptually:

```text
Migration M

base:
  Snapshot S1

result:
  Snapshot S2

changes:
  Entity P: PR1 -> PR2
```

A migration answers:

> How did this canonical state become that canonical state?

A migration is not the canonical state itself.

It is a first-class explanation of the transition.

The exact final authority remains the resulting snapshot and the revisions it resolves.

---

## 5. Migrations Are Immutable Historical Objects

Once a migration has been committed as history, its meaning must not change.

If a proposed operation is modified before acceptance, the system should treat the modified proposal as different work rather than rewriting committed history.

This preserves the same exactness property used elsewhere in Scriberig:

```text
historical reference
    -> exact historical meaning
```

Committed migrations may therefore be content-addressable or otherwise immutable in the same architectural sense as revisions and snapshots.

The precise identity scheme belongs in lower-level design.

---

## 6. A Migration May Be More Semantic Than a Snapshot Diff

The minimal mechanical difference between two snapshots may be represented as changed entity resolutions:

```text
P: PR1 -> PR2
Q: absent -> QR1
```

That information is useful but incomplete.

A domain may know that the same state transition represents:

```text
RenameSymbol
SplitParagraph
MergeParagraphs
InsertTableRow
MoveFunction
ChangeExpressionOperator
ResolveDecision
CompleteTask
```

Scriberig should preserve higher-level semantic operations when they are known.

Therefore a migration may contain two complementary views:

```text
exact state transition
+
semantic interpretation of the transition
```

The exact before and after states remain authoritative even if a higher-level interpretation is absent or incomplete.

---

## 7. Generic and Domain-Specific Change

The universal knowledge model needs domain-independent change primitives.

Examples include conceptual operations such as:

```text
create entity
replace entity revision
add relation
remove relation
insert collection member
remove collection member
move collection member
replace collection structure
```

Domain adapters may describe the same transition more precisely.

For example:

```text
Generic:
replace revision of expression E

Domain-specific:
change binary operator from Add to Multiply
```

Or:

```text
Generic:
change ordered children of section S

Domain-specific:
insert paragraph P3 between P1 and P2
```

The universal change model must not require all domains to expose the same vocabulary, but every domain-specific change must ultimately resolve to a valid transition in the universal state model.

---

## 8. Change Sources and Provenance

A migration should be able to state where the change came from.

Possible sources include:

- direct user action;
- external file or projection reconciliation;
- agent work;
- CLI command;
- API client;
- web editor;
- TUI action;
- importer;
- domain refactoring;
- merge;
- synchronization;
- system maintenance that truly changes canonical semantics.

The source is provenance, not authority by itself.

A user edit and an agent edit both produce canonical state only through the same commit rules.

This is an important invariant:

> All canonical write paths converge on the same migration and snapshot model.

No interface should have a privileged hidden mutation path.

---

## 9. Semantic Change and Representation Change

Not every externally visible change is a canonical semantic change.

Examples that may not change canonical state include:

- formatting a source file differently under another style;
- rendering the same session with another context policy;
- changing whitespace that is not semantically represented;
- rebuilding an index;
- updating a cache;
- changing physical database encoding without changing semantic meaning.

Those operations may create new projections, derived objects, or physical storage state without creating a semantic migration.

A semantic migration exists only when canonical knowledge changes.

This distinction prevents rendering, caching, storage maintenance, and semantic history from being conflated.

---

## 10. Change Sets Should Be Local Even When Snapshot Identity Is Global

Every canonical change creates a new snapshot identity.

That global sensitivity is intentional.

However, the migration should identify the smallest meaningful changed set rather than implying that every entity changed.

For example:

```text
Snapshot S1 -> Snapshot S2

changed:
  Paragraph P

unchanged:
  all other visible entities
```

The global snapshot answers:

```text
Did anything change?
```

The migration and semantic diff answer:

```text
What changed?
```

These are separate questions and must remain separate in APIs, caches, agents, and user interfaces.

---

## 11. Semantic Diff

A semantic diff compares two exact states and describes their meaningful differences.

At the universal level, a diff may report:

```text
entities created
entities removed from a scope
entity revisions changed
relations added or removed
collection membership changed
collection ordering changed
```

Domain-specific views may provide richer meaning.

For example, a source-code diff may report:

```text
function signature unchanged
one condition changed
one error branch inserted
one function moved
```

A document diff may report:

```text
section renamed
paragraph updated
table row inserted
```

A session diff may report:

```text
branch completed
decision added
open task resolved
```

Textual diffs may still be rendered when useful, but they are projections of the semantic change rather than the universal change model.

---

## 12. Diff Does Not Require Direct Ancestry

A diff is a comparison between two states.

A migration is a historical transition.

They are related but not identical.

For example:

```text
S1 -> S2 -> S3
```

The system may compute:

```text
diff(S1, S3)
```

without there being a direct migration from `S1` to `S3`.

Likewise, two sibling branch states may be compared:

```text
       S1
      /  \
    S2    S3
```

with:

```text
diff(S2, S3)
```

Therefore APIs and conceptual models must not use "diff" and "migration" interchangeably.

---

## 13. History Is a Directed Graph

Canonical history is not necessarily a single linear chain.

Branching creates multiple descendants of one snapshot:

```text
       S1
      /  \
    S2    S3
```

A merge may produce a state with more than one historical parent:

```text
S2 ----\
        -> S4
S3 ----/
```

History is therefore a directed acyclic graph of immutable states and explicit transitions, subject to the semantics of retained history.

A linear presentation may be useful for a UI, but it must not replace the actual topology.

---

## 14. Branches Are Named Lines of Work Over Snapshots

A branch is not a copy of the database.

A branch is a line of work anchored to immutable snapshots.

Conceptually:

```text
main -> S1

create branch A from S1
create branch B from S1

A -> S2
B -> S3
```

All unchanged state is shared.

The branch name or branch entity may advance over time:

```text
A -> S2
A -> S4
A -> S5
```

The snapshots do not move or mutate.

The branch reference advances to newer snapshots.

---

## 15. Branch Identity and Branch State Are Separate

A branch may itself be represented as a semantic entity with stable identity and evolving revision state.

For example, a session branch may have:

```text
title
purpose
status
short description
outcome
related entities
resulting migration
```

Those properties can evolve while the branch remains the same conceptual branch.

Separately, the branch has or refers to a current working snapshot.

This follows the same identity rule as the rest of Scriberig:

```text
stable entity identity
+
immutable revision state
+
immutable snapshot state
```

The exact representation of branch metadata and branch heads belongs in lower-level design.

---

## 16. Workspaces Are Branches for Isolated Work

A workspace is an isolated line of work based on a specific snapshot.

It may be used by:

- an agent attempting an edit;
- a human trying an alternative;
- a refactoring tool;
- an external importer;
- a merge process;
- a validation process;
- a speculative transformation.

Conceptually:

```text
base S1
  |
  +-- attempt S2
  |
  +-- attempt S3
```

Neither attempt mutates `S1`.

One may be promoted, both may be retained, or both may eventually become unreachable.

This makes speculative work cheap and safe.

---

## 17. Failed Attempts Are States, Not Corruption

An invalid or rejected workspace result does not damage the base state.

For example:

```text
S1
├── S2  compile failed
├── S3  tests failed
└── S4  accepted
```

`S1` remains exact throughout the process.

Whether failed attempts are retained is a policy decision.

Architecturally, the important rule is:

> Failure before promotion must not partially mutate the base branch.

This applies equally to agent work, manual editing, projection reconciliation, and merge attempts.

---

## 18. Promotion Advances a Named Root

A branch or workspace becomes externally current by advancing a named root or equivalent current reference to a completed snapshot.

Conceptually:

```text
main -> S1
```

After accepted work:

```text
main -> S2
```

`S1` remains immutable.

Promotion should be atomic.

A consumer must not observe a state where only part of the migration has become current.

This is the point at which prepared immutable work becomes the canonical state selected by that root.

---

## 19. Promotion Uses Optimistic Concurrency

A caller should normally state the snapshot it expects a named root to reference.

For example:

```text
expected:
  main -> S1

promote:
  main -> S2
```

If `main` has already advanced to `S3`, silently overwriting it would lose concurrent work.

The promotion should fail as a concurrency event rather than corrupt history.

The caller can then:

- inspect the new state;
- rebase its work;
- merge;
- abandon the proposal;
- create another branch.

This is a semantic concurrency boundary, not a low-level locking failure.

---

## 20. Concurrent Work Is Normal

Scriberig should assume that multiple actors may work from the same snapshot.

Actors may include:

- multiple users;
- multiple agents;
- background importers;
- filesystem reconciliation;
- API clients;
- web and TUI clients;
- automated refactoring or validation systems.

Starting from:

```text
S1
```

they may independently create:

```text
       S1
      /  \
    S2    S3
```

This is not exceptional state.

It is the ordinary shape of concurrent immutable work.

The system must preserve both results until policy or an explicit operation decides what to do with them.

---

## 21. Common Ancestor

Combining concurrent states requires an explicit base.

Given:

```text
       S1
      /  \
    S2    S3
```

`S1` is the common ancestor used to determine what each branch changed.

Conceptually:

```text
left changes  = diff(S1, S2)
right changes = diff(S1, S3)
```

Merge reasons about those two change sets, not merely about the final rendered representations of `S2` and `S3`.

The common ancestor is essential because the same final value may mean different things depending on what each side started from.

---

## 22. Three-Way Merge

The default semantic merge model is three-way:

```text
          base
         /    \
      left    right
         \    /
         merged
```

The merge process considers:

```text
base snapshot
left snapshot
right snapshot
```

and attempts to produce:

```text
merged snapshot
```

plus explicit merge provenance.

The merge result must not overwrite either input snapshot.

It creates another immutable state.

---

## 23. Disjoint Changes Should Merge Naturally

If two branches change unrelated entities, they should normally combine without conflict.

Example:

```text
Base S1

Function F -> FR1
Paragraph P -> PR1
```

Left:

```text
Function F -> FR2
Paragraph P -> PR1
```

Right:

```text
Function F -> FR1
Paragraph P -> PR2
```

Merged:

```text
Function F -> FR2
Paragraph P -> PR2
```

The universal snapshot model makes this case straightforward because the changed entity mappings are independent.

This should be the common inexpensive case.

---

## 24. Same Entity Does Not Always Mean Conflict

Two branches changing the same entity require deeper analysis, but they are not automatically irreconcilable.

Suppose both branches change a section revision.

One inserts a paragraph at the beginning.

The other inserts a different paragraph at the end.

A domain-aware collection merge may be able to preserve both.

Similarly, two source-code edits may affect different statements within the same function.

Therefore the merge model should allow progressively deeper reasoning:

```text
snapshot-level changed entity detection
        |
        v
entity-level revision comparison
        |
        v
field/relation/collection comparison
        |
        v
domain-specific semantic merge
```

The system should not declare conflict earlier than necessary.

---

## 25. But Merge Must Not Invent Certainty

When two changes cannot be combined safely, the system must represent uncertainty explicitly.

It must not silently choose one side merely to produce a result.

Examples include:

- both branches replace the same expression differently;
- both rename the same entity to different names;
- one branch deletes an entity that the other meaningfully edits;
- two structural edits produce an ordering whose intended semantics are ambiguous;
- domain invariants allow more than one plausible interpretation.

In these cases, the merge should produce structured conflicts or an unresolved merge workspace.

---

## 26. Conflicts Are Semantic Objects

A conflict should describe the semantic object and alternatives involved rather than only exposing textual conflict markers.

A generic conflict may contain conceptual information such as:

```text
base entity
base revision
left revision
right revision
conflict kind
affected relation or collection
available domain interpretation
provenance for each side
```

A code conflict may refer to a function, statement, or expression.

A document conflict may refer to a section, paragraph, row, or cell.

A session conflict may refer to a decision, task, branch outcome, or other structured object.

Text conflict markers may be rendered for compatibility, but they are not the canonical conflict representation.

---

## 27. Conflict Scope Should Be Minimal

A conflict affecting one entity should not make unrelated merged state unusable.

Conceptually:

```text
merged automatically:
  A
  B
  C

unresolved:
  D

merged automatically:
  E
  F
```

The system should preserve successful non-conflicting work while isolating unresolved semantic choices.

Whether an unresolved merge is allowed to become a canonical named root depends on policy and domain guarantees.

For ordinary project state, the default should be to resolve required conflicts before promotion.

---

## 28. Merge Produces Provenance

A merge result must record where it came from.

Conceptually:

```text
S2 ----\
        -> S4
S3 ----/
```

The history should retain both parent lines.

The resulting migration or merge record should identify:

- merge base where relevant;
- left input;
- right input;
- automatic resolutions;
- explicit resolutions;
- unresolved conflicts if the result remains provisional;
- validation evidence where appropriate.

This allows future consumers to understand whether state was created by ordinary linear change or by convergence of concurrent work.

---

## 29. Merge Is Not Textual File Merge

Files may be projections of canonical semantic state.

Therefore merging canonical knowledge should not normally be defined as:

```text
merge rendered file A
with rendered file B
```

The preferred direction is:

```text
semantic base
semantic left
semantic right
      |
      v
semantic merge
      |
      v
render projection
```

A domain adapter may use textual information as evidence during reconciliation, but the canonical result must be expressed in the semantic model.

This prevents formatting or projection choices from creating false semantic conflicts.

---

## 30. Reconciliation and Merge Are Related but Different

External projection reconciliation asks:

> Given canonical semantic state and an externally edited representation, what semantic change did the user make?

Merge asks:

> Given two semantic descendants of a common base, how can their changes be combined?

A projection reconciliation may itself require a three-way comparison when canonical state changed while the user was editing.

For example:

```text
B = state used to render the user's starting file
D = current database state
F = semantic state parsed from the externally edited file
```

The system may then merge:

```text
base  = B
left  = D
right = F
```

But reconciliation still has an additional responsibility: inferring semantic correspondence from an external representation.

The concepts should share merge infrastructure where appropriate without being treated as identical operations.

---

## 31. Rebase Re-Expresses Work Against a New Base

A consumer may prefer to re-express a line of work on top of a newer base rather than create an explicit merge result.

Conceptually:

```text
S1 -> S2    original work
 \
  -> S3     new current state
```

A rebase attempts to apply the semantic intent of:

```text
S1 -> S2
```

onto:

```text
S3
```

producing a new descendant:

```text
S3 -> S4
```

`S2` is not mutated or erased.

A rebase creates new history because the work is now interpreted relative to a different base.

The original branch may remain retained according to policy.

---

## 32. Replay Must Preserve Semantic Intent Where Known

A migration may contain richer semantic operations than a raw state difference.

When replaying or rebasing work, the system should prefer those semantic operations when they remain valid.

For example, a known operation:

```text
RenameSymbol X to Y
```

is more useful to replay than blindly applying a textual replacement derived from one source projection.

Likewise:

```text
InsertParagraph after P
```

carries clearer intent than a byte offset.

The exact algorithms are domain-specific, but the architectural principle is:

> Preserve and reuse semantic intent whenever it is available and validated.

---

## 33. Lineage

Entity continuity across revisions is distinct from snapshot ancestry.

For an entity:

```text
P@PR1 -> P@PR2 -> P@PR3
```

the system may expose lineage such as:

```text
previous revision
next revision
change that introduced the revision
branch on which it appeared
snapshot where it became visible
```

For replacements that create a new conceptual entity rather than another revision of the same entity, migrations may express relationships such as:

```text
split_into
merged_from
replaces
supersedes
extracted_from
```

Lineage belongs to change history rather than being forced into entity identity.

---

## 34. Creation, Deletion, and Absence

Deletion in a snapshot does not necessarily mean physical destruction.

If an entity is removed from the canonical scope represented by a branch, historical snapshots may still resolve it.

Conceptually:

```text
S1:
E -> R1

S2:
E no longer visible in this canonical scope
```

The migration records the semantic removal.

The immutable historical revision may remain retained because another snapshot, branch, session, provenance record, or policy still references it.

Physical garbage collection is therefore separate from semantic deletion.

Similarly, creation means an entity becomes part of the relevant canonical state; it does not imply that no equivalent immutable content existed elsewhere in storage.

---

## 35. Moves Should Preserve Entity Continuity

Moving a semantic entity should not normally be represented as delete plus unrelated create when the system can determine continuity.

Examples include:

- moving a paragraph to another section;
- moving a function to another module or projected file;
- moving a table row;
- reorganizing a session branch;
- moving an object between collections.

The entity may retain the same `EntityId` while structural owners receive new revisions.

The migration can then express the move explicitly.

This produces better history, more stable references, and better agent context than reconstructing identity from location.

---

## 36. Branch Descriptions Are Navigation Knowledge

A branch should be cheap to understand without opening its full history.

A branch may expose a short description or summary such as:

```text
"Investigate immutable node identity and render-cache invalidation."
```

Completed branches may additionally expose an outcome:

```text
"Use stable entities, immutable revisions, and local cache dependencies."
```

These descriptions are navigation aids for humans and agents.

They should be addressable and have provenance like other derived or authored descriptions.

A parent session or project view may retain only the compact branch descriptor by default while keeping the full branch available for deeper inspection.

---

## 37. Agent Work Uses the Same Change Model

Agents do not receive a separate mutation architecture.

An agent starts from an exact snapshot or branch head.

Its work creates one or more descendant snapshots in an isolated workspace.

Conceptually:

```text
base S1
   |
   +-- S2 attempt
   |     validation failed
   |
   +-- S3 attempt
         validation passed
```

If `S3` is accepted, the relevant named root may advance to it or merge it with newer concurrent state.

The agent does not directly mutate the previous canonical state.

The same model applies whether the agent changes source code, a document, a session, a decision, or another domain.

---

## 38. User Interfaces Use the Same Change Model

The CLI, API server, TUI, browser editor, external libraries, and agent runtime should all expose the same conceptual operations.

For example, editing a paragraph in the browser and editing the same paragraph through an agent should both result in:

```text
base snapshot
semantic change
new revisions
result snapshot
migration
optional validation
promotion
```

This makes behavior consistent across product surfaces and ensures that history, merge, provenance, and validation do not depend on which interface initiated the change.

---

## 39. Validation and Change Are Separate Concerns

A migration describes a transition.

Validation determines whether that transition is acceptable for a particular purpose.

Examples include:

- schema validation;
- source parsing;
- type checking;
- tests;
- document invariants;
- domain-specific constraints;
- policy checks.

A candidate snapshot may exist in a workspace even if validation fails.

Promotion policy decides whether failed or incomplete validation prevents a named canonical root from advancing.

Keeping these concepts separate allows the same migration model to work across domains with different validation requirements.

Detailed trust and validation policy belongs in the dedicated Level 1 design for those concerns.

---

## 40. Deterministic Convergence Is Valuable

When two independent operations produce the same exact canonical state, the resulting snapshot identity should converge when the identity model permits it.

Likewise, identical immutable revisions should be reusable.

This means two branches may independently arrive at the same state and be recognized as equivalent without replaying their entire history.

However, identical state does not erase provenance.

Two histories may reach the same snapshot through different migrations.

The system may preserve both historical explanations while sharing the identical resulting state.

---

## 41. State Equality and History Equality Are Different

Two branches may have the same current `SnapshotId` while having different historical paths.

For example:

```text
S1 -> S2 -> S4

S1 -> S3 -> S4
```

The current canonical state is identical at `S4`.

The histories are not identical.

Applications must therefore distinguish questions such as:

```text
Are these branches currently in the same state?
```

from:

```text
Did these branches arrive here through the same history?
```

Snapshot identity answers the first question.

History topology and migrations answer the second.

---

## 42. Change Queries

The architecture should support queries such as:

```text
what changed between snapshots A and B?
what migration introduced revision R?
what is the history of entity E?
which branch first introduced entity E?
what changed since snapshot S?
what branches descend from snapshot S?
what is the common ancestor of A and B?
what conflicts prevent merging A and B?
which migrations touched entity E?
which changes came from a particular branch or agent workspace?
```

These queries are core platform capabilities, not agent-specific features.

Agents are one class of consumer.

A database-only application should be able to use the same history and merge facilities.

---

## 43. Change Descriptions and Summaries

Migrations, diffs, branches, and merge results may be large.

They should support progressively disclosed descriptions like other Scriberig objects.

For example:

```text
Migration M
"Add timeout handling to payment processing."

changed entities: 4
created entities: 1
removed entities: 0
validation: passed
```

A deeper view may expose semantic operations.

A deeper view still may expose exact before and after revisions.

This allows humans and agents to navigate history without consuming every low-level change immediately.

Descriptions may be authored, mechanically derived, or model-generated, and their provenance should remain visible.

---

## 44. Fine-Grained Dependencies Survive Branching

A global snapshot changes whenever canonical state changes, but branch creation and unrelated changes must not invalidate all derived work.

Derived results should continue to depend on exact local inputs.

For example:

```text
Function summary
  depends on Function F@R7

Render cache
  depends on Section S@R3 and Style T@R2

Compiler analysis
  depends on exact source and configuration revisions
```

If a branch changes unrelated entity `P`, those results remain reusable.

The change and merge model must therefore preserve exact local revision identity through branching and merging whenever state is unchanged.

---

## 45. Named Roots Express Policy, Not State Identity

Names such as:

```text
main
feature-x
agent-workspace-17
active-session
published
```

are mutable references selected by an application or user policy.

They are not immutable state identities.

A name can move:

```text
main -> S1
main -> S2
```

The snapshots cannot.

A branch name may be deleted without deleting its historical snapshots if other retained roots still reach them.

This distinction is essential for both concurrency and garbage collection.

---

## 46. Retention of Change History Is Policy-Driven

The architecture permits rich immutable history, but not every speculative state must be retained forever.

Retention policy may differ for:

- promoted canonical history;
- published states;
- session branches;
- failed agent attempts;
- abandoned workspaces;
- merge experiments;
- imported temporary states;
- derived caches.

A retained migration must remain readable with the historical state it references.

Unretained unreachable states may eventually be garbage-collected according to persistence policy.

History semantics and physical retention are related but distinct concerns.

---

## 47. Cross-Domain Changes

One migration may legitimately span multiple domains because Scriberig stores one knowledge universe.

For example, a single accepted operation may:

```text
change source code
update a design decision
resolve a task
append a session branch result
```

If those changes must become visible atomically, they may belong to one resulting snapshot and one composite migration.

The system must not assume that a migration belongs to exactly one file, one language, or one document type.

This is one of the advantages of a universal snapshot model.

---

## 48. Partial Domain Availability

Not every consumer needs every domain adapter installed.

A generic consumer should still be able to understand universal change information such as:

```text
entity changed
relation changed
collection changed
snapshot ancestry
migration provenance
```

A consumer with the relevant domain adapter may additionally understand:

```text
function renamed
paragraph split
table row moved
session decision superseded
```

History therefore needs a universal base representation with optional richer domain interpretation.

---

## 49. Change Model Invariants

Lower-level designs and implementations must preserve the following invariants.

1. Existing snapshots are never mutated.
2. Existing immutable revisions are never rewritten to mean different state.
3. Every canonical state transition produces a new snapshot.
4. A committed migration identifies its exact base and result states.
5. Historical topology is explicit rather than inferred from write order.
6. Branches and workspaces reference snapshots; they do not copy the whole knowledge store.
7. Concurrent descendants of one snapshot are normal and independently valid.
8. Promotion of a named root is atomic.
9. Concurrent promotion must not silently overwrite a newer root.
10. Merge uses an explicit common base or equivalent ancestry information.
11. Disjoint semantic changes should merge without unnecessary conflict.
12. Conflicts are represented semantically and at the smallest practical scope.
13. Merge never mutates its input states.
14. Rebase creates new history rather than rewriting immutable historical state.
15. Semantic deletion is not physical destruction.
16. Moves should preserve entity continuity when continuity is known.
17. All write surfaces converge on the same migration/snapshot model.
18. Formatting-only or derived-data changes do not create semantic history unless canonical knowledge changes.
19. Snapshot equality and history equality are distinct concepts.
20. Generic change remains understandable even without a domain-specific adapter.

---

## 50. What This Design Does Not Decide

This Level 1 design deliberately does not prescribe:

- the database schema for migrations;
- the exact migration operation enum;
- the hash algorithm for migration identity;
- the persistent-map implementation;
- the exact branch metadata schema;
- one merge algorithm for all domains;
- one collection merge strategy;
- one conflict-resolution UI;
- one rebase algorithm;
- one textual diff format;
- one validation pipeline;
- retention durations;
- garbage-collection implementation;
- whether every intermediate workspace snapshot is persisted eagerly;
- how semantic operations are encoded on the wire.

Those decisions belong in Level 2 designs derived from these architectural rules.

## 51. Architectural Summary

Scriberig change history is a graph of immutable states connected by explicit semantic transitions.

The model can be summarized as:

```text
stable entities
      |
      v
immutable revisions
      |
      v
immutable snapshots
      |
      +--------------------+
      |                    |
      v                    v
  migration             branch
      |                    |
      v                    v
new snapshot        descendant snapshots
      |                    |
      +---------+----------+
                |
                v
              merge
                |
                v
         new immutable snapshot
```

The essential separation is:

```text
Snapshot
  exact canonical state

Migration
  explanation of a state transition

Branch
  named or semantic line of work over snapshots

Diff
  comparison between exact states

Merge
  combination of concurrent semantic changes

Conflict
  explicit unresolved semantic choice
```

Together these concepts allow Scriberig to support human editing, agents, external projections, concurrent clients, speculative work, history, rollback, semantic review, and reproducible merging without introducing in-place mutation as the foundation of the system.
