# Model-Driven Agent Execution and Branch Isolation

## 1. Purpose

This document defines how a model reached through an OpenAI-compatible API participates in Scriberig's agent architecture.

It refines, but does not replace, the principles in:

1. `009. agent interaction and sessions.md`;
2. `010. universal query and operation model.md`;
3. `011. runtime libraries protocol and product surfaces.md`;
4. `013. trust validation capabilities and provenance.md`.

The central rule is:

> The model is a replaceable reasoning engine operating inside a Scriberig session branch. Scriberig owns context construction, tools, capabilities, branch topology, canonical state, provenance, validation, and promotion.

The model does not own the project database, session store, tool implementation, branch structure, or product UI. It receives a bounded projection of those things and returns model output or tool requests that Scriberig interprets through trusted runtime boundaries.

This document is intentionally architectural. Concrete Rust modules, request DTOs, HTTP paths, cache records, UI components, and command flags belong in Level 2 and Level 3.

---

## 2. Relationship to the Existing Session Model

`009. agent interaction and sessions.md` already establishes that:

- sessions are structured knowledge graphs rather than transcript blobs;
- branches are first-class focused work units;
- branches may nest;
- completed branches may collapse to descriptors and results in parent context while remaining fully stored;
- agent context is a projection rather than canonical state;
- tool calls and tool results are structured session knowledge;
- speculative work does not become canonical project state without normal validation and promotion.

This document defines the missing execution rule that makes those ideas operational:

> Every integrated model-driven agent execution occurs in an explicit session branch, and every model request is compiled from the exact state visible to that branch.

A model request is therefore not "the session." It is one derived execution input for one step of one branch.

---

## 3. Architectural Roles

The architecture separates four roles that must not collapse into each other.

### 3.1 Scriberig knowledge and application layers

These own canonical and derived semantic state, snapshots, migrations, validation, capability checks, operations, and session-domain persistence.

They remain useful without a model provider.

### 3.2 Agent runtime

The agent runtime coordinates:

- branch creation and completion;
- context projection;
- tool exposure;
- model requests;
- tool execution loops;
- child-branch delegation;
- model-result caching policy;
- cancellation and operation lifecycle;
- conversion of completed work into session objects and result handles.

The runtime is trusted orchestration code, but it still cannot bypass the shared application mutation model.

### 3.3 Model provider

The provider is an external or local service reached through an OpenAI-compatible model API or another future provider adapter.

The provider receives a serialized model request and may return:

- assistant text;
- structured output;
- tool/function calls;
- usage metadata;
- stream fragments;
- provider diagnostics.

The provider is not authoritative over project state.

### 3.4 Product surfaces

One-shot CLI, TUI, web application, API clients, and future surfaces start or observe the same agent operations.

They do not assemble provider requests independently and do not implement their own branch semantics.

---

## 4. The Model Is Replaceable

Scriberig must not make session identity or project semantics depend on one model vendor.

A configured model provider is execution metadata. Conceptually it includes:

```text
provider profile
base endpoint
model identifier
compatibility capabilities
request options
credential reference
```

Credentials are runtime secrets and are never session knowledge.

The same session may use different model providers or model identifiers over time. Historical model invocations record sufficient non-secret provenance to identify what was requested and which provider profile/model handled it, but the session graph remains provider-neutral.

A branch result is meaningful because of its semantic outcome and provenance, not because it came from a particular vendor payload format.

---

## 5. One Model Step

A model step follows this logical flow:

```text
Branch state
  + current goal/purpose
  + parent branch descriptors/results
  + selected semantic knowledge
  + recent branch activity
  + capability-filtered tool catalog
  + context policy
        |
        v
Compiled model context
        |
        v
Provider adapter
        |
        v
OpenAI-compatible model endpoint
        |
        v
Model output
  text / structured result / tool calls
        |
        v
Agent runtime interpretation
```

The compiled context must preserve stable handles and enough provenance to reopen omitted detail.

No provider response directly mutates canonical knowledge.

---

## 6. Branches Are Execution Isolation Boundaries

A session branch is the primary isolation boundary for agent work.

A branch has, conceptually:

```text
identity
parent branch, if any
purpose
goal or requested task
base semantic scope
base snapshot/workspace when applicable
capability scope
context policy
status
child branches
observable execution events
result references
compact descriptor
```

The active branch owns the local sequence of model invocations, tool calls, observations, and outputs produced while completing its purpose.

A child branch inherits only explicitly selected context and capabilities from its parent. It does not automatically inherit the complete parent transcript.

A parent consumes a completed child primarily through `BranchResult` and the child's compact descriptor. Full child history remains available by reference.

---

## 7. Not Every Tool Call Requires a Child Branch

Branching is semantic isolation, not a requirement to create a node for every atomic read.

The runtime distinguishes two broad classes of tool execution.

### Atomic in-branch tool execution

A bounded operation that can be executed and returned without an independent reasoning loop may stay in the current branch. Examples include inspecting one entity, following one relation page, or reading operation status.

The invocation and result are still recorded as structured session objects.

### Child-branch execution

Work that can require its own model/tool back-and-forth, speculative mutations, retries, validation, conflict handling, or independent delegation should execute in a child branch.

Examples include:

- editing a function;
- reconciling a projection;
- investigating a failing test;
- comparing alternative implementations;
- resolving a merge conflict;
- performing a delegated research task.

The runtime or an explicit tool contract decides whether an operation is atomic or branch-producing.

This prevents branch explosion while preserving the context-isolation property that motivated the session tree.

---

## 8. Nested Branch Execution

Branches may recursively create child branches.

Conceptually:

```text
Root branch: implement feature
|
+-- child: inspect architecture
|   +-- atomic semantic reads
|   +-- BranchResult: relevant constraints
|
+-- child: edit module A
|   +-- model/tool loop
|   +-- child: validate candidate
|   |   +-- compiler/tests
|   |   +-- BranchResult: validation evidence
|   +-- BranchResult: candidate migration
|
+-- root continues using compact child results
```

A branch-depth limit, step budget, wall-clock budget, token budget, or operation policy may bound execution. Such limits are runtime policy, not canonical session semantics.

Nested branches must remain inspectable even when their detailed histories are omitted from the active parent context.

---

## 9. Branch Completion and Collapse

A completed branch produces a durable `BranchResult` or an explicit no-result outcome.

A useful branch result contains, conceptually:

```text
branch identity
status
short outcome summary
result kind
result handles
important touched entities
produced migration/workspace handles, if any
validation handles, if any
unresolved questions, if any
```

The parent context normally receives this compact result rather than every model/tool exchange from the child.

The parent may later reopen the child branch through a stable handle when the compact result is insufficient.

This is the principal mechanism by which long-running sessions avoid permanent context growth.

---

## 10. Model Context Is a Deterministic Projection Input

The context compiler constructs a provider-neutral context plan from exact branch and project state.

Its inputs include, when applicable:

- agent/profile instructions;
- current branch purpose and goal;
- current user instruction;
- exact parent branch descriptors/results selected for inheritance;
- recent activity in the current branch;
- accepted decisions and open tasks relevant to the branch;
- explicitly selected semantic objects and exact revisions;
- derived descriptions or summaries with provenance;
- capability-filtered tool definitions;
- context budget and policy revision.

The context plan records the exact semantic dependencies used to construct it.

The provider adapter then serializes that plan into the provider's request format.

This separation lets Scriberig change providers without changing the session model and lets context compilation be tested without a network.

---

## 11. Progressive Tool Disclosure

A model should not receive every operation in the system by default.

The runtime exposes a compact initial tool set suitable for orientation and capability discovery. Additional operations become available from semantic context, domain capabilities, stable result handles, or explicit branch policy.

Tool definitions therefore form part of model context and must participate in request identity.

A tool result should advertise useful next semantic handles and operations rather than forcing the model to infer hidden endpoint names or database structures.

Provider-native function/tool calling is a serialization mechanism for these trusted Scriberig tool contracts. It is not the source of tool semantics.

---

## 12. Tool Execution and Trust Boundary

A model-requested tool call is a proposal to invoke a named capability with structured arguments.

The runtime must:

1. resolve the advertised tool definition;
2. validate arguments against the trusted tool schema;
3. apply the caller/branch capability scope;
4. execute through application/session operations;
5. record the invocation and result;
6. return an appropriately bounded result projection to the model.

The model cannot bypass authorization by inventing a tool name or supplying arbitrary raw transport data.

Canonical mutations follow the same migration, validation, review, conflict, and promotion rules as human-initiated mutations.

---

## 13. Observable Reasoning, Not Hidden Chain of Thought

Scriberig does not require hidden model chain-of-thought for correctness, provenance, replay, or audit.

Durable execution records consist of externally meaningful artifacts such as:

- model invocation metadata;
- compiled context identity and dependency manifest;
- assistant output intended for use by the runtime/user;
- structured tool calls;
- tool results;
- branch creation and completion;
- decisions and observations;
- migrations and validation evidence;
- final branch results.

If a provider exposes opaque reasoning tokens or internal traces, they are not required canonical session content.

The system should prefer explicit concise observations or summaries that can be attributed and inspected.

---

## 14. Model Invocation Identity and Cacheability

Model invocations are derived computations and should support hash-based identity.

A request fingerprint is derived from all output-relevant, non-secret inputs, including conceptually:

```text
fingerprint schema version
provider compatibility profile
provider/model identifier
output-affecting model parameters
agent/profile revision
context-policy revision
canonical compiled context
exact semantic dependency identities/revisions
tool definition schema hashes
requested structured-output schema, if any
```

Credentials and secret header values are excluded.

The fingerprint identifies the request Scriberig intended to make, not necessarily the provider's hidden model binary.

Cache policy is explicit. Supported policies may include:

```text
record only
reuse exact successful result
disable cache
```

A reused model result keeps provenance to the original invocation and records that the new execution reused it.

Providers may be nondeterministic or silently update a model behind the same identifier. Cache metadata must therefore preserve provider/model identity and any provider fingerprint/version information that is available, and reuse must remain policy-controlled rather than pretending the provider is mathematically deterministic.

---

## 15. Streaming Is Observation, Not Canonical State

Provider streaming may expose partial text, tool-call fragments, usage updates, or progress.

Streams are useful for TUI, web, logs, and cancellation responsiveness, but partial fragments are not canonical project knowledge.

The runtime may emit transient operation events while assembling a complete model output. Durable session objects are committed at semantic boundaries such as:

- accepted assistant message/output;
- complete tool call;
- complete tool result;
- branch state transition;
- branch result;
- final agent output.

A client that disconnects and reconnects must be able to recover durable state by querying the session/operation rather than depending on replay of every stream fragment.

---

## 16. Cancellation and Failure

Agent execution is a long-running application operation.

Cancellation may be requested at any time through the shared operation boundary.

The runtime should propagate cancellation to:

- an in-flight provider request where transport support permits;
- pending child branches;
- cancellable application operations initiated by the branch.

Cancellation does not erase already durable session history.

Failure is also structured. A branch may fail because of:

- provider transport failure;
- provider protocol incompatibility;
- context compilation failure;
- tool validation failure;
- permission denial;
- semantic application failure;
- validation failure;
- budget/limit exhaustion;
- explicit cancellation.

The parent receives a compact failure result and may decide whether to retry, delegate differently, or stop.

---

## 17. One Shared Agent Operation across Product Surfaces

TUI, web, one-shot CLI, remote clients, and future product surfaces must use the same semantic agent operation.

Conceptually a start request identifies:

```text
prompt/instruction
session selector or create-new intent
parent branch or create-root intent
semantic selection/scope
agent profile
context policy
authorized capabilities
runtime limits/retention policy
```

Starting work returns immediately with stable handles such as:

```text
OperationId
SessionRef
RootBranchRef
```

The operation can then be observed through status/events and the session graph.

A product surface may choose to wait synchronously for the final result, but this is presentation behavior over the same long-running operation.

---

## 18. One-Shot CLI Semantics

The native one-shot surface is a non-interactive presentation of the same branch-aware runtime.

A one-shot invocation:

1. composes the local application and configured model provider;
2. creates or selects a session;
3. creates a root execution branch;
4. starts the shared agent operation;
5. waits for terminal completion while optionally rendering bounded progress;
6. prints the final agent output or structured failure;
7. leaves the session/branch/result inspectable according to retention policy.

One-shot mode does not implement a simplified direct-to-provider shortcut for normal agent work.

If a provider-diagnostic command exists, it is a separate diagnostic concern and must not be confused with the integrated one-shot agent semantics.

The existing `srig run <PROMPT>` command is the intended one-shot product surface. If `srig agent <PROMPT>` remains for compatibility or advanced profile selection, both commands must converge on the same integrated runtime rather than maintain two independent agent loops.

---

## 19. TUI Semantics

The TUI is an interactive observer/controller of shared agent operations.

It must be able to:

- start agent work against the current semantic selection/session/branch;
- show root and nested branch topology;
- show compact branch descriptors and results;
- expand a branch to inspect turns, tool calls, results, and provenance;
- display streaming/progress as transient operation state;
- navigate away while execution continues;
- cancel when authorized;
- activate result handles through normal semantic navigation;
- review/promote candidate changes through shared mutation workflows.

The TUI never stores provider credentials, builds provider requests, or owns branch completion logic.

---

## 20. Web Application Semantics

The browser application uses the public Scriberig protocol/client/model packages and does not contact the model provider directly.

The integrated web agent experience must be able to:

- start or continue agent work;
- bind work to the universal semantic selection;
- observe operation progress;
- render the session/branch tree;
- collapse completed child branches to compact result cards;
- expand any retained branch on demand;
- navigate result handles into raw/semantic/projection/history views;
- show candidate changes and validation through existing review surfaces;
- reconnect and rehydrate durable session state after stream interruption.

Reusable branch/session interaction belongs in public web packages, not only in the reference application.

---

## 21. Remote and Embedded Execution

The same agent semantics support both local and server-hosted composition.

### Embedded/local

A native one-shot command or local TUI may invoke the application/agent runtime in-process.

### Remote/server

The web application, remote TUI, or third-party client invokes the public Scriberig server protocol. The server hosts or delegates to the agent runtime and model provider.

The remote client must not need provider credentials or provider-specific request logic.

Embedded and remote results should be semantically equivalent for the same configured runtime and base state, subject to ordinary model nondeterminism/cache policy.

---

## 22. Retention and Reachability

Agent execution can generate large amounts of transient session knowledge.

Retention policy may distinguish:

- active root sessions;
- completed root branches;
- child branches referenced by retained `BranchResult` objects;
- audit-required model/tool records;
- abandoned/retry branches;
- raw provider payload artifacts;
- stream fragments.

A compact parent result may keep a child branch reachable even when the parent does not include its full contents in context.

Raw provider payload retention should be optional and sanitized because such payloads can contain duplicated context or external data. Canonical session semantics must never require raw provider JSON to remain forever.

---

## 23. Cross-Surface Invariants

The following must hold for one-shot, TUI, web, embedded use, and remote use.

1. The same semantic request starts agent work.
2. The same branch/session objects represent execution.
3. The same capability checks gate tools.
4. The same operation lifecycle represents progress and cancellation.
5. The same branch results are queryable after completion.
6. The same canonical mutation path handles proposed changes.
7. Provider details stay below the agent-runtime boundary.
8. Product surfaces may differ in presentation, waiting behavior, and navigation, not semantic ownership.

---

## 24. Architectural Invariants

Implementations must preserve these invariants.

1. **Every integrated model-driven execution belongs to an explicit session branch.**
2. **The model is replaceable execution infrastructure, not canonical authority.**
3. **The session schema remains provider-neutral.**
4. **Model context is a derived projection with exact semantic dependencies.**
5. **Child branches inherit selected context, not an implicit complete parent transcript.**
6. **Completed child branches may collapse to descriptors/results in parent context without losing stored history.**
7. **Nested branches are allowed and use the same model recursively.**
8. **Atomic tools may stay in-branch; complex/delegated work may create child branches.**
9. **Tool requests are validated and capability-checked by trusted runtime code.**
10. **The model cannot directly mutate canonical state.**
11. **Model invocations support hash-based request identity over non-secret output-relevant inputs.**
12. **Cache reuse is explicit and provenance-preserving.**
13. **Streaming fragments are observations, not canonical project mutations.**
14. **Cancellation and failure preserve already durable provenance.**
15. **One-shot, TUI, web, and remote clients converge on the same agent operation and session model.**
16. **The browser and TUI never require direct model-provider credentials.**
17. **No correctness property depends on storing hidden chain-of-thought.**
18. **Durable branch results remain reopenable through stable handles.**

---

## 25. Non-Goals

This design does not require:

- one permanent model vendor;
- OpenAI-specific session schemas;
- exposing all tools in every request;
- creating a child branch for every atomic tool call;
- storing hidden reasoning traces;
- deterministic provider behavior;
- storing every stream fragment forever;
- direct provider access from browser or TUI code;
- bypassing normal migration/review because the model requested a mutation;
- flattening nested branches into the parent transcript;
- making one-shot mode a separate semantic agent implementation.

---

## 26. Definition of Model-Driven Agent Execution

A Scriberig model-driven agent execution is a long-running, branch-scoped application operation that compiles a bounded semantic context, invokes a replaceable model provider, validates and executes model-requested tools through trusted capabilities, recursively delegates complex work into child branches when useful, and returns compact branch results while retaining full provenance by reference.

The same execution model powers interactive and non-interactive product surfaces. The TUI and web app expose the tree; one-shot mode waits for the root branch to finish. In all cases, Scriberig—not the model—owns the branch graph, tools, canonical state, validation, and durable meaning of the result.
