    Scriberig Vision and Principles¶

    1. Purpose¶

    Scriberig is a general system for storing, understanding, editing, and navigating structured knowledge.

    The system is designed for both humans and software agents. It must support source code, documents, sessions, PDFs, project decisions, tool results, and future domains without giving each domain a separate storage architecture.

    The central idea is simple:

    Store meaning as structured knowledge. Treat files, transcripts, user interfaces, and model context as projections of that knowledge.

    Scriberig is therefore not primarily a file editor, a chat application, or an agent harness. Those are products and interfaces built on top of a shared knowledge system.

    This document defines the vision and architectural principles that all lower-level designs and implementations must preserve.

    2. The Core Premise¶

    Scriberig has one universal typed knowledge store.

    Different domains specialize that store with schemas and relations.

    Examples:

    • a paragraph is an entity;
    • a Markdown section is an entity;
    • a source-code function is an entity;
    • an AST expression is an entity;
    • a PDF page is an entity;
    • a table row or cell is an entity;
    • an agent session is an entity;
    • a session branch is an entity;
    • a project decision is an entity;
    • a migration is an entity;
    • a style is an entity.

    Relations connect these objects.

    Examples:

    • contains;
    • calls;
    • references;
    • derived_from;
    • described_by;
    • supersedes;
    • produced_by;
    • belongs_to.

    Domain-specific systems define which entity types and relations are useful, but they do not replace the universal storage model.

    This allows the same fundamental operations to work across domains.

    For example, an agent or application should be able to inspect, traverse, search, compare, describe, render, branch, and modify knowledge using one general interaction model whether the target is code, a document, a PDF, or a session.

    3. Goals¶

    Scriberig should make the following possible.

    3.1 Structured access instead of raw file access¶

    An agent should normally work with semantic objects rather than unrestricted byte or text access.

    For example, instead of reading a large Markdown file, an agent can first list its top-level sections, inspect a selected section, see how many paragraphs or tables it contains, and read only the required objects.

    For code, an agent can inspect modules, functions, conceptual code groups, statements, and expressions progressively.

    The system should make the cheapest representation useful enough for the agent to decide what to inspect next.

    3.2 Human compatibility¶

    Humans must remain free to use ordinary tools.

    Users may edit source files, Markdown files, and other supported projections with external editors.

    Scriberig must import those changes back into the semantic store instead of requiring all edits to happen through a custom editor.

    The system must not trap a project inside a proprietary editing environment.

    3.3 Stable history¶

    Knowledge must have durable identity and history.

    The system must support:

    • immutable revisions;
    • snapshots;
    • branches;
    • migrations;
    • semantic diffs;
    • concurrent work;
    • merges;
    • rollback and inspection of historical state.

    3.4 Efficient incremental work¶

    A local change should not force unrelated knowledge to be recomputed, rerendered, reanalyzed, or reread by an agent.

    Unchanged semantic objects should remain reusable across snapshots.

    Derived results should be reusable whenever their exact dependencies have not changed.

    3.5 One platform, many consumers¶

    The storage and knowledge libraries must be useful without any agent runtime.

    A user may use Scriberig only as:

    • a versioned semantic database;
    • a structured document system;
    • a source-code analysis system;
    • a projection engine;
    • a query system;
    • an API server;
    • a reusable UI library.

    The full agent product is one consumer of these capabilities, not the owner of them.

    3.6 First-class reusable interfaces¶

    CLI, server API, TUI, web libraries, the full web editor, and agent tools must evolve together.

    User-level capabilities should be implemented vertically across the supported surfaces rather than existing only in one interface for long periods.

    The full Scriberig editor should use the same public libraries and APIs made available to third parties.

    4. Non-Goals¶

    The following are not foundational goals.

    4.1 Replacing every external tool¶

    Scriberig does not need to replace existing compilers, language servers, PDF parsers, editors, formatters, or databases when they can be integrated effectively.

    4.2 Treating every domain identically¶

    The storage and interaction model is universal, but domain semantics are not.

    A Rust function and a PDF table are different kinds of knowledge and may require different parsers, renderers, validators, and relations.

    The goal is shared foundations, not forced uniformity.

    4.3 Making raw storage representation the public API¶

    Consumers should use stable semantic APIs rather than depend directly on database tables or backend-specific details.

    The internal persistence implementation must be able to evolve without forcing all clients to change.

    4.4 Eliminating textual representations¶

    Text files remain important because they are portable, familiar, editable, reviewable, and compatible with existing tools.

    The change is that they are treated as projections rather than the only canonical representation of meaning.

    5. Fundamental Concepts¶

    Scriberig distinguishes three different questions.

    5.1 What thing is this?¶

    An entity identifies conceptual continuity.

    A function, paragraph, session branch, or decision may continue to be the same conceptual entity while its content changes over time.

    This is represented by an EntityId or an equivalent stable handle.

    5.2 What exact state is this thing in?¶

    A revision identifies an exact immutable state of an entity.

    Revisions do not change in place.

    A change creates another revision.

    This is represented by a RevisionId or equivalent immutable identity.

    5.3 What exact state is the whole knowledge universe in?¶

    A snapshot identifies a complete consistent state of the knowledge store.

    A snapshot determines which revision of each relevant entity is current for that snapshot.

    Any canonical change creates a new snapshot identity.

    This is represented by a SnapshotId or equivalent root identity.

    These three concepts must not be conflated.

    Stable entity identity provides local continuity. Immutable revision identity provides exactness. Snapshot identity provides global certainty.

    6. Principle: Knowledge Is Structured¶

    Canonical knowledge should be represented in forms that preserve meaningful structure.

    Examples include:

    • sections and paragraphs instead of only Markdown bytes;
    • tables, rows, and cells instead of only text ranges;
    • functions, statements, and expressions instead of only source lines;
    • session branches, decisions, and tool results instead of only transcript strings.

    The canonical representation should preserve the distinctions that matter to the domain.

    The system should not aggressively normalize semantically or syntactically meaningful choices merely because two forms may currently behave similarly.

    7. Principle: Revisions Are Immutable¶

    Canonical revisions are never edited in place.

    A change produces a new revision.

    Historical revisions remain addressable while retained by history, branches, snapshots, or other roots.

    Immutability enables:

    • reliable caching;
    • reproducible analysis;
    • branch isolation;
    • exact historical references;
    • safe concurrent work;
    • deterministic comparison;
    • structural sharing.

    Implementations may optimize physical storage, but they must preserve the logical immutability of revisions.

    8. Principle: Local Stability and Global Certainty¶

    A change deep in the knowledge graph must not unnecessarily redefine the conceptual identity of every semantic ancestor.

    For example, editing the text of a paragraph should not imply that the containing document is a new conceptual document. Editing an expression should not imply that the containing function is a new conceptual function.

    Local entities retain stable identity while receiving new revisions.

    At the same time, the top-level snapshot must change whenever canonical knowledge changes.

    This is intentional.

    A snapshot identity is a compact assertion about the entire visible state of knowledge.

    Therefore:

    • local revisions are used for fine-grained caching and incremental work;
    • the global snapshot is used for consistency, reproducibility, synchronization, branching, and change detection.

    The system should preserve both properties rather than choosing one at the expense of the other.

    9. Principle: Projections Are Functions of Semantic State¶

    Files, transcripts, UI views, and model context are projections of semantic state.

    Conceptually:

    projection = render(semantic_state, projection_configuration)

    Examples:

    Markdown graph + Markdown style -> .md
Code graph + source style -> source file
Session graph + chat style -> transcript
Session graph + context policy -> model context
Knowledge graph + UI state -> browser view

    Formatting and presentation configuration should not become semantic content unless the domain explicitly requires them to be meaningful.

    A style change should not normally change the semantic identity of the underlying knowledge.

    10. Principle: Supported Projections Are Bidirectional¶

    Where editing is supported, projections must work in both directions.

    Rendering converts semantic state into an external representation.

    Import and reconciliation convert an edited external representation into semantic changes.

    Conceptually:

    semantic state
    -> render
projection
    -> external edit
edited projection
    -> parse and reconcile
semantic migration
    -> new snapshot

    External edits should not be blindly accepted as a replacement for canonical state.

    They should be interpreted as proposed semantic changes relative to known previous state.

    When both the semantic state and an external projection have changed independently, reconciliation should use a three-way model and surface conflicts instead of silently overwriting one side.

    11. Principle: Changes Are Explicit¶

    Canonical changes should be represented as explicit migrations or equivalent transitions between snapshots.

    A migration records what changed and where the new state came from.

    Possible sources include:

    • human edits;
    • agent edits;
    • API clients;
    • CLI commands;
    • web editing;
    • imports;
    • merges;
    • automated transformations.

    All write paths should converge on the same change model.

    The browser editor, CLI, TUI, external file watcher, agent runtime, and API server must not each invent separate mutation semantics.

    12. Principle: Derived Knowledge Is Separate and Provenanced¶

    Not every useful fact belongs in canonical state.

    Examples of derived knowledge include:

    • compiler analysis;
    • symbol resolution;
    • call graphs;
    • control-flow and data-flow information;
    • PDF extraction indexes;
    • descriptions;
    • summaries;
    • model-generated interpretations;
    • rendered intermediate representations;
    • validation results.

    Derived knowledge should record:

    • what it was derived from;
    • the exact revisions or configuration it depends on;
    • the producer or method used;
    • enough provenance to distinguish authoritative facts from generated interpretations.

    Derived knowledge should be recomputable.

    When its dependencies are unchanged, it should be reusable even if unrelated parts of the global snapshot changed.

    13. Principle: Progressive Disclosure Is the Default Agent Interface¶

    Agents should not be forced to reconstruct high-level structure from large raw inputs.

    The system already knows structure and should expose it directly.

    An agent should typically navigate from coarse information to fine detail.

    Examples:

    Project
  -> subsystem
    -> module
      -> function
        -> code group
          -> statement
            -> expression

    Document
  -> section
    -> subsection
      -> paragraph/table/list
        -> row/cell/item

    Session
  -> branch/topic
    -> episode
      -> turn
        -> message/tool result

    Container objects should expose short descriptions, useful counts, relations, and stable handles before exposing full content.

    Tool results should make useful next navigation actions obvious.

    14. Principle: One Interaction Grammar Across Domains¶

    The agent and external applications should learn one general way to interact with the knowledge store.

    The universal interaction vocabulary should support concepts such as:

    • inspect;
    • list;
    • follow relations;
    • find;
    • query;
    • describe;
    • compare;
    • inspect history;
    • render;
    • branch;
    • propose a change;
    • validate;
    • commit or merge.

    Domain-specific schemas may expose specialized relations and operations, but they should extend the common model rather than create unrelated access systems.

    This makes it possible for a simple agent to navigate code, sessions, PDFs, documents, and future domains with the same basic tool discipline.

    15. Principle: Sessions Are Knowledge¶

    Agent sessions are stored in the same universal system as project artifacts.

    A session is not fundamentally a flat transcript.

    It may contain structured objects such as:

    • goals;
    • human inputs;
    • agent outputs;
    • observations;
    • decisions;
    • questions;
    • tool invocations;
    • tool results;
    • branches;
    • branch results;
    • summaries;
    • tasks;
    • references to project entities.

    Session branches are first-class objects.

    A branch should have a short description of its purpose and, when completed, its outcome.

    Completed exploratory branches may be omitted from normal model context and represented by compact branch summaries while remaining fully retrievable.

    This allows long-running work without requiring the permanent context to grow as a flat transcript.

    16. Principle: Files and Line Numbers Are Not Primary Semantic Handles¶

    Files remain important projections, but semantic identity should not normally depend on file location or line number.

    A function moved to another file may still be the same conceptual function.

    A paragraph shifted by inserted text may still be the same conceptual paragraph.

    Agents and applications should prefer stable semantic handles.

    File paths and line positions may be supplied as useful projection metadata, but they should not be the primary identity system when a semantic object exists.

    17. Principle: Validation Precedes Promotion¶

    Proposed changes should be validated before they become the promoted project state when the domain supports validation.

    Validation may include:

    • structural checks;
    • parser checks;
    • schema checks;
    • compiler checks;
    • type checking;
    • linting;
    • tests;
    • application-specific invariants.

    Agent work should normally occur on isolated branches or workspaces derived from a known snapshot.

    Failed attempts must not corrupt the base snapshot.

    Successful work can be compared, reviewed, validated, and merged explicitly.

    18. Principle: Consumers Are Peers¶

    The CLI, API server, TUI, browser editor, external applications, and agent runtime are peers over the same application capabilities.

    No interface should contain unique core business logic that other interfaces cannot reuse.

    The server is not the conceptual owner of the system. It is one adapter exposing application operations remotely.

    The full web editor is not privileged. It should be implemented with the same public client, model, and UI libraries intended for third-party applications.

    An agent is also not privileged. It is a consumer of the same semantic APIs available to ordinary programs, with permissions and capabilities determining what it may access.

    19. Principle: Develop Capabilities Vertically¶

    A user-facing capability should evolve across the supported surfaces together.

    For example, when semantic diff becomes a product capability, the design should consider its presence in:

    • core application operations;
    • protocol types;
    • server API;
    • CLI;
    • TypeScript client;
    • reusable web libraries;
    • reference web application;
    • agent tools where appropriate.

    Not every internal primitive requires every surface, but product-level capabilities should not accumulate exclusively in one interface.

    This keeps the public libraries capable enough to build the full product and prevents the web application or agent runtime from depending on private shortcuts.

    20. Principle: Reusable Platform Below Integrated Product¶

    Scriberig should be useful in layers.

    A consumer may stop at the immutable storage layer.

    Another may use the universal graph and query model.

    Another may add Markdown, code, PDF, or projection support.

    Another may consume the API and reusable web libraries.

    The integrated Scriberig product adds sessions, agents, UI, orchestration, and opinionated workflows on top.

    Lower layers must not depend on higher product layers.

    In particular:

    The knowledge store must not know that agents exist.

    Domain adapters must also remain useful without the agent runtime.

    21. Principle: Domain Adapters Specialize, They Do Not Fork the Architecture¶

    Each supported domain may provide:

    • schemas;
    • parsers;
    • renderers;
    • reconciliation logic;
    • validators;
    • derived indexes;
    • specialized queries;
    • semantic operations;
    • UI views.

    But these should plug into the common storage, revision, snapshot, migration, query, and projection systems.

    A new domain should not require a new persistence model or a completely separate agent access protocol.

    22. Principle: Cache Exact Inputs, Not Incidental Containers¶

    Caching should depend on the smallest immutable inputs that determine a result.

    For example:

    • a rendered semantic fragment may depend on an object revision and style revision;
    • a function summary may depend on the function revision and summary profile;
    • a compiler analysis may depend on a function revision plus exact relevant dependency revisions and toolchain configuration;
    • a session branch summary may depend on the branch revision and summary profile.

    The global snapshot should not be used as a cache key when only a local revision is relevant.

    This prevents unrelated changes from invalidating useful work.

    23. Principle: Provenance and Trust Are Visible¶

    The system must distinguish between sources of information.

    Examples include:

    • user-authored;
    • parser-derived;
    • compiler-derived;
    • static-analysis-derived;
    • system-generated;
    • model-generated.

    An agent should be able to tell whether a statement is an authoritative structural fact or an interpretation generated by another model.

    Important conclusions and project decisions should retain references to the sessions, branches, tools, or artifacts from which they were derived.

    24. Principle: The System Is Inspectable at Multiple Levels¶

    Users and developers should be able to inspect the same state at different abstraction levels.

    The integrated editor should eventually support views such as:

    • raw entity and relation browsing;
    • revision and snapshot inspection;
    • migration history;
    • semantic document views;
    • source-code views;
    • projection views;
    • session and branch views;
    • agent commands scoped to selected semantic objects.

    A selection in one view should resolve to the same semantic entity used by the other views.

    This makes the system debuggable and allows low-level and high-level operations to coexist.

    25. Architectural Invariants¶

    Lower-level designs must preserve these invariants unless a later Level 1 decision explicitly replaces them.

    • Canonical knowledge is structured and typed.
    • Conceptual entity identity is distinct from exact revision identity.
    • Revisions are immutable.
    • A snapshot represents one exact consistent global state.
    • Canonical changes produce new snapshots.
    • Local semantic identity should remain stable across unrelated or presentation-only changes.
    • Files and transcripts are projections, not the universal storage primitive.
    • Supported editable projections can be reconciled back into semantic changes.
    • Formatting and style are separate from semantic content unless a domain explicitly makes them meaningful.
    • Changes from all write surfaces converge on a common migration/change model.
    • Derived knowledge records provenance and dependencies.
    • Derived results can be reused when their exact dependencies remain unchanged.
    • Agents use progressive semantic disclosure by default.
    • Sessions and their branches are stored as structured knowledge.
    • Domain adapters reuse the common storage and interaction architecture.
    • Storage and domain libraries remain useful without an agent runtime.
    • CLI, API, web, TUI, and agent surfaces consume shared application capabilities.
    • The reference web application uses public reusable libraries rather than private product-only mechanisms.
    • Validation can occur on isolated branches before a result is promoted.
    • Historical and concurrent states remain explicitly addressable.

    26. Measures of Success¶

    The architecture is succeeding when the following statements are true.

    26.1 A large project can be navigated without reading it all¶

    An agent can locate and inspect a small relevant semantic region without loading an entire repository, document, or session into context.

    26.2 Formatting changes are cheap¶

    Changing a rendering style does not invalidate semantic identity or unrelated model understanding.

    26.3 Local edits remain local¶

    Editing one paragraph, expression, or session branch preserves unrelated revisions and derived caches.

    26.4 Global change is still detectable immediately¶

    A snapshot identity provides a compact way to determine whether canonical knowledge changed at all.

    26.5 External tools remain usable¶

    Users can edit supported projections with ordinary editors and import those changes without abandoning semantic history.

    26.6 Multiple consumers use the same platform¶

    The CLI, API, browser, TUI, agent runtime, and third-party applications use the same underlying operations and semantic references.

    26.7 The integrated editor is reproducible by public APIs¶

    The official web application can be built from the same reusable packages available to other applications.

    26.8 Agent history does not grow without structure¶

    Completed exploratory work can collapse to descriptions and results while remaining retrievable through session branches.

    26.9 The storage layer remains independently valuable¶

    A consumer can use the knowledge store, revisions, snapshots, queries, and domain adapters without installing or running an agent.

    27. Design Direction¶

    The intended architecture can be summarized as:

                         Universal Knowledge Store
                              |
              entities + revisions + relations
                              |
                         snapshots
                              |
        +---------------------+----------------------+
        |                     |                      |
    domain models        derived knowledge       sessions
        |                     |                      |
        +---------------------+----------------------+
                              |
                    application operations
                              |
          +-------------------+-------------------+
          |                   |                   |
        CLI/API             Web/TUI             Agents
          |                   |                   |
          +-------------------+-------------------+
                              |
                       semantic changes
                              |
                          migrations
                              |
                         new snapshot

    External projections such as files participate through render and reconciliation paths rather than bypassing this model.

    The architecture should remain understandable from this diagram even as individual domain adapters and product surfaces become sophisticated.

    28. Guidance for Lower-Level Design¶

    Level 2 documents may choose concrete architectures, crate boundaries, schemas, algorithms, protocol types, and library APIs as long as they preserve the principles in this document.

    Level 3 documents may define exact implementation tasks, acceptance tests, files to modify, and focused instructions for implementation agents.

    When implementation pressure conflicts with a principle in this document, the conflict should be made explicit. A local implementation shortcut should not silently redefine a Level 1 architectural decision.
