    Agent Profiles, Context Composition, and Evidence-Driven Optimization¶

    1. Purpose¶

    This document defines how Scriberig constructs the behavioral instructions supplied to models, how those instructions relate to recursive branch execution, and how agent behavior may be improved from execution evidence without turning prompt files into canonical state.

    It refines, but does not replace:

    1. 009. agent interaction and sessions.md;
    2. 016. model driven agent execution and branch isolation.md;
    3. 017. recursive agent decomposition and context isolation.md;
    4. 018. durable plans dependency scheduling and multi-model execution.md;
    5. 019. semantic agent operations and projection-first editing.md;
    6. 020. provider continuation state and observable model execution.md.

    The controlling rules are:

    Agent behavior is a versioned semantic configuration compiled into each effective model request. Prompt text is a projection of that configuration, not its canonical identity.

    A branch is a context-isolation frame, not automatically a new agent. The same executor may enter a child branch, work with additional branch-local context, finalize a compact durable result, and resume its parent context without inheriting the child transcript.

    Non-root branch completion is a handoff boundary. The executing model should make its final response a compact parent-consumable summary because that output is the natural source of BranchResult.summary; a second summarization model call is not required by default.

    Automated changes to agent behavior should be justified by durable execution evidence and promoted through the same candidate, validation, conflict, and revision discipline used elsewhere in Scriberig.

    2. Branch, Executor, Agent Profile, and Model Invocation Are Different Concepts¶

    Do not use branch, agent, executor, profile, and model invocation as synonyms.

    Conceptually:

    Branch
  -> canonical context-isolation scope in the session tree

Executor
  -> the active owner performing work in a branch

AgentProfile
  -> reusable versioned behavior/context configuration used by an executor

ModelInvocation
  -> one provider-neutral model request/response step inside a branch

    A common recursive execution therefore looks like:

    executor E using profile P at parent context X
  |
  +-- enter child branch B
  |     effective context = X + selected branch-local frame B
  |     model invocation
  |     tool/semantic operation
  |     model invocation
  |     final compact branch response R
  |     -> BranchResult(B, summary = R, handles = ...)
  |
  +-- resume parent
        effective context = X + selected durable result of B

    The child branch does not become a different executor merely because it is a child.

    A branch may instead be explicitly assigned another executor/model/profile. That is an execution-assignment decision layered onto the same branch topology:

    branch B
  executor E1 / profile P1 / model M1

branch C
  executor E2 / profile P2 / model M2

    The session architecture is unchanged in both cases.

    3. Context Frames and Context Compilation¶

    The useful mental model for recursive execution is push/pop of context frames:

    X
X + B
X + B + B1
X + B + B1 + B1a

    and then:

    X + B + B1 + B1a
        -> finalize B1a
X + B + B1 + BranchResult(B1a)
        -> finalize B1
X + B + BranchResult(B1)
        -> finalize B
X + BranchResult(B)

    This is a semantic model, not a requirement to concatenate byte-identical prompt strings.

    X means the parent's canonical effective context contract: the selected instructions, results, semantic scope, decisions, local history, capabilities, and execution configuration that Scriberig would compile for that parent location.

    The context compiler remains authoritative. It may reconstruct X + B from canonical session and semantic state rather than literally copying a provider request or parent transcript.

    Therefore both of these statements remain true:

    1. entering a normal child branch conceptually extends the current executor context with a focused child frame;
    2. child context is selected and compiled, not implemented by blindly copying the complete parent transcript.

    When the child frame is popped, child-local working history does not become parent-local history. The parent receives selected durable results and semantic state.

    4. Branches Do Not Imply New Provider Conversations or New Agents¶

    Branch topology and provider continuation are related but distinct.

    A provider continuation may be established independently for a child so that provider-local state cannot leak between branches. This does not mean Scriberig has created a new canonical agent identity.

    Likewise, a runtime may instantiate another provider client object or ProviderModel value for a child. That is an implementation detail unless the branch has a distinct executor/profile assignment.

    Use terminology carefully:

    child branch
nested branch
branch executor
branch assignment

    Prefer those terms over child agent when the only semantic change is context isolation.

    Reserve language such as different executor, different agent profile, or different model assignment for an actual execution-configuration distinction.

    5. Non-Root Branch Final Output Is a Handoff Contract¶

    A non-root branch normally exists so its internal work can be collapsed when control returns to the parent.

    The final model response of a successful non-root branch should therefore be intentionally shaped for BranchResult consumption.

    The default behavioral instruction should be equivalent to:

    When you are about to finish a non-root branch, make your final response a
compact one-paragraph summary for the parent. State the important outcome,
decisions or discoveries, remaining issues, and durable semantic/result
handles the parent may need. Do not reproduce the branch transcript or hidden
reasoning.

    The exact wording may evolve through profile revisions. The semantic contract is more important than one literal prompt string.

    The summary should be:

    • compact enough to keep parent context bounded;
    • specific enough that the parent can continue without reopening the branch in normal cases;
    • explicit about failure or unresolved questions;
    • grounded in durable result handles when exact state matters;
    • free of hidden chain-of-thought or transcript reconstruction.

    A branch result may carry structured fields in addition to the paragraph. The paragraph is not a substitute for exact handles, validations, candidate identities, touched entities, or unresolved-question identities.

    6. Root Completion Is Different¶

    The root branch normally ends in user-facing output.

    Do not force the non-root one-paragraph handoff format onto root completion. The root response may be long, structured, tabular, code-heavy, or otherwise shaped by the user's request.

    Conceptually:

    if branch is non-root:
    final output -> compact parent handoff
else:
    final output -> normal user-facing response

    A root BranchResult.summary may still be populated from the root output for durability, but that storage convenience does not constrain the user-facing response format.

    7. Do Not Add a Summarizer Call by Default¶

    Scriberig already has the strongest participant available at branch completion: the executor that performed the work and has the branch-local context.

    The default completion path should be:

    branch-local execution
  -> executor's final compact handoff response
  -> durable BranchResult.summary
  -> parent consumes BranchResult

    not:

    branch-local execution
  -> arbitrary final response
  -> second model call that re-reads/summarizes branch history
  -> BranchResult.summary

    A separate summarizer may exist later as an explicit policy for exceptional cases, archival compaction, migration of legacy histories, or quality repair. It is not the ordinary branch-completion mechanism.

    Avoiding the extra call reduces cost, latency, attribution ambiguity, and the risk that a summarizer drops exact result information the branch executor already knows.

    8. Agent Profiles Are Versioned Semantic Configuration¶

    An AgentProfile is reusable configuration that determines how an executor behaves and how context is assembled.

    Conceptually:

    AgentProfile
  identity
  revision
  name/description
  context components
  preferred execution configuration references
  context policy reference
  branching policy reference
  tool/capability exposure policy
  runtime policy references

    Profiles are not session identities and are not provider conversation identities.

    A branch/model invocation records the exact effective profile revision used so historical execution can be explained and compared.

    A profile may be selected by project/user defaults, session selection, branch assignment, plan-node assignment, or explicit invocation override according to the execution-resolution rules defined elsewhere.

    9. Context Components Are First-Class¶

    Do not model the entire agent prompt as one opaque mutable string.

    A profile should resolve to ordered, typed context components conceptually equivalent to:

    ContextComponent
  identity
  revision
  kind
  content
  activation rule
  scope/applicability
  priority/order
  estimated context cost
  provenance
  status

    Useful component kinds include:

    CoreInvariant
BehaviorPolicy
DomainGuidance
ToolGuidance
SkillTrigger
ExecutionLesson

    The exact type names belong in lower-level design. The architectural distinction matters:

    • CoreInvariant protects architecture/safety behavior that should usually be present;
    • BehaviorPolicy tells the executor how to work;
    • DomainGuidance supplies domain/practitioner knowledge;
    • ToolGuidance explains non-obvious capability use;
    • SkillTrigger activates a bounded procedure when a recognizable condition holds;
    • ExecutionLesson is learned derived guidance backed by execution evidence.

    A rendered system prompt or provider message is a projection of activated components plus branch/session context.

    10. Always-On Prompt Space Is Expensive¶

    Every always-on instruction competes with the actual task, semantic state, tool schemas, dependency results, and local branch history.

    Prefer the narrowest mechanism that reliably produces the required behavior.

    Conceptually:

    mechanical deterministic behavior
  -> runtime/application code

recognized bounded procedure
  -> activated skill/procedure component

tool-specific behavior
  -> tool descriptor/guidance activated with the tool

domain-specific knowledge
  -> domain guidance activated by semantic scope

cross-cutting model behavior that cannot be mechanical
  -> short always-on behavior/core component

    Do not accumulate every observed failure as another permanent paragraph in the base prompt.

    When adding always-on guidance, consider whether existing prose can be removed, narrowed, moved to a trigger, or implemented mechanically.

    11. The Core Always-On Invariants Should Remain Small¶

    The default profile should carry a short architecture-oriented invariant set equivalent in meaning to:

    You operate inside one Scriberig branch/context frame.
Prefer semantic entities and domain operations over raw files when the domain is understood.
Files/rendered documents are projections; raw writes are fallback behavior.
Canonical mutations use the shared candidate/migration/validation/promotion path.
Use stable semantic handles and exact snapshot/revision references when exact state matters.
Use child branches for focused context isolation when useful; a child branch does not by itself imply another agent.
Parents and dependencies consume compact durable results, not child transcripts.
Use capabilities progressively rather than assuming unrestricted filesystem, shell, or database access.

    This is a semantic baseline, not immutable literal prose. Its effective revision must be observable as part of the complete model request.

    12. Activation Is Part of Context Identity¶

    For a model invocation, Scriberig resolves which context components are active from exact state such as:

    agent profile revision
branch role: root or non-root
branch purpose/policy
semantic/domain scope
available capabilities/tools
plan-node assignment
accepted project/session policy
explicit user/branch overrides
applicable execution lessons

    The activated set and its order are output-relevant inputs. They therefore participate in canonical effective request identity and request fingerprinting.

    Full prompt inspection must make it possible to determine which exact component revisions were active, even if the presentation renders them as combined prose.

    Changing UI prompt visibility must not alter activation.

    13. Behavior Policy and Domain Knowledge Must Stay Distinct¶

    A useful optimization boundary is:

    BehaviorPolicy
  -> how the executor should reason/work/use capabilities

DomainGuidance
  -> knowledge about the subject/domain being worked on

    Do not hide project facts inside generic agent behavior instructions.

    A fact about one exact project/snapshot belongs to semantic project state or derived knowledge tied to exact provenance.

    A general reusable procedure may belong to domain guidance or a skill.

    This prevents accidental transfer of task-specific facts into unrelated future tasks.

    14. Execution Lessons Are Derived Knowledge with Provenance¶

    Scriberig may learn reusable execution guidance from completed work, but such guidance is derived knowledge rather than unquestioned canonical truth.

    Conceptually:

    ExecutionLesson
  identity
  revision
  cue
  lesson/operation guidance
  applicability scope
  evidence references
  confidence
  source experiment/run
  producer/model/profile provenance
  status

    An execution lesson should answer:

    • when is this lesson relevant;
    • what behavior should change;
    • what evidence supports the lesson;
    • how confident are we;
    • which runs/profile revisions produced the evidence;
    • whether later evidence has superseded or contradicted it.

    Do not use an unstructured mutable MEMORY.md as canonical learned behavior.

    A Markdown or configuration representation may exist as a projection/import/export surface.

    15. Prompt/Profile Changes Need Evidence¶

    Manual profile editing is allowed through normal authorized semantic change flows.

    Automated or optimization-driven changes should normally be traceable to observed execution evidence.

    Strong evidence may include:

    repeated failure of the base profile
behavioral divergence between candidate profiles
compiler/test/domain validation results
incorrect tool choice with visible consequence
missing branch-result information that forced reopening
context bloat that displaced required task information
successful correction repeated across independent tasks

    Weak evidence includes hypothetical risk without an observed trajectory, simple agreement between two model outputs, or the fact that a candidate happened to be adopted.

    When evidence is insufficient, retaining the current profile is a valid outcome.

    16. Prompt Experiments Are Structured Knowledge¶

    A profile optimization run should be represented durably rather than existing only as an ad-hoc transcript.

    Conceptually:

    PromptExperiment
  identity
  base profile revision
  task/branch or evaluation case
  candidate profile revisions
  probe branches/results
  behavioral differences
  validation evidence
  composition decision
  attribution assessments
  resulting candidate/profile revision

    Attribution should allow states equivalent to:

    helped
hurt
no observed effect
confounded

    Prefer confounded when the experiment does not isolate causality.

    Adoption of a profile revision is not proof that every included component helped.

    17. Propose-Probe-Compose Maps onto Existing Scriberig Structures¶

    A useful evidence-driven optimization pattern is:

    base profile
  |
  +-- baseline probe branch
  |
  +-- candidate A proposal
  |     -> candidate probe branch
  |
  +-- candidate B proposal
  |     -> candidate probe branch
  |
  +-- compose/evaluate plan node
        depends_on all required probe BranchResults
        -> validation
        -> selected/promoted candidate or keep-base
        -> optional ExecutionLesson

    This uses existing architecture:

    • branches isolate attempts;
    • plan dependencies coordinate probes;
    • BranchResults satisfy dependencies;
    • validators provide stronger evidence than model preference alone;
    • candidate/revision semantics preserve alternatives;
    • one coordinator owns automatic experiment advancement.

    Do not share candidate transcripts merely to make the composer aware of results. Supply compact results, exact profile/component identities, validation evidence, and explicitly selected behavioral contrasts.

    18. Candidate Profiles Use the Normal Change Discipline¶

    Automatically proposed profile/context changes are not privileged direct writes.

    Their lifecycle should follow the same architectural shape used for other canonical change:

    current AgentProfile revision
  -> candidate profile/component revisions
  -> probe/evaluation branches
  -> validation/evidence assessment
  -> conflict/policy review when needed
  -> promotion
  -> new current profile revision

    If profiles/components are represented through files for interoperability, those files remain projections when the semantic domain is understood.

    Do not let an optimizer overwrite AGENTS.md, prompt files, or provider configuration directly and thereby bypass Scriberig's revision/change model.

    19. Validators Are Preferred over Model Self-Approval¶

    When an experiment changes behavior that has objectively testable consequences, use the strongest available validator.

    Examples:

    source edit quality
  -> compiler/tests/domain validators

branch result completeness
  -> structured contract checks + parent consumption test

tool policy
  -> capability/audit assertions

context isolation
  -> deterministic compiled-context tests

provider continuation isolation
  -> lineage/fingerprint tests

    Model comparison may contribute evidence where no deterministic validator exists, but it should not replace available deterministic evidence.

    20. Full Effective Prompt Includes Profile/Component Identity¶

    The complete safe effective request defined by 020 must be able to answer not only "what text was sent/effective?" but also:

    which AgentProfile revision was resolved
which ContextComponent revisions activated
why conditional components activated when retained safely
what branch role/purpose applied
what semantic/dependency results were selected
what tool/capability definitions were active
what provider/model/thinking configuration was resolved

    Provider serialization may flatten this into ordinary messages. The provider-neutral retained request remains the observability boundary.

    This enables reproducible comparison between profile revisions and makes evidence-driven optimization auditable.

    21. Profile Selection and Executor Assignment Are Independent¶

    A branch may continue with the same executor while using the same profile, or it may explicitly resolve another profile/model assignment.

    Examples:

    same executor, same profile, child context frame
same executor identity, explicit branch profile override
different worker executor assigned by plan node
different model/provider profile for a competing sibling attempt

    Do not infer an executor change from branch creation alone.

    One branch still normally has one active executing owner. Competing attempts use sibling branches.

    22. Context Restoration and Provider Continuation¶

    When a same-executor child branch completes, Scriberig conceptually returns to the parent's canonical context frame plus selected durable child results.

    A provider continuation that advanced inside the child cannot be treated as though it were rewound to the parent state.

    Therefore:

    • parent and child provider-continuation lineages remain isolated according to 020;
    • the parent may resume compatible parent continuation state if it still represents the canonical parent lineage;
    • otherwise Scriberig recompiles/reseeds from canonical parent context;
    • child continuation state never defines parent context;
    • losing either continuation remains recoverable from Scriberig state.

    The push/pop context model is canonical Scriberig semantics, not a demand that a provider support conversation rewind.

    23. Product Surfaces Do Not Own Prompt Semantics¶

    CLI, TUI, web, server, clients, and editor surfaces may:

    • select an available profile or branch assignment when authorized;
    • inspect resolved profile/component provenance;
    • inspect prompt presentation according to visibility policy;
    • observe experiment/lesson state;
    • request authorized profile changes through shared application semantics.

    They must not independently concatenate prompts, inject hidden tool guidance, mutate learned lessons, or implement their own branch-final summary rules.

    Context composition belongs in shared agent/runtime/application semantics.

    24. Initial Implementation Priority¶

    The first implementation should not begin with an autonomous prompt optimizer.

    Prioritize in this order:

    1. make branch/executor terminology explicit in code/design;
    2. add a short Scriberig core behavior component to the effective model request;
    3. add the non-root branch final-handoff component and prove it is absent from root behavior;
    4. retain exact profile/component revision identity in compiled/effective request provenance;
    5. make profile/context components first-class and activation deterministic;
    6. add durable experiment/evidence/lesson structures;
    7. only then add automated propose/probe/compose orchestration and promotion policy.

    This order produces immediate prompt-quality benefits while keeping later optimization auditable.

    25. Architectural Invariants¶

    Implementations must preserve these invariants.

    1. A branch is a context-isolation frame; it does not automatically imply a new agent/executor.
    2. The same executor may recursively enter and leave child context frames.
    3. Child context is deterministically selected/compiled; it is not the unbounded parent transcript.
    4. Finishing a child restores parent canonical context plus selected durable results, not child working history.
    5. A non-root final response is a compact parent handoff and is the default source of BranchResult.summary.
    6. Root output remains user-facing and is not forced into the child-summary format.
    7. No extra summarizer model call is required for ordinary branch completion.
    8. Agent/profile instructions are versioned semantic configuration, not an opaque mutable prompt file.
    9. Activated context components participate in request identity and complete prompt observability.
    10. Always-on prompt content remains intentionally small; deterministic behavior belongs in code when possible.
    11. Project facts, domain guidance, behavior policy, and learned execution lessons remain distinguishable.
    12. Learned lessons carry evidence, scope, confidence, and provenance.
    13. Automated profile changes require evidence and use candidate/validation/promotion semantics.
    14. Prompt experiments use branches/results/plans rather than transcript sharing.
    15. Provider continuation never replaces canonical context push/pop semantics.
    16. Product presentation state never changes profile activation or execution semantics.
    17. Hidden chain-of-thought is never required for profile optimization or observability.

    26. Non-Goals¶

    This design does not require:

    • treating every child branch as a separate agent;
    • byte-for-byte inheritance of a parent provider request;
    • copying the complete parent transcript into a child;
    • copying the complete child transcript back into a parent;
    • an extra model call to summarize every completed branch;
    • one universal model/provider for all branches;
    • putting every skill/domain rule in always-on system prose;
    • letting an optimizer directly rewrite prompt files or AGENTS.md;
    • trusting model self-evaluation when deterministic validators exist;
    • transferring exact task/project facts into generic learned behavior;
    • exposing hidden chain-of-thought;
    • implementing automated profile optimization before deterministic profile/context composition exists.

    27. Definition¶

    Scriberig agent behavior is the deterministic, provider-neutral resolution of a versioned AgentProfile, its activated context components, exact branch/session/semantic state, durable ancestor/dependency results, capability/tool contracts, and execution configuration into one effective model request.

    Recursive branch execution pushes focused context frames over that behavior without inherently changing agent identity. Non-root branches finish by returning compact durable handoffs. Profile improvement is itself structured semantic work: proposed from evidence, probed in isolated branches, validated, attributed cautiously, and promoted as a new revision rather than silently accumulated as prompt text.
