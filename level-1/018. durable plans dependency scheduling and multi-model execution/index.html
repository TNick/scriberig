    Durable Plans, Dependency Scheduling, and Multi-Model Execution¶

    1. Purpose¶

    Scriberig must support long-running agent work that is planned, inspectable, interruptible, revisable, and executable by more than one model without collapsing into one ever-growing transcript.

    This document refines the session and agent architecture defined by:

    1. 009. agent interaction and sessions.md;
    2. 016. model driven agent execution and branch isolation.md;
    3. 017. recursive agent decomposition and context isolation.md;
    4. design/level-2/023. agent runtime model provider and branch orchestration.md.

    The controlling rule is:

    A plan is durable semantic knowledge that describes intended branch work and explicit dependencies. The plan is rendered through the same session tree as executed work, while scheduling remains a separate graph over that tree.

    The session branch tree remains the canonical structure for context ownership and recursive decomposition. A plan does not replace it with a generic DAG. Instead, plan nodes bind intended work to branch identities or future branch identities, and explicit dependency edges determine when those nodes are eligible to run.

    2. Why Plans Are First-Class¶

    A prose checklist in one model response is insufficient for long-running work because it has no durable identity, cannot be safely revised, cannot be assigned to another executor, cannot express scheduling dependencies precisely, and cannot survive product restart without reparsing text.

    Scriberig therefore treats a plan as structured session knowledge.

    A plan must be able to answer:

    • what is the overall goal;
    • which focused tasks exist;
    • how those tasks are nested;
    • which tasks are blocked by which other tasks;
    • which tasks are ready, running, completed, failed, skipped, or cancelled;
    • which model/profile/provider is assigned to a task;
    • which branch and semantic scope execute a task;
    • which result fulfills a dependency;
    • which revision of the plan is current;
    • who or what changed the plan;
    • which single coordinator is allowed to auto-advance the plan.

    The full plan remains inspectable after execution completes.

    3. /plan Creates Structured Planned Work¶

    The TUI command:

    /plan <goal>

    is a local product command that starts or requests plan construction through shared application semantics. It is not sent to the model as ordinary conversation text.

    A generated plan is represented conceptually as:

    Plan
  identity
  session
  anchor
  goal
  revision
  status
  coordinator assignment
  root plan nodes

    and:

    PlanNode
  identity
  plan
  parent plan node, if any
  branch or future branch identity
  purpose
  expected result shape
  semantic scope
  dependencies
  assignment
  scheduling state
  branch policy
  capability scope

    Exact storage types belong in lower-level design. The architectural requirement is stable identity and structured relations rather than text parsing.

    4. The Plan Reuses the Session Tree¶

    Planned work should be visible in the same tree that later contains execution.

    A node may begin as:

    ○ Implement PHP parser

    then become:

    ◉ Implement PHP parser

    and finally:

    ✓ Implement PHP parser
  PHP parser domain entities created and validated

    The logical node should retain stable identity through these states.

    The execution branch associated with the plan node is the context-isolation boundary. Planning metadata does not replace branch semantics.

    A plan may reserve future branch identities before execution begins, or bind a plan node to a branch when the node is claimed. The lower-level design may choose either strategy as long as stable plan-node identity is preserved and product surfaces can correlate planning with execution.

    5. Tree Structure and Dependency Structure Are Different¶

    Two different relations coexist.

    5.1 Structural parent/child relation¶

    This means:

    • context ownership;
    • decomposition;
    • result collapse;
    • provenance;
    • visible nesting.

    Example:

    Implement feature
  Implement parser
    Validate parser

    5.2 Dependency relation¶

    This means:

    this node is not eligible to execute until another node has produced the required terminal result.

    Example:

    Parser --------\
                -> Integration
Importer ------/

    Parser and Importer may both be structural children of the same parent while Integration depends on both.

    Do not encode dependency by inventing fake parentage. Do not infer dependency only from display order.

    The structural branch relation is tree-like. Dependency edges form an acyclic graph over plan nodes.

    6. Dependency Satisfaction Is Result-Based¶

    A dependency is not fulfilled merely because another process stopped running.

    The prerequisite node must reach a dependency-satisfying terminal state and publish the result required by its contract.

    Normally this is a durable BranchResult or another explicit result handle.

    Conceptually:

    PlanNode parser
  expected result:
    ParserImplementationResult

BranchResult BR42
  fulfills: ParserImplementationResult
  status: completed
  semantic handles: ...
  candidate/workspace: ...
  validation evidence: ...

    A dependent node receives the compact result and selected semantic state, not the prerequisite branch transcript.

    A failed, cancelled, or budget-exhausted prerequisite does not satisfy a success dependency unless the dependency explicitly accepts that result class.

    Initial implementation should support strict successful dependencies before introducing optional or soft dependencies.

    7. Dependency Graph Rules¶

    The plan subsystem must enforce at least these invariants:

    1. dependency edges refer to stable plan-node identities;
    2. dependency cycles are rejected;
    3. a node cannot become Ready while a required dependency is incomplete;
    4. a node cannot be claimed by two executors simultaneously;
    5. completion is recorded before dependents become ready;
    6. dependency-result handles are exact and revision/snapshot aware;
    7. removing or replacing a dependency creates a new plan revision rather than rewriting historical meaning;
    8. dependency order is not inferred from wall-clock creation order;
    9. sibling nodes may run concurrently when their dependencies and workspaces permit it.

    A simple readiness rule is:

    Ready(node) =
  node is planned
  AND every required dependency has an accepted terminal result
  AND node is not claimed or terminal
  AND branch/capability/runtime policy permits execution

    8. One Auto-Advancing Coordinator¶

    A plan has at most one auto-advancing coordinator at a time.

    The coordinator is responsible for plan-level orchestration such as:

    • inspecting plan state;
    • selecting ready unassigned work;
    • dispatching work according to policy;
    • consuming compact child results;
    • reacting to failures;
    • adding further decomposition when necessary;
    • updating dependencies;
    • revising the plan;
    • deciding when the plan is complete.

    The coordinator is not the only model allowed to execute work. It is the single owner of automatic plan advancement.

    This prevents several concurrent models from racing to reorganize the same global plan.

    Coordinator ownership must be represented as a claim/lease or equivalent application-level concurrency contract rather than process-local UI state.

    9. Workers Execute Focused Branches¶

    A worker is assigned one branch or one ready plan node at a time.

    A worker receives a bounded execution contract equivalent to:

    plan node identity
branch identity
purpose
expected result
selected dependency results
selected ancestor results
semantic scope
exact base snapshot/workspace
capability subset
agent/model profile
thinking level
context policy
branch policy
runtime budgets

    A worker does not automatically gain authority over unrelated siblings or the whole plan.

    A worker may recursively decompose its own branch when branch policy allows it. Such descendants remain under the worker's branch and return compact results according to ordinary branch-isolation rules.

    10. Multiple Models May Work on One Plan Concurrently¶

    Scriberig intentionally supports different executors on different branches of the same session tree.

    For example:

    Discover architecture
  model/profile: local-fast

Implement parser
  model/profile: openai-codex-high

Research language edge cases
  model/profile: openrouter-research

Documentation cleanup
  model/profile: local-cheap

    These assignments are ordinary execution metadata and provenance, not different session architectures.

    Each branch resolves and snapshots its effective execution configuration when execution begins.

    Changing the assignment of a node that has not started affects that future execution. Changing defaults does not mutate an already-running model invocation.

    11. Per-Branch Execution Configuration¶

    Model selection must remain hierarchical and explicit.

    Resolution should follow an order equivalent to:

    explicit invocation override
  > plan-node assignment
  > branch override
  > session selection
  > project/user default
  > runtime fallback

    A plan-node or branch assignment may select a reusable profile containing concepts such as:

    provider profile
model profile
credential reference
thinking level
context policy
branching policy
capability scope
runtime budgets
default generation parameters

    Secrets remain opaque credential references. They are never stored in session history, plan records, prompts, or protocol traces.

    The existing model-library and thinking-level architecture remains the source of model capability truth. Do not create a second planner-only model registry.

    12. One Executing Owner per Branch¶

    Multiple models may execute different branches concurrently, but one branch should normally have at most one active executing owner.

    Use an application/runtime claim equivalent to:

    BranchExecutionLease
  branch
  executor identity
  operation
  observed revision
  lease/heartbeat metadata when remote execution requires it

    If two models should independently attempt the same goal, create sibling attempt branches:

    Implement parser
  Attempt A — model X
  Attempt B — model Y
  Compare/select — depends on A and B

    Do not allow two providers to race mutations inside one branch merely because parallel execution is available.

    13. Concurrent Project Work Remains Isolated¶

    Two completed worker branches may produce two independent candidate workspaces derived from the same base snapshot.

    Dependency completion makes both results available. It does not silently merge them.

    A later integration node must explicitly combine them using the normal semantic merge/change machinery.

    For example:

    Parser branch -> Candidate PA
Importer branch -> Candidate PB

Integration branch
  depends on Parser, Importer
  merges PA + PB against common base
  resolves semantic conflicts if any
  produces Candidate PC

    This preserves exact history and prevents dependency scheduling from becoming a hidden canonical mutation path.

    14. Plan Revisions Are Durable¶

    Long-running plans evolve.

    A failure may reveal missing work. A user may reorder priorities. New semantic facts may require additional branches. A dependency may become unnecessary.

    Changes to plan structure create a new durable plan revision or equivalent immutable historical state.

    For example:

    Plan revision 1
  Parser -> Tests

Parser discovers unsupported type representation

Plan revision 2
  Investigate representation
    -> Extend type model
    -> Parser
    -> Tests

    The normal UI shows the current plan. History/debug views can inspect earlier revisions and provenance.

    Do not overwrite a completed historical plan shape as though it never existed.

    15. Replanning Is an Explicit Coordinator Operation¶

    Replanning may be triggered by:

    • user request;
    • failed branch result;
    • blocked dependency;
    • conflict;
    • budget exhaustion;
    • newly discovered semantic requirement;
    • coordinator policy.

    The coordinator may propose a revised plan through shared application semantics.

    Plan revision must validate:

    • parent/child structure;
    • dependency acyclicity;
    • references to existing completed work;
    • assignments and capability compatibility;
    • preservation of terminal historical nodes;
    • consistency of any migrated or superseded node relationships.

    Replanning is not hidden chain-of-thought. The durable plan is the externally meaningful planning artifact.

    16. /plan Lifecycle¶

    Product surfaces should expose semantics equivalent to:

    /plan <goal>      create/propose a structured plan at the current anchor
/plan start       begin coordinator auto-advancement
/plan pause       stop new automatic dispatch while preserving running work policy
/plan resume      resume automatic dispatch
/plan replan      request a revised plan from current state
/plan stop        request cancellation/terminal stop according to policy
/plan show        return to/focus the plan tree

    Exact command spelling is a product-surface detail, but the underlying operations must be shared.

    Recommended initial behavior is that /plan <goal> creates a reviewable plan before execution. A separate explicit start action begins long-running autonomous work.

    An optional later shortcut such as /plan --run <goal> may combine those actions when policy permits it.

    17. Coordinator Cursor and User Reply Anchor Are Distinct¶

    A running plan has a coordinator position indicating the node the auto-advancing coordinator is currently working from or evaluating.

    The user interface also has a reply anchor indicating where the next human message will attach.

    These concepts normally coincide while the user is simply watching, but they must not be the same state.

    Rules:

    1. while the user is idle and following the plan, the reply anchor may auto-follow the coordinator cursor;
    2. if the user deliberately selects a historical or sibling node, the reply anchor becomes pinned there;
    3. coordinator progress must not move the user's anchor out from under a partially written message;
    4. the user can explicitly resume following the coordinator;
    5. both positions resolve to stable session/plan identities, never terminal row numbers.

    This distinction becomes necessary as soon as more than one worker can run concurrently.

    18. TUI Rendering¶

    The default TUI conversation/tree projection should render planned and executed work together.

    A compact example:

    You
Implement PHP ingestion.

/ Plan: PHP ingestion
▏ ✓ Discover architecture                      local-fast
▏ ◉ Implement parser                           openai-codex
▏ ○ Implement importer                         openrouter-claude
▏   waits: parser
▏ ◉ Research PHP edge cases                    local-research
▏ ○ Integration                                openai-codex
    waits: parser, importer, research

    Expanded execution may show nested semantic operations and child branches beneath a running node.

    Planned/blocked/running/completed state must have textual or symbolic cues in addition to color.

    Dependency information should be compact by default and inspectable in more detail on demand.

    19. Auto-Follow Is Presentation State¶

    While a plan runs, the TUI may follow coordinator progress automatically.

    Recommended behavior:

    user idle -> viewport follows coordinator
user scrolls/selects -> follow pauses
explicit follow action -> resume coordinator follow

    Viewport following is disposable presentation state. It does not affect scheduling, branch context, or plan state.

    20. Human Intervention Uses the Same Tree¶

    The user may:

    • select a planned node and change its assignment before it runs;
    • add a message at a historical or current branch anchor;
    • request replanning;
    • pause automatic dispatch;
    • cancel a branch when authorized;
    • create an explicit alternative branch;
    • inspect or expand any retained child branch;
    • assign a specific model/profile to a ready node;
    • leave some nodes unassigned for coordinator policy to select.

    Human intervention does not require a parallel session model.

    21. Context Compilation for Planned Work¶

    A worker context is compiled from exact semantic dependencies, not from everything visible in the TUI.

    Conceptually:

    Worker context =
    branch purpose and expected result
  + selected ancestor descriptors/results
  + fulfilled dependency results
  + exact semantic selection and project state
  + current branch local history
  + accepted decisions/open tasks selected by policy
  + capability-filtered tool catalog
  + model/profile instructions

    It normally excludes:

    sibling transcripts
resolved implementation chatter from dependencies
unrelated plan history
collapsed or expanded UI state
other models' raw provider streams

    Dependency result handles therefore become first-class context inputs.

    22. Streaming and Durable Scheduling State¶

    Streaming model/tool activity is transient observation. Scheduling state changes are durable semantic/application state at meaningful boundaries.

    Examples of durable events/records include:

    plan created
plan revision accepted
node became ready
node claimed
branch execution started
branch result committed
node completed/failed/cancelled
coordinator changed
assignment changed

    A reconnecting TUI or web client must be able to rebuild plan state from durable records plus current live events. It must not require replaying provider token streams.

    23. Failure Behavior¶

    A failed worker does not automatically destroy the whole plan.

    The plan/coordinator policy decides whether to:

    • retry the same branch;
    • create a repair child;
    • create an alternative sibling attempt;
    • replan;
    • mark dependents blocked;
    • skip optional future work;
    • stop the plan.

    Failure results remain compact durable BranchResult/node results with inspectable provenance.

    The coordinator must not silently treat failure as successful dependency satisfaction.

    24. Cancellation and Pause¶

    Pause and cancellation are distinct.

    pause means the coordinator stops dispatching new automatic work according to policy. Existing workers may continue or may be paused only if the runtime supports safe suspension.

    cancel targets a specific operation/branch/plan and follows ordinary application cancellation semantics.

    Stopping a plan does not erase completed branch history or accepted candidate state.

    25. Cross-Surface Invariant¶

    The durable plan, dependency edges, assignments, branch claims, results, and coordinator state are shared application semantics.

    TUI, web, CLI, server, and third-party clients must observe the same plan topology and execution status.

    The TUI may provide /plan and /assign shortcuts, but it must not become the owner of planning/scheduling state.

    26. Non-Negotiable Summary¶

    Future designs and implementations must preserve these rules:

    1. /plan produces structured durable planned work, not only prose.
    2. Planned work is visible in the same session tree as executed work.
    3. Branch parentage expresses context/decomposition; dependency edges express scheduling and form a DAG.
    4. Dependencies are satisfied by explicit durable results, normally BranchResult, not by transcript completion.
    5. One plan has at most one auto-advancing coordinator at a time.
    6. Many worker models may execute different branches concurrently.
    7. One branch normally has one active executing owner; parallel attempts use sibling branches.
    8. Each branch may have its own provider/model/profile/thinking/context/capability configuration.
    9. Secrets remain opaque credential references.
    10. Plan revisions are durable and historical; replanning does not rewrite the past.
    11. Concurrent candidate states are not silently merged merely because dependencies completed.
    12. Worker context contains selected dependency results and semantic state, not sibling transcripts.
    13. Coordinator cursor and user reply anchor are distinct even when they usually auto-follow together.
    14. Scheduling and auto-follow are shared/application and presentation concerns respectively; neither may redefine branch semantics.
    15. All product surfaces consume the same durable plan and execution model.
