    Semantic Agent Operations and Projection-First Editing¶

    1. Purpose¶

    Scriberig agents must operate primarily on structured semantic knowledge rather than treating the repository as a bag of opaque text files manipulated through generic shell and file-writing tools.

    This document connects the universal knowledge model, domain adapters, migrations, projections, agent execution, and recursive branch architecture into one explicit rule for agent behavior.

    It refines and ties together:

    1. 002. universal knowledge model.md;
    2. 005. changes migrations branches and merge.md;
    3. 006. projections and bidirectional editing.md;
    4. 007. domain modeling and adapters.md;
    5. 010. universal query and operation model.md;
    6. 014. agent native semantic self hosting.md;
    7. 016. model driven agent execution and branch isolation.md;
    8. 017. recursive agent decomposition and context isolation.md;
    9. 018. durable plans dependency scheduling and multi-model execution.md.

    The controlling rule is:

    Once Scriberig understands a domain, the agent edits semantic entities, relations, collections, and revisions through domain/application operations. Source files and documents are projections of that semantic state. Generic raw file and shell operations are fallback, bootstrap, interoperability, or validation mechanisms—not the ordinary canonical editing interface.

    2. The Repository Is Not the Canonical Model¶

    A source path remains useful projection metadata and external interoperability state, but it is not the primary identity of known source knowledge.

    For understood source code, Scriberig should be able to represent structure such as:

    Project
  Module
    Type
    Function
      Parameter
      CodeGroup
        Statement
          Expression
    Comment

    For Markdown:

    MarkdownDocument
  Section
    Heading
    Paragraph
    List
      ListItem
    Table
      TableRow
        TableCell

    The exact domain schemas vary, but the agent should operate on stable semantic handles whenever those handles exist.

    A path, line number, byte span, rendered source fragment, or terminal row is an anchor into a projection. It is not a substitute for semantic identity.

    3. Source Files Are Projections¶

    For understood source domains, the conceptual flow is:

    canonical semantic state
        |
        v
source projection adapter
        |
        v
.rs / .ts / .php / .md / other file

    A canonical agent edit goes in the opposite conceptual direction only through the semantic change model:

    semantic operation
    -> candidate semantic state
    -> migration/change proposal
    -> validation
    -> accepted snapshot/workspace
    -> deterministic projection/materialization

    A model should not normally construct the entire final file text and call a generic write_file tool when a structure-preserving domain operation exists.

    4. Semantic Reads Come Before Raw Reads¶

    For known knowledge, agents should orient themselves using universal semantic operations such as:

    inspect
list
follow
find
query
history
diff
render

    Examples:

    inspect(Function parse_type)
list(Function parse_type, code_groups)
follow(Function parse_type, calls)
query(functions that implement DomainAdapter)
render(Function parse_type, source)

    render is available when exact presentation/syntax is needed. It should not be the first and only way to understand the object.

    Raw file reads may remain available for opaque or unsupported resources, bootstrap situations, external evidence, or exact projection inspection, but they are a lower-confidence/lower-semantics path.

    5. Semantic Writes Are Domain Operations¶

    The universal change model provides primitives equivalent to:

    create entity
replace entity revision
add relation
remove relation
insert collection member
remove collection member
move collection member
replace collection structure

    Domain adapters expose higher-level operations that preserve domain meaning.

    Source-code examples may include:

    code.add_function
code.remove_function
code.rename_symbol
code.add_parameter
code.remove_parameter
code.insert_statement
code.replace_statement
code.replace_expression
code.add_comment
code.extract_function
code.move_declaration

    Markdown examples may include:

    document.add_section
document.insert_paragraph
document.replace_paragraph
document.move_block
document.insert_table_row
document.update_table_cell

    The exact capability catalog is domain-specific and discoverable. The architectural requirement is that rich semantic operations extend the universal change model rather than bypass it.

    6. Tool Discovery Is Selection- and Capability-Driven¶

    The model should not receive one giant static catalog of filesystem and shell commands.

    The runtime builds a capability-filtered tool catalog from the current semantic scope.

    For a selected function, a compact tool catalog may advertise:

    inspect
list body/code_groups/parameters
follow calls/references
render source
code.insert_statement
code.replace_expression
code.add_comment
history
diff
validate

    For a Markdown section, it may advertise:

    inspect
list subsections/blocks
render markdown
document.insert_paragraph
document.add_subsection
document.move_block

    For an opaque artifact, the catalog may degrade to projection/raw capabilities.

    Capability discovery should make this degradation explicit instead of pretending every artifact has rich semantics.

    7. Raw File Operations Are a Fallback, Not the Default¶

    Generic file operations remain useful when:

    • the project has not yet been onboarded;
    • a file type has no semantic adapter;
    • exact external bytes are evidence that must be preserved;
    • an interoperability flow explicitly edits a projection;
    • a generated/opaque artifact must be handled as opaque data;
    • a domain adapter is being bootstrapped for a previously unsupported format;
    • recovery or diagnostics require direct projection inspection.

    When semantic capabilities exist, the runtime should prefer them and may avoid advertising unrestricted raw write operations to the model entirely.

    If a raw projection edit is permitted, it must reconcile back through the projection adapter and normal semantic migration path before becoming canonical.

    8. Shell Execution Is Also a Narrow Capability¶

    Scriberig does not need to ban process execution, but it should not make unrestricted shell access the normal model-facing editing mechanism.

    A model should prefer application capabilities such as:

    validate(candidate, profile)
dependency.add(...)
project.scan(...)
project.import(...)
projection.render(...)

    The implementation behind those capabilities may run external processes such as compilers, linters, test runners, formatters, or package managers in controlled workspaces.

    For example:

    validate(candidate C, rust-focused)

    may internally:

    materialize candidate projection
run cargo check
run focused tests
collect diagnostics
map diagnostics back to semantic handles

    The model receives a structured ValidationResult, not merely a terminal transcript.

    Direct shell execution, when exposed, should be capability-scoped, auditable, bounded, and treated as external-effect/runtime functionality.

    9. Diagnostics Should Resolve Back to Semantic Knowledge¶

    Compiler, parser, linter, test, or external-tool diagnostics may initially arrive in projection coordinates such as path/line/column.

    Adapters should resolve those coordinates back to semantic entities where possible.

    A useful diagnostic result is conceptually:

    ValidationDiagnostic D42
  projection: src/php/parser.rs
  anchor: line/column range
  semantic target: Function parse_type / Expression E17
  severity: error
  message: ...
  producer: rustc / parser / test runner / ...

    The agent can then inspect or edit the semantic target instead of repeatedly manipulating raw source ranges.

    10. “Create a File” Means Create Semantic Knowledge Plus a Projection¶

    When a task conceptually creates a new source file, the semantic interpretation should be something like:

    create Module M
insert Module M into project/module structure
create Function F1
create Function F2
create Type T1
insert declarations into Module M
associate/update source projection specification
render/materialize projection at path P

    The path remains important for source layout and interoperability, but the knowledge being authored is the module and its contents.

    For Markdown:

    create MarkdownDocument D
create Section S
create Paragraph P1/P2
attach semantic projection location docs/foo.md

    This rule prevents file paths from becoming accidental canonical identities.

    11. Semantic Identity Makes Planning More Stable¶

    Plan nodes should prefer semantic goals and scopes over textual file-edit instructions.

    Prefer:

    Extend PHP union-type parsing
  scope: Function parse_type

    rather than:

    Edit src/php/parser.rs

    Prefer:

    Register PHP source adapter
  scope: SourceDomainRegistry

    rather than:

    Modify registry.rs

    Projection paths may be shown as helpful metadata, but plan identity should survive moves, rerendering, style changes, or source-layout refactors when the semantic object remains the same.

    12. Semantic Results Improve Branch Isolation¶

    A child branch that implements a source capability should return semantic results rather than a prose statement that a file changed.

    Conceptually:

    BranchResult
  status: completed
  summary: PHP union parsing implemented
  touched:
    Function parse_type @ new revision
    Function parse_union_type @ revision
  candidate: Candidate C18
  validation: Validation V7
  projections:
    src/php/parser.rs will change

    A sibling test branch receives these exact handles and the resulting candidate/project state.

    It does not need the implementation child's raw write history or source-edit chatter.

    This aligns recursive branch isolation with the universal knowledge model.

    13. Semantic Results Improve Dependency Scheduling¶

    Plan dependencies should express required semantic outcomes where practical.

    For example:

    PlanNode Add tests
  depends_on: ParserImplementationResult

    not merely:

    wait until parser agent stops

    The parser result may guarantee:

    Function parse_type updated
Function parse_union_type created
candidate C18 available
source projection renderable
validation profile parser-structure passed

    The dependency edge then carries useful, deterministic context for the dependent worker.

    14. Semantic Change Enables Better Concurrency¶

    Two workers may change different semantic entities even when those entities render into the same file.

    Example:

    Worker A changes CodeGroup validation in Function parse_type
Worker B changes Function extract_attributes

    A textual patch system sees two edits to parser.rs.

    Scriberig can recognize distinct semantic targets and attempt a semantic merge against a common base.

    Likewise, a true conflict can be identified precisely when both workers modify the same entity/relation/collection member.

    This is one of the major benefits of using semantic operations in a multi-model plan.

    15. Candidate Workspaces Remain the Mutation Boundary¶

    Semantic edits still do not mutate canonical current state directly.

    An agent operation normally produces isolated candidate/workspace state derived from an exact base.

    Conceptually:

    base snapshot S1
  -> semantic operations
  -> candidate snapshot/workspace S2
  -> validation
  -> review/acceptance
  -> promotion/materialization

    Multiple workers may produce sibling candidates from the same base.

    Dependency completion does not auto-promote or auto-merge those candidates.

    16. Projection Materialization Happens After Semantic Change¶

    The normal editing path should not require touching live files during each semantic operation.

    The runtime may maintain an isolated candidate representation and render/materialize files when needed for:

    • validation;
    • external compiler/tool execution;
    • human review;
    • final accepted filesystem synchronization.

    This reduces accidental divergence between semantic candidate state and live working-tree bytes.

    The exact materialization policy may vary by domain and product composition.

    17. External File Editing Remains Supported¶

    Scriberig must continue to interoperate with ordinary editors and external tools.

    When an externally editable projection changes:

    last synchronized projection
  -> external edit
  -> parse
  -> candidate semantic representation
  -> reconcile identities
  -> migration proposal
  -> validate/commit

    This is the reverse path for interoperability. It is not evidence that the internal agent should prefer raw file editing when richer semantic operations are already available.

    18. Unknown and Opaque Artifacts¶

    Not every resource will immediately have a rich adapter.

    Scriberig should represent degraded capability honestly.

    Concepts may include:

    OpaqueArtifact
TextArtifact
ExternalArtifact
ProjectionOnlyResource

    A consumer may see capabilities such as:

    inspect metadata
render/read projection
replace opaque content candidate
validate external effect

    rather than AST-/document-level editing.

    The architecture should permit later adapter installation to make the same project progressively more semantic.

    19. Tool Presentation Should Reflect Semantic Operations¶

    The TUI should not visually pretend every tool invocation is a shell command.

    Compact semantic operation:

    ▏ add function parse_union_type to php::parser
▏ ✓ Function F194 created

    Detailed structured presentation:

    ▏ code.add_function
▏   module: php::parser
▏   after: parse_named_type
▏   name: parse_union_type
▏   return_type: TypeResult
▏ ✓ Function F194 @ Revision R1

    An actual external process may render as a shell-like command:

    ▏ cargo test -p scriberig-domain-php ...
▏ ✓ 12 tests passed

    Per-activity presentation modes control how much detail is visible. They never alter the underlying semantic operation or model context.

    20. Recursive Branch Example Rewritten Semantically¶

    Avoid thinking of a child branch as:

    write foo.rs

    Prefer:

    child: implement FooParser module

    Inside that child:

    inspect neighboring parser modules
inspect required adapter interfaces
create Module FooParser
create Type Parser
create Function parse
insert CodeGroups
insert Statements
replace Expressions
add Comments
validate candidate

    A nested validation child may materialize the candidate and invoke external compiler/test infrastructure.

    The parent receives:

    BranchResult
  FooParser implemented
  Module/Type/Function handles
  Candidate C
  Validation passed

    The parent does not inherit internal semantic-edit chatter unless explicitly reopened.

    21. Context Compilation Uses Semantic Handles¶

    The context compiler should prefer compact semantic objects, descriptions, exact revisions, selected relations, accepted decisions, branch results, and dependency results.

    It should not routinely fill model context with complete source files when a smaller semantic projection is sufficient.

    For example, a worker modifying one function might initially receive:

    Function parse_type
  purpose: parses PHP type expressions
  parameters: cursor, source
  code groups: prefix, named type, nullable suffix, result construction
  calls: parse_identifier, parse_generic_arguments
  diagnostics: none

    Then the model can inspect or render only the relevant group/expression when exact syntax is required.

    This applies the same progressive-disclosure principle to project knowledge that branch isolation applies to session history.

    22. The Four Relevant Structures Must Stay Distinct¶

    Scriberig combines several graphs/trees without collapsing them.

    Knowledge graph¶

    Project -> Module -> Function -> Statement -> Expression

    Session/branch tree¶

    Goal -> child branch -> grandchild branch -> BranchResult

    Plan dependency graph¶

    PlanNode A ----\
                -> PlanNode C
PlanNode B ----/

    Execution causality¶

    ModelInvocation -> SemanticOperation -> OperationResult

    Product surfaces may project these structures together, but canonical relations remain distinct.

    A branch may target a semantic entity. A plan node may execute as a branch. A dependency may link plan nodes. An activity may invoke a semantic operation that changes a candidate revision.

    23. Product-Surface Invariant¶

    CLI, TUI, web, server, and third-party clients should expose the same semantic capabilities and resulting handles.

    The TUI may provide convenient tree navigation and detailed tool rendering, but it must not own semantic-edit logic.

    A web editor may provide direct manipulation of semantic nodes, but it must produce the same application/change operations.

    The agent runtime consumes shared capabilities rather than inventing an agent-only patch or file-mutation path.

    24. Non-Negotiable Summary¶

    Future implementation work must preserve these rules:

    1. Known source/document files are projections of structured semantic state.
    2. Agents should address semantic entities rather than paths/lines whenever a richer object exists.
    3. Semantic/domain operations are the ordinary editing interface.
    4. Generic raw writes are fallback/bootstrap/interoperability capabilities, not the normal canonical edit path.
    5. Shell/process execution is primarily an implementation detail of bounded capabilities such as validation, not the universal model-facing interface.
    6. Diagnostics should resolve back to semantic handles whenever possible.
    7. Creating a source file normally means creating semantic module/document structure plus a projection mapping.
    8. Plan nodes should prefer semantic goals/scopes over path-based edit instructions.
    9. Branch results and dependencies should expose exact semantic handles/candidates/validation evidence.
    10. Multiple model workers produce isolated semantic candidates that merge through the normal semantic change system.
    11. Projection materialization does not become a hidden canonical write path.
    12. External projection editing remains supported through parse/reconcile/migration.
    13. Unknown formats degrade explicitly to opaque/projection capabilities.
    14. TUI tool presentation should distinguish semantic operations from actual shell/process execution.
    15. Knowledge graph, branch tree, dependency DAG, and execution causality remain separate structures even when one UI combines them.
