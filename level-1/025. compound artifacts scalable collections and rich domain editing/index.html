    Compound Artifacts, Scalable Collections, and Rich Domain Editing¶

    1. Purpose¶

    Scriberig is intended to edit structured project knowledge beyond source code and Markdown. Real projects may contain spreadsheets, rich documents, CAD drawings, geospatial datasets, QGIS projects, database-backed containers, and other artifacts whose logical structure is not equivalent to one text file.

    This document extends the durable architecture in:

    • 001. vision and principles.md;
    • 002. universal knowledge model.md;
    • 003. identity revisions and snapshots.md;
    • 005. changes migrations branches and merge.md;
    • 006. projections and bidirectional editing.md;
    • 007. domain modeling and adapters.md;
    • 010. universal query and operation model.md;
    • 011. runtime libraries protocol and product surfaces.md;
    • 013. trust validation capabilities and provenance.md;
    • 014. extensibility ecosystem and licensing.md;
    • 019. semantic agent operations and projection-first editing.md;
    • 024. projection styles personalized representations and materialization policy.md.

    It does not replace those documents. It defines the additional invariants needed when project knowledge is packaged, binary, spatial, very large, externally referenced, or only partially understood by Scriberig.

    The central rule is:

    Rich project artifacts are semantic domains over the same universal knowledge system. Their physical files, package members, database pages, external references, rendered canvases, and editor views are evidence or projections, not alternative canonical stores.

    A second rule is:

    Scriberig must be able to preserve exact external evidence and opaque author-significant content even when it understands only part of an artifact.

    A third rule is:

    Semantic addressability does not require eager one-record-per-object physical storage. Large tables, grids, feature sets, and drawings may use scalable indexed representations while remaining accessible through stable semantic handles and the universal query/change model.

    2. Why Ordinary File Semantics Are Insufficient¶

    The current file-oriented onboarding boundary is useful for discovery and source evidence, but richer formats expose several cases that cannot be modeled correctly as one path -> one independent editable blob.

    Examples include:

    .xlsx / .docx
  one ZIP package
  many related package parts
  relationships between parts
  semantic objects spanning several parts

.qgz
  one ZIP package
  project XML plus auxiliary members
  references to datasets outside the package

Shapefile dataset
  .shp + .dbf + .shx + .prj + optional sidecars
  several physical files represent one logical dataset

GeoPackage
  one SQLite file
  many logical vector/raster/attribute layers

DWG / DXF
  one drawing artifact
  many persistent drawing objects and cross references

    The architecture therefore distinguishes physical source evidence from logical artifacts and their semantic contents.

    3. External Artifact Is a Logical Boundary¶

    Introduce the durable concept of an external artifact or equivalent semantic boundary.

    Conceptually:

    ExternalArtifact
  stable semantic identity
  artifact kind
  source evidence
  physical members
  logical parts
  external references
  adapter/schema identity
  synchronization/materialization policy
  provenance

    The exact Rust type and storage layout belong in lower-level design.

    An external artifact may correspond to:

    • one ordinary file;
    • one archive containing many package members;
    • several coordinated filesystem files;
    • one database/container file exposing many logical resources;
    • one project description that references independently owned datasets;
    • an externally hosted resource that is imported or synchronized under an explicit trust policy.

    The artifact is not a second persistence system. It is semantic knowledge represented using the universal entity/revision/snapshot model.

    4. Exact Source Evidence Remains Separate from Semantic Interpretation¶

    Importing a rich format must preserve enough exact evidence to answer what external bytes or members were observed.

    Conceptually:

    exact external evidence
  -> parser/adapter
  -> canonical semantic knowledge
  -> derived interpretation

    These classes are not interchangeable.

    For example, a DOCX parser may understand paragraphs and tables while preserving unknown package parts. A PDF extractor may derive text regions while retaining exact PDF bytes. A CAD adapter may recognize ordinary entities while retaining unsupported proxy/custom data. A QGIS adapter may understand known project XML while preserving plugin-specific extension content.

    Exact evidence supports:

    • reproducibility;
    • audit and provenance;
    • round-trip preservation;
    • conflict explanation;
    • adapter upgrades;
    • re-import with improved interpretation;
    • preservation of unsupported content.

    Exact evidence does not automatically become canonical semantic meaning.

    5. Compound Physical Membership¶

    A logical artifact may own several physical members.

    Conceptually:

    Artifact A
  member M1 -> path/part/blob
  member M2 -> path/part/blob
  member M3 -> path/part/blob

    Membership and ordering are semantic structure owned by the artifact revision, not implicit assumptions reconstructed from directory enumeration each time.

    Examples:

    ShapefileDataset
  roads.shp
  roads.shx
  roads.dbf
  roads.prj

OpenXmlPackage
  [Content_Types].xml
  word/document.xml
  word/styles.xml
  word/_rels/document.xml.rels
  ...

    Scanning may initially discover independent paths. Classification/import may then group them into one logical artifact according to deterministic adapter rules.

    One physical file must not be forced to equal one semantic project root object.

    6. Logical Parts Inside Containers¶

    Archive/database formats expose addressable logical parts that need not materialize as ordinary files.

    Examples include:

    XLSX package part
DOCX relationship part
GeoPackage layer/table
QGZ project member
embedded image/object

    A logical part may have stable semantic identity and exact revision history even when its physical representation remains inside one container.

    Consumers should navigate semantic objects and logical parts rather than requiring extraction to temporary files as the canonical access model.

    Temporary extraction may be used internally by an adapter or validator, but it remains an implementation mechanism.

    7. Opaque Preservation Is First-Class¶

    Scriberig must not require complete understanding before safely editing a partially understood artifact.

    A domain may classify content as:

    understood canonical semantic structure
understood derived structure
projection-only representation state
opaque preserved canonical extension content
exact external evidence

    Opaque preserved content is content that Scriberig cannot currently interpret semantically but must retain because dropping or rewriting it could damage the artifact or erase author/tool intent.

    Examples may include:

    • unknown OOXML extension elements;
    • embedded/custom package parts;
    • application-specific CAD records;
    • QGIS plugin extension XML;
    • unsupported style/metadata records;
    • future-version fields unknown to the current adapter.

    An unrelated semantic edit must preserve opaque content unless the requested operation explicitly replaces/removes the owning structure or the adapter can prove that preservation is impossible.

    When preservation cannot be guaranteed, the projection/edit capability must degrade explicitly rather than silently losing content.

    8. Round-Trip Fidelity Is a Capability, Not an Assumption¶

    A format being parseable does not imply it is safely editable.

    Projection/domain capability discovery must be able to distinguish states equivalent to:

    InspectOnly
ReadOnlyDerived
LosslessEditable
LossAwareEditable
EditableWithOpaquePreservation
RestrictedExternalProviderEdit
Unsupported

    Exact names belong in Level 2.

    Capability is evaluated for the exact adapter/version, artifact, projection kind, resolved style, and preservation policy when those affect correctness.

    For example:

    • a simple XLSX workbook may be editable while an unsupported macro/signature mode is not;
    • a DOCX may be semantically editable while exact page layout remains derived/read-only;
    • DXF may be editable while native DWG support depends on an optional provider;
    • a QGIS project may be editable while one referenced remote layer is read-only;
    • a lossy user projection remains governed by Level-1 024 loss-aware reconciliation rules.

    9. Scalable Semantic Collections¶

    Spreadsheets and geospatial datasets may contain millions of meaningful elements. The universal knowledge model must preserve semantic addressability without requiring every element to be eagerly expanded into heavyweight graph records.

    Introduce a scalable collection concept or equivalent implementation strategy with these semantics:

    semantic collection
  stable owner and collection identity
  exact snapshot/revision binding
  deterministic paging/range access
  stable member handles
  query/index support
  local semantic mutation
  exact changed-set reporting

    Possible physical implementations may use:

    • sparse ranges;
    • persistent indexed tables;
    • database-backed rows;
    • columnar batches;
    • R-tree/spatial indexes;
    • compressed geometry stores;
    • adapter-owned immutable blocks.

    Physical representation is an implementation detail as long as universal operations preserve snapshot exactness, stable semantic handles, history, provenance, and change semantics.

    The system must avoid designs where importing five million GIS features requires putting five million objects into model context or rendering an enormous tree.

    10. Progressive Disclosure for Large Artifacts¶

    Large domains should expose coarse-to-fine navigation.

    Examples:

    Workbook
  -> worksheets
  -> used regions/tables
  -> bounded range
  -> cell

GeoDataset
  -> layers
  -> schema/extent/count
  -> spatial/query result page
  -> feature

Drawing
  -> layouts/layers/blocks
  -> bounded entity query
  -> drawing entity

    The agent, TUI, web editor, CLI, and API all consume the same semantic handles and pagination/query semantics.

    A huge collection must not become a huge static capability list or one giant serialized object.

    11. Non-Text Projection Anchors¶

    Text line/column is only one projection coordinate system.

    Rich domains need typed projection anchors such as:

    SpreadsheetAnchor
  sheet + row/column or range

DocumentLayoutAnchor
  page/region when layout exists

DrawingAnchor
  model/layout space + geometric bounds

MapAnchor
  CRS + geometry/bounding box + layer

PackagePartAnchor
  part identity + adapter-specific location

    Projection anchors remain non-canonical bridges back to semantic identity.

    Selections in a grid, canvas, map, page view, or drawing viewport should resolve to semantic entity/revision handles in the same way a source range resolves to a function or expression.

    12. Spreadsheet Domain Family¶

    Spreadsheets are a semantic domain family independent of XLSX as one external representation.

    A general spreadsheet vocabulary may include:

    Workbook
Worksheet
Row
Column
Cell
Range
Table
Formula
DefinedName
CellStyle
ValidationRule
Chart
ExternalLink

    Important rules:

    1. cell/range identity must not be reduced to display text;
    2. formulas preserve authored expressions while parsed references may be canonical or derived according to the domain model;
    3. cached formula results are not automatically authoritative calculations;
    4. row/column insertion and movement use semantic operations that update dependent references according to domain rules;
    5. worksheet data uses scalable/sparse collection mechanics;
    6. formatting/style is separated from value/formula semantics where the format permits that distinction;
    7. XLSX is an adapter/projection/package implementation, not the spreadsheet schema itself.

    13. Rich Document Domain Family¶

    Markdown and Word-like documents should share semantic concepts where they genuinely overlap without forcing identical representation.

    A common rich-document vocabulary may include:

    Document
Section
Paragraph
Inline/Run
List
Table
TableRow
TableCell
Image
Link

    Format-specific extensions may include:

    WordStyle
Field
Bookmark
Footnote
Endnote
HeaderFooter
Comment
TrackedChange
ContentControl
DrawingObject

    Pagination, exact line breaking, font substitution, and similar layout facts are normally derived projection knowledge unless a domain explicitly promotes them.

    DOCX is a compound-package adapter over the rich-document domain and its format-specific extensions.

    14. CAD Drawing Domain Family¶

    CAD semantics should be modeled independently from any one interchange/storage format.

    A useful common vocabulary may include:

    Drawing
DrawingSpace
Layout
Viewport
Layer
BlockDefinition
BlockReference
Line
Polyline
Arc
Circle
Text
Dimension
Hatch
Style
ExternalReference

    Domain-specific geometry and object types may extend this list.

    DXF and DWG are separate adapters over the CAD domain.

    External persistent identifiers such as native drawing handles are reconciliation/provenance evidence. They must not replace Scriberig EntityId.

    Initial editable CAD capability should favor formats/adapters whose preservation and licensing constraints can be validated. Native/proprietary integrations may be optional provider boundaries rather than dependencies of the reusable semantic platform.

    15. Geospatial Data and QGIS Are Distinct Domains¶

    A QGIS project is not the same thing as the data layers it references.

    The geospatial data domain may contain:

    GeoDataset
GeoLayer
Feature
Geometry
Field
CoordinateReferenceSystem
SpatialIndex
RasterResource

    The QGIS project domain may contain:

    QgisProject
LayerGroup
LayerReference
RendererStyle
LabelingConfiguration
Join
Relation
Layout
MapItem
ProjectSetting

    The domains connect through references such as:

    QgisLayerReference --references--> GeoLayer

    A GeoLayer may be backed by GeoPackage, Shapefile, GeoJSON, PostGIS, a remote service, raster data, CAD, or another provider.

    The QGIS project owns composition/configuration; it does not absorb ownership of every referenced dataset.

    16. Spatial Operations Extend Universal Query¶

    Geospatial semantics require domain-specific queries such as:

    features intersecting geometry/bbox
features within geometry
nearest features
features matching attribute predicate
layer extent
CRS transformation

    These extend the universal query and operation model. They do not create an independent GIS persistence/query architecture.

    Results remain snapshot-bound, paged, capability-scoped, and represented by stable semantic handles.

    17. Cross-Domain Relations Are Normal¶

    Rich project artifacts frequently reference each other.

    Examples:

    WordParagraph --references--> SpreadsheetRange
QgisLayerReference --references--> GeoLayer
CADExternalReference --references--> ExternalArtifact
SpreadsheetCell --references--> ProjectDecision
SessionBranch --touches--> GeoFeature
ReportTable --derived_from--> SpreadsheetRange

    Cross-domain references use the universal graph and must not require copying another domain's canonical content.

    Changes to one referenced object should invalidate/recompute only declared dependent derived knowledge and projections.

    18. Semantic Operations Remain the Editing Primitive¶

    Once a domain is understood, ordinary editing is performed through semantic operations.

    Examples include:

    spreadsheet.set_cell
spreadsheet.set_formula
spreadsheet.insert_rows
spreadsheet.rename_sheet

document.replace_paragraph
document.insert_table_row
document.accept_tracked_change

cad.move_entity
cad.change_layer
cad.insert_polyline
cad.update_text

geo.set_attribute
geo.replace_geometry
geo.insert_feature
geo.delete_feature

qgis.reorder_layer
qgis.change_renderer
qgis.update_layout_item

    Every such operation produces candidate semantic state and flows through migration, validation, review/policy, promotion, and materialization.

    A model must not normally edit XLSX ZIP members, DOCX XML, DWG bytes, SQLite tables, QGIS XML, or Shapefile sidecars directly when a semantic adapter exists.

    19. Compound Materialization Is Atomic at the Artifact Boundary¶

    Materialization may update one file, many coordinated files, or one container.

    The system must provide artifact-level materialization semantics equivalent to:

    candidate semantic state
  -> render all affected artifact members
  -> validate complete candidate artifact set
  -> stage outputs
  -> verify expected external baseline
  -> atomically replace/promote as far as platform permits
  -> record effect receipts and exact new synchronization baseline

    For multi-file artifacts, a partial successful write must not be reported as a successful materialization.

    Recovery must be explicit when the operating system cannot provide one primitive covering every member.

    20. Validation Is Domain-Specific but Evidence-Bound¶

    Validators may include:

    • package structural validation;
    • reopening the produced XLSX/DOCX with an independent parser;
    • formula/reference checks;
    • CAD parser/reopen checks;
    • geometry validity;
    • CRS/schema consistency;
    • QGIS project reference resolution;
    • GDAL/QGIS/native-provider diagnostics;
    • external application/provider validation where configured.

    Validation evidence binds to the exact candidate artifact state it checked.

    External tools may run in isolated candidate workspaces, but shell/process execution remains a runtime mechanism rather than the semantic editing API.

    21. Product Surfaces and RPI TUI Boundary¶

    The browser editor is expected to provide richer interactive projections such as:

    • spreadsheet grids;
    • rich-document editing;
    • CAD canvases;
    • map canvases;
    • layer/style inspectors.

    The TUI should provide semantic navigation, bounded tabular/textual inspection, operation invocation, candidate review, history, diagnostics, and suitable previews.

    The TUI is not required to recreate Excel, Word, AutoCAD, or QGIS as terminal widgets.

    Under the active RPI adoption work:

    • upstream RPI/RPI-TUI owns commodity terminal controls/runtime/theme;
    • Scriberig owns semantic selections, domain projections, semantic operations, candidate review, and domain capability contracts;
    • TUI-specific presentation state must not become domain state.

    CLI, web, TUI, agents, server, and third-party clients consume the same application/protocol semantics.

    22. Licensing and Optional Native Providers¶

    A semantic domain must not be coupled to one parser/library/provider whose license would unintentionally redefine the reusable platform's licensing boundary.

    Where a format requires proprietary, copyleft-incompatible, native, or separately distributed technology, the architecture should support an optional adapter/provider boundary.

    Provider identity, adapter version, fidelity, supported operations, and validation capabilities must be discoverable.

    Absence of an optional provider degrades that format's capability explicitly; it does not make the semantic schema unavailable to other adapters.

    23. Required Golden Workflows¶

    The implementation should eventually prove at least these product workflows through shared application semantics.

    23.1 XLSX¶

    open workbook
inspect sheets and used ranges
inspect formula/value
set one cell/formula semantically
review candidate
validate
promote
materialize XLSX
reopen and verify

    23.2 DOCX¶

    open document
navigate section/paragraph/table
replace paragraph or table cell semantically
preserve unrelated/opaque package content
review/validate/promote
materialize DOCX
reopen and verify

    23.3 CAD¶

    open drawing
navigate layer/block/entity
change one supported entity semantically
preserve unsupported records when required
review/validate/promote
materialize supported CAD representation

    23.4 QGIS/geospatial¶

    open QGIS project
resolve referenced editable layer
find feature by semantic/spatial/attribute query
change one attribute or geometry
review/validate/promote
materialize dataset
refresh project view without changing unrelated project configuration

    24. Conformance Requirements¶

    The completed architecture must prove all of the following:

    1. one logical artifact may have one, many, or container-internal physical members;
    2. exact source evidence remains inspectable independently of semantic interpretation;
    3. unknown preserved content survives unrelated edits when the adapter advertises preservation;
    4. format capability declares editability/fidelity instead of assuming parse implies write safety;
    5. large grids/layers can be queried and paged without eager full expansion;
    6. non-text selections resolve to semantic handles rather than becoming canonical coordinate identities;
    7. spreadsheet operations update semantic formulas/references according to domain rules;
    8. rich-document edits preserve format-specific structures not targeted by the operation;
    9. CAD external handles remain evidence, not Scriberig identity;
    10. QGIS project composition and geospatial datasets remain distinct but linked domains;
    11. spatial queries remain snapshot-bound and use the shared query model;
    12. compound materialization cannot silently leave a successful partial artifact;
    13. all edits flow through candidate/migration/validation/promotion;
    14. TUI/web/CLI/server/agents consume shared semantics;
    15. optional native/provider integrations do not become hidden mandatory dependencies of the universal platform.
