    Semantic Plan Entities, Evidence, Gates, and Recoverable Execution¶

    1. Purpose¶

    This document refines 018. durable plans dependency scheduling and multi-model execution.md so durable planning follows the same universal semantic identity, revision, snapshot, relation, and derived-knowledge rules as the rest of Scriberig.

    It does not replace the session tree, dependency DAG, coordinator model, branch isolation, or shared application-operation model from earlier designs.

    The controlling rule is:

    A Plan, PlanNode, gate, dependency, summary, and execution attempt are semantic knowledge with stable identities and exact revisions where their meaning requires independent history. A plan is not canonically stored as one opaque aggregate containing mutable vectors of all nodes and edges.

    A second rule is:

    Scriberig has one plan-node lifecycle vocabulary. Do not introduce a parallel PlanNodeWorkState or another user-visible state machine merely to represent rollups.

    The lifecycle remains conceptually:

    Planned
Ready
Running
Completed
Failed
Abandoned

    Lower-level designs may refine exact Rust names, but they must preserve this single-state-model principle.

    2. Relationship to Existing Plan Design¶

    018 remains authoritative for:

    • the distinction between structural decomposition and dependency scheduling;
    • result-based dependency fulfillment;
    • one auto-advancing coordinator per plan;
    • many concurrent workers on independent branches;
    • per-node execution assignment;
    • branch isolation and compact BranchResult handoff;
    • explicit replanning and durable history;
    • cross-surface plan semantics.

    This document is authoritative where it refines 018 on:

    • canonical persistence shape;
    • independent plan-node identity and revisioning;
    • plan summaries;
    • evidence;
    • gates;
    • derived parent/subtree status;
    • ignored/abandoned descendants;
    • recoverable failure;
    • execution-attempt history;
    • incremental status materialization.

    If older implementation documents describe the complete plan as a serialized Plan { nodes: Vec<PlanNode>, dependencies: Vec<...> } persistence unit, that representation is transitional and not the target architecture.

    3. Plans and Plan Nodes Are Ordinary Semantic Entities¶

    A plan has stable semantic identity:

    Plan P

    Each node has its own independent stable semantic identity:

    PlanNode N1
PlanNode N2
PlanNode N3

    Each meaningful canonical mutation creates a new immutable revision of the affected entity while preserving stable identity.

    For example:

    N2@R1  status = Planned
N2@R2  status = Ready
N2@R3  status = Running
N2@R4  status = Failed
N2@R5  status = Ready
N2@R6  status = Running
N2@R7  status = Completed

    The surrounding plan does not need a new semantic revision merely because a child node received a new content revision unless the plan's own canonical fields changed.

    The current exact world remains fixed by a snapshot that resolves stable entity identities to revisions.

    4. A Plan Is a Semantic Root, Not a Container Blob¶

    The plan entity owns plan-level meaning such as:

    identity
session / continuation anchor association
goal
plan lifecycle
coordinator policy/reference
coordinator cursor/reference when canonical
default policy or assignment references

    The plan must not canonically embed the complete mutable graph as opaque fields equivalent to:

    nodes: Vec<PlanNode>
dependencies: Vec<PlanDependency>
history: Vec<PlanRevision>

    Instead, plan topology is represented by semantic entities, collections, and relations.

    Conceptually:

    Plan P
  --contains--> N1
  --contains--> N2
  --contains--> N3

N1 --decomposes_to--> N1a
N1 --decomposes_to--> N1b

N3 --depends_on--> N1
N3 --depends_on--> N2

    Exact relation storage belongs to lower-level design.

    5. Structural Decomposition and Dependency Scheduling Remain Distinct¶

    The following structures must never be collapsed:

    Session tree:
Goal -> Branch -> Child Branch -> BranchResult

Plan structural tree:
PlanNode -> child PlanNode

Plan dependency DAG:
PlanNode -> depends_on -> PlanNode

    Structural child relations mean decomposition/context ownership/provenance.

    Dependency relations mean scheduling constraints.

    Adding a child must not silently invent a dependency edge between arbitrary siblings.

    Likewise, adding a dependency must not silently reparent either node.

    6. Plan Dependencies Need Independent History When They Carry State¶

    A dependency may carry meaning beyond a bare graph edge, including:

    prerequisite
dependent
required result contract
fulfilled_by exact result reference
optional/required policy when later supported
provenance

    When that state needs independent revision/history/provenance, represent the dependency as a first-class revisioned relation or semantic entity rather than hiding it in one node's payload.

    The target model is conceptually:

    PlanDependency D7
  prerequisite -> N1
  dependent -> N3
  required_result -> Contract C
  fulfilled_by -> BranchResult BR42

    A failed or abandoned prerequisite does not fulfill a successful dependency unless an explicit dependency/gate policy says otherwise.

    7. Keep One PlanNodeStatus Vocabulary¶

    Do not create a second lifecycle concept such as:

    PlanNodeWorkState
Planned / Implementing / Stalled / Ignored

    Use the existing plan-node lifecycle vocabulary for execution/scheduling semantics:

    Planned
Ready
Running
Completed
Failed
Abandoned

    Reasons and annotations refine a status without creating a second state machine.

    For example:

    Abandoned
  reason = Ignored

Abandoned
  reason = Superseded

Abandoned
  reason = Cancelled

Failed
  failure = exact attempt/result/evidence reference

    The exact reason vocabulary may evolve independently.

    8. Direct Status and Subtree Presentation Use the Same Status Vocabulary¶

    A node's canonical revision records its own lifecycle state.

    A product surface often needs the effective state of the complete structural subtree rooted at that node.

    That subtree state is a derived projection, not a second lifecycle model. It uses PlanNodeStatus values and is rebuildable from exact node/relationship revisions.

    Conceptually:

    PlanNodeView
  node
  direct_status: PlanNodeStatus
  effective_status: PlanNodeStatus
  contains_ignored: bool
  contains_abandoned: bool
  child counts
  unsatisfied gate counts

    effective_status and aggregate flags are derived/cache data. They must not participate in the canonical revision identity of the node merely because descendants changed.

    A backend may materialize these values for efficient reads.

    9. Effective Status Rollup¶

    The derived rollup must be deterministic and backend-independent.

    The default precedence is:

    1. explicitly Abandoned node -> Abandoned
2. any required self/descendant Failed -> Failed
3. any self/descendant Running -> Running
4. any executable self/descendant Ready -> Ready
5. any unresolved self/descendant Planned -> Planned
6. completion policy and completion gates satisfied -> Completed

    The precise treatment of optional descendants is controlled by their gate/dependency policy, not by presentation order.

    A descendant abandoned because it was ignored does not automatically make the parent Abandoned.

    Instead the parent exposes a derived flag:

    contains_ignored = true

    Likewise a generic:

    contains_abandoned = true

    may be exposed when useful.

    The rollup rule may be extended later, but all backends and product surfaces must consume the same semantic definition.

    10. Incremental Rollup Is Derived Knowledge¶

    Reading the status of a top-level plan node must not require recursively walking every descendant every time.

    Backends may maintain materialized child-status counts or equivalent derived indexes:

    planned_children
ready_children
running_children
completed_children
failed_children
abandoned_children
ignored_descendants

    When one descendant changes, the backend may update only the affected ancestor chain and stop when an ancestor aggregate no longer changes.

    Typical update complexity should be proportional to tree depth rather than total subtree size.

    Database triggers are an allowed backend implementation when the database has suitable normalized/indexed rows to react to.

    However:

    trigger behavior is an optimization of a backend-neutral semantic rule, not the semantic definition itself.

    An in-memory backend, SQLite backend, server cache, or future database must produce equivalent effective status.

    Derived rollups are rebuildable and excluded from canonical identity computation.

    11. Summary Is First-Class Plan Knowledge¶

    A plan node should support a concise current summary independent of its purpose and final result.

    Keep these concepts distinct:

    purpose
  what the node is intended to accomplish

summary
  compact current understanding/progress/state

result
  durable outcome produced by successful execution

    The preferred target is a normal semantic Summary entity/relation rather than permanently embedding an unversioned string inside every plan node.

    Conceptually:

    PlanNode N
  --summarized_by--> Summary S

    A generated summary should identify the exact node/child/result revisions it summarizes so staleness can be determined precisely.

    Do not deterministically concatenate child summaries into a parent summary. Status rollup is deterministic; semantic summarization is interpretive derived knowledge.

    12. Evidence Is Referential and Exact¶

    Plan work may accumulate evidence before, during, and after execution.

    Evidence should normally reference existing durable semantic objects rather than copy opaque blobs into the plan node.

    Evidence sources may include:

    BranchResult
ValidationResult
Decision
Candidate / Migration / Workspace
EntityRevision
Snapshot
Artifact
HumanApproval
ExternalObservation
structured failure result

    Evidence associations may carry a small typed role such as:

    Supports
Contradicts
Informational

    Conceptually:

    PlanNode N
  --supported_by--> ValidationResult V1
  --contradicted_by--> ValidationResult V2

    If the association itself needs independent author/provenance/history/waiver semantics, represent that association as a first-class relation/entity.

    Evidence must remain exact-revision/snapshot aware where the source is versioned.

    13. Gates Are Independent Semantic Requirements¶

    A gate expresses a condition that must be satisfied before a node may enter a phase or be considered complete.

    A gate has independent identity because it may be inspected, revised, evidenced, failed, or waived.

    Conceptually:

    PlanGate G
  owner -> PlanNode N
  phase = Entry | Completion
  requirement = typed requirement
  waiver = optional explicit waiver

    Initial typed requirements should remain simple and queryable, for example:

    ValidationPassed(profile/reference)
EvidencePresent(kind)
DecisionResolved(decision)
HumanApproval(policy/role)
SemanticCondition(reference/predicate)
RequiredChildCompleted(child)

    Do not begin with a general arbitrary Boolean-expression language.

    Gate evaluation state is normally derived from canonical gate definition plus exact evidence:

    Pending
Satisfied
Failed
Waived

    A waiver is canonical knowledge and must retain who/what authorized it, why, and the relevant exact revision/provenance.

    Do not make a gate disappear merely because it was waived.

    14. Dependencies and Gates Serve Different Purposes¶

    Dependencies express ordering/readiness relationships between independently schedulable plan nodes.

    Gates express requirements on one node's entry or completion.

    Do not duplicate every dependency as a gate.

    The default readiness concept is:

    Ready(node) =
  direct node state permits execution
  AND all required dependencies are fulfilled
  AND all entry gates are satisfied or explicitly waived
  AND no active claim owns the node
  AND execution policy permits dispatch

    The default completion concept is:

    Completed(node) =
  required result contract is satisfied
  AND all completion gates are satisfied or explicitly waived

    A failed dependency remains a failed dependency; a gate must not silently reinterpret it as success.

    15. Decomposition May Create Completion Obligations¶

    Creating a structural child does not itself create a dependency edge.

    However, decomposition often means the parent cannot truthfully complete until required child work is complete.

    The semantic operation that decomposes a node should therefore distinguish required and optional child work.

    For required decomposition, the operation should normally create or update a completion obligation equivalent to:

    RequiredChildCompleted(child)

    For optional/informational decomposition, no such completion obligation is required.

    This keeps structural parentage distinct from dependency scheduling while preventing a parent from silently reaching Completed with known required child work unfinished.

    16. Failed Is Recoverable¶

    Failed records that the current execution path/attempt did not satisfy the node.

    It is not semantic destruction of the intended work.

    A failed node may later:

    Failed -> Ready -> Running -> Completed

    through an explicit retry/repair/resume operation.

    Recovery must not erase the failed attempt or its evidence.

    A failed node continues to block success dependencies until a later accepted successful result fulfills them or the plan is explicitly revised/waived according to policy.

    The same principle applies at plan level:

    Plan Failed

    means automatic progress stopped and explicit recovery/replanning is required. It is recoverable.

    Only plan states equivalent to completed success or explicit cancellation/abandonment should be treated as irreversible terminal outcomes by ordinary mutation guards.

    17. Execution Attempts Preserve Failure and Retry Provenance¶

    Once failure is recoverable, a durable plan node may have more than one execution attempt.

    The node identity represents intended work.

    Each attempt represents one concrete execution lineage.

    Conceptually:

    PlanNode N
  --attempted_by--> Attempt A1
  --attempted_by--> Attempt A2

Attempt A1
  branch -> B1
  claim/generation -> ...
  outcome = Failed
  failure/result evidence -> ...

Attempt A2
  branch -> B2 or resumed B1 according to policy
  outcome = Completed
  result -> BR2

    The existing session branch and execution records may provide most attempt provenance. Lower-level design should avoid inventing redundant objects when a typed relation to existing branch/claim/result entities is sufficient.

    The requirement is durable attempt history, not a specific extra Rust struct.

    18. Normal Plan Evolution Is Not Replanning¶

    A running plan is expected to grow as work reveals more work.

    Ordinary plan evolution may include:

    add next step
add structural child/decomposition
add dependency
add gate
attach evidence
update summary
change assignment before execution
retry failed node

    These operations do not require the plan to enter a special failed/paused replan mode merely because new knowledge was discovered.

    Replanning is reserved for structural replacement/invalidation such as:

    supersede obsolete work
remove or replace dependencies after changed assumptions
replace failed strategy with a different strategy
perform broader restructuring

    The current coordinator/mutation mechanism remains the owner of plan change authorization and concurrency.

    19. Keep the Existing Plan Mutation/Coordinator Mechanism¶

    Independent storage does not mean callers mutate plan objects directly in the database.

    Shared semantic/application operations remain the mutation boundary.

    Existing concepts equivalent to:

    add_node
add_dependency
set_assignment
start/claim node
settle worker
retry failed node
complete node
replan

    remain useful domain operations.

    Their implementation changes from mutating one in-memory aggregate for persistence to producing one atomic semantic change set over the independently stored plan entities/relations.

    One accepted mutation may update:

    one Plan revision when plan-level state changed
one or more PlanNode revisions
relation/dependency/gate/evidence revisions
execution-attempt/result references
derived rollup/index state
current snapshot/root

    The operation remains atomic at the application/storage transaction boundary.

    20. Plan Mutation Revision Remains Useful¶

    A plan may retain a monotonic mutation/coordinator revision used for:

    compare-and-swap
coordinator concurrency
client stale-write detection
operation ordering
inspection/debugging

    That revision is not the same thing as serializing a full copy of every node and dependency into the plan entity.

    Historical exact state is obtained from semantic revisions, relation history, change provenance, and snapshots.

    A lightweight plan mutation record may summarize why a plan changed without duplicating the whole graph.

    21. Storage and Indexes Must Remain Backend-Neutral¶

    Canonical plan knowledge belongs in the universal semantic revision/snapshot store.

    Backend-specific tables/indexes may accelerate:

    plan membership lookup
parent/child lookup
dependency traversal
ready-node lookup
active claim lookup
gate lookup/evaluation
rollup counts
contains_ignored / contains_abandoned

    Those indexes are derived/rebuildable unless a lower-level design explicitly identifies canonical relation state.

    Do not make SQLite table layout part of the public semantic API.

    22. Product Views Consume Shared Plan Views¶

    CLI, server, Rust client, web, integrated editor, TUI, and agents must consume the same plan semantics.

    A shared plan-node view may expose concepts equivalent to:

    node identity
exact revision
parent identity
direct status
effective subtree status
contains_ignored / contains_abandoned
summary reference/preview
assignment reference
branch/attempt references
dependency counts/blockers
gate counts/failing gates
evidence counts/result references

    Product surfaces do not recompute semantic rollups from visual rows.

    23. TUI Builds on the Upstream-First RPI Design¶

    Any terminal implementation of these plan semantics must build on the design in:

    • design/level-2/032. upstream first agent runtime and terminal product ownership correction.md;
    • design/level-3/148. rebuild scriberig semantic session plan and review surfaces as upstream tui components.md.

    The plan surface remains a Scriberig semantic component because upstream cannot know Scriberig plan meaning.

    It must render through upstream rpi-tui component/layout/focus/overlay/scroll/theme contracts after task 148 establishes that product framework.

    Do not introduce a parallel Ratatui shell, plan-only widget framework, terminal lifecycle, or plan-local event runtime.

    Useful plan presentation includes:

    direct/effective status
contains ignored/abandoned indicator
summary
blocked dependency reason
failing/pending gates
evidence/result counts
execution attempts and current branch
coordinator location

    Detail inspection should use upstream component/overlay/navigation primitives around shared Scriberig views and operations.

    24. Migration from Aggregate Session Plan Storage¶

    The current implementation may temporarily store complete sessions/plans as serialized aggregates.

    Migration to semantic entities must preserve existing stable plan/node identities and accepted results where possible.

    During transition:

    1. choose one authoritative representation for each operation path;
    2. avoid uncontrolled dual-write semantics;
    3. provide deterministic import/upgrade of legacy plan aggregates;
    4. prove restart/reconnect preserves topology, statuses, results, and coordinator safety;
    5. remove aggregate plan persistence after semantic-store conformance is proven.

    Compatibility serialization may remain at protocol boundaries as a projection. It must not remain canonical storage merely because older clients expect aggregate DTOs.

    25. Non-Negotiable Summary¶

    Future designs and implementations must preserve these rules:

    1. Plan and PlanNode have stable independent semantic identities.
    2. Meaningful node changes create immutable node revisions resolved by snapshots.
    3. The complete plan graph is not canonically one opaque serialized aggregate.
    4. Structural decomposition and dependency scheduling remain distinct relations.
    5. Dependency state with history/provenance is first-class relation/entity state.
    6. There is one PlanNodeStatus lifecycle vocabulary; no parallel work-state enum.
    7. Effective parent/subtree status uses the same status vocabulary and is derived/rebuildable.
    8. Derived rollups and ancestor counters do not contaminate canonical revision identity.
    9. Backends may use triggers/materialized indexes for incremental ancestor updates.
    10. Nodes support first-class summaries distinct from purpose and result.
    11. Evidence references exact durable semantic objects.
    12. Gates are typed independent requirements with explicit evidence and waivers.
    13. Dependencies and gates remain distinct concepts.
    14. Required decomposition normally creates an explicit completion obligation rather than an implicit dependency.
    15. Failed is recoverable; retries preserve prior failure provenance.
    16. Failed work never silently satisfies successful dependencies.
    17. Normal plan growth while running is ordinary evolution, not automatically a replan.
    18. Existing coordinator/application mutation semantics remain the only normal write path.
    19. Plan mutation revision may remain a CAS/coordinator mechanism without embedding the whole graph.
    20. All product surfaces consume shared semantic plan views/operations.
    21. TUI work extends the upstream-first rpi-tui design and task 148 rather than competing with it.
